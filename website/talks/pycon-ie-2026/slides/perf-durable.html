Scaling with concurrent writers

mongodRust server

secantusd-mdb as of 18 November 2026, default flags, against mongod 8.0.38; medians of three passes on a shared 8-vCPU droplet.
Versions from the same day's latency run, not from the concurrency data. Both are single-node replica sets.

Write throughput as writers are added: each point is documents per second, the median of three 30-second passes. mongod goes from 5.9k docs/s with one writer to 19.7k with eight; our default from 4.0k to 10.2k. So mongod is about 1.5× ahead with one writer and 1.9× ahead with eight, and both keep climbing: no cliff. Both are fully durable: single-node replica sets whose default writes wait for the journal.

The passes are noisy on a shared-CPU droplet: at eight writers they ranged 9.8k–14.6k for us and 16.2k–29.1k for mongod. Read the shapes, not the last digit.

The benchmarking lesson: over a real network, one server droplet and two client droplets, we reach 0.51× of mongod's throughput. The same build first scored 0.14×, which looked like a huge regression. It wasn't: our server, as a replica-set primary, waits for the journal on every default write, and the benchmark had compared it against a standalone mongod that never waits. Put mongod in the same mode and it loses about half its throughput. Compare like with like.

If asked about the faster async stack: it is left out. That run used it on a store whose data tables were not logged, where a crash lost acknowledged writes; the server now refuses that combination, and the stack comes back once re-measured properly.
