Benchmarks

Measured, not promised

Every number on this page is measured on the same machine, through the same pymongo client, against the same on-disk WiredTiger storage — with real mongod as the reference — both measured against mongod 8.0.32 on a dedicated cloud instance, as part of cutting the release they describe. Two dimensions: per-operation latency (one client, nine workloads) and throughput under concurrent writers (1–8 parallel writer processes). Both harnesses ship in the repo; both tables regenerate with one command.

Per-operation latency

“Rust DB” here is the Rust MongoDB server — these harnesses drive the MongoDB wire protocol, so the Rust PostgreSQL server is measured separately, against PostgreSQL. Bar length is how many times slower than mongod each server is — median of five runs per workload, 10,000-document dataset, end-to-end through the wire protocol and driver.

The short version: the Rust DB runs at 1.2x–3.6x of mongod per operation (medians of 15 interleaved repetitions, 2026-11-18). Reads, update_many and the change-stream drain are at 1.2–1.4x, and delete_many and aggregation are at the high end. Both servers run as a single-node replica set, so a default write waits for the journal on both. Earlier tables compared against a standalone mongod, which does not wait for the journal, so they are not comparable with this one. Throughput under concurrent writers

Does throughput grow with writers? Each line is a server's aggregate write throughput in documents per second — N writer processes each streaming insert_many batches for 30 seconds against their own collections.

Two servers, honestly told, both as a single-node replica set with journaled default writes (2026-11-18). mongod scales furthest: 3.4x its own single-writer rate at eight writers. That is its C++ scheduler above WiredTiger doing its job. The Rust DB scales monotonically: 1.5x at two writers, 2.1x at four and 2.6x at eight (10.2k docs/s), with no cliff. The per-collection write-lock split, RecordId keying, a key-only oplog prune and append-tuned oplog btrees removed the old peak-then-collapse shape. The flattening that remains is WiredTiger itself: cache eviction and checkpoint pressure in one embedded connection, not a SecantusDB lock. The opt-in async + non-logged oplog stack is not charted: this run used it on a store whose data tables were not logged, where a crash lost acknowledged writes. The server now refuses that combination, and the stack returns once re-measured on logged data tables. Passes on a shared droplet are noisy, so read the shapes. The full concurrency story →

What to make of it

The trade SecantusDB started from was conformance and WiredTiger durability over raw speed. The Rust server closed most of that gap: at 1.2x–3.6x of mongod per operation, both durable, and scaling monotonically with writers, per-op latency has stopped being the reason to reach for a real mongod instead. What remains a reason is everything single-node scope excludes — replica sets, sharding, a cluster to fail over. And because the wire protocol is identical, moving between them is a connection-string change.

Caveats that apply to every number here: one machine (a dedicated 8-vCPU cloud instance, not a laptop — a laptop moves every column at once and nothing in the output says so), no network, no concurrent readers mixed with writers, dataset that fits in cache. The harnesses (bench.compare_servers, bench.concurrency) ship in the repository — run them on your own hardware and workload before drawing conclusions that matter.
