SecantusDB Rust PostgreSQL server

The same Rust storage as the MongoDB server, answering the PostgreSQL wire protocol instead. psql, psycopg, SQLAlchemy and any other stock PostgreSQL client connect and run real SQL — against the same WiredTiger home a MongoDB driver writes to. It is the newest of SecantusDB's servers — prebuilt for Linux x86_64 and macOS arm64, buildable from source anywhere else — and it is scored by psycopg's own test suite rather than by our own expectations.

Early access The Rust PostgreSQL server is the youngest thing in the project, and it is a server for tests. A role that has a password must prove it with SCRAM-SHA-256, and a wrong password is refused. A role with no password, and a user name the server has never seen, both connect without one. TLS is off unless the server is started with a certificate, and a client that does not ask for it is served in the clear. Keep it on loopback, and keep production data out of it.

Why a PostgreSQL server in a document database

Because the store underneath was never document-shaped by necessity — it is WiredTiger, the same B-tree engine MongoDB ships, and a row is as natural in it as a document. SecantusDB has served both protocols over one store since the Python implementation, where a pymongo-written collection is queryable as a table with no CREATE TABLE at all; this is that idea with a Rust server under it.

PostgreSQL's own parser

SQL is parsed by libpg_query — the real PostgreSQL grammar, vendored and compiled in — so a statement means here what it means there. No approximation layer inventing its own dialect.

One storage format

Tables live in the same WiredTiger home, in the same on-disk format every SecantusDB server uses. The Rust and Python PostgreSQL servers read and write each other's store — pinned in both directions by a regression test, because getting it wrong would be silent corruption rather than an error.

The extended protocol, properly

Parse / Bind / Describe / Execute, prepared statements, portals, and binary parameter and result formats. Not a simple-query shim — it is what every real driver actually speaks.

Real transactions

BEGIN / COMMIT / ROLLBACK backed by storage transactions, savepoints, and two-phase commit: PREPARE TRANSACTION makes the work durable and invisible, and a prepared transaction found on disk at startup is replayed when it is committed.

Error codes measured, not guessed

Every SQLSTATE, notice and detail line on the supported surface was measured against a live PostgreSQL 16 and matched — down to the DETAIL: Key (id)=(1) already exists. on a unique violation.

Scored by someone else's tests

psycopg 3's own tests run against it unmodified. Of the 5,731 that ran in the last measurement, 5,544 pass and none fail; the rest are tests psycopg itself skips or expects to fail.

What it speaks today

Not yetTLS client certificates and SCRAM channel binding: a client set to channel_binding=require is refused by its own library. A way to refuse a connection that is not encrypted. A password for every connection: a role without one, and an unknown user, are let in. EXPLAIN shows the plan's shape with every cost at zero. A parenthesised step inside a ROLLUP or CUBE, as in rollup ((a, b), c), is refused. A foreign table can be declared and not read, because there is no foreign-data wrapper behind it. A collection written by a MongoDB driver is not visible as a table; a table written here does read back through the Rust MongoDB server as a collection. There is no Windows binary. Replication and standbys are out of scope for a single-node server

Where that leaves it, measured on 2026-10-10 on macOS against the code of 0.1.0-beta.9, with psycopg 3.3.4: of the 5,731 tests that ran, the server passes 5,544 and fails none. psycopg skips 149 that need something out of scope and marks 34 as expected to fail; 4 more that it expects to fail pass here. Another 58 are left out on macOS, as psycopg's own CI leaves them out there: the tests that need its proxy fixture or assert wall-clock budgets of a few milliseconds, and two more that fail the same way against PostgreSQL itself. Whole type suites that a real client leans on — uuid, inet, enums, composites, ranges, COPY, server cursors — pass end to end. We are not publishing a head-to-head against the Python SQL server here: its last report predates the widening of this gauge, so the two ran different suites and the comparison would flatter one of them by accident.

Measured against PostgreSQL itself

Not against our own expectations: a release build of secantusd-pg and PostgreSQL 16 at its defaults, on the same 16-vCPU DigitalOcean droplet (ext4), every commit synced to disk on both. PostgreSQL is faster on every row: 1.3x to 1.7x on durable writes and 1.3x to 1.4x on reads by primary key, through eight clients. Both servers scale with clients, and eight clients writing one shared table cost us 8% against eight writing a table each. These are prepared statements, measured before 0.1.0-beta.8. On this droplet a statement sent as text with a different literal each time was where we were furthest behind: 380 microseconds against PostgreSQL's 128 for one row by primary key. 0.1.0-beta.8 plans such a statement once per shape. On a Mac, with the released binaries, that took it from 111 microseconds to 43, against PostgreSQL 15's 40; it has not been measured on the droplet yet.

Get it

A prebuilt archive for Linux x86_64 and macOS arm64, or from source on any other platform — there is no Windows build yet. Each archive ships with a .sha256. Binary releases are GitHub pre-releases, so they never show as “Latest” — the link below goes straight to the tag.

Prebuilt binary

Download, extract, run. No Rust toolchain, no Python, and since 0.1.0-beta.2 nothing but the platform's own C runtime — zlib and lz4 are linked in.

# from the release page, then:
./secantusd-pg ./data 127.0.0.1:5432

From crates.io

The secantus-pg crate builds the server and the WiredTiger it links. It needs a Rust toolchain, CMake, a C compiler and libclang. The binary takes a storage directory and an address.

cargo install secantus-pg --version {{ SECANTUS_PG_BINARY_TAG | replace("secantusd-pg-v", "") }}

secantusd-pg ./data 127.0.0.1:5432

Or from a checkout: git clone --recurse-submodules, then cargo build --release in crates/secantus-pg.

Connect

Any stock PostgreSQL client. The postgres role starts with no password, so none is asked for; give a role one with ALTER ROLE ... PASSWORD and it is checked from then on.

psql -h 127.0.0.1 -p 5432 -U postgres

# or from Python
import psycopg
psycopg.connect("host=127.0.0.1 port=5432 user=postgres")

For TLS, start the server with a PEM certificate and its key, and the client can ask for it:

secantusd-pg ./data 127.0.0.1:5432 \
    --tls-cert-file server.crt --tls-key-file server.key

psql "host=127.0.0.1 port=5432 user=postgres sslmode=require"
