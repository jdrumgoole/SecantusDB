### The ingress rate limiter comparison no longer depends on the client's load

The test that compares which of six simultaneous connections each server answers, with the ingress connection rate limiter at one a second, now stops the server while the six connect, so they reach it together whatever the load.

#### Fixed

- Fixes RM-372 (`tests/backlog/test_rm_001_028.py::test_ingress_rate_limiter_admits_queues_and_closes`).
  The test failed in CI twice (pg-batch PR #3036, run 45834896035, job 139961032166; rm-batch PR #3073, run 45959038413, job 140372204555) because six client threads under load did not connect within one second, so mongod's and this server's answers differed in a wait. It now stops each server (SIGSTOP) while all six connect and send `hello`, then continues it (SIGCONT): the kernel holds the six in the listen backlog and the server accepts them together. Every wait is measured from the SIGCONT in one thread, and the two servers' answers are still compared exactly, with no retry.
  A first version of this (e663afaaa, reverted in b2c5a42b6) failed on Linux CI (PR #3076, run 45985326929, job 140459373674): the test's own client lost its connection to this server, and the limiter was left on for five later tests. The cause was the server, not the client: see RM-836. The test also no longer puts its own traffic in the limiter's path. It sets and restores the limiter's parameters on a raw connection opened before the limiter is turned on, and if that connection is gone it opens a fresh one every 1.1 s, as the bucket refills, until the parameters are back (a minute at most, then it fails loudly), so a failing test can never leave the limiter on for the next.
  Evidence: on macOS 14 of 14 runs passed with 14 CPU burners running (load average 19.7) and 8 of 8 with 6. On Linux (a 2-vCPU VM, `mongod` 8.2.11 and `secantusd-mdb` built from this tree, both aarch64) the six answers matched `mongod`'s on 5 of 5 runs with 6 burners (load average 4.9), and also against the released x86_64 0.5.3-beta.199 under emulation, where the control connection is closed by the stop and the restore used a fresh connection. The same test fails, on its first answered-versus-closed connection, against a server whose limiter admits every connection. A restore with the control connection gone succeeded after one retry on both servers.
