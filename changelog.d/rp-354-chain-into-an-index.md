### EXPLAIN estimates a join of three or more tables whose last is read through its index

A nested-loop join of three to eight tables used to be priced only when none of them had an index. Now one with an index is priced too, as long as it has no filter of its own and its clauses link it to only one other table. That table's rows then parameterize the indexed table's scan as the loop's inner. PostgreSQL builds that index path once, counting its loops by the linking table's own rows (`get_loop_count`), whichever lower join holds that table. Each join that holds the table weighs the path against the plain and materialised inners. The Memoize over it is called once per row of the lower join, its key's distinct count read from the linking table's statistics. PostgreSQL 15.19 prints `select * from e join e e2 on e.a < e2.a join k on e2.a < k.a` (1,000 analysed rows each, `k.a` the primary key) as `Nested Loop (cost=0.29..2404325.85 rows=111111000 width=21)` over the lower loop and a `Memoize` keyed by `e2.a` over `Index Scan using k_pkey on k`, `Index Cond: (a > e2.a)`. This server now prints the same plan. It also matches four tables with the last indexed, two indexed tables each linked to the first, and a `<>` that moves into the index scan with the index qual.

#### Fixed

- EXPLAIN of an inner join of three to eight tables by `<`, `<=`, `>`, `>=` or `<>` clauses, where an indexed table without a filter is linked to one other table, prints PostgreSQL's parameterized Index Scan, its Memoize, and the costs, rows and widths of every join (RP-354, part).
