### Rust storage — RecordId step 2/3 (index entries + tailable cursors) + oplog raw-splice, reviewed in full

The cycle's real content is three related Rust-storage changes, all inside
`crates/secantus-storage/src/lib.rs` (+`secantus-storage-adapter`,
`secantus-commands/{admin,find,storage}.rs`, `secantus-core/diff.rs`):

- **`4af58aae` (RecordId step 2)** — index entries now carry the doc's
  RecordId (8-byte big-endian, fixed-width) instead of its `id_key`, removing
  the `id_key → _id index → RecordId` hop from every IXSCAN fetch
  (`pack_entry`/`unpack_entry`, `write_index_entries`,
  `delete_index_entries`, `index_entry_diff`, `unique_conflict`, rename). Read
  the full diff end to end:
  - **Fail-closed migration, not silent misread.** A store written by a
    pre-step-2 build has index-entry payloads whose trailing half is an
    `id_key` (variable length), not an 8-byte RecordId. `unpack_entry` now
    returns `None` for any trailing half that isn't exactly 8 bytes rather
    than reinterpreting those bytes as a RecordId — and `Storage::open`
    additionally refuses to open such a store outright
    (`reject_legacy_index_entry_format`, gated on a new `entryFormat`
    catalog marker since the WT `key_format` itself doesn't change). Both the
    "refuse at open" path and the "defensive `None` even if something slipped
    past that gate" path are covered by dedicated tests
    (`open_rejects_legacy_index_entry_format`,
    `unpack_rejects_a_step1_entry`). This is the same pattern step 1 (doc-table
    RecordId keying, reviewed 2026-07-24) used, applied consistently.
  - **Unique-conflict self-exclusion correctness.** `unique_conflict`'s
    `is_self` check changed from `exclude_id_key == Some(row_id)` to
    `row_id.is_some() && exclude_recordid == row_id` — deliberately treating a
    (structurally-impossible-post-migration-gate) `None` row as "not me"
    rather than a wildcard match, so a corrupt/legacy row can only ever
    produce a false *conflict* (fails safe: rejects a write) never a false
    *pass* (silently permits a duplicate). Correct direction for a uniqueness
    check.
  - **`escape_kb`/`ENTRY_SEP` collision analysis re-verified.** The packed
    payload is still `escape(kb) + \x00\x00 + <trailing>`, and the trailing
    half is now fixed-width 8 bytes and taken whole rather than split on a
    second separator search — the "RecordId bytes routinely contain a bare
    `\x00\x00`" case (every small RecordId does, big-endian) is exercised by
    `unpack_splits_on_first_separator` and doesn't reopen the ambiguity the
    escaping scheme exists to prevent, because the split point is still
    "first occurrence in the escaped `kb` half," which can't produce one.
  - **Collection rename (`renameCollection`) now rebuilds index entries
    instead of copying them.** Copying would have silently produced index
    entries pointing at RecordIds that don't exist in the destination
    (rename re-mints every RecordId) — a correctness bug the commit avoids by
    decoding each moved doc and calling `write_index_entries` fresh against
    the destination's RecordIds. Reviewed and sound; no wire-reachable path
    was left that could copy stale entries.
- **`6f3a8e05` (RecordId step 3)** — capped-collection tailable cursors
  (`find(tailable: true)`) now track position by RecordId
  (`scan_docs_after_recordid` / `collection_min_recordid` /
  `collection_max_recordid`) instead of `id_key`, fixing a real
  pre-existing correctness gap: `id_key` order only equals insertion order
  for monotonic `_id`s, so a capped collection with custom non-monotonic
  `_id`s could previously miss follow-up inserts in a tailable cursor or
  fail to detect `CappedPositionLost` on rollover. New trait methods on the
  `Storage` interface (`secantus-commands/src/storage.rs`) default to
  `Ok(Vec::new())`/`Ok(None)` for backends that don't implement them —
  reviewed, this is a safe default (an unimplemented backend simply yields no
  tail rows / reports an empty collection, never panics or returns
  unvalidated data).
- **`3a36674b` (oplog raw-splice)** — the hot CRUD oplog-emit path
  (`oplog_entry_crud`) now builds `{op, ns, ui, o, o2}` by splicing
  already-encoded BSON bytes (the doc-table `blob`, the tiny `{_id}` `o2`)
  into a `RawDocumentBuf` instead of re-encoding an owned `bson::Document`.
  Checked specifically for the class of bug this pattern invites (unvalidated
  raw-byte splice on a wire-adjacent path): both `o` and `o2` inputs
  originate from bytes the *server itself* already produced and validated
  this same request (`encode_doc`/the stored doc blob) — never unvalidated
  wire bytes spliced straight through — and `RawDocument::from_bytes` is
  still called on each before splicing, so a corrupt internal blob would
  surface as a `StorageError::Bson`, not silent malformed output. No `unsafe`
  in this path.
- **Grep for new `unsafe`/`.unwrap()`/`.expect()`/`panic!` outside test code**
  across every changed Rust file this cycle (`git diff 00519352..HEAD --
  'crates/**/*.rs' | grep -nE '^\+.*(unsafe|\.unwrap\(\)|\.expect\(|panic!)'`,
  then checked each hit's line against `mod tests` boundaries): every hit
  outside `mod tests` is `ui.as_ref().unwrap()` inside the three oplog-entry
  call sites — and that exact pattern was already present on the *removed*
  side of the same diff hunks (i.e. carried over verbatim by the refactor,
  not newly introduced). No new production-path `unwrap`/`panic`/`unsafe`
  landed this cycle.

### Python storage — oplog prune is now O(deleted), not O(oplog size)

`e6d17afd` rewrites `_prune_oplog_locked` to stream only the oldest oplog
entries (`_iter_oplog_oldest`, a lazy k-way merge generator) and stop at the
first entry neither retention criterion dooms, using a new in-memory
`_oplog_live_count` (seeded by a one-time key-only count on open, maintained
incrementally on every emit/prune) to make the entry-cap decision without a
full scan. This is a correctness-adjacent change to the retention logic this
checklist's §7 explicitly cares about (oplog growth bounding), so it got a
full read rather than a skim:

- **Retention-bound equivalence.** The old two-phase algorithm (scan
  everything, compute `doomed` from both criteria, delete) and the new
  streaming algorithm (walk oldest-first, doom entries until neither
  criterion applies, stop) are logically equivalent *because* both criteria
  only ever doom a prefix of the seq-ascending oplog: time retention dooms
  every entry older than the cutoff (seq is minted jointly-monotonic with
  `ts`, so "older than cutoff" is exactly an oldest-prefix), and the entry
  cap dooms the oldest surplus by construction. The new code's per-entry
  `over_cap = (live - len(doomed)) > self.oplog_max_entries` check correctly
  recomputes against the shrinking live count as entries are added to
  `doomed` within the same pass.
- **Reopen correctness covered by test.** `_oplog_live_count` is seeded from
  a real on-disk count on every `Storage.__init__`, not just carried in
  memory — `test_live_count_is_reseeded_on_reopen` explicitly asserts a
  fresh instance recovers the true count rather than starting at zero, which
  would have made the first prune's cap decision wrong (either failing to
  trim, i.e. unbounded growth, or over-trimming). This is exactly the drift
  class worth checking for a project rule that treats an oplog-retention bug
  as a data-integrity issue, not a performance footnote.
- **Streaming-scope test.** `test_prune_reads_only_the_doomed_prefix` spies on
  the generator to assert a 100-row prune over a 600-row oplog reads ≤102
  entries, confirming the "never the whole oplog" claim empirically rather
  than by inspection alone.
- No lock/threading change: `_prune_oplog_locked` is still called only under
  `self._lock` (unchanged), so the incremental `_oplog_live_count` mutation
  has no new concurrency surface.

Reviewed and sound. No finding.

### W2 (carried forward, still open — 2nd consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24
