## 🟡 INFO (Best-practice recommendations)

- **RM-365's session-pool `Drop` and `reusable()` gate, read in full**
  (`crates/secantus-storage/src/lib.rs`, `OpSession::Pooled` and its `Drop`
  impl at the top of the file; `crates/secantus-wt/src/lib.rs:745-749`'s
  `Session::reusable`): a pooled autocommit session is returned to
  `Storage::op_pool` only when it has no transaction running, no
  `cursor_config` set, and no pending `txn_end` callbacks — otherwise it
  falls through and closes like an unpooled session always did. The pool is
  capped at `OP_POOL_MAX = 64` (excess sessions close rather than growing
  the pool unboundedly), and `Storage::close()` clears it **twice**: once
  before the background compaction/pruner/checkpoint threads are stopped
  (matching the existing `txn_session_pool` pattern, with the same
  documented reason — `conn`'s `Arc` must not reach zero before a pooled
  session holding raw WiredTiger pointers closes), and again afterward,
  because those background threads (not ordinary connection threads, which
  `RunningServer::stop` has already drained by this point per the inline
  comment) could park a session into the just-cleared pool while they wind
  down. This reasoning is sound and mirrors the pre-existing
  `txn_session_pool` close ordering rather than introducing a new teardown
  race. A session whose stat-collection `Err` fires in `Drop` is dropped
  rather than pooled (not a silently-corrupted entry reused later). No
  wire-reachable input selects which session comes out of the pool or
  decides pool size — the pool is a plain LIFO stack keyed on nothing
  attacker-controlled — so this is not a cross-connection data-leak
  surface (a WiredTiger session carries no authentication or tenant
  context in this single-process, single-store design).
- **RM-366's new step-up collections, confirmed unreachable from the wire**:
  `record_session_state_collections` and `record_sessions_collection_ttl`
  (`cluster_admin.rs`) are called only from `secantus-server`'s `bind()` at
  process start and from the internal logical-session-cache refresh
  (`logical_sessions.rs:165`) — never from a dispatched command — so the new
  `config.system.indexBuilds` / `analyzeShardKeySplitPoints` /
  `sampledQueries` / `sampledQueriesDiff` collection creation is not
  attacker-triggerable at a time of the attacker's choosing, and the TTL
  index each gets (`expireAfterSeconds: 0` on `expireAt`) matches the
  existing TTL-pruning discipline this project already applies elsewhere.
- The carried-forward INFO notes from prior cycles (unbounded
  `atClusterTime` wait, `snapshot::read_point`/`check_at`'s type-mismatch
  fallback, the `BinDataOrder` thread-local, synchronous index-rebuild-at-
  open latency, stale comments referencing deleted workflows, the unbounded
  `planCacheSetFilter` filter table, `opclasses.rs`'s unguarded `args[0]`
  downgrade, `applyOps`-of-`applyOps` recursion, `killOp`'s self-vs-other
  distinction, the `rustls-pemfile` RUSTSEC-2025-0134 pin, and the two
  cryptography CVE identifiers) are unchanged — none of their referenced
  files appear in this window's diff.
