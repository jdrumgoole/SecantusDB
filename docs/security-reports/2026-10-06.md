## 🔴 CRITICAL (Immediate action required)

### 1. `pymongo`/`bson` is pinned at a version vulnerable to 4 disclosed CVEs, including a heap out-of-bounds write reachable from the exact codec the wire layer is built on

`uv.lock` pins `pymongo==4.17.0` (verified directly: `grep -A2 'name = "pymongo"' uv.lock`); `pyproject.toml`'s floor (`pymongo>=4.6`) does not exclude it. PyPI's current release is `4.18.2`. Confirmed live via WebSearch against MongoDB's own advisory feed and the PyMongo 4.18.2 release notes:

- **CVE-2026-96749** (CVSS 8.4, GHSA-v4x9-3549-crwv): heap out-of-bounds write via signed 32-bit integer overflow in the native BSON **encoder**'s buffer-size guard — the overflow check itself is written in a form whose behavior the C standard leaves undefined. A party with no privileges who can get a large-enough value encoded into a document may write outside an allocated buffer; MongoDB's own advisory notes this opens toward arbitrary code execution if the attacker can also influence memory layout. Fixed in 4.18.2.
- **CVE-2026-88029**: GridFS ID matching used a non-exact match. Fixed 4.18.1.
- **CVE-2026-96748** (CVSS 6.5): connection-string host injection via percent-decoding applied before the host list is split on its delimiters. Fixed 4.18.2.
- **CVE-2026-96747** (CVSS 5.3): a KMS endpoint ending `.sock` was accepted and forced onto `AF_UNIX`, letting a party who can write to the key vault redirect the driver's KMS connection to an arbitrary local Unix socket. Fixed 4.18.2.

This sits squarely in this project's own stated threat model: `bson` is the codec `src/secantus/{wire,storage,commands,query,expressions,aggregate,...}.py` use pervasively to decode attacker-controlled wire bytes and re-encode outgoing documents and oplog/change-stream entries. CVE-2026-96749 in particular is a memory-corruption bug (CWE-190) in that exact encoder, with the vulnerable version sitting in the lockfile today.

**Fix:** bump the `pymongo` floor to `>=4.18.2` in `pyproject.toml`, re-lock (`uv lock`), re-run the full suite. This is a one-line dependency bump, not a design change.

**New finding — not a duplicate of any tracked issue.**

## 🟠 WARNING (Address within 1 week)

### 2. Rust MongoDB server has no connection cap, no write-timeout, and `stop()` doesn't force-close live sockets — unbounded resource exhaustion plus a shutdown-time storage race

Three compounding gaps in `crates/secantus-server/src/lib.rs`, all confirmed absent by direct grep (`max_connections`/`MAX_CONNECTIONS`/`set_write_timeout` — zero hits in the crate):

- **No connection cap.** `accept_loop` (`lib.rs:417-452`) spawns one OS thread per `listener.accept()` unconditionally — no `max_connections`-style limit exists anywhere in `config.rs`/`args.rs`/`lib.rs`. The Python server has an explicit, enforced `DEFAULT_MAX_CONNECTIONS = 1000` (`src/secantus/server.py:70`, confirmed present) that refuses sockets over the cap; the Rust server has no equivalent. A client opening thousands of raw TCP connections (no auth, no valid frame needed) exhausts OS threads/fds/memory.
- **No write-timeout.** Only `set_read_timeout` is ever called (`lib.rs:459-464`); `set_write_timeout` is never called anywhere in the crate. Every reply path (`write_op_msg`, the streaming writer, `send_bad_value`) calls `stream.write_all(&frame)` on a socket with no write deadline — a peer that stops reading wedges that thread in `write_all` forever. Python's socket-wide `settimeout(client_idle_timeout_s)` (`server.py:420`) covers `sendall` too, so the equivalent Python path times out within `client_idle_timeout_s` (default 300s).
- **`stop()` doesn't force-close sockets.** `RunningServer::stop()` (`lib.rs:276-291`) polls for threads to drain for up to 10s and then **gives up and returns regardless**, by the code's own comment, to avoid hanging shutdown on a wedged thread — but the only place any socket is force-`shutdown()`'d is the `killOp` command path, which `stop()` never invokes. A thread wedged by the write-timeout gap above can therefore outlive `stop()` and later `Drop` its `Arc<Storage>` handle against a directory the caller has since removed/reopened — the exact "WT_PANIC when WiredTigerHS.wt vanished mid-checkpoint" hazard this project's own `CLAUDE.md` names as a serious data-integrity failure mode, now reachable from a network peer rather than only a test-internal race. Python's drain (`server.py:307-348`) is actually effective here: it calls `sock.shutdown(SHUT_RDWR)` on every tracked connection, which does unblock a thread parked in `recv`/`sendall`.

Combined: a handful of connections that each send one cheap command and then stop reading pin threads indefinitely, and a shutdown racing those threads risks real storage corruption, not just a hung process.

`crates/secantus-server/src/lib.rs` (accept_loop, stop(), write paths).

**New finding.**

### 3. Insufficient ReDoS guard on MongoDB `$regex` family (Python server)

`_MAX_REGEX_PATTERN_LEN = 1000` (`src/secantus/query.py:1418-1433`, mirrored in `src/secantus/expressions.py:2670-2691` for `$regexMatch`/`$regexFind`/`$regexFindAll`) caps **pattern length** only. Classic catastrophic-backtracking patterns (`(a+)+$`, etc.) are short, so the length cap does nothing against them; Python's `re` has no built-in match timeout. A single `find`/`aggregate` with such a pattern matched against an existing field value (up to the 16MB document limit) can pin a CPU core. This is distinct from already-tracked **#1707**, which covers the SQL-side `regexp_*` functions — this is the MongoDB-wire-side `$regex` family, which is not yet tracked.

**New finding.**

### 4. `getMore` cursor ownership is namespace-only, not per-connection — a monitoring-privilege principal can read another connection's in-flight results

`src/secantus/commands.py:6855-6870`'s `getMore` ownership check only compares the claimed `collection` against the cursor's stored namespace; `cursors.py`'s `_Entry` carries no owning-connection id at all. `getMore` itself is exempt from the RBAC action-table check (`_NO_PRIVILEGE_COMMANDS`). Meanwhile `currentOp` (`commands.py:1224-1286`) exposes every live cursor's id and namespace to any principal holding only the cluster-wide `inprog` action — no privilege on the target collection required. Chained: a principal authorized only to monitor the server (an `inprog` grant) can discover and then drive another connection's open cursor via `getMore`, reading its in-flight query results — something real `mongod`'s per-user cursor binding prevents. Requires `--auth` plus an `inprog` grant (or guessing a 63-bit cursor id).

**New finding.**

### 5. `insert`/`update`/`delete` enforce only the lower write-batch-size bound, not the upper one `bulkWrite` enforces

`commands.py:2480-2492` (insert), `:3015-3024` (update), `:3760-3767` (delete) each reject an empty array but never check an upper bound. `bulkWrite` does enforce one (`_BULK_WRITE_MAX_OPS = 100000`, `commands.py:3387,3540-3546`), and the server advertises `maxWriteBatchSize: 100000` in `hello` — so a single plain `insert` can carry many millions of minimal documents up to the 48MB message cap, well past the bound the server itself claims to honor, inflating per-request CPU/memory.

**New finding.**

### 6. `CursorRegistry` has only a global cursor cap, not a per-connection one

`DEFAULT_MAX_CURSORS = 10_000` (`src/secantus/cursors.py:21-25`) is shared across every connection. A single connection repeatedly opening small-`batchSize` finds (optionally `noCursorTimeout: true`, which also exempts a cursor from TTL pruning) can fill the entire registry, denying every other connection the ability to open a cursor.

**New finding.**

### 7. Admin UI renders a raw credentialed connection URI into page HTML, despite already computing a scrubbed one

`src/secantus/admin/routers/server.py:43-53` passes both `uri` (raw, with password) and `display_uri` (scrubbed) per saved target to the template; `src/secantus/admin/templates/pages/server.html:121,125` emits the raw form: `<input type="hidden" name="uri" value="{{ t.uri }}">` (confirmed by direct read of both files). The plaintext credential lands in the DOM / page source / browser cache on every visit to `/server`, even though `display_uri()` is already called and available for exactly this purpose elsewhere on the same page. Directly violates this project's own stated requirement ("must not log or render stored URIs with embedded credentials").

**New finding.**

### 8. Incomplete fix of the embedded-NUL `cstr()` panic (#139) — several secondary namespace fields still unguarded

`crates/secantus-wt/src/lib.rs:568-570`'s `cstr()` panics via `.expect()` on any string containing an embedded NUL (legal inside a length-prefixed BSON string). The #139 fix added `nul_in_namespace()` and wired it at the dispatch-level top-value db/collection-name check and at the `createIndexes`/`dropIndexes` index-name sites — but not at: `$lookup`'s `from` (`crates/secantus-commands/src/aggregate.rs:1206`), `$graphLookup`'s `from` (`:1381`), `$unionWith` (`:1543,1546`), `$out`/`$merge` targets (`:2171,2176-2177`), or `renameCollection`'s `to` field (`crates/secantus-commands/src/admin.rs:1784-1800` — note the *source* collection name of `renameCollection` IS covered by the top-level check; only `to` is missed). Repro shape: `{aggregate: "validColl", pipeline: [{$lookup: {from: "evil\u0000coll", ...}}], cursor: {}}`.

Kept at WARNING rather than CRITICAL because two existing defenses limit the blast radius: `secantus-server`'s dispatch wraps every call in `catch_unwind` (explicitly citing #139) and replies with a generic `InternalError` instead of dropping the connection, and the codebase's consistent `.lock().unwrap_or_else(|e| e.into_inner())` mutex-poison recovery stops the panic from cascading to other requests. Still, it's an incomplete fix of a documented, named hazard.

**New finding — extends the already-fixed #139, not itself tracked.**

### 9. Rust PostgreSQL server has no `catch_unwind` equivalent at its dispatch boundary

`crates/secantus-server/src/lib.rs:916-925` explicitly wraps MongoDB-server dispatch in `catch_unwind`, citing parity with the Python server's catch-all. `crates/secantus-pgserver` has no equivalent anywhere (`grep -rn catch_unwind crates/secantus-pgserver/src` — no matches); each connection is its own `tokio::spawn`'d task with no awaited `JoinHandle` and no panic boundary. Tokio keeps a panicking task from crashing the process, but with no catch_unwind, a panic reachable from a crafted statement/parameter just drops that one connection abruptly instead of returning a PostgreSQL-shaped error reply — a divergence from the "same error-surfacing discipline on both servers" property this project requires. (The ~37k-line `secantus-pgserver/src/lib.rs` and ~32k-line `secantus-pgplan/src/lib.rs` were spot-checked rather than exhaustively audited for the underlying panic; every site sampled was correctly guarded, but the missing boundary means any future miss degrades worse here than on the Mongo server.)

**New finding.**

### 11. Unchecksummed tarball fetch in a wheel-build script

`tools/build_lz4_macos.sh` downloads `lz4` v1.10.0 source via `curl -fsSL https://github.com/lz4/lz4/archive/refs/tags/v${LZ4_VERSION}.tar.gz` and statically links it into the macOS wheel with no checksum or signature verification. ### 14. `claude.yml` has no authorization gate on who can trigger it

The `if:` condition only checks `contains(..., '@claude')` in a comment/issue/review body or title — any user who can comment on an issue or PR (any public GitHub user, on a public repo) can invoke the agent. The job runs with `id-token: write` plus `contents`/`pull-requests`/`issues: read` declared, but (per this project's own adjacent comment in `security-review.yml`) `id-token: write` lets `claude-code-action` mint a GitHub App installation token whose *effective* permissions come from the App installation, not the declared YAML scope — which is exactly why `security-review.yml` deliberately omits `id-token: write`. `claude.yml` does not have that safeguard. This may be the standard upstream pattern for this action, but the review spec explicitly asks to hold this file "to the same standard" as `security-review.yml`, so it's worth tracking.

**New finding.**

## 🟡 INFO (Best-practice recommendations)

- Python server has no cross-connection allocation budget for in-flight message bodies (Rust has an explicit 512MB `AllocBudget`; Python only bounds a single message to 48MB). Bounded in practice by the 1000-connection cap, but a divergence between the two servers on a security-relevant property worth closing for consistency.
- Rust's raw-insert fast path (`crud.rs:113-173`) defers full BSON structural validation from the wire layer to the storage layer rather than skipping it — traced forward and confirmed the full decode (`secantus-storage/src/lib.rs:8396`) happens before any WT write and failures propagate as errors, not silent corruption. Structural difference from Python (which always fully decodes at the wire layer), not a hole.
- `crates/secantus-commands/src/transactions.rs:495-503` (`in_progress_count`, a test/introspection helper) uses plain `.lock().unwrap()` instead of this codebase's otherwise-consistent poison-recovery pattern. Not reachable from a live request path; worth matching for uniformity.
- `killAllSessionsByPattern` is a third, unlisted sibling of already-tracked **#1226** (same cluster-wide-destructive RBAC gap) — flagging so a generic fix for #1226 doesn't miss this command name.
- `replSetGetStatus` is likewise missing from the RBAC action table (same class as tracked **#1661**), but it's read-only and reveals only topology info already implied by the unauthenticated `hello` reply — low impact.
- `createSearchIndexes`/`dropSearchIndex`/`updateSearchIndex` are also absent from the RBAC action table, but all three route to a "not supported" stub, so there's no real effect to bypass.
- `validate.yml`'s `pgjdbc-report` job has no explicit `permissions:` block (no workflow-level default either); low blast radius (checkout + artifact merge/upload, no secrets, no push) but a gap in the "every job declares permissions" rule.
- `claude-code-review.yml` runs automatically on every PR (correctly via `pull_request`, not `pull_request_target`) and spends OAuth-token quota on every PR event with no rate-limit or authorization gate — a cost/quota-exhaustion vector via PR spam, not a secret-exposure one.
- `CLAUDE.md` cites the PostgreSQL-crates version as `0.1.0-beta.0` (dated 2026-09-18); the actual `Cargo.toml` version is now `0.1.0-beta.2` — a stale doc snapshot, not a code defect.
- The top-level `rust/` directory (a separate "Phase 0 spike" workspace with its own `Cargo.lock`, containing only `bson 2.15.0` / `time 0.3.47` — no advisories found) isn't mentioned in `CLAUDE.md`'s crate inventory; worth folding into whatever periodic Rust dependency audit covers `crates/`.

**Wire-protocol parsing (§3 — both servers):**
- Header parsing in both `wire.py` and `secantus-wire` rejects a length smaller than the header *and* larger than the 48MB cap, in that order, before any body read or subtraction — no underflow or huge-allocation vector.
- `OP_MSG` kind-0/kind-1 section parsing in both languages checks declared section/document lengths against the remaining buffer before every slice, rejects any doc length `< 5` before computing `offset + doc_len`, and the parse-loop offset strictly increases every iteration — no infinite-loop or out-of-bounds-read vector regardless of attacker-chosen bytes.
- `checksumPresent` trailing-4-byte trim is computed from the already-known buffer length, not an attacker field, in both implementations.
- `OP_QUERY`/`OP_REPLY` legacy path: the NUL-terminated cstring collection name is bounded, a missing NUL converts to a recoverable error rather than an unbounded scan or panic, in both languages.
- Every `bson.decode`/`Document::from_reader` call on the wire path is inside error handling that converts to a clean `{ok:0, errmsg, code, codeName}` reply and keeps the connection alive; Python explicitly catches `RecursionError` from a pathologically deep document rather than letting it escape; Rust additionally wraps the whole dispatch call in `catch_unwind`.
- Partial-frame/stalled-client handling for the read side is bounded in both servers (Python via whole-socket `settimeout`, Rust via a per-message read deadline) — the gap found is specifically the *write* side and shutdown-force-close, covered in Finding 2 above.

**Storage/FFI & Rust unsafe (§4, §9):**
- `(db, coll)` names never reach a WT URI string in `storage.py` — only ever travel as key-column data across a fixed, hashed set of 16 shard tables.
- `:memory:` → `tempfile.mkdtemp()` with owner-only perms, explicit `rmtree` with a documented symlink-race guard on close.
- Every WT write/commit/checkpoint/close failure is logged, never silently swallowed; `WT_ROLLBACK` vs `WT_PANIC` are correctly distinguished.
- Vendored WT submodule pin matches the recorded gitlink exactly — no drift.
- Every `unsafe` block in `crates/secantus-wt` reviewed: buffer-lifetime discipline (held allocations across `set_key`/`set_value` → `insert`/`search`) is sound; no wire-input-derived length/pointer reaches an `unsafe` call without going through an owned, correctly-sized Rust allocation first.
- Broader Rust panic sweep: `secantus-wire`, `secantus-commands/{auth,cursors,admin}.rs`, `secantus-storage-adapter` have zero production-code `.unwrap()`/`.expect()`/`panic!` (all such hits are confined to `#[cfg(test)]`); sampled sites in `secantus-core`'s query/expressions/update/aggregate/projection/windowfields modules are consistently guarded by a preceding length/type/null check.

**Auth, dispatch, resource limits, network, admin UI (§5-§8, §10):**

- **Top 3 priorities for the team:**
  1. **Bump the `pymongo` floor to `>=4.18.2` and re-lock.** This is the cheapest fix in the whole report — a one-line dependency change — against the only CRITICAL finding, a CVSS-8.4 memory-corruption bug in the BSON encoder every document write path uses.
