### Python storage — RecordId step 4a/4b/4c (doc table, index entries, tailable cursor), reviewed in full

Three related commits (`86cbfdf3`, `541d97e7`, `86c4d4d5`) bring the Python storage layer's on-disk layout to parity with the Rust `secantus-storage` RecordId work reviewed in the 2026-07-24/25 reports: the document table is now keyed by a monotonic `RecordId` instead of the byte-sortable `id_key`, index entries carry the `RecordId` directly (removing the `id_key → _id index → RecordId` hop from every IXSCAN fetch), and the tailable-cursor watermark (`_find_tailable` in `commands.py`) tracks `RecordId` instead of `id_key` — fixing a real correctness gap where a capped collection with non-monotonic custom `_id`s could silently drop a later insert from a tailable cursor's stream. Read end to end with the same lens as the Rust equivalents:

- **Fail-closed migration, no in-place upgrade.** `_reject_pre_recordid_doc_format` inspects each doc shard's on-disk `key_format` via a `metadata:` cursor at `Storage.__init__` time and raises `IncompatibleStorageFormatError` if it's the legacy `SSu` (id_key-keyed) rather than the new `SSq` (RecordId-keyed) shape; `_reject_legacy_index_entry_format` does the equivalent check for index entries via a new `options.entryFormat` catalog marker (index entries can't distinguish the two formats from `key_format` alone — both are `SSSu` — so the marker's *absence* is the legacy signal). Both refusals happen before `_migrate_legacy_docs` (the separate, still-supported pre-*shard* single-table migration) and before any read/write against the mismatched table, so there's no path that silently misreads an old store's bytes as the new frame. On the refusal path the bootstrap session and the WT connection are torn down (`boot.close()` then `self._conn.close()`, both `contextlib.suppress`-wrapped since the connection may already be in a bad state) rather than leaving a live WT handle — and home-directory lock — behind for a `Storage` that never comes into existence.
- **`_unpack_entry` fails safe, not silently.** A packed index-entry payload whose trailing half isn't exactly 8 bytes (a pre-migration `id_key` tail) now returns `(escaped_kb, None)` rather than reinterpreting those bytes as a `RecordId`; every call site (`_scan_index_for_id_keys`, `_all_id_keys_for_index`, `_range_scan_index`, `_compound_range_scan_index`, the geo range scanner) filters `None` out rather than propagating a wrong id — defense in depth behind the open-time refusal, exactly mirroring the Rust side's two-layer approach reviewed 2026-07-25.
- **Duplicate-`_id` detection correctly relocated.** Because the doc table is now keyed by the *unique* RecordId rather than `id_key`, it can no longer reject a duplicate `_id` itself; `_write_nat_entry` moved that check to the `_id` index (`_NAT_SEQ_TABLE`, `overwrite=False`) and distinguishes the three possible WT outcomes explicitly: `_is_wt_rollback` → `WriteConflictError` (retry, not a real dup), `_is_wt_duplicate_key` (a new helper, `"WT_DUPLICATE_KEY" in str(exc)`) → `None` (genuine dup, caller raises the Mongo E11000 shape), anything else → re-raised unchanged. That third branch is exactly the class of bug this file's "never dress up a real storage failure as a duplicate-key rejection" comment calls out — checked and correct: a WT panic or rollback-adjacent I/O error on this path can't be mistaken for a client-facing "your write was rejected" response.
- **Cross-server on-disk compatibility preserved.** `_frame_doc_value`/`_unframe_doc_value` (`[u32-LE id_key_len][id_key][blob]`) and `_pack_entry`/`_unpack_entry` (`escape(kb) + \x00\x00 + RecordId as 8-byte big-endian`) are explicitly documented and structured to be byte-identical to the Rust `frame_doc_value`/`pack_entry` reviewed 2026-07-24/25 — this is what keeps cross-server backup/PITR portability intact. Spot-checked the encoding: `recordid.to_bytes(8, "big", signed=True)` matches a Rust `i64::to_be_bytes`, and big-endian keeps per-key entries in RecordId (insertion) order with no escaping needed even though small RecordIds routinely contain a literal `\x00\x00` in their big-endian form — the split point is still "first occurrence in the escaped `kb` half," which cannot produce one, so the separator-collision property this scheme depends on holds.
- **Test coverage matches the risk.** `tests/test_indexes.py` (+130) and `tests/test_storage.py` (+120) add reopen-roundtrip and legacy-format-refusal coverage alongside the functional RecordId assertions — consistent with this project's rule that a storage-format change needs a reopen test, not just an in-process one.

Reviewed and sound. No finding.

### Rust storage — async/decoupled oplog (prototype, opt-in) + `SECANTUS_WT_CONFIG_EXTRA` tuning hook

`b951257b` adds an opt-in background oplog-drainer pool (`SECANTUS_OPLOG_ASYNC=1`) that moves oplog persistence off the write transaction's critical path, and `0810a451` adds a `SECANTUS_WT_CONFIG_EXTRA` env var that appends a raw clause to the WiredTiger connection-config string. Both are explicitly labelled prototypes / tuning hooks in `tasks/rust-perf-findings.md` and `tasks/rust-async-oplog-prototype.md`, default to the prior synchronous/fixed behaviour, and are not reachable from any wire-protocol input — reviewed anyway since both touch the storage engine's durability contract, which this project treats as a correctness issue rather than a performance footnote.

- **Durability trade-off is disclosed, not swallowed.** In async mode the document write itself stays fully synchronous/durable (unchanged WT transaction); only the *oplog* entry (and hence change-stream visibility) is deferred to a drainer thread. A hard crash between commit and drain loses the undrained oplog entries — the code's own doc comment states this plainly, `Storage::drop` flushes every drainer (`Shutdown` + `join()`) *before* the close-time checkpoint so a clean shutdown never loses an entry, and a drainer write failure is retried in a loop and logged via `eprintln!` rather than silently dropped (`persist_and_record`'s "durability signal" comment). A batch that can't even be *enqueued* because its drainer has already exited also logs loudly (`"async oplog drainer gone; {n} committed entries not persisted"`) rather than vanishing. This is the right shape for an accepted, disclosed trade-off — consistent with how this codebase already treats the regex-ReDoS and multikey-cartesian-product acceptances.
- **One rough edge, not currently exploitable:** `Storage::drop`'s drainer-shutdown loop discards both the `Shutdown` send result and each `handle.join()` result with bare `let _ =` (`crates/secantus-storage/src/lib.rs`, the new `Drop` block). If a drainer thread had already panicked before shutdown, its death is already loudly logged at the point of failure (either inside `persist_and_record`'s write-failure `eprintln!`, or via `drain_pending_oplog`'s "drainer gone" `eprintln!` on the next enqueue attempt), so no failure currently goes unreported end-to-end — but the panic payload/backtrace `handle.join()` would have surfaced is thrown away at the one point (`close()`) this codebase's own convention says a durability signal must be surfaced loudest. Filed as INFO (I36) rather than WARNING: opt-in prototype, off by default, no wire reachability, and the failure is already reported elsewhere by the time `drop` runs — this is a polish gap, not a live loss-of-signal.
- **`SECANTUS_WT_CONFIG_EXTRA` is a local-environment hook, not a network-reachable one.** It appends a raw WiredTiger config clause (e.g. `cache_size=4G`) read once at `Storage::open` from the process environment — never from a wire command, a config file field the server parses from client input, or anything else attacker-reachable per this project's threat model (§8 of the review checklist: dependency/wire/wheel, not "attacker already has shell on the host"). Noted that WiredTiger connection config supports an `extensions=` clause that loads an arbitrary shared library by path, so in principle this hook *could* be used to load native code — but an attacker with the ability to set this process's environment variables already has an equivalent or greater capability (replace the binary, `LD_PRELOAD`, etc.), so this crosses no new privilege boundary. INFO only (I37).
- **Grep for new `unsafe`/`.unwrap()`/`.expect()`/`panic!` outside test code** across the full 570-line diff turned up one hit (`pc.as_ref().unwrap()` in `write_drain_batch`), immediately preceded by the `if pre_cur.is_none() { pre_cur = Some(...) }` that makes it structurally infallible — not a real panic risk. No other new production-path `unwrap`/`panic`/`unsafe`.
- No new third-party dependency: every `crates/*/Cargo.lock` diff this cycle is the lockstep version-string bump only (`grep -E '^\+name|^\+version'` across all four workspace/py lockfiles shows only `version = "0.5.3-beta.148"` changes).

Reviewed and sound; two new INFO items recorded (I36, I37), no WARNING/CRITICAL.

### W1 (carried forward, still open — 6th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:3738` and `:3817` this cycle (line drift only, from the ~570 inserted lines earlier in the file this cycle — re-confirmed by direct grep of every `self.oplog.lock()` call site: the new async-oplog code added this cycle correctly uses the poison-tolerant `unwrap_or_else(|e| e.into_inner())` pattern throughout — `persist_and_record`, `wait_for_oplog`, `flush_oplog`, `Storage::drop`'s meta read, `drain_pending_oplog` — but the same two pre-existing `live_count` accessors (`prune_oplog`'s early-out read and its post-prune decrement) still use bare `.lock().unwrap()`).

Already tracked as open issue [#593](../../../../issues/593), filed 2026-07-21, unfixed across **six** consecutive review cycles (07-21 through 07-26) — including this cycle's substantial (570-line) edit to this exact file, which added ten *new* correctly poison-tolerant lock acquisitions on the same mutex without touching these two.

**Recommendation:** unchanged — convert both sites to `self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The grep-based CI gate recommended in the last five reports (`! grep -rn '\.lock()\.unwrap()' crates/secantus-storage crates/secantus-commands` outside `#[cfg(test)]`) remains unimplemented after six nightly re-discoveries — at this point the manual-fix loop has demonstrably not converged and the CI gate itself is the higher-leverage fix.

### W2 (carried forward, still open — 3rd consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:5591` (`drop_index`) and `:5708` (`drop_all_indexes`) — re-confirmed present by direct read this cycle: both still open only `with self._lock:`, never `self._coll_lock(db, coll)`.

Already tracked as open issue [#635](../../../../issues/635), filed 2026-07-24. This cycle's storage.py changes (the RecordId step 4 migration reviewed above) touched locking discipline extensively elsewhere in the file (every write path now threads a `recordid` through `_write_index_entries`/`_delete_index_entries` under the same lock scopes as before) but did not touch either drop method's critical section — the hazard described in the 2026-07-24/25 reports is unchanged: a concurrent `insert`/`update`/`delete` (which takes `_coll_lock` first) is not excluded by `drop_index`'s `_lock`-only critical section, so a write's index-entry mutation and a drop's scan-then-delete can still interleave.

**Recommendation:** unchanged — `with self._coll_lock(db, coll), self._lock:` in both methods, plus a regression test mirroring `test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop path.
