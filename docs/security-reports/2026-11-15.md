## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`EXPLAIN` (and `EXPLAIN ANALYZE`) of `INSERT`/`UPDATE`/`DELETE`/`COPY
  FROM` bypasses the target table's privilege check entirely — `EXPLAIN
  ANALYZE` lets a zero-privilege role actually write to a table it holds no
  grant on** (high/high, overall high).
  `secantus_pgplan::privileges::sql_relations_uncached`
  (`crates/secantus-pgplan/src/privileges.rs:254`) derives the
  `(relation, privilege)` worklist `PgHandler::check_sql_privileges_inner`
  (`crates/secantus-pg/src/lib.rs:17042`) enforces, mirroring PostgreSQL's
  `ExecCheckRTPerms`. Its top-level match has explicit arms for
  `InsertStmt`/`UpdateStmt`/`DeleteStmt`/`TruncateStmt`/`CopyStmt`, and a
  special unwrap for `DeclareCursorStmt` into its inner query
  (lines 321-326) — but **no arm or unwrap for `ExplainStmt`**, falling
  through the trailing `_ => {}` at line 311. For `EXPLAIN INSERT INTO t
  ...` / `EXPLAIN UPDATE t ...` / `EXPLAIN DELETE FROM t ...` / `EXPLAIN
  COPY t FROM ...`, the top-level parsed node is `ExplainStmt` wrapping the
  real DML statement in its `.query` field, so none of the explicit arms
  fire; the fallback generic-node walk only pushes a `SELECT` requirement
  for nodes tagged `Context::Select`, which a DML target is not (confirmed
  by the fact that an ordinary top-level `INSERT` does not spuriously also
  require `SELECT` on its own target). Net effect: the target table of an
  `EXPLAIN`-wrapped `INSERT`/`UPDATE`/`DELETE`/`COPY FROM` requires **zero
  privilege**, when real PostgreSQL's `ExecutorStart` -> `InitPlan` ->
  `ExecCheckRTPerms` runs the normal permission check unconditionally, even
  under `EXEC_FLAG_EXPLAIN_ONLY` (that flag only skips actual row
  modification, never the permission check). For `EXPLAIN` without
  `ANALYZE` this is plan-metadata disclosure (table existence, cost
  estimate, column names) to a role with no grant on the table. For
  `EXPLAIN ANALYZE`, this server deliberately executes the wrapped
  statement (`crates/secantus-pg/src/lib.rs:45933`, matching real
  PostgreSQL's own `ANALYZE` semantics) via the same `execute_statement`
  path — so the same zero-privilege gap lets an authenticated low-privilege
  role **actually `INSERT`/`UPDATE`/`DELETE` rows** in a table it holds no
  grant on and does not own. A sibling function in the same crate
  (`crates/secantus-pgplan/src/schema_refs.rs:115`) already special-cases
  `ExplainStmt` for an unrelated purpose, confirming the unwrap pattern is
  known in this codebase and was simply never applied to `privileges.rs`.
  An independent verifier, briefed to try to refute this from scratch,
  confirmed every step of the trace from the wire-protocol entrypoint
  through to the `EXPLAIN ANALYZE` execution call site and found no
  secondary gate anywhere in the `plan_explain` path
  (`crates/secantus-pgplan/src/lib.rs:11944-12038`, which performs only
  analysis-refusal-ordering checks).
  **Fix:** unwrap `ExplainStmt` to its inner statement node before both the
  top-level match (`privileges.rs:265`) and the inner-node walk
  (`privileges.rs:316`), exactly mirroring the existing `DeclareCursorStmt`
  unwrap, so the wrapped DML's target gets the same explicit privilege push
  its unwrapped form would get.
  **Filed as a new issue** (no duplicate found; the closest relative, open
  issue **#1678**, is the same bug-class — an unhandled top-level match arm
  — for `MergeStmt`, not `ExplainStmt`).

- **dbCheck's `extraIndexKeysCheck` computes an uncapped cartesian product
  of multikey field values — unlike its own storage-layer sibling — letting
  a planted document OOM/hang the whole shared server when an administrator
  later runs dbCheck** (medium/high, overall high).
  `doc_keys()` in `crates/secantus-commands/src/db_check.rs:597` (added this
  window for dbCheck's `extraIndexKeysCheck` validate mode) computes the
  cartesian product of every indexed field's candidate key values with
  **no size bound** (the loop at lines 637-648). The identical computation
  exists twice already in the storage layer —
  `crates/secantus-storage/src/lib.rs`'s `reference_keys()` (line 17844,
  cap enforced at line 17875) and the insert-time `index_key_variants()`
  (lines 4523-4545) — both capped at `MAX_COMPOUND_KEYS = 10_000` (defined
  at line 1602), with the storage layer's own comment stating the cap
  exists "to avoid exponential blowup when multiple fields are
  array-valued" and explicitly noting this codebase deliberately does
  **not** enforce mongod's "cannot index parallel arrays" restriction — it
  accepts documents where more than one compound-index field is
  simultaneously a multi-element array, relying entirely on the cap to
  bound the resulting blowup. `doc_keys()` reuses that same unrestricted
  precondition but omits the cap. `doc_keys()` runs once per document for
  every row of the collection (`db_check.rs:442-452`) before any
  batching/throttling parameter (`maxDocsPerBatch`, `maxCount`) is applied
  — those only throttle how the already-computed key list is chunked
  afterward, not this initial per-document computation. A document of a
  few hundred KB to a few MB, with two or three fields each holding tens of
  thousands of small array elements, produces on the order of 10^9-10^10
  combinations, each involving an allocation, a KeyString encode, and an
  O(n) linear `seen`-containment scan — enough to exhaust memory or run
  unbounded. dbCheck requires the cluster-level `dbCheck` privilege (an
  administrator-grade role: `clusterManager`/`clusterAdmin`/`root`); planting
  the triggering document requires only ordinary collection write access —
  so a low-privileged writer can cause a crash/hang of the single shared
  `secantusd-rs` process the next time a higher-privileged administrator
  (or an automated periodic job — dbCheck's documented normal usage) runs
  dbCheck on that namespace. An independent verifier, briefed to try to
  refute this, confirmed the parallel-array precondition is genuinely
  unrestricted and that no other bound in `db_check.rs` rescues this
  specific allocation.
  **Fix:** reuse the existing `MAX_COMPOUND_KEYS` constant in `doc_keys()`'s
  `combos` loop, breaking out of both loops once the bound is reached,
  mirroring `reference_keys()`'s pattern exactly; surface a dbCheck
  health-log warning when a document's key set was truncated, rather than
  silently dropping the remaining combinations.
  **Filed as a new issue** (no duplicate found; the related but distinct
  open issue **RM-688** in `tasks/backlog-rust-mongodb.md` only covers
  Decimal128/geo/wildcard-index refusals and missing batch-size throttling
  of the already-computed key list — not this uncapped precomputation).
