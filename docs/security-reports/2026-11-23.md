## 🟠 WARNING (Address within 1 week)

### New this cycle

- **Catalog-adoption `ident` is never validated against this server's own
  reserved internal table names, letting an adopted, crafted/corrupted
  catalog alias a client namespace onto `_mdb_catalog` itself**
  (medium/high, overall medium, confidence high; **issue #2960**).
  `crates/secantus-storage/src/adopt.rs:107` (`placement_of`) reads a
  catalog row's `ident` field verbatim (`row.entry.get_str("ident")`) with
  no shape or reserved-name check, and `adopt_row`/`write_placement`
  (`adopt.rs:282-286`, `mdb_catalog.rs:173-180`) write it unconditionally
  into the live `secantus_idents` registry whenever `Storage::open` finds
  the store was last written by `mongod` or touched by another server since
  (`lib.rs:8146`) — the documented mongod hand-off scenario. The only gate
  before that write, `store_format::catalog_findings`
  (`store_format.rs:331-477`), checks collection/index options, index
  kind/version, replset size, FCV and users/roles counts, but never the
  `ident` field's shape (it collects idents at `store_format.rs:344-345`
  purely to look up fixed namespaces by name). `mdb_catalog::table_uri`
  (`mdb_catalog.rs:91-93`) formats the ident straight into a WiredTiger URI
  (`table:{ident}`) with no escaping or allow-list, and this server's own
  `_mdb_catalog` bootstrap table (`lib.rs:2859-2868`) uses byte-for-byte the
  same WiredTiger config (`key_format=q,value_format=u`) as every ordinary
  collection table, so a cursor opened on `table:_mdb_catalog` through the
  generic per-document CRUD path (`open_doc_cursor`, `lib.rs:836-868`;
  `placement_ident`, `lib.rs:878-909`) succeeds rather than failing on a
  schema mismatch. The codebase already has the right defensive convention
  elsewhere — `reconcile_idents` (`lib.rs:25426-25459`) checks
  `ident.starts_with("collection-") || ident.starts_with("index-")`
  (`lib.rs:25447`) — but only to decide which orphaned WT tables are safe to
  drop at startup; that check is never applied to what `adopt_row` accepts
  into the registry. **Independently confirmed three separate times** (the
  original hunter, a post-wave coverage critic, and a fully independent
  verifier), all three reaching an identical `file:line` trace by reading
  the current source directly. **Severity note**: the first two passes
  scored this overall `high`; the third, independent pass — the only one to
  explicitly work through the realistic attacker position — determined the
  precondition is an operator opening the server against a store whose
  catalog bytes are *already* crafted/tampered/corrupted at process
  startup, not a capability reachable by an ordinary wire-protocol client
  against an already-running server, and recalibrated to overall `medium`
  (likelihood low, impact high); this report carries that calibrated
  severity. **Fix:** reject any catalog `ident`/`idxIdent` value that does
  not match the `collection-<uuid>`/`index-<uuid>` shape this server and
  mongod always generate, and additionally refuse any ident equal to one of
  this server's own reserved/bootstrap table names, before it is ever
  written into the registry — mirroring `reconcile_idents`'s existing check.
  **Filed as new issue #2960.**
