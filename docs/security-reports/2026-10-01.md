## The new finding this cycle — confirmed by running the code, not by reading it

**New CRITICAL — a `MERGE` statement on the Rust PostgreSQL server bypasses
table privileges entirely for its target table. Any authenticated role,
including one with zero grants and not the table's owner, can `INSERT`/
`UPDATE` an arbitrary table via `MERGE`.**

`crates/secantus-pgplan/src/privileges.rs:19`-`103` (`sql_relations`) is the
function `check_sql_privileges` (`crates/secantus-pgserver/src/lib.rs:6862`)
calls for every statement before it runs (`lib.rs:17207`, the universal
pre-execution gate: "Table privileges, read off the SQL before planning...
must not start before the check"). Its match arm covers `InsertStmt`
(pushes `INSERT`), `UpdateStmt` (`UPDATE`), `DeleteStmt` (`DELETE`),
`TruncateStmt` (`TRUNCATE`), `CopyStmt` (`INSERT`/`SELECT`) — and has **no
arm for `MergeStmt`** (`privileges.rs:30`-`80`, `_ => {}` at the bottom).
Confirmed by execution, not inference: built `secantus-pgplan` standalone
(no WiredTiger needed — it is a pure parse/privilege/lowering crate) and ran

```rust
secantus_pgplan::privileges::sql_relations(
    "MERGE INTO t USING s ON t.id = s.id \
     WHEN MATCHED THEN UPDATE SET x = s.x \
     WHEN NOT MATCHED THEN INSERT (id, x) VALUES (s.id, s.x)"
)
```

which returns **`[("s", "SELECT")]`** — the source table gets its read
privilege, the **target table `t` gets no entry at all**. `check_sql_privileges`
(`lib.rs:6862`-`6901`) only raises `42501 insufficient_privilege` for
privileges `sql_relations` actually names; a target with zero entries is a
target with zero checks. The doc comment on `sql_relations` enumerates
`INSERT`/`UPDATE`/`DELETE` and separately *justifies* excluding
`ViewStmt`/`CreateFunctionStmt`/`RuleStmt` ("a view's DEFINITION is not
checked here") — `MergeStmt` appears in neither the match nor the comment,
which reads as an oversight (an unconsidered statement type) rather than a
reasoned exclusion like the three that are named.

Blast radius: a role that is authenticated but holds **no privilege
whatsoever** on a table — not `SELECT`, not `INSERT`, not `UPDATE`, not
ownership, not superuser — can still run `MERGE INTO <table> USING
<anything-it-can-read> ON ... WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED
THEN INSERT ...` and the server will write rows into `<table>` unchecked.
This is a complete bypass of the `GRANT`/`REVOKE` model for the write half of
`MERGE`'s two actions, reachable over the wire by any authenticated session —
the same severity class, and the same "read/write data-access widening", that
earned the Mongo-wire server's `bulkWrite` RBAC gap (**#1160**) its CRITICAL
rating in every prior cycle of this report.

**The Python PostgreSQL server does not share this bug** — checked directly
since §9 requires confirming the two servers don't diverge on a security
property, and here they do, in the safe direction. `src/secantus/sql/authz.py`
`required_privilege` (`:77`-`78`) maps `exp.Merge` to `(rbac.A_UPDATE, False)`
unconditionally, gated through the **database-wide** Mongo-RBAC role check
(`rbac.check_privilege`) with no table-level `GRANT` fallback for `MERGE`
specifically (`_target_table`/`_primary_write_target`, `authz.py:137`-`214`,
have no `exp.Merge` branch, so `_table_grant_allows` always returns `False`
for it). That is a usability gap in the opposite direction — a role holding
only a table-level `UPDATE` grant without the broader Mongo `readWrite` role
would be wrongly *denied* `MERGE` — not a privilege-escalation hole. Not filed
(it is a correctness/usability question, not a security one), but worth
contrasting: the Python implementation is accidentally safe here by being
stricter, the Rust one is unsafe by being silent.

Not reachable from an unauthenticated connection — PostgreSQL-wire auth is
unchanged this cycle (§5b below) — but needs no privilege beyond a bare
authenticated session, exactly like **#1160**.

**Filed as a new GitHub issue this cycle, graded CRITICAL.**

rewrite is a judgement call for the team rather than something this review
prescribes. Separately confirmed via source inspection (no `uv`/`cibuildwheel`
available in this review's sandboxed environment to build and check

`crates/secantus-storage/target/` (the name `.gitignore` already covers) is

Recommend adding a defensive `crates/*/target-dev/**` sdist exclude
regardless of the git-tracking fix.

## This cycle's other real changes, read and checked

**Trigger-call recursion in the new Rust trigger-firing path is bounded by
the existing guard, not a new unbounded-recursion instance.** `triggers.rs`
is new/heavily changed this cycle (part of batches 10–15's feature push,
`crates/secantus-pgserver/src/triggers.rs:407`-`441`, `run_trigger`). Checked
specifically because this project's own `CLAUDE.md` tracks 19+ open Rust
unbounded-recursion issues and the PL/pgSQL interpreter (reviewed last cycle)
is exactly this shape: `run_trigger` wraps every PL/pgSQL body invocation in
`self.with_call_depth(...)` (`lib.rs:6053`-`6066`), the same 200-level counter
plus `stacker` growth already in place for ordinary function calls — so a
trigger that fires a trigger that fires a trigger is capped the same way a
recursive function call already was. `rule_rewrite.rs:828` separately detects
rule-rewrite cycles explicitly ("infinite recursion detected in rules for
relation"). Both guards shipped in the same commits that introduced the
recursion risk, continuing last cycle's positive trend. Clean.

**A new thread-local unsafe pointer pattern (`expr_where.rs`, expression-index
`WHERE` rewriting) follows the project's own established-safe idiom exactly.**
`crates/secantus-pgplan/src/expr_where.rs:20`-`47`: a `thread_local!` `Cell<Option<*const
Hook>>`, installed for the duration of a closure by `with_expr_index_hook`,
restored by an RAII `Drop` guard so a panic during the closure still restores
the previous pointer, read back by `indexes_of`. This is the identical shape
already in `correlated.rs`'s `with_sequence_hook`/`with_function_hook`
(reviewed in earlier cycles), with the same safety comment discipline (`//
SAFETY: ... only the lifetime is erased, and Restore reinstates the previous
pointer before the borrow ends`). Sound: the raw pointer never outlives the
scope that installed it, and a thread-local means a second thread without its
own hook installed just sees `None`, never another thread's pointer. Clean.

**`sortkey.py`'s new entry-format-4 document/array index encoding
(`index entry format 4 -- documents and arrays keyed by value`, landed just
before this window at `498b2c7b`, touched again this cycle via `_id_key`
rename) recurses by document nesting depth through plain Python function
calls (`_encode_doc` → `encode_value` → `_encode_doc` for a nested document).**
Checked because this is a new recursive encoder on a path reachable from
ordinary writes (any insert/update into an indexed collection whose indexed
field holds nested documents/arrays) — the same "unbounded recursion" shape
flagged repeatedly on the Rust side. Python's own recursion limit turns a
too-deep structure into a catchable `RecursionError` (not a native stack
overflow for ordinary interpreted calls), and `commands.py`'s dispatch already
catches every handler exception generically and turns it into a wire error
reply (unchanged this cycle — `commands.py` has zero diff in this window).
The wire-level BSON *decode* path already has its own explicit `RecursionError`
guard for exactly this document-depth shape (`wire.py:145`-`154`, pre-existing,
unchanged). Not filed: the failure mode is an error reply, not a crash or a
hang, consistent with how this report series has treated catchable-exception
recursion paths before.

**`COPY ... PROGRAM` (a classic PostgreSQL superuser-RCE vector elsewhere) is
not implemented as command execution.** Checked specifically because this
cycle's `CopyStmt` privilege-mapping work touched COPY: grepped the whole of
`secantus-pgserver`/`secantus-pgplan` for `std::process::Command`,
`Command::new` — zero hits anywhere in either crate, this cycle or
previously. `COPY` only reads/writes through the storage layer. Clean,
worth stating given how often this exact feature is the vulnerability
elsewhere.

**`pgwire`'s vendored test fixture stopped reading a static SSL key from
disk.** `crates/vendor/pgwire/src/tokio/server.rs` (+23/-11, test-only,
`#[cfg(test)]`) replaced a (missing, never-committed) `examples/ssl/server.key`
file read with an `rcgen`-generated throwaway self-signed certificate per test
run. Not a finding — it removes a dependency on a key file this repository
deliberately never carried (`*.key` is gitignored), rather than introducing
one. Noted because §2's secrets sweep specifically looks for committed key
material near SSL/TLS code, and this is the opposite of that.

**New Rust dependencies this cycle** (`aes`, `blowfish`, `cast5`, `des`,
`hmac`, `md-5`, `sha1`, `getrandom`, `icu_collator`, `icu_locale`, `flate2`,
`pwhash`, a `version` crate, `prost` gaining `no-recursion-limit`) — the
weak/legacy ciphers (`blowfish`, `cast5`, `des`) are for `pgcrypto` fidelity:
PostgreSQL's own `pgcrypto` extension ships these for backward compatibility,
and `CLAUDE.md` already documents this project's position on them ("do not
'fix' them to agree with a PG error" when the reference's own OpenSSL 3 build
lacks the cipher). Offering a deliberately weak cipher *because the real
product does* is a measured-fidelity decision already made, not a new one.
`cargo audit` (see below) raised no advisory, new or otherwise, against any of
them.
