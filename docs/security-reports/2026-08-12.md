## What's new since the last review

Thirteen commits landed since the 2026-08-11 report's cutoff (`179c22e7`)
through today's `HEAD` (`6c37e33b`): a new PostgreSQL Large Object API over
the Fastpath sub-protocol plus pgjdbc callable-statement support (#832, the
biggest single feature this window), SQL read-only-transaction enforcement +
`SHOW TRANSACTION ISOLATION LEVEL` (#827), a SQL parsed-statement cache
(#821), admin-UI surfaces for collection DDL (`create`/`collMod`/`rename`)
and change-stream watch options (#825), a Rust-side chunked collection-drop
purge so a huge drop can no longer wedge the engine (#833, the largest diff
in the window at 536 lines in `crates/secantus-storage`), a tailable-cursor
`awaitData`/resume-token correctness fix (#830), `TCP_NODELAY` on accepted
sockets on both servers (#824/#826, fixing a 200x CI stall), and `serverStatus`
`storageEngine` reporting parity (#829).

Every commit was reviewed individually against the same
authorization/DoS/panic-safety/injection lens applied in prior cycles, using
four parallel deep-dives: the admin-UI diff, the new Large Object feature
(the highest-value target this window — real PostgreSQL restricts
`lo_import`/`lo_export` to superusers because they read/write arbitrary
files on the server's filesystem), the remaining core-engine + Rust diffs,
and a full re-confirmation sweep of every standing finding plus a fresh
dependency/secrets/workflow check.

**Two new findings surfaced this cycle**, both in code that shipped this
window:

- **C3 (NEW CRITICAL)** — a stored client-side-template-injection (XSS) in
  the admin UI's collections page: a MongoDB collection name (fully
  attacker-controlled by any client that can reach the Mongo wire port, no
  admin-UI auth required) is spliced unescaped into an Alpine.js directive's
  JS-string-literal context, letting a single quote in the name break out
  and execute arbitrary JavaScript in the admin operator's authenticated
  browser session — a pivot from the wire port (unauthenticated by default)
  to full admin-UI control.
- **W7 (NEW WARNING)** — the new Fastpath Large Object sub-protocol
  (`_handle_fastpath` in `pgserver.py`) dispatches straight to
  `largeobjects.call(...)`, bypassing both `authz.authorize()` (the SQL
  RBAC gate) and the new read-only-transaction check entirely. With
  `--auth` + per-role bindings, a session with no write privilege — or a
  session inside `BEGIN READ ONLY` — can still create/read/write/truncate/
  unlink large objects.

The Large Object filesystem-access angle itself (`lo_import`/`lo_export`)
was checked closely and found **not implemented** — no code path in the new
feature opens a file by a client-supplied path, so there is no
arbitrary-file-read/write surface. All eight previously-standing findings
(C1, C2, W1–W6) were independently re-confirmed present, unchanged in
substance this cycle; line numbers shifted in several files due to
unrelated churn (noted per-section below).

## 3. Wire-protocol parsing safety

`src/secantus/wire.py`: zero commits this window. The new SQL-side
"Fastpath" sub-protocol parsing (`pgwire.py`'s `parse_function_call`, used
by the new Large Object feature — see §6/§10 for the feature review) was

### C3 (NEW) — Admin UI: MongoDB collection name is spliced unescaped into an Alpine.js directive, enabling stored client-side-template-injection (XSS) that pivots from the (by-default-unauthenticated) wire port to the admin operator's authenticated browser session

**Files:** `src/secantus/admin/templates/pages/collections.html:89,94,98,121`.

This window's admin-UI DDL surfaces commit (#825) added a "Modify"/"Rename"
UI per collection, driven by Alpine.js `x-show`/`@click` state keyed on the
collection's raw name:

```
@click="open = (open === 'mod-{{ c.name }}' ? null : 'mod-{{ c.name }}')"   # line 89
@click="open = (open === 'ren-{{ c.name }}' ? null : 'ren-{{ c.name }}')"   # line 94
<tr x-show="open === 'mod-{{ c.name }}'" x-cloak>                          # line 98
<tr x-show="open === 'ren-{{ c.name }}'" x-cloak>                          # line 121
```

`c.name` comes straight from `listCollections` — i.e. from whatever name a
client passed to the `create` command. `commands.py`'s `_create` handler
(`:3075` onward) validates option shapes (capped/size/validator/etc.) but
places **no character restriction on the collection name itself** — a name
containing a single quote is accepted and stored as-is.

Jinja's default autoescaping does apply here (it turns a literal `'` in the
rendered attribute value into `&#39;`), but that only protects the *HTML*
parse layer. The browser's HTML parser decodes `&#39;` back into a literal
`'` when building the DOM attribute string, and Alpine.js then evaluates
that decoded string as a JavaScript expression (`x-show`/`@click` are
compiled via `new Function(...)`). A collection named

```
x' + (fetch('/db/'+db_name+'/drop',{method:'POST'}),'') + 'x
```

(single quotes, standard BSON string — no `\0` byte, so it passes every
existing namespace check) renders as an Alpine expression whose
HTML-entity-decoded form breaks out of the `'mod-...'` string literal and
splices in attacker JavaScript. `x-show` evaluates on initial page render
with **no click required** — visiting the collections page for the
compromised database is enough to trigger it. The executed JS runs with the
ambient admin-UI session (the browser holds the auth-token cookie), so it
can drive any admin-UI endpoint the operator's own session is authorized
for — create/drop databases, manage users and roles, etc.

The correct pattern (`| tojson`, which produces a JS-safe literal) is
already used elsewhere in the *same* PR — `changestream.html:7-17`'s
`x-data='changestreamPage({{ {...} | tojson }})'` — so this is a
missed-instance inconsistency, not a systemic gap; `roles.html`'s
equivalent diff this window does not exhibit the pattern (its `{{ }}`
interpolations land in ordinary HTML attribute/text-node contexts, which
plain autoescaping does protect).

**Why this clears the project's CRITICAL bar** (a missing CSRF token on a
127.0.0.1-only admin page is explicitly INFO per this project's threat
model, but this is different in kind): the trigger is reachable from the
Mongo wire port, which has **no authentication by default** (`--auth` is
opt-in) — a strictly lower trust tier than the admin UI's own token auth.
Arbitrary JS execution in the admin operator's authenticated session is a
genuine pivot, not merely a missing defense-in-depth header.

No CSP header is set anywhere in the admin app (`grep` for
`Content-Security-Policy`/`unsafe-eval` across `src/secantus/admin/**`
returned nothing), so nothing mitigates the `new Function()` evaluation
Alpine relies on.

**Recommendation:** wrap `c.name` in `| tojson` (matching the
`changestream.html` pattern already in this codebase) everywhere it's
interpolated into an Alpine expression, or move the open/closed state to a
data attribute (`data-coll="{{ c.name }}"`) read via `$el.dataset.coll`
instead of string-building the Alpine expression itself. Filed as issue
[#834](../../../../issues/834). **Not fixed in this review pass** —
review/document/file only, per this run's scope.

**W6 (carried forward, still open, issue #806):** re-confirmed present and

### W7 (NEW) — SQL Large Object Fastpath sub-protocol bypasses both RBAC authorization and the new read-only-transaction gate

**Files:** `src/secantus/sql/pgserver.py:612-637` (`_handle_fastpath`),
`src/secantus/sql/largeobjects.py`, `src/secantus/sql/engine.py:359`
(`authz.authorize` call site), `:368-369` (`_write_statement_verb` read-only
gate), `src/secantus/sql/scalar.py:2860` (`lo_creat`/`lo_unlink` as
ordinary SQL-callable scalar functions).

This window's Large Object feature (#832) added a second write path into
the SQL server that doesn't go through the normal statement pipeline.
Ordinary SQL statements flow through `engine._dispatch` (`engine.py:322`),
which calls `authz.authorize(stmt, session, storage, catalog)` at line 359
(opt-in, active only when the session was started with `require_auth` +
role bindings — `authz.py:9-15`) and, new this window, the read-only-
transaction check at `:368-369` (`_write_statement_verb` classifies the
statement's AST node type and raises PG's `25006` if the session is
`BEGIN READ ONLY`).

The Fastpath sub-protocol (pgjdbc's `LargeObjectManager` API path) skips
this pipeline entirely: `_handle_fastpath` (`pgserver.py:612`) parses the
wire call and dispatches straight to `largeobjects.call(fn_oid, args,
storage=self.storage, db=session.database, session=session)` at line 621 —
no `authz.authorize` call anywhere on this path, no read-only check either.
Two concrete consequences:

1. **RBAC bypass.** With `--auth` and per-role bindings active
   (`authz_active`), a session with no configured write privilege — or no
   privilege at all — can still `lo_creat`/`lowrite`/`lo_truncate`/
   `lo_unlink` any large object via Fastpath, because the check that would
   normally gate a write statement never runs for this sub-protocol. Large
   objects are keyed by a sequential OID from `_FIRST_LO_OID = 16384`
   (`largeobjects.py:69`, allocated at `:141-144`) with no owner field on
   the metadata document (`{_id: oid, size: N}`, `:132-133`), so OIDs are
   trivially enumerable — any session can act on any other session's
   objects within the same database (objects are correctly scoped
   per-database via `session.database`, so no cross-database leak).
2. **Read-only-transaction bypass.** A session inside `BEGIN READ ONLY`
   can still issue Fastpath `lowrite`/`lo_truncate`/`lo_unlink`/`lo_creat`
   calls — `_write_statement_verb`'s classification never runs for
   Fastpath. A narrower second instance of the same bypass: `lo_creat`/
   `lo_unlink` are also exposed as **ordinary SQL-callable scalar
   functions** (`scalar.py:2860`), reachable via `SELECT lo_unlink(12345)`
   — `_write_statement_verb` classifies a bare `Select` AST node as
   non-write, so this mutating call also slips past the read-only gate
   even on the normal statement path.

This is the same *shape* of bug as the standing C2 finding (a second write
surface that doesn't route through the shared authorization/consistency
check), but narrower in blast radius — scoped to large-object binary data,
not arbitrary table rows — so filed as WARNING rather than CRITICAL.
`lo_import`/`lo_export` (the filesystem-touching functions real PostgreSQL
restricts to superusers) are **not implemented** at all: `LO_PROC_OIDS`
(`largeobjects.py:40-54`) lists only the 13 non-filesystem functions
(`lo_open`/`lo_close`/`loread`/`lowrite`/`lo_lseek[64]`/`lo_creat`/
`lo_create`/`lo_tell[64]`/`lo_unlink`/`lo_truncate[64]`); an unresolvable
OID (including real Postgres's hardcoded 764/765 for `lo_import`/
`lo_export`) is rejected at `largeobjects.py:231-233` with `42883 function
... does not exist` — confirmed by grep, no `open(`/`os.open`/`pathlib`
usage anywhere in the new files. **No filesystem-access CRITICAL exists
here.**

**Recommendation:** call `authz.authorize()` (mapping each `lo_*` function
to the same `readWrite`-class action a table write would need) and the
read-only-transaction check inside `_handle_fastpath` before dispatching to
`largeobjects.call`, and route `scalar.py`'s `lo_creat`/`lo_unlink`
scalar-function wrappers through the same read-only check
`_write_statement_verb` already applies to statement-shaped writes. Filed
as issue [#835](../../../../issues/835). **Not fixed in this review pass**
— review/document/file only, per this run's scope.

`--auth` gating (Mongo-wire, general): re-confirmed unchanged —
`_NO_PRIVILEGE_COMMANDS` allowlist minimal (aside from W6), `getMore`
cursor ownership check present (I18, unchanged).
