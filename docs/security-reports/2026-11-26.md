## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`EXPLAIN` on a chain of independently-removable self `LEFT JOIN`s
  triggers Θ(3^N) recursive replanning in `secantusd-pg`** (likelihood
  high, impact high, overall **high**, confidence high; **issue #3017**).
  `secantus-pgplan`'s new RP-1060 `EXPLAIN` join-removal feature
  (`crates/secantus-pgplan/src/join_removal.rs:73-117`, function
  `candidates()`) enumerates every syntactically-removable `LEFT JOIN` in a
  query's `FROM` clause with no cap — `removable()` (line 228) uses a
  purely syntactic test with no unique-index lookup, and critically, the
  test for one join is unaffected by removal of any other join (the "read
  nowhere but its own ON" probe only clears the candidate join's own
  quals against the unmodified rest of the tree — independently re-derived
  and confirmed by the verifier, not assumed). The caller in `plan_explain`
  (`crates/secantus-pgplan/src/lib.rs:12824-12837`) recursively re-invokes
  the full, real top-level `EXPLAIN` planner (the same `plan_explain`
  entered from `plan_node`'s `ExplainStmt` dispatch at line 6495) once per
  candidate, capped at 3 **per level**, with that cap applied identically
  at every recursion depth — giving an uncapped-depth, branching-factor-3
  recursion: Θ(3^N) total `plan_explain` invocations for a query with N
  independently-removable joins. A chain of ~20 self-joins of a table the
  caller can already `SELECT` from (no unique index, no elevated privilege,
  no DDL rights needed) already exceeds any practical completion time. The
  shipped default `statement_timeout` is `"0"` (disabled, matching real
  PostgreSQL's own default — `crates/secantus-pg/src/lib.rs:29521`), and
  while `cancel::check()` is reached transitively inside the recursion (a
  correction the verifier added to the hunter's bare claim), it does
  nothing under that default. On this single-node server, a single
  unprivileged client's `EXPLAIN` can pin a worker thread in synchronous
  CPU work indefinitely, denying service to every other connection sharing
  the process, with no privilege escalation required. This is a structural
  deviation from PostgreSQL's own `remove_useless_joins`, which removes all
  eligible joins in one bottom-up pass rather than recursively re-planning
  the whole statement per candidate. **Fix (smallest effective):** thread a
  single global budget (not a per-level `take(3)`) through the recursive
  `plan_explain` calls so the total number of join-removal re-plans per
  statement is capped regardless of recursion depth, and/or call
  `cancel::check()` inside the candidate loop itself so a running statement
  is interruptible even under the default `statement_timeout=0`. **Filed as
  new issue #3017.**

## 🟡 INFO (Best-practice recommendations)

- **`secantus-pg`'s new catalog-placement accounting model
  (`catalog_places.rs`) grows a process-wide, never-reclaimed `Vec<Row>` on
  every `CREATE TABLE`, soft-deleting rather than compacting on `DROP
  TABLE`, with the only reclamation point at full clean server shutdown**
  (confirmed, overall **low**; not filed as an issue — see rationale
  below). `write()` (`crates/secantus-pg/src/catalog_places.rs:167`) pushes
  unconditionally into a `static Mutex<State>` shared by every database and
  connection the one server process serves; `end_xact()` (line 236) only
  flips a `live` flag on a committed `DROP`; the module's own doc comment
  (line 20) states plainly that pruning/VACUUM-style reclamation "is not
  placed" by design. Any ordinary, non-superuser role with `CREATE`
  privilege on a schema can loop `CREATE TABLE`/`DROP TABLE` and grow this
  shared structure for the life of the process. The independent verifier
  confirmed the mechanism exactly as the hunter traced it, but weighed
  realistic per-operation cost (tens of small `Row` structs, ~100-300 bytes,
  per DDL statement) against this project's own single-node developer/
  application threat model and concluded this needs a sustained, very
  high-volume loop (hundreds of thousands-plus of cycles) to become
  operationally significant — real, but a slow leak rather than an urgent
  availability threat, and it recovers on restart with no data-integrity
  consequence. **Not filed as an issue per this report's convention** (only
  CRITICAL/WARNING findings are filed); worth a backlog entry
  (`tasks/backlog-rust-postgres.md`) at the team's discretion. **Fix:**
  reclaim dead `Row`s and compact `by_lead` on `end_xact`'s commit path,
  mirroring the VACUUM semantics the module's own doc comment already
  references but does not implement.
- The `pg15-current-openssl` CI action (unchanged mechanism, doc-comment-
  only update this window) continues to verify downloaded OpenSSL/
  PostgreSQL source tarballs against a same-release-channel checksum, not a
  GPG signature or a separately-trusted channel — unchanged observation
  from every prior cycle, no reachable boundary violation given the job has
  no secrets and does not publish.
