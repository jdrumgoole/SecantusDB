## 3. Wire-protocol parsing safety

**Core Mongo `wire.py`/`server.py`:** zero diff this window, unchanged since
2026-08-16.

**PG extended-protocol (`pgwire.py`/`pgextended.py`, the wire-adjacent SQL
layer):** reviewed the Bind format-code validation (`ce46fdaf`) and the new/
changed binary parameter decoders in full.

- `parse_bind` (`pgwire.py:226-248`) reads the format-code and parameter
  counts as `uint16` (inherently ≤65535, no unbounded-allocation path), and
  every subsequent `struct.unpack_from` bounds-checks itself — a truncated
  Bind message raises `struct.error` on the very first out-of-range read
  rather than looping or reading out of bounds. **No crash, no OOB read, no
  hang.** The one gap: that `struct.error` isn't caught by name in
  `parse_bind`/`_bind` (`pgextended.py:1404`), so it falls through to the
  generic `except Exception` in `process()` (`pgextended.py:1319-1325`) and
  returns `XX000` instead of the more specific `08P01` a truncated-message
  SQLSTATE deserves. Safe; cosmetic gap only (see INFO below).
- `_decode_numeric` (`pgextended.py:77-107`) unpacks 8 fixed bytes before
  its `dscale` bound check; a parameter shorter than 8 bytes raises an
  uncaught `struct.error`, caught by the same generic handler → `XX000`
  rather than `08P01`. Every other binary decoder touched this window
  (`_decode_inet`, `_decode_jsonb`, `_decode_array`) has an explicit
  length guard added by `00c83289` ("malformed parameters raise proper
  SQLSTATEs, never XX000") — `_decode_numeric` was missed. No crash risk
  either way (see INFO below).
- The new `citext`/`jsonpath`/`ltree` binary decoders (`pgextended.py:
  324-326`) call `.decode("utf-8")` with no `try/except`; a malformed
  UTF-8 payload raises `UnicodeDecodeError`, again caught only by the
  generic handler → `XX000` instead of `22021` (the pattern `_decode_jsonb`,
  added in the same window, correctly uses). No crash risk.
- All three gaps above are **caught by the outer generic exception
  handlers on both the simple-query path (`pgserver.py:839`) and the
  extended-protocol path (`pgextended.py:1319`)** — every code path was
  confirmed to log server-side and return a non-leaking `XX000 internal
  error`, never a raw Python traceback, and never hang or crash the
  connection thread. This is a SQLSTATE-precision regression, not a
  wire-safety hole. Tracked as INFO, not WARNING — see below.

**Connection lifecycle / traceback leakage:** unchanged, no diff to the
generic-exception-handler wrapping this window.

## 5. Authentication & Authorization  ← this cycle's finding

`src/secantus/auth.py` (Mongo SCRAM/X.509): zero diff.

**🔴 NEW CRITICAL (C6) — `DROP TABLE a, b, …` (multi-name form) bypasses
RBAC entirely; a zero-privilege session can drop any table(s) it names.**

Landed this cycle in `ce46fdaf` ("atomic multi-name DROP TABLE + Bind
format-code validation"). sqlglot can't parse Postgres's multi-name
`DROP TABLE a, b, c` form, so the planner falls back to a synthetic
`exp.Command(this="MULTIDROP_TABLE", …)` node
(`src/secantus/sql/planner.py:11253-11268`) carrying the individually
parsed `Drop` nodes in a `drops` attribute. This synthetic command still
runs through the normal `_dispatch` → `authz.authorize` gate
(`engine.py:399`) like every other statement — but `authz._command_privilege`
(`src/secantus/sql/authz.py:42-63`), the function that maps an `exp.Command`
verb to an RBAC action, has no branch for verb `"MULTIDROP_TABLE"`. It falls
through every `if verb == …` check and hits the final `return None`
(`authz.py:63`), which `required_privilege` (`authz.py:66-104`) treats as
"exempt, no privilege needed" — the same exemption legitimately used for
`FETCH`/`MOVE`/`SET CONSTRAINTS`. `authz.authorize` (`authz.py:262-…`)
therefore no-ops for the whole statement, and `_run_statement`
(`engine.py:2539-2549`) drops every named table with **zero** privilege
check. Meanwhile the single-name form (`DROP TABLE a`) parses as a normal
`exp.Drop` and IS correctly gated (`required_privilege`'s `isinstance(stmt,
exp.Drop)` branch, `authz.py:80-82`, requiring `A_DROP_COLLECTION`/
`A_DROP_INDEX`) — so this bug is reachable **only** via the ≥2-name spelling,
which is exactly the form `pgbench -i`-style bulk-drop tooling and any
`psql \i` script emits, i.e. not an obscure edge case. Reachable under the
same threat model as C1-C5 (`--auth` + per-user/table-scoped roles; off by
default — no exposure without it). **A new tracking issue has been filed
for this.**

**🔴 NEW CRITICAL (C7) — SQL-level `PREPARE`/`EXECUTE` bypasses RBAC
entirely; any authenticated session, regardless of granted privilege, can
run an arbitrary SELECT/INSERT/UPDATE/DELETE via a prepared statement.**

Not introduced by this window's commits — the `PREPARE`/`EXECUTE` feature
predates this review cycle (since #284) — but this is its **first time
being reported**, surfaced while auditing this window's `c00674ec` ("EXECUTE
portals describe their underlying statement") for the same bug class.
`EXECUTE name(args)` parses as `exp.Command(this="EXECUTE", …)`. Exactly
like C6, `authz._command_privilege` (`authz.py:42-63`) has no `"EXECUTE"`
branch (nor `"PREPARE"`), so the outer command is exempt from
`authz.authorize` at `engine.py:399`. `_run_statement`'s `exp.Command`
dispatch (`engine.py:2507-2508`) then calls `_execute_statement`
(`engine.py:2704-2725`), which looks up the previously-`PREPARE`d query AST
from `session.prepared`, substitutes the `EXECUTE` call's argument literals
for its `$N` placeholders (`_bind_parameter_nodes`, `engine.py:2716-2725`),
and calls `_run_statement(bound, storage, db, catalog, session)` directly
(`engine.py:2725`) — the **inner, actually-executing** statement (which
could be a `DELETE`/`UPDATE`/`INSERT`/sensitive `SELECT`) never passes
through `_dispatch`/`authz.authorize`/`authz.authorize_source_reads` at
all. Concretely: a role holding zero grants (or only an unrelated table's
`SELECT`) can `PREPARE p AS DELETE FROM secrets; EXECUTE p;` and the delete
runs unauthorized. This is architecturally the same root cause as C6 — a
synthetic `exp.Command` verb the authz privilege table never learned about
— but the blast radius is broader: C6 is scoped to `DROP TABLE`, this one
covers **every statement kind** a session can `PREPARE`, making it a
complete RBAC bypass for any client willing to route through
`PREPARE`/`EXECUTE` instead of running the statement directly. (Note this
is the *SQL-level* `PREPARE ... AS`/`EXECUTE name` statement pair
documented in `engine.py:2662-2672`, distinct from the wire extended
protocol's binary Parse/Bind/Execute messages that JDBC/psycopg2 use
internally for ordinary parameterized queries — those messages carry the
literal SQL text of the *original* statement in `Parse`, which — confirmed
in §3 above — still reaches `_dispatch` normally per-Execute. The exposure
here is specifically the `PREPARE`/`EXECUTE` SQL statements a driver or
`psql` user issues explicitly.) Reachable only under `--auth` (off by
default). **A new tracking issue has been filed for this.**

non-leaking `XX000` — but it burns a large call stack and CPU with no

as I49 for self-referencing plpgsql triggers (which has an FK-cascade
`_depth > 20` guard elsewhere in the codebase as a precedent to follow).

parser" follow-up alongside I49.

`jsonpath.py`'s tokenizer regex (`_TOKEN_RE`) was checked for ReDoS: every
alternative (including the quoted-string branch) is disjoint on its first
consumed character, so matching stays linear — **no backtracking risk**.

(`engine.py:2091-2172`): an unrecognized keyword only ever becomes literal

## 7. Resource exhaustion / DoS

**🟠 NEW WARNING (W9) — PG extended-protocol named portals have no count
cap and, inside an explicit transaction block, eagerly materialize their
full result set into memory at Bind time with no row/byte ceiling.**

`_bind` (`pgextended.py:1438`) stores every `Bind` into
`self.portals[portal]` with no eviction and no maximum-portal-count check.
`786ddc60` ("bind-time portal snapshots") added `_maybe_snapshot_execute`
(`pgextended.py:1442-1485`), which — for a read-only `SELECT`/set-operation
portal bound inside an *explicit* (non-implicit) transaction block — now
runs the query immediately at Bind and stores the **full** result set on
`portal.result` (not paginated by `max_rows`, which is an Execute-only
concept in the wire protocol). A client that opens an explicit transaction
and sends many `Bind`s under distinct portal names without ever sending
`Sync`/`Close` accumulates unboundedly many fully-materialized result sets
in server memory — a straightforward memory-exhaustion DoS from a single
connection. This is a pre-existing gap (no portal cap existed before this
window either — the general "no cursor cap/TTL" concern was previously
tracked and closed as #194 for a different code path) that this window's
eager-materialization feature meaningfully amplifies: previously an
unexecuted portal held only its bound parameter values; now a SELECT
portal can hold its entire result set well before `Execute` is ever sent.
Reachable regardless of `--auth` (no privilege needed to Bind, matching the
threat model note in the review prompt about DoS not requiring an
authorization bypass). **A new tracking issue has been filed for this.**

Everything else in this section is unchanged from 2026-08-16: `CursorRegistry`
idle TTL (600s), oplog retention/`prune_oplog`, `maxBsonObjectSize`/
`maxMessageSizeBytes`/`maxWriteBatchSize` (`hello`), the SQL statement-length
cap (`MAX_SQL_LENGTH`, `planner.py:11233-11238`, unchanged this window and
confirmed still gating parse cost before any multi-drop/EXECUTE work runs).

     total bytes a session's eagerly-materialized portal results may hold,
     mirroring the existing `CursorRegistry` idle-TTL/cap discipline on the
     Mongo side.
  3. **#909** — still the highest-leverage single fix available: closing
     it also closes this cycle's confirmed second symptom (plpgsql
     refcursors), and the systemic fix from priority #1 would likely close
