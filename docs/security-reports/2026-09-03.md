## 🔴 CRITICAL (Immediate action required)

All three are unchanged from 2026-09-02 — re-verified by reading current
source, not carried on trust. All are reachable from an ordinary
(unauthenticated, for the first two) wire client:

- **#995** — `crates/secantus-wire/src/lib.rs:136-150` (`Header::body_len`).
  Read fresh this cycle:
  ```rust
  pub fn body_len(&self) -> Result<usize, WireError> {
      if (self.message_length as usize) < HEADER_SIZE { ... }
      if self.message_length > MAX_MESSAGE_SIZE { ... }
      Ok(self.message_length as usize - HEADER_SIZE)
  }
  ```
  `message_length` is `i32`. A header with `message_length = -1` sign-extends
  under `as usize` to `usize::MAX` in the **first** check (cast precedes the
  sign check, so the comparison is `usize::MAX < 16` → false, guard doesn't
  fire) and the **second** check compares the still-signed `i32` (`-1 >
  MAX_MESSAGE_SIZE` → false) — both guards pass a negative length straight
  through, and the function returns `Ok(usize::MAX - 16)`. Confirmed the
  call site (`crates/secantus-server/src/lib.rs`) still turns this into
  `vec![0u8; body_len]`, which is an unrecoverable allocator abort — not
  catchable by `catch_unwind`, kills the whole process — from one
  unauthenticated 16-byte frame. **Not fixed.**

- **#1160** — `src/secantus/commands.py`. Re-confirmed: `"bulkWrite":
  _bulk_write` is registered in the dispatch table (line 8608) but has no
  entry in `_COMMAND_ACTIONS` (the dict spanning 8693-8776, read in full this
  cycle) and is not in `_NO_PRIVILEGE_COMMANDS` (8783-8806) either. The
  privilege gate (`commands.py:9614`, `info = _COMMAND_ACTIONS.get(name); if
  info is not None: ...`) is fail-*open*: a command absent from the table is
  silently exempted from RBAC rather than denied. `bulkWrite` still bypasses
  authorization entirely under `--auth`. **Not fixed.**

- **#977** — `src/secantus/query.py:1275` (`_MAX_REGEX_PATTERN_LEN = 1000`).
  Still a length cap only, no backtracking-depth or match-time budget. Per
  2026-09-02's live-verified finding (a pathological `(a+)+$`-shaped pattern
  starves the whole process because CPython's `_sre` engine never releases
  the GIL mid-match — confirmed to hang an unrelated second connection's
  `ping`, not just the attacking connection), this remains classified
  CRITICAL rather than the single-connection-cost WARNING the open issue's
  title still describes. **Not fixed.**
