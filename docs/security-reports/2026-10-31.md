**The three changed Rust files, in detail:**

- **`secantus-storage/src/lib.rs` (+166/-19, RP-296):** adds
  `move_unique_claims` and `take_stale_claim`, called from the three update
  paths (`update_one`-style single-doc update, bulk-write replace, and the
  cursor-driven multi-update loop) right after `index_entry_diff`. This
  fixes a data-integrity bug — an UPDATE that moved a row off a unique
  value left the storage's claim on the old value, so no other row could
  ever take it — by claiming the new keys first (`overwrite=false`, so two
  writers racing onto the same value still collide in WiredTiger) and then
  releasing the old keys this row still owns, taking over a claim whose
  holder no longer exists or no longer has an index entry for the value.
  Read end-to-end for the properties this review cares about: no new
  `unsafe`, no new `unwrap()`/`expect()`/`panic!` reachable from the write
  path (the `.expect("ResTarget has a val")` the diff's context lines show
  is pre-existing, in `secantus-pgplan`, unrelated to this file), every WT
  error branch is matched explicitly (`is_duplicate_key`, `is_not_found`,
  or propagated via `?`) — none silently dropped on this write path, which
  is exactly the discipline `CLAUDE.md`'s "Never ignore or discount an
  error" demands of a storage write. The loop bound is the document's own
  index descriptors × its `key_variants` (already-existing multikey
  expansion used elsewhere) — no new cartesian blow-up or unbounded
  allocation is introduced.
- **`secantus-pgcatalog/src/lib.rs` / `secantus-pg/src/lib.rs`
  (RP-293, RP-299):** `TableDef::natts()` is a small, bounded
  `max()` over existing column/dropped-attnum lists (no new allocation
  pattern); `size_call` now runs through `read_in_block` so a size function
  sees an index created in the still-open transaction. Both are read-path
  catalog-shape fixes with no new external input surface.
- **`secantus-pgplan/src/lib.rs` (RP-288, RP-307):** adds a
  `correlated::has_volatile_call` check that refuses to fold or
  constant-evaluate a volatile call (`nextval(...)`) in a two-table join's
  select list, and refuses (rather than silently mis-planning) a LIMIT/OFFSET
  on a joined subquery feeding an aggregate. Both changes **narrow** what the
  planner accepts by returning `Error::Unsupported` for the previously
  wrong-answer case — the faithful direction per `CLAUDE.md`'s "wire-protocol
  fidelity over feature completeness."

None of the four touch wire parsing, auth, FFI/`unsafe` boundaries, or

## 🟡 INFO (Best-practice recommendations)

- **The RP-296 fix is a textbook example of the error-handling discipline
  this review checks for**: every WT error branch on the new write path
  (`move_unique_claims`, `take_stale_claim`) is matched by name
  (`is_duplicate_key()`, `is_not_found()`) rather than caught generically,
  and anything else propagates via `?` instead of being swallowed — worth
  citing back if a future session asks what "surface errors faithfully"
