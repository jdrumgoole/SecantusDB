## This cycle's real changes, read in full

**`configureFailPoint` gated behind `enableTestCommands`** (`src/secantus/{cli,
config,server,commands}.py`, `crates/secantus-{server,commands,server-py}/src/
lib.rs`, `crates/secantus-server/src/{args,config}.rs`) closes **W6 from
`docs/security-reports/2026-08-10.md`**, already tracked as issue #1160's sibling
concern (RBAC action mapping) plus a defense-in-depth opt-in gate. Traced the
full mechanism: the standalone daemons (`secantusd-rs`, the Python `--auth`

constructing a `FailPointRegistry` is what makes `configureFailPoint` *exist*

`secantus-commands/src/lib.rs:800-806`). The **embedded** test handles
(`SecantusDBServer`, the PyO3 `RustServer`) default it **on**, because

behavior; a test harness gets the feature). The RBAC action-table entry added

by direct read rather than assumed from the earlier report. **Fully closes the

**`maxTimeMS` enforcement lands on the Rust server**
(`crates/secantus-core/src/deadline.rs`, new file, +244 lines) — a thread-local
cooperative deadline armed by `dispatch` around the handler
(`secantus-commands/src/lib.rs:1149-1167`) and polled every 64 documents from
the storage scan, index build, and geo-index build loops
(`crates/secantus-storage/src/lib.rs`, seven call sites). This is a
**resource-exhaustion FIX**, not a new surface: a client-supplied `maxTimeMS`
now actually bounds a long-running scan on the Rust server the way it already
did on the Python server (`secantus/deadline.py`), rather than being parsed,
validated, and ignored. Read the whole new file plus every call site; the
guard-based nesting (`Guard::drop` restores the outer budget) prevents a
handler that dispatches an inner command from silently widening its own
limit, and the poll-interval (`POLL_EVERY = 64`) bounds worst-case overrun to
64 documents rather than the whole collection. No new panic/unwrap surface;
six unit tests exercise nesting, cross-thread isolation, and the exact poll
boundary. Clean.

## Sub-pass: the PG-server feature batch (`secantus-pgplan`, `secantus-pgserver`)

The two largest files in the diff (`+3840`/`+3180` lines: `ALTER TABLE`,
sequences/identity, subqueries/CTEs, window functions, `GROUPING SETS`/
`ROLLUP`/`CUBE`, `ON CONFLICT`, pattern matching, `information_schema`) were
reviewed for the standing risk classes this codebase already tracks —
reachable panics, the "unbounded Rust AST recursion" class (19 issues already
open), authorization-gap consistency with existing DDL, and injection via a
SQL-supplied name reaching a WT URI/path. Findings below were each re-verified
by this session with a direct source read (not taken on the sub-pass's word
alone):

- **New CRITICAL: exponential AST blow-up from non-recursive CTE self-reference
  fan-out.** `crates/secantus-pgplan/src/lib.rs`: `inline_ctes` (:6637-6666),
  `substitute_ctes` (:6672-6689), `substitute_in_from` (:6699 onward). CTEs are
  resolved in declaration order; each CTE's body is fully substituted
  (`inline_ctes`/`substitute_ctes` deep-clone the referenced CTE's already-
  substituted `SelectStmt`) before being recorded in `defs` and made available
  to later CTEs. A later CTE that references an earlier one **more than once**
  (e.g. `b AS (SELECT * FROM a x, a y)`) embeds two full clones of `a`'s
  already-substituted body; if `a` itself doubled a still-earlier CTE, the
  clone size roughly doubles at every declaration level with no depth, node-
  count, or size cap anywhere in the crate (confirmed: no
  `MAX_.*NODE`/size-guard identifier exists in `secantus-pgplan`). A query of
  the shape `WITH c0 AS (SELECT 1), c1 AS (SELECT * FROM c0 a, c0 b), c2 AS
  (SELECT * FROM c1 a, c1 b), ... c30 AS (...)` — a few KB of SQL text, thirty
  sequential, non-recursive `WITH` items — drives `inline_ctes`'s clone/
  allocation work toward `2^30` nodes before planning even begins. This is
  the classic "billion laughs" amplification shape applied to SQL CTEs, and it
  is **new**: CTEs did not exist on this server before this diff (`git show
  d16469fc:crates/secantus-pgplan/src/lib.rs` has no `with_clause`/
  `CommonTableExpr` handling at all), so there is no prior, unchanged baseline
  to compare against. `WITH RECURSIVE` is correctly refused (:6641) — but that
  guard stops literal self-reference, not this fan-out-and-double shape, which
  uses only non-recursive `WITH`. Given the Rust PG server has **no
  authentication at all** (standing issue #1191, re-confirmed unchanged this
  cycle — see below), this is reachable by any TCP client that can complete a
  startup packet, no valid credential required. **Filed as a new GitHub
  issue.**
- **New WARNING: new instance of the standing "unbounded Rust recursion" class
  — subquery/CTE expression walkers.** `crates/secantus-pgplan/src/lib.rs`:
  `resolve_sublinks_in_select` (:6205) / `resolve_sublinks_in_expr` (:6342,
  hand-rolled recursive descent over `TypeCast`/`AExpr`/`FuncCall`/`BoolExpr`/
  `CaseExpr`/etc. with no depth counter) / `resolve_one_sublink` (:6397, which
  recurses back into `resolve_sublinks_in_select` for the subquery body,
  forming unbounded mutual recursion keyed directly on SQL nesting depth).
  `SELECT (SELECT (SELECT (SELECT ...)))` nested to the platform stack limit
  is a stack-overflow DoS with no privilege required (same no-auth baseline as
  above). This generalizes the exact class already tracked at #1117, #1161,
  #1192/#1193, #1355-1357, #1394-1396, #1430-1433, #1454-1456, #1550, #1564 (19
  open issues) — a new instance introduced by code that didn't exist before
  this diff (subqueries are new this cycle), not a change to any of those
  existing sites. Consistent with that class's established severity.
  **Filed as a new GitHub issue.**
- **New WARNING: unbounded memory from uncorrelated-subquery materialization.**
  `crates/secantus-pgserver/src/lib.rs`: `subquery_rows` (:2158) /
  `materialise_sub` (:2198). Matches `CLAUDE.md`'s own description of the
  design ("An uncorrelated subquery is RUN during planning and replaced by the
  values it returned") — confirmed by direct read that there is no row-count
  or byte-size cap on the collected `Vec`. `WHERE x IN (SELECT huge_col FROM
  huge_table)` fully materializes the inner result set in server memory before
  the outer query runs at all. New surface (subqueries did not exist before
  this diff); comparable in shape and severity to the already-filed #949
  (extended-protocol portal materialization) and #1451/#1452 (unbounded
  caches/inboxes on the same server). **Filed as a new GitHub issue.**
- **INFO, not filed:** `expand_grouping_sets`'s `1u32 << keys.len()`
  (`secantus-pgplan/src/lib.rs`, `CUBE` expansion) is an unguarded shift that
  panics in a debug build and silently wraps in a release build without
  `overflow-checks` at ≥32 `CUBE` grouping columns — narrow (needs a very wide
  `CUBE(...)` list) and no `Cargo.toml` in the tree sets `overflow-checks` for
  release, so the shipped behavior is silent wraparound (wrong grouping) rather
  than a crash. `plan_window_frame`'s offset validation
  (`secantus-pgplan/src/lib.rs`) has a comment claiming PostgreSQL's
  negative-bound error applies, but only the non-integer branch actually
  raises it — a negative `ROWS BETWEEN -1 PRECEDING` integer is accepted and
  silently clamped downstream by `window_frame_bounds`'s own `.max(0)`/
  `.min(n-1)` guards (`secantus-pgserver/src/lib.rs:15403`), so it produces a
  wrong-but-bounded answer, not a crash — the "comment cites the oracle, code
  doesn't match it" shape `CLAUDE.md` warns about, but not itself a security
  finding since no panic or unbounded work follows from it.
- **Checked and CLEAN:** sequence/catalog names ride as WT query *data* (`_id:
  name` documents in `__sql_sequences__`, `crates/secantus-pgcatalog/src/
  lib.rs:22` and every `secantus-pgserver` call site) — never formatted into a
  WT URI, path, or config string; no injection surface from `CREATE SEQUENCE`/
  `ALTER TABLE ... RENAME`/identity-column names. No privilege/role model
  exists anywhere in the Rust PG server for *any* DDL (`grep` for `authorize`/
  `privilege`/`GRANT` across `secantus-pgserver`+`secantus-pgplan` is empty) —
  `ALTER TABLE`, sequences, and `IDENTITY` are exactly as unguarded as the
  pre-existing `CREATE TABLE`, which is the standing #1191 baseline, not a new
  regression introduced by this batch. New array/vector indexing introduced
  this cycle (`f.args[0]`, `c.fields[0/1]`, `s.from_clause[0]`, window
  peer-group arrays, `agg.group_by[i]`) is guarded by a preceding length/
  emptiness check at every site checked; no new reachable panic found beyond
  the `CUBE`-shift INFO item above.
