## 5. Authentication & Authorization ← this cycle's substantive finding

`src/secantus/auth.py`: zero commits since 2026-08-06, SCRAM/X.509/mTLS
paths unchanged and re-confirmed sound (constant-time verifier compare,
stdlib-`ssl`-verified peer cert for the DN path).

**C1 (Mongo-wire `aggregate` RBAC gap):** re-confirmed still present and
unfixed at the same locations (`commands.py:5871`'s stale comment,
`aggregate.py` — zero `check_privilege` hits). Tracked via open issue
[#783](../../../../issues/783); no code changes landed this cycle (out of
scope for this review pass regardless — review/document/file only).

**New this cycle — C2:** applied the same investigative question that
surfaced C1 ("does the primary-namespace-only check pattern recur
elsewhere?") to the **SQL/Postgres-wire server's** authorization layer
(`src/secantus/sql/authz.py`), which supports a *finer-grained*
capability than the Mongo server: per-table and per-column `GRANT`/
`REVOKE` (`_table_grant_allows`, `catalog.has_table_privilege` /
`has_column_privilege`, #127/#131), layered on top of the Mongo-style
db-wide role check.

Traced `authorize()` (`authz.py:206-229`), `required_privilege()`
(`:66-98`), and `_target_table()` (`:125-144`) end-to-end:

- For `exp.Select`, `_target_table` correctly returns `None` whenever the
  statement has a `JOIN` or contains an `exp.Subquery` (`:137-138`) —
  this **forces** a multi-table `SELECT` to fall back to the db-wide
  Mongo-role check, correctly denying a session that holds only a
  narrow table-level grant. This path is sound.
- For `exp.Insert`, `exp.Update`, and `exp.Delete`, `_target_table`
  unconditionally returns the single primary table (`:129-135`) — insert
  target, update target, delete target — **with no equivalent
  join/subquery guard.** But `_run_insert` (`engine.py:2386-2420`) fully
  supports `INSERT INTO t SELECT ... FROM other_table` (running the
  source through the ordinary `_run_query`/`_run_select` path, which may
  itself join or subquery arbitrarily), and the engine separately
  implements `UPDATE ... FROM` (`_run_update_from`, `engine.py:1102`)
  and `DELETE ... USING` (`_run_delete_using`, `engine.py:1074`). None of
  these secondary-table references are ever passed through `authorize()`
  — `authz.authorize()` is called exactly once per top-level statement
  (`engine.py:346`), and grep confirms it is the *only* call site in
  `engine.py`.

**Impact:** a session holding a table-level `INSERT` grant on table `A`
(and explicitly **no** `SELECT`/`find` grant, table-level or db-wide, on
table `B`) can run:

```sql
INSERT INTO a SELECT * FROM b RETURNING *;
```

`required_privilege` classifies this as a plain `exp.Insert` → checks
only `A_INSERT` against `a` (`authz.py:69-70`, `_touched_columns` +
`_table_grant_allows` at `:180-202`) — `b` is never named to the
authorization layer at all. The statement both **copies every row of
`b` into `a`** (readable afterwards via any ordinary `SELECT * FROM a`
the attacker's own insert grant almost certainly already implies) and,
since `RETURNING` is implemented generically for INSERT/UPDATE/DELETE/
MERGE (`executor.py:771-841`), **echoes `b`'s rows directly in the
command response** without a second `SELECT` even being necessary. The
identical shape applies to `UPDATE a SET x = b.secret FROM b WHERE
a.id = b.id RETURNING x` and `DELETE FROM a USING b WHERE a.id = b.id
RETURNING b.secret` — both read an unauthorized table `b` under only an
`UPDATE`/`DELETE` grant on `a`.

This defeats the SQL server's per-table/per-column `GRANT` system's
entire promise in exactly the way C1 defeats Mongo-wire collection-scoped
roles: the minimum-privilege case the grant model exists to express
(insert-only on one table) is fully bypassed for reading any other table
in the same connected database. Scope is narrower than C1's (same
database only — the SQL layer has no cross-database table reference at
all, confirmed via `qualified_table_name`/`qualify_from_search_path` in
`planner.py:4507-4622`, so this cannot reach a different Mongo database
the way `$out`/`$lookup` can), but within a database it is a complete
bypass, not a partial one, so it is filed at the same **CRITICAL**
severity as C1. See the finding writeup below for the full recommendation.

`--auth` gating (§ generally, Mongo-wire): re-confirmed unchanged —
`_NO_PRIVILEGE_COMMANDS` allowlist minimal, `getMore` cursor ownership
check present (I18, unchanged), `bulkWrite` absent from both
`_COMMAND_ACTIONS` and `_HANDLERS` (hits `CommandNotFound` before RBAC
would matter — not a live gap).

### C2 (new) — SQL server's `INSERT ... SELECT` / `UPDATE ... FROM` / `DELETE ... USING` check RBAC only on the primary target table; the source table is never authorized

**Files:**
- `src/secantus/sql/authz.py:125-144` (`_target_table` — unconditionally
  returns the single primary table for `Insert`/`Update`/`Delete`, with
  no join/subquery guard, unlike the `Select` branch just above it which
  correctly returns `None` for exactly this reason), `:66-98`
  (`required_privilege` — one `(action, cluster)` per statement *type*,
  blind to how many tables the statement's source clause touches),
  `:206-229` (`authorize` — the single call site, confirmed via grep to
  be the only place `authz.authorize(` is invoked)
- `src/secantus/sql/engine.py:346` (the one-shot dispatch-time call),
  `:2386-2420` (`_run_insert` — runs an arbitrary `SELECT`/`SetOperation`
  source with no additional privilege check), `:1074` (`_run_delete_using`),
  `:1102` (`_run_update_from`)
- `src/secantus/sql/executor.py:771-841` (`_returning_result` and
  `RETURNING` wiring — generic across INSERT/UPDATE/DELETE/MERGE, so the
  unauthorized source table's data is directly echoed in the command
  response, no follow-up `SELECT` required)

**Impact:** the SQL/Postgres-wire server layers a genuine per-table and
per-column `GRANT`/`REVOKE` system (`catalog.has_table_privilege`/
`has_column_privilege`) on top of Mongo-style db-wide roles — exactly the
fine-grained, minimum-privilege capability RBAC exists to provide. That
system is fully bypassed for reads: any session holding only an
`INSERT` grant on table `a` (explicitly *no* `SELECT` grant, table-level
or db-wide, on table `b`) can run

```sql
INSERT INTO a SELECT * FROM b RETURNING *;
```

and receive `b`'s rows back directly in the response — `required_privilege`
sees only `exp.Insert` and checks `A_INSERT` against `a`; `b` is never
named to the authorization layer. The same shape applies to
`UPDATE a SET x = b.secret FROM b WHERE a.id = b.id RETURNING x` (needs
only `UPDATE` on `a`) and `DELETE FROM a USING b WHERE a.id = b.id
RETURNING b.secret` (needs only `DELETE` on `a`). Note the contrast with
`exp.Select`'s handling in the same file (`_target_table:137-138`), which
correctly falls back to requiring a db-wide role the moment a `JOIN` or
`Subquery` is present — the `Insert`/`Update`/`Delete` branches simply
never got the equivalent guard.

Scope is bounded to a single connected database (the SQL layer has no
cross-database table reference — confirmed via `planner.py:4507-4622`),
narrower than C1's cross-database blast radius, but within a database
the bypass is total: any table reachable from any writable table via a
subquery, `FROM`, or `USING` clause is readable regardless of that
table's own grants. Filed at the same CRITICAL severity as C1 because it
defeats the SQL server's finer-grained authorization model's core
promise, not a partial or edge-case gap.

**Reproduction (illustrative, SQL server with per-user roles / grants
active):**
```sql
-- As an admin: grant `writer` only INSERT on public.scratch, nothing on public.sensitive.
GRANT INSERT ON public.scratch TO writer;

-- As `writer`:
INSERT INTO public.scratch SELECT * FROM public.sensitive RETURNING *;
-- succeeds; response body contains every row of `sensitive`, which `writer`
-- was never granted SELECT on.
```

**Recommendation:** extend `_target_table` (or add a parallel helper) to
walk *all* table references a statement's source/FROM/USING clause
touches — not just the write target — and require `A_FIND` (or the
appropriate table/column-level SELECT grant) on each one before
executing `INSERT ... SELECT`, `UPDATE ... FROM`, `DELETE ... USING`, and
`MERGE ... USING` (the `MERGE` source is a different code path,
`_merge_source` in `engine.py`, and should be checked as part of the
same fix). Mirror the `Select` branch's existing join/subquery-detection
logic rather than inventing new detection. Add a regression test with a
table-scoped `INSERT`-only role attempting to read a second table via
each of `INSERT ... SELECT` / `UPDATE ... FROM` / `DELETE ... USING`,
expecting `42501 insufficient_privilege`. **Not fixed in this review
pass** — tracked via GitHub issue only, per this run's scope.
