## 🟠 WARNING (Address within 1 week)

### New this cycle

- **Storage repair's `_id`-index rebuild fully decodes and retains every
  document of a collection in memory before writing a bounded chunk**
  (medium/medium, overall medium, confidence high; **issue #2921**).
  `Storage::rebuild_indexes` (`crates/secantus-storage/src/repair.rs:243-249`)
  collects `(RecordId, Document)` for every row of a collection into one
  `Vec`, where `decode_doc` (`lib.rs:3253-3255`) is a full owned BSON decode
  — before the subsequent `rows.chunks(PURGE_CHUNK_MAX_ROWS)` loop (:253)
  begins bounding anything, and that loop only bounds each write
  transaction's size, not this prior collect step. The decoded `Document` is
  only ever used for its `_id` field (:262); the codebase already has a
  cheaper raw-bytes `_id`-extraction pattern (`raw_id_key`, `lib.rs:6071-6081`)
  that this path does not use. **Confirmed as a regression** introduced by
  this window's storage-model rewrite (the prior version held only small,
  already-escaped id-key bytes, not full decoded documents, per `git diff`).
  Reachable only through the local-admin `secantusd-mdb --repair` path
  (post-crash/salvage recovery, never wire-reachable) — exactly the scenario,
  and exactly the large collections, most likely to need repair after a
  crash. **Independently confirmed** by a fresh verifier (high confidence).
  **Fix:** extract just `_id` via the existing raw-bytes pattern instead of
  decoding the whole document. **Filed as new issue #2921.**
- **Unguarded recursive `uses_variable` walk over a client `$lookup`
  sub-pipeline stage — stack-overflow DoS** (medium/high, overall high,
  confidence medium; **issue #2922**). A new helper added this window,
  `uses_variable` (`crates/secantus-commands/src/aggregate.rs:3410-3423`),
  recurses into a client-supplied BSON Document/Array value tree with no
  depth bound, called from `apply_lookup` (:3718-3723) on the first stage of
  a client-supplied `$lookup.pipeline` whenever the command is a
  collectionless `aggregate` — no special privilege, no stored data needed
  (`$documents` suffices). No depth cap sits anywhere between decode and
  this call. **Independently confirmed** as a distinct root cause from
  #2137 (pipeline-nesting, not value-tree-nesting) and from #1780 (the
  generic decode-level recursion, which runs at a much shallower stack depth
  and does not make this call-depth-specific recursion safe even once fixed).
  **Fix:** thread a depth counter mirroring `crud.rs`'s `too_deep`/
  `MAX_NESTING_DEPTH`. **Filed as new issue #2922.**
- **`EXPLAIN`'s `sort_key_cost` does an O(select-list × order-by-list)
  Debug-format-plus-regex comparison with no cancellation check**
  (medium/medium, overall medium, confidence high; **issue #2923**). Found
  opportunistically while hunting this window's (unrelated) `scan_estimate.rs`
  diff; confirmed **pre-existing**, not introduced by this window
  (`sort_key_cost`/`same_row_expr` are byte-for-byte unchanged in this
  diff). `sort_key_cost` (`crates/secantus-pg/src/scan_estimate.rs:6851-6879`)
  scans the whole select-list for every ORDER BY key via `same_row_expr`
  (:6883-6910), which Debug-formats and regex-normalizes both sides on every
  pair with no memoization, reachable via a bare (non-`ANALYZE`) `EXPLAIN`
  with no elevated privilege, no cancellation checkpoint anywhere in the
  file. No duplicate found among this project's ~10 other open "uncapped
  O(n^2)/no-cancellation" issues. **Fix:** memoize the comparison key per
  select-list entry; add a `cancel::pending()` checkpoint. **Filed as new
  issue #2923.**

## 🟡 INFO (Best-practice recommendations)

- **The `tokio` `RUSTSEC-2026-0386` `AsyncFd`-unsound pin is unchanged** —
  unfixed across an **eighteenth** consecutive review cycle now; confirmed
  this cycle that `1.51.6+`/`1.53.3+`/`1.54.x` are the patched versions
  available upstream.
- **`rustix 1.1.4` (`RUSTSEC-2026-0486`) remains present only via the
  dev-only, test-only `tempfile` dependency** — not reachable from
  production, unchanged.
- **A discarded directory-fsync `Result` in `store_format.rs`**
  (`crates/secantus-storage/src/store_format.rs:207-209`): `write_atomically`
  creates a temp file, writes and `sync_all`s it, renames it into place, then
  does `let _ = dir.sync_all();` on the parent directory to persist the
  rename — discarding any I/O error from that directory fsync. Confirmed
  present by direct re-read. Recorded as INFO rather than a confirmed finding:
  the adjacent comment ("not every platform can sync a directory") documents
  a deliberate cross-platform trade-off rather than a careless swallow, and
  the failure mode (a rare fsync-failure-plus-crash combination on a freshly
  created store, possibly re-triggering `StoreKind::Created` handling on next
  open) is narrow and local-filesystem-only, not wire-reachable. Worth a
  conscious call on logging the failure rather than silently discarding it,
  per CLAUDE.md's general "never swallow a write-path error" stance, but not
  actionable as a security fix today.
- **A malformed `secantus_idents` row is silently read back as "no
  placement"** (`crates/secantus-storage/src/mdb_catalog.rs:114-142`):
  `Placement::from_doc` returns `None` (via `?` on `Option`) for a row
  missing `ident`/`catalogId` or holding a non-string index ident, and
  `read_placement` wraps that `None` in `Ok(None)`, indistinguishable from
  "no placement exists for this (db, coll)." Confirmed present by direct
  re-read. Not reachable through ordinary client traffic against a healthy
  store — only an already-corrupted or unexpectedly-shaped row (bit rot, a
  partial write surviving WT recovery, a future format read by an older
  build) triggers it, and the consequence (a caller seeing `Ok(None)` could
  mint a new ident/table for `(db, coll)`, orphaning the old table's
  documents instead of failing loudly) is a storage-integrity concern rather
  than a client-exploitable one.
- **A second, currently-unreachable recursive decoder in `keystring/decode.rs`**:
  `skip_value`/`skip_bson` (decode.rs:694-866, the implementation behind the
  exported `get_key_size`) recurse through nested OBJECT/ARRAY ctype sequences
  with no depth parameter, unlike the structurally identical `to_bson_value`/
  `to_bson_object` pair, which threads a `depth: u32` and enforces
  `MAX_DEPTH = 200`. Confirmed present, and confirmed **not currently
  reachable from any production code path** — `get_key_size` has no caller
  outside this module's own tests. Latent, not actionable today; worth
  mirroring the existing depth guard before any future caller wires this
  function to untrusted bytes (e.g. a future repair/migration feature reading
  a foreign/corrupted index file).
- **A weakened (no longer unconditional) duplicate-key recheck in
  `index_build.rs`**: `check_duplicates`'s final re-derivation step
  (index_build.rs:1467-1511) now `continue`s rather than erroring when it
  can't re-derive a confirmed-duplicate prefix's key from the current
  document, where the pre-rewrite code's `unescape_kb`-based check was
  unconditional. No concrete BSON input was found (by the hunter) that
  defeats the match under current locking; recorded as a structural
  weakening of defense-in-depth around a uniqueness guarantee, not a
  demonstrated live bug.
