## 🔴 CRITICAL (Immediate action required)

All three CRITICAL findings are the same recurring bug class first
catalogued across issues #783/#785/#806/#881: a new SQL statement kind,
synthetic command verb, or embedded/secondary execution path is added
without a matching entry in `src/secantus/sql/authz.py`'s
`_command_privilege` dispatch table, so that path executes with **zero
RBAC check** regardless of the calling session's role. This is now the
codebase's most persistent bug class — 7+ confirmed instances to date. All
three below were re-verified against current `HEAD` (`9ce9d26f`) by reading
the actual execution path, not by trusting the issue tracker.

### #909 (carried forward, still open) — plpgsql function/trigger bodies bypass RBAC, and the confirmed scope is wider than originally filed

**Files:** `src/secantus/sql/plpgsql.py:775-781` (`_run_sql`),
`:763-773` (`_run_into`), `_run_open_for` (`OPEN cursor FOR <query>`).

`authz.authorize()` is only invoked from `_dispatch()`
(`src/secantus/sql/engine.py:406`), which gates each *top-level* statement
passed to `run_sql`. plpgsql's `_Runner` never routes its embedded SQL
through `_dispatch`/`run_sql`: `_run_sql` calls
`_engine._run_statement(...)` directly, `_run_into` (`SELECT ... INTO`)
calls `_engine.run_inner_select(...)` directly, and `_run_open_for` calls
`_engine.materialize_cursor(...)` directly — all three are internal "guts"
functions with no authz check. This means **any** `LANGUAGE plpgsql`
function body — trigger-invoked (`invoke_trigger`) or ordinary
(`invoke`), both `plpgsql.py:800`/`818` — executes embedded
INSERT/UPDATE/DELETE/SELECT with no privilege check at all. By contrast,
DO-block dynamic `EXECUTE '<sql>'` (`engine.py:5841`) correctly calls
`run_sql(...)` and *is* gated — only the plpgsql `_Runner`'s three direct
paths are unguarded.

**This cycle's finding:** the issue as filed is titled "trigger bodies";
re-verification confirms the root cause and blast radius are broader — it
covers *all* plpgsql function execution (triggers and ordinary functions
alike) and *all three* of `_run_sql`/`_run_into`/`_run_open_for`, not just
the trigger-invocation entry point. No new issue filed (same file, same
mechanism, same tracked bug) — a clarifying comment was added to #909 to
widen its scope for whoever picks it up, so the fix addresses all three
call sites in one pass.

### #947 (carried forward, still open) — multi-name `DROP TABLE a, b, c` bypasses RBAC

**Files:** `src/secantus/sql/planner.py:11587` (builds
`exp.Command(this="MULTIDROP_TABLE", ...)`), `src/secantus/sql/engine.py:2600-2611`
(dispatch), `src/secantus/sql/authz.py:42-63` (`_command_privilege`).

`_command_privilege` has no `verb == "MULTIDROP_TABLE"` branch; the
tail-based checks only fire for `verb in ("CREATE", "DROP", "ALTER")`, so
`"MULTIDROP_TABLE"` never matches and `required_privilege` returns `None`
— `authorize()` no-ops. Repro: a session with no DROP privilege runs
`DROP TABLE a, b` (the multi-name, comma-separated form) and both tables
drop with zero RBAC check, while `DROP TABLE a` alone (single name) is
correctly gated. Commit `7cc46cf3` (`fix(sql): DROP TABLE no longer
self-pins against the active-cursor guard`, landed this window) was
checked directly — it is unrelated, touching only cursor-pin behaviour,
not `authz.py`.

### #948 (carried forward, still open) — SQL-level `PREPARE`/`EXECUTE` bypasses RBAC for any statement kind

**Files:** `src/secantus/sql/engine.py:1632`/`2568` (`verb == "EXECUTE"`
dispatch), `:2765-2786` (`_execute_statement`), `authz.py:42-63`.

`_command_privilege` has no `"EXECUTE"` case, so the outer `EXECUTE name`
command itself is unguarded — and worse, `_execute_statement` binds the
stored prepared query and calls `_run_statement(bound, ...)` directly
(`engine.py:2786`), bypassing `_dispatch`/`authz.authorize` entirely for
the *actual* statement being run, whatever kind it is. Repro:
`PREPARE p AS DELETE FROM secrets; EXECUTE p` runs unauthorized under a
read-only role, deleting the table's contents.

**No new instance introduced this cycle.** The three commits that landed
in the SQL surface since the 2026-08-17 review (`6b484cd9`, `90f83f70`,
`9ce9d26f`) are wire-fidelity/type-metadata changes (RowDescription
column identity, GUC/void-OID handling, binary-param error
classification) — none touch `authz.py`, add a new statement kind, or
introduce a new execution path (confirmed via `git show --stat` on all
three).

## 🟠 WARNING (Address within 1 week)

### New this cycle — filed as GitHub issues

**W1 — PG SCRAM authentication leaks user existence via mismatched mock-credential shape (user enumeration)**

**Files:** `src/secantus/sql/pgauth.py:64-78` (`mock_credentials`),
contrast with `src/secantus/auth.py:63-71` (`derive_credentials`
defaults) and `src/secantus/sql/pgserver.py:568-576` (server-first
message).

`mock_credentials()` — the fabricated verifier returned for an *unknown*
username, specifically to prevent enumeration — hardcodes
`salt=os.urandom(16)` and `iteration_count=4096`. A *real* SCRAM-SHA-256
user, derived via `UserStore.from_passwords` → `derive_credentials(...,
mechanism=SCRAM_SHA_256)`, gets `salt_bytes=28` and
`iteration_count=15000` (`auth.py:63-66`, `DEFAULT_ITERATIONS`). Both
values are echoed unencrypted in the `AuthenticationSASLContinue`
server-first message (`s=<salt_b64>,i=<iterations>`) *before* the client
submits any proof. A client can distinguish "user exists" from "user
doesn't exist" purely from the returned salt length / iteration count —
exactly the oracle the function's own docstring says it exists to
prevent. The Mongo-side equivalent (`auth.py:346-356`) does not have this
gap: its fabricated credentials use the same derivation path (same salt
length, same iteration default) as real credentials, so no such oracle
exists there. Distinct from the already-fixed and closed #195 (SCRAM
proof comparison wasn't constant-time) — this is a different bug in the
same file.

**Severity:** WARNING, not CRITICAL — it leaks account existence, not
credential material, and only when `--auth` is enabled on the SQL
surface. Still a real defence-in-depth gap in the one security control
the product offers when turned on.

**W2 — Mongo `$regex` has no guard against catastrophic-backtracking patterns (CPU-pinning DoS)**

**File:** `src/secantus/query.py:1041-1068` (`_compile_regex`,
`_validate_regex_pattern`).

There is a pattern-**length** cap (`_MAX_REGEX_PATTERN_LEN = 1000`,
`query.py:1041`), but no guard against pathological-but-short patterns
(e.g. nested-quantifier constructs) compiled via bare `re.compile` with
no timeout or complexity check. A short, well-under-1000-char pattern can
still trigger exponential backtracking against a crafted matched string,
pinning a worker thread — the exact scenario `CLAUDE.md` §6 calls out:
"an attacker pinning a CPU with one `find` is a DoS." No existing
backlog/issue tracks this; it is a genuine gap, not previously filed.

**W3 — `rust-wheels.yml`'s `build` and `sdist` jobs declare no `permissions:` block**

**File:** `.github/workflows/rust-wheels.yml:52` (`build`), `:90`
(`sdist`); contrast `:105-112` (`publish`, correctly scoped to
`id-token: write`).

This workflow runs on both `pull_request` and `push: [main]`
(`rust-wheels.yml:17-37`) and compiles PR-supplied Rust code via maturin,
yet unlike every sibling workflow in this repo (`wheels.yml:39`,
`test.yml:61`, both explicitly `contents: read` with a least-privilege
comment), `build`/`sdist` here inherit the default token grant with no
explicit scope-down. Not independently exploitable given GitHub's
fork-PR token restrictions, but it's a real inconsistency with this
repo's own documented least-privilege convention on a workflow that
produces release artifacts.

## 🟡 INFO (Best-practice recommendations)

- **I1** — `cryptography` 48.0.0 (dev-extra-only, pulled transitively via
  `trustme` for ephemeral TLS test certs in `tests/test_tls.py`) has three
  technically-applicable 2026 CVEs (CVE-2026-69247/69248/69249, fixed in
  49.0.0/50.0.0). Not reachable from the base runtime/wheel dependency
  closure. Recommend a routine bump when convenient; not urgent.
- **I2** — `[tool.scikit-build].sdist.exclude` in `pyproject.toml` lists
  `tests/cross_driver/**` and the vendored gauge/driver dirs explicitly,
  but not a blanket `tests/` exclusion. `wheel.packages = ["src/secantus"]`
  means the **wheel** is unaffected regardless (only `src/secantus` is
  packaged); this is at most sdist packaging bloat, not a runtime or
  security exposure.
- **I3** — `.github/workflows/crash-repro.yml` pins `actions/checkout@v7`,
  `astral-sh/setup-uv@v7`, `actions/upload-artifact@v7` to moving
  major-version tags instead of commit SHAs (`crash-repro.yml:90,104,333`),
  unlike every other workflow in the repo. Blast radius is limited:
  `workflow_dispatch`-only trigger, `permissions: contents: read`
  (`:75-76`), no `secrets.*` used anywhere in the file. Worth tightening
  for consistency; not filed as a WARNING given the near-zero exploit
  path.
- **I4** — The GitHub ruleset protecting `refs/tags/v*` /
  `refs/tags/secantusdb-v*` (id 18530430) blocks `deletion` and
  `non_fast_forward` but has no `creation` restriction — tag-creation
  authority is governed by ordinary repo collaborator write access, not a
  ruleset. Standard GitHub model; note as a posture item, not a
  regression.
- **I5** — `crates/secantus-commands/src/transactions.rs:467`
  (`TransactionRegistry::in_progress_count`) uses `.lock().unwrap()`
  while every other lock site in the same file uses
  `.unwrap_or_else(|e| e.into_inner())` to tolerate a poisoned mutex
  (the pattern #577/#593's fixes established repo-wide). Currently
  unreachable from wire input — its only callers are unit tests — so this
  is a latent inconsistency, not an exploitable path today. Worth fixing
  if this function is ever wired into a live diagnostic command.
- **I6** — `src/secantus/sql/pgauth.py:139-140`: `base64.b64decode(proof_b64)`
  has no `try/except`, and the subsequent `zip(client_proof,
  client_signature, strict=True)` has no prior length check — unlike the
  Mongo equivalent (`auth.py:403-409`), which explicitly guards both. A
  malformed SCRAM client-final message raises a bare `ValueError` that
  isn't caught by `except PGAuthError:` in `pgserver.py:583` and instead
  falls through to the outer generic `except Exception` in
  `_handle_client` (`pgserver.py:376-377`) — connection drops instead of
  returning a polite `28P01`. No crash, no traceback on the wire, no OOB
  read; a divergence from the Mongo side's more careful handling of the
  same crypto step.
- **I7** — `src/secantus/commands.py:2042-2050` rejects only
  `len(documents) == 0` on insert; there's no explicit rejection for
  batches exceeding the advertised `maxWriteBatchSize: 100_000`
  (`commands.py:611`). In practice this is bounded by
  `wire.py:28`'s `MAX_MESSAGE_SIZE = 48_000_000`, enforced *before* any
  body bytes are read (`wire.py:122-124`), which caps total per-message
  insert volume regardless of document count. Worth adding the explicit
  count check for parity with the advertised limit, but the real exploit
  path is narrow.
- **I8** — No explicit depth cap on `$and`/`$or`/`$expr` nesting or SQL
  CTE/plpgsql recursion; both are bounded only by Python's own recursion
  limit, which surfaces as a clean `RecursionError`-derived failure
  rather than unbounded memory growth or a crash loop (confirmed same
  pattern already fixed and tested for `$jsonSchema`,
  `query.py:107-119`, per a 2026-07-20 review finding).

     report since 2026-08-16 has recommended: route every embedded/
     synthetic/secondary statement execution (plpgsql bodies, multi-name
     DDL, PREPARE/EXECUTE, and whatever `exp.Command` subtype comes next)
     through one shared authorization gate instead of hand-adding cases
     to `_command_privilege` per feature. This closes #909 (all three
     call sites), #947, and #948 in one pass and — based on the pattern's
     7-instance history — is very likely to prevent an 8th recurrence
     that a per-symptom patch would not.
  2. **#949** — cap live portals per PG connection and/or the total bytes
     a session's eagerly-materialized portal results may hold, mirroring
     `CursorRegistry`'s existing idle-TTL/count-cap discipline on the
     Mongo side.
  3. **W1 (PG SCRAM user enumeration)** — the highest-leverage of this
     cycle's three new findings to fix, since it's a one-line change
     (make `mock_credentials()`'s salt length and iteration count match
     `derive_credentials`'s real defaults) that closes a genuine
     information-disclosure gap in the SQL surface's only auth control.
