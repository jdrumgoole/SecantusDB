## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Unbounded recursion in the core Mongo query matcher and expression
  evaluator lets a client crash the whole server with a deeply nested filter**
  (high/high, overall high). `secantus_core::query::matches`/`match_clause`/
  `match_clause_raw` (`crates/secantus-core/src/query.rs`) and
  `secantus_core::expressions::eval`/`apply_op`
  (`crates/secantus-core/src/expressions.rs`) recurse once per nesting level
  of a client-supplied `$and`/`$or`/`$nor` clause or expression operator with
  no depth counter anywhere on the call path. `find.rs`'s
  `validate_empty_result` calls `query::matches` directly against an empty
  document whenever a scan returns zero rows, so no stored data is needed to
  trigger it. The only two depth guards in the codebase
  (`update.rs`'s `nesting_depth`, `crud.rs`'s `too_deep`) apply only to
  documents being WRITTEN, never to a query filter; `secantus-pgplan`'s
  `MAX_EXPR_DEPTH` guards the SQL parser's tree, not a Mongo filter. The
  MongoDB server's default configuration sets `require_auth: false`, so this
  is reachable without credentials. This is the same recurring bug shape
  this project's own review series has already confirmed in three other
  files — `projection.rs`/`elem_match_key.rs` (#2164), `explain/hoist.rs`
  (#2679, #2813) — all rated critical/high for the same reason: an unguarded
  Rust stack overflow is understood to take down the whole process, not one
  connection. This instance reaches further than any of those three: it sits
  in the single most heavily used code path (every `find`/`delete`/`update`
  filter), not a narrow feature.
  **Independently confirmed** by a fresh verifier, who additionally
  confirmed `require_auth: false` as the live default and traced the full
  call chain from wire decode through both recursion sites.
  **Fix:** add one explicit recursion-depth counter to
  `query::matches`/`matches_raw`/`match_clause`/`match_clause_raw` and to
  `expressions::eval`/`apply_op`, mirroring `secantus-pgplan`'s
  `MAX_EXPR_DEPTH` pattern, checked before recursing.
  **Filed as a new issue** (no duplicate found; cross-references #2164,
  #2679, #2813 as the same recurring root-cause class in different files).

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`SASLInitialResponse::decode_body` only treats the exact value `-1` as
  NULL; any other negative length panics via `BytesMut::split_to`**
  (medium/medium, overall medium). `crates/secantus-pgwire/src/messages/
  startup.rs`'s `SASLInitialResponse::decode_body` checks `data_len == -1`
  for NULL, unlike every sibling nullable-length decoder in the same crate
  (`Bind`, `FunctionCall`, `FunctionCallResponse`), which all treat any
  negative value as NULL — matching the real PostgreSQL wire protocol's
  convention. A client sending `data_len = -2` sign-extends to near
  `usize::MAX` and panics `split_to`. Reachable during a SASL exchange,
  before credentials are verified. Each PostgreSQL connection runs on its own
  dedicated OS thread/single-worker tokio runtime with no `panic = "abort"`
  profile anywhere in the workspace, so the panic is confined to that one
  connection — matching the severity bar this project's own review series
  has applied to the closely related #1725 class.
  **Independently confirmed** by a fresh verifier, who additionally
  confirmed the backend-per-connection isolation architecture and the three
  sibling decoders' `>= 0` convention.
  **Fix:** change `data_len == -1` to `data_len < 0` at
  `startup.rs:732`, matching the convention already used elsewhere in the
  same crate.
  **Filed as a new issue** (no duplicate found).

### Carried forward / re-confirmed as duplicates of existing issues this cycle

- **Negative `message_length` bypasses `Header::body_len()`'s bound checks**
  — re-confirmed via today's source re-read as the same root cause tracked
  by **#995** (filed 2026-08-19, still open). Today's trace additionally
  corrects #995's claimed crash mechanism: the resulting `vec![0u8;
  body_len]` request (`body_len` ≈ `usize::MAX`) exceeds `isize::MAX`,
  which Rust's `Vec` allocation path rejects via a **catchable
  `capacity overflow` panic**, not the `handle_alloc_error` unconditional
  process abort #995's text describes — and the panic occurs inside a
  per-connection `thread::spawn` closure with no process-wide `panic =
  "abort"` profile, so it is understood to terminate only that connection's
  thread. **Commented on #995** with this correction rather than filing a
  duplicate issue; the fix location and root cause are unchanged.
- **A crafted PG-wire message panics the connection via an unchecked length
  field** — re-confirmed via today's source re-read as the same root cause
  tracked by **#1725** (filed 2026-10-03, still open) for three of today's
  four PG-wire candidates: `Bind`'s unguarded first two element counts,
  `FunctionCall`'s entirely unguarded element counts, and the `copy.rs`
  length-word-underflow sink. Today's hunter additionally found the
  identical length-word-underflow root cause (missing `msg_len >= 4` check
  in `codec::decode_packet`) reaching two sinks `#1725` does not name:
  `PasswordMessageFamily::decode_body` and `SASLResponse::decode_body`
  (both in `startup.rs`). **Commented on #1725** with these two additional
  sinks and today's independent re-confirmation of its three originally
  named sinks, rather than filing a duplicate issue.
