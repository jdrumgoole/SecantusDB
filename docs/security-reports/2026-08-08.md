## 🔴 CRITICAL (Immediate action required)

### C1 (new) — `aggregate`'s RBAC check only covers the primary collection; `$out`/`$merge`/`$lookup`/`$graphLookup`/`$unionWith` write or read arbitrary, unauthorized namespaces

**Files:**
- `src/secantus/commands.py:5865-5871` (`_COMMAND_ACTIONS["aggregate"] =
  (A_FIND, SCOPE_COLLECTION)`, with a stale comment claiming a second
  check exists), `:6667-6693` (the single dispatch-time privilege check,
  which never re-fires per-stage)
- `src/secantus/aggregate.py:61-91` (`PipelineContext` — no auth/roles
  field), `:2059-2075` (`_stage_out`), `:2127+` (`_stage_merge`),
  `:1547` (`_stage_lookup`), `:3153` (`_stage_graph_lookup`), `:3966`
  (`_stage_union_with`) — none call `check_privilege`, none have access
  to the connection's `effective_roles`
- `crates/secantus-commands/src/aggregate.rs:1513-1558+`
  (`apply_out`/`apply_merge`) — same gap, confirmed independently in the
  Rust server

**Impact:** With `--auth` enabled, RBAC's entire promise is that a
principal can only act within their granted role bindings — e.g. a role
scoped to `find` on `db.reports` only. The dispatcher enforces that
correctly for the *outer* `aggregate` command (you must have `find` on
`db.reports` to run the aggregation at all). But every stage that
references a **second** namespace is unchecked:

- `{$out: "adminSecrets"}` or `{$out: {db: "otherApp", coll: "users"}}` —
  **drops and overwrites** an arbitrary collection in an arbitrary
  database the caller has no `insert`/`remove` privilege on. Real mongod
  requires `insert` + `remove` on the `$out` target; SecantusDB requires
  nothing.
- `{$merge: {into: {db: "otherApp", coll: "billing"}}}` — same, for
  `$merge`'s `insert`/`update` requirement.
- `{$lookup: {from: "otherCollection", ...}}` / `$graphLookup` /
  `$unionWith` — **reads** documents from a foreign collection the caller
  has no `find` privilege on, joined into the result set of a query they
  were only authorized to run against the primary collection.

Any authenticated user holding `find` on a single collection — the
minimum privilege RBAC is designed to express — can therefore both
exfiltrate data from, and overwrite data in, any other collection or
database on the server. This defeats collection-scoped RBAC entirely; the
practical blast radius is bounded only by what the attacker can name in a
pipeline. This is not a mongod-internal bug being ported over — it's a
gap between SecantusDB's own `_COMMAND_ACTIONS` design (which explicitly
claims per-stage write-action checks happen) and what the code actually
does.

**Reproduction (illustrative, `--auth` enabled):**
```python
# Setup (as admin): a role with only find on shop.orders
db.command({"createRole": "ordersReader", "privileges": [
    {"resource": {"db": "shop", "coll": "orders"}, "actions": ["find"]}
], "roles": []})
db.command({"createUser": "reader", "pwd": "x", "roles": [
    {"role": "ordersReader", "db": "shop"}
]})

# As `reader` (find-only on shop.orders):
client.shop.orders.aggregate([
    {"$out": {"db": "shop", "coll": "customers"}}   # overwrites shop.customers — no insert/remove grant needed
])
client.shop.orders.aggregate([
    {"$lookup": {"from": "secrets", "localField": "_id",
                 "foreignField": "orderId", "as": "leak"}}  # reads shop.secrets — no find grant needed
])
```

**Recommendation:** thread `ctx.connection_auth.effective_roles` (Python)
/ the equivalent connection auth state (Rust) into `PipelineContext` /
the aggregate execution context, and call `check_privilege` for
`A_INSERT`+`A_REMOVE` before `$out` writes, `A_INSERT`+`A_UPDATE` before
`$merge` writes, and `A_FIND` on the foreign namespace before `$lookup` /
`$graphLookup` / `$unionWith` reads — mirroring mongod's documented
per-stage privilege requirements. Add a regression test with a
minimally-privileged role attempting each stage against an unauthorized
namespace, expecting `13 Unauthorized`. This gap should be fixed in both
servers together per the "must not diverge on a security property" rule.
**Not fixed in this review pass** — tracked via GitHub issue only, per
this run's scope (review/document/file, no code changes).
