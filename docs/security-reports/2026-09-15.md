## 🔴 CRITICAL (Immediate action required)

All three unchanged from every prior cycle back to 2026-09-08 — the three
files each lives in are **provably byte-identical** to the 2026-09-09 baseline
(`git diff 0160063f..HEAD -- <file>` is empty for all three), so no
re-derivation was needed, only confirmation that no other commit touched them
indirectly (`git log 0160063f..HEAD -- <file>` is also empty for all three).
All are reachable from an ordinary (unauthenticated, for the first two) wire
client:

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  `self.message_length as usize` casts the `i32` directly, so
  `message_length = -1` sign-extends to `usize::MAX` on 64-bit *before*
  either bound check runs; the `MAX_MESSAGE_SIZE` check still compares the
  raw signed `i32`, so `-1 > 48_000_000` is also false. Both guards let a
  negative length through and the function returns `Ok(usize::MAX - 16)`.
  Feeds straight into an oversized allocation on the accept path, aborting
  the process from one unauthenticated 16-byte frame. **Not fixed.**

- **#1160** — `src/secantus/commands.py`. `"bulkWrite": _bulk_write` is
  registered in `_HANDLERS` but `_COMMAND_ACTIONS` and
  `_NO_PRIVILEGE_COMMANDS` both have zero `"bulkWrite"` entries. Dispatch's
  `if info is not None:` guard has no `else` branch — when `info is None` the
  RBAC check is silently skipped. `bulkWrite` still bypasses authorization
  entirely under `--auth`. **Not fixed.**

- **#977** — `src/secantus/query.py:1407` (`_MAX_REGEX_PATTERN_LEN = 1000`).
  `_compile_regex` only checks pattern *length*, then calls `re.compile`
  unguarded; a second bare `re.compile` call is equally unguarded. No
  backtracking-depth or match-time budget — the cap doesn't help against a
  pathological `(a+)+$`-shaped pattern, 6 characters, far under the 1000-char
  ceiling. CPython's `_sre` engine never releases the GIL mid-match, so this
  remains a whole-server CPU-pinning DoS from one unauthenticated `find`.
  **Not fixed.**

### New this cycle — six findings, all independently confirmed by direct source read

All six are filed (`#1451`–`#1456`); three were spot-checked personally
against their cited line numbers with `sed -n` before filing, the remaining
three (the two `parse_date_text` findings and `group::gkey`) were verified by
the reviewing sub-agent with cited diffs against the 2026-09-09 baseline and
are consistent with this repo's established calibration for the recursion
class.

- **NEW — #1451 — PG server's process-wide catalog lookup cache has no size
  bound (memory-exhaustion DoS).** `crates/secantus-pgserver/src/lib.rs:
  176-206` (`CatalogCache`), fill site `lib.rs:3273-3326` (`Session::lookup`).
  New this cycle (relation-lookup perf work). No `MAX_ENTRIES`, no LRU — only
  version-bump invalidation, never size-based, unlike the two sibling memos
  added in the same batch (`crates/secantus-pgplan/src/lib.rs`'s `parse_tree`
  and `max_param_number`, both capped at 4096 with wholesale-clear eviction).
  Any unauthenticated client (per #1191) grows the map without bound using
  cheap, read-only `SELECT 1 FROM nonexistent_table_N` statements — no write
  privilege or persisted object needed.

- **NEW — #1452 — PG server LISTEN/NOTIFY inbox has no size cap;
  idle-in-transaction listener accumulates unbounded notifications.**
  `crates/secantus-pgserver/src/lib.rs:63-84` (`BackendEntry.inbox`/
  `.listening`), push site `:5780-5799` (`settle_notifies`), drain gate
  `:5802-5822` (`drain_notifications`). `queue_notify` caps a single payload
  at <8000 bytes and dedupes per-transaction, but neither the channel list nor
  the per-backend notification queue has a count cap, and a backend sitting
  idle inside an open transaction (`BEGIN; LISTEN x;`, never committed) never
  drains its inbox — matching real PostgreSQL's delivery-timing rule, but
  with no bound on how much can pile up while it waits. Any other
  unauthenticated client can flood that inbox with repeated `NOTIFY`s. Same
  failure shape as the already-tracked #949 (SQL portal accumulation gated
  behind an open transaction).

- **NEW — #1453 — `pg_terminate_backend`/`pg_cancel_backend` have no
  authorization check; `pg_stat_activity` exposes every backend's full query
  text.** `crates/secantus-pgserver/src/lib.rs:5574-5646` (the
  `ConstCol::TerminateBackend`/`CancelBackend` resolver, confirmed by direct
  read: the only condition gating the arm is whether the target pid exists in
  `backend_registry()` at all — no role/ownership check) and `:3136-3177`
  (`pg_stat_activity`, `d.insert(field("query"), a.query)` at `:3172`,
  unconditional — real PostgreSQL restricts this column to the same role or
  `pg_read_all_stats`). Combined with #1191, any anonymous client can
  enumerate every live session via `pg_stat_activity` (pid, username,
  database, full in-flight query text) and then kill or cancel any of them by
  pid — a novel availability capability layered on top of the general "no
  auth" finding, plus an information-disclosure gap of its own.

- **NEW — #1454 — Unbounded recursion in `expressions::parse_date_text`'s
  military-zone-letter peel — stack-overflow DoS via `$toDate`.**
  `crates/secantus-core/src/expressions.rs:4597-4668`, recursive call at
  `4661`. New this cycle (`$toDate` timelib-format-table support, backs
  `$convert`/`$toDate` generally via `convert_value` at `:6169`). The trailing
  military-zone-letter fallback peels one character per recursive call for
  any ASCII letter except `J`; a flat string of a few thousand repeated `A`
  characters recurses that many times with **no BSON nesting required** —
  cheaper to trigger than most of the tracked class. Trigger:
  `{$project: {x: {$toDate: "AAAA...A"}}}` against any collection (or a
  `$documents`-sourced pipeline with none), no auth beyond an open
  connection.

- **NEW — #1455 — Reachable panic in `expressions::parse_date_text`'s
  compact-timestamp branch (non-char-boundary `split_at`).**
  `crates/secantus-core/src/expressions.rs:4620-4621` —
  `text.split_at(8)` on a 15-byte string with no prior ASCII/char-boundary
  check, unlike every sibling branch in the same function. Reproduced with a
  standalone repro: a 15-byte UTF-8 string with a multi-byte character
  straddling byte offset 8 (e.g. `"1234567é890123"`) panics
  `str::split_at`. Caught by `secantus-server`'s per-request `catch_unwind`
  and storage's poison-tolerant `.lock().unwrap_or_else(|e| e.into_inner())`
  pattern, so it does **not** crash the process — lower severity than the
  recursion class, but still a genuine violation of "never panic on
  malformed input," killing that one connection's in-flight request with a
  generic `InternalError` instead of mongod's `241 ConversionFailure`.

- **NEW — #1456 — Unbounded recursion in `group::gkey` — stack-overflow DoS
  via `$group`/`$bucket`/`$densify`.** `crates/secantus-core/src/group.rs:
  117-162`. Recurses through `Bson::Document`/`Bson::Array` with no depth
  cap. Confirmed **pre-existing** (unchanged by this cycle's diff, which only
  widened the leaf-value match arms to cover Decimal128/Binary/Timestamp/
  Regex/MinKey/MaxKey/Code — verified via `git show 0160063f:crates/
  secantus-core/src/group.rs`), but never previously filed — checked the full
  40-issue open tracker before this cycle's filings and none referenced
  `group.rs`/`gkey`. Reachable from `$group`'s `_id` bucketing, `$bucket`'s
  boundary comparison, and `$densify`'s partition keys. Same trigger shape as
  the rest of the class: a deeply nested literal in a grouping key, no
  persisted data required.

**Flagged but not filed — needs a follow-up probe first:** nested `DO $$ ...
EXECUTE 'DO $$ ... $$' ... $$` blocks re-enter `run_typed` → `run_do`
(`crates/secantus-pgserver/src/do_block.rs:112-147`,`314-334`) with no depth
counter in the dispatch chain; a dollar-quoted `EXECUTE` payload can nest N
levels roughly linearly in size (distinct quote tags avoid escaping cost).
`do_block.rs`/`plpgsql_do.rs` themselves are flat and iterative (full read of
both, no other recursion or unsafe/eval surface found) — the *only* iffy edge
is the async re-dispatch loop, and unlike the other six findings this one
was not driven to a confirmed crash (async executor polling makes the
stack-depth-per-nesting-level relationship uncertain). Recommend a concrete
crash reproduction before filing at WARNING tier; noted here so a future
cycle doesn't have to rediscover it.
