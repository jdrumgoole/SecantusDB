# Security Review — 2026-10-25

Diff-driven review against the 23 commits that landed since the last report
(`59d50b34`, the 2026-10-24 report's reviewed HEAD → `b37237ee`, today's HEAD,
confirmed matching `origin/main` throughout). **204 files changed,
+38,168/-1,742 lines** — eleven batches of Rust PostgreSQL-server backlog
work (B-tree splits and bottom-up/simple deletion, heap-across-a-restart,
cumulative statistics views, object identities/addresses, COPY streaming and
error reporting, ON CONFLICT over computed partial unique indexes, operator
classes of every index method, ispell and thesaurus text-search dictionaries,
extension members, schema primary keys, database encodings, sampled column
statistics, SELECT INTO, checkpoint on its own thread) and five batches of
Rust MongoDB-server work (find/aggregate cursors reading on as `getMore`
asks, `getLog`'s structured log, the slow-operation log, find's positional
and `$slice` projections, which variables `mongod` treats as constants).
Two real dependency changes landed (`crates/Cargo.lock` et al.): a new direct
dependency `log = "0.4"` (the server's own logging facade, used by the new
slow-query log) and a transitive bump of `ctutils` 0.4.2 → 0.4.5. No
`.github/workflows/`/`.github/actions/` file changed in this window
(confirmed via `git diff --stat 59d50b34..HEAD -- .github/workflows
.github/actions` — empty, and no new workflow file via
`--diff-filter=A`).

The review split the diff across four parallel passes, each re-traced to
exact file:line against the current tree before being accepted (one
subagent's claim about `pg_mcv_list_items` being newly bounds-checked was
independently re-read line-by-line and found to be a refactor of the
*header*-field parsing only — the actual unbounded-allocation gap in the
*value* arrays is unchanged and is reported again below): (1) the new
PostgreSQL B-tree/heap/statistics on-disk code, (2) the new PostgreSQL
text-search dictionary and extension/catalog code, (3) the new MongoDB-server
cursor/projection/logging code, (4) re-verification of every carried-forward
finding plus dependency/secrets/workflow re-audit.

**Net result: 4 new CRITICAL, 1 new WARNING, 1 new INFO, plus one dependency
bump that incidentally fixes an open advisory.** This continues the pattern
of the last four cycles: brand-new parsing/decoding/building surface
(a B-tree-model deserializer trusting a persisted count field, an ispell
compound-word analyzer, a `find`/`$elemMatch` projection-validator, a
slow-query logger) keeps reproducing this project's two signature bug
classes — unbounded recursion on attacker-shaped input, and unbounded
allocation/computation sized from an unchecked count — and, new this cycle,
a third shape: **sensitive command payloads reaching a diagnostic log with
no redaction**, on a feature introduced this same window.

## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`crates/secantus-pg/src/btree_model.rs:1679-1680`'s `from_docs` —
  unbounded allocation from a persisted `npages` field, reachable by an
  ordinary, unprivileged SQL client with no `CREATE INDEX` even involved,
  that aborts the whole `secantusd-pg` process for every connected
  client.** New this window (B-tree batches 60/71, RP-196). `from_docs` reads
  `npages` straight out of a document in the internal `__sql_btree_pages__`
  collection and immediately does `vec![None; n]` (line 1680) with **no
  upper-bound check** against `n` — confirmed by direct read; the function's
  only other validation is on `_id`/`kind`/`items`, never on `npages`.
  `__sql_btree_pages__` is not registered through the SQL catalog at all: its
  name is the bare WT-collection constant `btree::COLLECTION` (`btree.rs:752`),
  created lazily on first touch (`btree.rs:811-812`,
  `if !storage.collection_exists(...) { create_collection(...) }`) — there is
  **no reserved-name check anywhere in `CREATE TABLE`'s handler**
  (`lib.rs:35718-35722`, confirmed by grep across `secantus-pg`/`secantus-pgplan`
  for a reserved/`__sql_` guard on table creation: none exists; the only
  `lookup`-based duplicate check at `lib.rs` is against the *SQL* catalog,
  which this internal collection never joins). Worse, `create_collection`
  itself is **idempotent and does not error when the collection already
  exists** (`secantus-storage/src/lib.rs:11522-11527`,
  `if collection_registered(...) { return Ok(false); }` — no error surfaced to
  the caller), so this is not a first-mover-only race: it works against a
  mature database that already has real indexes, not just a freshly created
  one.
  **Concrete trigger, no elevated privilege:**
  ```sql
  CREATE TABLE "__sql_btree_pages__" (id text PRIMARY KEY, index bigint, npages bigint, root bigint);
  INSERT INTO "__sql_btree_pages__" VALUES ('seed', <any existing index oid>, 9223372036854775807, NULL);
  ```
  The next cold access to that index's B-tree model (a fresh server process
  against the same storage directory — the normal lifecycle of this
  ephemeral test server — or simply the first touch after the model is
  evicted) calls `from_docs`, attempts `vec![None; 9223372036854775807]`,
  Rust's global allocator calls `handle_alloc_error`, and **the entire
  process aborts**, dropping every connected client's session, not just the
  attacker's. Compare `heap_store.rs`'s analogous restart-reconciliation code
  (`heap_from`, lines 112-143), which reconstructs state from the actual BSON
  array length rather than trusting a separate stored count field —
  `btree_model.rs::from_docs` is the one place in this diff that doesn't
  follow that safer, already-established pattern in the same crate.
  **Fix direction:** validate `n` against a sane bound (or against the actual
  number of `block` documents present) before allocating, mirroring
  `heap_store.rs`'s approach; separately, consider a reserved-prefix guard on
  `CREATE TABLE`/`CREATE SCHEMA` so no SQL object can ever alias an internal
  `__sql_*` collection.

- **`crates/secantus-pgplan/src/ts_ispell.rs` — the ispell dictionary's
  compound-word analysis recurses with no bound and runs `O(word_len²)` work,
  reachable through the standard sample dictionary via a plain, two-argument
  `ts_lexize()` call that bypasses the tokenizer's own size cap.** New this
  window. `normalize_word` (line 1690) checks the input through
  `normalize_sub_word` (which *does* cap at `MAXNORMLEN = 256`, line 1464),
  but when `self.usecompound` is true it separately calls
  `self.split_to_variants(None, &[], word, 0, -1)` (line 1705) on the **full,
  unbounded** `word` with no length check at all. `usecompound` becomes true
  for the **shipped sample dictionary itself**:
  `crates/secantus-pgplan/src/tsearch_data/ispell_sample.affix:1` contains
  `compoundwords controlled Z`, which `import_affixes` turns into
  `self.dict.usecompound = true` (confirmed by direct read of the file and
  the parser at `ts_ispell.rs:470`). `split_to_variants` genuinely recurses
  (lines ~1628 and ~1664) at depth proportional to the number of
  compound-affix boundaries found in `word`, and separately,
  `check_compound_affixes` (line 1541) does an `O(remaining_len)` byte-window
  scan at every position once the dictionary trie stops matching — summed
  over the whole string this is `O(word_len² × affix_count)` even without
  deep recursion. The entry point has no size cap of its own:
  `ts_lexize(oid, token)` (`ts_dicts.rs:756`) → `lexize()`'s `Ispell` branch
  (`ts_dicts.rs:710-717`) calls `normalize_word` directly on the caller's
  `token`, and this path is **not** routed through `MAX_LEXEME = 2047`
  (`fts.rs:536`), which only guards `to_tsvector`/`to_tsquery`'s own
  tokenizer (`fts.rs:555-564`). `ts_lexize` is an ordinary two-argument SQL
  function with default `EXECUTE` granted to `PUBLIC`, matching real
  PostgreSQL.
  **Concrete trigger, no elevated privilege:**
  ```sql
  CREATE TEXT SEARCH DICTIONARY my_ispell (template=ispell, dictfile=ispell_sample, afffile=ispell_sample);
  SELECT ts_lexize('my_ispell', repeat('footballklubber', 2000000)); -- ~32MB
  ```
  (`footballklubber` is literally the sample dictionary's own documented
  compound-word test case, `ts_ispell.rs:1757-1767`, i.e. public PostgreSQL
  tutorial knowledge, not insider access.) A Rust stack overflow from deep
  recursion is an unrecoverable SIGSEGV/abort — since this server is a single
  multi-connection process (unlike real `postgres`, which forks a backend per
  connection), **this crashes the whole server for every connected client**,
  not just one session; even without hitting the recursion limit, the
  quadratic scan alone pins a CPU core for an attacker-chosen duration from
  one unprivileged query.
  **Fix direction:** cap `word.len()` before the `usecompound` branch in
  `normalize_word`, same as `normalize_sub_word` already does; separately,
  route `ts_lexize`'s input through the same `MAX_LEXEME` cap the tokenizer
  uses before calling any dictionary's `lexize`.

- **`crates/secantus-core/src/projection.rs`'s `filter_has_expr` and
  `crates/secantus-core/src/elem_match_key.rs`'s `leaves` — two new,
  independently unbounded `$and`/`$or`/`$nor` recursions in `find`'s
  positional-projection path, one at parse time before any document is
  read.** New this window (RM-286/287/296/297). `filter_has_expr`
  (`projection.rs:320-328`) recurses into nested `$and`/`$or`/`$nor` with no
  depth counter, called from `validate_projection` (`projection.rs:313`)
  during **parse-time validation of every `find` that uses a positional
  (`"arr.$"`) projection** — reachable with zero documents in the collection.
  `leaves` (`elem_match_key.rs:106-120`) has the identical shape, called from
  `elem_match_key::elem_match_key` (via `projection.rs:755`) once per matching
  document returned under a positional projection. Both are confirmed by
  direct read: neither function threads or checks a depth parameter. This is
  the same bug class the last three review cycles found reproduced in
  `expr_parse.rs`, `sbe.rs`, and `aggregate.rs`'s `validate_parse` — all three
  of which, per the carried-forward section below, are *still open* today, so
  this is now the **fifth and sixth living instance** of the identical
  unguarded-recursion shape in Rust MongoDB-server code alone.
  **Concrete trigger:**
  ```js
  db.c.find({"$and":[{"$and":[ /* tens of thousands deep */ ]}]}, {"arr.$": 1})
  ```
  A payload comfortably under BSON's 16 MB document limit nests deep enough
  to exhaust a thread's stack. Blast radius: Rust stack overflow aborts the
  whole process (not catchable — `catch_unwind` does not recover from a
  guard-page overrun), dropping every connected client, not just the
  attacker's connection.
  **Fix direction:** thread a depth counter through both functions and
  refuse past a bound, exactly the fix already proposed (and still
  outstanding) for `expr_parse.rs`/`sbe.rs`/`jsonschema.rs`/`json.rs` — this
  is now five-plus instances of the same missing structural fix.

- **`crates/secantus-commands/src/slowop.rs`'s `command_shown` — the new
  slow-query log and `getLog` buffer embed raw command documents with no
  redaction, including plaintext passwords and SASL/SCRAM payloads.** New
  this window (RM-299/185/303, RM-302). `command_shown` (`slowop.rs:258-264`)
  strips only an `insert`'s `documents` field before the command is recorded
  into the `Slow query` line's `command` attribute
  (`attributes`, `slowop.rs:292`) and written out via `log::info!` (line 135)
  to the server's own process log, as well as into the in-memory `getLog`
  ring buffer (`RM-302`). No field- or command-name-based redaction exists
  anywhere in this new path (confirmed by reading `command_shown` in full and
  grepping the new logging code for `redact`/`pwd`/`payload`: zero hits).
  `createUser`/`updateUser` carry a cleartext `pwd` field
  (`auth.rs:698,857,719,876` — confirmed `"pwd"` is a plain `Field::Str`
  command argument, not hashed before logging) and `saslStart`/`saslContinue`
  carry a `payload` field (`auth.rs:345,391` — cleartext for the PLAIN
  mechanism, and SCRAM proof/nonce material otherwise) that would be captured
  verbatim by `command_shown` the moment either command runs slower than
  `slowms` (default 100ms — plausible for a PBKDF2-backed SCRAM exchange) or
  with `slowms` set negative, which this project's own code already
  documents as mongod's "log every operation" mode. Real `mongod` explicitly
  redacts sensitive command fields from its diagnostic log and profiler for
  exactly this reason (this project's own CLAUDE.md-equivalent review
  instructions call out "nothing sensitive should hit logs" as a standing
  check, §5) — this surrogate implementation has no equivalent exclusion
  list.
  **Blast radius:** any operator with access to the server's stdout/log
  file, or any client able to call `getLog` (gated by whatever privilege this
  server requires for that command — not independently re-verified this
  cycle, but even operator-only log access is a real credential-disclosure
  path this project didn't have before this window), can recover a
  user-created password or an in-flight SCRAM exchange's payload.
  **Fix direction:** extend `command_shown` with the same kind of
  command-name/field-name redaction list real `mongod` uses — at minimum
  `createUser`/`updateUser`'s `pwd`, and `saslStart`/`saslContinue`/
  `authenticate`'s `payload`.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`crates/secantus-pg/src/lib.rs`'s `record_analyze` — `ANALYZE`'s
  extended-statistics pass lost its size gate and now runs over the
  **unsampled, full table** regardless of size, and the whole
  `VACUUM`/`ANALYZE`/`REINDEX`/`CLUSTER` family still has no
  ownership/privilege check.** New this window (RP-099, `7e530974`/
  `3bad0a3f`). Confirmed by direct diff read: the prior gate (`if docs.len()
  as u64 <= 300 * target { build_extended_statistics(...) }` — i.e. skip
  entirely for tables too large to fit the sample bound) was replaced with an
  **unconditional** `self.build_extended_statistics(table, &def, &docs,
  columns, target as usize)?` call, and `docs` at that point is
  `self.table_docs(table)?` — the full, unsampled table (`lib.rs:15068`); the
  later `acquire_sample_rows` call that actually samples happens
  *afterward* and only feeds the ordinary per-column stats, not the extended
  ones. So `build_extended_statistics`'s `ndistinct`/`dependencies`
  combinatorial work (already flagged above as uncapped in column count) now
  runs on every row of an arbitrarily large table, every time, rather than
  being skipped once the table outgrew the sample. Separately,
  `Statement::Maintenance`'s dispatch (`lib.rs:39739`) has no
  `is_owner`/`is_superuser` check anywhere in the function body (confirmed by
  direct read), so any authenticated role can `ANALYZE`/`REINDEX` a table it
  does not own. Trigger: `CREATE STATISTICS s (dependencies) ON c1..c30 FROM
  t; ANALYZE t;` from any session with `CREATE` on its own schema (the
  default posture), against any table including ones it doesn't own — a
  CPU/memory cost now proportional to full table size with no sampling
  relief, compounding the still-open column-count CRITICAL above.
  **Fix direction:** restore sampling before the extended-statistics call
  (or pass the already-sampled `docs`), and add the same ownership/superuser
  check views/schemas already use elsewhere in this file to the
  `Maintenance` dispatch.

## 🟡 INFO (Best-practice recommendations)

  dependency `ctutils` was bumped 0.4.2 → 0.4.5 across every `Cargo.lock`
  that pulls `digest`/`hmac`/`sha2`/`sha1` (which `crates/secantus-auth`

  the fix. Since this crate sits under this project's SCRAM auth stack, a
  timing side-channel in its constant-time primitives would have been
  directly relevant to credential verification; noting this explicitly so a
  future cycle doesn't need to re-discover it, and because it landed as a
  side effect of unrelated feature work rather than a deliberate security fix.

  added for the slow-query log) has no known advisory and is low-risk by
  nature — noted only for completeness since it's a new dependency this
  cycle.
- CVE-2026-34073 and CVE-2026-39892 (cryptography) surfaced in this cycle's
  routine re-search are very likely non-applicable to the pinned 48.0.0 (see
  WARNING section above) but were not pinned down to an authoritative

- The remaining carried-forward INFO notes from 2026-10-21 through

## 🟢 CLEAN (Passed review)

- **Path traversal / arbitrary file read — re-verified CLEAN for the new
  ispell and thesaurus dictionary templates.** Both go through the same
  mechanism already confirmed clean for `synonym`/`simple`/`snowball`:
  `config_file_name()` whitelists names to `[a-z0-9_]+` and the only "files"
  served are a small fixed set of compile-time `include_str!`-compiled
  constants. Directly confirmed `ts_ispell.rs`'s `import_dictionary`/
  `import_affixes` and `ts_thesaurus.rs`'s `Thesaurus::build` never call
  `std::fs::*`/`File::open`/build a filesystem `Path` from an option value —
  **no filesystem access of any kind occurs in this new code.** (The security
  issue found in this code, above, is CPU/stack exhaustion via the compound
  analyzer, not file access.)
- **`crates/secantus-pg/src/objaddr.rs`** (+1401 lines, all new): every
  element-indexing operation is preceded by an `exactly(n, ...)` length check
  or a nested `?`-returning guard; zero `.unwrap()`/`.expect()`/`unsafe`;
  all dynamic SQL goes through `quote_literal`/`quote_identifier`;
  nonexistent oids resolve to `NULL`/`XX000`, never a panic.
- **`crates/secantus-pg/src/pgstat.rs` / `pgstat_sql.rs`** (new): `pg_stat_reset()`
  and the single-object variants are correctly superuser-gated through the
  existing `restricted_builtins.tsv` → `check_sql_privileges` pipeline,
  matching PostgreSQL 15's default revoke-from-PUBLIC; no raw indexing, no
  `unsafe`, memoization caches are size-capped.
- **`crates/secantus-pg/src/btree.rs`** (new): purely server-internal model
  bookkeeping over already-validated SQL data, no `unsafe`, write-path
  failures are logged and the model re-marked dirty for retry.

- **Resolved this cycle:** none of the carried-forward CRITICAL/WARNING
  items were fixed; one (`extstats.rs`'s `mcv_items`) was refactored in a way

  window that adds new document/expression/dictionary-parsing code
  reproduces the unbounded-recursion and unbounded-allocation bug classes in
  the brand-new surface, this time in a B-tree-model deserializer, an ispell

  **unredacted sensitive command payloads reaching a diagnostic log**, via
  the new slow-query-log/`getLog` feature. Total known-open
  `security`-labelled issues before this cycle's filings: **124**.
- **Top 3 priorities for the team:**
  1. **Redact `createUser`/`updateUser`'s `pwd` and `saslStart`/
     `saslContinue`/`authenticate`'s `payload` from the new slow-query log
     and `getLog` buffer before this feature sees any wider use** — this is
     the first finding in this project's review history where a credential
     could be captured by a normal, already-landed feature rather than by an
     attacker-crafted request, and it is cheap to fix with a short
     command-name/field-name exclusion list.
  2. **Give the unguarded-recursion class a structural fix** — now six-plus
     living instances across both servers (`expr_parse.rs`, `sbe.rs`,
     `jsonschema.rs`, `json.rs`, `aggregate.rs`'s `validate_parse`, and this

     has been the top priority for four consecutive cycles; a shared
     `with_depth_guard`-style helper used by every new parser would stop this
     specific finding from reappearing in the next file that adds
     nested-document handling, which has now happened in every single
     review window since the pattern was first named.
  3. **Fix the two still-open unbounded-allocation-abort findings

     of lines of ordinary, unprivileged SQL, and PostgreSQL's own source
     already has the exact validation pattern to copy for the last of the
