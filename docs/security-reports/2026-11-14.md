## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **ALTER TABLE / DROP TABLE / CREATE INDEX / DROP INDEX / CLUSTER run with
  no table-ownership check at all** (high/critical, overall critical).
  The Rust PostgreSQL server's single universal per-statement privilege
  gate (`PgHandler::check_sql_privileges_inner`,
  `crates/secantus-pg/src/lib.rs:16901-16961`) derives its worklist from
  `secantus_pgplan::privileges::sql_relations`
  (`crates/secantus-pgplan/src/privileges.rs:254-311`), which models
  PostgreSQL's DML-only `ExecCheckRTPerms` and has **no match arm** for
  `IndexStmt`, `AlterTableStmt`, or a table-targeted `DropStmt` — they fall
  through a trailing `_ => {}`. Independently, none of the statement
  handlers implement an ownership check of their own: `check_alter_action`
  (`lib.rs:31118-31144`), including its `OwnerTo` arm
  (`lib.rs:31139-31141`, which only verifies the *named* role exists and
  then unconditionally accepts it), `create_index` (`lib.rs:17942-18030`),
  `check_drop_kinds` (`crates/secantus-pg/src/drop_kind.rs:137-167`, the
  sole gate for `DROP TABLE`/`DROP INDEX`, existence/kind-only), and the
  `Cluster` handler all mutate or delete a table with zero comparison of
  the caller's role to the table's recorded owner
  (`def.extra["owner"]`, set at `CREATE TABLE` time, `lib.rs:41759` —
  the state *is* tracked, just never read back). This is the exact
  `must be owner of <kind>` idiom the codebase correctly implements for
  databases (`database_ddl.rs:389`), schemas, views, subscriptions,
  text-search configs/dictionaries, transforms, and operator
  classes/families — simply never extended to tables, indexes, or (per
  the still-open #2696 below) functions/operators/casts. An independent
  adversarial verifier re-derived the full trace from scratch, specifically
  trying to refute the claim by searching for a check dispatched through
  any other gate, any role-membership path, and any test asserting the
  missing behavior, and confirmed none exists.
  **Fix:** add a `pg_class_ownercheck` equivalent (superuser, or
  `caller == owner`, or `INHERIT` membership in the owner role) at the top
  of the `AlterTable` dispatcher, inside/after `check_drop_kinds` for
  `DropTable`/`DropIndex`, in `create_index` before building the index, and
  in the `Cluster` handler; require membership in the new owning role for
  `OWNER TO` specifically.
  **Filed as a new issue**, cross-referencing the mechanistically-related,
  already-open **#1678** (the same `sql_relations` gate missing a
  `MergeStmt` arm) and **#2696** (the same "ownership never added for this
  object kind" family, different object kinds).

- **Unbounded recursion in the regex-selectivity estimator (RP-354, new
  this window) lets a `GROUP BY`/`DISTINCT` query with a `~` predicate
  abort the whole `secantusd-pg` process** (high/high, overall high).
  `crates/secantus-pgplan/src/colstats.rs`'s `regex_fixed_prefix`/
  `regex_prefix`/`regex_atoms`/`regex_selectivity`/`regex_selectivity_sub`
  — introduced this window by commit `c4a0d8ce` (confirmed absent at the
  prior report's HEAD via `git log -S`) — recursively descend into a
  client-supplied regex pattern string with no depth or length bound.
  `regex_selectivity_sub` (`colstats.rs:1244-1325`) recurses once per
  top-level parenthesized group and once per top-level `|` alternation; the
  anchored-prefix path (`regex_atoms`/`walk`) recurses once per `(` too. An
  independent verifier re-derived the true entry chain — reachable via a
  `GROUP BY` (`hash_agg_order_over`, `lib.rs:8198`) or `SELECT DISTINCT`
  query shape over a table that already carries `ANALYZE` statistics, not
  literally "every WHERE" as first framed — and confirmed both conditions
  are ordinary (any table with normal write volume is auto-`ANALYZE`d by
  `autovacuum.rs`'s launcher, matching real PostgreSQL's own default
  thresholds). The connection's worker-thread stack is set to 256 MiB
  (`crates/secantus-pg/src/server.rs:427`, specifically because an earlier
  `||`-chain incident overflowed the 2 MiB default and aborted the whole
  process, per the comment at `server.rs:628-634`), which raises the
  nesting depth needed into the low millions — but the ~1 GiB Parse-message
  size cap leaves enormous headroom over the few-MB payload actually
  required, so the larger stack does not meaningfully protect against this.
  No `catch_unwind` exists anywhere in `secantus-pg`, and a Rust stack
  overflow is a hard process abort (SIGSEGV on the guard page), not a
  catchable panic, regardless.
  **Fix:** convert `regex_selectivity_sub` (and `regex_atoms`/`walk`) to an
  explicit-stack iterative algorithm, or add a hard recursion-depth/
  pattern-length cap that falls back to `DEFAULT_MATCH_SEL` once exceeded.
  **Filed as a new issue.**

- **Unbounded recursive-descent JSON parsing in json/jsonb casts can
  stack-overflow and abort the whole `secantusd-pg` process — a NEW file
  (`json_lex.rs`, added this window) independently duplicates an
  already-tracked defect in a second parser** (medium/high, overall high).
  Casting client-controlled text to `json`/`jsonb` runs
  `crates/secantus-pgplan/src/json.rs`'s `parse_value`/`parse_array`/
  `parse_object` with no depth bound — this is the exact, already-tracked
  defect in open issue **#2110** (filed 2026-10-23, re-confirmed still
  unfixed today). If that parse fails, `json_input_error` calls the new
  `crates/secantus-pgplan/src/json_lex.rs`'s `Lexer::parse()` ->
  `value()`/`array()`/`object()`/`object_field()` (`json_lex.rs:141-224`,
  added this window, +597 lines) — an independent recursive-descent
  re-walk of the same text, **also** with no depth bound, and not
  mentioned anywhere in #2110's text. Either recursion, given deep enough
  nesting, exhausts the call stack and aborts the whole process (same
  256 MiB worker-stack and no-`catch_unwind` facts as the regex finding
  above, independently re-confirmed for this candidate too).
  **Fix:** add an explicit recursion-depth counter to both `json.rs`'s
  `parse_value`/`parse_array`/`parse_object` and `json_lex.rs`'s
  `value`/`array`/`object`/`object_field`, refusing with SQLSTATE 54001
  past a bound sized to the worker stack.
  **Action split**: commented on **#2110** confirming `json.rs`'s
  recursion is still unfixed as of today's HEAD; **filed a new issue** for
  `json_lex.rs` specifically, since it is a new file this window
  implementing the identical defect in a second, independent parser,
  cross-referencing #2110.

## 🟢 CLEAN (Passed review)

- **The MongoDB `$queryStats`/profiler/slow-op/query-shape/diagnostics
  rework**: `$queryStats` requires the `queryStatsReadTransformed`/
  `queryStatsRead` cluster privileges, enforced before any row is produced,
  and granted only to cluster-monitor/admin-shaped roles, never
  read/readWrite; every stored query shape routes literal values through a
  `representative()`/debug-type shapify step before storage, so no raw

  reader; `system.profile` records are written to and readable only
  through their own database's namespace, matching mongod's per-database
  scoping; the server-wide `QueryStatsStore` has a real, enforced memory
  cap with LRU eviction, and raising that cap requires the admin-only
  `setParameter` privilege.
- **The MongoDB command-surface wiring pass**, including `notablescan.rs`'s
  removed `plan_and_check` helper: the distinct-of-a-view path was
  refactored to run through the standard `aggregate()` command instead,
  which still resolves the view to its base collection and still calls
  `notablescan::check` on it — the table-scan refusal is preserved, not
  bypassed. `getMore` cursor-ownership enforcement, and the namespace/admin
  checks in `crud.rs`/`findandmodify.rs`/`admin.rs`/`bulkwrite.rs`, all
  survived this window's parse/validate-split refactor (RM-386) unchanged
  in substance, only reordered relative to the extracted field-parse code.
  No new aggregation stage skips the foreign-namespace `notablescan` check
  applied to sibling stages.
- **The MongoDB aggregation spill-to-disk rework** (beyond the WARNING
  above): no write/flush/close `Result` is swallowed anywhere in the new
  `spill_file.rs`/`spill_table.rs`/`secantus-storage/src/spill.rs`/
  `lockfile.rs`; cleanup (`Drop` impls) runs on every exit path including a
  mid-write failure; the memory-budget check gates every accumulation path
  consistently across `$group`/`$setWindowFields`/sort, matching mongod's
  own check-after-add-one-item model; the new `lockfile.rs` correctly fails
