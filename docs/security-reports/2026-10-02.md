## The new finding this cycle — confirmed by running the code, not by reading it

**New CRITICAL — schema-qualified table references silently bypass ALL
privilege checking on the Rust PostgreSQL server.** This cycle's
schema-qualified-relations feature (`fc1715f9`, "feat(pgserver): schema-
qualified relations on the Rust server") stores any relation outside
`public` under the catalog key `"schema.name"` (`crates/secantus-pgplan/src/
schemas.rs:1`-`16`, `relation_key`) and rewrites every `RangeVar` in the
parsed AST to that key before planning (`schemas.rs::qualify`). But the
privilege gate, `crates/secantus-pgplan/src/privileges.rs`'s `sql_relations`,
extracts relation names straight off `RangeVar.relname` and never looks at
`RangeVar.schemaname` (the `InsertStmt`/`UpdateStmt`/`DeleteStmt`/
`TruncateStmt`/`CopyStmt` arms at lines 30-72, and the generic `SELECT`
RangeVar walk at lines 90-96) — `schemaname` is consulted only to special-
case `pg_catalog`/`information_schema`. Confirmed by execution, not
inference: built `secantus-pgplan` standalone and ran

```rust
secantus_pgplan::privileges::sql_relations("SELECT * FROM myschema.secret")
```

which returns **`[("secret", "SELECT")]`** — the schema qualifier is
silently dropped. The same holds for `INSERT INTO myschema.secret VALUES
(1)` → `[("secret", "INSERT")]` and `DELETE FROM myschema.secret` →
`[("secret", "DELETE")]`.

`check_sql_privileges` (`crates/secantus-pgserver/src/lib.rs:6926`) passes
that bare name straight to `check_privilege_as` (`lib.rs:1665`), which does

```rust
let Some(def) = self.lookup(table) else { return Ok(()); };
```

(`lib.rs:1681`-`1683`) — and `lookup`/`lookup_inner` (`lib.rs:12994`,
`13010`-`13062`) resolve a name with a single exact-match catalog read,
`bson::doc!{"_id": name}` (`lib.rs:13043`), with **no schema resolution at
all**. Since the table's real catalog `_id` is `"myschema.secret"`, looking
it up as bare `"secret"` finds nothing, and the lookup miss is treated as
**fail-open, not fail-closed**: `return Ok(())` grants the request with no
check performed, rather than erroring. The statement then proceeds to the
real execution path, which *does* resolve `myschema.secret` correctly via
`schemas::qualify` and reads/writes the real table.

Concrete exploit: role `alice`, authenticated, zero grants of any kind,
not the owner, on a table `secret` that another role `bob` created inside
schema `myschema` (`CREATE SCHEMA myschema; CREATE TABLE myschema.secret
(...)`, owned by `bob`, no grants to `alice` or `PUBLIC`). `alice` runs
`SELECT * FROM myschema.secret`, or `INSERT INTO myschema.secret VALUES
(...)`, or `DELETE FROM myschema.secret` — all three bypass privilege
checking entirely and succeed. (If a same-named bare `public.secret` table
also exists, the lookup instead silently checks the **wrong** table's
grants — a related, separate correctness bug, but the zero-table case above
is the clean privilege-bypass.) This is the same severity class, and the
identical "read off the raw SQL text, not the catalog-resolved relation"
root cause, as yesterday's filed `MERGE` CRITICAL (**#1678**) — a new
feature landed without a matching update to the one function every write
path is supposed to funnel through for authorization.

Not reachable from an unauthenticated connection — PG-wire auth is unchanged
this cycle (§5b below) — but needs no privilege beyond a bare authenticated
session, exactly like **#1678** and **#1160**.

**Filed as new GitHub issue #1706, graded CRITICAL.**

## The second new finding — a second unauthenticated CPU-pinning DoS, on the SQL surface this time

**New CRITICAL — SQL `regexp_replace`/`regexp_match`/`regexp_matches`/
`regexp_split_to_array`/`regexp_count`/`substring(... FROM pattern)` compile
an attacker-supplied regex with no length cap, no cache, and no backtracking
guard — the same bug shape already filed as CRITICAL for the Mongo-wire
`$regex` operator (#977), on the Python PostgreSQL server's scalar-function
surface instead.** `src/secantus/sql/scalar.py:1621`-`1635` (`_re_compile`)
takes a pattern straight from the SQL statement (a string literal or a
column value) and calls plain `re.compile(pattern, f)` — no
`_MAX_REGEX_PATTERN_LEN`-style cap, no `lru_cache`, unlike the existing
mitigation for the Mongo query engine in `src/secantus/query.py:1418`-`1435`
(`_compile_regex`, capped at 1000 chars, cached). Python's `re` module has
no match timeout, so a pattern with catastrophic backtracking —
`(a+)+$`-shaped — applied to a crafted input hangs the connection's worker
thread indefinitely. Call sites reached from ordinary SQL: `scalar.py:1393`
(`substring(... FROM pattern)`), `:1652` (`regexp_match`), `:1695`
(`regexp_count`), `:4923`/`:4932` (`regexp_matches` non-SRF path /
`regexp_split_to_array`), `:5255` (`regexp_replace`), and
`src/secantus/sql/srf.py:472` (`regexp_matches` as a set-returning
function). Every one of these is an ordinary scalar SQL function a client
calls directly — `SELECT regexp_replace('x', '(a+)+$', 'y')` is enough.

This is pre-existing code (unchanged in this cycle's diff — `scalar.py` was
touched this cycle but not at these lines, and the gap predates the window
reviewed), not something this cycle's commits introduced; it surfaced
because this cycle's agent slice specifically re-checked `scalar.py` for the
regex-DoS shape CLAUDE.md flags as a recurring bug class, and — unlike
`query.py`'s `$regex` path — no prior report in this series had reviewed the
*SQL* regex functions as a distinct surface from the Mongo one. Graded
CRITICAL to match the established severity for this exact bug shape
(unauthenticated-or-bare-session CPU-pinning DoS via catastrophic
backtracking) already applied to #977, since the mechanism, reachability,
and impact are identical — only the wire protocol differs.

**Filed as new GitHub issue #1707, graded CRITICAL.**

  time in this series a CRITICAL was established by executing code under

  CRITICAL and zero new WARNING**, and the first of the two CRITICALs is the
  **same root cause as yesterday's**, recurring in a *different* new
  feature one day later: a new SQL construct (first `MERGE`, now a
  schema-qualified table reference) lands without updating
  `privileges.rs::sql_relations`, the single function every write path is
  supposed to route authorization through. The second CRITICAL
  (SQL-surface regex ReDoS) is a different mechanism but the same
  "the Mongo-wire mitigation didn't travel to the PostgreSQL-wire
  equivalent" pattern already seen in this codebase's own documented bug-
  class list.
- **Top 3 priorities for the team:**
  1. **The privilege-check-omission pattern needs a structural fix, not a
     third patch.** Two cycles running, a new top-level SQL construct
     (`MERGE`, now schema-qualified `RangeVar`s) has landed without a
     matching update to `privileges.rs::sql_relations`, and in both cases
     the omission fails OPEN — zero privilege entries means zero checks,
     not a conservative refusal. Beyond fixing the two instances (add a
     `MergeStmt` arm; make `sql_relations` resolve `schemaname` through the
     same `schemas::relation_key` the planner uses, and make
     `check_privilege_as`'s `lookup` miss at `lib.rs:1681`-`1683` an error
     rather than a silent pass), the systemic fix recommended in this report
     series for two cycles now — a lint or test that fails CI when a new
     statement/AST-node type reaches execution with no corresponding
     privilege-table entry on either server — would have caught both.
  2. **Port the Mongo-wire regex-DoS mitigation to the SQL scalar-function
     surface.** `query.py`'s `_MAX_REGEX_PATTERN_LEN` + `lru_cache` pattern
     (already a known-incomplete fix per the standing #977 — its `TypeError`
     fallback still escapes the cap) needs an equivalent in
     `scalar.py::_re_compile`, which currently has no cap at all. Given both
     servers now have an unauthenticated-or-bare-session CPU-pinning DoS via
     regex, this is no longer a single-surface issue.
  3. **The three long-standing whole-server-DoS-from-one-request CRITICALs
     (`#995`, `#1160`, the original `#977`) and the CTE blow-up (`#1636`)
     remain unmoved across many review cycles now, and the open CRITICAL
     count has grown for two cycles running** (5 → 6 → 7). With feature work
     continuing to land on top of an unfixed privilege-check-omission
     pattern, scheduling at least the structural fix in priority 1 ahead of
     further PostgreSQL-wire feature surface would stop the count from
     growing a third time.
