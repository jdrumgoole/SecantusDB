Diff-driven review against the 16 commits that landed since the last report

`origin/main` throughout this review). Ten are real code changes; the other
six are a `CLAUDE.md` prose-only edit (`132674d5`), a `tasks/` planning-doc

landing commit (`af9f3972`, meta, not reviewable application code). Two
sub-agents (foreground, one per Rust server — this repo's own convention of
"one session per server" extended to review) read every real commit's
production-code diff end to end; the dependency/workflow/wheel/secrets
sections were done directly in this session against the GitHub, crates.io
and RUSTSEC-adjacent sources rather than quoted from a prior cycle.

The ten real commits: `9d129460` (Rust PG server: backlog batch — built-in
coverage, typed values, a new full-text-search word parser `wparser.rs`,
window-function output order), `a1150430` (Rust MongoDB server: admin/
diagnostic commands — `hostInfo`, `replSetResizeOplog`/`replSetInitiate`/
`appendOplogNote`, plan-cache commands), `44d34ba7` (Rust PG server: GRANT/
REVOKE visible inside the issuing transaction block), `bd0198fa` (Rust
MongoDB server: register a collection a transaction creates when it
commits), `a7b32d97` (Rust PG server: composite fields, PostgreSQL's
transaction-id/`age(xid)` model), `95a28986` (bulkWrite retries, upserted
ids, clustered TTL, dropped indexes, view depth), `677a7d52` (rebuild old or
foreign collated/geo indexes when a store opens — touches both servers),
`e96bf7f0` (Rust PG server: `json`'s own text/encoding functions, 52 more
built-ins), `4f365088` (Rust MongoDB server: `dbHash`, `logRotate`,
`connPoolStats`, `setDefaultRWConcern`, `setFeatureCompatibilityVersion`),
`44dafb91` (Rust PG server: literal row decode, `pg_lsn`, eight silent
wrong answers).

**Net result: 2 new CRITICAL findings, 2 new WARNING findings.** Both
CRITICALs are new, unguarded-recursion stack-overflow-DoS sites in the Rust
PostgreSQL server's new text-processing code — the same bug *class* this
project's tracker already carries ~20 open instances of, found again in
code landed this cycle. One WARNING is a reachable (but caught) panic in a
new admin command; the other is a previously-undiscovered authorization
gap in SQL `GRANT`/`REVOKE` itself, found while reviewing a commit that
touched the surrounding code without introducing the gap.

## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Unguarded recursion in the new `json` (non-`jsonb`) parser —
  unauthenticated stack-overflow DoS, crashes the whole process.**
  `crates/secantus-pgplan/src/json.rs:572`'s `value()` (added in `e96bf7f0`,
  "Rust PG server: json's own text, encodings, and 52 more built-in
  functions") recurses once per `[`/`{` byte it meets while walking a
  `json`-typed literal, with **no depth counter anywhere in the file**
  (confirmed: `grep -n "depth\|MAX_" json.rs` returns nothing). The
  project's own SQL-statement depth guard (`MAX_EXPR_DEPTH = 2500`,
  `check_depth()` at `crates/secantus-pgplan/src/lib.rs:3679,3770`) cannot
  see into this: a JSON literal is one opaque string token to that guard, so
  arbitrarily deep bracket nesting *inside* the string is invisible to it.
  Reachable via any client statement that applies a `json`-path operator to
  a nested literal, e.g. `select '[[[[...100000 deep...]]]]'::json -> 0`
  (confirmed call sites at `crates/secantus-pgplan/src/lib.rs:11387,30368`
  and `jsonops.rs:425`). A Rust stack overflow is a hard process abort, not
  a catchable panic — it bypasses `catch_unwind` entirely regardless of
  whether one is installed, so this takes down every connection, not just
  the attacker's. **No auth required** (SQL parsing happens before/
  independent of the privilege gate). Needs: a depth-tracked iterative
  parser or an explicit recursion-depth cap inside `json.rs`, matching the
  pattern already used for the top-level SQL statement guard.

- **Unguarded recursion in the new `ts_rewrite()` tree walk — stack-overflow
  DoS via a client-controlled tsquery.** `crates/secantus-pgplan/src/
  ts_rewrite.rs` (new file, `9d129460`) implements PostgreSQL's
  `tsquery_rewrite.c`/`QTNode` machinery. Its `sort` (line ~196), `ternary`
  (~210), `binary` (~231) and sibling walks each recurse once per child with
  **zero depth check** — confirmed absent via `grep -n
  "depth_guard\|MAX_DEPTH"` on the file, versus the project's own idiom for
  exactly this hazard class, present elsewhere (`lib.rs:3770`,
  `grace_join.rs:41`). The tree depth is driven directly by the number of
  boolean operators in a client's `to_tsquery(...)` argument: a statement
  like `select ts_rewrite(to_tsquery('a&a&a&...&a' /* ~10^5 terms */),
  to_tsquery('x'), to_tsquery('y'))` builds a tree deep enough to exhaust the
  stack and abort the whole server process. **No auth required.** The
  underlying tsquery-parsing recursion in `fts.rs` this tree comes from is
  itself unguarded too (pre-existing, out of this cycle's diff, not newly
  introduced — but `ts_rewrite()` is a brand-new SQL-callable entry point
  that adds several more unguarded walks over the same unguarded tree, so it
  independently qualifies as new).

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`replSetResizeOplog` panics on a non-finite (`Infinity`/`-Infinity`)
  `size` or `minRetentionHours` — caught, but reachable from unauthenticated
  wire input.** `crates/secantus-commands/src/replset_admin.rs:117`'s
  `render_g()` formats an out-of-range bound/value for the error message; for
  `x = Infinity`, `format!("{x:.5e}")` renders the literal string `"inf"`
  (Rust's `LowerExp` has no exponent marker for non-finite floats), so the
  `split_once('e').expect("exponent form")` at line 124 panics.
  `resize_number()` (line 141, new this commit) converts the client's BSON
  field to `f64` and only special-cases `NaN` (→ 0.0) — `Infinity`/
  `-Infinity` pass through unchanged into the comparison that triggers
  `render_g`. Reproducible with `{replSetResizeOplog: 1, size: Infinity}` (a
  valid BSON double). The panic **is** caught — `crates/secantus-server/src/
  lib.rs:952` wraps `dispatch` in `std::panic::catch_unwind`, confirmed
  present and unchanged — so this degrades to one failed request rather than
  a process crash or a wedged connection, which is why this is WARNING and
  not CRITICAL. `replSetResizeOplog` requires the `replSetResizeOplog`
  cluster privilege under `--auth` (confirmed: `authz.rs:348` area carries a
  real match arm — see CLEAN section), but `--auth` is off by default.

- **SQL `GRANT`/`REVOKE` has no ownership, superuser, or `WITH GRANT
  OPTION` check on the CALLER — any authenticated role can grant itself (or
  anyone) arbitrary privileges on any table, schema, sequence, or function.**
  Found while reviewing `44d34ba7` ("GRANT and REVOKE take effect inside the
  block"); the gap itself is **pre-existing** in code that commit did not
  touch, not introduced by it — `44d34ba7` only changed whether a GRANT is
  visible to later statements in the same open transaction
  (`within_block(...)` at `crates/secantus-pg/src/lib.rs` around the call
  sites of `check_sql_privileges`), which is orthogonal.
  `fn grant()` (`crates/secantus-pg/src/lib.rs:10638`, the table-kind path)
  and `fn grant_object()` (`crates/secantus-pg/src/object_acl.rs:183`, the
  schema/sequence/function-kind path) both walk straight from parsed
  arguments to writing the ACL/grant collection — neither calls
  `object_privilege_held()` (`object_acl.rs:157`, the helper that already
  exists and already checks superuser / ownership / membership / existing
  grants-with-option, and which other code paths use to check whether a
  role may *read* an object) against the **issuing role's own** authority to
  grant. `check_sql_privileges()` (`lib.rs:9261`), the general gate every SQL
  statement passes through before executing, does not help either: it works
  from `secantus_pgplan::privileges::sql_relations(sql)`, which extracts only
  DML-style table references and their required SELECT/INSERT/UPDATE/DELETE
  privilege — confirmed (`grep -n Grant privileges.rs` has no hits) that it
  never inspects a `Statement::Grant` at all. Net effect: a role with zero
  privileges can run `GRANT ALL ON any_table TO any_role` (including itself)
  and the server applies it unconditionally — a full bypass of the PG
  server's own privilege model, not merely a missing check on one statement
  kind. No existing tracked issue matches this (searched `gh issue list
  --label security --state all --search GRANT`; the closest, #1678 "MERGE
  bypasses all table privileges for its target", and #1723/#1724, are about
  *using* a privilege they don't hold, not about *creating* privileges out of
  nothing).

  (`crates/secantus-pg/src/lib.rs:571`) and `expr_index.rs`/
  `scan_partitions.rs:167` now call `secantus_core::bsondoc::from_bytes`
  instead of serde's `bson::from_slice`/`Document::from_reader` — the exact
  fix this project's own `CLAUDE.md` prescribes for the extended-JSON-
  sniffing decode bug class (a `{$numberLong: "1"}`-shaped sub-document no
  longer gets silently reinterpreted as a typed value on read).
- **`a7b32d97`'s new xid/transaction-id code has no unchecked arithmetic on
  client-controlled values**: `xids.rs`/`snapshots.rs` use
  `wrapping_sub`/`checked`-style conversions throughout; its new recursive
  `composite_type` parsing in `pgplan/lib.rs` is transitively covered by the
  existing `check_depth`/`MAX_EXPR_DEPTH` guard (a composite-field chain
  costs more source characters per nesting level than that guard's
  short-circuit threshold assumes, so it cannot be used to exceed the guard
  before being rejected on length grounds first).
- **No new `unsafe` block anywhere in the ten commits** introduces a new
  pattern: the one new raw-pointer use (`bd0198fa`'s deferred-create
  handling) and the two in `9d129460` (`schemas.rs`, `unknown_args.rs`)
  each reuse an existing, already-reviewed idiom (`active_handle()`/
  `nodes_mut()`) with a matching SAFETY comment, not a new design.
- **`wparser.rs`/`states.rs`'s one recursive construct (`sub_token`) is
  self-limiting** — it consumes a `bool` via `mem::take`, capping nesting at
  depth 2 regardless of input length — and **`sbcs.rs`'s `direct_byte`**
  checks `b < 0x80` before every subtraction that feeds an array index, so
  neither is a new recursion/panic site despite being large new files.
- **No swallowed storage error.** `677a7d52`'s `let _ =
  session.rollback_transaction(None)` (index-rebuild-on-open path) is
  best-effort cleanup immediately *before* propagating the real `Err(e)` from

  an instance of the "swallowed `Result` on a write/commit/close path"

## 📊 Summary

- **Date of review:** 2026-10-15.
- **SecantusDB version reviewed:** Python `0.7.0b3` (unchanged this window);
  Rust MongoDB-server crates `0.5.3-beta.195` (bumped from `0.5.3-beta.194`
  by the already-reviewed `80afdb48`, not by this window's real commits);
  Rust PostgreSQL-server crates `0.1.0-beta.16` (bumped from `0.1.0-beta.15`,
  same commit).
- **This cycle's new findings:** 2 CRITICAL (unguarded recursion in
  `secantus-pgplan::json::value` and `secantus-pgplan::ts_rewrite` — both
  unauthenticated stack-overflow-DoS, both in new Rust PostgreSQL server
  code), 2 WARNING (`replSetResizeOplog`'s caught-but-reachable panic on a
  non-finite float; SQL `GRANT`/`REVOKE` having no caller-authorization
  check at all), plus several INFO notes (new dependency provenance, a
  routine `rustls` advisory-fix confirmation, two config-only diffs).
- **Resolved this cycle:** none — no commit in this window's message or
  diff references closing a tracked `security`-labelled issue, re-confirmed
  against the live tracker (88 open both before and after this review's new
  filings, pending the four new issues filed below).
- **Comparison with previous report (2026-10-14):** that cycle found zero
  new findings and instead reported substantial RBAC-rewrite progress on the
  Rust MongoDB server. This cycle reverses that: zero MongoDB-server
  findings of note (its new admin/diagnostic surface area is cleanly gated
  by the RBAC rewrite that landed last cycle — see CLEAN), and all four new
  findings are in the Rust PostgreSQL server, which had the larger share of
  real commits this window (6 of 10) and the two genuinely new attack
  surfaces (a full-text-search word parser, a `json`-type text/operator
  surface).
- **Top 3 priorities for the team:**
  1. **Add a depth guard to `secantus-pgplan::json::value()` and to
     `ts_rewrite.rs`'s tree walks** — both are unauthenticated,
     process-crashing stack-overflow DoS, reachable by any TCP client
     regardless of `--auth`, and both have an existing in-repo pattern
     (`MAX_EXPR_DEPTH`/`check_depth`, `depth_guard`) to copy rather than
     design from scratch.
  2. **Gate SQL `GRANT`/`REVOKE` on the caller's own authority** — wire
     `object_privilege_held(caller, kind, name, privilege, with_option:
     true)` (or ownership/superuser) into `grant()` and `grant_object()`
     before they mutate the ACL collections; the helper already exists and
     is already used for read-side checks, so this is a narrow fix, not a
     new subsystem.
  3. **Bump the `pymongo` floor to `>=4.18.2`** (#1742) — still the cheapest
     fix in the whole open tracker, unchanged for a second cycle, against a
     CVSS-8.4 heap-out-of-bounds-write CVE in the BSON encoder every
     Python-server document write uses.

If any of the above is superseded by a fix landed after this report was
written, the next review cycle is expected to catch it via re-execution
against the oracle and against the GitHub/crates.io APIs — per this
project's own standing rule, not by re-reading this document's claims.
