## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Compound wildcard- and `2dsphere`-index key generation builds an
  uncapped Cartesian product over array-valued ordinary fields, with an
  additional O(n²) dedup making a ~20 KB document enough to pin a core —
  an unauthenticated-in-default-mode remote resource-exhaustion DoS of the
  single shared server process** (high/high, overall high, confidence high;
  **issue #2971**). `crates/secantus-storage/src/lib.rs:2284-2325`
  (`IndexDesc::wildcard_key_values`) and `crates/secantus-storage/src/lib.rs:2710-2734`
  (`GeoSphere::key_values`) each multiply the in-progress index-key list by
  every value of every *ordinary* (non-wildcard, non-geo) field in a
  compound index's key spec whenever that field holds a BSON array in the
  document being written — via `.flat_map` with no counter, no break, and
  no size check. The sibling path for ordinary compound multikey indexes,
  `index_key_values_c` (`lib.rs:4655`, cross-product at `lib.rs:4718-4742`),
  explicitly caps the identical computation at `MAX_COMPOUND_KEYS = 10_000`
  (`lib.rs:1874`), with its own comment stating this exists "to avoid
  exponential blowup when multiple fields are array-valued" and that the
  codebase deliberately does **not** implement mongod's `171
  CannotIndexParallelArrays` refusal, relying on the cap as the substitute
  control. Neither new function ports that cap. `crates/secantus-commands/
  src/admin.rs:3668-3681`'s `createIndex` validation does not reject a key
  spec mixing `$**`/`2dsphere` with one or more ordinary fields (only a
  32-key-field count limit applies, `admin.rs:3683`), so `createIndex({a: 1,
  "$**": 1})` or `createIndex({loc: "2dsphere", a: 1, b: 1})` is accepted
  outright. `createIndex` requires only the ordinary `readWrite` role
  (`crates/secantus-commands/src/builtin_roles.rs:200`), the same role as
  `insert`, and **auth is off by default** (`Builder::default()`,
  `crates/secantusdb/src/lib.rs:229`), so in the documented default
  configuration this requires no credentials at all. An independent
  verification pass additionally found the practically decisive factor the
  original trace missed: `wildcard_key_values`'s dedup at `lib.rs:2319`
  (`if !out.contains(&k)`) is a linear scan of the whole accumulated output
  per candidate key — O(output²) — against mongod's own O(n log n)
  sorted-set dedup, so a document as small as roughly 20 KB (one array of
  ~1,000 small integers in the ordinary field, ~1,000 wildcard leaves) is
  enough to pin one core for tens of minutes; a few hundred KB is enough to
  OOM-kill the single shared process outright. Growth is polynomial (nᵏ for
  k array-valued ordinary fields, maximised within the 16 MB
  `maxBsonObjectSize` cap at k≈2, ≈(750K)² ≈ 5.6×10¹¹), not exponential as
  the raw field count might suggest. The operation is **uninterruptible**:
  no `maxTimeMS`/`killOp` poll exists inside key generation (the nearest
  deadline check, `lib.rs:14821-14824`, runs only after a retryable-write
  batch completes). `GeoSphere::key_values`'s `maxCellsInCovering` parameter
  is not attacker-controlled (it is absent from `admin.rs`'s
  `INDEX_SPEC_KNOWN_OPTIONS` and would be rejected as an unknown field, so
  the S2 covering is pinned at its default size) — the ordinary array
  fields are the sole attacker-controlled lever for both index kinds.
  **Independently confirmed twice** (the original hunter plus my own direct
  source re-derivation) and then **independently re-verified a third time**
  by a fresh agent with no access to either prior pass's reasoning, which
  corrected the growth-rate framing and surfaced the O(n²) dedup as the
  dominant real-world cost — all three passes converge on the same two
  `file:line` root causes. This is the fourth distinct instance, across this
  review series, of the same uncapped-combinatorial-explosion pattern this
  codebase has already named and partially guarded against elsewhere (see
  #2954 and #2763), newly introduced by this window's index-fidelity work
  and uniquely reachable from the ordinary write path rather than a read or
  admin path. **Fix (smallest effective, mirroring the existing sibling
  exactly):** (1) replace the `if !out.contains(&k)` linear-scan dedup at
  `lib.rs:2319` with a `HashSet`-keyed dedup, the same pattern
  `index_key_values_c` already uses; (2) add the same `MAX_COMPOUND_KEYS`
  break-both-loops cap to both `wildcard_key_values` (`lib.rs:2290-2322`)
  and `GeoSphere::key_values` (`lib.rs:2715-2732`) that `index_key_values_c`
  already carries at `lib.rs:4730`/`4737`. The more faithful fix per
  CLAUDE.md's "always the most faithful implementation" and "never a
  stand-in of our own" — recommended as the follow-up, not a blocker for
  the immediate cap — is to implement mongod's own `171
  CannotIndexParallelArrays` refusal in index key generation, reusing the
  sort-key-side machinery that already exists for it
  (`secantus-core/src/paths.rs`'s `sort_key_refusal`/`PARALLEL_ARRAYS_MESSAGE`),
  which would let `MAX_COMPOUND_KEYS` be removed everywhere rather than
  merely ported to two more call sites. **Filed as new issue #2971.**
