## What's new since the last review

Twenty commits landed since 2026-07-28's `d2ddd133` cutoff (`git log
d2ddd133..HEAD`). Two carry substantive code changes; the rest are release
mechanics (version bumps, changelog collation, two `Release vX.Y.Z` commits)
or docs/site content. Each substantive commit reviewed in full:

- **`09e12cae` — Lazy shard creation (both servers) + fix `Storage.close()`
  shutdown hang (#680).** Both servers now create the 16 documents shards and
  16 oplog shards on demand (first collection-create / first oplog write)
  instead of all 32 eagerly at open, cutting per-open WT `create()` calls from
  ~37 tables to ~13 + only what's used. Every read/scan/merge/delete/rename
  path was audited for the corresponding "shard doesn't exist yet" case:
  - Python: a new `_cursor_optional()` wraps `_cursor()` and returns `None` on
    a WT "table does not exist" error, treated identically to an empty shard
    at every call site (`read_oplog`, `oplog_floor_seq`, `_scan_docs`,
    `_docs_by_recordids`, `_collect_prefix`, etc.). `_is_missing_table()`
    matches on the substring `"No such file or directory"` in the exception
    string — this only fires on a genuine WT cursor-open ENOENT (there is no
    path where user-controlled document content reaches this string), so a
    false-positive silent-empty-read is not reachable; noted as a minor
    robustness nit (a specific errno/error-code check, as the Rust side does,
    would be more future-proof than string matching) rather than a finding.
  - Rust: `WtError::is_missing_table()` checks the WT error **code** (`== 2`,
    POSIX `ENOENT`) rather than a string — the more robust of the two
    implementations, confirmed at `crates/secantus-wt/src/lib.rs`. Every
    `open_cursor` call on a shard table across `secantus-storage/src/lib.rs`
    now matches `Err(e) if e.is_missing_table()` explicitly rather than
    propagating a raw error.
  - Separately, `Storage.close()` previously joined the TTL-sweeper /
    noop-heartbeat threads with a 2s timeout and then tore WiredTiger down
    regardless — under load this could close a still-live thread's WT session
    cross-thread and hang `WT_CONNECTION->close` forever (a real shutdown-hang
    bug, not a security issue per se, but relevant to the "never ignore an
    error" storage discipline: a hung close previously surfaced as an
    anonymous killed worker rather than a diagnosed failure). Fixed by joining
    to completion before teardown and having each background loop close its
    own thread-local session in a `finally` on its owning thread. This is a
    correctness/reliability fix with no new attacker-reachable surface — no
    wire input drives shard creation timing or the close path.
  - No new `eval`/`exec`/network/subprocess calls; no path/URI built from wire
    input (shard names are still derived from a fixed hash of `(db, coll)`,
    unchanged from the eager-creation scheme).
- **`9fdab88a` — fix(rust): tolerate absent shard when dropping a
  never-written collection (#681).** Follow-on to the above: `drop_collection`
  no longer errors when a lazily-never-created shard is dropped. No
  wire-facing or auth-relevant change; regression-tested.
- **`.github/workflows/release-binaries.yml`** (127 lines) — reworked the
  arm64-macOS on-target PGO build into a self-written-profile path (moved
  `macos-14` → `macos-15` runner; both GitHub-hosted). No `${{ github.event.*
  }}` expanded into `run:`, no new `secrets.*` reference, all `uses:` lines
  remain the same SHA-pinned actions as before. Build-only change, not part of
  the shipped artifact's runtime.
- **`crates/secantusdb/src/main.rs` / `crates/secantusdb/Cargo.toml`** — a new
  `pgo-instrument` Cargo feature (off by default, symbols only exist under
  `-Cprofile-generate`) adds an `unsafe` FFI call to
  `__llvm_profile_set_filename`/`__llvm_profile_write_file` on shutdown,
  writing to a path taken from the `SECANTUS_PGO_OUT` env var. Reviewed: this
  path is compiled in only for the CI-only instrumented stage-1 PGO build (the
  optimized stage-3 build and every shipped binary/wheel build without the
  feature), the env var is set by the release workflow itself (not
  attacker-influenced), and a failed `CString::new` (embedded NUL) is handled
  with `if let Ok`. No exposure in the shipping artifact.
- `mimalloc` became an optional/default-on Cargo feature (same rationale,
  toggled only by the PGO instrumented build) — no dependency added or
  removed, confirmed by diffing every `Cargo.lock` for added/removed `name =`
  lines (none; only version-bump lines changed).
- Release mechanics: `pyproject.toml` / `src/secantus/__init__.py` bumped

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open — 9th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:3921` and `:4000` (line numbers
shifted from `:3878`/`:3957` by the lazy-shard-creation diff; same two call
sites) — re-confirmed present by direct grep this cycle
(`grep -n "self.oplog.lock()" crates/secantus-storage/src/lib.rs`, 13 call
sites total, matching yesterday's count): every other site uses the
poison-tolerant `unwrap_or_else(|e| e.into_inner())` pattern; these two
`prune_oplog` accessors (the `live_count` early-out read and its post-prune
decrement) still use bare `.lock().unwrap()`.

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **nine** consecutive review cycles (07-21 through
07-29). No commit touched this file's locking logic this cycle — the two
`09e12cae`/`9fdab88a` diffs to `secantus-storage/src/lib.rs` this cycle only
add lazy-shard-creation branches around `open_cursor`/`create` calls,
untouched w.r.t. the oplog mutex.

**Recommendation:** unchanged — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The grep-based CI gate
recommended in the last eight reports (`! grep -rn '\.lock()\.unwrap()'
crates/secantus-storage crates/secantus-commands` outside `#[cfg(test)]`)
remains unimplemented after nine nightly re-discoveries.

### W2 (carried forward, still open — 6th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:5749` (`drop_index`) and `:5866`
(`drop_all_indexes`) — line numbers shifted from `:5617`/`:5734` by the
lazy-shard-creation diff; re-confirmed present by direct read this cycle:
both still open only `with self._lock:`, never `self._coll_lock(db, coll)`.

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24. The only commit touching `storage.py` this cycle (`09e12cae`) is
the lazy-shard-creation change reviewed above — it does not touch
`drop_index`/`drop_all_indexes`. The hazard is unchanged: a concurrent
`insert`/`update`/`delete` (which takes `_coll_lock` first) is not excluded by
`drop_index`'s `_lock`-only critical section.

**Recommendation:** unchanged — `with self._coll_lock(db, coll), self._lock:`
in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop path.

## 🟡 INFO (Best-practice recommendations)

One new item this cycle (I39); every other INFO item from 2026-07-28 is
re-confirmed present and unchanged (their underlying files were not touched
this cycle, except where noted):

- **I39 (new)** — `Storage._is_missing_table()` (`src/secantus/storage.py`,
  new this cycle) detects a missing WT shard table by substring-matching
  `"No such file or directory"` in the caught exception's string form, rather
  than a specific error code/type (the Rust equivalent,
  `WtError::is_missing_table()`, checks the WT error code `== 2` directly —
  the more robust of the two). Not independently exploitable (the string only
  appears on a genuine WT-raised ENOENT from a cursor-open call, never from
  document content), but a future WT version or locale change to the error
  message would silently stop matching and the exception would propagate
  normally (fail-safe, not fail-open) — low risk either direction, flagged for
  future-proofing.
- **I3** — `CursorRegistry` (`DEFAULT_MAX_CURSORS = 10_000`) still enforces
  only a global cursor cap, no per-connection limit.
- **I4** — `$regex` residual ReDoS risk (`query.py`,
  `_MAX_REGEX_PATTERN_LEN = 1000`) — pattern-length cap only, unchanged.
- **I6** — All 13 workflow files declare `permissions:` blocks
  (workflow- or job-level); re-verified this cycle by direct grep across
  every `.github/workflows/*.yml`, including the modified `release-binaries.yml`.
- **I7** — `pyproject.toml`'s `sdist.exclude` still doesn't cover `docs/`,
  `tasks/`, `bench/`, `.github/`, or most of `tests/`; sdist-tarball bloat,
  not an installed-wheel exposure.
- **I9** — `maxWriteBatchSize: 100_000` advertised in `hello` but not
  independently enforced on `insert`; bounded indirectly by the 48MB wire
  message ceiling (`MAX_MESSAGE_SIZE = 48_000_000`, re-confirmed at
  `wire.py:28`).
- **I10** — No tag-protection ruleset for `v*`/`secantusdb-v*` confirmed from
  this vantage (unverifiable without branch-protection API access).
- **I11** — `max_connections` (default 1000) on the Mongo server remains a
  global cap with no per-IP rate limit.
- **I13** — `src/secantus/admin/routers/server.py`'s unused
  `current_uri_raw` template context variable; dead code, no live leak.
- **I17** — `pgserver.py` still sends the raw Python exception string to the
  wire client; unchanged.
- **I18** — `getMore` cursor "ownership" (`commands.py`) is still a
  namespace-match, not a connection-identity check; mitigated by 63-bit
  random cursor IDs.
- **I24** — Admin UI routers still don't use a centralized Pydantic
  validation layer.
- **I25** — `cargo-audit.yml` installs `cargo-audit` unpinned by version.

  connection-config clause from the process environment; unchanged this
