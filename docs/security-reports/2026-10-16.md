# Security Review — 2026-10-16

Diff-driven review against the 17 commits that landed since the last report
(`9d129460`, 2026-10-15 → `3e7e59fc`, HEAD, confirmed unchanged on
`origin/main` throughout this review). Thirteen are real code/test changes;
the other four are two pure version-bump commits (`1a942422` Rust MongoDB
crates → `0.5.3-beta.196`, `f1e55b0e` Rust PG crates → `0.1.0-beta.17`) and
two `site:`/blog-post commits with no application logic (`6caf3a89`,
`0958bbde`). Two sub-agents (foreground, one per Rust server — this repo's
own "one session per server" convention extended to review) read every real
commit's production-code diff end to end; every CRITICAL/WARNING claim below
was independently re-verified directly in this session by reading the actual
source (not taken on the sub-agent's word) before being included. The
dependency/secrets/workflow/wheel sections were done directly in this session.

The thirteen real commits: `40ca21f3` (Rust MongoDB server: profiler, wire
compression `OP_COMPRESSED`, serverStatus counters, `notablescan`,
`$listCatalog` — Phase 2 batch 2), `43463aa6` (Rust MongoDB server: geo reads
in mongod's order, a ~2,800-line S2-geometry port — Phase 3), `2964619a`
(Rust MongoDB server: mongod's plan trial, router index reads, classic
aggregate explain — Phase 4), `f301d636` (exact-value numeric comparison,
stores re-keyed on open — RM-152), `d7f06a26` (Phase 6: driver-gauge re-run,
a binary smoke test — mostly docs/test infra), and eight Rust PostgreSQL
server "backlog batch" commits (`239ebbb0`, `54d80309`, `449eb4d1`,
`69db4750`, `798dcd6b`, `0ff472c4`, `1e8f4ec1`, `3e7e59fc`) landing several
hundred built-in functions, login-rule tightenings, and privilege-check
extensions.

**Net result: 5 new CRITICAL findings, 1 new WARNING finding.** All five
CRITICALs are the same bug *class* this project's tracker already carries
~20 open instances of (unauthenticated-reachable unbounded recursion ⇒
stack-overflow ⇒ whole-process abort) — two of yesterday's own new findings
in this class (#1970 `json.rs::value`, #1971 `ts_rewrite.rs`) were
re-confirmed still open and unfixed (neither file gained a depth check), and
five *more* independent instances were found in this cycle's new code,
spanning both servers. The WARNING is a newly-discovered RBAC gap on a
command added in this cycle (`$listCatalog`'s collectionless form), found
while reading the commit that introduced it.

## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Unbounded recursion in the new S2-polygon port, driven by RING COUNT
  (not nesting depth) — stack-overflow DoS via a crafted `$geoWithin` /
  `$geoIntersects` / `$near` query.**
  `crates/secantus-core/src/s2legacy/loops.rs:637` (`insert_loop`) and
  `:661` (`init_loop`), added in `43463aa6` ("geo reads in mongod's order,
  geo edges"). `insert_loop` recurses once per ancestor ring it must descend
  through when placing a new ring into the polygon's containment tree
  (confirmed: no depth parameter, no counter anywhere in the function);
  `init_loop` does an unguarded depth-first walk of the same tree
  (`for &child in &children[at] { init_loop(..., depth + 1, ...) }`, no
  cap). Both are reached from `Polygon::new` (`loops.rs:330`), reached from
  `crates/secantus-core/src/geoorder/parse.rs`'s GeoJSON `Polygon`/
  `MultiPolygon` parser, which places **no limit on the number of rings** in
  a `coordinates` array. Unlike `coverer.rs`/`region.rs`'s S2-cell recursion
  (bounded by the fixed ~30-level S2 cell hierarchy regardless of input —
  confirmed clean), this recursion's depth is driven directly by how many
  (minimal 4-point) rings a client packs into one GeoJSON polygon — tens of
  thousands fit comfortably inside the 16 MB BSON document limit, and each
  ring costs only array bytes, not nested-document depth, so this is **not**
  mitigated by any BSON-nesting-depth fix (unlike several findings below).
  Trigger: `db.coll.find({loc: {$geoWithin: {$geometry: {type:
  "MultiPolygon", coordinates: [<40000 disjoint-but-deeply-contained
  4-point rings>]}}}})` against a collection with (or without) a `2dsphere`
  index. No auth required beyond ordinary `find` privilege (or none at all,
  since `--auth` is off by default).

- **Unbounded recursion in the new aggregate `$match`-hoisting code,
  reachable from ordinary `aggregate`, not just `explain` — stack-overflow
  DoS via a deeply nested `$and`/`$or`/`$nor`/`$expr` filter.**
  `crates/secantus-commands/src/explain/hoist.rs`: `clause_paths` (`:43`)
  and `filter_paths` (`:59`) mutually recurse on `$and`/`$or`/`$nor` arrays
  with no depth limit, and `expr_paths` (`:11`) recurses into every nested
  `Bson::Document`/`Bson::Array` under `$expr`, also with no depth limit —
  all new in `2964619a` ("mongod's plan trial, router index reads, classic
  aggregate explain", Phase 4). `hoist_matches` (`hoist.rs:104`, which calls
  these) is invoked from `crates/secantus-commands/src/aggregate.rs:512` on
  the **ordinary aggregate dispatch path**, whenever a pipeline has no
  leading `$geoNear` candidate — i.e. on essentially every `aggregate` call,
  to lift a `$match` for index acceleration — not merely inside `explain`
  (which also calls it, at three more sites in `explain/mod.rs` and
  `explain/shape.rs`). Trigger: `db.coll.aggregate([{$match: {$and: [{$and:
  [{$and: [ ... 50,000 levels ... ]}]}]}}])`. This recursion is bounded by
  BSON *document nesting* depth (unlike the ring-count finding above), so it
  is partly a second chokepoint behind the already-tracked #1780 ("Rust bson
  decoder has no nesting-depth limit") — but this project's own practice is
  to file each unguarded-recursion function as its own tracked item even
  when a shared root cause exists (there are already ~20 such paired/related
  entries in the tracker), so it is filed here too: fixing #1780 with a
  generous depth cap (mongod's own ~200) would incidentally close this one,
  but `hoist.rs` has no depth guard of its own today and should get one
  regardless (defense in depth, and in case #1780's eventual fix uses a
  looser cap than is safe for this function's own stack cost per frame).

- **Unbounded recursion in the new `jsonb_hash`/array-hash code — stack-
  overflow DoS via `jsonb_hash`, `hash()` over an array, or any `GROUP BY` /
  hash-join on a `jsonb` or array column.**
  `crates/secantus-pgplan/src/hashfn.rs`: the new `fn walk(...)` (jsonb tree
  walk, ~line 521, added in `798dcd6b` "backlog batch 6") and the new inner
  `fn flatten(...)` inside `hash_array` (~line 398, same commit) both
  recurse into `Json::Array`/`Json::Object` and `Bson::Array` respectively
  with no call to the crate's own `check_depth()`/`MAX_EXPR_DEPTH` guard
  (`crates/secantus-pgplan/src/lib.rs:3745-3837`) and no depth counter of
  their own. `walk` operates on an already-parsed `jsonb` value, so very deep
  nesting is partly gated by the pre-existing unguarded `json::value()`
  parser (#1970) crashing first; `flatten` operates on a native SQL `ARRAY`
  literal's `Bson::Array` representation, which is a **separate** input path
  gated only by the already-tracked, also-unfixed `ArrayParser::parse_braced`
  recursion (#1433) — so this is an independent chokepoint behind a
  different existing crash, not a duplicate of #1970. Trigger (once either
  upstream parser is hardened, or today if the attacker tunes nesting depth
  to survive parsing but still exceed hashing's own stack budget):
  `SELECT jsonb_hash('[[[[[...]]]]]'::jsonb)` or `SELECT hash(ARRAY[ARRAY[...
  deeply nested ...]])`. No privilege beyond running a `SELECT` is required.

- **Unbounded recursion in the new `jsonb` ordering/comparison code —
  stack-overflow DoS via `ORDER BY jsonb_col`, `<`/`>` on `jsonb`, or
  `DISTINCT`/`GROUP BY` over `jsonb`.**
  `crates/secantus-pgplan/src/json.rs`'s new `fn jsonb_tokens<'a>(v, top,
  out)` (~line 875, added in `1e8f4ec1` "backlog batch 8 … jsonb ordering
  fixed"), called from the new public `jsonb_compare` (`:775`), recurses
  into `Json::Array`/`Json::Object` with no depth bound. `jsonb_compare`
  first calls the pre-existing, already-tracked-unguarded `parse()`
  (#1970's `value()`), so very deep literals already crash during parsing —
  but `jsonb_tokens` is an **independent second unguarded walk** over the
  same tree, newly added by this commit specifically to wire jsonb into
  `ORDER BY`/comparison operators, and the task of actually fixing #1970
  (capping `value()`'s parse depth) does not by itself audit or fix this
  function; both need a guard. Trigger: `SELECT '[[[[[...]]]]]'::jsonb <
  '[]'::jsonb;` or any `ORDER BY`/aggregate `ORDER BY` over a `jsonb`
  column holding a deeply nested value.

- **Unbounded recursion in the new `tsquery` comparison code — stack-
  overflow DoS via `ORDER BY`/`DISTINCT`/comparison on `tsquery`.**
  `crates/secantus-pgplan/src/fts.rs`'s new `fn node_cmp(a: &Query, b:
  &Query) -> i32` (~line 237, added in `1e8f4ec1`) and its `children()`
  helper recurse over the `tsquery` boolean-operator tree with no depth
  check, called from the new public `query_cmp` wired into `tsquery_cmp` in
  `cmpfn.rs`. This walks the exact same `QTNode`-shaped tree that
  yesterday's #1971 (`ts_rewrite.rs`) already covers for a *different*
  function over the *same* underlying unguarded `to_tsquery` parser — this
  is a second, independently unguarded walker over that tree, newly added in
  this cycle. Trigger: `SELECT tsquery_cmp(to_tsquery('a&(a&(a&(a&...)))'),
  to_tsquery('x'));` (or any `<`/`>`/`ORDER BY`/`DISTINCT` over `tsquery`)
  with a few thousand nested boolean operators in the first argument.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`$listCatalog`'s collectionless form has no RBAC privilege requirement
  at all — any authenticated user, regardless of granted role, can read the
  full catalog (collection names, index specs, namespaces, WiredTiger
  idents) of every database on the server.**
  `crates/secantus-commands/src/list_catalog.rs` (new in `40ca21f3`) wires
  `{aggregate: 1, pipeline: [{$listCatalog: {}}]}` against `admin` to
  `list_catalog::entries(storage, "admin", None)`, which with `coll: None`
  calls `storage.list_databases()` and walks **every** database's
  collections (`list_catalog.rs:100-108`). The authorization path never
  requires any privilege for this: `crate::authz_pipeline::aggregate`
  (`authz_pipeline.rs:169-192`) only adds a `Need` when `doc.get_str
  ("aggregate")` is a string naming a collection — the collectionless form
  uses the bare integer `1`, so `collection` is `None` and the `if let
  Some(coll) = collection { ... }` block (the one place `needs` would gain
  an entry) is skipped entirely. `walk()` (`authz_pipeline.rs:52-161`), which
  processes the pipeline's own stages, has **no `"$listCatalog"` arm** —
  confirmed by reading the full match; it falls through to `_ => {}`, adding
  nothing. `Check::allowed` is initialized `true` (`authz.rs:150`) and
  `needs()` over an empty `Vec` (`authz.rs:59-63`) never sets it `false`, so
  the command is allowed by default — the same "closed by default" gate this
  project's prior reports praised as intact (`_ => c.allowed = false` at
  `authz.rs:465`) never fires here because the pipeline-stage match has its
  own silent default of "needs nothing," one level up from that gate.
  Real `mongod` requires the `listCatalog` cluster-level privilege action
  for exactly this collectionless form. Severity is WARNING rather than
  CRITICAL because it requires an authenticated connection (not a bare TCP
  client) and exposes catalog **metadata** only, not document contents —
  the same calibration this report series used for yesterday's SQL
  GRANT/REVOKE authorization gap, which was more severe (full privilege
  escalation) yet also WARNING.

## 🟡 INFO (Best-practice recommendations)

- **"Unknown users refused by default" (`1e8f4ec1`) is a genuine
  tightening, verified directly, not a regression.** The old
  `refuse_unknown_users` field defaulted `false` (the insecure direction:
  unknown users let in); the new `trust_unknown_users` field also defaults
  `false`, but the guard flips from `if role.is_none() &&
  self.refuse_unknown_users` to `if role.is_none() &&
  !self.trust_unknown_users` (`crates/secantus-pg/src/lib.rs:18499`) — so
  the *default* behavior itself flips to "refuse," matching CLAUDE.md's
  recorded 2026-10-16 decision. The old builder method is kept only as a
  `#[deprecated]` shim that maps onto the new field
  (`embedded.rs:284-286`, `server.rs:475-477`). Confirmed consistent across
  `embedded.rs`, `lib.rs`, `main.rs`, and `server.rs` — no stray call site
  still reads the old field's old default.
- **New Rust dependencies this cycle, checked for scope and provenance**:
  wire compression pulled in `snap` (pure-Rust Snappy), `zstd`/`zstd-safe`/
  `zstd-sys` 2.1.1+zstd.1.5.7 (C bindings to libzstd — memory-safety-
  relevant FFI, but decompression is bounded by the wire-declared
  `uncompressedSize` checked against `MAX_MESSAGE_SIZE` *before* any
  allocation, confirmed in `secantus-wire/src/compression.rs:201-213`, with
  a passing decompression-bomb regression test). The Rust PG server's new
  encrypted-PEM-key support (for `--tls-key-passphrase-command`) added
  `pkcs8` 0.10.2 (`encryption`/`pem`/`std` features), `pkcs5`,
  `pem-rfc7468`, `block-padding`, and, for OpenSSL's **legacy** PEM
  encryption format specifically, `md-5` 0.11.0, `aes` 0.8.4, `des` 0.8.1,
  `cbc` 0.1, `scrypt` 0.11.0, `salsa20` 0.10.2. MD5/DES are cryptographically
  weak, but here they only *decrypt* a key file in a legacy format
  PostgreSQL itself still accepts (`EVP_BytesToKey`-derived keys) — matching
  an existing format rather than minting new weak key material — and the
  code path is local-file/CLI-flag-gated, not wire-reachable. No RUSTSEC
  advisory found for any of the newly-added crate versions (WebSearch); no
  `cargo-audit` binary available in this sandboxed review environment to
  cross-check directly, so this leans on the search alone this cycle (the
  project's own `cargo-audit.yml` CI gate is the authoritative check and
  should be read directly next time a local binary is available). `md-5`
  now resolves to three different versions (0.9.1, 0.10.6, 0.11.0) across
  the dependency graph — a build-bloat note, not a security issue.
- **A new ~1.5 MB generated ICU collation-tailoring data file**
  (`crates/secantus-pgplan/src/icu_baked/collation_tailoring_v1.rs.data`,
  landed in the ICU-data work mentioned by batch 8) is plain-text Rust
  source data marked `// @generated`, part of a larger `icu_baked/`
  directory of similar files (the largest well under the repo's 8 MB
  tracked-file ceiling, `tests/test_no_tracked_build_output.py` still
  passes by inspection) — a legitimate vendored/generated data asset in the
  same spirit as `vendor/wiredtiger`, not a build artifact or secret.
- **No workflow, dependency-pin, or wheel-packaging change this window**:
  `.github/workflows/`, `pyproject.toml`, and `uv.lock` all have zero diff
  in this 17-commit range — the full §12/§13 audits from prior cycles stand
  unchanged; `vendor/wiredtiger`'s submodule pin
  (`eaa187c86147b561c940e9b0e5e628f5e86d075d`) and `cmake/patch_wt_*.py` are

- **PyPI version-drift check (§13d) was inconclusive this cycle** — `pip

## 🟢 CLEAN (Passed review)

- **`OP_COMPRESSED` decompression (`secantus-wire/src/compression.rs`) is
  properly bounded.** `uncompressed_size` is range-checked (`< 0` and
  against `MAX_MESSAGE_SIZE`) *before* any buffer is allocated
  (`compression.rs:201-213`); snappy pre-validates its length preamble via
  `decompress_len` before allocating; zlib's `decompress_vec` is capacity-
  bounded and errors (`BufError`) rather than growing past the declared
  size; zstd's `bulk::decompress(data, size)` is bounded by construction. A
  decompression-bomb regression test exists and passes. The server read
  path additionally reserves from a global allocation budget before
  allocating either the compressed or inflated buffer. Deliberate,
  well-built hardening for a brand-new attack surface.
- **The new profiler (`system.profile`) is size-capped like mongod's.** The
  collection is created capped at a fixed byte ceiling
  (`PROFILE_COLLECTION_BYTES`); the command-text truncation routine checks
  `is_char_boundary` before slicing, so no multi-byte-UTF-8 panic.
- **The store re-key-on-open path (`f301d636`, RM-152) follows this
  project's own "never swallow a storage error" rule.** Every real write in
  `rekey_numeric_ids`/`upgrade_number_keys` propagates failure via `?`; the
  only `let _ = session.rollback_transaction(None)` calls are best-effort
  cleanup *after* the real error has already been captured for return, the
  documented-correct idiom, not a swallowed write/commit error.
  `upgrade_number_keys()?` is called from `open_with_options` and aborts the
  open on failure rather than continuing with a partially-rekeyed store.
  This is an open-time operation, not wire-reachable.
- **No new `unsafe` block across either server's reviewed commits operates
  on a wire-derived length or pointer.** The new `secantus-wt` FFI additions
  (`get_value_stat`, `version_string`, `with_key_sssu`) all consume
  WiredTiger's own library-populated pointers/lengths, not attacker-
  supplied ones, with lifetimes confined by `FnOnce` closures matching the
  crate's existing sound idiom. The Rust PG server's new `unsafe` libc
  wrappers (`getnameinfo`/`getifaddrs` for `samehost`/`samenet`,
  `libc::kill` for signal handling) operate on server-local, non-client-
  controlled data with bounded buffers.
- **No secrets, no new secret-shaped file.** Grepped every added line
  across the full 17-commit diff for credential/token/PEM/JWT/connection-
  string shapes (one hit, a test fixture using the literal password `"pw"`
  for two named test-user scenarios — not a real secret). No tracked file
  over the repo's 8 MB build-output limit added; the one large new data
  file is the `@generated` ICU asset noted above.
- **Login-direction changes in `0ff472c4`/`1e8f4ec1` all tighten rather than
  weaken.** "An expired password runs the exchange before it fails" removes
  a potential early-exit timing oracle (still ends in refusal, never admits
  the user); `role_is_member_nosuper` stops treating a superuser as
  implicitly a member of every role for `pg_hba.conf` `+group` matching — a
  stricter, not looser, membership test.

## 📊 Summary

- **Date of review:** 2026-10-16.
- **SecantusDB version reviewed:** Python `0.7.0b3` (unchanged this window);
  Rust MongoDB-server crates `0.5.3-beta.196` (bumped from `0.5.3-beta.195`
  by `1a942422`); Rust PostgreSQL-server crates `0.1.0-beta.17` (bumped from
  `0.1.0-beta.16` by `f1e55b0e`).
- **This cycle's new findings:** 5 CRITICAL (all unguarded-recursion
  stack-overflow DoS: `s2legacy::loops::{insert_loop,init_loop}` driven by
  polygon ring count; `explain::hoist::{clause_paths,filter_paths,
  expr_paths}` reachable from ordinary `aggregate`; `hashfn::{walk,
  flatten}`; `json::jsonb_tokens`; `fts::node_cmp` — the last three all in
  the Rust PostgreSQL server's new jsonb/array/full-text-search surface), 1
  WARNING (`$listCatalog`'s collectionless form has no RBAC requirement at
  all — any authenticated user can enumerate every database's catalog),
  plus several INFO notes (new dependency provenance including legacy
  crypto scoped correctly to local-file decryption, a large but properly
  generated ICU data asset, zero workflow/dependency/wheel diff this
  window, a PyPI check that could not run in this sandbox).
- **Resolved this cycle:** none — no commit in this window's message or
  diff references closing any tracked `security`-labelled issue, confirmed
  against the live tracker (92 open both before and after this review's own
  new filings).
- **Comparison with previous report (2026-10-15):** that cycle found 2
  CRITICAL + 2 WARNING, both CRITICALs the same unguarded-recursion class in
  brand-new Rust PostgreSQL server code. This cycle finds *more* instances
  of exactly that class (5, not 2) spread across *both* servers for the
  first time — the Rust MongoDB server's large new geometry port
  (`s2legacy/`) and its new explain/aggregate planning code
  (`explain/hoist.rs`) are new to this finding category; the Rust
  PostgreSQL server contributes three more instances in its continuing
  built-in-function expansion. Both of yesterday's CRITICALs (#1970, #1971)
  were re-confirmed still open and unfixed. Unlike yesterday, this cycle's
  one WARNING is a freshly-discovered RBAC gap rather than a second
  recursion-adjacent finding.
- **Top 3 priorities for the team:**
  1. **Treat unguarded-recursion-on-client-input as a class, not five (now
     twenty-five-plus) one-off bugs.** Every new feature batch in both
     servers keeps introducing at least one more instance of a pattern this
     project has a working fix idiom for (`MAX_EXPR_DEPTH`/`check_depth()`
     in `secantus-pgplan`; an analogous iterative-or-depth-capped rewrite
     is needed in `secantus-core`/`secantus-commands` for the MongoDB
     server). A lint, a code-review checklist item, or a shared
     depth-guarded recursion helper that every new parser/tree-walker is
     required to use would close this class faster than filing and fixing
     one function at a time.
  2. **Add the missing RBAC arm for `$listCatalog`'s collectionless form**
     (`crates/secantus-commands/src/authz_pipeline.rs`'s `walk()` match) —
     a one-arm fix (`"$listCatalog" => c.cluster("listCatalog")` or
     equivalent), narrow and well-scoped like the DECLARE/TABLESAMPLE fix
     landed this same cycle.
  3. **Bump the `pymongo` floor to `>=4.18.2`** (#1742) — unchanged for a
     third cycle, still the cheapest fix in the whole open tracker, against
     a CVSS-8.4 heap-out-of-bounds-write CVE in the BSON encoder every
     Python-server document write uses.

If any of the above is superseded by a fix landed after this report was
written, the next review cycle is expected to catch it via re-execution
against the oracle and against the GitHub/crates.io APIs — per this
project's own standing rule, not by re-reading this document's claims.
