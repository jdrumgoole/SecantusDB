## 🔴 CRITICAL (Immediate action required)

All three unchanged, re-confirmed by direct read against current HEAD:

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  Re-read in full this cycle, byte-identical to the prior cycle's citation:
  `if (self.message_length as usize) < HEADER_SIZE` casts the signed `i32` to
  `usize` first, so a negative `message_length` sign-extends to `usize::MAX`
  on 64-bit and passes both guards; `body_len()` then returns
  `usize::MAX - 16`, which the caller (`crates/secantus-server/src/
  lib.rs:553-562`) feeds straight to `vec![0u8; body_len]` after an
  `AllocBudget` check that lets a single request through by design (`used ==
  0`). Rust's global allocator aborts the whole process on an allocation
  failure of that size — one unauthenticated 16-byte frame is a full-server
  abort. **Not fixed.**
- **#1160** — `src/secantus/commands.py` and
  `crates/secantus-commands/src/lib.rs`, both servers. Re-checked this cycle:
  `"bulkWrite"` still appears in neither `_COMMAND_ACTIONS`
  (`commands.py:8834`) nor `_NO_PRIVILEGE_COMMANDS` (`commands.py:8924`), and
  the Rust `command_action()` still has no `"bulkWrite"` arm. This cycle's
  `aggregate.py`/`expressions.py` changes don't touch RBAC dispatch at all.
  **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471` (`_MAX_REGEX_PATTERN_LEN =
  1000`, `_compile_regex`). Re-read this cycle: unchanged (`query.py` has no
  diff since `50105e14`) — still a length guard with no backtracking-depth or
  match-time budget, and a second uncapped `re.compile` fallback in the
  `TypeError` recovery branch. **Not fixed.**

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **Unbounded per-query cost multiplier from exact-numeric-at-any-width, both
  PG servers** (filed as a new issue below). `src/secantus/sql/numeric.py`
  (new this cycle, porting `crates/secantus-pgplan/src/numeric.rs`'s
  pre-existing design) sets `MAX_INT_DIGITS = 131072`, `MAX_SCALE = 16383`
  (`numeric.py:48-49`) with no cap on how many such wide values one query may
  contain. `check_limits` (`numeric.py:81-91`) is the only per-value gate; a
  numeric literal near `1e131071` can be ~130 KB of query text and, when it
  does not fit a Decimal128 exactly, `_bracket()` (`numeric.py:175-216`) runs
  a `normalize`/`quantize` under a `decimal.Context` with `prec=147457`
  (`EXACT`, `numeric.py:54-59`) — a real per-value CPU/memory cost that used
  to be impossible (every numeric was rounded to a cheap 34-digit Decimal128
  before this feature). `planner.py:679-685` (`_numeric_in`) builds one such
  `$or` arm per element of a `WHERE numeric_col IN (v1, …, vN)` list or `= ANY
  (array)` (`planner.py:1458-1478`) with no cap on `N`. Confirmed the same
  gap exists in the Rust PG server this was ported from
  (`crates/secantus-pgplan/src/numeric.rs:42,140,154` carries the identical
  `MAX_INT_DIGITS`/`MAX_SCALE` constants with no list-size cap anywhere in
  the crate) — so this is a cross-server, not Python-only, gap; it has simply
  never been flagged, and this cycle is the first time the Python side
  carries it too. The PG server has no authentication (#1191) and no
  statement-level cooperative deadline check inside planning
  (`pgextended.py`'s `statement_timeout` machinery arms at Execute, not
  during the planner's numeric-literal lowering), so an unauthenticated
  client sending one crafted multi-MB statement (a `WHERE … IN (…)` list of a
  few thousand near-maximum-width numeric literals) forces hundreds of MB of
  synchronous full-precision decimal work with no size ceiling beyond the
  statement itself. Not CRITICAL: it needs a deliberately large query body
  (the attacker pays roughly proportional bytes to send it), does not crash
  the process, and PostgreSQL itself accepts the same numeric width — but
  this server had no comparable per-query cost before this feature landed,
  and the cost is convex in list length with no cap.
- **Per-row synchronous storage probe during bulk insert once a numeric PK
  table has any wide value, Python PG server** (filed as a new issue below).
  `src/secantus/sql/executor.py:1308-1343` (`_check_numeric_pk_values`): once
  a table's `_id`/PK column has ever stored (or the current batch contains) a
  wide numeric — i.e. any value outside Decimal128's 34-digit exactness —
  every row of every subsequent `INSERT` on that table pays one
  `storage.find_matching(...)` call (an actual WiredTiger query) run
  sequentially inside the write path (`executor.py:1338-1340`), in addition
  to an in-memory `seen` set for the batch's own duplicates. An
  unauthenticated client can (a) insert one row with an oversized numeric PK
  (e.g. `1e40`) to flip the table into this mode permanently, then (b) issue
  a single large batch `INSERT`/`COPY` that now costs one extra synchronous
  index probe per row with no batching or cap. Checked the Rust origin this
  was "ported from" (`wide_numeric_pk_conflict`,
  `crates/secantus-pgserver/src/lib.rs:4131-4160`): it only compares rows
  **within the current batch** via an in-memory `Vec` scan — it does not
  query storage per row against previously-stored data — so the Python port
  introduced a materially more expensive implementation, not a like-for-like
  port. Per `CLAUDE.md`, `Storage`'s public methods are serialized by one
  process-wide `RLock` in the Python engine, so this connection's
  per-row storage round-trips also serialize every other connection's writes
  for the batch's duration — a small-input, server-wide-latency amplification
  distinct from (and cheaper to trigger than) the existing tracked PG-server
  resource-exhaustion gaps (#1194/#1195/#1451/#1452).

  **2 new**, both in the exact-numeric-at-any-width feature ported into the

  `security`-labelled issues after this cycle: 49** (3 CRITICAL + 42 WARNING
  + 4 INFO-tracked).
- **Comparison with the previous report (2026-09-19):** A substantial cycle
  landed 29 commits including a new embeddable Rust PostgreSQL server
  (`PgServer`, mirroring the existing embedded Mongo `RustServer`'s sound
  loopback-default / owned-storage-checkpoint-on-stop design), a PG-server
  catalog-cache correctness fix, and a batch of SQL numeric/timestamp
  precision fixes — including porting the Rust server's
  exact-numeric-at-any-width support into the Python PG server for the first
  time. That last piece of work is what produced this cycle's two new
  findings: widening a numeric column's representation from a bounded
  34-digit Decimal128 to an effectively arbitrary-width value (up to ~131,072
  integer digits) removed an implicit cost ceiling that had never needed to
  be stated, and the Python port additionally introduced a per-row storage
  round-trip its own Rust "origin" does not have. Everything else this
  cycle — the embeddable PgServer, the catalog-cache fix, the `$lookup`
  numeric-equality fix, the `$toDecimal` rounding fix — was read in full and
  found to be either a sound new addition or a correctness fix for an
  existing BSON-equality-semantics bug class, not a new security defect.
- **Top 3 priorities for the team:**
  1. **The two whole-server-DoS-from-one-request bugs remain unmoved for at
     least fourteen review cycles** — `#995`'s Rust `body_len` cast-before-
     check and `#977`'s regex GIL-starvation. Both remain a single crafted
     request away from taking the whole Mongo-wire server offline,
     unauthenticated in `#995`'s case.
  2. **New this cycle: cap the cost of exact-numeric-at-any-width before it
     ships more broadly.** The feature is real and matches PostgreSQL's own
     numeric range, but landing it with no per-query cap on wide-numeric
     literal count (`IN`/`ANY` lists) or on per-row storage probes during
     bulk insert gives an unauthenticated PG-server client (per #1191, there
     is no authentication at all) a new way to impose disproportionate
     synchronous CPU/storage cost with a single statement. Both are cheap to
     bound (a literal-count cap in the planner, batching the PK-probe query)
     and worth fixing before this feature is exercised by real workloads.
  3. **The PG-server feature surface continues to grow** (an embeddable
     server handle, catalog caching, exact-numeric-at-any-width, all landed
     in the last two cycles) **on top of a fully-open, unauthenticated
     attack surface (#1191) that remains completely untouched.** The new
     embeddable `PgServer` is a sound, minimal addition on its own terms
     (loopback-default, checkpoint-on-stop), but it is one more caller of the
     same unauthenticated accept loop. Landing #1191 before the next feature
     round remains the highest-leverage open item, unchanged advice from the
     last four cycles.
