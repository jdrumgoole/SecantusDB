## 🔴 CRITICAL (Immediate action required)

All three re-confirmed by fresh direct reads against current HEAD (not by
trusting the diff — each file was opened and the exact lines re-verified):

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  Re-read in full this cycle (file has zero diff since last report, confirmed
  by `git diff --stat 1d785631..697778ba -- crates/secantus-wire`).
  `message_length` is `pub message_length: i32` (`lib.rs:100`) and
  `MAX_MESSAGE_SIZE: i32 = 48_000_000` (`lib.rs:57`). For a negative
  `message_length` (e.g. `-1`): `(self.message_length as usize)` on line 138
  sign-extends to `usize::MAX - n`, which is `>= HEADER_SIZE`, so the first
  guard does **not** fire; `self.message_length > MAX_MESSAGE_SIZE` on line
  144 compares the still-negative signed `i32` against a positive bound,
  which is never true, so the second guard does **not** fire either. Line 150
  then computes `Ok(self.message_length as usize - HEADER_SIZE)` — the same
  huge value minus 16. The caller (`crates/secantus-server/src/lib.rs:552-561`,
  also zero-diff, re-checked) feeds that straight to `vec![0u8; body_len]`
  after `shared.alloc_budget.acquire(body_len)`. Re-read `AllocBudget::acquire`
  in full this cycle (`crates/secantus-server/src/lib.rs:87-94`):
  `while *used != 0 && *used + n > self.cap { ... }` — when `*used == 0` (the
  first in-flight request on a connection, or any moment nothing else is
  reserved) the loop condition is false regardless of how large `n` is, so
  the wait is skipped unconditionally and the reservation is granted for the
  full attacker-chosen size before `vec![0u8; body_len]` runs. Rust's default
  allocator aborts the process on an allocation failure at this size — one
  unauthenticated 16-byte frame takes the whole server down. **Not fixed.**
- **#1160** — `src/secantus/commands.py:8834-8917` / the dispatch gate at
  `9747-9756`. Re-grepped `_COMMAND_ACTIONS` (`bulkWrite` search returns only
  the handler-table entry at `8749` and unrelated field-name lines — no
  `_COMMAND_ACTIONS` row) and `_NO_PRIVILEGE_COMMANDS` (re-read in full,
  same membership as last cycle, no `bulkWrite`). The gate at `9747-9760`
  reads `info = _COMMAND_ACTIONS.get(name); if info is not None: ...` — when
  `info` is `None` the entire privilege check is skipped, i.e. **skip-on-
  unknown rather than deny-on-unknown**. An authenticated connection with
  zero role grants under `--auth` can still call `bulkWrite`. `commands.py`
  has zero diff this cycle. **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471`. Re-read `_compile_regex`
  (`1410-1416`): the only gate is `len(pattern) > _MAX_REGEX_PATTERN_LEN`
  (1000 chars) before an unbounded `re.compile(pattern, flags)` — no
  backtracking-depth limit, no compile/match timeout. A second, uncapped
  `re.compile(regex_pattern, flags)` fallback still exists inside the
  `TypeError` recovery branch (`1465-1469`), bypassing even the length cap. A
  short pathological pattern (e.g. `(a+)+b`, 8 characters) matched against an
  adversarial non-matching string pins a worker thread's CPU indefinitely —
  an unauthenticated `find` with a crafted `$regex` is a single-request
  CPU-exhaustion DoS. `query.py` has zero diff this cycle. **Not fixed.**
