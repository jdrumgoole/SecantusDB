## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Pipeline-form update bypasses the write path's nesting-depth guard;
  `diff.rs`'s unguarded recursion risks a process-ending stack overflow**
  (medium/high, overall high, confidence high; **issue #2947**). A
  pipeline-form update (`updateOne`/`updateMany`/`findAndModify` with an
  array update spec, an ordinary MongoDB feature) builds its post-image via
  `secantus_core::aggregate::apply_pipeline`, called from
  `crates/secantus-storage/src/lib.rs:20937`
  (`update_matching_pipeline_supplied`) — a path that never reaches
  `update.rs`'s one nesting-depth check (`MAX_NESTING_DEPTH=180`,
  `update.rs:1818`, scoped to the operator-form branch only), and
  `aggregate.rs` itself has no depth guard on stage output. A pipeline of N
  chained single-field-wrapping stages manufactures N levels of document
  depth from a flat, shallow wire payload (well under the 16MB document
  limit for N in the hundreds of thousands). When `enable_oplog` is on (the
  default), that post-image reaches `crates/secantus-core/src/diff.rs`'s
  mutually recursive tree walkers (`walk`/`diff_doc`/`describe`/
  `parse_oplog_diff`/`apply_node`), which have **zero depth bound anywhere in
  the file** (confirmed by reading every line of it). A genuine Rust stack
  overflow aborts the whole process — it is not interceptable by the
  server's dispatch-level `catch_unwind` — dropping every connected client,
  reachable with **no authentication** under the default config
  (`require_auth: false`). The same unguarded recursion also re-fires every
  time a stored diff of comparable depth is read back by a change-stream
  consumer or oplog replay, turning one write into a persistent crash-on-read
  landmine. **Independently confirmed** by a fresh verifier, who additionally
  confirmed this is a distinct, independently-reachable sink from the
  `bsondoc.rs` gap below (it builds its depth *after* wire decode, from a
  flat payload). **Fix:** thread a `MAX_NESTING_DEPTH`-style counter through
  `diff.rs`'s recursive functions, and/or re-check `nesting_depth` on a
  pipeline update's post-image before it reaches `diff::pipeline_update_description`.
  **Filed as new issue #2947.**

### Carried forward, re-confirmed via comment this cycle (tracked by existing issues)

- **Rust BSON decoder has no nesting-depth limit — unauthenticated
  single-frame stack-overflow crashes the whole process** (**#1780**, filed
  2026-10-07, still open) — this cycle's post-wave critic found that the
  *mechanism* has shifted since the original filing without the issue being
  updated: the pre-dispatch `OP_MSG`/`OP_QUERY` call sites (`secantus-server/src/lib.rs:1319-1320`,
  `:1077`) no longer call the `bson` crate's `Document::from_reader` at all —
  they call this project's own hand-rolled decoder,
  `secantus_commands::bsondoc::from_bytes` (`crates/secantus-core/src/bsondoc.rs`'s
  `read_doc`/`read_value`, lines 342-416), which has the **identical**
  missing-depth-bound property. Practically, this means upgrading the `bson`
  crate to ≥3.1.0 — the fix this issue originally suggested waiting on — would
  **no longer fix this vulnerability**, since that crate's decoder is no
  longer on the wire-decode path at all. Independently re-confirmed directly
  from source by the parent (not assigned to a hunter, per the quick
  profile's one-hunter-wave rule). **Commented on #1780** with the corrected
  root cause and current line numbers, rather than filing a duplicate.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`secantusd-mdb service install` writes unescaped newlines from
  server-option argv into the systemd unit's `ExecStart=` line, enabling
  directive injection on `daemon-reload`** (low/medium, overall medium,
  confidence high; **issue #2948**). `systemd_word`/`systemd_value`
  (`crates/secantus-server/src/service.rs:236-260`) escape only `%`/`$` and
  quote-plus-backslash-escape `"`/`\`/`;`/whitespace, but never escape a
  literal `\n`/`\r` — a value containing one is classified as "needs
  quoting" (since `\n` is whitespace) but the quoting loop's escape set
  doesn't cover it, so it passes through raw. Because systemd unit files are
  line-oriented, that raw newline becomes a structural line break once
  written, letting a crafted value append a new `[Service]` directive (e.g.
  `ExecStartPre=...`). `install()` writes the file and unconditionally runs
  `daemon-reload`/`enable`/`restart` right after, with no approval gate. This
  is local-operator-triggered, never wire-reachable; the realistic threat is
  an automation/packaging script forwarding a less-trusted string into this
  CLI's argv, not the operator attacking their own shell session — the
  launchd/macOS path is unaffected (its XML escaping fully neutralizes the
  one structurally-meaningful character class there). **Independently
  confirmed** by a fresh verifier. **Fix:** reject any control character in a
  value destined for the generated unit file, centrally in
  `systemd_value`/`systemd_word`. **Filed as new issue #2948.**

### Carried forward / not re-checked this cycle (tracked by existing issues)

- **Unbounded recursion over client-walked trees** — the ~45-strong tracked

  planner/geo/text-search engines) — not re-checked this cycle outside the

## 🟡 INFO (Best-practice recommendations)

### New this cycle

- **`changestreams.rs::hex_decode` panics on a non-ASCII client-supplied
  resume-token `_data` string** (high/low, overall low, confidence high; not
  filed as a dedicated issue per this review's CRITICAL/WARNING-only filing
  rule). `hex_decode` (`crates/secantus-storage/src/changestreams.rs:147-155`)
  checks only that `_data`'s byte length is even before slicing `&s[i..i+2]`
  on a `&str`; a value like `"a€"` (4 bytes, even, but byte offset 2
  falls inside the 3-byte encoding of U+20AC) panics with Rust's
  "byte index is not a char boundary" instead of returning `None`. Reached
  from any `$changeStream` `resumeAfter`/`startAfter`, before the
  panic-safe `resume_keystring::mongod_verdict` fallback is tried. **Scored
  low impact, not medium/high**, because each connection runs on its own OS
  thread with no shared mutex held across the dispatch call, and the
  server's dispatch-level `catch_unwind` (an ordinary bounds-check panic, not
  a stack overflow) recovers it into a wrong-but-safe `InternalError` reply —
  confirmed by an independent verifier who traced the per-connection-thread
  model and the thread-local per-operation state reset to rule out any
  cross-connection or process-wide effect. **Fix:** decode via `as_bytes()`
  rather than `&str` range indexing.
