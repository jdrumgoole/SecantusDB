## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`CALL` of a stored procedure never checks EXECUTE privilege — any
  authenticated role can run a `REVOKE`d procedure** (high/high/high).
  `crates/secantus-pg/src/procedures.rs`: scalar user functions are gated by
  `call_user_function` (`lib.rs:14369`), which calls
  `object_acl.rs::check_function_execute` before running. `CALL` of a
  *procedure* goes through a separate chokepoint — `call_procedure` ->
  `run_procedure` -> `resolve_call` (`procedures.rs:116-354`) — that calls
  `require_routine_schema` (confirms the schema exists, nothing about
  privilege) and a "is this actually a procedure" check, then proceeds
  straight into argument binding and body execution. `check_function_execute`
  is never called anywhere on this path (confirmed by grepping every call
  site in the crate: exactly two, the scalar-function path and
  `triggers.rs:171` for trigger functions). The ACL *data* side is fully
  wired — `GRANT`/`REVOKE EXECUTE ON PROCEDURE` writes a real ACL record of
  kind `"function"` keyed by the routine (`object_acl.rs::function_acl_key`)
  — only the read-back at `CALL` time is missing. A verifier confirmed this
  independently, including checking for (and ruling out) an earlier
  checkpoint that might subsume the check, and confirmed real PostgreSQL
  itself requires EXECUTE privilege to `CALL` a procedure, same as invoking a
  function. **This is not new to this window**: `CALL`/`CREATE PROCEDURE`
  support landed in commit `aab6d333` (2026-10-23); this window's two
  `procedures.rs` commits (RP-509) only reworked named-argument/overload
  resolution inside the same already-ungated function. It is a long-standing
  gap discovered today, not introduced today.
  **Fix:** in `resolve_call` (`procedures.rs`, right after the matched
  procedure document is chosen), call
  `self.check_function_execute(doc.get_str("_id")?, name)?` before binding
  arguments or executing the body — mirroring exactly what
  `call_user_function` already does for scalar functions. Covers both the
  top-level `CALL` dispatcher and the nested PL/pgSQL `CALL` path, since both
  funnel through `run_procedure` -> `resolve_call`.
  **Filed as a new issue** (duplicate search found only the deprecated Python
  server's analogous, differently-rooted `#996` — a different codebase, not
  this gap — and the unrelated parse-depth-guard issue `#1783`; no existing
  issue covers `secantus-pg`'s `procedures.rs`/`object_acl.rs`).

- **Unbounded native-stack recursion in the new PL/pgSQL block-scope builder
  and executor — a single `CREATE FUNCTION` crashes the whole server**
  (high/high/high). `crates/secantus-pg/src/plpgsql_fn/block_scope.rs` (new
  this window): `Builder::stmt`/`Builder::stmts` (lines 212-321) recurse once
  per nested `BEGIN...END`/`IF`/`CASE`/`FOR`-body with no depth counter and
  no `stacker::maybe_grow` — the codebase's only such guard
  (`lib.rs:14316-14345`'s `with_call_depth`, capped at 200) bounds
  *cross-function call* depth, not intra-function block nesting, and sits
  nowhere above this call chain. `block_scope::annotate` runs unconditionally
  inside `parsed()`, called from `validate()`, which runs directly from the
  `CREATE FUNCTION`/`CREATE PROCEDURE` DDL handler (`lib.rs:13553`) with no
  stack-growth wrapper at all — so the crash point is DDL time, before the
  function is ever invoked. The same unguarded recursion exists a second
  time, independently, at execution time (`Interp::stmt`/`stmt_inner`/
  `block`/`stmts` in `plpgsql_fn.rs`), partially but not fully mitigated
  there by `with_call_depth`'s one-time 16 MiB stack grab. A verifier
  confirmed no body-length cap makes "many thousands of nesting levels"
  impractical (each level costs ~10-16 bytes of source text against a
  simple-Query message cap near 1 GB), and confirmed a true native stack
  overflow aborts/SIGSEGVs the process rather than unwinding through
  `catch_unwind` — taking down every connection on this single-node server,
  not just the attacker's own session. Requires only ordinary `CREATE`
  privilege on a schema the role already owns or can use — no escalation,
  but a shared-process crash from one connection is the "stop of a shared
  service" severity anchor.
  **Fix:** add a `check_stack_depth()`-style guard (PostgreSQL's own
  mechanism for exactly this class of deeply-nested-construct recursion,
  SQLSTATE `54001`) to both `Builder::stmt`/`stmts` in `block_scope.rs` (so
  `CREATE FUNCTION` itself refuses past a bound) and to `Interp::stmt`/
  `stmt_inner`/`stmts`/`block` in `plpgsql_fn.rs` (so a single function
  body's intra-function nesting is bounded independent of
  `with_call_depth`'s once-per-invocation grow).
  **Filed as a new issue** (duplicate search for `block_scope`/PL-pgSQL
  stack-depth/stacker found no existing match).

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **The new WITH-item unread-CTE check is an uncapped `O(n²)`-class
  full-AST-walk, with zero `cancel::check()`** (medium/medium/high).
  `crates/secantus-pgplan/src/unread_ctes.rs` (new this window, commit
  `7a240f51`, RP-501): `analyse_with`'s `read(i)` closure
  (lines 79-84) and the driving `(0..names.len()).rev().find(|&i|
  !read(i))` (line 85) re-walk the statement's full AST (via
  `pg_query::NodeEnum::nodes()`, which eagerly materializes every descendant
  before any short-circuit can apply) once per CTE that the final query
  references directly — the ordinary pattern of a `SELECT` that joins/reads
  many/all of its own CTEs, no adversarial inter-CTE wiring required. A
  verifier corrected the hunter's own framing (a literal `c2` -references-
  only-`c1`-references-only-nothing *chain* is actually close to linear,
  because the `||` short-circuits on the very first later-CTE check) but
  confirmed the bottom line: the far more ordinary "final `SELECT` joins N
  CTEs directly" shape is an unavoidable `O(N * |statement|)` re-walk with no
  inter-CTE wiring needed, no `WITH`-list-length cap exists anywhere in the
  wire layer (the simple-Query cap is the same ~1 GB generic ceiling real
  Postgres uses), and `plan_select`'s only `cancel::check()` runs once,
  *before* this function, not during it — so a long-running instance can't be
  interrupted by `statement_timeout`/`CancelRequest` either, silently
  defeating that fidelity promise for this one path.
  **Fix:** replace the per-index recomputation with a single backward
  accumulation pass — one `HashSet<&str>` built by walking each CTE body
  exactly once, checked in O(1) per index instead of re-walked per index —
  and add a `cancel::check()?` inside the loop (mirroring the project's own
  RP-202 precedent for exactly this class of problem) so a pathological
  `WITH` list stays interruptible even before the algorithmic fix lands.
  **Filed as a new issue** (duplicate search found `#1636`, a different
  mechanism — exponential blow-up in `inline_ctes`/`substitute_ctes` — and
  `#2219`, `cte_walk.rs`'s unrelated recursion-depth gap for `WITH
  RECURSIVE`; neither covers `unread_ctes.rs`'s quadratic reference check,
  confirmed a genuinely new file/root cause this window).
