## 🟠 WARNING (Address within 1 week)

### New this cycle (filed as new issues)

- **Unbounded recursive descent in MongoDB query-shape hashing crashes the
  whole server on a deeply nested filter** (medium/medium/medium).
  `crates/secantus-commands/src/query_shape.rs` (new this window) builds a
  normalized "query shape" for every `explain` command by recursively
  walking the client's own filter/pipeline document (`parse`/`pathless` at
  line 354+, `serialize` at 667, `expr` at 870) with **no nesting-depth
  counter anywhere in the module**, and nothing upstream caps document
  nesting for a filter/pipeline either — the only depth caps found in the
  tree (`crud.rs:152` `MAX_NESTING_DEPTH=180`, `update.rs:1960`,
  `resume_keystring.rs:63` `MAX_DEPTH=200`) apply only to the insert/update/
  resume-token paths. `explain/mod.rs:1719-1724`'s `explain()` reaches this
  unconditionally, unauthenticated by this server's documented default
  (`require_auth=false`). At ~19 bytes/nesting-level, a filter nested a few
  thousand levels deep (comfortably under the 16 MB BSON limit) exceeds a
  MongoDB connection thread's 2 MiB platform-default stack
  (`secantus-server/src/lib.rs:567`, no explicit `stack_size`); Rust's
  guard-page stack overflow is a SIGSEGV/abort that `catch_unwind`
  (`secantus-server/src/lib.rs:1208`) does not catch, taking down the whole
  process and every connection it serves. A verifier independently confirmed
  this (correcting the hunter's "high" to "medium" given the single-node
  developer/CI deployment context and the crash-only, no-data-corruption
  impact) and additionally noted the same missing cap likely exists in
  `secantus-core`'s own filter validators (`query.rs:479/518/705`), reached
  even earlier in the same request — worth a follow-up unit next cycle.
  **Fix:** a single iterative (non-recursive) depth check at the wire/decode
  boundary mirroring `mongod`'s `BSONDepth::kDefaultMaxAllowableDepth=200`,
  applied before any of these recursive walkers get a chance to run.
  **Filed as a new issue** (search of open `security`-labelled issues found
  no match).

- **EXPLAIN's new expression-qual selectivity estimation runs three uncapped
  O(n²) loops over a client-supplied WHERE clause** (medium/medium/medium).
  `crates/secantus-pg/src/scan_estimate.rs`'s new `expr_selectivity`
  (added this window for RP-404, EXPLAIN pricing of an expression- or
  LIKE-filtered scan) dedups and indexes its list of distinct filter
  expressions with two Vec linear-scan passes (`contains`+`push` at line
  4266, then `iter().position()` at line 4288), and its callee
  `colstats.rs::clauselist_with` (986-991) inserts via a pointer-equality
  `find()` plus `insert(0, ..)` — none HashSet/HashMap-backed, none capped,
  none interruptible (zero `cancel::check()` calls in the chain). RP-387's
  new PostgreSQL-matching caps (1600 columns, 1664 target-list entries) do
  **not** bound WHERE-conjunct count, so this is a genuinely new, unbounded
  path: the same bug shape RP-387/RP-388 just fixed at five sibling call
  sites this exact window, left open at this sixth, newly-added one. A
  verifier reconstructed the asymptotics independently (≈1.25e9 string/
  pointer comparisons plus ≈30 GB of memmove traffic at N=50,000 distinct
  conjuncts, ~100-300x the cost of merely parsing the same bytes) and
  confirmed no precondition or pre-existing cap makes this unreachable (the
  specific distinction — RP-387's caps count columns/target-list entries,
  not WHERE conjuncts — is exactly the kind of check that sank two
  similar-looking candidates in the 2026-11-06 cycle; this one survived it).
  **Fix:** a single `HashMap<&str, usize>` in `expr_selectivity` for both the
  dedup and the position lookup; an insertion-order-preserving map in
  `clauselist_with` instead of `ptr::eq`-`find`+`insert(0,..)`; and
  `cancel::check()` added to the loop so this path honors `statement_timeout`/
  `CancelRequest` like the rest of the planner's big-input paths. **Filed as
  a new issue** (distinct root cause from `#2289`/`#2346` per the verifier's
  explicit check — a fresh list, not downstream of either fixed bound).

- **The new 42703 (undefined-column) error-hint pass clones the whole join
  range table once per join, uninterruptibly** (medium/medium/medium).
  `crates/secantus-pgplan/src/colhint.rs` (new this window) builds a "did you
  mean column X" HINT for any `42703` error by re-parsing the statement and
  walking its FROM clause; for a JOIN chain, `with_level()` (264-268)
  deep-clones the accumulated range-table `Vec` (every relation's owned
  column-name `String`s included) once per ON-clause visit
  (`range_item`'s JoinExpr arm, 406-424), giving ~N²/2 `Rte` clones for an
  N-way left-deep join — work spent entirely on a statement that has already
  failed. Zero `cancel::check()` calls in the file, and the one cancellation
  signal reachable on this path (`walk_expr`'s `Result` at line 302) is
  discarded via `let _ =`. A verifier corrected the hunter's join-count
  ceiling (the pre-existing `MAX_EXPR_DEPTH=2500` cap bounds a left-deep
  chain to ~1250 joins, not 2500) and added the column-count multiplier the
  hunter had omitted (up to PostgreSQL's own 1600-column cap, reachable via
  an ordinary `CREATE TABLE`), landing at roughly 1.25 billion owned-`String`
  allocations (tens of seconds of one core) from a single ~28 KB query
  message against a wide table — confirmed superlinear relative to the
  planner's own O(N·columns) legitimate name resolution of the identical
  bytes (~600x amplification), which is what distinguishes this from a
  2026-11-06 rejection of a superficially similar candidate (no cheaper
  equivalent-cost path exists elsewhere on the same connection for this
  one). Requires an authenticated session (default `trust_unknown_users=
  false` refuses unknown users) with read access to one relation it already
  owns or can read — not pre-authentication. **Fix:** give `with_level` a
  borrowed form instead of cloning the range table per JoinExpr (turns
  O(N²·columns) into O(N·columns)); separately, stop discarding
  `walk_expr`'s `Result` at line 302 and add `cancel::check()` at
  `range_item`'s entry so a `57014` cancellation can actually land. **Filed
  as a new issue.**
