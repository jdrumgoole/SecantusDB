## 🟢 CLEAN (Passed review)

**This cycle's one piece of new application logic — the SQL plan-cache
template optimization (`24f68221`, `69dd6f70`, `9fb29975`):**

`secantusd-pg` gained a cache that lets a prepared `SELECT`/`UPDATE`/
`DELETE`/`INSERT` reuse a previously-planned statement across different
parameter values rather than re-planning from scratch — a correctness-
sensitive optimization by nature, since reusing the wrong plan for the
wrong value means a statement reads or writes the wrong row. The commit
that added it was followed, in the same window and before any tagged
release, by a Linux measurement (`69dd6f70`) that found a case where a
parameter gets folded into a constant while planning (`k = $1 % 100000`,
`values ($1 % 1000)`) so that two different sentinel values pass through
the fold unchanged and the cached plan is wrongly reused for a later,
unfolded value — and a same-day fix (`9fb29975`).

Read the fixed state in full (`crates/secantus-pg/src/plan_cache.rs`,
529 lines, plus the call site in `lib.rs`):

- `params_stand_alone` is a conservative pre-filter: a statement is only
  considered for templating if every `$n` parameter appears exactly where
  substitution can safely land (compared directly with a column in a WHERE,
  one item of an INSERT's VALUES row, the whole of an UPDATE's
  `SET col = $n`, or one operand of `SET col = col <op> $n` evaluated per
  row by the executor) — anything folded into an expression at plan time
  (arithmetic, casts, `CASE`, `LIMIT`) makes the statement ineligible, which
  is the exact class of bug that got through before this commit.
- Crucially, this pre-filter is **not the only safety net**. `is_template`
  — the function that actually decides whether a plan gets cached and
  reused — does a full **structural equality check**: it takes the plan
  built with one sentinel set, mechanically substitutes the other sentinel
  set's values into it, and compares the result byte-for-byte against a
  plan built independently (via a fresh, un-related planning pass) from the
  other sentinel set. Even a parameter shape `params_stand_alone` failed to
  recognize as unsafe would, in the general case, produce a structural
  mismatch here and be refused caching rather than silently reused — the
  pre-filter is an optimization that avoids wasted planning work on
  statements doomed to fail this check, not the thing providing the
  guarantee.
- `stores_verbatim` further restricts which cached plans may be reused when
  a stand-in lands in a **stored** value (an INSERT row, an UPDATE SET):
  only the four pairings where the column has no width/domain/enum/
  generation to check and the BSON type exactly matches the column's
  storage type (`int4`←int32, `int8`←int64, `float8`←double, `text`←string)
  qualify — anything else (a `varchar` length, a domain, a narrower integer
  type) is correctly excluded, because a sentinel value passing a column
  check says nothing about whether the real value would.
- The cache (`plan_cache: Mutex<HashMap<PlanKey, PlanEntry>>`) is a field of
  `PgHandler`. Per the 2026-10-07/08 review of the per-thread catalog-cache
  change, each connection gets its own `PgHandler` on its own OS thread —
  so this cache cannot be poisoned across sessions or connections; the only
  question was ever within-session correctness, which the structural check
  above covers.

No new finding. This is exactly the kind of self-caught, same-window,
pre-release fix the project's own process (claim → measure → fix) is
designed to produce, and it worked as intended here.
