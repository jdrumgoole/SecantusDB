## This cycle's real change, read in full

`enableTestCommands` flipped from `False` to `True` in
`_get_parameter`/`getParameter` (`commands.py:1801`), and `configureFailPoint`
gained two more live behaviours: an `appName` filter scope
(`failpoints.py`'s `_FailCommand.app_name`, matched in `dispatch` via
`_failpoint_app_name`) and a `maxTimeAlwaysTimeOut` failpoint
(`_configure_max_time_always_timeout` / `_max_time_forced_to_expire`). This
matters here specifically because `configureFailPoint` is fault injection —
`closeConnection`, forced error codes, forced timeouts — and unlike most
commands it is deliberately **not** in `_NO_PRIVILEGE_COMMANDS`. Traced the
gate for both new behaviours before treating this as safe:

- `_configure_fail_point`'s registration in `_COMMAND_ACTIONS`
  (`commands.py:8985`: `"configureFailPoint": (A_CONFIGURE_FAIL_POINT,
  SCOPE_CLUSTER)`, with the comment "Fault injection is a server-wide DoS
  lever ... require an explicit cluster-admin grant under `--auth`") is
  unchanged by this commit — the new `appName` scoping and
  `maxTimeAlwaysTimeOut` mode are both configured through the same
  `configureFailPoint` handler, so they inherit the existing gate. Confirmed
  the identical entry exists on the Rust side
  (`crates/secantus-commands/src/rbac.rs:63-66,138`,
  `crates/secantus-commands/src/lib.rs:1674`) — the two servers do not
  diverge on this property.
- `server.py`'s new `except CloseConnectionRequested: return False` (for a
  `closeConnection` failpoint firing mid-streamed-heartbeat) and the Rust
  mirror in `secantus-server/src/lib.rs` (three `if close { return Ok(...) }`
  sites) both drop the socket cleanly rather than looping or leaking a
  traceback — read in full, no error-swallowing on a write/commit path (N/A
  here, this is a read-only diagnostic path) and no unbounded retry.
- `cursors.py`'s new `mark_time_limited` / `is_time_limited` add one `bool`
  field per existing cursor entry — no new allocation surface, no new cap
  needed beyond the cursor registry's existing TTL pruning.

**Found while tracing this: the Rust server's `killSessions` /
`killAllSessions` / `killAllSessionsByPattern` went from an inert no-op to a
live one in the same commit, and inherited a standing bug in the process.**
`crates/secantus-commands/src/lib.rs:447-450` used to route all four
session-admin commands to `diagnostics::ok_session_noop`. This commit splits
them: `endSessions`/`killSessions` now call `abort_listed_sessions`
(aborts the transaction of every session ID listed in the command),
`killAllSessions`/`killAllSessionsByPattern` now call
`TransactionRegistry::abort_all()` (aborts *every* open transaction on the
server, ignoring the user/pattern filter, matching `commands.py`'s existing
`_kill_all_sessions` — this asymmetry with real mongod is intentional per
its own comment). None of the three privileged-sounding names — `killSessions`,
`killAllSessions`, `killAllSessionsByPattern` — appear in `command_action()`
(`lib.rs:1626`, the Rust mirror of `_COMMAND_ACTIONS`) or in
`is_no_privilege_command()` (`lib.rs:1599`), so they fall through the same
fail-open "`if let Some((action, scope)) = command_action(name) { check }`"
gate as **#1160**/**#1226** on the Python side (`lib.rs:1510-1511`, mirroring
`commands.py:9834`). This is exactly the standing WARNING **#1226**
("killSessions/killAllSessions/killAllSessionsByPattern bypass RBAC
entirely"), which was filed against the Python server on 2026-09-02 when the
Rust side's equivalent commands were still harmless no-ops. As of this
commit that is no longer true: under `--auth`, any authenticated user on the
Rust server can now call `killAllSessions` and abort every other principal's
in-flight transaction cluster-wide, with real effect. Documented as a
comment on the existing issue rather than a duplicate filing — same bug
class, same command names, same fix (add the three to both servers'
privilege tables together so they can't drift again):
<https://github.com/jdrumgoole/SecantusDB/issues/1226#issuecomment-5853538140>.
`endSessions` itself is unaffected: mongod allows it pre-auth and
privilege-free too (a session ID is a high-entropy UUID, not something an
attacker enumerates), so that part matches the exemplar and is not a
regression.

## 🔴 CRITICAL (Immediate action required)

All three re-confirmed by fresh direct reads against current HEAD (see above):

- **#995** — `crates/secantus-wire/src/lib.rs:100-151` (`Header::body_len`).
  `message_length` is `pub message_length: i32`; `body_len()` does
  `if (self.message_length as usize) < HEADER_SIZE { ... }` first — for a
  negative `message_length` (e.g. `-1`) this sign-extends to
  `usize::MAX - n`, which is `>= HEADER_SIZE`, so the floor guard does not
  fire; `if self.message_length > MAX_MESSAGE_SIZE` next compares the
  still-negative signed `i32` against a positive bound, which is never true,
  so the ceiling guard does not fire either. The final line
  `Ok(self.message_length as usize - HEADER_SIZE)` returns the same huge
  value minus 16. The caller (`crates/secantus-server/src/lib.rs`) feeds that
  straight to `shared.alloc_budget.acquire(body_len)` — whose
  `while *used != 0 && *used + n > self.cap` loop **skips its own wait
  whenever `*used == 0`**, i.e. on an otherwise-idle server — and then to
  `vec![0u8; body_len]`. Rust's default global allocator aborts the process
  on an allocation failure at this size. One unauthenticated 16-byte frame
  (a crafted header with a negative `message_length`) takes the whole
  Mongo-wire Rust server down. **Not fixed.**
- **#1160** — `src/secantus/commands.py:8914-8997` (`_COMMAND_ACTIONS`
  table, 84 entries), `:9834` (the RBAC gate: `info =
  _COMMAND_ACTIONS.get(name); if info is not None: ...` — skip-on-unknown
  rather than deny-on-unknown). `bulkWrite` is not a key anywhere in the
  table (confirmed by a full read of the dict this cycle). An authenticated
  connection with zero role grants under `--auth` can still call `bulkWrite`
  and have every one of its constituent insert/update/delete ops executed
  with no privilege check at all. **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471`. `_compile_regex`'s only gate
  is `len(pattern) > _MAX_REGEX_PATTERN_LEN` (1000 chars) ahead of an
  unbounded `re.compile(pattern, flags)` — no backtracking-depth limit, no
  compile/match timeout — and the `TypeError`-recovery fallback inside
  `_op_regex` (triggered by an unhashable pattern argument) does a second,
  uncapped `re.compile(regex_pattern, flags)` that bypasses even the length
  check. A short pathological pattern (e.g. `(a+)+b`) against an adversarial
  non-matching string pins a worker thread's CPU indefinitely via an
  unauthenticated `find`. **Not fixed.**
