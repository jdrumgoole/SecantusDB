## 🟠 WARNING (Address within 1 week)

### Updates to open issues this cycle (not new issues — same root cause)

- **`#2289` (RP-320/RP-321) — reachability widened.** RP-321's O(n²)
  `count()`-target dedup loop (`crates/secantus-pg/src/lib.rs:41649`,
  `for f in agg.items.iter().filter_map(...) { if !fields.contains(&f) {
  fields.push(f); } }`) keeps a byte-identical loop body (confirmed via
  content hash against the base commit), but this window's RP-382 work
  (`#2353`+) deleted its `let indexed = self.index_relations()...` /
  `&& (agg.filter.is_empty() || !indexed)` guard and widened the outer
  structural match from `tree.children[0].name.starts_with("Seq Scan on ")`
  to `explain::is_relation_scan(...)`, which also matches `"Index Scan
  using "` and `"Index Only Scan using "` (`crates/secantus-pg/src/
  explain.rs:1778-1782`). Net effect: `EXPLAIN SELECT count(c1), ...,
  count(cN) FROM t WHERE <clause>` now reaches the uncapped dedup loop on an
  indexed table with a WHERE, or on a plan the server resolves to an Index
  or Index-Only Scan — plan shapes the original `#2289` finding's `!indexed`
  guard excluded. The sibling RP-320 block (`lib.rs:41537-41557`) was **not**
  broadened; it still carries its own `!indexed` guard. The worst case is
  unchanged (the pre-existing unindexed-Seq-Scan shape already admitted an
  unbounded column count), so severity stays **medium/medium/medium**,
  matching `#2289`'s existing rating — only the reachable-shape set grew, not
  the blast radius. **Fix:** the `HashSet`-based rewrite `#2289` already
  recommends for both blocks closes this too; additionally fix the
  structurally identical loop at `lib.rs:41737-41741` (grouped-aggregate
  block) in the same pass, since it shares the shape and could be
  broadened the same way by a future change.

- **`#2346` (`comma_join_conds`) — strengthened: two more uncapped quadratic
  loops added alongside the original one.** RP-375 (`#2355`) rewrote the
  `spanning`/`rest` computation in `crates/secantus-pgplan/src/ruleutils.rs`'s
  `comma_join_conds` (now at lines 4333-4399). The original defect — `for i
  in spanning.into_iter().rev() { texts.push(quals.remove(i).0); }`
  (line 4392, each `Vec::remove` an O(len−i) memmove) — survives verbatim.
  Alongside it, this window added: (B) a `rest` filter (line 4379-4382) that
  calls `spanning.contains(i)` — a linear scan — once per conjunct, Θ(N·
  |spanning|); and (C) a reordering loop (line 4386-4389) that calls
  `slots.iter().position(...)` once per element of `rest`, Θ(|rest|²). A
  fresh verifier independently re-derived all three from scratch and
  corrected the wire-ceiling citation: the real inbound bound is
  `LARGE_PACKET_SIZE_LIMIT` (~1 GiB − 1, `crates/secantus-pgwire/src/
  messages/mod.rs:51`), not `i32::MAX` (that constant is the *outbound*
  `LONG_BACKEND_PACKET_SIZE_LIMIT`, irrelevant here); `MAX_TEXT_BYTES` (2 MiB,
  `crates/secantus-pgplan/src/lib.rs:4353`) only skips the parse-tree memo,
  not statement rejection, and ~170,000 short conjuncts already fit under
  it. `ruleutils.rs` has **zero** effective cancellation points (the one
  expression walk reachable, `qual_operators`, discards its cancellable
  `Result` with `let _ =`). The three loops have complementary trigger
  shapes — loop A is cheap when conjuncts are all cross-table equalities
  (contiguous-suffix removal), which is exactly when loops B/C are
  expensive, and vice versa for an interleaved payload — so **a fix limited
  to the `Vec::remove` loop, as `#2346`'s current text proposes, would leave
  a reachable quadratic behind.** Severity unchanged at
  **medium/medium/medium** (CPU confined to the issuing connection's own OS
  thread, `crates/secantus-pg/src/server.rs:762`'s one-thread-per-connection
  model). **Fix (updates `#2346`'s remediation):** replace `spanning:
  Vec<usize>` with a per-position classification (`Vec<bool>` or small enum)
  computed in one pass so the membership test is O(1) (kills loop B); build
  both output vectors in a single forward pass over
  `std::mem::take(quals).into_iter().enumerate()` instead of repeated
  shifting removals (kills loop A); and replace the `slots`/`originals`/
  `position` round-trip with a direct `sort_by_key` on the collected
  join-filter conjuncts alongside their cost (kills loop C). Separately, add
  a `cancel::check()?` at the head of the partition pass (or hoist one into
  `plan_explain` before the call, `crates/secantus-pgplan/src/lib.rs:10102`),
  and have `qual_operators` propagate `walk_expr`'s `Result` instead of
  discarding it.
