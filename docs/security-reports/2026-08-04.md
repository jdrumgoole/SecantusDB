- **`246fec1f` + `6a703d80` + `28c16ee1` — Rust storage engine: background
  oplog pruner, shard-existence mask, transactional DDL, DDL-vs-scan
  generation check, gated post-image clone, `anyhow` RUSTSEC fix (#752,
  #761, #757).** The single largest diff (`crates/secantus-storage/src/lib.rs`,
  +872/−295 net across the cycle) and this cycle's main review target.
  Read in full (`git diff a60c8184..HEAD -- crates/secantus-storage/src/lib.rs`,
  1312 diff lines) rather than sampled, given the file's history (W1 and W4
  both live here). Findings:
  - **New background thread (`spawn_oplog_pruner`)** moves oplog-retention
    sweeps off the writer/drainer threads. Every new lock acquisition uses
    the poison-tolerant `.lock().unwrap_or_else(|e| e.into_inner())` form —
    exactly the pattern **W1** has been asking for on the *pre-existing*
    oplog mutex for fourteen cycles, just not applied there yet (W1's two
    sites are untouched by this diff — see below). Sweep failures are
    `eprintln!`'d, never swallowed, and retried on the next wake — consistent
    with `CLAUDE.md`'s "never dismiss an error" rule. The thread is stopped
    and joined in `Storage::drop` before the WT connection closes (it opens
    its own WT sessions, so ordering matters and is handled correctly).
  - **`ddl_generation_scope` / `with_ddl_generation_check`** — a seqlock-style
    counter closes the "Rust lock-free reads: DDL-vs-scan wobble" gap
    (`tasks/backlog.md`, previously documented as returning a *partial*
    result set — never a wrong document, but an incomplete one — when a
    lock-free scan raced a `dropCollection`/`renameCollection`/`dropDatabase`).
    The retry loop is soundly bounded: `const DDL_SCAN_RETRIES: usize = 5`,
    with a 1ms sleep between attempts only when a DDL is genuinely mid-flight
    — a DDL storm degrades to "last result stands" (pre-fix behaviour), it
    cannot livelock or spin a reader. Pre-bump-not-post-commit ordering
    (`fetch_add` before the DDL's row writes, guard restores parity on every
    exit path including error) is the detail that makes the seqlock sound;
    verified the guard type (`DdlGenScope`) unconditionally decrements on
    `Drop`, so an early `?` return can't leave the generation stuck odd.
  - **Namespace DDL now runs inside `with_statement_txn` +
    `retry_write_conflicts`** (create/drop index, drop-all-indexes,
    create/drop/rename collection, `dropDatabase`) instead of
    autocommit-per-row-write, closing a previously-documented crash-window
    where a mid-DDL crash could strand orphan index-entry rows. `dropDatabase`
    commits per-collection (bounded WT dirty-cache footprint, matches
    mongod's unit). No new `unsafe`, no new panic/unwrap/expect reachable
    from a request — the sole new `.expect(...)` in the whole diff is
    `spawn_oplog_pruner`'s `.expect("spawn secantus-oplog-pruner")` on
    `thread::Builder::spawn`, which only fails on OS thread-exhaustion at
    `Storage::open` time, not from any wire input.
  - **`want_post_image: bool` plumbed through the update/pipeline-update
    storage trait** (`crud.rs`, `findandmodify.rs`, `storage.rs`,
    `secantus-storage-adapter`, `secantus-storage-py`, `replay.rs`) so a
    plain `update` skips the per-doc post-image clone that only
    `findAndModify {new: true}` actually reads. Pure plumbing, every call
    site updated consistently (grepped `want_post_image` across all six
    touched files — no site left passing a stale positional arg), no
    security-relevant change.
  - **`cargo update -p anyhow` (1.0.102 → 1.0.104) in all four lockfiles**
    clears **RUSTSEC-2026-0190** (`anyhow::Error::downcast_mut()` unsoundness)
    — `tasks/backlog.md` had this queued as "do it next time the relevant
    lockfiles are regenerated"; this cycle did. `cargo-audit.yml`'s next
    scheduled/PR run (`30827899219`, 2026-08-03T15:31:32Z, **after** the fix
    commit) passed clean. See CLEAN below.
  - **W1 and W4 status, re-verified directly rather than assumed stale:**
    W1's two `.lock().unwrap()` sites on the oplog mutex are **unchanged in
    substance** — still exactly 2 bare (non-poison-tolerant) sites, now at
    `lib.rs:5123` and `:5222` (shifted from `:4897`/`:4989` purely by the
    872-line file growth above them; same `prune_oplog`-adjacent
    `live_count` accessors, byte-identical statements). W4's
    `pending_async: Vec<(OplogEntry, Option<Vec<u8>>)>` still has no
    size/count cap (`grep -n pending_async` → same 6 call sites, `.clear()`/
    `mem::take()` on commit/rollback, nothing bounding growth *during* an
    open transaction). Neither fix rode in on this cycle's otherwise
    security-conscious storage slice — both remain open on their existing
    issues.
  - **I36, updated (not a new item — a scope correction from re-reading the
    whole `Storage::drop` this cycle instead of the previously-documented
    subset):** the bare `let _ =` join/send-result discard pattern in
    `Storage::drop`'s shutdown path is broader than previously written up.
    Direct read of `:drop` end-to-end found **four** sites across three
    thread groups: the (new this cycle) oplog-pruner join (`:3263`), the
    (pre-existing, previously unmentioned by I36) periodic checkpoint-thread
    join (`:3277`), and the (pre-existing, what I36 originally described)
    async-oplog drainer's `tx.send(Shutdown)` (`:3291`) and `handle.join()`
    (`:3296`). All four are the same low-severity shape: best-effort
    shutdown of a thread whose work is already durable by the time `drop`
    reaches it (the pruner's sweep target is opportunistic maintenance, the
    checkpoint thread's real correctness anchor is the explicit
    `self.stable_checkpoint()` call two lines later, and the drainer's
    entries are flushed before this point per the surrounding comment) — a
    discarded panic-on-join here would surface as a silent thread death, not
    a lost write. Same recommendation as before: `if let Err(e) = h.join()
    { eprintln!(...) }` at all four sites rather than `let _ =`, for the
    same "never silent" principle the file's own checkpoint-error handling
    two lines away already follows.
- **SQL/Postgres-wire datetime fixes (`0be96ccd`, `3ae2c351`, `e12d0040`,

  surface added. `parse_iso_datetime`'s new leap-second handling recurses
  at most once (the recursive call strips `:60`→`:59`, so the second call's

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open — 15th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:5123` and `:5222` (line numbers
shifted from `:4897`/`:4989` purely by this cycle's 872-line net growth
earlier in the file — same two `prune_oplog`-adjacent `live_count`
accessors, confirmed byte-identical statements by direct diff). Notably,
this cycle's *new* oplog-pruner thread (added in the same file, same
commit range) uses the poison-tolerant `unwrap_or_else(|e| e.into_inner())`
form throughout for its own new lock sites — the fix pattern is already
established local precedent in this exact file, just not yet backported to
these two pre-existing sites.

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **fifteen** consecutive review cycles.

**Recommendation:** unchanged — convert both sites to
`ctx.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The recommended
grep-based CI gate (`! grep -rn '\.lock()\.unwrap()' crates/secantus-storage
crates/secantus-commands` outside `#[cfg(test)]`) remains unimplemented
after fifteen nightly re-discoveries.

### W2 (carried forward, still open — 12th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:6004` (`drop_index`) and `:6121`
(`drop_all_indexes`) — file untouched this cycle (not in the 83-file diff),
re-confirmed present by direct read: both still open only `with self._lock:`,
never `self._coll_lock(db, coll)`, unlike `create_index` (`:5768`, `with
self._coll_lock(db, coll), self._lock:`).

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24. The hazard is unchanged: a concurrent `insert`/`update`/`delete`
(which takes `_coll_lock` first) is not excluded by `drop_index`'s
`_lock`-only critical section.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.

### W3 (carried forward, still open — 5th consecutive cycle) — `_emit_oplog`'s bare-autocommit path can permanently freeze the change-stream visible tail on a write error

**File:** `src/secantus/storage.py:2382-2484` (`_emit_oplog`) — untouched

surrounding `try/finally`, unlike `_batch_transaction` and
`commit_user_transaction`'s flush, which both deregister inside a `finally`.

Already tracked as open issue [#714](../../../../issues/714), filed
2026-07-31, unfixed across a 5th consecutive cycle.

**Recommendation:** unchanged — wrap the mint-to-deregister region of the
bare autocommit path in `try/finally`.

### W4 (carried forward, still open — 3rd consecutive cycle) — Rust user-transaction async-oplog buffer (`pending_async`) has no size/count cap

**File:** `crates/secantus-storage/src/lib.rs:148`
(`UserTransactionHandle::pending_async: Vec<(OplogEntry, Option<Vec<u8>>)>`)
— re-confirmed present and unchanged this cycle despite the same file
receiving substantial (+872/−295) unrelated changes elsewhere this cycle;
`grep -n pending_async` returns the same 6 call sites as last cycle
(construction, two `.clear()` sites, one `mem::take`), none of which add a
bound.

Already tracked as open issue [#750](../../../../issues/750), filed
2026-08-02, unfixed across a 3rd consecutive cycle.

**Recommendation:** unchanged — add a size/count ceiling on `pending_async`
and reject or flush early once exceeded, rather than growing unbounded for
the life of an open transaction (bounded to the 60s
`transactionLifetimeLimitSeconds`-equivalent reap, not truly unbounded, but
still uncapped within that window).
