- **`3bb6a791` — "let WiredTiger enforce unique indexes" (`src/secantus/storage.py`, +190/−7).**
  A new WT table, `table:secantus_unique_keys` (`(db, coll, index,
  escape(sortkey)) -> RecordId`), closes a previously-documented gap
  (`tasks/backlog.md` "UNIQUE constraints across transactions"): the old
  uniqueness check was a snapshot-read probe taken *before* the write, which
  cannot see a value another transaction committed after that snapshot, nor a
  second writer inserting the same value concurrently — both were silent
  duplicate-storage windows. The new table makes the key **be** the indexed
  value, so a non-overwrite WT insert (`_claim_unique_key`) turns a real
  duplicate into WT's own `WT_DUPLICATE_KEY`, and two racing inserts of the
  same value collide as a write conflict (retried into a clean 11000 by the
  existing retry wrapper) rather than both silently succeeding. Reviewed the
  full diff line-by-line:
  - **Every `_write_index_entries` call site that can raise the new
    `UniqueKeyTaken` is caught** — grepped all four call sites
    (`insert_many` ordered/unordered, `update`, `findAndModify` upsert) and
    confirmed each is wrapped in `except UniqueKeyTaken`, translating it into
    the same `{code: 11000, errmsg, keyPattern, keyValue}` shape the
    pre-existing probe error uses, so a client sees one behaviour either way
    and no Python traceback reaches the wire.
  - **Additive, not a format change** — the entries table (`_IDX_ENTRIES_TABLE`)
    and every read/query path are untouched; a store opened from an older
    build gets an empty `_UNIQ_TABLE` (created idempotently at every open,
    matching the existing "WT create is idempotent" pattern the doc-shard
    comment already documents) rather than a migration or a refused-open. The
    team's own `tasks/backlog.md` writeup explicitly reasons through this: an
    empty table on an upgraded store "cannot produce a FALSE rejection" —
    confirmed correct by reading the insert-only claim path, which only
    *rejects* on a collision it can see, never manufactures one.
  - **One accepted, explicitly-documented residual gap, not a new finding**:
    `create_index` only backfills `_UNIQ_TABLE` when building a *new* index
    (the scan-and-claim loop added at `:5968` / `:6013`); an index that was
    already built before this feature shipped hits the "index exists, return
    False" early-out and is never rescanned, so its pre-existing keys aren't
    retroactively claimed. The old snapshot-probe remains the sole guard for
    those specific untouched keys until the index is next rebuilt or each key
    is individually re-touched by a write — a narrow, low-severity
    upgrade-window gap the team already reasoned through and wrote up
    verbatim in `tasks/backlog.md` ("a store written by an older build simply
    has an empty table, which cannot produce a FALSE rejection"). Reviewed
    and concur with that call; recorded under CLEAN below rather than as a
    new item since it's a considered, documented trade-off, not an
    oversight.
  - **New `contextlib.suppress(Exception)` cleanup paths — flagged as I41,
    see INFO.** `_undo_partial_insert` (rolls back a doc row + `_id` index
    entry after an unordered-batch insert loses a unique-key race) and
    `_release_unique_keys` (gives a claimed key back on delete/update) both
    swallow exceptions on their cleanup writes.
- **`61b996dc` — "back UNIQUE constraints with a storage unique index"
  (`src/secantus/sql/executor.py` +58/−4, `src/secantus/sql/virtual.py` +7/−0).**
  Wires the storage fix above into the SQL front end: `CREATE TABLE …
  UNIQUE` and `ALTER TABLE … ADD CONSTRAINT … UNIQUE` now call
  `storage.create_index(..., {"unique": True, "partialFilterExpression":
  <all-columns-not-null>})` instead of relying solely on
  `executor._validate_unique_rows`'s own probe-then-write. Reviewed:
  - **SQL NULL semantics preserved correctly.** SQL treats NULLs as
    mutually-distinct for UNIQUE (any number of NULLs are allowed; a
    multi-column constraint is unconstrained if *any* column is NULL) —
    opposite of a bare Mongo unique index, which would collide NULLs. The
    partial filter (`{$and: [{col: {$ne: None}} for col in columns]}`)
    reproduces the SQL rule exactly, and the code comment correctly notes
    *why* `sparse` alone would be wrong (a SQL NULL is stored as an explicit
    BSON null, not a missing field, so a sparse index would still index it).
  - **DEFERRABLE constraints are deliberately excluded** (`if getattr(uq,
    "deferrable", False): return`) — a WT-enforced index would reject the
    transiently-invalid intermediate state a deferred constraint is supposed
    to tolerate (the classic value-swap case,
    `tests/test_sql_deferred.py`). Documented as an accepted, narrow
    trade-off in `tasks/backlog.md`, not a bug.
  - **`ALTER TABLE … DROP CONSTRAINT`** drops the backing storage index
    inside `with contextlib.suppress(Exception):` before removing the
    constraint from the catalog unconditionally — see I41 below; if the
    storage-level drop fails, the SQL catalog says the constraint is gone
    but the WT-level index keeps enforcing it, so a later legitimately-valid
    insert can fail with a confusing duplicate-key error against a
    constraint the client believes doesn't exist any more.
  - **Reflection deduplication** (`virtual.py`): `_indexes()` now skips a
    storage index whose name matches a declared constraint's name (the
    constraint's own row already carries the `conname`/`conkey` a client
    expects) — without it `pg_indexes` would have listed the same index
    twice. Straightforward, no injection surface (pure Python set
    membership against catalog-internal names, no client input).
  - No new `eval`/`exec`/dynamic SQL construction; the new `create_index`
    call passes a Python dict built from catalog column names, never a
    client-supplied string.
- **`970a0756` + `12de0609` — `validate.yml` gains a `plan` job to filter its
  33-lane matrix by the `only` workflow_dispatch input (`.github/validate-lanes.json`
  extracted from the old inline matrix, `plan` job resolves + filters it via
  `jq`, `validate` consumes it via `fromJSON(needs.plan.outputs.matrix)`).**
  The first attempt (`#773`, folded into last cycle's report) put
  `matrix.driver.name` in the `validate` job's own `if:`, which GitHub
  rejects at parse time (`matrix` isn't a value a job-level `if` can see) —
  broke every trigger, including the Monday cron, until `970a0756` moved the
  filtering into a separate `plan` job. `12de0609` then fixed a `jq` scoping
  bug in that job's `select()` (piping `.name` through `$only` indexed a
  string instead of comparing against it — `"Cannot index string with
  string"`, caught on the first real `only=rust` dispatch). Reviewed both
  for the workflow-security checklist:
  - **§12b (untrusted-input injection): the `only` input is read via `env:
    ONLY: ${{ inputs.only || '' }}` and referenced as `"$ONLY"` inside the
    `run:` block, never interpolated directly into the shell script** —
    correct pattern, matches the rest of the file. The `jq --arg only
    ",$ONLY,"` call passes it as a bound jq variable, not string-concatenated
    into the jq program text, so there's no jq-program-injection angle
    either (jq has no shell-out primitive `--arg` values could reach even if
    there were).
  - **§12a (pinning): the new `plan` job's `actions/checkout` is SHA-pinned**
    (`3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`), consistent with
    every other job in the file; it also uses `sparse-checkout:
    .github/validate-lanes.json` to avoid a full clone for a job that only
    needs one file — a nice-to-have, not a security property, but worth
    noting as a good pattern.
  - **§12c (permissions scope): the new `plan` job — like the pre-existing
    `validate` job — declares no `permissions:` block**, so both inherit
    whatever the repository's default `GITHUB_TOKEN` scope is rather than an
    explicit least-privilege grant. This is the same standing gap as **W5**
    (below), now present on two jobs instead of one; `plan` only checks out
    one file and doesn't push/write anything, so its actual blast radius from
    the missing grant is smaller than `validate`'s, but the fix is the same
    one-line addition and should cover both jobs at once.
  - Zero new `uses:` lines beyond the reused, already-pinned `actions/checkout`;

## 🟡 INFO (Best-practice recommendations)

One new item this cycle (I41); all others re-confirmed present and
unchanged (their underlying files were not touched this cycle):

- **I41 (new this cycle)** — Three new `contextlib.suppress(Exception)`
  sites added by this cycle's unique-index feature, all on cleanup/rollback
  paths rather than the primary write path, but all silently discard an
  error the codebase's own stated policy ("never dismiss or suppress...this
  is a database") argues should at minimum be surfaced (`eprintln!`-style,
  matching the pattern this file's own oplog-pruner thread already uses on
  the Rust side per prior cycles):
  - `src/secantus/storage.py` `_undo_partial_insert` (`:6394-6407`) — rolls
    back a doc-table row and `_id`-index entry after an unordered batch
    insert loses a unique-key race; if the rollback write itself fails
    (e.g. a WT error), the failed insert's partial row can be left behind
    unreachable via the normal `_id` lookup path (orphaned row, not a lost
    or corrupted *existing* document — the insert that triggered this was
    already being rejected with a duplicate-key error to the client).
  - `src/secantus/storage.py` `_release_unique_keys` (:6435-6455) — gives a
    claimed unique-index key back on delete/update; if the release fails,
    the key stays reserved indefinitely, causing a **future**,
    legitimately-valid insert of that same value to be incorrectly rejected
    as a duplicate (an availability/correctness regression, not a data-loss
    one).
  - `src/secantus/sql/executor.py` `_apply_alter_action`'s `DROP CONSTRAINT`
    path (:445-447) — drops the backing storage index inside `suppress`,
    then unconditionally removes the constraint from the SQL catalog
    regardless of whether the drop succeeded; a failed drop leaves the WT
    index still enforcing uniqueness under a constraint the catalog now
    says doesn't exist, so a later valid insert can fail with a
    duplicate-key error the client has no way to explain from the schema it
    can see.

  All three require an underlying WT operation to fail on an
  already-narrow, already-erroring code path (not attacker-triggerable via
  ordinary wire input) — hence INFO, not WARNING — but they're new code
  this cycle adding exactly the swallowed-exception shape the project's own
  CLAUDE.md and prior reports' I36 have flagged elsewhere. Recommendation:
  replace each `contextlib.suppress(Exception)` with a narrow
  `except`+`eprintln!`/`logging.warning`-equivalent that surfaces the
  failure rather than a blanket swallow, consistent with the "never dismiss
  an error" rule the surrounding storage code otherwise follows carefully
  (e.g. this exact cycle's own `_claim_unique_key` re-raises rather than
  swallowing).
