**The four changed commits, in detail:**

- **RP-297 (`#2239`, `secantus-pg/src/lib.rs` + `serializable.rs`):**
  `priced_scan_am`'s planner-costing path previously sized a table's heap by
  decoding every row (`heap_pages`) just to learn whether it returned `Some`,
  and sized each B-tree index from a full row count — an O(n) cost to answer
  a planning question, causing a 200k-row lookup after any DDL to take ~2.1s.
  It now reads the heap's and each B-tree model's page counts the way
  PostgreSQL's `RelationGetNumberOfBlocks` does, falling back to a row count
  (behind a `OnceCell`-memoised closure, so it is computed at most once per
  call even when both the heap-sizing and index-sizing paths need it) only
  for tables/indexes with no page model. This is a planner **performance**
  fix with no behavioural/security surface: no new `unsafe`, no new
  panic/unwrap/expect reachable from a client query, no change to what a SQL
  client can read or write — purely how the cost estimate is computed
  internally. The `OnceCell` closure runs on the same thread handling the
  one query, so there's no concurrency hazard. Also touched:
  `validation_summary/driver_panels.py`'s artifact-age check moved from a
  naive local `datetime.fromtimestamp` to UTC (fixing a DST-crossing test
  flake) — internal tooling, no wire exposure.
- **RP-294 (`#2240`, `secantus-pg/src/lib.rs` + `secantus-pgplan/src/lib.rs`):**
  `int2vector`/`oidvector` fields (used by the built-in catalog rows,
  e.g. `pg_proc.proargtypes`) were being pushed through the general array
  decoder, so a one-element vector became a bare integer and a
  multi-element one a string — breaking `proargtypes::regtype[]`. The fix
  routes these two types through their own input functions
  (`secantus_pgplan::cast_text_to`, already used for every other typed
  literal) in three reachable spots: `copy_field` (a `COPY`-loaded value),
  comparison-operand coercion (`coerce_unknown_operand`), and column-literal
  coercion (`coerce_to_column`). All three reuse the existing, already-
  reviewed `cast_text_to`/`cast_value` machinery rather than adding a new
  parser; the input is a short, space-separated list of small integers
  (type OIDs), bounded by the same overall message-size limits as any other
  literal — no new unbounded-allocation surface. No `unsafe`, no new
  panic path.
- **RP-308 (`#2241`, `secantus-pgplan/src/lib.rs`):** a `WITHIN GROUP`
  ordered-set/hypothetical-set call with a mismatched argument count
  previously raised a generic `function rank(unknown) does not exist`;
  it now names every argument's actual resolved type (direct args, then the
  ordering columns'), and adds PostgreSQL's hypothetical-set hint text.
  Purely an error-message fidelity improvement — the new code only builds a
  `Vec<String>` of type names already resolved elsewhere and formats a
  string; it introduces no new parsing of attacker-controlled bytes, no
  `unsafe`, and the error text echoes back only type names the planner
  itself already derived (no reflection of raw client bytes beyond what
  the pre-existing error path already did).
- **RP-302 (`#2242`, `secantus-pg/src/{catalog_fill.rs,catalog_meta.rs}` +
  `pg_attribute_system.tsv`):** the built-in relations' `pg_attribute` rows
  (`attcollation`/`attndims`/`attstorage`) now come from a static,
  build-time-embedded TSV of PostgreSQL 15.19's own catalog facts (via a
  `HashMap` keyed by `(attrelid, attnum)`, memoised in a `OnceLock`) instead
  of being derived from the column's type — a read-path catalog-fidelity
  fix. The TSV itself is a large (+5460/-worth of diff) regenerated data
  file with no executable content; `system_attribute_facts` only looks up
  entries for the server's own synthetic system relations (`table_by_oid`
  returning `None`), never for user data. No new external input surface.

None of the four touch wire parsing, auth, FFI/`unsafe` boundaries, cursor
