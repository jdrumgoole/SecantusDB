## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Time-series bucket catalog's per-field bookkeeping is a linear Vec scan
  under one global lock, giving O(F²) work for F distinct fields in one
  document** (likelihood high, impact high, overall **high**, confidence
  high; **issue #3117**). `crates/secantus-commands/src/bucket_catalog.rs`'s
  `Bucket.new_field_names` and `Bucket.columns` are both plain `Vec`
  collections (lines 291 and 274) rather than hash-based structures like the
  struct's own sibling fields `field_names`/`uncommitted_field_names` (lines
  267-268, correctly `HashSet<String>`). `try_stage()` tests membership with
  `Vec::contains` (line 884) and `insert_one()` looks up a field with
  `Vec::iter_mut().find()` (line 1707) — both O(n) scans against a
  collection that grows by one entry per distinct field name already seen,
  giving O(F²) total work for F distinct fields in one document. This runs
  entirely inside the single process-wide `BucketCatalog`'s one `Mutex`
  (confirmed singleton, `crates/secantus-storage-adapter/src/lib.rs:157`),
  held for the whole insert batch (locked at `bucket_catalog.rs:715`), so the
  cost is paid by every other time-series client on the node, not just the
  caller's own collection. No cap on distinct field names per measurement
  exists anywhere (`bucket_catalog.rs`/`ts_buckets.rs`/`crud.rs`/
  `timeseries.rs`), and a single sub-16MB document with short numeric field
  names can carry roughly a million distinct fields. **Fix (smallest
  effective):** change `new_field_names` to `HashSet<String>` (it is only
  ever membership-tested, then drained into other `HashSet`s), and add a
  `HashMap<String, usize>` side index for `columns` (keeping the existing
  `Vec` for document-field-order fidelity), turning both hot paths from
  O(F) to O(1) amortized and the whole operation from O(F²) to O(F).

- **Time-series insert-batch grouping by series key is O(n²), and the legacy
  insert command does not enforce the advertised `maxWriteBatchSize` cap**
  (likelihood high, impact high, overall **high**, confidence high; **issue
  #3118**). `bucket_catalog.rs`'s `by_series()` (lines 724-737) groups one
  insert batch's measurements into series via
  `groups.iter_mut().find(|(k, _)| *k == key)` against an accumulating
  `Vec<(Vec<u8>, Vec<Measurement>)>` rather than a `HashMap` — O(n²) total
  `Vec<u8>` comparisons for n measurements with distinct metadata in one
  batch, run under the same single global bucket-catalog mutex as the
  finding above. Separately, `crud.rs`'s legacy `insert`/`update`/`delete`
  command path (`write_parse_problem`, lines 619-656; `write_parse`, lines
  974-987) checks only that a batch is non-empty, with no upper bound —
  unlike the newer `bulkWrite` command (`bulkwrite.rs:165,612-622`), which
  does enforce `MAX_OPS` against the advertised `maxWriteBatchSize: 100_000`
  (`handshake.rs:211`). A single legacy `insert` OP_MSG can therefore carry
  several times the documented 100,000-document limit (bounded only by the
  48MB `maxMessageSizeBytes`), each measurement feeding the O(n²) scan — and
  the algorithmic flaw is already exploitable *within* the documented limit
  alone. **Fix (smallest effective):** replace `by_series()`'s linear scan
  with a `HashMap<Vec<u8>, usize>` index (series key → group position),
  making grouping O(n); separately, add the same `MAX_OPS`-style bound
  `bulkwrite.rs` already enforces to the legacy insert/update/delete
  command's parse path.

- **`$lookup`'s `foreignField` dotted-path recursion in the new SBE
  indexed/nested-loop-join builder has no depth cap, crashing the whole
  server via native stack overflow** (likelihood high, impact high, overall
  **high**, confidence high; **issue #3119**). The brand-new
  `crates/secantus-commands/src/explain/sbe/index_join.rs` (993 lines, RM-683
  "lookup indexed/nested loop join SBE") implements two new `$lookup` join
  strategies. `crates/secantus-commands/src/explain/sbe/lookup.rs`'s
  `build()` splits `foreignField` on `.` (line 198) with only an emptiness
  check (line 199), no length cap, and either strategy — `NestedLoopJoin`
  (lines 255-276, selected whenever no qualifying index exists and
  `allowDiskUse:false`, an ordinary aggregate option, against *any* existing
  foreign collection, no index required) or `IndexedLoopJoin` (lines
  230-254) — reaches `index_join.rs`'s `foreign_filter()` (called at lines
  423/559), whose inner `level()` helper (lines 162-216) recurses once per
  dotted-path component (recursive call at line 198) with no depth guard
  anywhere in the function or upstream (`secantus-core/src/sbe.rs`'s
  pushdown check and `expr_parse.rs`'s field-name validation check content,
  not component count). A `foreignField` with tens of thousands of
  dot-separated components — a few hundred KB, trivially under the 16MB
  command-document limit — drives unbounded native-stack recursion during
  plan construction, aborting the whole Rust process (not a catchable
  panic) for every connected client. This is the same bug family (client-
  controlled `$lookup` metadata driving unbounded recursion during
  explain/SBE plan construction) that produced two CRITICAL findings in this
  exact area over the last two review cycles — now reproduced a third time,
  in new code, for a new feature, rather than fixed at its root. **Fix
  (smallest effective):** add a dotted-path component-count cap (e.g. 100)
  at `build()`'s single chokepoint (`lookup.rs`, right after line 198's
  split), rejecting past the cap (returning `None`, which already makes the
  caller fall back to the non-SBE classic explain path) — one guard
  protects every downstream recursive consumer, including the related,
  unmodified `path_below()` used by the pre-existing `HashJoin` strategy.

- **The new SBE indexed-loop-join's `index_entries()` reimplements
  compound-index-key combinatorics without the storage layer's own
  `MAX_COMPOUND_KEYS` cap** (likelihood high, impact high, overall **high**,
  confidence high; **issue #3120**). `crates/secantus-storage/src/lib.rs`'s
  `index_key_values_c` (lines 4891-4909) deliberately accepts a document
  with 2+ array-valued compound-index key fields (real mongod would reject
  this as `CannotIndexParallelArrays`/error 171) and bounds the combinatorial
  blow-up at `MAX_COMPOUND_KEYS = 10_000` (line 2014) — the write succeeds,
  silently truncated, no client-visible error. `index_join.rs`'s
  `index_entries()` (lines 111-156) is a wholly separate reimplementation of
  the same per-document combinatorics: it rebuilds `per_field` from the raw
  document via `secantus_core::index_keys::field_keys` (unbounded) and
  builds the full cartesian product (lines 125-137) with **no size cap**,
  never calling into or reusing `MAX_COMPOUND_KEYS`. A client can insert one
  document with two large array-valued compound-index key fields (storage
  silently truncates only the *stored* index at 10,000 entries) and then run
  an ordinary `explain` on an `aggregate` with a matching `$lookup` — which
  reads the whole foreign collection (`explain/mod.rs`'s `Target::docs`) and
  recomputes the full, untruncated cartesian product for that one document,
  synchronously, with no `maxTimeMS`/interrupt check anywhere in
  `index_join.rs`/`lookup.rs`/`lookup_joins`. Two ~50,000-element arrays
  yield a 2.5-billion-entry product from one 16MB document and the cheapest
  explain verbosity. **Fix (smallest effective):** thread the same
  `MAX_COMPOUND_KEYS` bound into `index_entries()`'s combination-building
  loop (ideally via a shared helper both the storage and commands crates
  call), stopping generation once the cap is reached per document, mirroring
  `lib.rs:4898-4909` exactly.

- **PL/pgSQL's fast-path `DO`/`EXECUTE` interpreter recurses with no
  call-depth guard, unlike every sibling procedural-code entry point,
  letting an authenticated client crash the whole server via native stack
  overflow** (likelihood high, impact high, overall **high**, confidence
  high; **issue #3121**). `crates/secantus-pg/src/do_block.rs`'s `run_do()`
  dispatches `Stmt::Execute` to `do_execute()` (line 140), which (lines
  455-466) evaluates the `EXECUTE` argument to a SQL string and calls
  `do_run_sql()` (line 253), which calls the top-level async dispatcher
  `run_typed()` (`lib.rs:36873`) → `run_typed_inner()` (line 37270). If the
  dynamic SQL text is itself `DO $$ ... $$`, `run_typed_inner` (lines
  37507-37509) calls `run_do()` again, closing a recursive cycle with no
  depth counter and no native-stack-growth guard anywhere in it. The
  codebase's own `with_call_depth()` (`lib.rs:16951-16979` — a thread-local
  `CALL_DEPTH` counter, refusing past 200 with SQLSTATE `54001`, plus
  `stacker::maybe_grow`) is applied at all four of the codebase's *other*
  procedural-recursion surfaces (`call_user_function` at `lib.rs:17015`,
  `CALL` in `procedures.rs:296`, `triggers.rs:476`, `event_triggers.rs:477`)
  but not here. The full PL/pgSQL interpreter's own dynamic-`EXECUTE` path
  *does* explicitly refuse a nested `DO` (`lib.rs:44817-44823`, "this
  statement is not supported inside another") — proving the project already
  considers nested `DO` dangerous enough to refuse — but the fast-path
  `do_block.rs` interpreter (used whenever a `DO` block's body parses as
  only `RAISE`/`EXECUTE`/`PERFORM`/`NULL` statements, trivially satisfiable)
  calls `run_typed` directly instead, never reaching that refusal. A
  client-supplied statement containing many nested levels of literal
  `DO $$ ... EXECUTE 'DO $$ ... $$' ... $$` text (no actual
  self-reference/quine needed, just mechanically nested text, feasible in a
  few hundred KB) drives unbounded recursion, and a native stack overflow in
  this server is an uncatchable process abort — taking down every other
  connected client. Reachable by any authenticated client permitted to run
  `DO` (PUBLIC's default `plpgsql` `USAGE` grant in real PostgreSQL; nothing
  on this path imposes a stronger gate). **Fix (smallest effective):** apply
  the same `CALL_DEPTH` counter and `54001` convention at the one point the
  cycle closes (`lib.rs:37507`'s `Statement::Do` branch) via a small
  async-compatible depth guard, or more defensively, route the fast-path
  `do_block.rs` `EXECUTE` through the same "not supported inside another"
  refusal the full interpreter already enforces.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **A naive O(Q²) union-find in the PostgreSQL planner's join equivalence-
  class cost estimation, reachable via `EXPLAIN` of a many-equality join —
  same bug family as issue #3071, different file** (likelihood medium,
  impact medium, overall **medium**, confidence high; **issue #3122**).
  `crates/secantus-pg/src/scan_estimate.rs`'s `join_classes()` (lines
  8302-8414) builds equivalence classes of joined columns from a join's
  ON-clause equalities using `id()` (lines 8352-8360,
  `members.iter().position(...)`) and `find()` (lines 8363-8364,
  `classes.iter().position(|c| c.contains(...))`) — both plain linear scans
  over `Vec`s growing by up to two entries per conjunct, no hash map, no
  path compression, no union-by-size — giving O(Q²) total work for Q
  equality conjuncts. The call site in `joined_sides()` (lines 2502-2515)
  invokes it before later shape-restricting early-exit checks (lines
  2516-2526), so the expensive call runs even when its result is immediately
  discarded. **Reachability was corrected during independent verification**:
  the hunter's original claim was "reachable from ordinary query execution,"
  which a fresh verifier rejected after exhaustively tracing every caller
  (`joined_sides`, `hash_join_estimate`, `joined_implied_estimate`,
  `semi_join_estimate`, `chain_class_constant`, `hash_join_reads`,
  `shared_join_classes`) into `secantus-pg/src/lib.rs`'s `Statement::Explain`
  match arm (line 47649) and nowhere else — confirmed by `join_analyze.rs`'s
  own module comment that this server does not execute plan-node-by-node, so
  this whole subsystem exists only to make `EXPLAIN`'s printed costs match
  real PostgreSQL. The narrower, corrected claim (`EXPLAIN`-only, same shape
  as the already-filed `#3071`) stands confirmed at medium severity: cost
  scales with the square of the size of the attacker's own transmitted query
  text (bounded by pgwire's ~1GiB message limit, the same limit real
  PostgreSQL enforces), confined to that one connection's planning time, not
  demonstrated to block other connections. **Fix (smallest effective):** add
  a side `HashMap<Member, usize>` alongside the existing `Vec<Vec<usize>>`,
  turning `id()`/`find()` into O(1) amortized lookups — the same fix
  direction already recommended for `#3071`'s `ruleutils::class_ranks`.
  Secondarily, move the `join_classes()` call in `joined_sides()` to after
  the early-exit checks it currently precedes.
