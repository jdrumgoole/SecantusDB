## What's new since the last review

Nine commits landed since 2026-07-22's `2c4add75` cutoff. Zero touched
`src/secantus/**` (the Python server) at all — confirmed directly:
`git log 2c4add75..HEAD --name-only` shows only `crates/secantus-{commands,
server,storage}/src/lib.rs` (+ `crud.rs`), `tests/test_{cross_driver_features,
geo_cross_driver}.py`, and docs/changelog/backlog files touched. Three
commits carry genuine security-relevant surface (all Rust storage/server), the
rest are CI-timeout/docs-only:

- **`aa578dcc` — raw-BSON write path for inserts (~+11% single-writer).** The
  biggest surface-area change this cycle: an `insert`'s `OP_MSG` kind-1
  document sequence is now diverted un-decoded (`CommandContext.
  raw_insert_documents`) so the handler can hand the client's original bytes
  straight to `Storage::insert`/`insert_one`, which store them verbatim when
  `_id` already leads the document — skipping up to four decode/re-encode
  round-trips. Reviewed closely for exactly the class of bug a "skip
  validation for speed" change would introduce:
  - **Full BSON decode/validation still happens, exactly once, at the
    storage layer.** `Storage::insert`/`insert_one` still call `decode_doc
    (doc_bytes)?` unconditionally (`crates/secantus-storage/src/lib.rs:3196`
    region) before deciding whether to reuse the raw bytes or re-encode —
    `decode_doc` returns a `Result` (`StorageError::Bson`, not a panic) on
    malformed input, so a client sending garbage BSON in the raw path still
    gets a clean `{ok:0, errmsg}` wire error, not a crash. Verified
    `decode_doc`'s body directly (`Document::from_reader(...).map_err(...)`,
    lib.rs:851-854) — no `.unwrap()`/`.expect()` in the path.
  - **The size cap survives unconditionally.** `blob.len() >
    MAX_BSON_OBJECT_SIZE` is checked identically whether `blob` is the raw
    client bytes or a freshly re-encoded buffer, in both `insert_one` and the
    batch `insert` loop — the fast path doesn't create a way to smuggle an
    oversized document past the existing ceiling.
  - **The command-layer `_id` `$`-key pre-check (`raw_id_dollar_key_error`,
    `crud.rs`) degrades safely on malformed input** — it parses `_id` as a
    `RawDocument` and returns `None` (skip the pre-check, not an error) if
    that parse fails, but the document still flows to `storage.insert`,
    which performs the authoritative decode and rejects it there. No bypass:
    the pre-check is optimistic/best-effort, the storage layer is the actual
    gate.
  - **No new `unsafe`, no new path/URI interpolation.** The raw bytes never
    touch a WT table/URI string — they go through the same `(db, coll)`
    key-column path as before (`set_key_ssu` / `set_value_u`), just with the
    value bytes sourced from the client instead of a re-encode. `git show
    aa578dcc -- crates/ | grep -nE "unsafe|\.unwrap\(\)|panic!"` matches only
    the new unit test's own `.unwrap()` calls on `tempfile`/`Storage::open`
    (test-harness code, not the request path).
  - Sound. This is a real perf win with the validation/size-cap discipline
    fully intact — reviewed and confirmed no shortcut was taken on the
    security-relevant checks.
- **`da8da7ab` — Rust `Storage::Drop` now takes a final WiredTiger checkpoint
  in durable mode** (parity with the Python server's long-standing
  close-checkpoint). Not attacker-reachable (fires on clean process shutdown,
  after `RunningServer::stop` has drained every connection thread — no
  request is in flight). Checkpoint failure is `eprintln!`'d, never silently
  swallowed, consistent with `CLAUDE.md`'s "never ignore an error" — matches
  the existing pattern one line above it (the pre-existing oplog-meta
  persist-on-close error handling, unchanged). `durable`/`in_memory` are
  resolved once at `open()` from environment precedence
  (`SECANTUS_FORCE_DURABLE` > explicit > `!SECANTUS_TEST_FAST_STORAGE`) —
  pure function (`resolve_durable`), unit-tested, no process-env mutation
  races. Sound; a durability/perf-parity fix, not a security change.
- **`79421bcd` — disable WiredTiger log pre-allocation** (`prealloc=false`)
  to stop CI disk exhaustion on the Windows runner. Config-string change
  only, `file_max=128MB` retained; commit message states no durability
  change (recovery replays the same log records), and this only reduces
  idle-disk footprint. No attacker-reachable input involved. Sound.

The remaining six commits (`ce78fccc`, `c1ba5c5a`, `1c70f0c2`, `a432ba87`,

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**Files:** `crates/secantus-storage/src/lib.rs:2919` and `:2998`, inside
`prune_oplog_inner` (line numbers shifted again from the 2026-07-22 report's
`:2816`/`:2895` — this cycle's `aa578dcc`/`da8da7ab`/`79421bcd` all inserted
lines earlier in the same file; same two call sites, re-verified present by
direct grep of every `self.oplog.lock()` call site in the current file: 11
total, 9 using the poison-tolerant `unwrap_or_else(|e| e.into_inner())`
pattern at lines 1974, 2273, 2334, 2368, 2383, 2403, 2414, 2870, 4932, and the
two holdouts at 2919 and 2998 still using bare `.lock().unwrap()`).

This is unchanged from the last two reports and is **already tracked as open
issue [#593](../../../../issues/593)** ("Rust oplog mutex: two
non-poison-tolerant lock sites reintroduced same-day as the prior fix"),
filed 2026-07-21, still open, now unfixed for its third consecutive review
cycle. No new issue filed for it today.

**Recommendation:** unchanged from #593 — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. Two-line fix, no
behaviour change on the non-panicking path. Given this has now survived three
review cycles untouched despite two of them (today's and 07-22's) landing
substantial edits to the exact same file, the grep-based CI gate recommended
in the last two reports (`! grep -rn '\.lock()\.unwrap()' crates/
secantus-storage crates/secantus-commands` outside `#[cfg(test)]`) is
overdue — a mechanical check would have caught this reappearing risk-free at
every one of this cycle's three storage-file edits, instead of relying on a
human/LLM reviewer to re-grep it nightly.
