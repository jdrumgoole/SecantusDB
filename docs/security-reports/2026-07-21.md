## 🟠 WARNING (Address within 1 week)

### W1 (new) — Two fresh non-poison-tolerant `.lock().unwrap()` sites on the Rust oplog-state mutex, landed the same day as the fix for the identical pattern

**Files:** `crates/secantus-storage/src/lib.rs:2657` (`prune_oplog_inner`,
`live_count` read) and `crates/secantus-storage/src/lib.rs:2736` (same
function, `live_count` write).

`852ea758` fixed the 2026-07-20 report's W1 by converting every
`.lock().unwrap()` in `secantus-storage`/`secantus-commands` to
`unwrap_or_else(|e| e.into_inner())`, including all pre-existing
`self.oplog.lock()` call sites (`lib.rs:1763, 2011, 2072, 2106, 2121, 2141,
2152, 4630` — all poison-tolerant, confirmed by direct grep). Twenty-three
minutes later the same day, `cbdad10d` ("Rust: sharded oplog + bounded
prune — 1.77x single / 12.4x 8-writer writes") added a new
`prune_oplog_inner` function containing two more `self.oplog.lock()` sites,
both written with the plain `.unwrap()` form — the exact pattern that had
just been swept out everywhere else in the same mutex's call sites.

**Failure scenario:** `self.oplog` is a single `Mutex<OplogState>` guarding
oplog sequencing/timestamp state consulted by every write's `emit_oplog`
call and by the periodic prune sweep. If any code executing while this
specific lock is held ever panics, the standard library poisons the mutex
permanently; every subsequent `.lock().unwrap()` against it — including all
8 already-poison-tolerant call sites' *sibling* code paths that still route
through this same mutex instance — then also panics. Unlike the original
per-collection `coll_lock` (blast radius: one collection) or per-cursor
locks (blast radius: one cursor), this mutex is server-wide: poisoning it
would durably wedge oplog emission for every write on every collection, and
therefore change streams as a whole, until restart. No concrete
currently-reachable panic trigger was found inside either guarded section
in this pass — both are a single field read/arithmetic op, not a
panic-capable operation — so this is a defense-in-depth regression, not a
demonstrated live exploit. It is nonetheless a real regression of a fix
that was complete and correct at the moment it landed, on the single
highest-blast-radius mutex in the file.

**Recommendation:** convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`, matching every
other call site against the same mutex in the same file. This is a
two-line change. Given how this slipped in (a fast-follow perf commit
landing minutes after the sweep, touching the same mutex via new code the
sweep predates), consider a lint/grep-based CI check (`grep -rn
'\.lock()\.unwrap()' crates/secantus-storage crates/secantus-commands`,
excluding `#[cfg(test)]` blocks) so a future perf/feature commit can't
reintroduce the pattern silently.

### New this cycle

- **I25 — `cargo-audit.yml` installs `cargo-audit` unpinned by version.**
  `.github/workflows/cargo-audit.yml` runs `cargo install cargo-audit
  --locked` with no `@version` pin — `--locked` only pins cargo-audit's own
  transitive dependencies via its shipped lockfile, not which release of
  cargo-audit itself gets installed. Every other tool/action in this new
  workflow is precisely pinned (both `uses:` are full 40-char commit SHAs);
  this is the one moving-target install. Low severity — a CI-only build
  tool, not shipped to consumers, not secret-bearing — but worth a version
  pin (`cargo install cargo-audit@X.Y.Z --locked`) for full reproducibility
  and to avoid a future cargo-audit release silently changing gate
  behavior.
- **I26 — Admin change-stream websocket has no cap on concurrent
  `/ws/changes/*` connections per session.** `src/secantus/admin/routers/
  changestream.py` — an authenticated admin client can open an unbounded
  number of concurrent change-stream websockets, each holding a tailable
  cursor plus a poll thread (now correctly bounded to 500ms cadence and
  disconnect-aware by `f7c953b7`, see §7 below, but still one thread per
  open stream). Not exploitable pre-auth (token-gated by
  `verify_websocket_token`), consistent with the admin UI's
  loopback/dev-tool threat model. Worth a soft cap if the admin UI is ever
  used in a shared/multi-tenant context, not urgent for the current
  single-developer-loopback model.
