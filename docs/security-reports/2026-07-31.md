## 🟠 WARNING (Address within 1 week)

### W3 (new this cycle) — `_emit_oplog`'s bare-autocommit path can permanently freeze the change-stream visible tail on a write error

**File:** `src/secantus/storage.py:2429-2464` (`_emit_oplog`).

This cycle's oplog-visibility-point fix (`ce83e9fd`) introduces a
process-wide `self._oplog_in_flight: dict[int, int]` (`storage.py:1499`) that
tracks minted-but-unresolved oplog seq ranges; `oplog_visible_tail_seq()`
(`:1939-1949`) clamps the change-stream/tailable visible tail to
`min(self._oplog_in_flight) - 1` whenever the dict is non-empty. Every range
minted by `_mint_oplog_seq_and_ts` (`:1897-1916`) **must** eventually be
removed via `_deregister_minted`, or it pins the tail for the whole server,
forever.

There are three call sites that resolve a minted range, and only two of them
are exception-safe:

- `_batch_transaction` (`:3579-3597`) — deregisters inside a `finally`, on
  both commit and rollback.
- `commit_user_transaction`'s flush (`:3742-3750`) — deregisters inside a
  `finally`, on both a successful commit and an exception path (which then
  re-raises through `abort_user_transaction`).
- **The bare autocommit path, `_emit_oplog` itself (`deferred=False`)** —
  deregisters at `:2464`, with **no surrounding `try/finally`**. The
  preceding cursor-write loop (`:2432-2444`, `op_cur[seq] = bson.encode(...)`,
  optionally `pre_cur[seq] = pre`) must complete without raising for that line
  to be reached at all.

This bare path is the one every DDL write goes through directly (`with
self._lock:` or `with self._coll_lock(db, coll), self._lock:`, never through
`_batch_transaction`): `create_collection` (`:3895`), `create_index`
(`:5661`, wrapped only by the DDL locks), `record_collmod` (`:5603`),
`drop_collection` / `drop_database` / `drop_index` / `drop_all_indexes`
(`:5444` / `:5491` / `:5897` / `:6014`), the startup "initiating set" noop,
and the periodic heartbeat.

If the write loop throws for any reason — a WT write error under resource
pressure, a `WT_ROLLBACK` under contention (both explicitly called out in
`CLAUDE.md` as things this project must surface, never swallow), or any
future entry shape that `bson.encode` can't serialize — the request still
fails cleanly to the client (still caught by `dispatch`, no traceback leak),
but the minted range is **never removed** from `_oplog_in_flight`. From that
point on, `oplog_visible_tail_seq()` is frozen at that seq for the life of
the process: every future `read_oplog_scan`, tailable-getMore wake,
`_aggregate_change_stream` position, and PITR archive head clamps there —
change streams across the whole server silently stop advancing until
restart. This is a self-inflicted denial-of-service on the change-stream
subsystem, triggered by exactly the class of storage error (`WT_ROLLBACK`,
write-under-pressure) `CLAUDE.md`'s own "never ignore an error" standard
treats as expected to happen and required to be handled, not an exotic edge
case. It also directly undermines change-stream reliability as an
audit/security-logging mechanism, which this review's threat model calls out
as in-scope.

**Recommendation:** wrap the mint-to-deregister region of the bare autocommit
path in `try/finally`, mirroring the other two resolution points:

```python
try:
    for i, (entry, pre) in enumerate(zip(entries, pre_images, strict=True)):
        ...
finally:
    if not deferred:
        self._deregister_minted([(start_seq, start_seq + n)])
```

A regression test that forces the cursor-write loop to raise mid-batch (e.g.
monkeypatching the WT cursor to throw on the second entry) and then asserts
`oplog_visible_tail_seq()` still advances on a subsequent successful emit
would pin this.

### W1 (carried forward, still open — 11th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:4599` and `:4687` (line numbers
shifted again from `:4115`/`:4194` last cycle — the file grew by 627 lines
this cycle; same two pre-existing call sites, confirmed by `git blame` to
predate this cycle's diff at `cbdad10d`, 2026-07-20). 16 total
`self.oplog.lock()` sites; every site *added* this cycle (three new ones, in
the periodic stable-checkpoint thread and its `Drop`) correctly uses the
poison-tolerant `unwrap_or_else(|e| e.into_inner())` pattern — only the same
original two `prune_oplog` accessors remain bare.

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **eleven** consecutive review cycles
(07-21 through 07-31).

**Recommendation:** unchanged — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The grep-based CI
gate recommended in the last ten reports (`! grep -rn '\.lock()\.unwrap()'
crates/secantus-storage crates/secantus-commands` outside `#[cfg(test)]`)
remains unimplemented after eleven nightly re-discoveries.

### W2 (carried forward, still open — 8th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:5897` (`drop_index`) and `:6014`
(`drop_all_indexes`) — line numbers shifted from `:5749`/`:5866` last cycle
(the file grew by 168 lines this cycle from the W3-adjacent `ce83e9fd`
change, which does not touch these methods); re-confirmed present by direct
read: both still open only `with self._lock:`, never
`self._coll_lock(db, coll)`.

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24. The hazard is unchanged: a concurrent `insert`/`update`/`delete`
(which takes `_coll_lock` first) is not excluded by `drop_index`'s
`_lock`-only critical section.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.
