`Document::from_reader` call at the same site, which had the identical

already reachable from wire input before this commit, under a different
entry point, with the same underlying unbounded-nesting gap — but it is one
more call site that inherits the fix automatically whenever #1780 lands
upstream, and one more reason that fix is overdue.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`crates/secantus-pgplan/src/like_match.rs`'s new `like_match_bytes`
  (added in `2bc0eb25`, for `bytea LIKE bytea`) is a naive, unmemoized
  recursive backtracking matcher, and it is reachable from a single,
  ordinary SQL statement with no special privilege.** For each `%` in the
  pattern it tries every possible split point and recurses
  (`for skip in 0..=subject.len() { like_match_bytes(&subject[skip..], rest,
  escape)? }`), with no memoization and no short-circuit for a pattern that
  cannot possibly match the remaining subject. This is exactly the
  "wildcard matching" shape known to be exponential without memoization: a
  pattern of repeated `a%` pairs matched against a same-length run of the
  letter it expects, ending in one byte that never matches, forces the
  matcher to explore every way the `%`s could have split the subject before
  it can conclude failure.

  **Verified empirically, not just reasoned about** (`/tmp/like_sim2.py`, a
  line-for-line transliteration of the Rust function's control flow into
  Python): call count against `subject = "a"*n`, `pattern = ("a%")*  (n/2)
  + "Z"` grows from 58 calls at `n=6` to 878,810 calls at `n=20` — almost
  exactly doubling every time `n` grows by 1, i.e. `O(2^n)`. Even in slow
  interpreted Python this was already 0.19s at `n=20`; the growth rate means
  a pattern/subject pair of a few dozen more bytes (trivially sent in one
  `SELECT 'aaaa...a'::bytea LIKE 'a%a%a%...%Z'::bytea` or any `WHERE
  bytea_col LIKE $1` predicate) pins a connection's thread at 100% CPU for a
  duration that is for practical purposes unbounded, from a request smaller
  than this paragraph.

  **This is called from the general row/expression evaluator, not just
  constant-folding** — `eval_pattern_match_const` (the function that calls
  `like_match_bytes`, `crates/secantus-pgplan/src/lib.rs:34755`) is reached
  from the same two call sites that handle every `LIKE`/`ILIKE` expression,
  including one bound to a table column, so a single row's `WHERE` evaluation
  is enough; no large table or repeated query is needed to trigger it.

  **Not mitigated by `statement_timeout`**: it defaults to `0` (disabled,
  matching real PostgreSQL), and even with it set, the check only runs
  between portal-stream *batches* (`portal_stream.rs`, "checked before each
  batch") — a single scalar or single-row `LIKE` evaluation has no internal
  yield point, so a timeout cannot interrupt it mid-recursion regardless of
  configuration.

  Contrast with the *existing*, unmodified text `LIKE` matcher
  (`match_text`, same file, not touched this window): it is PostgreSQL's own
  `MatchText` algorithm transcribed faithfully, including its `Abort` early
  state that stops exploring a branch the moment it cannot possibly succeed
  — the reason it does *not* have this complexity class. The new bytea path
  reimplements `%` handling from scratch without that optimization. The
  text-vs-regex paths elsewhere in this same commit (`regexp_replace` and
  friends, `crates/secantus-pgplan/src/builtins_regex.rs`) are safe by
  construction because they go through the `regex` crate, which is
  guaranteed-linear (no backtracking) by design — this is the one place in
  the commit that rolled its own matcher instead and lost that guarantee.

  Filed as **#1921**.

## 🟡 INFO (Best-practice recommendations)

- **`dataSize` joins the carried-forward low-RBAC-granularity list** (see
  above): with `--auth` on, any authenticated user — regardless of granted
  roles — can call `dataSize` against any namespace and learn its byte count
  and document count, on both servers. Real MongoDB requires `find` on the
  target namespace for this command. Low practical impact (it leaks size
  metadata, not document contents) and consistent with this project's
  existing, disclosed gap for `replSetGetStatus` / the search-index
  commands — tracked here for visibility, not worth its own issue while
  those others aren't broken out individually either.
- **Carried unchanged from prior cycles** (no commit in this window touches
  the relevant surfaces): no cross-connection allocation budget on the
  Python server's in-flight message bodies (Rust has one); the "Protect
  release tags" ruleset gap (doesn't cover `refs/tags/secantusd-pg-v*`); the
  residual `--sync-on-commit` coverage gap on the MongoDB server for the
  `method=fsync` log-sync patch (still unmeasured).
- **The new CI lane (`psycopg-tls.yml`, created this window) reviewed for
  the standing GitHub Actions checklist and found consistent with it:**
  every `uses:` is SHA-pinned with a version comment, `permissions:
  {contents: read}` only, no `pull_request_target`, no `github.event.*`
  interpolated into any `run:` block, no secrets referenced, and its
  `pull_request` trigger is scoped by `paths:` to the TLS/login source files
  plus itself — not a blanket trigger on every PR. Not a new finding; noted
  because it's new surface and this is the first cycle to see it.
- **Not a security finding, flagged for awareness only:** `bench/do_pg_bench.py`
  (new, `7311dae3`) interpolates an operator-supplied `--version` string
  directly into a shell script body that is sent over SSH to a benchmark

  client), so it sits outside this project's stated threat model
  ("a malicious wire client, a poisoned dependency, or a bad wheel") the
  same way the rest of `bench/` and `tools/probes/` do. No issue warranted.
