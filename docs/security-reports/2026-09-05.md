## 🔴 CRITICAL (Immediate action required)

All three unchanged from 2026-09-04 — re-verified by reading current source,
not carried on trust. All are reachable from an ordinary (unauthenticated, for
the first two) wire client:

- **#995** — `crates/secantus-wire/src/lib.rs:136-150` (`Header::body_len`).
  Re-read this cycle, byte-identical to yesterday:
  ```rust
  pub fn body_len(&self) -> Result<usize, WireError> {
      if (self.message_length as usize) < HEADER_SIZE { ... }
      if self.message_length > MAX_MESSAGE_SIZE { ... }
      Ok(self.message_length as usize - HEADER_SIZE)
  }
  ```
  `message_length` is `i32`. A header with `message_length = -1` sign-extends
  under `as usize` to `usize::MAX` in the first check (comparison becomes
  `usize::MAX < 16` → false, guard doesn't fire), and the second check
  compares the still-signed `i32` (`-1 > MAX_MESSAGE_SIZE` → false) — both
  guards let a negative length through, and the function returns
  `Ok(usize::MAX - 16)`. Traced this cycle into `crates/secantus-server/src/
  lib.rs:553-562` (unchanged): `body_len` feeds straight into `vec![0u8;
  body_len]` after an `AllocBudget::acquire` that explicitly **lets a lone
  request through uncapped** ("a lone oversized request proceeds rather than
  deadlock", `lib.rs:87-91`) — so the budget is not a backstop here, and the
  huge allocation reaches the global allocator, which aborts the process (not
  a catchable `Result`) from one unauthenticated 16-byte frame. **Not fixed.**

- **#1160** — `src/secantus/commands.py`. Re-confirmed this cycle:
  `"bulkWrite": _bulk_write` is registered in the dispatch table (line 8608)
  but has no entry in `_COMMAND_ACTIONS` (span checked fresh this cycle,
  8693-8783, zero hits) and is not in `_NO_PRIVILEGE_COMMANDS` (8783-8806)
  either. The privilege gate at `commands.py:9613-9614` (`info =
  _COMMAND_ACTIONS.get(name); if info is not None: ...`) is still fail-*open*:
  a command absent from the table is silently exempted from RBAC rather than
  denied. `bulkWrite` still bypasses authorization entirely under `--auth`.
  **Not fixed.**

- **#977** — `src/secantus/query.py:1275` (`_MAX_REGEX_PATTERN_LEN = 1000`),
  re-read this cycle at the same line. Still a length cap only, no
  backtracking-depth or match-time budget — and the cap doesn't even help
  here: a pathological `(a+)+$`-shaped pattern is 6 characters, far under the
  1000-char ceiling. Per the 2026-09-02 live-verified finding (CPython's
  `_sre` engine never releases the GIL mid-match, confirmed to hang an
  unrelated second connection's `ping`, not just the attacking connection),
  this remains CRITICAL rather than a single-connection-cost WARNING.
  **Not fixed.**
