## 🔴 CRITICAL (Immediate action required)

All six carried forward from 2026-08-26, re-confirmed present and unfixed
(files unchanged this window, re-read against current `HEAD`, not trusted
from the prior report):

- **#1037** — `src/secantus/query.py:855-908` (`_resolve_bitmask`): the
  `$bitsAllSet`/`$bitsAnySet`/`$bitsAllClear`/`$bitsAnyClear` array-argument
  branch has no upper bound on the bit-position integer, so `mask |= 1 << bit`
  with an attacker-chosen multi-billion `bit` forces CPython to allocate and
  physically touch gigabytes of real memory while holding the GIL —
  wire-reachable via any `find`/`count`/`aggregate $match`/`update`/`delete`
  filter, no auth required with `--auth` off (the shipped default). The Rust
  engine already bounds this to `0..64` and does not have the bug — a
  Python-server-only divergence. `query.py` had zero commits this window;
  re-read lines 855-919 directly, mechanics unchanged. Issue **#1037** open.
- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`): a
  `message_length = -1` wire frame sign-extends to `usize::MAX` under the
  lower-bound check and still compares as a negative `i32` under the
  upper-bound check, so both guards pass; the caller's `vec![0u8; body_len]`
  aborts the whole Rust server via `handle_alloc_error` from one
  unauthenticated 16-byte frame. Not fixed.
- **#996** — `src/secantus/sql/authz.py:42-63` (`_command_privilege`): no
  `"CREATE_PROCEDURE"`/`"DROP_PROCEDURE"`/`"CALL"` branch, all three fall
  through to `return None` (no-op authorization); `plpgsql.py:789`
  (`_run_sql`) also bypasses `_dispatch`/`authz.authorize` directly for a
  procedure body. Not fixed.
- **#909** — `src/secantus/sql/plpgsql.py`: `_open_cursor` (line 711),
  `_run_into` (line 777), `_run_sql` (line 789, shared with #996) all call
  their engine entry points directly, none route through
  `_dispatch`/`authz.authorize`. Not fixed.
- **#947** — `src/secantus/sql/planner.py:11961` builds
  `exp.Command(this="MULTIDROP_TABLE", ...)` for `DROP TABLE a, b, c`;
  `_command_privilege` has no matching branch → unauthorized multi-table
  drop. Not fixed.
- **#948** — `src/secantus/sql/engine.py:2778-2799` (`_execute_statement`)
  binds and runs a prepared statement directly at line 2799, bypassing
  `_dispatch`; no `"EXECUTE"` branch in `_command_privilege` either, so
  `EXECUTE name` is unauthorized regardless of the underlying statement's own
  privilege requirement. Not fixed.
