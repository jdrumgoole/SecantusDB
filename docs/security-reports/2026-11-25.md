## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Compound `2d`/`2dsphere` geo-index key generation on the READ path
  builds an uncapped Cartesian product, independent of and in addition to
  the still-open `GeoSphere::key_values`/`wildcard_key_values` write-path
  instance (#2972)** (medium/high, overall high, confidence high; **issue
  #2982**). `GeoIndex::keys` (`crates/secantus-core/src/geoorder/mod.rs:271-
  309`) multiplies the key parts of every field of a compound geo index into
  a running product with no cap, no `checked_mul` guard and no
  `maxTimeMS`/`killOp` poll, reached from the ordinary (non-`explain`) `find`
  path (`Scan::order`, `crates/secantus-commands/src/explain/geo.rs:398`) and
  from `$near` (`Measure::candidate`, `crates/secantus-core/src/geoorder/
  near.rs:143`) — no hint required for the latter. The write-path sibling for
  a `2d` index, `Geo2d::key_values` (`crates/secantus-storage/src/
  lib.rs:2612-2635`), deliberately keeps a multi-valued trailing field whole
  ("a `2d` index is never multikey"), so the triggering document inserts
  cheaply and only a subsequent read explodes. `createIndexes` accepts a
  32-field compound geo index with no `171 CannotIndexParallelArrays`-style
  refusal (`crates/secantus-commands/src/admin.rs:3500-3539,3696`). The same
  file's `GeoIndex::geo_key_parts` (`geoorder/mod.rs:256-266`) separately
  dedups geo key parts with a linear `Vec::contains` inside a loop over
  document-controlled values — O(N²) for N distinct geo values along an
  array path, reachable from an ordinary `insert`/`createIndexes` and
  repeated at least twice per insert (`geo_cells` in `crates/secantus-
  storage/src/lib.rs:2551-2559` repeats the same pattern); the sibling
  `extract_elements` in the same file dedups with `sort_by`+`dedup_by`
  (O(N log N)). Both are in the default no-auth configuration, unauthenticated.
  **Fix (smallest effective):** port `MAX_COMPOUND_KEYS` (`crates/secantus-
  storage/src/lib.rs:1856`) into `GeoIndex::keys`, matching `Geo2d::key_values`
  by keeping a `2d` index's trailing array fields whole rather than
  cross-producing them; replace `geo_key_parts`'s `Vec::contains` dedup (and
  `geo_cells`'s copy of it) with a `HashSet`-keyed dedup, the same pattern
  `extract_elements` already uses. **Filed as new issue #2982.**

- **A plain `$or` of same-path equalities is folded into an `$in` and then
  deduplicated with an O(n²) scan, reachable from an ordinary `find`/`count`
  with no matching documents required** (high/high, overall high, confidence
  high; **issue #2983**). `explain::lone_in` (`crates/secantus-core/src/
  explain.rs:839-847`) counts the distinct values of an `$or`-derived `$in`
  by scanning a growing `Vec<&Bson>` per value (`distinct.iter().any(|d|
  order::cmp(d, v) == Equal)`), though the result is only ever tested for
  `distinct.len() == 1` (line 848) — all work past the second distinct value
  is dead. `or_as_in` (`explain.rs:862`) has a second, independent O(n²): a
  linear `paths.iter_mut().find(...)` lookup per `$or` branch when branches
  span distinct paths. Neither has a size cap or interrupt check; a 16MB
  filter with ~800,000 same-path branches costs on the order of `3×10¹¹`
  comparisons, and `maxTimeMS`/`killOp` cannot abort it. Reached twice per
  command via `crates/secantus-commands/src/explain/order.rs`'s
  `ordered_rows` (line 1572) and `count_index_use` (line 2105), both on the
  ordinary (non-`explain`) read path. The sibling `$in` dedup in
  `crates/secantus-commands/src/explain/parsed.rs:72-73` already uses
  `sort_by`+`dedup_by` (O(n log n)) — the bounded alternative this path does
  not use. **Independently confirmed distinct from** the Quine–McCluskey
  finding below (different file, different module, different trigger shape,
  no call relationship). **Fix:** make `lone_in`'s distinctness test
  early-exit after the second distinct value, and replace `or_as_in`'s
  linear path-grouping with a map. **Filed as new issue #2983.**

- **The new Quine–McCluskey Boolean-expression simplifier never re-checks
  its own documented 1,000-minterm cap inside its merge loop, letting the
  term set balloon ~15x before collapsing** (medium/high, overall high,
  confidence high; **issue #2984**). `crates/secantus-commands/src/explain/
  simplify.rs`'s module doc (lines 37-39) states that more than
  `internalQueryMaximumNumberOfMintermsInSimplifier` (1,000) terms "at any
  step" must leave the tree unchanged; the cap is enforced only on the
  *inputs* to DNF construction (lines 313, 335) and to `simplified` (line
  286), never inside `quine_mccluskey`'s growth loop (lines 256-283), which
  rescans its whole term set each round with a nested O(n²) loop (lines
  261-276) and grows it via `terms.extend(merged)` (line 281) with no
  re-check. A filter encoding ~1,000 distinct 10-bit sign patterns over 10
  fields (via `$ne` canonicalising onto the same predicate bit as `$eq` with
  inverted polarity, `crates/secantus-core/src/explain.rs:281`) drives the
  classic Quine–McCluskey intermediate-term peak to `C(10,3)×2⁷ = 15,360`
  terms, costing on the order of `10⁸`-`10⁹` operations, reached on the
  ordinary `find`/`count`/multi-update/multi-delete path via
  `count_index_use`/`through_cache`/`ordered_rows`
  (`crates/secantus-commands/src/find.rs:466`), not only under `explain`.
  **Independently confirmed distinct from** the `lone_in`/`or_as_in` finding
  above — a sequential, non-overlapping stage of the same pipeline, amplifying
  on a different payload shape. **Fix:** re-check `MAX_MINTERMS` inside
  `quine_mccluskey` after each merge round's growth, aborting (as `dnf`'s
  `Or`/`And` boundaries already do) rather than only at the function's
  input. **Filed as new issue #2984.**

- **`secantusd-pg`'s TLS client-certificate revocation check rebuilds the
  certificate chain from the client's own, unfiltered certificate bag by
  subject-DN match instead of the webpki-verified path, letting a
  self-crafted decoy certificate skip the CRL check on a revoked
  intermediate CA** (medium/high, overall high, confidence high; **issue
  #2985**). `Revocation::check` (`crates/secantus-pg/src/crl.rs:389` onward)
  selects "the next certificate above" the current one purely by
  `subject == issuer` DN byte-equality over the client's raw, unfiltered
  `intermediates` list (`crl.rs:404-407`, forwarded verbatim from
  `crates/secantus-pg/src/tls.rs:384`), advancing only to the client-ordered
  first match (`crl.rs:416`); the walk's termination test treats *any*
  self-issued certificate as a trust anchor (`crl.rs:401-403`) without
  checking it is one of the operator's configured `authorities`. A client
  holding a certificate issued by an intermediate CA the operator revoked
  (by listing its serial in the root's CRL) can present `[leaf, decoy,
  genuine-intermediate]`, where the decoy's subject DN copies the genuine
  intermediate's (public information, visible in the chain the client
  itself presents): the walk either ends at the decoy's self-issued
  shortcut before the genuine intermediate is ever checked, or is diverted
  to check the wrong (attacker-chosen) serial. The leaf itself is still
  checked correctly, which is why the honest chain ordering (and every
  existing test) passes. Confirmed reachable because the pinned
  `rustls-webpki` `0.103.16` tolerates a Certificate message containing
  certificates outside the path it actually verified (non-fatal continue on
  a non-participating candidate — confirmed from the pinned version's
  upstream source, not assumed). This defeats PostgreSQL's
  `X509_V_FLAG_CRL_CHECK_ALL` semantics — the explicit control `crl.rs`'s own
  module header states it exists to reproduce — for every certificate above
  the leaf, when `--tls-crl-file` is configured against a multi-level client
  CA hierarchy. **Fix:** stop re-deriving the path from untrusted client
  input — either obtain the actual webpki-verified path and run the
  revocation check over it in order, or (if the local walk is kept) make
  every step cryptographic (verify the candidate's signature over `current`)
  and terminate the walk only at a certificate byte-equal to one in the
  operator's configured `authorities`, never merely because it is
  self-issued. **Filed as new issue #2985.**

## 🟡 INFO (Best-practice recommendations)

- **The new `pg15-current-openssl` CI action verifies downloaded OpenSSL/
  PostgreSQL source tarballs against a checksum fetched from the same
  release channel (GitHub Releases / `ftp.postgresql.org`'s own `.sha256`),
  not a GPG signature or a separately-trusted channel.** This defends
  against generic transport corruption but not against a compromise of the
  upstream release infrastructure itself (which would also control the
  checksum file). No reachable boundary violation given the job has no
  secrets and does not publish; a defense-in-depth improvement, not a
  finding.
- **A CRL list `check_one` can never consult — a delta, a reasons-only
  list, or an indirect one — is dropped silently with no log line**
  (`crates/secantus-pg/src/crl.rs:436`). An operator who publishes
  revocations only in a form the server cannot use gets no signal, and the
  failure mode is a certificate being accepted (correct per OpenSSL's own
  behaviour, but silent). A startup log line naming each unusable list would
  make this visible.
- **`crl.rs`'s delta-CRL detection depends on a specific DER encoding
  succeeding** (`x509::extension(...).is_some()` at `crl.rs:259`, which
  requires the extension value to be a well-formed OCTET STRING): a delta
  CRL encoded any other (still-valid) way would not be marked `unusable` and
  would be read as a full list again — the same shape as the bug RP-747
  already fixed for the common encoding. Operator-supplied-file trust
  boundary only.
