## What's new since the last review

Eighteen commits landed since 2026-07-31's `fff45dbf` cutoff

- **`4b8a0aa6` — SQL: schema-qualified tables, views, sequences (#722).**
  Relations in a user schema now store under dotted catalog keys
  (`test_schema.users`) via the new `planner.qualified_table_name()`
  helper, threaded through every DML/DDL path (tables, views, sequences,
  indexes, comments, FKs). Reviewed the trust chain this creates: a
  schema-qualified name becomes both a `Catalog` key and — per
  `_write_target_collection` — the backing Mongo **collection name**. Per
  `CLAUDE.md`'s storage-layer invariant, `(db, coll)` reach WT only as
  data in key columns (`key_format=SS`), never formatted into a WT URI —
  confirmed by direct grep (`grep 'f"table:' src/secantus/storage.py`
  finds only the two *numeric shard-index* interpolations, nothing that
  takes `coll`). A dotted, attacker-influenced collection name is
  therefore inert from a path/URI-injection standpoint; it is opaque
  bytes throughout. Also fixed a real wrong-answer bug (sqlglot parses
  `NOT LIKE` as `Like(negate=True)`, silently ignored by both the pushdown
  translator and the row evaluator) — a correctness fix, not a security
  regression class (the old behavior returned more, not fewer, rows, so
  it wasn't an auth-bypass shape).

### W1 (carried forward, still open — 12th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:4749` and `:4837` (line
numbers shifted again from `:4599`/`:4687` last cycle — the file grew by
233 lines this cycle from the Phase C storage-mode-options diff; same two
pre-existing `prune_oplog` call sites, re-confirmed unchanged by direct
read of both lines this cycle). 20 total `self.oplog.lock()` sites; every
site *added* this cycle (in the new periodic stable-checkpoint thread's
bookkeeping) correctly uses the poison-tolerant
`unwrap_or_else(|e| e.into_inner())` pattern — only the same original two
`prune_oplog` accessors (reading/decrementing `live_count`) remain bare.

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **twelve** consecutive review cycles (07-21
through 08-01).

**Recommendation:** unchanged — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The grep-based CI
gate recommended in the last eleven reports (`! grep -rn
'\.lock()\.unwrap()' crates/secantus-storage crates/secantus-commands`
outside `#[cfg(test)]`) remains unimplemented after twelve nightly
re-discoveries.

### W2 (carried forward, still open — 9th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:5897` (`drop_index`) and `:6014`
(`drop_all_indexes`) — line numbers unchanged from last cycle (`storage.py`
was not touched at all this cycle); re-confirmed present by direct read:
both still open only `with self._lock:`, never `self._coll_lock(db,
coll)`.

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24. The hazard is unchanged: a concurrent `insert`/`update`/`delete`
(which takes `_coll_lock` first) is not excluded by `drop_index`'s
`_lock`-only critical section.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.

### W3 (carried forward, still open — 2nd consecutive cycle) — `_emit_oplog`'s bare-autocommit path can permanently freeze the change-stream visible tail on a write error

**File:** `src/secantus/storage.py:2365-2467` (`_emit_oplog`) — unchanged
this cycle (`storage.py` not touched); re-confirmed present by direct read:
the bare-autocommit deregistration at `:2464`
(`self._deregister_minted([(start_seq, start_seq + n)])`) still has no
surrounding `try/finally`, unlike `_batch_transaction` (`:3597`) and
`commit_user_transaction`'s flush (`:3750`), which both deregister inside a
`finally`.

If the preceding cursor-write loop (`:2432-2444`) throws — a WT write
error under resource pressure, a `WT_ROLLBACK` under contention, or any
future entry shape `bson.encode` can't serialize — the request still fails
cleanly to the client, but the minted range is never removed from
`self._oplog_in_flight`, and `oplog_visible_tail_seq()` freezes at that seq
for the life of the process: every future tailable-getMore wake,
change-stream position, and PITR archive head clamps there. This is a
self-inflicted denial-of-service on the change-stream subsystem, in a path
(DDL writes: `create_collection`, `create_index`, `drop_collection`,
`drop_index`, the periodic heartbeat) that is the *only* one of the three
resolution points not exception-safe.

Already tracked as open issue [#714](../../../../issues/714), filed
2026-07-31, unfixed across a 2nd consecutive cycle.

**Recommendation:** unchanged — wrap the mint-to-deregister region of the
bare autocommit path in `try/finally`:

```python
try:
    for i, (entry, pre) in enumerate(zip(entries, pre_images, strict=True)):
        ...
finally:
    if not deferred:
        self._deregister_minted([(start_seq, start_seq + n)])
```
