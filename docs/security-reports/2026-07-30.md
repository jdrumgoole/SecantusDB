## What's new since the last review

Fifteen commits landed since 2026-07-29's `15fdac21` cutoff
(`git log 15fdac21..HEAD`). Four carry substantive code/config changes; the
rest are release mechanics (version bumps, changelog collation, one
`Release vX.Y.Z` commit) or docs/site content. Each substantive change
reviewed in full:

- **`efbd32d2` — Rust server: oplog visibility point — change streams stop
  losing cross-collection events (#696).** The largest change this cycle
  (279 lines in `crates/secantus-storage/src/lib.rs`). Fixes a genuine
  correctness bug: the sync-mode tailable path treated the highest *minted*
  oplog seq as the readable tail, but a seq is minted inside its writer's
  still-open WT transaction — a writer on collection A could commit a later
  seq while an earlier mint on collection B was still in flight, and a
  change-stream poll in that window could permanently skip the in-flight
  entry once it committed. Reviewed for security-relevant regressions
  specifically:
  - No new `unsafe` block (`git show efbd32d2 -- crates/ | grep unsafe` —
    empty).
  - All new/modified lock acquisitions use the existing poison-tolerant
    `self.oplog.lock().unwrap_or_else(|e| e.into_inner())` pattern, not bare
    `.lock().unwrap()` — this PR did not introduce new instances of the W1
    pattern (see below).
  - The new `Drop` impls (`UserTransactionHandle`, the `SyncMintScope` /
    `Harvest` scope guards) all deregister minted seq ranges on every exit
    path — normal return, error return, and panic-unwind — so a panicking
    statement cannot permanently pin the visible tail below a stranded
    range. This is exactly the kind of "backstop on `Drop`" discipline the
    project's error-handling standard calls for.
  - `debug_assert_eq!` calls added in the deregistration paths only fire in
    debug builds and only compare the project's own internal bookkeeping
    (minted-range bounds), not data derived from wire input — not a
    release-build DoS vector.
  - No wire-input-derived value reaches a path, URI, or format string; no
    new `eval`/subprocess/network call.
  - The bug itself is a **data-consistency** issue (a lost change-stream
    event under a specific concurrent-transaction interleaving), not an
    attacker-reachable memory-safety, auth-bypass, or RCE issue — outside
    this review's CRITICAL/WARNING bar, but worth naming because a
    change-stream consumer used for audit/security logging silently missing
    an event is a defense-in-depth-relevant class of bug. `tasks/backlog.md`
    §5 now also records two narrower residuals from the same class (Python
    server: the same race via user transactions; Rust:
    `find_seq_for_ts`/`startAtOperationTime` can still land inside an
    in-flight window) — both already tracked as open backlog items with a
    concrete fix design, not silently deferred.
- **`ed1c0b8d` — Rust concurrency: honest re-measurement, CI wiring,
  findAndModify steal telemetry (#464).** Adds a warn-every-5s log line to
  `findAndModify`'s existing (mongod-equivalent) unbounded re-pick loop when
  a document is repeatedly stolen by concurrent writers. Reviewed the new
  `eprintln!` call: it logs `db_name`, `coll`, elapsed time, and a steal
  count — no document content, no credentials, nothing wire-input-derived
  beyond namespace names the client already supplied for this exact
  operation. Also adds a CI job step (`.github/workflows/test.yml`) running
  existing stress tests in the one lane that builds `_secantus_server`; no
  new `secrets.*`, no untrusted-input injection into the added `run:` block.
- **`002088db` — tests: pass `filter="data"` when extracting backup
  archives (#697).** Test-only. Extends the same `hasattr(tarfile,
  "data_filter")` capability probe `Storage.extract_backup_archive`
  (production code, `src/secantus/storage.py:523`) already uses to three
  test call sites that previously called `tarfile.extractall()` with no
  `filter` kwarg. Confirmed the production path was already correct before
  this commit; this commit only brings the tests in line with it and
  silences a Python-3.14 deprecation warning. No behavior change to shipped
  code.
- **`3d3dbeb8` — ci: bump the github-actions group across 1 directory with
  13 updates (dependabot, #665).** Diffed every changed `uses:` line
  (`git show 3d3dbeb8 | grep uses:`): every currently-SHA-pinned action
  stayed SHA-pinned (dependabot updated the SHA + version comment together,
  e.g. `actions/checkout@9c091bb2…` → `@3d3c42e5…  # v7.0.1`); the three
  lines already on moving tags in `crash-repro.yml` (I27, unchanged) simply
  moved from one moving tag to another (`@v4`→`@v7`, `@v5`→`@v7`). No
  pinning regression introduced anywhere in this bump.
- **`2f0d0bd9` — Admin-UI screenshots in the docs (#691).** Adds a
  dev-only screenshot generator (`scripts/admin_screenshots.py`, gated
  behind `invoke admin-screenshots`, not shipped — `docs/**` is excluded

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open — 10th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:4115` and `:4194` (line
numbers shifted from `:3921`/`:4000` by the oplog-visibility-point diff,
which added code earlier in the file; same two call sites) — re-confirmed
present by direct grep this cycle (`grep -n "self.oplog.lock()"
crates/secantus-storage/src/lib.rs`, 17 call sites total, up from 13 last
cycle because the new visibility-point code added its own — every one of
those *new* sites correctly uses the poison-tolerant
`unwrap_or_else(|e| e.into_inner())` pattern; only the same original two
`prune_oplog` accessors (`live_count` read and its post-prune decrement)
still use bare `.lock().unwrap()`).

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **ten** consecutive review cycles (07-21 through
07-30). The commit that touched this file most this cycle (`efbd32d2`) adds
a dozen new lock acquisitions and gets every one of them right — it simply
didn't happen to touch these two pre-existing sites.

**Recommendation:** unchanged — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The grep-based CI
gate recommended in the last nine reports (`! grep -rn '\.lock()\.unwrap()'
crates/secantus-storage crates/secantus-commands` outside `#[cfg(test)]`)
remains unimplemented after ten nightly re-discoveries — the fix is now
smaller than the review overhead of re-confirming it every night.

### W2 (carried forward, still open — 7th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:5749` (`drop_index`) and `:5866`
(`drop_all_indexes`) — line numbers unchanged from last cycle (`storage.py`
was not touched this cycle); re-confirmed present by direct read: both
still open only `with self._lock:`, never `self._coll_lock(db, coll)`.

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24. No commit touched `storage.py` this cycle at all. The hazard is
unchanged: a concurrent `insert`/`update`/`delete` (which takes
`_coll_lock` first) is not excluded by `drop_index`'s `_lock`-only critical
section.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.
