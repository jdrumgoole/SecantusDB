## 3. Wire-protocol parsing safety

Core Mongo `wire.py`/`server.py`: zero diff since last review, confirmed
unchanged. All 26 commits' wire-adjacent surface is the SQL/Postgres server
(`pgwire.py`, `pgextended.py`, `pgserver.py`, `pgnotify.py`, `session.py`,
`cursors.py`, `commands.py`), read in full against the diff, not grepped.

**CancelRequest (new this cycle, `b8b1b171`):** sound. Truncated bodies
(<12 bytes) are bounds-checked (`struct.unpack_from` wrapped in
try/except → `PGProtocolError`, `pgwire.py:109-113`). Routing
(`pgserver.py:417-424`) checks the target session's `cancel_key` (a
`secrets.randbits(31)` value, unguessable) before firing `cancel_event`; a
bad pid/secret is silently ignored exactly like real PG — no cross-session
hijack. Dead sessions are removed from `_cancel_targets` under `_cancel_lock`
at teardown, no stale-session dangling reference.

**Statement/parameter cap (new this cycle, `ba395810`):** sound.
`MAX_SQL_LENGTH` raised 1 MB→16 MB is checked *first*, before any
regex/tokenizer work (`planner.py:10915`), so no unbounded
allocation/parse-cost risk; still well under the pre-existing (unchanged)
100 MB single-message ceiling in `read_message` (`pgwire.py:143`).
`ParameterDescription`'s int16 count now wraps (`& 0xFFFF`) instead of
raising `struct.error` at ≥65536 params, matching real PG's `pq_sendint16`
behaviour — no crash reintroduced.

**Stray COPY frame discard (`486db764`) / legacy COPY BINARY keyword
(`7aa3705e`) / dollar-quote + nested-comment tokenizer (`e69ca976`):**
sound. Stray COPY frames outside a COPY operation are discarded
(`pgserver.py:653-661`) without touching the extended-protocol dispatcher —
no buffer confusion. The dollar-quote/nested-comment stripping
(`planner.py`'s `_strip_nested_block_comments`, `decode_nonstandard_strings`)
is a single linear pass with no nested-quantifier regex — no ReDoS.

**🟠 NEW WARNING (W8) — LISTEN idle-poll read can desynchronize the PG wire
byte stream.** `src/secantus/sql/pgserver.py:576-604`
(`_read_next_message`, new in `f2891c28`/`84025cc0`): when a session has an
active `LISTEN`, the socket timeout is dropped to 0.25s and a
`TimeoutError` is treated as "no data yet, poll again." But `recv_exactly`
(`pgwire.py:55-64`) has no resumption state — if the 0.25s timeout fires
*mid-frame* (e.g. after the 1-byte type is read but partway through the
4-byte length, or partway through the payload), those already-received
bytes are silently discarded by the `except TimeoutError` handler in
`_read_next_message`, and the next `read_message()` call starts realigned
on stale header/payload bytes instead of a real message boundary — every
subsequent byte on that connection is now misinterpreted. Verified directly:
`read_message` (`pgwire.py:139-146`) performs three separate blocking
`recv_exactly` calls (type byte, length, payload) with no partial-read
buffer threaded across calls, and `_read_next_message`'s `while True` loop
simply re-enters `pgwire.read_message(conn)` from scratch after a timeout.
This is reachable by ordinary network jitter, not only a malicious client —
any session that pairs `LISTEN` with a slow or fragmented client write can
trip it. Blast radius is bounded to that one connection: the resulting
garbage length/type almost always fails the `4 <= length <= 100_000_000`
sanity check or the outer `except Exception` in `_handle_client`
(`pgserver.py:375`), which closes the connection cleanly with no traceback
leak and no thread pinning. But it silently drops a legitimate connection
rather than surfacing a clean protocol error, and a client that
deliberately paces writes to straddle the 0.25s window could reproduce it
at will as a self-targeted connection-reset nuisance. Filed as a new issue
(see below) — recommend buffering partial-read state across timeout
retries, or only polling for notifications between complete messages via a
non-blocking peek.

**🟡 NEW INFO (I45)** — `pgextended.py`'s `_execute` (`while True` retry,
~line 1412) and `_settle_implicit_txn` (~line 1273) retry indefinitely on
repeated `40001` (serialization failure) for the first pipelined statement,
with no cap/backoff. Not a parsing bug — matches PG's own read-committed
retry semantics in spirit — but under adversarial sustained write-write
contention a client could pin a connection thread in a livelock rather than
receiving a deterministic `40001`. Low severity; worth a bounded-retry
follow-up, not urgent enough for a tracking issue this cycle.

**🔴 NEW CRITICAL (C4) — `CREATE TABLE ... AS SELECT` is a fourth instance
of the C1/C2/W7 RBAC-secondary-namespace family.** CTAS landed this cycle
(`e69ca976`, `_run_create_table_as`, `src/secantus/sql/engine.py:1921-1974`).
Its authorization runs through `authz.required_privilege`'s generic
`exp.Create` branch (`src/secantus/sql/authz.py:79-81`):
```python
if isinstance(stmt, exp.Create):
    kind = (stmt.args.get("kind") or "TABLE").upper()
    return (rbac.A_CREATE_INDEX if kind == "INDEX" else rbac.A_CREATE_COLLECTION, False)
```
This returns `A_CREATE_COLLECTION` regardless of statement shape — it never
inspects `stmt.args.get("expression")` (the source query) to also require
`A_FIND` on whatever tables the `SELECT` reads. `_run_create_table_as` then
calls `_run_query(source, ...)` directly (`engine.py:1940`) with no
additional check. Verified concretely against `rbac.py:161-183`
(`_DBADMIN_ACTIONS`): the `dbAdmin` role grants `A_CREATE_COLLECTION` but
**not** `A_FIND`. A SQL client authenticated only with `dbAdmin` can
therefore run `CREATE TABLE stolen AS SELECT * FROM secrets` and
materialize a full copy of a table it has no read privilege on — the exact
same "write-scoped role reads data it shouldn't" shape as C1/C2, in a new
statement type. Same trigger conditions (`--auth` + per-user/table-scoped
roles). Filed as a new issue rather than folded into #785, since it's a
distinct statement type with its own code path and fix site
(`authz.required_privilege`'s `exp.Create` branch needs to walk
`stmt.args.get("expression")` the same way the `Select`/`SetOperation`
branch at line 91-97 already walks for embedded writes).

**W6 (carried forward, still open, issue #806):** unchanged —
`configureFailPoint` absent from `_COMMAND_ACTIONS`
(`commands.py:6875-6897`), so any authenticated principal with zero granted
roles can arm it when `--auth` is on (unauthenticated callers are still
blocked by the earlier auth-required gate, since it isn't in
`_PRE_AUTH_COMMANDS`).

`--auth` gating (general): unchanged.

### C3 (carried forward, still open) — Admin UI: unescaped collection name in an Alpine.js directive enables stored XSS that pivots from the unauthenticated-by-default wire port to the admin operator's authenticated session

**Files:** `src/secantus/admin/templates/collections.html:89,94,98,121`.

### C4 (new this cycle) — `CREATE TABLE ... AS SELECT` bypasses RBAC on its `SELECT` source, the same shape as C2/W7 in a fourth statement type

**Files:** `src/secantus/sql/authz.py:79-81` (`required_privilege`'s
`exp.Create` branch), `src/secantus/sql/engine.py:1921-1974`

it's discovered.**

**Files:** `src/secantus/sql/pgserver.py:691-716` (`_handle_fastpath`),

### W8 (new this cycle) — LISTEN idle-poll read can desynchronize the PG wire byte stream on ordinary network jitter

**Files:** `src/secantus/sql/pgserver.py:576-604` (`_read_next_message`),
`src/secantus/sql/pgwire.py:55-64` (`recv_exactly`), `:139-146`
(`read_message`).

Landed as part of `f2891c28`/`84025cc0` (async LISTEN/NOTIFY push to idle
connections). When a session has an active `LISTEN`, the per-message socket
timeout drops to 0.25s so queued notifications can be flushed between
polls. `recv_exactly` has no partial-read resumption state; if the 0.25s
timeout fires mid-frame, the bytes already read for that frame are
discarded and the next call to `read_message()` re-synchronizes on the
wrong byte offset — every subsequent byte on that connection is
misinterpreted as a new message. Reachable by ordinary network jitter (not
only a malicious client): any session pairing `LISTEN` with a slow or
fragmented client write can trip it. Blast radius is bounded to the one
connection — the resulting garbage almost always fails length/protocol
validation and the outer exception handler in `_handle_client` closes the
connection cleanly, no traceback leak, no thread pinning, no cross-session
impact — but it silently drops a legitimate connection instead of
surfacing a clean protocol error, and a client can reproduce it at will by
pacing writes to straddle the 0.25s window (a self-targeted
connection-reset nuisance, not a cross-client DoS). **A new tracking issue
has been filed for this (see below).** Recommend buffering partial-read
state across timeout retries in `recv_exactly`/`read_message`, or
restructuring the poll to only check for pending notifications between
complete messages (e.g. `select()`/`socket.MSG_PEEK` on the idle wait
rather than a hard read timeout mid-frame).

### W1 (carried forward, still open — 26th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**Files:** `crates/secantus-storage/src/lib.rs:5244`, `:5343`.
