## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`explain::window_stack` (RP-355) runs an O(W²) window-deduplication
  loop with no cap and no cancellation point, reachable via a plain
  `EXPLAIN` on a SELECT with many distinct window functions.**
  `crates/secantus-pg/src/explain.rs:371-386` scans every previously-seen
  distinct window for each of a SELECT's `W` window-function calls
  (`steps.iter_mut().find(...)` against `partition_by`/`order_by`/`frame`),
  giving O(W²) when most windows are pairwise distinct — trivially arranged
  by varying only a `ROWS BETWEEN <n> PRECEDING AND CURRENT ROW` integer
  bound per window, since `WindowFrame`/`FrameBound`
  (`crates/secantus-pgplan/src/lib.rs:2482-2549`) derive structural
  `PartialEq`/`Eq`. Reachable from `crates/secantus-pg/src/lib.rs:40857`
  (`Statement::Explain`, unconditional, `ANALYZE` not required) through
  `explain::plan_tree`'s unconditional call whenever `sel.windows` is
  non-empty (`explain.rs:106`). The only size bound on this path is the
  unrelated 2 MiB `MAX_TEXT_BYTES` statement cap — tens of thousands of
  ~60-70-byte window definitions fit comfortably under it — and
  `cancel::check()`, the mechanism a client's own Cancel/`statement_timeout`
  routes through, is `pub(crate)` inside `secantus-pgplan`
  (`crates/secantus-pgplan/src/cancel.rs:61`) and is never reachable from
  `secantus-pg::explain`, so nothing interrupts the loop once started.
  Independently confirmed by a fresh verifier reading every cited line from
  scratch, who also confirmed the blast radius is scoped to the issuing
  connection's own dedicated OS thread (`crates/secantus-pg/src/server.rs:
  762`'s one-thread-per-connection model) — a real CPU-exhaustion DoS,
  multipliable across several connections, but not a process-wide stall, a
  crash, or a data/privilege compromise. The verifier also flagged that the
  hunter's own suggested fix (a `HashMap` keyed on
  `(partition_by, order_by, frame)`) does not compile as stated, since
  `OrderKey`/`ColumnExpr` derive only `PartialEq`, not `Eq`/`Hash`,
  likely deliberately (a `ColumnExpr` can carry a float literal). **Fix:**
  group by a canonical lossy string key (e.g. `Debug`-formatted
  partition/order/frame) for O(W log W) dedup, and/or cap window count with
  a fallback to the unoptimized path past a generous bound; separately,
  the sibling pairwise tie-break loop (lines 409-423) is also worst-case
  O(distinct_windows²) and should be covered by the same fix, since a
  crafted input that varies `ORDER BY` columns instead of frame bounds
  would not hit the same early short-circuit.

- **`ruleutils::comma_join_conds` (RP-372) builds a comma join's condition
  with an O(N²) `Vec::remove` loop over client-controlled WHERE conjuncts,
  reachable via a plain `EXPLAIN` on a two-table comma join.**
  `crates/secantus-pgplan/src/ruleutils.rs:4137-4185` extracts cross-table
  equality conjuncts out of the WHERE clause's flattened AND-list by
  removing each one with `quals.remove(i)` inside a loop keyed by their
  positions (`spanning`, line 4172); `Vec::remove` is a documented O(len)
  shift, and with cross-table and single-table conjuncts interleaved
  throughout an N-conjunct WHERE clause (trivial: alternate `a.x=b.x` with
  `b.y=1`), total shifting cost is Theta(N²). Reached unconditionally (no
  `ANALYZE` needed) from `crates/secantus-pgplan/src/lib.rs:10088`'s
  `plan_explain` whenever a plain two-relation comma join has no explicit
  ON-clause. A fresh verifier independently traced and tightened the bound
  claim: the 2 MiB `MAX_TEXT_BYTES` constant does **not** reject an
  oversized statement, it only skips caching its parse tree
  (`crates/secantus-pgplan/src/lib.rs:4345-4347`) — the real wire-level
  ceiling is pgwire's `LARGE_PACKET_SIZE_LIMIT`, ~1 GiB
  (`crates/secantus-pgwire/src/messages/{simplequery.rs:42,mod.rs:51}`),
  so N's practical bound is far larger than the hunter's own citation
  suggested. The nesting-depth guard (`nesting_bound`/`check_depth`,
  `crates/secantus-pgplan/src/lib.rs:4395,4461`) resets at every AND/OR
  token and does not bound a flat conjunct count either. No
  `cancel::check()` anywhere in `ruleutils.rs`. Blast radius confirmed
  scoped to the issuing connection's own OS thread, same as the sibling
  finding above. **Fix:** replace the per-index `Vec::remove` loop with a
  single O(N) partition pass (precompute the spanning-index set, then build
  the kept and extracted vectors in one linear pass instead of repeated
  shifting removals) — a concrete sketch is in the full report's
  remediation.

  explain.rs:1542-1558`'s `implied_nest_loop` omits the
  `root.children[1].children.len() != 1` guard its two siblings
  (`price_merge_join`, `price_hash_join`) both have before popping the
  "Hash" node's only child with `.expect("one child")`. Traced to the only

  **unreachable today**: every path that can build a `tree.name == "Hash
  Join"` plan node on this route constructs its "Hash" child via
  `PlanNode::over("Hash", right)`, which always gives it exactly one child,
  and no transform between construction and the call site changes that
  child count. It is a latent landmine, not a live bug — worth adding the
  matching guard defensively before a future caller or refactor in the
  same `if tree.name == "Hash Join"` block removes the implicit invariant
  it currently relies on.
- `crates/secantus-pgplan/src/colstats.rs`'s `distinct_slots_of`
  (`None =>` match arm) computes `track.len() - 1` unconditionally; this
  underflows if `target == 0` is ever reached with an empty `track`. **Not
  reachable today**: the only wired caller always passes
  `default_statistics_target`, GUC-range-checked to `[1, 10000]`
  (`pg15_settings.tsv`, `guc_values.rs`); the per-column `ALTER COLUMN ...
  SET STATISTICS 0` override (which real PostgreSQL does honor) is stored
  in `attstattarget` but never read back by `record_analyze`/`stats_entry`.
  Worth guarding (`saturating_sub(1)` or an explicit `target == 0` early
  return) **before**, not after, any future change wires that per-column
  override into `ANALYZE` to close the fidelity gap against real
  PostgreSQL — otherwise that fidelity fix would silently reopen this as a
  live panic.
