## 🟢 CLEAN (Passed review)

**This cycle's new application logic, read in full:**

- **Slow-operation logging (`crates/secantus-commands/src/slowop.rs`, new
  file, #f2ad4d09).** mongod logs every operation over `slowms` as a `Slow
  query` line; this is the Rust server's port. Read closely because any
  logging path is a potential sensitive-data leak (the auth review in §5
  grep's for exactly this pattern). It is deliberately narrow: `attributes()`
  never serializes the request or reply document wholesale — it reads only
  the command name, the target namespace, and a short, named allowlist of
  outcome fields (`n`/`nModified`/write-error count/`ok`/`code`/`codeName`),
  explicitly by design ("The command's own documents are left out: an
  `insert` of a thousand documents is not a log line"). Traced the call site
  (`secantus-server/src/lib.rs:954`): it runs for every dispatched command,
  including auth commands (`saslStart`/`saslContinue`/`authenticate`), but
  since the function only ever reads `request.get(name)` (the top-level
  command's own value, used solely to decide the logged namespace) and a
  fixed set of reply keys, a SCRAM payload or password field is never on the
  path to the log line — there's no document traversal that could stumble
  onto one. Clean.
- **Read-only views (`crates/secantus-commands/src/views.rs`, new file,
  #3ed5992a).** Refuses `insert`/`update`/`delete`/`findAndModify`/
  `createIndexes`/`dropIndexes`/`validate`/rename against a view, and blocks
  `$out`/`$merge` from writing into one (checked via `write_target`, which
  resolves `$merge`'s `into` in both its string and document forms). The
  view-definition cycle check (`definition_problem`) bounds its walk at
  `chain.len() <= 64` — a crafted cyclic `viewOn` chain cannot loop forever
  or exhaust memory building the cycle-report path. Matches §6's "unbounded
  recursion" concern and holds. Note for context, not a current finding: the
  module's own doc comment records that until the commit that added this
  file (2026-10-09), an `insert` into a view was silently acknowledged and
  stored under the view's name — a real data-integrity bug, already fixed in
  the code under review, nothing to file.
- **Capped-collection eviction (`crates/secantus-storage/src/lib.rs`,
  `enforce_capped_bounds`, #f8e6f18f).** This one is worth flagging even
  though it's already fixed, because the bug it fixes is a genuine resource-
  exhaustion shape: until this window, newly-inserted documents within one
  insert batch were protected from capped-collection eviction
  (`fresh_id_keys`), which meant **one `insertMany` could push a capped
  collection arbitrarily far past its configured `size`/`max` bound with no
  limit** — a single large batch escaped the cap entirely rather than being
  evicted down to it. The fix removes that protection and makes eviction
  uniform (mongod's own behaviour, confirmed in the code's comment: an
  `insertMany` of five documents into a `max: 3` collection leaves the *last*
  three, exactly as mongod 8.2.11 does). Also fixed in the same diff: a
  `size`/`max` of zero or less — which a pre-2026-10-09 store could hold —
  is now treated as "no bound" rather than as a limit that evicts everything
  but the newest document. Read the current function in full
  (`crates/secantus-storage/src/lib.rs:11246`): the loop still always leaves
  at least one document (`if count <= 1 { break; }`), the scan is bounded by
  the collection's own document count (no unbounded growth), and eviction
  walks `scan_docs`' RecordId (insertion) order so FIFO holds even for
  non-monotonic custom `_id` values. No new finding — this is exactly the
  "find it, measure it, fix it" loop the project's own process is supposed
  to produce, and it produced a correct fix.
- **Unprepared-statement plan-cache templating (`crates/secantus-pg/src/
  plan_cache.rs`, extended this window by `e4962a2a`).** This extends the
  correctness-sensitive plan-reuse mechanism already read in full during the
  2026-10-09 cycle (the CLEAN write-up of `24f68221`/`69dd6f70`/`9fb29975`)
  to cover unprepared statements (a literal SQL string sent with no `$n`
  placeholders at all — the common case for drivers/ORMs that don't use
  server-side prepare). The new piece is `literal_family()`: a conservative
  hand-written scanner that identifies a statement's literal values (plain
  integers and single-quoted strings only) and rewrites them to `$n`
  placeholders, producing a "family" key so that `select v from t where k =
  5` and `... where k = 6` can share a learned plan.
  - It refuses to scan (returns `None`, falling back to "plan from scratch,
    no caching") on anything ambiguous: `$`, `\`, `;`, `--` comments, `/*`
    comments, typed/prefixed string literals (`E'..'`, `B'..'`, `X'..'`,
    `U&'..'`), a string literal split across a newline-joined pair, and more
    than 64 literals (a bulk INSERT) for cost reasons.
  - Crucially, **the same structural-equality safety net already verified
    for the prepared-statement path also gates this one.** Read
    `learn_plan_template` (`crates/secantus-pg/src/lib.rs:36699`): for a
    family, it writes two independent sentinel value-sets into the *exact
    original byte spans* the scanner found, plans each rewritten SQL text
    independently, and only caches the result when `plan_cache::
    is_template(&plan_a, &plan_b, &a, &b)` confirms the two plans are
    structurally identical after substitution. A scanner mistake that
    produced a template not matching the statement's real shape would either
    fail to parse (caught by `plan(&a)?`/`plan(&b)?` returning `None`) or
    produce two structurally different plans (caught by `is_template`) —
    there is no path from "the hand-written scanner guessed wrong" to "a
    wrong cached plan gets reused," because nothing is cached without that
    check passing first. The cache key is also derived from the scanner's
    own templated text plus each value's BSON type tag, so two statements
    only ever share a cache entry when their non-literal skeleton is
    byte-identical.
  - This is the second time this exact mechanism has been extended and the
    second time the review has found the safety net still intact under
    extension — worth noting for a future cycle: if a *third* extension
    lands, check whether `is_template`'s invariants still cover the new
    surface, since that is the single point every variant of this feature
    depends on.
- **WiredTiger `method=fsync` log-sync patch (`cmake/patch_wt_fsync_group.py`,
  #b8712264).** Read in full (134 lines). Idempotent by marker-comment
  detection (same pattern as the existing dsync patch), refuses to touch any
  file but `log.c`, and refuses to write anything if any of its three anchor
  strings doesn't match exactly once in the current vendored source —
  verified by `tests/test_a_missing_anchor_leaves_the_file_untouched` test,
  which confirms a shifted anchor aborts the patch rather than silently
  applying two of three edits to a commit-path function. Its own durability
  argument is also mechanically checked by
  `test_the_sync_is_credited_only_with_what_was_written_before_it`: the LSN
  credited to a sync is read from `log->write_lsn` *before* the `fsync`
  call, and only credited when the syncing thread's own sync covered it, in
  the same log file, with that file still current — exactly the ordering a
  correct "credit what was already flushed" optimization needs, and the test
  checks the ordering appears in that sequence in the generated C, not just
  that the patch applies. See the WARNING section for how its actual
  durability property (not just its code shape) was validated.
- **`mimalloc` as the `secantusd-pg` binary's global allocator (`a0af4c7c`).**
  New dependency (`mimalloc = "0.1"`, `libmimalloc-sys`), gated behind a
  `mimalloc` Cargo feature that is default-on for the *binary* only (`#[cfg
  (feature = "mimalloc")]`), explicitly not applied to the library (an
  embedding test or the Python handle keeps its own allocator). This mirrors
  the existing, previously-reviewed precedent for `secantusd-rs`. `mimalloc`
  is a mainstream, widely-used allocator (Microsoft); no RUSTSEC advisory
  found for it or `libmimalloc-sys`.
- **Everything else in this window's diff:** `secantus-commands/src/
  admin.rs` (827 lines, index-management / hidden-index / `$geoWithin`
  boundary work) introduces no new `.unwrap()`/`.expect()`/`panic!` on the
  added lines (grepped the diff directly). `secantus-core/src/group.rs`'s
  new `pipeline_prefix_fields` (a decode-only-what's-needed optimization for
  aggregation pipelines ending in `$group`/`$count`/`$sortByCount`) is
  conservative by construction — it returns `None` (full decode, the safe
  fallback) for every pipeline shape it doesn't fully understand, including
  every whole-document reference (`$$ROOT`, `$$CURRENT`) and every stage not

  bail-out cases. No third-party dependency changed in any `Cargo.lock`
