## 🔴 CRITICAL (Immediate action required)

All three unchanged from 2026-09-06 — re-verified by reading current source,
not carried on trust. All are reachable from an ordinary (unauthenticated,
for the first two) wire client:

- **#995** — `crates/secantus-wire/src/lib.rs:135-151` (`Header::body_len`).
  Re-read this cycle, byte-identical logic to the last six cycles (a doc
  comment was added, referencing `wire.py::read_message`, but the bug is
  unchanged): `self.message_length as usize` (line 138) casts the `i32`
  directly, so `message_length = -1` sign-extends to `usize::MAX` on 64-bit
  *before* either bound check runs; the second check (`message_length >
  MAX_MESSAGE_SIZE`, line 142) compares the still-signed `i32`, so `-1 >
  48_000_000` is also false. Both guards let a negative length through and
  the function returns `Ok(usize::MAX - 16)`. Feeds straight into an
  oversized allocation on the accept path, aborting the process from one
  unauthenticated 16-byte frame. **Not fixed.**

- **#1160** — `src/secantus/commands.py`. Re-confirmed this cycle at the
  (shifted, +14 lines earlier in the file) current locations: `"bulkWrite":
  _bulk_write` is registered in `_HANDLERS` at line 8622, but `_COMMAND_
  ACTIONS` (8707–8790) and `_NO_PRIVILEGE_COMMANDS` (8797–8820) both have
  zero `"bulkWrite"` entries. Dispatch logic (`9620`-`9629`): `info =
  _COMMAND_ACTIONS.get(name)`; when `info is None` there is no `else` branch
  — execution falls through with no privilege check. `bulkWrite` still
  bypasses authorization entirely under `--auth`. **Not fixed.**

- **#977** — `src/secantus/query.py:1364` (`_MAX_REGEX_PATTERN_LEN = 1000`),
  re-read this cycle at the (shifted) current line. `_compile_regex` (line
  1368-1373) still only checks pattern *length*, then calls `re.compile`
  unguarded (line 1373); a second bare `re.compile` call at line 1424 is
  equally unguarded. No backtracking-depth or match-time budget — the cap
  doesn't help against a pathological `(a+)+$`-shaped pattern, 6 characters,
  far under the 1000-char ceiling. CPython's `_sre` engine never releases the
  GIL mid-match, so this remains a whole-server CPU-pinning DoS from one
  unauthenticated `find`. **Not fixed.**

**Three new findings this cycle — all extend the standing "no BSON/type
nesting-depth cap on the Rust wire/decode path" recursion class
(#1117/#1161/#1192/#1193), verified by reading the current source, not
inferred from the diff summary:**

- **NEW — `crates/secantus-core/src/aggregate.rs:322` (`render_value_
  compact`) gains a new unauthenticated call site: `update`/`delete` `hint`
  error rendering.** This function was already flagged unbounded (#1161
  finding 1, recursing into `Bson::Array`/`Bson::Document` with no depth cap,
  previously reachable only via `$redact`). This cycle's diff wires it into a
  second, more directly reachable path: `crates/secantus-commands/src/
  util.rs:100-103` (`validate_write_hint`, part of the new-this-window
  BadHint-message fix, commit `713a3ea8`) renders any non-string `hint` value
  via `secantus_core::aggregate::render_value_compact(other)` when the hint
  doesn't match an existing index. **Trigger:** `update`/`delete` against any
  collection with `hint: <deeply-nested array or document>` targeting a
  nonexistent index — no auth, no prior state. A Rust stack overflow aborts
  the whole process; not caught by `secantus-server`'s `catch_unwind` (which
  only guards ordinary panics, not stack-overflow aborts).
- **NEW — `crates/secantus-pgplan/src/pgtypes.rs:55` (`oid_of_name`, new
  file/function this cycle, commit `7270b8d8`) recurses once per trailing
  `"[]"` in a type name with no depth guard.** Reachable via `to_regtype(...)`
  (`crates/secantus-pgplan/src/lib.rs:5684`) and `'...'::regtype` casts
  (`lib.rs:2236, 4222`), both ordinary SQL a client sends over the pgserver
  wire — which has **no authentication at all** (`NoopStartupHandler`,
  `crates/secantus-pgserver/src/lib.rs:1126,4899`, tracked separately as
  #1191). **Trigger:** `SELECT to_regtype('int' || repeat('[]', 200000))` (or
  any string built the same way) — recursion depth scales linearly with the
  number of `[]` pairs in a single small SQL statement, no prior state, no
  auth.
- **NEW — `crates/secantus-core/src/explain.rs`'s `canonical_match` /
  `clauses` / `field_clauses` / `canonical_children` / `negate` (new file,
  511 lines, this cycle) mutually recurse on nested `$and`/`$or`/`$nor`/
  `$elemMatch`/`$all` with no depth cap.** Reachable from the `explain`
  command's `filter` (`crates/secantus-commands/src/admin.rs:449,514`), which
  any client can send (`db.collection.find(<filter>).explain()`) with no
  auth by default. **Trigger:** `explain({find: "c", filter: {$and: [{$and:
  [...nested tens of thousands of levels deep...]}]}})`.

  All three: single unauthenticated request, no precondition beyond an open
  connection (pgserver) or an existing collection (Mongo-wire). Rated
  WARNING, matching this repo's established tier for the rest of the
  recursion-DoS class (see the 2026-09-06 report's summary) rather than
  CRITICAL, since exploitation requires constructing a several-KB-to-MB
  request to reach practical stack limits and the failure mode is a single
  connection thread's process-wide abort, not memory disclosure or RCE.
