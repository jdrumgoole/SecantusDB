## 🔴 CRITICAL (Immediate action required)

### #995 (new this cycle) — Rust wire `body_len()` sign-extends a negative `message_length`, causing an unrecoverable allocation abort

**Files:** `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`),
`crates/secantus-server/src/lib.rs:550-559` (caller), `:66-94`
(`AllocBudget`).

`message_length` is a signed `i32` read straight off the wire — the first
field of the 16-byte header every connection sends before any
authentication. `body_len()` checks it in two steps:

```rust
if (self.message_length as usize) < HEADER_SIZE { ... }   // casts BEFORE the sign check
if self.message_length > MAX_MESSAGE_SIZE { ... }          // still a signed i32 compare
Ok(self.message_length as usize - HEADER_SIZE)
```

A negative value (e.g. wire bytes `FF FF FF FF`) sign-extends under `as
usize` on a 64-bit target to `usize::MAX` (confirmed directly with `rustc`:
`-1i32 as usize == 18446744073709551615`). That defeats both checks: the
floor check casts first, so `usize::MAX` is not `< 16`; the ceiling check
compares while still `i32`, so `-1 > 48_000_000` is false. `body_len()`
returns `Ok(~1.8×10^19)`.

The caller (`secantus-server/src/lib.rs:550-559`) does
`shared.alloc_budget.acquire(body_len)` then `vec![0u8; body_len]`.
`AllocBudget::acquire` only blocks when another allocation is already
outstanding (`*used != 0 && *used + n > cap`, `lib.rs:89`) — on an idle
server `used == 0`, so a lone oversized request is deliberately let through
rather than blocked (per its own doc comment, to avoid a deadlock). The
subsequent `vec![0u8; ~1.8×10^19]` fails to allocate, which triggers Rust's
global `handle_alloc_error` — an **unconditional process abort**, not a
catchable panic.

**Impact:** a single unauthenticated 16-byte TCP frame with a negative
`message_length` crashes the entire Rust server process, dropping every
connection for every client. The Python server is unaffected —
`src/secantus/wire.py`'s equivalent check compares `message_length` while
still signed, with no premature cast. This is a Rust-port-only regression;
yesterday's report (2026-08-18) characterized this exact bounds discipline
as "mirrored" between the two engines — it was not, in this one spot. The
existing unit test `body_len_bounds` (`secantus-wire/src/lib.rs:646-669`)
covers too-short and over-`MAX_MESSAGE_SIZE` cases but has no
negative-`message_length` case. The sibling `check_doc_len` in the same
file does the comparison correctly (floor-checks while still `i32`, before
any cast) — this looks like a one-off oversight in `body_len` specifically,
not a systemic pattern; a targeted grep for other `as usize` casts
preceding a bound check found none elsewhere in the file.

Filed as **#995**. Not fixed in this run per the review's scope.

### #996 (new this cycle) — `CALL` / `CREATE PROCEDURE` / `DROP PROCEDURE` bypass SQL RBAC entirely — 4th instance of the recurring authz-dispatch gap

**Files:** `src/secantus/sql/authz.py:42-63` (`_command_privilege`),
`src/secantus/sql/planner.py:11926-11929` (statement construction),
`src/secantus/sql/engine.py:4649-4684` (`_call_procedure`),
`src/secantus/sql/plpgsql.py:783-789`/`845-857` (`_run_sql`,
`invoke_procedure`).

Every daily review since 2026-08-16 has found the same recurring bug class:
a new statement kind or embedded-execution path is added without a
matching entry in `authz.py`'s `_command_privilege` dispatch table (or
without routing through `_dispatch`/`authz.authorize()` at all), so it runs
with zero RBAC check. Commit `99cf2042` ("stored procedures — CREATE
PROCEDURE / CALL / DROP PROCEDURE", 2026-08-19) is a new, more severe
instance — a **double bypass**, independently re-verified by hand against
current `HEAD`:

1. **Command-level check is a no-op.** `planner.py:11926-11929` parses
   `CREATE PROCEDURE`/`DROP PROCEDURE` into
   `exp.Command(this="CREATE_PROCEDURE"|"DROP_PROCEDURE", ...)`; `CALL` is
   parsed as `exp.Command(this="CALL", ...)`. Every statement passes
   through `_dispatch` (`engine.py:361`) → `authz.authorize()`
   (`:406`) → `required_privilege()` → for an `exp.Command`,
   `_command_privilege()` — confirmed by direct read: that function has
   branches only for `DECLARE`, `REFRESH`, `GRANT`/`REVOKE`, and
   `CREATE`/`DROP`/`ALTER` with specific tails
   (`ROLE `/`USER `/`GROUP `/`MATERIALIZED`/`SEQUENCE`/`TYPE`). There is no
   `"CREATE_PROCEDURE"`, `"DROP_PROCEDURE"`, or `"CALL"` branch — all three
   fall through to `return None` (`authz.py:63`), and `authorize()`
   short-circuits on `need is None`.
2. **The procedure body bypasses a second, independent way** — the exact
   mechanism #909 already tracks for plpgsql functions.
   `_call_procedure` (`engine.py:4649`) calls
   `plpgsql.invoke_procedure(func, arg_vals, ctx)`
   (`plpgsql.py:845-857`), which runs the body through `_Runner.run`.
   The runner's embedded-SQL dispatch (`plpgsql.py:783-789`, `_run_sql`)
   calls `_engine._run_statement(stmt, ...)` **directly**, never through
   `_dispatch`/`authz.authorize`. So even a gated `CALL` would still let
   the body's writes through unauthorized.

**Repro** (mirrors #948's `PREPARE`/`EXECUTE` style) — a session
authenticated with only a read-only role, `authz_active=True`:

```sql
CREATE PROCEDURE pwn() LANGUAGE plpgsql AS $$
BEGIN
  DELETE FROM secrets;
END;
$$;
CALL pwn();
DROP PROCEDURE pwn;
```

All three statements succeed under a read-only role — `CREATE PROCEDURE`
gets no check, `CALL pwn()` runs the embedded `DELETE` with no
`authz.authorize` ever seeing it, and `DROP PROCEDURE` erases the evidence,
also unauthorized. `4b3a4319` (pgjdbc `CALL`/OUT-param wire fidelity, same
day) extends this same unguarded surface without adding any check —
confirmed via diff, it only reworks `Describe`/`nargs` handling for
extended-protocol `CALL` portals. No RBAC/privilege test coverage exists
for the new feature (`tests/test_sql_procedure.py`, added in the same
commit, has no role/authz case). `DROP TRIGGER` (`856cc7e2`, same window)
was checked as a candidate 5th instance and ruled **not** a bypass — it's
parsed as a genuine `exp.Drop` node, which `required_privilege` already
handles generically (`kind == "TRIGGER"` → `A_DROP_COLLECTION`), so it is
correctly gated.

Filed as **#996**. Not fixed in this run per the review's scope.
