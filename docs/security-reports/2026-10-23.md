## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Unbounded recursion in the new `$jsonSchema` translator — stack-overflow
  DoS reachable from an ordinary, unauthenticated `find`/`aggregate`/
  `update`/`delete`.** `crates/secantus-core/src/jsonschema.rs` is a new
  1,619-line file (landed in `ed65c777`/`29dd7140`, RM-268/269/270-273).
  Its entry point `parse_top` (line 300) → `parse` (line 308) recurses into
  nested sub-schemas with **no depth counter anywhere in the file**
  (confirmed: `grep -n 'depth\|MAX_' crates/secantus-core/src/jsonschema.rs`
  returns nothing) — `object_keywords` (line 1021) calls `parse(Some(name),
  sd)` once per nested `properties`/`patternProperties`/
  `additionalProperties` schema (verified at lines 1053, 1085, 1091),
  `array_keywords` (line 669) recurses through `items`, and
  `logical_keywords` (line 1201) recurses through `allOf`/`anyOf`/`oneOf`/
  `not`. This is exactly the bug class the project's own SQL-side
  `nesting_bound`/`check_depth` guard
  (`crates/secantus-pgplan/src/lib.rs:3950,3975`) exists to prevent, and
  that guard's comment at line 4025 ("the … decoder … recurse[s] once per
  level, before `check_depth` can look") is the precise failure mode
  reproduced here: the project's existing `MAX_NESTING_DEPTH = 180` guard on
  *stored documents* (`crud.rs`/`update.rs`) does not cover a `$jsonSchema`
  **command argument**.

  Reachability is direct, requires no privilege, and needs no stored
  documents at all:
  - `crates/secantus-core/src/query.rs:366` — `$jsonSchema` inside any
    `find`/`aggregate $match`/`update`/`delete` filter calls
    `jsonschema::parse_top(cond)` during match evaluation.
  - `crates/secantus-commands/src/argtypes.rs:1726` (new this window) —
    filter validation calls `json_schema_keyword_error` →
    `query.rs:1876`'s `parse_top` at **parse time**, before any document is
    even read (confirmed by reading `query.rs:1875-1885`).
  - `crates/secantus-commands/src/validation_errors.rs` walks a
    collection's `$jsonSchema` validator with the same unbounded recursion
    when a refused write "explains itself" (`createCollection`/`collMod`
    with a deeply nested validator, then one failing `insert`).

  Concrete trigger: `db.c.find({$jsonSchema: {properties: {a: {properties:
  {a: {properties: {a: /* … tens of thousands of levels … */}}}}}}})`. BSON's
  16 MB document limit comfortably fits a nesting depth deep enough to blow
  a default thread stack. A Rust stack overflow is a hard process abort
  (SIGSEGV on the guard page), not a catchable panic — it takes down every
  connected client, not just the attacker's.
  **Fix direction:** thread a depth counter through `parse`/
  `object_keywords`/`array_keywords`/`logical_keywords` (and the mirroring
  walk in `validation_errors.rs`) and refuse past a bound, the same way
  `MAX_NESTING_DEPTH` already works for stored documents.

- **Unbounded recursion in `secantus-pgplan::json::parse_value` (and
  `parse_array`/`parse_object`) — stack-overflow DoS via any `jsonb`-typed
  literal, reachable from dozens of existing call sites.** Not part of this
  window's diff (the function predates it — confirmed pre-existing by its
  many long-standing callers), but newly **discovered and unfiled** during
  this cycle while tracing a subagent-reported finding in the window's new
  `crates/secantus-pgplan/src/datum_size.rs` (see WARNING, below). `parse_value`
  (`json.rs:65`), `parse_array` (`json.rs:212`), and `parse_object`
  (`json.rs:234`) have **no depth tracking at all** (`grep -n 'depth\|MAX_'
  crates/secantus-pgplan/src/json.rs` matches nothing in any of the three
  functions). This is a *different* function pair from the one already
  tracked by `#1970` (that issue is specifically about the `json`-typed
  (not `jsonb`) literal path through `value()`/`parse_raw`, used by `->`/
  `#>`; it does not cover `jsonb`'s own parser). `json::parse` is called
  from at least `lib.rs` (six sites, including the core `::jsonb` cast
  path at `lib.rs:12539`,`33225`), `geometry.rs:863`, `hashfn.rs:478`,
  `jsonfn.rs:52,384`, `jsonops.rs:21,285`, `jsonpath.rs:2447`, and this
  window's new `fts.rs` (three sites) and `datum_size.rs:140`. A plain
  `SELECT '[[[[[[ … 100000 levels … ]]]]]]'::jsonb;` already reaches the
  cast path at `lib.rs:12539`/`33225` with no SQL-syntax-level nesting for
  `check_depth` to see (the brackets are inside one string-literal token),
  the same failure mode as `#1970`. No authentication required.
  **Fix direction:** same as `#1970` — add an explicit depth cap inside
  `parse_value`, or rewrite it iteratively. Filing as its own issue since it
  is a distinct function from `#1970`'s `value()`/`parse_raw` and a
  distinct, currently-unfiled gap.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`datum_size.rs`'s `jsonb_value`/`jsonb_container`/`array_size`/
  `record_size` have no depth cap of their own, independent of the parser
  bug above.** New this window (`crates/secantus-pgplan/src/datum_size.rs`,
  landed in `5a5634cd`, backlog batch 25), backing the new `pg_column_size()`
  support. `jsonb_value` (line 95) and `jsonb_container` (line 113) walk an
  *already-parsed* `Json` tree with mutual, uncapped recursion; `array_size`
  and `record_size` (lines ~197-234, per the reviewing subagent) have the
  same shape for `ARRAY[...]`/`ROW(...)`. Today this is **not an
  independently exploitable path**: by the time a tree reaches these
  functions it has already survived `json::parse`'s own unbounded recursion
  (the CRITICAL above), so these functions only add stack pressure on top
  of a tree whose depth was already whatever the parser tolerated — they
  don't let an attacker go *deeper* than the parser already would. It is a
  genuine defense-in-depth gap, though: fixing the parser's depth cap alone
  would leave these walkers still uncapped, so if any future caller ever
  hands them a tree built some other way (e.g. a bind parameter decoded
  outside `pg_query`'s SQL-text path), the same unguarded recursion applies
  again. **Fix direction:** cap depth in `jsonb_value`/`jsonb_container` (and
  `array_size`/`record_size`) in the same change that fixes the parser, so
  the two don't drift back out of sync.

- **`expr_rewrite.rs`'s constant-fold widening now runs the existing,
  already-unbounded `expressions::evaluate` recursion eagerly at
  aggregate-pipeline-*parse* time, over an empty collection, and reaches
  more operator children than before.** Landed across `7451a781` (RM-251)
  and `7d866a46`/`eb462511` this window. `expressions::evaluate` itself has
  no depth guard (pre-existing, confirmed by grep, out of this window's
  diff and not a new bug), but `constant_expr_fault`/`switch_fault`
  (`secantus-core/src/expr_rewrite.rs`) and the new fold checks in
  `aggregate.rs`'s `stage_fold_error` and `find.rs`'s projection-fold check
  mean a deeply-nested `$expr` now gets evaluated for constant-folding
  purposes **without needing any documents in the collection**, and the
  widened fold now descends into `$map`/`$filter`/`$let` children it didn't
  reach before. This doesn't introduce the recursion but materially widens
  how cheaply an attacker can trigger it (no data setup required — a single
  `aggregate` against an empty collection). **Fix direction:** the same
  depth-bound fix tracked for the broader unguarded-recursion class would
  cover this; worth calling out separately because it changes the *cost* of
  triggering a pre-existing bug, which is exactly the kind of regression a
  diff-driven review exists to catch even when the root cause isn't new.

- **Top 3 priorities for the team:**
  1. **Fix the new `$jsonSchema`-translator recursion** (this cycle's most
     severe finding): unauthenticated, reachable from a single `find`
     command, no stored data required.
  2. **Fix `secantus-pgplan::json::parse_value`'s matching recursion** (the

     reachable from a plain `::jsonb` cast that's been live for many

     not-yet-filed sibling of the ~31-instance unguarded-recursion class
     before assuming the known list is complete.

     from the last six cycles' top priority: 31+ known instances (now 33+
     counting this cycle's two) across `secantus-core`, `secantus-commands`,
     `secantus-pg`, `secantus-pgplan`, and the `bson` crate itself (`#1780`);
     the project's own `secantus-pgplan::nesting_bound()` iterative-pre-scan
     pattern is the fix and simply isn't applied uniformly, including, now
     demonstrably, to brand-new files.
