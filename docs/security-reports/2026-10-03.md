## New CRITICAL #1 — large objects have no privilege enforcement at all; any bare session reads/overwrites/deletes any blob by oid

This cycle's PL/pgSQL-API push (`feat(pgserver): money, large objects,
refcursor OPEN, database settings`, commit `39340e61`) added large-object
support across two brand-new files, confirmed newly created in this review
window (`git log --follow` on both bottoms out at `39340e61`, no prior
history): `crates/secantus-pgserver/src/largeobjects.rs` (534 new lines, the
Fastpath `lo_*` RPCs `lo_open`/`loread`/`lowrite`/`lo_truncate`/`lo_unlink`/
etc., reached via a new vendored-`pgwire` message type — see below) and
`crates/secantus-pgserver/src/largeobjects/sql.rs` (144 new lines, the
SQL-callable equivalents `lo_get`/`lo_put`/`lo_from_bytea`/`lo_unlink`/etc.).

**Neither file, nor any call site, performs an ownership or ACL check.**
`lo_open` (`largeobjects.rs:325`-`338`) checks only that the object exists
(`self.lo_size(oid)?.is_none()`) before handing back a readable/writable
descriptor — no comparison against the current role or any
`object_privilege_held` call. `lo_get`/`lo_put`
(`largeobjects/sql.rs:72`-`102`) are worse: they need no descriptor at all —
`SELECT lo_get(12345)` or `SELECT lo_put(12345, 0, '\\x65766c')` reads or
overwrites large object `12345` directly by a guessable, sequentially-assigned
oid (`lo_next_oid`, starting at `16384`), with zero session state and zero
check, from any authenticated connection. `lo_unlink` deletes an object by oid
the same way. Confirmed this is a structural gap, not an oversight in one
function: `crates/secantus-pgserver/src/object_acl.rs`'s `kind` dispatch (the
single ACL-lookup entry point this cycle's own privilege-hardening work wired
up for `schema`/`sequence`/`function`/`table`) has **no `largeobject` case at
all** — large objects sit entirely outside the ACL system this same cycle
extended for three other object kinds.

Real PostgreSQL enforces exactly this (`lo_compat_privileges`, off by default
since 9.0): reading or writing a large object you don't own, with no grant,
answers `42501 permission denied for large object N`. SecantusDB's Rust
PostgreSQL server grants it unconditionally. Reachable by any authenticated
role, no privilege required to acquire — the same severity bar as `#1706`/
`#1678`/`#1160` (new RPC surface, zero privilege-table entry, fails open).
**Filed as new GitHub issue (see below).**

## New CRITICAL #2 — `ALTER DATABASE ... SET` has no superuser-or-owner check; any bare session can plant a GUC default for the whole database

The same commit (`39340e61`, later touched by `555f45a5`) added
`crates/secantus-pgserver/src/db_settings.rs` (200 new lines, confirmed newly
created this window) implementing `ALTER DATABASE d SET name = value`
(PostgreSQL's `pg_db_role_setting`: a GUC default every *new* session of `d`
starts with). `alter_database_set` (`db_settings.rs:62`-`97`) checks only that
the named database exists and is the current session's database
(`:68`-`81`), then checks the setting *name* isn't one of a short
postmaster/SIGHUP/backend-context blocklist (`setting_change_refusal`,
`:83`-`85`) — **no `is_superuser` check, no database-owner check, anywhere in
the function or at its single dispatch site**
(`crates/secantus-pgserver/src/lib.rs:27038`-`27042`, which calls it directly
off the parsed `Statement::AlterDatabaseSet` with nothing in between).
`search_path` is a user-context GUC, so it is not blocked by
`setting_change_refusal` either.

Real PostgreSQL requires database-owner or superuser for `ALTER DATABASE ...
SET`, precisely because an unprivileged role being able to set another
session's default `search_path` is a standing escalation primitive: a bare
authenticated role can plant a same-named object earlier in the search path
than the schema a privileged user actually intends, so that user's later
unqualified reference resolves to the attacker's object instead. SecantusDB's
Rust PostgreSQL server grants the `ALTER DATABASE SET` unconditionally to
anyone. A second sub-agent, reviewing the `secantus-pgplan` side independently
and without seeing this finding, separately flagged `AlterDatabaseSetStmt` as
a brand-new top-level statement kind this cycle and noted it doesn't appear in
`privileges.rs`'s `sql_relations` — correctly reasoning that's not *that*
specific bug class (it isn't a table-row statement), which is what led to
tracing the actual gate (there isn't one) on the `secantus-pgserver` side
instead. **Filed as new GitHub issue (see below).**

## New WARNING — a crafted PG-wire `Bind` (pre-existing) or new `FunctionCall` message panics the connection via an unchecked length field

While reviewing the new Fastpath `FunctionCall` message this cycle added
(`crates/vendor/pgwire/src/messages/fastpath.rs`, new file, wired up end to
end: decoded in `crates/vendor/pgwire/src/messages/mod.rs:355`-`356`,
dispatched in `crates/vendor/pgwire/src/tokio/server.rs:348`, handled by
`largeobjects.rs`'s `fastpath_call`) against section 3's standing instruction
to treat every wire length field as hostile: `FunctionCall::decode_body`
(`fastpath.rs`) reads a per-argument `i32` length straight off the wire and
calls `buf.split_to(len as usize)` with **no check that `len` bytes actually
remain** in the buffer. This is not a new pattern — it is copied verbatim from
the pre-existing (unchanged this cycle) `Bind` message decoder
(`crates/vendor/pgwire/src/messages/extendedquery.rs:292`-`302`,
`data_len`-driven `split_to`), which has carried the identical gap since
before this report series started reviewing it (the codec's own
`codec::ensure_count` helper exists and is used for the *next* field in the
very same function, at line 305, but not for this one or for the
`parameter_format_codes` loop above it). A third instance,
`crates/vendor/pgwire/src/messages/copy.rs:37` (`CopyData`,
`buf.split_to(len - 4)`), underflows the same way on a declared length < 4.

**Confirmed by execution, not inference**, for two of the three: built a
15-byte `Bind` message by hand (empty portal/statement names, 0 format codes,
1 parameter declaring a 1,000,000-byte value with none of it present) and
called `Bind::decode` directly —

```
thread '...' panicked at .../bytes-1.12.1/src/bytes_mut.rs:408:9:
split_to out of bounds: 1000000 <= 0
```

— and a 5-byte `CopyData` message declaring length `2` (below the mandatory
4-byte minimum) —

```
thread '...' panicked at src/messages/copy.rs:37:33:
attempt to subtract with overflow
```

(the subtraction overflow panics in the debug/test build shown; the release
profile, confirmed to have no `overflow-checks` override anywhere in this
repo's `Cargo.toml`s, wraps instead and panics identically one line later in
`split_to`). Both test files were reverted (`git checkout --`) immediately
after, leaving no diff. `FunctionCall` was read-confirmed to share the
identical unchecked-`split_to` shape rather than separately executed, since
the mechanism is the same primitive (`bytes::BytesMut::split_to`) already
proven to panic the same way.

Each PG-wire connection runs in its own `tokio::spawn`'d task
(`crates/vendor/pgwire/src/tokio/server.rs:940`/`1105`,
`crates/secantus-pgserver/src/server.rs:409`), and no `Cargo.toml` in this
repo sets `panic = "abort"`, so the panic unwinds and kills only the one
attacking connection's task — the server process and every other connection
keep running. That is the same bounded blast radius this report series has
consistently graded WARNING for the "Rust unbounded-recursion" class (19
pre-existing issues, e.g. `#1471`'s reachable PostGIS-parser panic) rather
than CRITICAL, and the same bar is applied here. Reaching `Bind`/`FunctionCall`
needs a completed PG-wire startup handshake (not a raw first packet like
`#995`), though `#1191` (already filed: the PG server authenticates a
password-less or unknown role regardless) means that bar is low. **Filed as
new GitHub issue (see below)**, citing all three sites (`Bind`, `FunctionCall`,
`CopyData`) as one finding since they share one root cause and one fix
(apply `codec::ensure_count` — or an equivalent `buf.remaining() >= needed`
check — before every length-driven `split_to`/arithmetic in this file, the
same way it's already applied to one field in the same function).

## New WARNING — streamed-portal reader threads have no cap on concurrently busy count

`crates/secantus-pgserver/src/portal_stream.rs` (new this cycle, part of
"precise row waits, plan reuse, streaming portals", commit `eaa58af1`) spawns
a dedicated OS thread (`std::thread::Builder::new().spawn`, `:85`-`87`) to
drive a suspended SELECT portal's blocking WiredTiger reads off the async
executor, reusing an idle-thread pool capped at `MAX_IDLE_READERS = 16`
(`:64`). The cap bounds the **idle** pool only — nothing bounds the number of
threads concurrently *busy* servicing distinct suspended portals. A single
authenticated connection can `Bind` many distinct named portals for eligible
plain `SELECT`s with `max_rows > 0`, issue one partial `Execute` on each
(leaving every one suspended with its own parked thread + open WiredTiger
session), and grow the process's OS-thread count without an upper bound from
one connection's portal count. Threads are a shared process-wide resource,
so this is a narrower-blast-radius sibling of the already-tracked `#1194`
("no connection cap or idle/read timeout") and `#949` ("PG extended-protocol
portals have no count cap") rather than a wholly new mechanism, but it is a
distinct code path (a thread per *busy* streamed portal, not a memory
materialization) that neither existing issue's text describes. **Filed as new
GitHub issue (see below), cross-referenced to `#949`/`#1194`.**
