## 🔴 CRITICAL (Immediate action required)

All three re-confirmed by fresh direct reads against current HEAD:

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  Re-read in full this cycle (file has zero diff since last report, confirmed
  by `git diff --stat b520e04f..HEAD -- crates/secantus-wire`). `message_length`
  is `pub message_length: i32` and `MAX_MESSAGE_SIZE: i32 = 48_000_000`. For a
  negative `message_length` (e.g. `-1`): `(self.message_length as usize)` on
  line 138 sign-extends to `usize::MAX - n`, which is `>= HEADER_SIZE`, so the
  first guard does **not** fire; `self.message_length > MAX_MESSAGE_SIZE` on
  line 144 compares the still-negative signed `i32` against a positive bound,
  which is never true, so the second guard does **not** fire either. Line 150
  then computes `Ok(self.message_length as usize - HEADER_SIZE)` — the same
  huge value minus 16. The caller (`crates/secantus-server/src/lib.rs:552-561`,
  also zero-diff, re-checked) feeds that straight to `vec![0u8; body_len]`
  after `shared.alloc_budget.acquire(body_len)`; `AllocBudget::acquire` only
  blocks when `*used != 0`, so the first in-flight connection's request on a
  fresh connection skips the wait unconditionally. Rust's default allocator
  aborts the process on an allocation failure at this size — one
  unauthenticated 16-byte frame takes the whole server down. **Not fixed.**
- **#1160** — `src/secantus/commands.py:8834-8917` / the dispatch gate at
  `9747-9756`. Re-grepped `_COMMAND_ACTIONS` (`bulkWrite` search returns only
  the handler-table entry at `8749` and unrelated field-name lines — no
  `_COMMAND_ACTIONS` row) and `_NO_PRIVILEGE_COMMANDS` (re-read in full,
  17 entries, no `bulkWrite`). The gate at `9747-9760` reads
  `info = _COMMAND_ACTIONS.get(name); if info is not None: ...` — when `info`
  is `None` the entire privilege check is skipped, i.e. **skip-on-unknown
  rather than deny-on-unknown**. An authenticated connection with zero role
  grants under `--auth` can still call `bulkWrite`. `commands.py` has zero
  diff this cycle. **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471`. Re-read `_compile_regex`
  (`1411-1416`): the only gate is `len(pattern) > _MAX_REGEX_PATTERN_LEN`
  (1000 chars) before an unbounded `re.compile(pattern, flags)` — no
  backtracking-depth limit, no compile/match timeout. A second, uncapped
  `re.compile(regex_pattern, flags)` fallback still exists inside the
  `TypeError` recovery branch (`~1467`), bypassing even the length cap. A
  short pathological pattern (e.g. `(a+)+b`, 8 characters) matched against an
  adversarial non-matching string pins a worker thread's CPU indefinitely —
  an unauthenticated `find` with a crafted `$regex` is a single-request
  CPU-exhaustion DoS. `query.py` has zero diff this cycle. **Not fixed.**

## 🟠 WARNING (Address within 1 week)

**One new finding this cycle**, filed as **#1564**:

- **NEW — `pgplan::extract_aggregates` (`crates/secantus-pgplan/src/lib.rs:4078-4148`),
  no depth guard, unbounded recursion over a client-supplied SQL expression
  tree.** This is new code added this cycle (commit range `b520e04f..HEAD`;
  absent from the prior report's HEAD) implementing "an aggregate wrapped in
  an expression" — `SELECT count(*) + 1`, `coalesce(sum(n), 0)`. It walks
  `AExpr` (both `lexpr`/`rexpr`), `FuncCall` (every arg), `TypeCast`,
  `CoalesceExpr`, and `BoolExpr` nodes recursively with **no depth parameter
  and no recursion-depth cap** — structurally identical to the already-tracked
  `contains_nested_aggregate`'s `walk()` (which at least threads a `depth`
  counter through, even though nothing caps it either — that's `#1550`'s
  standing gap) but with *no* depth tracking at all. It's called once, from
  `finish_aggregate` (`crates/secantus-pgplan/src/lib.rs:5307`), on any target-list
  expression that isn't a bare group-by column once the query is already
  recognised as an aggregate query — which itself requires passing through
  `has_aggregate` → `contains_nested_aggregate`, so a sufficiently deep
  expression may stack-overflow in either function depending on shape, but
  `extract_aggregates` is reachable on its own for expressions that trip
  `contains_nested_aggregate`'s "found an aggregate" case shallowly (e.g. a
  wide, non-deep `FuncCall`/`CoalesceExpr` argument list) and then recurse
  deep on a *different* subtree during rewriting. A client sending
  `SELECT count(*) + (1 + (1 + (1 + ... )))` with enough nesting overflows the
  Rust stack and aborts the server process. **Same class, same severity
  calibration as the 18 prior sites in this list** (`#1117`, `#1161`, `#1192`,
  `#1193`, `#1355`, `#1356`, `#1357`, `#1394`, `#1395`, `#1396`, `#1430`,
  `#1431`, `#1432`, `#1433`, `#1454`, `#1456`, `#1471`, `#1550`) — WARNING
  rather than CRITICAL by the project's established precedent for this shape,
  though note (as in prior cycles) that `#1191` (no auth at all on the PG
  server) means every one of these, including this new one, is reachable
  **pre-authentication**. Filed as **#1564**.
