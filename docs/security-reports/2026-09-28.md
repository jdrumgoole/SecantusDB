## This cycle's real changes, read in full

**`_require_api_version_1` (`commands.py:9652`) and its Rust mirror
(`secantus-commands/src/lib.rs`'s `validate_api`/`api_v1_command`)** replace a
one-command allowlist (`_API_V1_REJECTED_BY_NAME = {"distinct"}`) with a
48-command measured allowlist plus a `_NON_V1_MONGOD_COMMANDS` set for names
mongod has but this server doesn't implement. Traced the ordering in
`dispatch` before treating this as safe: the new gate sits **above the handler
lookup** (so it fires for `testVersion2`, a command mongod recognises but this
server never implements) and **above both the pre-auth check and the RBAC
check** (`commands.py:9915` `ctx.require_auth and name not in
_PRE_AUTH_COMMANDS`, `:9927` the `_COMMAND_ACTIONS` privilege check). That
means an unauthenticated client with `--auth` on can now get a 323
`APIStrictError` (revealing only "this command is outside API Version 1",
which is documented mongod behaviour) instead of a 13 `Unauthorized` for a
command it wasn't authorized to run either way — the same class of
information the existing, already-reviewed `maxTimeMS`-wins-over-auth check
produces, and the same severity call: it distinguishes "this command name is
recognised by mongod" from "this command name is unrecognised", not
"this account has a role". No new privilege-check bypass — a command that was
previously denied for a *missing RBAC entry* (the standing #1160/#1226 class)
is unaffected by this gate, since `_require_api_version_1` returns `None` for
any name not in its own two small maps and falls straight through to the
existing handler-lookup/auth/RBAC chain. The docstring is explicit that the
auth-ordering question was **not** independently probed against mongod (it
was placed to match the neighbouring `maxTimeMS` check's already-measured
ordering) — noted as a documented, low-severity assumption rather than a
finding, since the worst case is an information disclosure no worse than the
command-name enumeration `CommandNotFound` (59) already provides
pre-auth for any unrecognised command.

**`crates/vendor/pgwire/src/tokio/server.rs`'s `lingering_close`** (a
SecantusDB-local patch to the vendored `pgwire` crate) closes the write half
of a finished connection and then drains reads for up to `LINGER_DRAIN_MILLIS
= 5_000` before dropping the socket, so a client's in-flight write after a
server-sent FATAL is consumed rather than answered with a TCP RST that would
otherwise race and hide the error (the bug this fixes: a `pg_terminate_backend`
or idle-timeout FATAL followed by an immediate `Drop` sometimes reset the
client's receive buffer before it read the error text). Checked for a new
resource-exhaustion angle before clearing it: the drain only runs on a
connection that has *already* been accepted and has *already* finished its
request processing, so it adds no new pre-auth allocation or thread/task
surface — it is a bounded (5s ceiling, ends early on the client's own EOF)
tail added to a socket that was already live, using the same async task the
connection already occupied. Ordinary close (`Terminate` + hang-up) costs
nothing measurable per the code comment's own reasoning, and the value
(nginx uses the identical 5s `lingering_timeout` default for the same reason)
matches established practice. No cap regression: the server's existing
connection-accept limits (unchanged by this diff) still bound how many such
5-second tails can exist concurrently. Clean.

**`sql/planner.py`'s `_like_to_regex`** fix (a `LIKE` pattern ending in a bare
escape character now compiles to `(?!)`, matching nothing, instead of falling
through to treat the dangling escape as a literal) and **`sql/typemap.py`'s**
four new catalog-only `pg_type` rows (`char`/`json`/`pg_lsn`/`txid_snapshot`)

takes attacker-controlled input to an unbounded operation — `_like_to_regex`
still runs through the same `_MAX_REGEX_PATTERN_LEN`-guarded `_compile_regex`
path reviewed under §6 below (the escape handling only affects how one
character is translated before compilation, not the compiled pattern's
length or complexity), and the typemap change only adds four static tuples
to an existing dict/tuple, no user input reaches it.

## 🔴 CRITICAL (Immediate action required)

All three re-confirmed by fresh direct reads against current HEAD (see above):

- **#995** — `crates/secantus-wire/src/lib.rs` (`Header::body_len`).
  `message_length` is `pub message_length: i32`; `body_len()` does
  `if (self.message_length as usize) < HEADER_SIZE { ... }` first — for a
  negative `message_length` (e.g. `-1`) this sign-extends to
  `usize::MAX - n`, which is `>= HEADER_SIZE`, so the floor guard does not
  fire; `if self.message_length > MAX_MESSAGE_SIZE` next compares the
  still-negative signed `i32` against a positive bound, which is never true,
  so the ceiling guard does not fire either. The final line
  `Ok(self.message_length as usize - HEADER_SIZE)` returns the same huge
  value minus 16. The caller (`crates/secantus-server/src/lib.rs`) feeds that
  straight to `shared.alloc_budget.acquire(body_len)` and then to
  `vec![0u8; body_len]`. Rust's default global allocator aborts the process
  on an allocation failure at this size. One unauthenticated 16-byte frame
  (a crafted header with a negative `message_length`) takes the whole
  Mongo-wire Rust server down. **Not fixed.**
- **#1160** — `src/secantus/commands.py:8918-8997` (`_COMMAND_ACTIONS` table),
  `:9927` (the RBAC gate: `info = _COMMAND_ACTIONS.get(name); if info is not
  None: ...` — skip-on-unknown rather than deny-on-unknown). `bulkWrite` is
  not a key anywhere in the table (confirmed by a full read of the dict this
  cycle). An authenticated connection with zero role grants under `--auth`
  can still call `bulkWrite` and have every one of its constituent
  insert/update/delete ops executed with no privilege check at all.
  **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471`. `_compile_regex`'s only gate
  is `len(pattern) > _MAX_REGEX_PATTERN_LEN` (1000 chars) ahead of an
  unbounded `re.compile(pattern, flags)` — no backtracking-depth limit, no
  compile/match timeout — and the `TypeError`-recovery fallback inside
  `_op_regex` (triggered by an unhashable pattern argument) does a second,
  uncapped `re.compile(regex_pattern, flags)` that bypasses even the length
  check. A short pathological pattern (e.g. `(a+)+b`) against an adversarial
  non-matching string pins a worker thread's CPU indefinitely via an
  unauthenticated `find`. **Not fixed.**
