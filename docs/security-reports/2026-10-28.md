## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`WITH RECURSIVE`'s new dependency-graph and well-formedness analysis
  recurses over the *entire* JSON-serialized raw parse tree with no depth
  bound of its own, and is not actually covered by the planner's existing
  2,500-level `check_depth` gate at the granularity that matters — an
  ordinary, unprivileged `WITH RECURSIVE` query can overflow the connection
  thread's stack and crash the process.**
  `crates/secantus-pgplan/src/nodetostring/cte_walk.rs` (new this window,
  commit `c2d3e9ee`, part of the RP-028 batch): `Dep::walk` (lines 95–105)
  and `Chk::walk` (229–247) are each a direct, unguarded recursion —
  `Value::Array(a) => a.iter().for_each(|x| self.walk(x))` and
  `Value::Object(m) => m.values().for_each(|x| self.walk(x))` — over
  `serde_json::Value`, the result of `serde_json::to_value()`-serializing a
  CTE's raw `pg_query` parse tree (`to_json`, line 62). Both are mutually
  recursive with `node`/`fields`/`stmt` (`Dep`, lines 107–165) or
  `node`/`select_with`/`select_fields`/`select_stmt` (`Chk`, lines 256–438):
  every statement, join, sublink and sub-select re-enters `walk`.
  Reachable from any ordinary SQL session with no elevated privilege: the
  only caller is `transform_with_clause` (`nodetostring/parse.rs:869-871`,
  `dependency_order(&ctes)` then `check_well_formed_recursion(&ctes,
  &order)`), invoked whenever a statement's `WITH` clause is `RECURSIVE`.
  **This path is not inside the planner's existing stack-safety net.** The
  only two places this codebase runs client-controlled tree processing on a
  deliberately oversized stack are the raw `pg_query::parse()` call itself
  (`parse_guarded`, `secantus-pgplan/src/lib.rs:4328-4356`, up to 1 GiB) and
  cloning a large already-parsed tree out of the statement memo
  (`parse_one`, `lib.rs:4399`, also on a 1 GiB stack) — neither covers the
  *analysis* phase that runs `transform_with_clause`, which executes on
  the connection's ordinary thread stack. The generic guard that does run
  before analysis, `check_depth` (`lib.rs:4361-4371`), rejects a statement
  only when some node's *logical* parse-tree depth exceeds
  `MAX_EXPR_DEPTH = 2500` (`lib.rs:4269`) — and even that is a permissive
  bound, not a safety margin: it was sized to match PostgreSQL's own
  `max_stack_depth`-driven limit, not to bound a hand-rolled Rust
  recursive-descent walker's stack usage. Worse, `check_depth`'s depth
  counts only `Node`-wrapper nesting (the parse tree's semantic levels); the
  new walker here instead recurses through *every* JSON container level
  serde produces for that same tree — each struct field, `Vec`, and
  `Option` layer the protobuf's `#[derive(Serialize)]` emits becomes its own
  `Value::Object`/`Value::Array` hop that `walk` steps into — so for a given
  SQL nesting depth, this walker's actual Rust call-stack depth is some
  multiple of the "logical" depth `check_depth` measured and allowed through
  at up to 2500. And for a short statement (`sql.len() <= 512`), `check_depth`
  does not run *at all* (`lib.rs:4240-4243`, `parse_tree`'s
  `TOO_SHORT_TO_NEST` skip) — an assumption calibrated for ordinary operator
  chains (`a || b || ...`, "a level of nesting costs at least a character of
  text"), not for this walker's higher per-SQL-level stack cost.
  **Concrete trigger, ordinary `psycopg`, no privilege needed:**
  ```sql
  WITH RECURSIVE r(n) AS (
      SELECT 1
      UNION ALL
      SELECT n+1 FROM r
      WHERE EXISTS (SELECT 1 WHERE EXISTS (SELECT 1 WHERE EXISTS (SELECT 1
          -- ~2,000 more nested EXISTS(SELECT 1 WHERE EXISTS(...)) wrappers
      )))
  )
  SELECT * FROM r;
  ```
  Each `EXISTS (SELECT 1 WHERE ...)` wrapper costs under 30 bytes of text (so
  the whole statement clears the 512-byte skip trivially) and one extra level
  in `check_depth`'s logical-depth count, but several `SubLink` /
  `SelectStmt` / list-wrapper JSON layers in `Chk::walk`'s actual recursion —
  reaching a Rust stack-overflow well before 2,000 SQL-visible nesting levels
  exhausts the 2,500-deep allowance `check_depth` grants. This is the same
  failure shape as the already-tracked `filter_kind`
  (`secantus-pgplan/src/joins.rs:1959-1998`, still open, re-confirmed
  unchanged this window — see Carried, below) and `join_order.rs::walk_tree`
  findings: a client-supplied tree walked by directly-recursive Rust with no
  depth counter of its own, just a brand-new instance in a brand-new file.
  **Fix direction:** route `Dep::walk`/`Chk::walk` through this project's
  planned shared recursion-depth guard (the same remediation already
  recommended for `filter_kind` and `join_order.rs::walk_tree`) before they
  are ever called on a client-supplied CTE tree, and lower `TOO_SHORT_TO_NEST`
  or otherwise stop assuming a uniform "characters per nesting level" cost
  across every tree-walking consumer of a parsed statement.

## 🟢 CLEAN (Passed review)

- **The zstd dependency bump** (commit `f83f723d`): `crates/Cargo.lock`
  confirmed at zstd 0.14.3 / zstd-safe 8.2.0 / zstd-sys 2.1.2, the exact
  versions that clear RUSTSEC-2026-0391/0398/0403/0410; `cargo-audit.yml`
  green on both the landing PR and the PR that followed it. The
  `secantusdb` crate's dev-only `mongodb` driver dependency also dropped the
  `zstd-compression` cargo feature (test-only; not shipped), avoiding a
  transitively-pulled older zstd in the test binary.
- **The non-UTF-8 database/collection-name machinery, read in full**
  (`crates/secantus-commands/src/names.rs`, new, 412 lines; `secantus-wt`'s
  `cstr`/`name_bytes`/`escape_name`, `secantus-wt/src/lib.rs:1126-1181`):
  `fix()` (`names.rs:43-54`) refuses any bare `Bson::String` with an embedded
  NUL before it is ever escaped, so a client's own NUL can never collide
  with the new NUL-plus-two-hex-digits escape scheme; `secantus-wt::cstr`'s
  fallback to `CString::new(s).expect(...)` for a non-escape-shaped NUL is
  reachable only if a NUL somehow still reached that layer, which the
  command-layer `nul_in_namespace` guard (`secantus-commands/src/lib.rs:
  1519-1546`, itself updated this window to call `bsondoc::key_bytes`
  instead of a bare NUL check) and `names.rs::fix` both independently
  refuse first. This is the SAME class of bug the new `$setField` WARINING
  (carried, above) represents, but for collection/database names it is
  closed on every path checked (`from_bytes`'s own doc-comment: "the first
  field and `$db` keep their own refusal in `dispatch_inner`") — the
  contrast underlines that the `$setField` gap is a narrower miss in a
  different code path (in-document field keys), not a sign the general
  escaping mechanism is unsound.
- **The new WT FFI surface for session statistics** (`secantus-wt`'s
  `Session::statistics`/`collect_operation_statistics`/
  `discard_statistics`, the `statistics:session` cursor, RM-023/RM-356): the
  two new raw-pointer derefs this window
  (`unsafe { &*session_ptr }.discard_statistics()`,
  `unsafe { &*active }.collect_operation_statistics()`,
  `secantus-storage/src/lib.rs:10526,10549`) follow the codebase's
  pre-existing `ACTIVE_TXN_SESSION`/`ACTIVE_HANDLE` thread-local
  raw-pointer pattern — the pointer is the current transaction's own
  session object, installed earlier in the same call by the same thread,
  never wire-derived — and every new fallible WT call on this path
  (`open_cursor`, `get_key`, `get_value`) is matched and its error either
  propagated or explicitly logged via `eprintln!`, never silently dropped.
- **`WITH RECURSIVE`'s topological-sort and mutual-recursion rejection
  logic itself** (`cte_walk.rs::dependency_order`'s cycle-detection loop,
  lines 185–200): correctly refuses mutual recursion between WITH items
  with a proper PostgreSQL-matching error rather than looping or
  recursing — the walker's *tree traversal* (CRITICAL, above) is the
  problem, not this function's own control flow.
- **Full-diff secrets scan, workflow-file inventory (14 confirmed, none
  added/removed), build-output/oversized-file check**: all clean, detailed
  above.

  1. **Build the shared recursion-depth guard this project has now needed
     independently in at least four places** (`filter_kind`, `join_order.rs

     every session that adds a new client-tree walker to either Rust server
     reintroduces this bug absent a primitive that makes it the default. This
     cycle's new instance (`cte_walk.rs`) is evidence the existing
     `check_depth` gate is not actually load-bearing for every consumer that
     assumes it is: it bounds *logical* parse-tree depth, not the deeper,
     per-walker stack cost a hand-rolled JSON-tree recursion adds on top.
  2. **Fix the three still-open CRITICALs that have now survived substantial,
     unrelated churn in their own file without being touched**
     (`xids.rs::take()`'s swallowed write error, `btree_model.rs::
     from_docs`'s unbounded allocation, `expressions.rs`'s `$setField` NUL

     original filings, #2136/#2162/#2202) that a session working anywhere
     near these files should pick up opportunistically rather than leave for
     a fourth, fifth, or sixth re-confirmation cycle.
  3. **Watch `crates/secantus-pg/src/lib.rs`'s growth rate** (+2,086/-435
     this window alone, on top of being the single largest file in the
     repository) — it was spot-checked rather than read in full this cycle
     for the carried `Maintenance`-dispatch/`record_analyze` WARNING
     (#2166); a file growing this fast increases the chance a future
     session's spot-check misses a real regression in that area.

If any of the above is superseded by a fix landed after this report was
written, the next review cycle is expected to catch it via re-execution
against the oracle and the current code — not by re-reading this document's
claims.
