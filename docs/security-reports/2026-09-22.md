## 🔴 CRITICAL (Immediate action required)

All three re-confirmed by fresh direct reads against current HEAD (not by
trusting the diff — each file was opened and the exact lines re-verified):

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  Re-read in full. `message_length` is declared `pub message_length: i32`
  (`lib.rs:100`) and `MAX_MESSAGE_SIZE: i32 = 48_000_000` (`lib.rs:57`). For a
  negative `message_length` (e.g. `-1`): `(self.message_length as usize)` on
  line 138 sign-extends to `usize::MAX - n`, which is `>= HEADER_SIZE`, so the
  first guard does **not** fire; `self.message_length > MAX_MESSAGE_SIZE` on
  line 144 compares the still-negative signed `i32`, which is never greater
  than a positive bound, so the second guard does **not** fire either. Line
  150 then computes `Ok(self.message_length as usize - HEADER_SIZE)` — the
  same huge value minus 16. The caller
  (`crates/secantus-server/src/lib.rs:552-560`) feeds that straight to
  `vec![0u8; body_len]` after `shared.alloc_budget.acquire(body_len)`
  (`lib.rs:559`); `AllocBudget::acquire` (`lib.rs:83-93`) only blocks when
  `*used != 0` — the very first in-flight connection's request sees
  `used == 0` and skips the wait unconditionally, so the allocation budget
  never protects the first request on a fresh connection. Rust's default
  allocator aborts the process on an allocation failure at this size — one
  unauthenticated 16-byte frame takes the whole server down. **Not fixed.**
- **#1160** — `src/secantus/commands.py:8834-8917` / the dispatch gate at
  `9747-9756`. Re-grepped `_COMMAND_ACTIONS`: `"bulkWrite"` still has no entry
  in the 84-key table (confirmed by reading the full table). `_resource_for_
  command` (`8950-8968`) and the privilege gate both key off
  `_COMMAND_ACTIONS.get(name)`; the gate at `9754-9756` reads
  `info = _COMMAND_ACTIONS.get(name); if info is not None: ...` — when `info`
  is `None` the entire privilege check is skipped, i.e. **skip-on-unknown
  rather than deny-on-unknown**. `bulkWrite` is also absent from
  `_NO_PRIVILEGE_COMMANDS` (`8924-8947`, re-read in full — 17 entries, no
  `bulkWrite`), so this isn't a deliberate exemption; it's a missing table
  row. An authenticated connection with zero role grants under `--auth` can
  still call `bulkWrite`. Not independently re-checked on the Rust side this
  cycle (zero diff in `crates/secantus-commands/src/lib.rs`, confirmed by the
  overall diff-stat above), but the prior cycle's finding there stands on the
  same unchanged-file basis. **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471`. Re-read `_compile_regex`
  (`1411-1416`): the only gate is `len(pattern) > _MAX_REGEX_PATTERN_LEN`
  (1000 chars) before an unbounded `re.compile(pattern, flags)` — no
  backtracking-depth limit, no compile/match timeout, no `re2`-style engine
  swap. A second, uncapped `re.compile(regex_pattern, flags)` fallback still
  exists at line 1467 inside the `TypeError` recovery branch, bypassing even
  the length cap. A short pathological pattern (e.g. `(a+)+b`, 8 characters,
  well under the 1000-char cap) matched against an adversarial non-matching
  string still pins a worker thread's CPU indefinitely — an unauthenticated
  `find` with a crafted `$regex` is a single-request CPU-exhaustion DoS.
  **Not fixed.**

## 🟡 INFO (Best-practice recommendations)

Fresh CVE sweep this cycle (WebSearch, dependency pins unchanged from last
cycle per the empty `uv.lock`/`Cargo.lock` diff):

- **NEW: `anyio` CVE-2026-64847 / GHSA (process-pool stderr-pipe resource
  exhaustion, CVSS 6.8, Moderate).** Prior to 4.14.2, `anyio`'s process-pool
  workers connect stderr to a pipe the parent never drains; worker code that
  writes enough attacker-influenced data to stderr can fill the pipe and
  block the process-pool call indefinitely, holding memory/process handles.
  Affects `anyio` from at least 4.11.0 through 4.14.1 (multiple trackers
  explicitly list `anyio-4.13.0-py3-none-any.whl` as vulnerable — this repo's
  exact pin), fixed in 4.14.2. **Classified INFO, not WARNING**: `grep -rn
  "to_process\|anyio" src/secantus/` returns nothing — this repo never
  imports `anyio` directly or calls `anyio.to_process`/spawns an `anyio`
  process pool; the dependency is purely transitive (via `starlette`/`httpx`
  in the `admin`/`opsboard` extras), and this specific vulnerability requires
  the app to actually use the process-pool feature with attacker-controlled
  worker stderr output, which SecantusDB's admin UI does not do. Same
  reasoning already applied to CVE-2026-63374 (the IDNA/TLS one, tracked as
  INFO last cycle) — still recommend bumping to `anyio>=4.14.2` at the next
  dependency-hygiene pass to clear both advisories at once. (A third `anyio`
  advisory, CVE-2026-63349, a POSIX privilege-dropping bypass, only affects
  4.14.0–4.14.1 and does **not** apply to this repo's 4.13.0 pin — checked
  and excluded.)
- **NEW: `cryptography` CVE-2026-69247 (PKCS#7 `EnvelopedData` decryption
  Bleichenbacher oracle, CVSS 8.2, High).** `pkcs7_decrypt_der`/
  `pkcs7_decrypt_pem`/`pkcs7_decrypt_smime` report decryption outcomes in a
  distinguishable way (both by error shape and by timing), letting an
  attacker who can submit crafted `EnvelopedData` to a decrypting application
  run a Bleichenbacher attack against the content-encryption key. Affects
  `cryptography` 44.0.0 through 49.x — **notably wider than the two
  already-tracked advisories** (#1023 tracks CVE-2026-69248/69249, both fixed
  at 49.0.0); this one is fixed only in **50.0.0**, so upgrading merely to
  clear the tracked pair would leave this one open. Pin is `48.0.0`,
  unchanged this cycle. **Classified INFO, not WARNING**: `grep -rn "pkcs7\|
  PKCS7" src/secantus/` returns nothing — this codebase never calls any
  `pkcs7_*` decrypt function; `cryptography` is used here for TLS
  cert/key handling (mTLS, SCRAM), not S/MIME-style enveloped-data
  decryption, so the vulnerable code path is unreachable from any input this
  server processes. Worth folding into #1023's remediation target (50.0.0,
  not just 49.0.0) at the next dependency-hygiene pass regardless.
- **`pymongo` CVE-2026-88029** (GridFS NoSQL injection, CVSS 8.3) — re-checked
  affected range this cycle: 1.6.0 through <4.18.1, fixed 4.18.1. Pin
  `4.17.0` unchanged, still open, still not directly exploitable (dependency
  used only for its bundled `bson` codec, never as a GridFS client over

- **`cryptography` CVE-2026-69248 / CVE-2026-69249** (#1023, open) — unchanged

  by 50.0.0 per the new CVE-2026-69247 finding above).
