## 🟠 WARNING (Address within 1 week)

### New this cycle

- **The new SERIALIZABLE (SSI) implementation has no bound on the memory
  it accumulates while a long-lived serializable transaction is open,
  unlike the fixed-size shared-memory table it reproduces —
  an ordinary, unprivileged client can grow server memory without limit
  simply by holding one transaction open.** New this window (`ssi.rs`,
  `serializable.rs`, RP-061). `ssi.rs`'s own module doc comment names this
  directly: "Not modelled: summarizing old transactions into the SLRU
  (PostgreSQL does it only when its fixed table of transactions is full;
  **this one has no fixed size**)." Confirmed by direct read of the
  mechanism: `State::clear_old` (`ssi.rs:1146-1175`) is the only path that
  frees a finished transaction's `Sxact` entry, its predicate locks, its
  conflict records, and the row *versions* it wrote
  (`State::release_one`, `ssi.rs:1179-1228`, which removes a `versions`
  entry only once the owning xid is retired) — and `clear_old` only acts on
  a finished transaction once `self.global_xmin` has advanced past that
  transaction's `finished_before` (`ssi.rs:1151`). `global_xmin` is the
  minimum snapshot `xmin` across every **currently active** serializable
  transaction (`State::new_global_xmin`, `ssi.rs:1005-1022`), so one
  transaction that simply stays open (`BEGIN; SET TRANSACTION ISOLATION
  LEVEL SERIALIZABLE;` and no `COMMIT`/`ROLLBACK`) pins `global_xmin` at
  its own snapshot for as long as it is held, during which every other
  serializable transaction's writes keep accumulating in
  `State::versions` (`ssi.rs:229`, a `HashMap` keyed by relation and ctid,
  populated by `note_version` on every insert/delete,
  `serializable.rs:771-790`) and every finished transaction queues in
  `State::finished_list` (`ssi.rs:227`) without ever being released. None
  of `Sxact`, `Conflict`, `Version`, or the `targets`/`xids`/`versions`
  maps that hold them has a capacity ceiling, a count-based eviction, or an
  error path analogous to PostgreSQL's own "out of shared memory" when its
  fixed `max_pred_locks_per_transaction`-sized table fills — PostgreSQL
  degrades to a hard error for the *new* lock request once its bounded
  table is exhausted; this implementation instead keeps allocating.
  **Concrete trigger, no elevated privilege, ordinary SQL only:**
  ```sql
  -- session 1: holds the gate open
  BEGIN; SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  SELECT 1; -- never COMMIT or ROLLBACK

  -- any number of other, ordinary sessions, repeated indefinitely:
  BEGIN; SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
  INSERT INTO t VALUES (...);  -- or UPDATE/DELETE
  COMMIT;
  ```
  Every one of the second session's inserts (and every other serializable
  writer's, concurrently) adds a `Version` and an `Sxact`/`finished_list`
  entry that session 1's held-open transaction prevents from ever being
  reclaimed, for as long as session 1 stays idle in its transaction. Because
  this project's own threat model (`scripts/security-review-prompt.md` §7)
  treats resource exhaustion reachable by an ordinary wire client as in
  scope, and because the test-tool server is a single multi-connection
  process (so this is exhaustion of every connected client's shared
  process, not just the attacker's own session), this is a real,
  if slower-acting, DoS rather than a cosmetic gap — real PostgreSQL bounds
  the equivalent state and fails the *new* request once full, rather than
  letting any one session grow host memory without limit.
  **Fix direction:** either cap the tracked state (reject new SSI
  registrations or versions past a configurable ceiling, surfacing
  PostgreSQL's own `ERROR: out of shared memory`/`HINT: You might need to
  increase max_pred_locks_per_transaction` rather than growing unboundedly),
  or — since this server has no shared-memory ceiling to reproduce at
  all — apply `idle_in_transaction_session_timeout`-style enforcement (the
  GUC already exists in `pg15_settings.tsv`) specifically to the path that
  pins `global_xmin`, so a forgotten `BEGIN` cannot indefinitely block
  reclamation on everyone else's behalf.

## 🟢 CLEAN (Passed review)

- **`crates/secantus-pg/src/hash_index.rs`** (new, 445 lines): every
  attacker-influenced numeric input that reaches arithmetic here —
  `fillfactor` from an index's `WITH (...)` reloptions — is range-checked
  (10–100) by `secantus_pgplan::check_index_reloption` at `CREATE
  INDEX`/`ALTER INDEX` time (`secantus-pgplan/src/lib.rs:7633-7636`)
  *before* it is ever stored, so the arithmetic in `Meta::init`
  (`8192 * fillfactor / 100`, which would overflow `u32` for an
  unvalidated large `fillfactor`) never sees an out-of-range value through
  the normal `CREATE INDEX` path. Bucket-count growth
  (`Meta::insert`/`total_buckets`/`spare_index`) is driven by the table's
  actual row count, not an attacker-supplied count field; no `unsafe`, no
  unguarded indexing, no panic found.
- **`crates/secantus-pg/src/autovacuum.rs`** (new, 339 lines): the
  `autovacuum_naptime` value the launcher thread parses
  (`parse_seconds` → `Duration::from_secs_f64`) looked, on first read,
  like it could carry an attacker-controlled out-of-range duration into a
  panicking `Duration` conversion — traced the full path and found it
  cannot: every GUC of `vartype = "integer"` (including
  `autovacuum_naptime`, bounds 1–2,147,483 seconds per
  `pg15_settings.tsv`) is range-checked and unit-normalized by
  `guc_values::canonical_int` (`crates/secantus-pg/src/guc_values.rs:364-399`)
  at `SET`/`ALTER DATABASE ... SET` time, before the value is ever stored,
  so by the time the autovacuum launcher reads it back the value is always
  within `Duration`'s range. (Even if it were not: a panic here would
  unwind only the autovacuum launcher's own background thread — this
  project sets no `panic = "abort"` profile — silently disabling
  autovacuum for the rest of the process's life rather than crashing the
  server; worth a defensive bound in `parse_seconds` the next time this
  file is touched, but not rising to a standalone finding given the value
  is unreachable out-of-range today.) No ownership/privilege gap: the
  worker's own `ConditionalLockRelationOid`-equivalent
  (`table_lock_free`) correctly skips a table another session holds,
  matching PostgreSQL's own autovacuum skip-on-lock-conflict behaviour.
- **`crates/secantus-pg/src/ssi.rs` / `serializable.rs`** (new, 1,255 +
  909 lines) **otherwise**: no `unsafe`; every `Sxact`/`Conflict` index
  access goes through `.expect("a live sxact")`/`.expect("a live
  conflict")` guarded by the same `Mutex`-serialized `State` that
  allocates and frees those slots, and no code path was found that looks
  up a freed slot's index (`by_pid`/`xids`/`targets` are kept in lock-step
  with `sxacts`' `Some`/`None` slots on every insert and release) — the
  resource-exhaustion gap above is a capacity/design gap, not a
  memory-safety one. Connection teardown is handled: `Drop for PgHandler`
  (`lib.rs:25690-25724`) unconditionally calls `self.ssi_end(false)` (plus
  `xids::end`, `table_locks::release`, `advisory::release_session`), so a
  client that disconnects mid-transaction (TCP reset, crash) without
  `ROLLBACK` still releases its predicate locks and SSI registration —
  this is exactly the cleanup path that would be missing if the resource
  gap above were instead a *leak* rather than a bounded-by-session design
  limitation; it is not a leak, which is why the finding above is a
  WARNING (slow, sustained-interaction resource growth) rather than a
  CRITICAL (no single request grows it, and every session's own
  contribution is reclaimed once no transaction's snapshot still needs
  it).
- **`crates/secantus-pg/src/btree.rs`** (+203 this window, RP-196/RP-254
  wiring): the new `btree_index_scanned`/`ssi_duplicate` functions and the
  SSI-event plumbing in `btree_insert_versions` read already-validated,
  already-stored model state (no new allocation from an attacker-supplied
  count); `kill_items`'s dead-entry marking operates over ranges already
  bounded by the scan's own key range.
- **`crates/secantus-pgplan/src/joincost.rs`'s new `cheapest_full_join`**
  (RP-028, FULL-join costing): its `.expect("a join has paths")`
  (`joincost.rs:546`) looked like a candidate reachable panic — traced
  `add_full_paths` (`joincost.rs:769-832`) and confirmed its hash-join
  branch (`for o in &outers { consider(hash_join(o, inner), hash); }`)
  runs unconditionally regardless of `mergeable` or sort order, and
  `outers` always contains at least the plain `outer` side
  (`std::iter::once(outer).chain(...)`), so at least one path is always
  added for both values of `b_outer` before `.cheapest()` is called — the
  `.expect()` is backed by a real invariant, not a latent panic.
- **`crates/secantus-pg/src/join_order.rs` / `join_search.rs`**, and
