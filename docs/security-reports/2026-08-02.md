## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open — 13th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:4897` and `:4989` (shifted from
`:4749`/`:4837` last cycle — `prune_oplog`'s body was extracted into a new
free function `prune_oplog_sweep(ctx: &PruneCtx, ...)` so the async-oplog
drainer pool can call it without borrowing `Storage`; `self.oplog` became
`ctx.oplog` at these two call sites, nothing else changed). Direct grep this
cycle: 73 total `.lock()` sites (71 last cycle; the two new sites — a
`PruneCtx::archive_dir` setter/getter — are both poison-tolerant), still
exactly 2 bare `.lock().unwrap()`, still the same two `prune_oplog` accessors
(reading/decrementing `live_count`).

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **thirteen** consecutive review cycles.

**Recommendation:** unchanged — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())` (now written as
`ctx.oplog.lock().unwrap_or_else(...)` post-refactor). The recommended
grep-based CI gate (`! grep -rn '\.lock()\.unwrap()' crates/secantus-storage
crates/secantus-commands` outside `#[cfg(test)]`) remains unimplemented
after thirteen nightly re-discoveries.

### W2 (carried forward, still open — 10th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:6004` (`drop_index`) and `:6121`
(`drop_all_indexes`) — line numbers shifted slightly from last cycle (the
file grew from unrelated changes elsewhere), re-confirmed present by direct
read: both still open only `with self._lock:`, never `self._coll_lock(db,
coll)`, unlike `create_index` (`:5817`, `with self._coll_lock(db, coll),
self._lock:`).

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24. The hazard is unchanged: a concurrent `insert`/`update`/`delete`
(which takes `_coll_lock` first) is not excluded by `drop_index`'s
`_lock`-only critical section.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.

### W3 (carried forward, still open — 3rd consecutive cycle) — `_emit_oplog`'s bare-autocommit path can permanently freeze the change-stream visible tail on a write error

**File:** `src/secantus/storage.py:2382-2484` (`_emit_oplog`) — untouched
this cycle (confirmed by diff and direct read); the bare-autocommit
deregistration at `:2481` (`self._deregister_minted([(start_seq, start_seq +
n)])`) still has no surrounding `try/finally`, unlike `_batch_transaction`
and `commit_user_transaction`'s flush, which both deregister inside a
`finally`.

Already tracked as open issue [#714](../../../../issues/714), filed
2026-07-31, unfixed across a 3rd consecutive cycle.

**Recommendation:** unchanged — wrap the mint-to-deregister region of the
bare autocommit path in `try/finally`.

### W4 (new this cycle) — Rust user-transaction async-oplog buffer (`pending_async`) has no size/count cap

**File:** `crates/secantus-storage/src/lib.rs:137`
(`UserTransactionHandle::pending_async: Vec<(OplogEntry, Option<Vec<u8>>)>`),
introduced by this cycle's async-oplog hardening work (`#744`/`#746`).

Under async-oplog mode (`--oplog-async` / `SECANTUS_OPLOG_ASYNC=1` — an
operator-set, opt-in storage mode per `CLAUDE.md`'s "Phase C" description,
**not** the default), every statement inside an open multi-document
transaction now buffers its full oplog entry — the encoded document blob
plus, when pre-images are enabled, the pre-image bytes — in this
process-heap `Vec` for the entire transaction lifetime (`with_user_
transaction`'s `AsyncHarvest` guard at `:5162-5186` moves each statement's
buffered entries onto the handle; nothing bounds the handle's cumulative
size). Compare the sync path's much lighter `minted_ranges: Vec<(i64,
i64)>`, which only ever holds seq-range tuples.

**Mitigating factor found during review:** `src/secantus/transactions.py`
and `crates/secantus-commands/src/transactions.rs` both enforce a
`mongod`-style `transactionLifetimeLimitSeconds`-equivalent reap (default
60s), so a transaction cannot be held open indefinitely. That bounds the
exposure to "however many/large writes a client can push through one
connection in 60 seconds," not truly unbounded — but within that window a
client opening a transaction and sending a rapid sequence of large inserts
can grow `pending_async` well past what the sync path or a bounded
per-transaction byte cap would allow, with no cap or count/byte accounting
found in this diff or the surrounding code.

**Recommendation:** add a size/count ceiling on `pending_async` (mirroring
the sync path's lightness, or at minimum enforcing the same
`maxTransactionLockRequestTimeoutMillis`/byte-budget style caps applied
elsewhere), and reject or flush early once exceeded rather than growing
unbounded for the life of the transaction.
