nesting-depth limit — unauthenticated single-frame whole-process-abort DoS)
remains the one open CRITICAL, and is untouched by this window's commits:
`bson = "2.15.0"` is still the resolved version in all three relevant
lockfiles (`crates/Cargo.lock`, `crates/secantus-pg/Cargo.lock`,
`crates/secantus-server-py/Cargo.lock`), confirmed directly this cycle, and
every dependent `Cargo.toml` still pins a caret `bson = "2"`.

**Correction to the carried-forward status, checked against the GitHub API
and crates.io rather than re-quoted:** the 2026-10-13 report (and the
original #1780 text) describes the upstream nesting-depth fix as shipping
"in 3.1.0, not yet released as of this filing." That is not accurate as
written, and worth fixing in the tracker now rather than letting a fourth
report repeat it. `gh api repos/mongodb/bson-rust/pulls/694` shows the fix
PR merged to `main` at `2026-09-18T11:58:44Z`. `crates.io`'s own version
history (`crates.io/api/v1/crates/bson`) shows `v3.1.0` was published
`2025-11-20T20:51:22Z` — **about ten months before the fix PR merged** — and
no `bson-rust` tag or crates.io release exists after `v3.1.0` as of this
review. So the fix is not "unreleased 3.1.0"; it is **on `bson-rust`'s `main`
branch and not in ANY released version yet**, including the one already
published as 3.1.0. Upgrading the pinned dependency to `3.1.0` today would
not close #1780 — it would need an unreleased future version, or vendoring
the fix, or the stopgap of a pre-decode depth check already suggested in the
issue. Added a clarifying comment to #1780 recording this so the next cycle
doesn't inherit the wrong target version.

### Status checks on previously-filed items (confirmed this cycle, not re-filed)

**Significant partial progress, read in full because it touches the RBAC
surface directly: `705b077c` ("Rust MongoDB server: privileges enforced as
mongod does") rewrites the Rust server's entire `--auth` privilege check**
(`crates/secantus-commands/src/authz.rs`, new, 462 lines + `authz_pipeline.rs`,
new, 376 lines, replacing the old per-database-only `command_action` /
`resource_for_command` pair in `lib.rs`). Read end to end, with particular
attention to the default-fallthrough behaviour, because that is exactly the
bug shape this project's own `CLAUDE.md` names as recurring (a command
missing from the privilege table silently gets no privilege requirement at
all). The new table is **closed by default**: `authz::check`'s final match
arm is `_ => c.allowed = false` — a command the table does not name is
refused for every authenticated user, the opposite of the old behaviour.
Confirmed by direct code reading that `authorize()` (`lib.rs`) is invoked
unconditionally inside `dispatch_inner`'s `Some(handler) =>` arm for every
command that has a handler, so no handler can reach execution without going
through this gate.

This closes the **Rust-server half** of three previously-filed "bypasses
RBAC entirely" issues, confirmed by reading the new match arms and (for two
of the three) by the new integration test
(`crates/secantus-storage-adapter/tests/auth_enforcement_wt.rs`,
`open_and_closed_by_default`, asserting `Some(13)` for a zero-privilege user)
rather than by code-reading alone:

- **#1226** (`killSessions`/`killAllSessions`/`killAllSessionsByPattern`
  bypass RBAC entirely): `authz.rs` now requires `killAnySession` on the
  cluster for any session the caller does not own, and for both
  `killAllSessions` forms unconditionally. The integration test asserts a
  zero-role user gets `13` on `killAllSessions`.
- **#1661** (`replSetStepDown` bypasses RBAC entirely): `authz.rs` now
  requires `replSetStateChange` on the cluster. The integration test asserts
  `13` for a zero-role user. **Only the RBAC dimension of #1661 is closed** —
  the issue's second, independent finding (`step_down()` takes the step-down
  period with no upper bound, so even an *authorized* caller can force an
  unbounded write outage) is untouched by this commit and the issue should
  stay open for that reason alone.
- **#1160** (`bulkWrite` bypasses RBAC entirely): `authz_pipeline::bulk_write`
  now derives `insert`/`update`/`remove` (+ `bypassDocumentValidation`) needs
  per operation from `nsInfo`, wired through `authz::check`'s
  `"bulkWrite" => c.needs(pipe::bulk_write(doc))` arm. Confirmed by reading
  the wiring and the function's own unit tests; unlike the other two, there
  is no end-to-end `Some(13)`-style integration assertion for `bulkWrite`
  specifically in the new test file, so this is slightly less thoroughly
  pinned than the other two but the code path is unambiguous.

It also fixes two gaps this project's own backlog had recorded (not
GitHub-tracked issues, so nothing to close, but worth recording as closed):
the Rust check previously named only a **database**, never a collection, so
a user granted `insert` on `app.c` could insert into `app.other` — measured
2026-10-14 and now fixed, per `tasks/backlog.md`'s diff; and `createRole`
accepted every mongod role name while `rbac.rs`'s enforcement only knew a
short hardcoded list, so a user granted an unrecognised built-in role (e.g.
`hostManager`) could be created and then do nothing. Also closes the
Rust-server side of the **INFO**-level low-RBAC-granularity gaps this
report's lineage has carried for `replSetGetStatus` and `dataSize`
(2026-10-12/13 reports): both now have real per-action cluster/collection
checks (`c.cluster("replSetGetStatus")`, `dataSize`'s `find`-on-namespace
arm) rather than being either fully open or fully closed regardless of role.

## 🟡 INFO (Best-practice recommendations)

- **The new `checkpoint_seconds` / `SECANTUS_CHECKPOINT_SECONDS` plumbing
  (`b5c8fe26`, `d111914a`) reads an environment variable, not wire or
  command input**, so there is no injection surface — confirmed by reading
  both the Python (`storage.py`'s f-string building a WT config string from
  an `int()`-cast value) and Rust (`spawn_checkpoint_thread`) sides. A
  periodic checkpoint failure is surfaced via `eprintln!` rather than
  silently dropped, consistent with this project's existing pattern for the
  sibling stable-checkpoint thread (not escalated to a panic or process
  exit, which is a reasonable tradeoff for a background maintenance thread
  and not a new divergence from the project's "never ignore an error" rule
  — the error is printed, not swallowed).
- **`crates/secantus-server/src/lib.rs` gained `auth_state.peer_address`**
  (`de66bde8`), the connecting socket's own address, used only by
  `whatsmyuri` (a pre-auth, no-privilege command in both the old and new
  table) to report a client's own address back to itself — matches mongod's
  `whatsmyuri` exactly and is not a new information-disclosure surface.
- **Carried unchanged from prior cycles** (no commit in this window touches
  the relevant surfaces): no cross-connection allocation budget on the
  Python server's in-flight message bodies (Rust has one); the "Protect
  release tags" ruleset gap (doesn't cover `refs/tags/secantusd-pg-v*`); the
  residual `--sync-on-commit` coverage gap for the `method=fsync` log-sync
  patch (still unmeasured).
- **`validate`'s new `check_collection`** (`93ed9da8`) materializes a
  `HashSet` of every index entry and every document id for the whole
  collection in memory while holding the collection lock, to compare
  expected vs. actual index contents. This is the same cost shape real
  `mongod`'s `validate` has (it is a known-expensive, admin-gated diagnostic
  command in both products, and is now gated by the new `validate` cluster/
  collection privilege under `--auth`), so this is not treated as a new
  resource-exhaustion finding distinct from the project's existing,
  by-design "no `--auth` means no gate at all" posture — noted for
  awareness, not filed.
- **Not a security finding, flagged for awareness only:**
  `scripts/build_pg_release.sh` (new, `bfc1e085`) runs an instrumented build
  of the release binary and drives it with a workload script over a plain
  TCP loopback connection as part of the release pipeline; it installs
  `psycopg[binary]` from PyPI via `uv run --with` at build time. This is
  maintainer/CI-run release tooling, not reachable by a wire client and not
  part of the published wheel, so it sits outside this project's stated
  threat model the same way the rest of `bench/` does. No issue warranted.

- **`705b077c` / `04c256b1`'s new `authz.rs`, `authz_pipeline.rs`,
  `privileges.rs`, `umc.rs`, `builtin_roles.rs`** (the full RBAC rewrite):

  `eprintln` call anywhere in the diff). Clean on both counts.
- **`fa3069b2` (geo queries): the new `geoshape.rs` (1,166 lines) and
  `near.rs` (250 lines) parse fully attacker-controlled GeoJSON/legacy
  geo documents from both insert payloads and query filters.** Checked
  every new array-indexing site in polygon/ring walking (`ring[i]`,
  `ring[(i+1) % n]`) for a divide-by-zero or out-of-bounds panic when `n =
  ring.len()` is zero: every such loop is bounded by `0..n`, which is empty
  when `n == 0`, so the modulo is never evaluated in that case — no reachable
  panic on an empty/degenerate ring. The one `.expect("a GeoJSON object")`
  in the new `$geoNear` stage parser is guarded by the exact `matches!`
  pattern one line above that proves the value is already a `Bson::Document`
  — not reachable with a different value. No new `unsafe` block.
