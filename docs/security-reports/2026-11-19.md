  `groups × last-row-size` estimate understate true held memory relative to

  regardless of the sampling gap, and the small-group table side still
  forces a spill once `groups × last-row-size` crosses the budget (just at a
  larger document count than a true sum would require). Recorded as INFO/
  hardening, not filed as an issue.

  `attach_verbose_chain::walk()` (~line 3966-4050) recurses once per join
  node (`walk(outer, ...)` then `walk(&mut hash.children[0], ...)`) when
  building `EXPLAIN VERBOSE`'s join-chain text, with no depth counter and no
  `cancel::check`/`stacker::maybe_grow` (this crate's own established
  pattern for exactly this hazard, used by `with_call_depth`,
  `lib.rs:16399-16429`, which this new function ignores). No practical
  join-count cap blocks reachability: `join_order.rs`'s DP search only
  covers 4-8 leaves; above that, `lib.rs:11113-11141` still builds (and then
  prints) a left-deep plan over all N tables. An authenticated client with
  ordinary `CREATE TABLE` privilege (ownership of its own tables, no
  elevation) self-joining a few hundred tables and running `EXPLAIN VERBOSE`
  crashes the whole `secantusd-pg` process for every connection — a genuine
  native-stack overflow is a guard-page `SIGSEGV`, uncatchable by
  `catch_unwind` regardless of panic strategy (confirmed: no `panic =
  "abort"` anywhere in the workspace, and no `catch_unwind` wraps EXPLAIN
  execution — moot either way). **Commented on #2070** with this sink and
  fix direction rather than filing a duplicate.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`COMMENT ON` has no ownership/privilege check for any object kind**
  (medium/medium, overall medium). `crates/secantus-pg/src/lib.rs:20430-
  20742`'s `comment_on` (dispatched from `Statement::Comment`,
  `lib.rs:49243`) performs zero owner/superuser check across ~20 object-kind
  branches (table, column, function, operator, type, database, role,
  operator class/family, and — new this window via RP-969 — access method,
  conversion, language, collation, text search parser/template, builtin
  schema/extension). No generic gate covers it either:
  `secantus-pgplan::privileges::sql_relations` has no `CommentStmt` arm, so
  the universal per-statement privilege check (#2740's gate) is a silent
  no-op for every `COMMENT ON`. A working check exists next door and isn't
  called: `opclasses.rs:1330`'s `owned_or_superuser` gates the ALTER-style
  owner-rename handler for operator classes/families (`opclasses.rs:1755`)
  but not the adjacent `comment_on_opclass` (`opclasses.rs:1773-1804`) that
  writes the identical object's comment. Any authenticated, unprivileged
  role can run `COMMENT ON TABLE other_role_owned_table IS 'x'`, `COMMENT ON
  DATABASE postgres IS 'x'`, `COMMENT ON ROLE admin IS 'x'`, or (new this
  window) `COMMENT ON TYPE int4 IS 'x'`, silently overwriting metadata
  visible to everyone via `\d+`/`pg_description`/`pg_shdescription`.
  Blast radius is confined to comment/description text — metadata
  defacement, not data loss or privilege escalation — hence medium rather
  than the critical/high rating given to the data-destructive gaps in
  #2740/#2696/#2812 (same general shape, different statement family, not
  duplicates).
  **Independently confirmed** by a fresh verifier, who additionally
  confirmed the `opclasses.rs` ALTER-vs-COMMENT inconsistency and the
  absence of a `CommentStmt` arm in `sql_relations`.
  **Fix:** add an ownership/superuser check at the top of `comment_on`'s
  dispatch, reusing `opclasses.rs::owned_or_superuser` where an owner field
  exists, and gating the RP-969 builtin-object branches to superuser only.
  **Filed as new issue #2885** (no duplicate found).

  this cycle that `1.53.3`/`1.51.6` are the patched versions available

  dev-only, test-only `tempfile` dependency** — not reachable from
  production, unchanged.
- **`sbe_hashagg.rs`'s `MemoryCheck::should_spill` samples only the most
  recently processed row's size, multiplied by group count, rather than
  summing true per-group memory** — a client varying the `$group` key on
  almost every document can make this estimate understate true held memory
  relative to a true sum. Recorded as hardening, not a finding: this is a
  deliberate, test-verified (`sbe_hashagg.rs`'s own
  `checkpoints_are_mongods` test) port of mongod 8.2's own documented
  `HashAggBaseStage` sampling heuristic (CLAUDE.md: "model the real
  product's mechanism" — reproducing a known upstream imprecision is not a
  bug introduced here), and every individual accumulator is independently
  capped by an exact running total against its own ~100 MiB budget
  (`group.rs:521-601`), so no single group can exceed that bound regardless
  of the sampling gap. Worth a conscious call on whether to add a periodic
  true-sum safety net distinct from faithfully reproducing mongod's
  sampling, but not actionable as a security fix today.
- **`multiwrite_chunk.rs`'s new paged multi-write tests don't exercise
  interruption mid-page** (unlike the existing single-chunk
  `multi_update_interrupted_in_an_expression_writes_nothing` test) — a
  coverage gap, not a traced bug; each page still writes via its own
  transaction retried through the pre-existing `retry_write_conflicts`
  machinery, so no durability issue was found by tracing the code, but the
  interrupted-mid-page case itself remains untested by this batch.
