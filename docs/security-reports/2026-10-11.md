## 🟢 CLEAN (Passed review)

**This cycle's new application logic, read in full:**

- **Server-side TLS for the Rust PostgreSQL server
  (`crates/secantus-pg/src/tls.rs`, new file, #4db8cd6f).** Read in full (129
  lines). `TlsConfig::acceptor()` builds a `rustls` `ServerConfig` via
  `builder_with_provider(ring::default_provider())`, `with_safe_default_protocol_versions()`,
  and explicit `with_no_client_auth()` — a documented, deliberate scope
  decision, not an oversight (the module's own header comment lists what is
  "Not here": client certificates and SCRAM channel binding). Certificate and
  key are read once via `rustls_pki_types`' own PEM reader (not the
  unmaintained `rustls-pemfile`), and every failure path names the offending
  file without ever printing key material. `read_certs` explicitly rejects an
  empty certificate file rather than silently building an acceptor with no
  certificate. The negotiation itself (the in-band `SSLRequest` / `N`-or-`S`
  response) is the vendored `secantus-pgwire` fork's existing, previously-
  reviewed code path (`crates/secantus-pgwire/src/tokio/server.rs`), unchanged
  in this diff apart from a Cargo feature flip (`server-api` →
  `server-api-ring`) that supplies it a crypto provider; the new file here
  only builds the `ServerConfig` the existing acceptor path consumes.
  - **Dependency hygiene:** the new dependency set (`rustls 0.23.45`,
    `ring 0.17.14`, `rustls-webpki 0.103.15`, `rustls-pki-types 1.15.1`,
    `tokio-rustls 0.26.6`, plus the `x509-certificate`/`der`/`spki` family
    pulled in transitively) was checked against the public advisory record
    rather than assumed current. `rustls 0.23.45` is specifically the
    version that **fixes** RUSTSEC-2026-0285 (a TLS 1.3 handshake
    encryption-boundary issue affecting `>=0.23.13,<0.23.45`) — the pinned
    version is the fixed one, not merely "not yet patched." `ring 0.17.14`
    is likewise already past RUSTSEC-2025-0009 (an overflow-checks-only
    debug-build panic in AES, inapplicable to release profiles anyway, and
    fixed at this exact version). No advisory found for `rcgen` (dev-
    dependency only — used by the TLS tests to mint an ephemeral,
    never-persisted certificate per test run, confirmed by its own
    Cargo.toml comment: "A self-signed certificate for the TLS tests, made
    per test and never stored") or for any `icu_*` crate (see below).
  - **The binary-smoke test exercises the published artifact, not just the
    source tree** (`tests/test_rust_pg_binary_smoke.py::test_binary_serves_tls`,
    new this window): it spawns the actual `secantusd-pg` binary with
    `--tls-cert-file`/`--tls-key-file`, connects with `psycopg` at
    `sslmode="verify-full"` (the strictest client mode — full chain and
    hostname verification against a `trustme`-issued CA, never the
    self-signed cert alone), and asserts `ssl_in_use` plus a working
    round-trip over the encrypted connection. This is the right level of
    proof for a TLS feature whose crypto provider is chosen at build time
    (the test module's own docstring states why: "a source-tree test says
    nothing about whether the archive about to be published has it").
- **ICU4X collation rewrite (`crates/secantus-core/src/collation.rs`, 1,370
  lines of diff, #ccd37037).** Replaces the prior hand-rolled
  `unicode-normalization` + `unicode-properties` combination with the
  Unicode Consortium's own `icu_collator`/`icu_normalizer`/`icu_locale_core`
  stack, closing most of a 462-of-764 divergence from real `mongod` down to
  8 (`tasks/backlog.md` §7.070). Read the production (non-test) code in full
  looking specifically for the two things a string-processing rewrite this
  size could introduce: no `.unwrap()`/`.expect()`/`panic!`/`unreachable!`/
  `unsafe` appears outside the `#[cfg(test)]` module, and the plumbing that
  threads the active collation through comparisons (`order::cmp`,
  `order::bson_lt`, `group::gkey`, `diff::eq`, `update.rs`'s `$max`/`$min`
  tie-break, `expressions.rs`'s `$setEquals`/`$minN`/`$maxN` family,
  `fill.rs`/`densify.rs`/`windowfields.rs`'s partition and sort-key builders)
  is purely a comparison substitution — no new attacker-controlled-length
  allocation, no new indexing without a prior length check. One slice access
  in `densify.rs` (`keyed[keyed.len() - 1]`) is guarded three lines earlier by
  `if keyed.is_empty() { continue; }`; every other new indexing operation
  found in the diff (`expressions.rs`'s `kept[0]`/`arrays[0]`/`arrays[1]` in
  the `$minN`/`$maxN`/`$setDifference`/`$setIsSubset`/`$setEquals` family,
  `admin.rs`'s `a[0]`/`a[1]` in `$mod`'s explain-shape renderer and
  `same_key[0]`/`same_key[1]` in the ambiguous-index-key error) is likewise
  guarded by an exact-arity pattern match or an explicit `.len()` check
  immediately before it. No advisory found for any of the thirteen new
  `icu_*` crates pulled in (`icu_collator 2.3.1`, `icu_normalizer 2.3.0`,
  `icu_properties 2.3.0`, `icu_locale_core 2.3.0`, `icu_provider 2.3.1` and
  their `*_data`/support crates) — all are the upstream Unicode Consortium's
  own `unicode-org/icu4x` project, a 2.x release line.
  - **Worth noting as a finding the project already found and fixed itself,
    not a current defect:** `expressions.rs`'s `op_set_equals` carries a
    comment recording that `{$setEquals: []}` from any client used to
    **panic the server thread** ("range start index 1 out of range for
    slice of length 0") before an explicit `if arrays.len() < 2` arity check
    was added ahead of the `&arrays[1..]` slice — exactly the "reachable
    panic from wire input = DoS" shape this review's own threat model
    watches for, caught and fixed within this window rather than found by
    this review. Confirmed the guard is in the code under review and that
    the three sibling functions (`$setIntersection`, `$setDifference`,
    `$setIsSubset`) either enforce an exact arity of 2 through
    `set_arrays(..., Some(2), ...)` before any indexing, or (for
    `$setIntersection`, arity `None`) only ever index after an `Option`-safe
    `.first()` check. No `security` issue needed — nothing in the shipped
    code under review can still reach the panic.
- **`bulkWrite` input validation (`crates/secantus-commands/src/bulkwrite.rs`,
  499 lines of diff, extends the command tracked by the open #1160 RBAC
  finding).** The two `.expect("checked above")` calls added this window
  (`raw.as_document().expect(...)`) are genuinely safe: both sites iterate
  `ops`, and every element of `ops` is pattern-matched against
  `Bson::Document` with an early `wrong_type` return on failure in a loop
  that runs unconditionally before either `.expect()` site is reached — by
  construction, every remaining `raw` is already a document. This is the
  validate-everything-before-writing-anything discipline the function's own
  comment describes ("CHECKED BEFORE ANYTHING IS WRITTEN... A malformed
  third op used to leave the first two applied" — also a prior self-found-
  and-fixed bug, this one a correctness rather than security defect). Not
  reachable as a panic. **#1160 (bulkWrite bypasses RBAC entirely) remains
  open and untouched by this diff** — this window's `bulkWrite` changes are
  validation-ordering fixes, not an authorization change, so the existing
  finding is unaffected either way.
- **Time-series collection validation (`crates/secantus-commands/src/
  timeseries.rs`, new file, 694 lines, #ac890f16) and `$out`'s validator
  handling.** Read the production code in full: no `.unwrap()`/`.expect()`/
  `panic!`/`unreachable!`/unchecked indexing appears outside the test module.
  Closes most of a 139-of-187 divergence from `mongod` down to 24
  (`tasks/backlog.md` §7.071); the remaining gaps are fidelity-shaped
  (no `system.buckets.<name>` view, field/row ordering, a few command
  refusals) rather than security-shaped, and are tracked there rather than
  filed here.
- **`search_path`/`public`-visibility and `GROUPING SETS` fixes
  (`crates/secantus-pgplan/src/schemas.rs` +111, `src/lib.rs` +36,
  #d113c889).** Closes a real isolation-adjacent gap: before this window, a
  session with `search_path` set to exclude `public` (e.g. `pg_catalog` only)
  could still read, insert, update, and delete a `public`-schema table by
  its bare name — a result real PostgreSQL does not produce (`SELECT`/
  `INSERT`/`UPDATE`/`DELETE`/`COMMENT ON` over such a table now correctly
  answer `42P01`, matching PostgreSQL; `DROP` without `IF EXISTS` likewise).
  This is a single-tenant test database (no untrusted multi-tenant isolation
  claim exists for this project), so the practical severity of the prior gap
  was low, but the fix itself is read and is sound: `hidden_in_public` is
  gated by a thread-local (`AS_SENT`) set only while rewriting a statement a
  client actually sent, never while the server reads back its own stored
  view/function definitions, so the fix cannot make a legitimate internal
  read fail. The `GROUPING SETS` half (`finish_aggregate`'s new
  `GROUPING()`-inside-an-expression guard, the `GROUP BY (a, b)` row-form
  flattening) is pure planner logic with no new unsafe surface. Three
  residual gaps are left open in `tasks/backlog.md` (a relation of `public`
  still found via a string/`regclass` cast or `DROP ... IF EXISTS`; a syntax
  error from the extended-protocol `Parse` message carries no error
  position) — fidelity gaps, not newly-introduced security defects, and
  already tracked there.
