## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Nested `$lookup` explain amplification: product-of-document-counts
  recursive `explain_reply` calls** (likelihood high, impact high, overall
  **high**, confidence high; **issue filed**). Explaining (with
  `executionStats`/`allPlansExecution` verbosity) a `$lookup` stage with
  both `localField` and `foreignField` plus a `pipeline` array makes
  `crates/secantus-commands/src/explain/sub_stages.rs`'s `lookup()` treat
  the stage as `correlated` unconditionally (line 221-228), fetch every
  matching outer document with an uncapped `cursor: {batchSize: i32::MAX}`
  (`documents_through`, `mod.rs:2175`), and then — for **each** outer
  document — build and run a full nested `{explain:{aggregate,pipeline},
  verbosity:"executionStats"}` command via `explain_reply()`
  (`sub_stages.rs:283`), which re-enters the *entire* explain dispatcher. If
  the inner pipeline itself contains another such `$lookup`, the recursion
  repeats one level deeper, so total nested `explain_reply` invocations are
  the **product**, not sum, of per-level matched-document counts (e.g. two
  levels of 1,000 matching documents each ⇒ up to ~1,000,000 nested calls
  from one client-sent command). No depth cap, no per-request budget, and no
  interrupt/deadline check exists inside the per-document loop — the only
  `DEPTH` thread-local in `explain/plan.rs` tracks planning-time
  attribution and only fires its one interrupt check at `DEPTH==1`, which
  nested recursive levels bypass. An ordinary authenticated client with only
  the read privilege it already needs for the involved collections — no
  special grant — can tie up the single shared server process for every
  other connection with one request. **Fix (smallest effective):** add a
  periodic interrupt/deadline check inside the per-outer-document loop in
  `lookup()` so the client's own `maxTimeMS`/`killOp` bounds the recursive
  cost, and add a fixed ceiling on total nested `explain_reply` invocations
  within one top-level explain as a backstop independent of
  `maxTimeMS`.

- **`$lookup` `localField`/`foreignField` dotted-path length drives
  unbounded recursion during SBE explain plan construction — stack overflow
  DoS** (likelihood high, impact high, overall **high**, confidence high;
  **issue filed**). `crates/secantus-commands/src/explain/mod.rs`'s
  `lookup_joins()` (line 3001) reads a client's `$lookup` `localField`/
  `foreignField` strings with checks only on type, foreign-collection
  existence/size (`<=10,000` docs/`100MiB`), and absence of a leading index
  on `foreignField` — no length or dot-count cap. This SBE/hash-join path is
  the **default** (only excluded when a client explicitly sets
  `queryFramework:"classic"`). `crates/secantus-commands/src/explain/sbe/
  lookup.rs`'s `path_below()` (line 65) recurses once per dot-separated
  `localField` component with no depth guard, and the foreign-field loop
  (line 246) builds a `Stage` chain whose depth equals `foreignField`'s
  dot-count, subsequently walked recursively (again with no depth guard) by
  `corr::exec()`, `Stage::run()`, the pretty-printer, and the new
  `stats_doc`/`examined_by` functions. The only `MAX_DEPTH` constants in the
  codebase (`keystring/decode.rs`, `resume_keystring.rs`, both `200`) are
  unrelated to this path. A `localField` with low hundreds of thousands of
  dot-separated components — trivially representable within the 16MB BSON
  document limit — drives tens of MB of recursive stack usage **during plan
  construction, before any row is scanned**, exceeding both an 8MB
  main-thread and a typical ~2MB worker-thread default stack and aborting
  the whole process (Rust cannot intercept a real stack overflow via
  `panic::catch_unwind`). Reachable via one ordinary `aggregate`+
  `explain:true` command from any client with normal CRUD/read access; no
  special privilege needed. **Fix (smallest effective):** in
  `lookup_joins()`, reject (fall back to the classic/non-SBE path, or
  return an explicit error) whenever `localField`/`foreignField` has more
  dot-separated components than a small fixed bound matching mongod's own
  `FieldPath`/`BSONDepth` component limit (e.g. 200) — one guard at this
  entry point protects every downstream recursive consumer.

### New this cycle

- **`EXPLAIN` of a many-equality-predicate joined query drives an `O(Q²)`
  naive union-find in `ruleutils::class_ranks`** (likelihood medium, impact
  medium, overall **medium**, confidence high; **issue filed**).
  `crates/secantus-pgplan/src/ruleutils.rs`'s `class_ranks` (new this
  window, lines 6170-6185), wired in from `crates/secantus-pgplan/src/
  lib.rs:12996-13001` inside the `joined` branch of `plan_explain`, builds
  equivalence classes of joined columns from a query's equality predicates
  using a union-find with no path compression and no union-by-size: each of
  `Q` equality quals does two linear scans (`classes.iter().position()` then
  `.contains()`) over the total members accumulated so far, giving `O(Q²)`
  total work for a self-join chain of `Q` equality predicates
  (`t1.a=t2.a AND t2.a=t3.a AND ...`) written directly in client SQL text.
  Reachable **only** via an explicit `EXPLAIN` of a multi-table query (the
  only callers of `plan_explain` are the top-level `ExplainStmt` dispatch
  and two internally-bounded recursive self-calls, confirmed by a
  whole-tree grep) — not from ordinary query execution. The only size cap on
  the SQL text itself is pgwire's `LARGE_PACKET_SIZE_LIMIT` (~1 GiB, the same
  limit real PostgreSQL enforces, not a SecantusDB-specific tightening), so
  a client can transmit the few-hundred-KB of SQL text (on the order of
  10,000 predicates) needed to reach multi-second planning latency. Medium,
  not high, because the cost scales with the size of the attacker's own
  transmitted query text rather than a disproportionate amplifier, and is
  confined to that one connection's `EXPLAIN` planning time, not demonstrated
  to affect other connections. **Fix (smallest effective):** add a side
  `HashMap<Member, usize>` (member → class index) alongside the existing
  `Vec<Vec<Member>>`, updated on every push/merge, turning `find()` into
  `O(1)` amortized while preserving the existing output-ordering contract.

## 🟡 INFO (Best-practice recommendations)

- **An unguarded `DropStmt` catch-all in `catalog_reads.rs` forces a full
  views+functions catalog re-decode on every `DROP` of any object kind when
  the statement runs inside a transaction block** (confirmed, overall
  **low**; not filed as an issue — see rationale below).
  `crates/secantus-pg/src/catalog_reads.rs`'s DDL-effects dispatch has a
  correctly kind-guarded `DropStmt` arm for `ObjectTable` (line 5045), but a
  second, unguarded `N::DropStmt(_)` arm in the trailing catch-all (line
  5108) matches *every* `DropStmt` regardless of object kind — so `DROP
  INDEX`/`DROP TYPE`/`DROP SCHEMA`/`DROP SEQUENCE` etc. all trigger
  `snapshot_objects()` → `placed_objects()`, a full decode of the entire
  views and functions catalog collections, run once before and once after
  the statement. The existing per-catalog-version memoization that would
  normally make the "after" call free is bypassed when the statement runs
  inside an explicit `BEGIN`/`COMMIT` block (`in_user_txn()` true skips the
  incremental catch-up path entirely) or once the bounded catalog
  change-log/id-cap (`PATCH_MAX = 64`) is exhausted under concurrent churn.
  The independent verifier corrected the hunter's "every time" framing to
  this precise conditional trigger and confirmed the **low** severity call:
  real, reproducible added latency on subsequent DDL (proportional to total
  accumulated views/functions and prior effort invested), shared across
  connections on that database, but no crash, no data exposure, no boundary
  violation, and no permanent effect (nothing survives that requires
  cleanup). **Not filed as an issue per this report's convention** (only
  CRITICAL/WARNING findings are filed); worth a backlog entry
  (`tasks/backlog-rust-postgres.md`) at the team's discretion. **Fix:**
  restrict the catch-all `DropStmt` arm to the `ObjectType` values that can
  actually remove a view, function, or schema, mirroring the existing
  `ObjectTable` guard on the preceding arm.
