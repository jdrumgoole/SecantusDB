reload). This is the window's one genuinely new attack surface and got the
most attention this cycle: all of `crates/secantus-pg/src/{x509,
scram_binding, crl, ident, hba, tls}.rs` were read in full, along with the

**Net result: zero new findings.** No issue filed, none closed.

  consistent with the code, and backlog-tracked rather than
  review-discovered:** `docs/servers.md`'s TLS section (re-read against
  `crates/secantus-pg/src/tls.rs` and `x509.rs`) states up front that a key
  with a passphrase is not supported, that a certificate signed with Ed25519
  offers channel binding but any login that takes it up fails with
  PostgreSQL's own "could not find digest for NID UNDEF" (matches
  `scram_binding.rs`'s `no_digest` path, read and tested), and that
  `--refuse-unknown-users` is the only way to close the "a user the server
  has never heard of is trusted" gap (the one case `a4634416`'s commit
  message flags as differing from PostgreSQL in 4 of 154 measured
  scenarios, closed for operators who opt in via `bdfc0eae`). None of this
  is a regression from a prior, stronger state — each is the first version
  of a feature landing with its own scope honestly stated at the moment it
  landed, which is this project's own pattern for a deliberate limitation.
  Not worth a `security` issue on its own.
- **Not a security finding, flagged for awareness only:** `9f4168d0`'s
  change-stream probe recorded (in `tasks/backlog.md` §7.074) that a
  transaction's change-stream events carry a fixed `uid` (the SHA-256 of
  the empty string) rather than a hash of the authenticated user, unlike
  `mongod`. This is a wire-fidelity gap (a resume-token field that doesn't
  vary the way `mongod`'s does), not an information-disclosure risk — if
  anything a fixed, content-free value leaks strictly less than a
  per-user hash would. No issue warranted.

## 🟢 CLEAN (Passed review)

**This cycle's new application logic, read in full, with the auth-relevant
pieces read line by line rather than diff-skimmed:**

- **`x509.rs` (new, 625 lines): a hand-rolled DER/ASN.1 reader for
  certificate fields** (serial, issuer/subject Name, SubjectPublicKeyInfo,
  the signature's AlgorithmIdentifier) used for SCRAM channel binding and
  for `cert`/`clientname`/`pg_stat_ssl` certificate-holder identity. Read
  for the two things a bespoke binary parser needs to get right: every
  length field is checked against the remaining slice before use
  (`header.checked_add(len)?` then `input.len() < end` — no unchecked
  arithmetic, no indexing past a verified bound), and the test suite proves
  it with a cut-every-prefix loop (`for cut in 0..der.len()`) against both
  synthetic TLVs and a real `rcgen`-issued certificate. The module's own
  doc comment states its security precondition accurately: this is a
  reader over already-`rustls`-verified bytes, not a validator, and
  nothing here is asked to validate a chain — confirmed by tracing
  `record_tls_session`'s call to `client.client_certificates()`, which only
  returns a certificate rustls has already checked against the configured
  CA.
- **`scram_binding.rs` (new, 289 lines): SCRAM-SHA-256-PLUS channel
  binding**, transcribed from PostgreSQL's `auth-scram.c` behaviour rather
  than written from the RFC alone. Read in full: the GS2 header `n`/`y`/`p`
  cases, the authorization-identity rejection (a client sending `a=...`),
  the "client thinks binding wasn't offered but it was" refusal, and the
  Ed25519/RSASSA-PSS `no_digest` → `could not find digest for NID UNDEF`
  path all match PostgreSQL's own error text and are each pinned by a
  dedicated test, including a cut-every-prefix-of-the-header loop. The
  binding comparison itself is a value equality on the decoded base64, not
  a raw byte compare exposed to timing — channel binding is a protocol
  correctness property here (detecting a relay), not a secret comparison,
  so this is the right shape.
- **`crl.rs` (new, 448 lines): certificate revocation list checking**,
  matching OpenSSL's (and so PostgreSQL's) exact order of failure
  (dates before signature before revocation) and its one-list-per-issuer
  rule. Read in full: `verify_client_cert` in `tls.rs` wires this in as a
  **second** gate after rustls's own chain verification, and any error
  from either gate fails the TLS handshake outright (`Err(TlsError::...)`)
  — there is no path where a revoked or unreadable certificate's handshake
  completes. Critical X.509 extensions this reader does not understand
  (scoped/delta/indirect lists) are refused when the file is read rather
  than silently ignored, matching OpenSSL's own critical-extension rule.
  The chain walk is bounded (`MAX_CHAIN = 16`) against a certificate loop.
- **`ident.rs` (new, 296 lines) and `hba.rs` (new, 801 lines): `pg_ident.conf`
  / `pg_hba.conf` readers.** Both operate only on local, operator-supplied
  config files (never on wire input) and are read for the one thing that
  would matter if they did reach the wire: `hba.rs`'s address matching
  correctly treats an IPv4-mapped IPv6 client address as IPv4 (tested:
  `::ffff:10.0.0.1` matches an IPv4-only line, an IPv6-only line does not
  match an IPv4 client), and `Hba::decide` takes the **first** matching
  line and stops, matching PostgreSQL's documented behaviour exactly
  (tested against a 15-line fixture covering every field kind). A
  `pg_ident.conf` regular expression is compiled from the operator's own
  file, not from a client-supplied string, so this is not a regex-DoS
  surface despite compiling user-authored-looking patterns.
- **The login decision's wiring (`lib.rs`, `server.rs`):** traced
  `check_hba` → `Hba::decide` → `certificate_terms` → `complete_login`'s
  certificate-holder check end to end. Two things worth confirming
  explicitly because a layering slip here would be a real auth bypass: (1)
  `complete_login`'s cert-holder comparison runs for `ClientCert::Cert`
  *and* `ClientCert::VerifyFull`, and the user-name-map lookup
  (`map.allows(holder, &user)`) replaces, rather than loosens, the
  bare-equality check — there is no code path where a login with a map
  configured falls back to accepting any certificate; (2) `pg_reload_conf()`
  is gated to the role recorded as superuser **at login time**
  (`self.is_superuser(&self.session_user_name())` captured once, in a
  closure, at `finish_startup`), so a role change mid-session can't retroactively
  grant reload — the gate's error message (`"permission denied for function
  pg_reload_conf"`) is produced on the refusal path in
  `secantus-pgplan/src/scalar.rs` and was confirmed present, not just
  implied by a comment.
- **`crates/secantus-pgwire`'s two-line TLS-session accessor addition**
  (`tls_session()` on `ClientInfo`, `a4634416`): a pure read of already-
  negotiated protocol version and cipher suite for `pg_stat_ssl` reporting;
  no new parsing of attacker-controlled bytes.
- **Rust MongoDB server commits (`58e3ab61`, `721f7326`, `9f4168d0`,
  `2310c167`) — scanned for the one pattern this project's own `CLAUDE.md`
  names as the recurring Rust-server risk (a reachable `panic!`/`.unwrap()`/
  `.expect()`/unchecked array index added to a production path).** Diffed
  every changed production file (all 22 non-test `crates/*/src/*.rs` files
  these four commits touch) for newly-added `.unwrap()` / `.expect()` /
  `panic!` / `unreachable!` / `unsafe` / bare `[0]`/`[1]` indexing outside
  `#[cfg(test)]`. The only production-code hit was a pre-existing,
  already-established pattern (`def.field_of(name).expect("column")`
  against a hard-coded, same-file catalog schema in `secantus-pg/src/lib.rs`
  — not attacker-reachable, and the exact pattern already used hundreds of
  times elsewhere in the same file for the same purpose). The only other
  new `unsafe` block in this window (`main.rs`'s SIGHUP handler,
  `0fecb975`) is a single `libc::signal` call whose handler only stores to
  an `AtomicBool` — async-signal-safe by construction, and the same shape
  as the pre-existing `ctrlc` handler it documents replacing.
- **`.github/workflows/test.yml`'s one addition** (`825888ef`, +40 lines):
  installs PostgreSQL 15 from the official `apt.postgresql.org` repository
  (fixed URL, fixed signing key fetched with `curl --fail`, no
  `github.event.*` interpolated into any `run:` block) so
  `tests/test_rust_pg_login_differential.py` — the standing comparison
  against real PostgreSQL for everything reviewed above — runs in CI
  instead of silently skipping for want of `SECANTUS_PG15_BIN`. This closes
  exactly the gap the 2026-10-11 report's own threat model would have
  flagged (a login-rules change whose only proof was local, not CI-gated).
  No new `uses:`, no workflow permissions change, no secrets touched.
- **Everything else in this window's diff:** the WiredTiger submodule pin
  is byte-identical across the range (`git log -p` over `vendor/wiredtiger`
  is empty for the range); no new GitHub workflow file (still 18); no
  `pyproject.toml` / `uv.lock` change (so no dependency-version movement to
  re-check, and no Python `version` bump, consistent with the project's
  release-only versioning rule); no file matching
  `*.env`/`*.key`/`*.pem`/`*secret*`/`*credential*` was added
  (`git log --diff-filter=A` over the full range is empty for those
  patterns); the thirteen lockstep MongoDB-side `Cargo.toml` bumps and the
  three PG-crate bumps are version-string-only. §5–§10 and §13 of the
  standing checklist (core Python auth/dispatch, resource limits, network
  defaults, admin UI, wheel/PyPI packaging) are unchanged — none of
  `src/secantus/auth.py`, `src/secantus/server.py`, `src/secantus/wire.py`,
  `src/secantus/commands.py` (other than the TTL fix noted below), the
  admin FastAPI app, `pyproject.toml`, or the publish workflows appear in
  this window's diff.
- **`2310c167`'s Python-side fix (`src/secantus/storage.py`'s
  `prune_ttl`)** is a correctness/data-loss fix (a partial TTL index had
  been expiring documents outside its own filter, and a compound-index TTL
  wasn't refused at `collMod` time) rather than a security change; read it
  to confirm the new filter-construction path (`matches(doc, ttl_filter)`
  built from the index's own field/partial-filter) introduces no new
  attacker-reachable code shape — it reuses the existing `query.matches`
  evaluator unchanged, just with a differently-built filter document.
