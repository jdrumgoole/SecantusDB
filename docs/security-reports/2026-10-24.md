## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`crates/secantus-core/src/expr_parse.rs` — new mongod-expression-grammar
  parser recurses with no depth bound, reachable from an ordinary,
  unauthenticated `find` projection before any document is read.** This is
  a brand-new file (landed in `94ee5012`, RM-281/282/284/285) implementing
  `operand`/`object`/`operator`/`argument` as mutual recursion:
  `operand` (line 142) → `object` (line 152) → `operator` (line 162) →
  `argument` (line 186) → back into `operand` for the argument's own value,
  and separately `operand` recurses directly into itself over `Bson::Array`
  items (line 145). `grep -n 'depth\|MAX_' crates/secantus-core/src/expr_parse.rs`
  returns nothing — there is no depth counter anywhere in the file. It is
  wired into parse-time validation at `crates/secantus-commands/src/find.rs:568`
  (`projection_spec`), `crates/secantus-commands/src/findandmodify.rs:278`,
  `crates/secantus-commands/src/aggregate.rs:1467-1523` (`$addFields`/`$set`,
  `$project`/`$unset`, `$replaceWith`/`$redact`, `$replaceRoot`, `$expr`), and
  `crates/secantus-core/src/group.rs:1856` (accumulator expressions). A
  single small request such as `db.c.find({}, {a: {$add: [{$add: [{$add:
  [ /* thousands of levels */ ]}]}]}})` costs roughly 20 bytes per nesting
  level, so BSON's 16 MB document limit comfortably permits a nesting depth
  deep enough to exhaust a thread's stack. This is exactly the bug class
  the prior two reports' top priority named ("give the unguarded-recursion
  class a structural fix") reproducing itself in brand-new code, and it is
  cheaper to trigger than the already-filed `jsonschema.rs` CRITICAL — a
  plain projection document, no `$jsonSchema` keyword needed. A Rust stack
  overflow is a hard process abort (SIGSEGV on the guard page), taking down
  every connected client, not just the attacker's.
  **Fix direction:** thread a depth counter through `operand`/`object`/
  `operator`/`argument` (and the sibling `add_fields_element`/
  `add_fields_object`/`ProjectionParse::element`/`sub_object` functions in
  the same file) and refuse past a bound, mirroring the fix already
  proposed for `jsonschema.rs`.

- **`crates/secantus-core/src/sbe.rs` — the new slot-based-engine
  compatibility checker's `expression_compatible`/`filter_compatible`/
  `projection_compatible` recurse with no depth bound, reachable from any
  pipeline's leading `$match`.** New this window (`99b7d55b`, RM-280).
  `expression_compatible` (line 174) recurses into every array item and
  every document value with no counter; `filter_compatible` (line 194)
  recurses through nested `$and`/`$or`/`$nor`; `projection_compatible`
  (line 209) recurses through nested sub-projection documents. Called from
  `crates/secantus-commands/src/aggregate.rs:664,2792` on every pipeline's
  first `$match` stage, specifically to decide a routing question (does
  this pipeline qualify for the SBE-compatible fast path), which means the
  check itself walks attacker-shaped structure before deciding how to
  execute it. `grep -n 'depth\|MAX_' crates/secantus-core/src/sbe.rs`
  confirms no bound exists anywhere in the file. Same trigger shape as
  above: `db.c.aggregate([{$match: {$expr: {$and: [{$and: [{$and: [ /*
  thousands deep */ ]}]}]}}}])`, no documents required in the collection,
  no privilege required.
  **Fix direction:** same structural fix — a depth counter threaded through
  all three functions, refusing (falling back to "not SBE-compatible,"
  which is always a safe answer for this specific function) past a bound.

- **`crates/secantus-pgplan/src/extstats.rs`'s `mcv_items` — unbounded
  allocation from attacker-controlled bytes, reachable via a plain
  `pg_mcv_list_items(decode(...))` call with no privilege and no prior
  `CREATE STATISTICS`.** New this window (`59d50b34`, batches 47-53).
  `mcv_items` (line 404) reads `nitems` (line 417), `ndims` (line 418), and
  each dimension's `nvalues` (line 426) as raw little-endian integers taken
  directly from the input byte slice, then immediately calls
  `Vec::with_capacity(*nvalues)` (line 435), `Vec::with_capacity(nitems)`
  (line 447), and nested per-dimension/per-item allocations — all **before
  any check that the buffer actually contains that many elements**. The
  call path from SQL has no gate that the bytes actually originated from
  `pg_statistic_ext_data.stxmcv`: `crates/secantus-pgplan/src/lib.rs:13966`
  (`"pg_mcv_list_items" => ... extstats::mcv_list_rows(&a[0])?`) hands
  `mcv_list_rows` whatever value the argument expression evaluates to, and
  `mcv_list_rows` (`extstats.rs:472`) accepts **any** `Bson::Binary` — the
  same `Bson::Binary` representation an ordinary `bytea` value has. The
  comment at `lib.rs:32177` ("An MCV list read from `pg_statistic_ext_data`
  is one already; no literal is") is incorrect: `decode('...', 'hex')`
  also produces a `Bson::Binary`, and `cast_value`'s match arm at
  `lib.rs:32178` (`v @ Bson::Binary(_) if target == "pg_mcv_list" => Ok(v)`)
  passes it straight through with no provenance check. A client can send
  `SELECT * FROM pg_mcv_list_items(decode('c251a6e1 01000000 ffffffff
  0a00', 'hex'))` (magic + type tag + a huge `nitems`/`nvalues` field, well
  under 100 bytes total) and force a multi-gigabyte-to-terabyte allocation
  request. Rust's global allocator calls `handle_alloc_error` on failure,
  which **aborts the whole process**, not just the connection — one short,
  unprivileged query takes down the server for every client.
  **Fix direction:** before each `Vec::with_capacity` call, validate the
  requested count against the remaining buffer length (e.g.
  `bytes.len().saturating_sub(at) / min_item_size`) and return the existing
  `None`/"invalid MCV list" error instead; additionally refuse
  `pg_mcv_list_items` unless the argument can be shown to have come from
  the catalog column (not strictly necessary once the length check lands,
  but closes the provenance gap the misleading comment assumed existed).

- **`crates/secantus-pg/src/extstats.rs`'s `ndistinct`/`dependencies` — no
  cap on `CREATE STATISTICS`'s column/expression count, so `ANALYZE`
  performs combinatorial work unbounded in the number of columns a client
  names.** New this window. `ndistinct` (line 77) and `dependencies` (line
  144) both iterate `k` from 2 to `dims.len()` and enumerate **all**
  `C(dims.len(), k)` combinations (`combinations`/`dependency_orders`,
  lines 109-140), each doing a full sort over the sampled rows.
  `crates/secantus-pgplan/src/catalog_stmts.rs::plan_create_statistics`
  (line 124) checks only a **minimum** of 2 columns/expressions (line 163)
  — there is no maximum, whereas real PostgreSQL enforces
  `STATS_MAX_DIMENSIONS = 8` in `CreateStatistics` and refuses with
  `errmsg("cannot have more than %d columns in statistics")`. Any
  authenticated session that owns a table (the default posture for a test
  database) can do:
  ```sql
  CREATE TABLE t (c1 int, c2 int, ..., c30 int);
  CREATE STATISTICS s (dependencies) ON c1,c2,...,c30 FROM t;
  ANALYZE t;
  ```
  — `dependencies()` alone would attempt on the order of `C(30,15)` ≈ 155
  million combination-sorts from one `ANALYZE`, an unbounded CPU/memory DoS
  triggerable with four lines of ordinary SQL and no elevated privilege.
  **Fix direction:** reject `CREATE STATISTICS` with more than 8 combined
  columns+expressions, matching PostgreSQL's own limit exactly.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`crates/secantus-pg/src/access_methods.rs` — `CREATE ACCESS METHOD` /
  `DROP ACCESS METHOD` perform no privilege check at all.** New this window
  (`59d50b34`). `execute_access_method` (line 79) dispatches
  `AccessMethodOp::Create` (line 82) and `AccessMethodOp::Drop` (line 133)
  with no call to `is_superuser`/`require_superuser` anywhere in the
  function (confirmed by `grep -n "is_superuser" access_methods.rs`
  returning nothing), whereas real PostgreSQL's `CreateAccessMethod`/
  `DropAccessMethod` (`amcmds.c`) refuse with 42501 unless the caller is a
  superuser. Any authenticated role — including one with only `CONNECT` —
  can run `CREATE ACCESS METHOD x TYPE TABLE HANDLER heap_tableam_handler`
  or `DROP ACCESS METHOD ... CASCADE`, polluting (or, with `CASCADE`,
  deleting other users' objects that reference) the shared `pg_am` catalog
  for the whole current database. Impact is bounded — the handler name is
  checked against a fixed whitelist, so there's no code-execution path —
  but it's a genuine authorization gap and a cheap per-database DoS/
  name-squatting vector.
  **Fix direction:** add the same `is_superuser` check used elsewhere in
  this crate (e.g. `parameter_acl.rs`'s pattern) before `Create`/`Drop`.

- **`crates/secantus-pg/src/xids.rs`'s `take()` — a failed xid-block
  reservation write is only logged to stderr, not surfaced, and the caller
  still gets a "reserved" xid.** New this window (part of the heap/xid
  model landed in `59d50b34`, following Joe's "always choose the Postgres
  model" direction for `age(xid)`). Lines 154-169:
  ```rust
  fn take(c: &mut Cluster) -> u64 {
      let xid = c.next;
      c.next += 1;
      if xid >= c.reserved {
          if let Some(storage) = c.storage.upgrade() {
              match reserve(&storage, xid + BLOCK) {
                  Ok(()) => c.reserved = xid + BLOCK,
                  Err(e) => eprintln!("secantusd-pg: {e}"),
              }
          }
      }
      xid
  }
  ```
  If the underlying `__sql_xid__` write fails (disk full, a WiredTiger
  error), the function prints to stderr and still hands out the xid as
  though the reservation succeeded. Per this project's own "never ignore a
  storage write error" rule, a swallowed write here is a correctness
  hazard for exactly the durability property this model exists to be
  faithful to: an unrecorded reservation can let an xid be reused after a
  crash/restart, corrupting the MVCC/`age()` bookkeeping the whole feature
  was built to get right.
  **Fix direction:** propagate the error so the transaction requesting the
  xid fails, rather than silently continuing past a logged-only error.

- **`crates/secantus-commands/src/aggregate.rs`'s `validate_parse` — its
  own `$lookup`/`$unionWith`/`$facet` sub-pipeline recursion is
  independently unbounded**, a different nesting dimension from the two
  CRITICALs above (nested *pipelines*, not nested *expressions*). Present
  at `aggregate.rs:1466` in this window's validation path; each level
  costs more bytes than the compact `expr_parse.rs` case (a full stage
  document per level rather than one operator object), so it's a less
  cheaply-triggered instance of the same bug class, which is why this is a
  WARNING rather than a fifth CRITICAL — but it is still unbounded and
  still reachable from an ordinary, unprivileged `aggregate` command.
  **Fix direction:** the same depth-bound fix tracked for the broader
  unguarded-recursion class covers this too; worth its own line so it isn't
  lost once the expression-level bugs are fixed and this one is forgotten.

- **`crates/secantus-core/src/expr_rewrite.rs`'s constant-fold recursion
  (already flagged as a pre-existing, unguarded gap in the 2026-10-23
  report) is widened again this window** to also traverse `$let`/`$map`/
  `$filter`/`$reduce` bodies, and a new `let_fault` path eagerly evaluates
  constant `$let` bindings via `expressions::evaluate` at pipeline-parse
  time — before any document is read, same as the widening the last report
  already called out for `$switch`/other operators. This doesn't introduce
  the recursion (still tracked under the 31+-instance class) but again
  lowers the cost of triggering it: a single `aggregate` against an empty
  collection with a deeply-nested `$let` now reaches the eager-evaluation
  path that previously required documents to flow through the pipeline.
  **Fix direction:** unchanged from the 10-23 report — the same depth bound
  fix for the unguarded-recursion class resolves this; calling it out
  separately because it's a second widening of the same bug's reachability
  in consecutive cycles, which is worth tracking as its own regression
  rather than silently folding into the structural ticket.

## 🟢 CLEAN (Passed review)
