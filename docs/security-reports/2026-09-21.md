## 🔴 CRITICAL (Immediate action required)

of this cycle's 24 commits touch their files — confirmed via
`git diff --stat 7126a589..HEAD -- src/secantus/wire.py src/secantus/server.py
src/secantus/storage.py src/secantus/auth.py crates/secantus-wire
crates/secantus-server` returning only two one-line version-bump diffs in
`Cargo.toml`.

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  ```rust
  pub fn body_len(&self) -> Result<usize, WireError> {
      if (self.message_length as usize) < HEADER_SIZE {   // sign-extends first
          return Err(...);
      }
      if self.message_length > MAX_MESSAGE_SIZE {          // compares the signed, still-negative value
          return Err(...);
      }
      Ok(self.message_length as usize - HEADER_SIZE)
  }
  ```
  A negative `i32` `message_length` sign-extends to near `usize::MAX` on the
  cast, which passes the first guard (it's huge, not small) and passes the
  second guard (a negative `i32` never exceeds `MAX_MESSAGE_SIZE`). The
  caller (`crates/secantus-server/src/lib.rs:553,561-562`) feeds the result
  straight to `vec![0u8; body_len]`; the `AllocBudget::acquire` check
  (`lib.rs:87-94`) skips its wait unconditionally when `used == 0`, so the
  very first in-flight request is never bounded. Rust's global allocator
  aborts the whole process on an allocation failure of that size — one
  unauthenticated 16-byte frame is a full-server abort. **Not fixed.**
- **#1160** — `src/secantus/commands.py:8834-8947` / `crates/secantus-commands
  /src/lib.rs:1518-1569`. `"bulkWrite"` is in neither `_COMMAND_ACTIONS` nor
  `_NO_PRIVILEGE_COMMANDS` on the Python side, and `command_action()` has no
  `"bulkWrite"` arm on the Rust side. On both servers the privilege check is
  **skip-on-`None`, not deny-on-`None`**
  (`commands.py:9754-9755`: `if info is not None: ...` — the whole check is
  bypassed when `info` is `None`), so an authenticated user with zero role
  grants can call `bulkWrite` on both servers when `--auth` is enabled.
  **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471` (`_MAX_REGEX_PATTERN_LEN =
  1000`, `_compile_regex`). Still a length-only guard: `re.compile(pattern,
  flags)` at line ~1411 has no backtracking-depth or match-time budget, and a
  second, uncapped `re.compile` fallback remains at lines 1463-1471 inside
  the `TypeError` recovery branch. A short pathological pattern (e.g.
  `(a+)+b`) under the 1000-char cap against a long non-matching string still
  pins a worker thread's CPU indefinitely. **Not fixed.**

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **Unchecked arithmetic in `declared_typmod` now reachable from plain DDL,
  panics in debug builds — Rust PG server** (filed as a new issue below).
  `crates/secantus-pgplan/src/lib.rs:1985-2001` computes a declared type's
  `atttypmod` from client-supplied type-modifier literals with plain
  (unchecked) `+`/`<<` arithmetic — `numeric(p,s)`: `(p << 16) + 4` or
  `((p << 16) | (s & 0x7FF)) + 4`; `char(n)`/`varchar(n)`/`bit(n)`: `n + 4`.
  This arithmetic predates this cycle, but the `char(n)`-padding feature
  (#1534) added a **new call site** at `plan_create`
  (`crates/secantus-pgplan/src/lib.rs:2128`:
  `column.typmod = cd.type_name.as_ref().map(declared_typmod).unwrap_or(-1);`),
  so a bare `CREATE TABLE t (a char(2147483647))` now reaches it directly —
  no `CAST` needed. In a **debug build** — which is what
  `./inv rust-pgserver-build` produces and what the local gauge/dev workflow
  runs per `CLAUDE.md` — Rust's default checked-overflow-panics-in-debug
  semantics turn `n + 4` into a panic, an unauthenticated remote DoS (the PG
  server has no auth at all, #1191). Checked the **release** build path
  (`crates/secantus-pgplan/Cargo.toml` / the workspace has no
  `overflow-checks = true` override in `[profile.release]`, and
  `release-pg-binaries.yml` builds `--release`): in release mode the same
  expression silently *wraps* instead of panicking, so the shipped
  `secantusd-pg` binary does not crash here — it stores a wrapped, likely
  negative, `typmod`. That negative value is consumed at
  `crates/secantus-pgserver/src/lib.rs:11946-11961` (`blank_padded`), which
  guards `field.type_modifier() <= 4` and no-ops for any negative value, so
  the release-mode consequence is silently-wrong-but-harmless (no crash, no
  out-of-bounds read). **Net severity: WARNING, not CRITICAL** — the crash is
  real but confined to debug/dev builds; the release binary degrades to
  silently ignoring the declared width rather than crashing or corrupting
  memory. Still worth a `checked_add`/`saturating_add` fix: relying on
  release-mode overflow *wrapping* to save you is exactly the kind of
  implicit-behavior-by-build-profile this project's "never ignore an error"
  ethos warns against.
- **Two more unbounded-recursion sites added by this cycle's SQL feature
  work, Rust PG server** (filed as a new issue below, extending the
  already-tracked 14-instance class — #1117/#1161/#1192/#1193/#1355-1357/
  #1394-1396/#1430-1433/#1456). All three lack any depth counter or
  recursion-guard, matching the exact shape CLAUDE.md documents recurring in
  this codebase:
  - `crates/secantus-pgplan/src/lib.rs:461` (`plan_select`/
    `plan_set_operation`) plus the runtime counterparts in
    `crates/secantus-pgserver/src/lib.rs` (`set_op_rows`/`rows_with_schema`)
    — new this cycle for `DISTINCT`/set-operation support (#1529). Mutually
    recursive over nested `UNION`/`INTERSECT`/`EXCEPT`; a deeply nested
    set-operation statement can stack-overflow the process both at plan time
    and at execution time.
  - `crates/secantus-pgplan/src/lib.rs:583` (`plan_having`) plus
    `having_holds` in `crates/secantus-pgserver/src/lib.rs` — new this cycle
    for `HAVING` support (#1546). Recurses into nested `AND`/`OR`/`NOT` with
    no depth cap, at both plan time and per-row eval time.
  - `crates/secantus-pgplan/src/lib.rs:347` (`contains_nested_aggregate`'s
    `walk()`) — recurses into nested `FuncCall`/`AExpr`/`TypeCast`/
    `BoolExpr`/`CoalesceExpr`/`CaseExpr` arguments with no depth cap.

  All three are reachable by any client (unauthenticated, #1191) via a single
  crafted `SELECT` statement with deeply nested boolean/set-operation syntax.
- **Schema-qualified function name is joined into a catalog dict key without
  escaping literal dots — Python PG server** (filed as a new issue below).
  This cycle's schema-visibility fix (#1523,
  `src/secantus/sql/engine.py:5061-5062`) widened function-name qualification
  from only `pg_temp_*` to *any* named schema:
  ```python
  if fn_schema is not None and fn_schema.name not in ("", "public"):
      name = f"{fn_schema.name}.{name}"
  ```
  The joined string becomes the catalog storage key
  (`_function_key`, `src/secantus/sql/catalog.py:1240-1241`:
  `f"{name.lower()}/{nargs}"`), and the same join is reconstructed
  symmetrically at call time (`src/secantus/sql/scalar.py:4322`:
  `f"{schema.lower()}.{name}"`) and at reflection time
  (`_split_user_type_name`, `src/secantus/sql/virtual.py:1048`, a naive
  `name.split(".", 1)[0]`). PostgreSQL identifiers may be double-quoted to
  embed a literal `.`, so `CREATE FUNCTION admin.run()` (schema-qualified,
  schema=`admin`, name=`run`) and `CREATE FUNCTION "admin.run"()`
  (unqualified — one identifier that happens to contain a dot) mint the
  **identical** stored key `admin.run/0`. `put_function`
  (`catalog.py:1243-1246`) deletes-then-inserts under that key, so an
  unrelated client's `CREATE OR REPLACE FUNCTION "admin.run"()` silently
  overwrites a same-named function a different, genuinely schema-qualified
  `CREATE FUNCTION admin.run()` created. This is the same "user-supplied path
  used as a dict key" shape `CLAUDE.md` already documents three prior
  instances of (the upsert seed, `$lookup`'s `as`, `$graphLookup`'s `as`).
  No CREATE-FUNCTION-time ownership/privilege check exists in this codebase
  today, so the collision does not currently cross an *enforced* privilege
  boundary — but it is a real, trivially crafted integrity hazard (silent
  wrong-function substitution) on an unauthenticated server (#1191), and
  becomes a genuine privilege-escalation primitive the moment schema-level
  CREATE privilege enforcement lands. WARNING, not CRITICAL, for that reason.
