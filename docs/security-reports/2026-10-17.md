## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Unbounded recursion in the new `$expr` query-optimizer rewrite — stack-
  overflow DoS reachable from ordinary `find`/`aggregate`/`update`/`delete`/
  `findAndModify`/`distinct`, not merely `explain`.**
  `crates/secantus-core/src/expr_rewrite.rs` (new file, commit `31198d79`,
  "`$expr` planned as mongod plans it"). Five functions walk a client-supplied
  `$expr` expression tree (nested BSON arrays/documents) with **no depth
  counter anywhere in the file** (grepped for `depth`/`MAX_`/counter
  variables — zero hits): `is_constant` (`:118`, recurses via
  `Bson::Array::iter().all(is_constant)` and `d.values().all(is_constant)`),
  `optimize` (`:193`, recurses into `Bson::Array`/`Bson::Document` members),
  `optimize_operator` (`:221`, recurses once per operator argument via
  `list.iter().map(optimize)`), `constant_expr_fault` (`:141`, recurses via
  `items.iter().find_map(constant_expr_fault)` and
  `d.values().find_map(constant_expr_fault)`), and `rewrite` (`:262`,
  recurses on `$and`/`$or` argument arrays). These are not confined to
  `explain`: `constant_expr_error_in_filter` (`:161`, itself recursive on
  `$and`/`$or`/`$nor`) is called from
  `crates/secantus-commands/src/argtypes.rs:1755` inside
  `expression_problem_in_filter`, which is confirmed (by direct `grep`) to be
  invoked from `find.rs:446`, `crud.rs:1114` and `:1367` (ordinary
  `update`/`delete`), `findandmodify.rs:104`, `distinct.rs:69`, and
  `profiler/filter.rs:205` — i.e. on the ordinary data-command path for any
  filter containing `$expr`, which needs no special privilege (and no
  privilege at all with `--auth` off, the default). Trigger:
  `db.coll.find({filter: {$expr: {$and: [{$and: [{$and: [ ... 100,000 levels
  ... ]}]}]}}})`. BSON nesting costs only a few bytes per level, so this fits
  comfortably inside the 16 MB document limit. Rust's default handler aborts
  the **entire process** on stack overflow, not just the offending
  connection thread, so one unauthenticated client request takes down every
  other connection on the server. This is a fresh instance of the bug class
  this project's tracker already has ~25+ open examples of (see the
  2026-10-16 report and its own carried-forward list) — in code that did not
  exist before this cycle, not a re-discovery of previously-known code.

- **Unbounded recursion in the new `$toHashedIndexKey` hashing — stack-
  overflow DoS via any aggregation `$project`/`$addFields`/`$group`, or a
  `find`/`update`/`delete` filter's `$expr`, that calls the operator over a
  deeply nested literal.**
  `crates/secantus-core/src/hashed.rs` (new file, commit `55e7a52a`, "cycle 2
  batch … `$toHashedIndexKey` …"). `hash_element` (`:62`) and `hash_members`
  (`:88`) are mutually recursive over `Bson::Document`/`Bson::Array` with no
  depth limit: `hash_element` matches `Bson::Document(d) =>
  hash_members(m, d.iter()...)` and `Bson::Array(a) => hash_members(m,
  ...)`, and `hash_members` calls `hash_element` once per member with no
  counter. Reachable via the `$toHashedIndexKey` expression operator
  (`crates/secantus-core/src/expressions.rs:7717`,
  `op_to_hashed_index_key`), which first fully *evaluates* its argument
  (`eval(arg, ctx)?`) and then calls `hash64(&v, ...)` on the resulting
  value — so `{$toHashedIndexKey: {$literal: <array nested 100,000 levels
  deep>}}` evaluates the literal as-is (no evaluation-time recursion limit
  applies to a literal) and then recurses through `hash_element`/
  `hash_members` once per level. `$toHashedIndexKey` is an ordinary
  aggregation-expression operator usable in `$project`, `$addFields`,
  `$group`, or inside `$expr` on `find`/`update`/`delete` — no special
  privilege needed. Same stack-overflow/whole-process-abort consequence as
  the finding above, and the same bug class.

Both were verified by reading the full function bodies (not inferred from
the diff hunk or the function name) and by tracing the actual call chain
from the wire-facing command handler down to the recursive function, per
this project's own "reproduce before reporting" standard.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **A deadlock cycle spanning the new shared advisory-lock wait-for graph
  and the Rust PostgreSQL server's pre-existing, separate row-lock /
  table-lock waiters is invisible to all three detectors — two ordinary
  sessions can hang forever (`lock_timeout` defaults to `0`, i.e. no
  timeout) instead of one being aborted with `40P01`/`55P03` as PostgreSQL
  would.**
  `crates/secantus-pg/src/lock_manager.rs` (new, commit `2a2fd490`,
  "advisory-lock deadlock detection on a shared wait-for graph") wires
  `pg_advisory_lock`/`pg_advisory_xact_lock` (`advisory.rs:117`, the only
  call site of `lock_manager::` outside the module itself, confirmed by
  `grep`) onto a new, correctly-built iterative cycle detector
  (`deadlocked()`, `:42`, a `while let Some(p) = stack.pop()` DFS with a
  `seen` visited-set — not recursive, so it carries no stack-overflow risk
  of its own, and its graph is bounded by the number of concurrently-waiting
  sessions, not by anything a single client can inflate). But
  `crates/secantus-pg/src/{row_waits.rs,table_locks.rs}` — the pre-existing
  detectors for row locks and table-level `LOCK`/DDL waits — were **not**
  migrated onto this graph and keep their own separate bookkeeping. A
  session that holds an advisory lock while waiting on another session's row
  (or vice versa) therefore completes a real wait-for cycle that no single
  detector can see in full: each detector only sees its own lock kind's
  edges. The commit's own author found and filed this in the same commit
  (`tasks/backlog-rust-postgres.md`, `RP-048`, confirmed present verbatim:
  "a deadlock cycle that runs through two lock kinds is not detected …
  Measured 2026-10-17: both sides answer `55P03` after a 3 s `lock_timeout`
  … The fix is the consolidation the review planned: migrate `row_waits::
  Waiting` and `table_locks`' waits onto `lock_manager`'s single graph.").
  Severity is WARNING rather than CRITICAL: it needs two sessions actively
  cooperating or colliding across two specific lock kinds (not a single
  malicious client, and not a crash — a hang), and PostgreSQL's own
  `deadlock_timeout` mechanism is itself bypassed only in this narrow
  cross-kind case, not for same-kind deadlocks (which the three detectors
  each still catch within their own kind). It is filed here as a tracked
  `security` issue, separate from its `RP-048` backlog entry, because this
  review's own instructions require a `security`-labelled GitHub issue for
  every WARNING/CRITICAL regardless of whether an engineering backlog entry
  already exists — the backlog and the issue tracker serve different
  purposes and audiences, and this project's own rule elsewhere ("never use
  a lingering report PR/branch as the tracking mechanism") implies the
  converse too: a backlog line is not a substitute for the issue that makes
  a security finding visible to someone scanning `gh issue list --label
  security`.

## 🟡 INFO (Best-practice recommendations)

- **The Rust PostgreSQL server's new WHERE-clause-lowering recursion
  (`flatten`/`canonical`/`where_or` in `crates/secantus-pg/src/lib.rs:642-
  710`, all new in `27b452f7`) has no depth guard of its own, but is not
  independently exploitable today — this was the one place this review's
  initial sub-agent pass called CRITICAL and a direct re-read downgraded.**
  `flatten` recurses once per `$and` nesting level with no counter;
  `canonical`/`where_or` are mutually recursive over `WhereClause::Or` arms,
  also uncounted. But every SQL statement this server executes is parsed
  through the single memoized `parse_tree()` entry point
  (`crates/secantus-pgplan/src/lib.rs:3723`), which unconditionally runs
  `check_depth()` against `MAX_EXPR_DEPTH = 2500` for any statement over 512
  characters (`:3738-3740`) — short statements are provably too short to
  reach 2 characters/level × 2500 levels — and even routes pathologically
  long statements through a dedicated 1 GiB stack
  (`parse_guarded`/`cancel::interruptible(BIG_STACK_BYTES, ...)`,
  `:3819-3847`) specifically so libpg_query's own recursive parser/protobuf
  round-trip cannot overflow first. Since the BSON filter `where_clauses`
  operates on is derived from that same depth-capped AST, the new functions
  can recurse at most ~2500 levels — and the server's ordinary per-
  connection worker thread stack is a generous 256 MiB
  (`crates/secantus-pg/src/server.rs:390`, `WORKER_STACK_BYTES = 256 << 20`).
  Even a pessimistic 10 KiB-per-frame estimate for these simple enum-walking
  functions puts 2500 levels at ~25 MiB — well inside the 256 MiB budget,
  with roughly 10x headroom to spare. This is a real difference from the
  2026-10-16 report's `explain::hoist.rs` finding, which was filed CRITICAL
  specifically because its upstream mitigation (`#1780`, the `bson` crate's
  depth-unlimited decoder) **does not exist yet**; here the upstream
  mitigation (`MAX_EXPR_DEPTH`/`check_depth`) is already live, comprehensive
  (applies to every parsed statement, not an opt-in), and the arithmetic
  clears with a wide margin. Still worth hardening defensively — a future
  loosening of `MAX_EXPR_DEPTH`, or a new code path that reaches
  `where_clauses` without going through `parse_tree()`, would remove the
  only line of defense these three functions have — but it is not a
  currently-exploitable finding, so it is recorded here rather than as a
  CRITICAL or WARNING. No separate issue filed for this one.
- **The Rust MongoDB server's new real lock manager
  (`crates/secantus-commands/src/lock_manager.rs`, `4792a18d`) was checked
  for the analogous cross-transaction deadlock shape the PG WARNING above
  describes, and is structurally deadlock-free rather than merely
  undetected.** `statement_chain()`/`statement_rounds()` always acquire
  resources in the fixed order Global → Database → Collection(s) (and
  `renameCollection`'s second collection is always appended last), so two
  statements can never form a lock-ordering cycle *within* this manager — a
  classic deadlock-prevention-by-ordering discipline, needing no detector.
  A multi-statement transaction that locks collections in different orders
  across its lifetime can still in principle block indefinitely against
  another such transaction with no `maxTimeMS` armed; the module's own doc
  comment (`:19-26`) states this is deliberate and matches mongod's own
  behaviour exactly ("Waits poll the request's deadline … with no budget
  armed the wait is unbounded, as mongod's is without `maxTimeMS`") —
  per this project's explicit design rule that `mongod` is the exemplar
  "however long-standing" a matched behaviour is, this is parity, not a
  divergence, and is not filed as a finding.
- **No new `unsafe` block in either server's reviewed diff operates on a
  wire- or SQL-derived length or pointer.** The Rust MongoDB server's new
  `unsafe` (`crates/secantus-commands/src/procstats.rs::fs_space`, a
  `statvfs` FFI call) operates on the server-local storage directory path,
  not client input. The WT FFI crate's diff in this window only reshuffles
  an existing struct field. The Rust PostgreSQL server's diff adds no new
  `unsafe` block at all.
- **The new SCRAM first-step change (`crates/secantus-commands/src/auth.rs`,
  `aee63535`) tightens rather than weakens authentication**: it now fails at
  `saslStart` for an unknown user or an undersized client nonce instead of
  deferring the rejection to the proof step, matching mongod's measured
  behaviour; the new nonce-slicing helper is bounds-checked.
- **`crates/secantus-commands/src/resume_keystring.rs`** (new, change-stream
  resume-token parsing over client-controlled bytes) is a positive example
  worth naming: its recursive `object`/`value` walk is explicitly depth-
  guarded (`MAX_DEPTH: u32 = 200`, checked at the top of `value`), and every
  buffer read goes through bounds-checked accessors — the correct version of
  the pattern the two CRITICALs above are missing.
- **One unverified cross-function invariant in new Rust PostgreSQL join
  code**: `crates/secantus-pg/src/lib.rs:8745`,
  `self.narrow_with_implied(join).expect("narrow_join_method checked it")`
  assumes `narrow_with_implied` (new) always succeeds whenever a sibling
  function `narrow_join_method` (new) already succeeded for the same join

## 🟢 CLEAN (Passed review)

- **Change-stream >16 MB splitting**
  (`crates/secantus-storage/src/changestreams.rs::stamp_split_event`,
  `fe878c66`) was read in full: the inner `Iterator::next().expect("peeked")`
  calls are always preceded by a `peek().is_some()` check in the same
  iteration, so they cannot panic; an over-large single field returns a
  clean `Err` rather than panicking or looping; the outer loop always
  consumes at least one field per iteration, so it terminates in O(fields)
  with no unbounded allocation beyond the input document's own (16 MB-
  capped) size.
- **The Rust PostgreSQL server's multi-table join search
  (`crates/secantus-pg/src/{join_search,join_order}.rs`, new) is hard-
  capped, not combinatorially explosive.** `three_table_plan` requires the
  join tree to destructure into exactly two nested levels over three leaves
  and bails otherwise; `four_table_chain` walks the join tree's left spine
  with a plain `while` loop (not recursion) and bails unless it finds
  exactly three joins. The DP in `search_four` runs only over a fixed
  `n = 4`. A query joining more tables simply falls through to the
  pre-existing, unaccelerated join path.
- **The deadlock detector itself** (`lock_manager.rs::deadlocked`, see the
  WARNING above for its scope gap) is sound in isolation: iterative DFS with
  a visited-set, graph size bounded by concurrently-waiting sessions, self-
  edges dropped, so a single session cannot manufacture a false cycle
  against itself.
- **No reintroduction of the serde-BSON extended-JSON decode bug** this
  project previously fixed project-wide (`tests/test_rust_literal_bson_
  decode.py`'s guarded class): grepped the full 21-commit diff for
  `bson::Document::from_reader`/`bson::from_slice` — none added.
- **No new `let _ =` swallowing a `Result` on a write/commit/close path** in
  either server's diff.
- **No command dispatch table in either server's diff lost its catch-all
