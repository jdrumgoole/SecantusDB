## 🔴 CRITICAL (Immediate action required)

All three unchanged from 2026-09-07 — re-verified by reading current source,
not carried on trust. All are reachable from an ordinary (unauthenticated,
for the first two) wire client:

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  `self.message_length as usize` (line 138) casts the `i32` directly, so
  `message_length = -1` sign-extends to `usize::MAX` on 64-bit *before*
  either bound check runs; the `MAX_MESSAGE_SIZE` check (line 144) still
  compares the raw signed `i32`, so `-1 > 48_000_000` is also false. Both
  guards let a negative length through and the function returns
  `Ok(usize::MAX - 16)`. Feeds straight into an oversized allocation on the
  accept path, aborting the process from one unauthenticated 16-byte frame.
  Only line numbers shifted (135-151 → 137-151) since last cycle. **Not
  fixed.**

- **#1160** — `src/secantus/commands.py`. `"bulkWrite": _bulk_write` is
  registered in `_HANDLERS` at line 8622, but `_COMMAND_ACTIONS`
  (8707-8790) and `_NO_PRIVILEGE_COMMANDS` (8797-8820) both have zero
  `"bulkWrite"` entries. Dispatch logic (9620-9629): `info =
  _COMMAND_ACTIONS.get(name)`; when `info is None` there is no `else`
  branch — execution falls through with no privilege check. `bulkWrite`
  still bypasses authorization entirely under `--auth`. **Not fixed.**

- **#977** — `src/secantus/query.py:1364` (`_MAX_REGEX_PATTERN_LEN = 1000`).
  `_compile_regex` (1369-1373) still only checks pattern *length*, then
  calls `re.compile` unguarded (line 1373); a second bare `re.compile` call
  at line 1424 is equally unguarded. No backtracking-depth or match-time
  budget — the cap doesn't help against a pathological `(a+)+$`-shaped
  pattern, 6 characters, far under the 1000-char ceiling. CPython's `_sre`
  engine never releases the GIL mid-match, so this remains a whole-server
  CPU-pinning DoS from one unauthenticated `find`. **Not fixed.**
