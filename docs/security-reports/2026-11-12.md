## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`decode()` recurses once per nested level of an interleaved BSONColumn
  reference document with no depth limit, reachable via a direct insert into
  `system.buckets.<name>` — a crafted bucket aborts the whole server
  process** (medium/high/high).
  `crates/secantus-core/src/bsoncolumn.rs`'s `reference_nodes()` (lines
  2359-2387) and `interleaved_fields()` (2432-2475) recurse once per nested
  `OBJECT`/`ARRAY` field in an interleaved control block's reference
  document, with **no depth counter anywhere in either function, the file,
  or any caller**. Each nesting level costs only ~7 bytes, so a `Binary`
  value sized up to the 16 MiB BSON document ceiling can encode on the order
  of 2×10^6 recursion levels. Reachable because `crud.rs::insert()`'s
  time-series validation gate is keyed off the **exact target namespace**
  of the insert (`storage.get_collection_options(&db, &coll)`,
  crud.rs:995-998) and `admin.rs::invalid_write_namespace` **explicitly
  exempts `system.buckets.*`** from its reserved-namespace block
  (admin.rs:3841-3848) on the premise, stated in its own comment, that
  "the existing timeseries handling" covers it. It does not: the physical
  bucket collection's own stored catalog options are
  `{clusteredIndex: true}` only (`ts_store::bucket_collection_options`,
  ts_store.rs:46-48), never a `timeseries` key, so `timeseries::Fields::of`
  (timeseries.rs:28-34) returns `None` for a direct insert against
  `system.buckets.<name>` once it exists — skipping `measurement_problem`
  validation entirely and storing an arbitrary `data.<field>:
  Binary(subtype=7, ...)` value verbatim. That value is later fed straight
  into `bsoncolumn::decode()` with no structural check beyond the binary
  subtype tag, from two call sites: `ts_store::unpack()` (reached by any
  `find`/`aggregate` on the logical collection) and `bucket_catalog.rs`'s
  bucket-reopen path (reached by a subsequent, entirely ordinary insert of a
  real measurement). The project's only generic nesting-depth guard
  (`crud.rs`'s `too_deep()`, `MAX_NESTING_DEPTH=180`) never inspects the
  bytes inside a `Binary` value, so it does not see the nesting encoded
  inside the crafted column payload. A Rust stack overflow from unbounded
  recursion is not a catchable panic — it aborts the whole process, taking
  down every connected client on this single-node server. An independent
  verifier re-read every cited line, re-confirmed the write-path bypass,
  re-confirmed the absence of any depth counter, and promoted the hunter's
  own cautious `needs_validation` draft to `confirmed`, since the missing
  bound is fully settled by source alone.
  **Fix:** add an explicit depth counter (or an iterative traversal) to
  `reference_nodes()`/`interleaved_fields()`, reusing the same 180-level
  ceiling `crud.rs` already enforces for ordinary documents; separately,
  close the write-path gap so a direct insert into `system.buckets.<name>`
  still resolves to the logical collection's time-series validation (or is
  refused outright).
  **Filed as a new issue** (duplicate search found no existing coverage).

- **`bsoncolumn::decode()`'s Simple-8b RLE expansion has no cap relating a
  claimed repeat count to input size — the same `system.buckets.<name>`
  write-path bypass can drive multi-gigabyte memory allocation from under
  1 MB of stored bytes** (medium/high/high).
  The same new file's Simple-8b RLE decoder (`S8Iter::load_block`, lines
  1962-1966) sets `rle_remaining = (ext+1)*120 - 1` straight from a 4-bit
  field in an attacker-controlled 8-byte word — up to 1920 repeats per word,
  up to 30720 per 128-byte control block — and **neither `load_block`,
  `advance()`, nor the main `decode()` loop ever compares the cumulative
  produced-value count against `buf.len()` or any ceiling** before pushing
  another heap-allocated `Value`. Tiling the pattern to the 16 MiB document
  ceiling yields on the order of 3.8 billion allocations from a single
  stored document. Reachability is the identical write-path bypass as the
  recursion finding above (same `crud.rs`/`ts_store.rs`/`admin.rs` chain,
  same two `decode()` call sites). An independent verifier re-derived the
  RLE arithmetic from source independently (not merely trusting the
  hunter's numbers), re-confirmed the write-path bypass down to the exact
  call site, and promoted the draft from `needs_validation` to `confirmed`
  on the same "fully source-settled" basis as the sibling finding.
  **Fix:** bound the per-block and per-column total decoded-value count
  against mongod's own bucket-size limits (at most ~1000 measurements per
  bucket), erroring out once exceeded; combined with the recursion fix
  above, this closes both amplification vectors through the same write-path
  gap.
  **Filed as a new issue** (duplicate search found no existing coverage).

- **No ownership check on `CREATE OR REPLACE FUNCTION` / `DROP FUNCTION` /
  `DROP OPERATOR` / `DROP CAST` / cascaded row-type-dependent drops: any
  authenticated SQL role can overwrite or destroy another role's routines,
  operators and casts** (medium/high/high).
  `secantusd-pg` implements real `must be owner of X` (42501) checks for
  views, schemas, databases, subscriptions, text-search configs/
  dictionaries, transforms, and operator classes/families — comparing
  `current_role_name()` against the object's stored `owner` before
  mutating or deleting it. That pattern is **entirely absent** for
  functions, operators and casts: `create_user_function`
  (`crates/secantus-pg/src/lib.rs:13798-13988`, handling `CREATE [OR
  REPLACE] FUNCTION`) unconditionally overwrites an existing routine of the
  same signature — silently reassigning `owner` to the caller
  (lib.rs:13877) — with no comparison to the prior owner; the `DROP
  FUNCTION` statement handler (lib.rs:42245-42578), `catalog_objects.rs::
  drop_operator` (162-193, despite `create_operator` writing an `owner`
  field at line 103 that `drop_operator` never reads), `casts.rs::drop_cast`
  (339-368), and the cascade helpers `drop_function_casts`/
  `operators_on_function` (casts.rs:580-651) and `row_type_depends.rs::
  drop_row_type_dependents` (320-337, reached via `DROP TABLE`/`VIEW ...
  CASCADE`) all delete the catalog row with **zero ownership check**. No
  generic dispatch-level privilege wrapper covers these statements either —
  each sibling object kind implements its own inline check, and functions/
  operators/casts simply never got one. An independent verifier
  specifically re-read two of the cited sibling checks (view drop, the
  `subscription_owner_check` pattern) to confirm the codebase really does
  have and use this pattern elsewhere — ruling out "ownership isn't
  enforced anywhere yet" as an alternative framing — and confirmed the
  `owner` field really is tracked (just not enforced) for functions and
  operators. The verifier judged the "stored script execution affecting
  other users" severity anchor applies even under invoker-rights execution,
  because the destructive `DROP`/overwrite capability alone, combined with
  the complete absence of a control this codebase otherwise implements
  consistently, defeats an explicit authorization boundary with real
  consequences.
  **Fix:** add the same owner-vs-`current_role_name()` check (superuser and
  role-membership bypass included) already used for views/schemas/
  subscriptions to `create_user_function`'s replace branch, the `DROP
  FUNCTION` handler, `drop_operator`, and `drop_cast` (gating `CREATE`/`DROP
  CAST` on superuser-or-type/function-ownership, matching PostgreSQL's own
  `CreateCast`/`RemoveCastById`); extend the same check to the cascade
  helpers, or at minimum to the root object a `CASCADE` originates from.
  **Filed as a new issue**, cross-referencing the same recurring pattern
  already tracked by open issue **#2135** (`CREATE`/`DROP ACCESS METHOD`
  missing the equivalent check) as a related-but-distinct instance, not a
  duplicate.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **The new in-memory time-series bucket catalog has no cap or eviction on
  the number of open/archived buckets it holds — an unauthenticated client
  can grow shared server memory without bound via distinct meta values**
  (medium/medium/medium).
  `crates/secantus-commands/src/bucket_catalog.rs` (new this window,
  commit `18f0700b`, RM-088) keeps one `Collection { open: Vec<Bucket>,
  archived: BTreeMap<...>, .. }` per bucket collection inside a single,
  process-wide `BucketCatalog`. `allocate()` (lines 944-996) unconditionally
  pushes a new `Bucket` onto `coll.open` whenever a measurement's series key
  — derived directly from the client-supplied `metaField` value — has no
  matching bucket, with **no cap check of any kind**. A bucket for a series
  that is never written to again meets none of `rollover_reason()`'s exit
  conditions and is never archived, closed, or evicted — it is retained,
  along with its `min`/`max` field-value copies, until the process restarts.
  The module's own doc comment discloses that mongod's real memory-
  threshold-based idle-bucket eviction is "Not modelled," and this exact gap
  is independently corroborated by the project's own open backlog item
  **RM-549** (with a decision from Joe, 2026-11-11, to build the eviction
  mechanism — open and unfixed at time of review). Before this window, no
  in-memory catalog existed at all (buckets were derived fresh from stored
  documents on every read); this is a **new** exposure, not a pre-existing
  gap newly reached. Since `require_auth` defaults to `false`, no
  credentials are needed to reach it. An independent verifier re-confirmed
  the absence of any cap in `allocate()`/`eligible_bucket()`/`Collection`,
  re-confirmed the catalog is a single process-wide instance, and
  independently re-derived the "new this window" claim from `git log`.
  **Fix:** implement the idle-bucket memory accounting and eviction RM-549
  already names as the direction to build; until it lands, a defensive hard
  cap on open+archived bucket count per collection is a cheap stopgap.
  **Filed as a new issue** (duplicate search found no existing coverage;
  cross-references open backlog item RM-549).

- **`delete`/`update`/`count`/`findAndModify` (and, to a lesser extent,
  `find`/`aggregate`) against a time-series collection's physical
  `system.buckets.<name>` namespace skip all time-series handling, the same
  way `insert` does — letting an ordinary writer corrupt bucket state in
  ways visible to other clients** (medium/medium/medium).
  The same root cause underlying both CRITICAL findings above — every
  command that decides whether to apply time-series semantics keys off the
  **client-given namespace's own** stored catalog options
  (`ts_store::layout_of`, ts_store.rs:26-32), and the physical bucket
  collection's options never carry the `timeseries` key that decision needs
  — also affects `delete` (crud.rs:1450), `update` (crud.rs:2227, unrestricted
  to the meta field unlike the logical-name path), `count` (crud.rs:1663),
  and `findAndModify`'s remove branch (findandmodify.rs:345), plus (lower
  severity, read-only) `aggregate.rs::collection_documents` (`$lookup`/
  `$graphLookup`/`$unionWith`/`distinct`) and `explain/order.rs::find()`
  (plain `find`). `admin::invalid_write_namespace`'s own comment claims
  `system.buckets.*` writes are "left to the existing timeseries handling" —
  which, as traced, does not actually gate any of these four write commands.
  Verified cross-client impact: a bypass delete can desync the in-memory
  `BucketCatalog` from stored state, surfacing an unexpected `WriteConflict`
  (code 112) to an *unrelated* client's later insert into the same
  collection (`bucket_catalog.rs::commit`, line 1521-1540); a bypass update
  can rewrite `control.min`/`control.max`/`data` outside the meta-only
  restriction, and because `ts_store` re-reads those fields fresh from
  storage on every call, a corrupted bucket produces wrong query results or
  decode errors for **any** later reader of the logical collection, not only
  the writer that made the change. An independent verifier re-traced every
  call site, independently confirmed the `aggregate.rs` and `explain/
  order.rs` extensions (the latter newly confirmed by the verifier itself,
  beyond what the post-wave critic had flagged as unconfirmed), and kept the
  medium/medium/medium severity: real but requires ordinary write
  credentials already held, and stops short of privilege escalation or data
  disclosure beyond the attacker's own grant.
  **Fix:** at each gate site, when the client-given name itself starts with
  the `system.buckets.` prefix, strip the prefix and re-run the time-series
  check against the **logical** collection name before falling back to
  ordinary CRUD; route the operation through the bucket-aware path if the
  logical collection is indeed time-series, or refuse it outright (matching
  mongod's own guidance against direct bucket manipulation); correct
  `invalid_write_namespace`'s comment to match whichever choice is made.
  **Filed as a new issue** (duplicate search found no existing coverage).
