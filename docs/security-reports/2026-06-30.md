### W1 — CVE-2026-53539: `python-multipart` 0.0.28 vulnerable to quadratic CPU DoS

**File:** `pyproject.toml` admin extra + `uv.lock`  
**CVE:** CVE-2026-53539 (GHSA-5rvq-cxj2-64vf) — High severity  

The locked `python-multipart` version is **0.0.28**, which is inside the vulnerable range `< 0.0.30`. The vulnerability is a quadratic-complexity DoS in `QuerystringParser` when processing `application/x-www-form-urlencoded` bodies containing semicolons. An attacker who can reach an admin endpoint that processes form data can hang the worker by sending a crafted body.

The admin extra's `pyproject.toml` floor is `>=0.0.9`, far below the patched version. Even if the current lockfile resolves a newer version in future `uv sync` runs, the floor should be bumped to enforce the safe minimum.

**Mitigating factor:** The admin UI is loopback-only with per-launch token auth, so an attacker must already be on the same host and know the session token. Severity is reduced but the DoS is still relevant against a same-host adversary.

**Fix:** Bump `python-multipart>=0.0.30` in the `[admin]` extra. Re-run `uv lock`.

### W2 — CVE-2026-48710 ("BadHost"): `starlette` 1.0.0 — Host-header auth bypass

**File:** `uv.lock` (admin extra transitive dep: `starlette==1.0.0`)  
**CVE:** CVE-2026-48710 — High severity  

The locked Starlette version is **1.0.0**, which is inside the vulnerable range `0.8.3 <= version < 1.0.1`. Starlette builds `request.url` from the raw HTTP `Host` header without RFC 9112 validation. An attacker can inject path separators (`/`, `?`, `#`) into the `Host` value to shift what `request.url.path` returns.

`TokenAuthMiddleware` in `src/secantus/admin/middleware.py` gates bypass prefixes (`/healthz`, `/static/`) on `request.url.path`:

```python
path = request.url.path
if any(path == p or path.startswith(p) for p in _BYPASS_PREFIXES):
    return await call_next(request)  # ← no token check
```

By sending `Host: 127.0.0.1:PORT/healthz?t=`, `request.url.path` returns `/healthz`, bypassing the token check for arbitrary admin endpoints. The actual path (e.g. `/api/collections`) is then served unauthenticated.

**Mitigating factor:** The admin runs loopback-only (`127.0.0.1`) and is embedded in a `pywebview` window. A local adversary (same user, same host) can reach the port; the token was designed exactly to block "a malicious process running as the same user" (per `middleware.py` docstring). The BadHost bypass undermines this protection.

**Fix:** Constrain `starlette>=1.0.1` in the `[admin]` extra (directly or via `fastapi`). Re-run `uv lock`.

### W3 — Stored XSS in admin geo page via `| safe` on BSON document data

**File:** `src/secantus/admin/templates/pages/geo.html:51`  
**Related:** `src/secantus/admin/routers/extras.py:155`

The geo viewer page injects document data into a `<script>` block using Jinja2's `| safe` filter:

```html
<script>
(function() {
  const features = {{ features_json | safe }};
```

`features_json` is generated by:

```python
features = _extract_features(docs, geo_field)
features_json = json_util.dumps(features)
```

`_extract_features` reads `_id` values and geometry coordinates directly from database documents. `json_util.dumps` serializes BSON types to JSON — but JSON strings are not HTML/script safe. A document with a string `_id` (or a string field inside its geometry) containing `</script>` will close the script block and inject arbitrary JavaScript:

```
db.locations.insertOne({_id: "</script><script>alert(document.cookie)//", loc: [0,0]})
```

Opening the geo page in the admin UI executes the injected script. With the `pywebview` embedding, this gives access to native Python bindings exposed via `js_api`.

**Mitigating factor:** The admin UI requires auth (per-launch token). An attacker must first compromise the database to insert the malicious document, then wait for an admin user to visit the geo page.

**Fix:** Replace `| safe` with a properly-escaped approach. Use `tojson` or escape `</script>` sequences after `json_util.dumps`:

```python
import re
# Escape </script> to prevent premature script tag closure
features_json = re.sub(r"</script>", r"<\\/script>", json_util.dumps(features))
```

Or render via a `data-*` attribute rather than directly into `<script>`.

### W4 — OP_QUERY with no NUL byte drops connection silently (no error reply)

**File:** `src/secantus/wire.py:149`

```python
name_end = buf.index(b"\x00", offset)
```

`buf.index(b"\x00", offset)` raises `ValueError` when no NUL byte is present after `offset`. Unlike `bson.InvalidBSON` and `_BodyBoundsError`, `ValueError` is **not** caught by `read_message`'s handler:

```python
except (bson.InvalidBSON, _BodyBoundsError) as exc:
    raise MalformedBodyError(header, ...) from exc
```

The `ValueError` propagates to `_handle_client`'s outer `except Exception:` block, which logs a traceback and terminates the connection without sending a wire-level `{ok: 0}` error reply. The correct behaviour (matching `mongod`) is to return a `BadValue` reply and keep the connection alive.

A malicious OP_QUERY frame (opcode 2004) with no NUL byte in the body terminates the connection — not a server crash, but also not the correct wire behaviour. This affects any client that sends OP_QUERY; the legacy handshake path is the primary use-case.

**Fix:** In `_parse_op_query`, replace bare `buf.index(b"\x00", offset)` with a bounds-checked call that raises `_BodyBoundsError` when no NUL is found:

```python
try:
    name_end = buf.index(b"\x00", offset)
except ValueError:
    raise _BodyBoundsError("OP_QUERY: collection name not NUL-terminated")
```

### W5 — GitHub Actions: no commit-SHA pinning on high-privilege workflows

**Files:** `.github/workflows/publish.yml`, `.github/workflows/security-review.yml`, `.github/workflows/wheels.yml`, `.github/workflows/rust-wheels.yml`, et al.

Every `uses:` entry across all workflows is pinned to a **moving tag**, not a commit SHA:

| Action | Workflow | Risk |
|--------|----------|------|
| `pypa/gh-action-pypi-publish@release/v1` | `publish.yml` | Publishes PyPI wheel; sees `id-token: write` |
| `anthropics/claude-code-action@v1` | `security-review.yml`, `claude.yml`, `claude-code-review.yml` | `contents:write` + `pull-requests:write` + `issues:write` |
| `pypa/cibuildwheel@v2.21` | `publish.yml`, `wheels.yml` | Executes the vendored-WT build system |
| `actions/checkout@v4`, `@v5` | All | Checks out code |
| `astral-sh/setup-uv@v4` | Multiple | Runs uv install; `PATH` injection vector |
| `dtolnay/rust-toolchain@stable` | Multiple | Installs Rust toolchain |
| `PyO3/maturin-action@v1` | `rust-wheels.yml` | Builds Rust extension wheel |
| `softprops/action-gh-release@v2` | `release-binaries.yml` | Uploads release assets |

A tag can be silently rewritten to point to a malicious commit with no visible diff in the workflow YAML. The publish pipeline actions have access to `id-token: write` (OIDC PyPI token) and produce the binary wheel that ships to consumers.

**Fix:** Pin each `uses:` to the **commit SHA** that the current tag resolves to. Example: `actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af68 # v5`. Use Dependabot or `pin-github-action` tooling to automate SHA management. Prioritise `pypa/gh-action-pypi-publish`, `pypa/cibuildwheel`, and `anthropics/claude-code-action`.

## 🟡 INFO (Best-practice recommendations)

### I1 — `release-binaries.yml`: workflow_dispatch `tag` input expanded inline in shell

**File:** `.github/workflows/release-binaries.yml:76`

```yaml
run: |
  if [ "${{ github.event_name }}" = "workflow_dispatch" ]; then
    tag="${{ github.event.inputs.tag }}"
```

`github.event.inputs.tag` is expanded directly into the shell `run:` block. If a maintainer enters a value containing shell metacharacters (e.g., `$(id)`, backticks), they execute as the workflow runner. Only maintainers can trigger `workflow_dispatch`, but the safe pattern is to pass untrusted inputs via `env:` and reference as `$VAR`.

**Fix:**
```yaml
env:
  TAG_INPUT: ${{ github.event.inputs.tag }}
run: |
  tag="${TAG_INPUT:-${GITHUB_REF_NAME}}"
```

### I2 — Admin token comparison is not constant-time

**File:** `src/secantus/admin/middleware.py:52` and `:99`

```python
if presented != self._token:   # line 52 (dispatch)
return presented == expected   # line 99 (websocket)
```

Python's `str.__eq__` is not constant-time. An attacker on localhost could mount a timing oracle to recover the admin token bit by bit. The token is 32 bytes of `secrets.token_urlsafe(32)` (high entropy), but the comparison itself should be constant-time.

**Fix:** Use `hmac.compare_digest(presented, self._token)` in both places.

### I3 — No per-connection cursor limit

**File:** `src/secantus/cursors.py`

`CursorRegistry` enforces a global `max_cursors=10_000` cap, but there is no per-connection limit. A single attacker connection can open cursors up to the global cap (or until OOM), starving all other connections of cursor slots. This is most relevant against an unauthenticated server or one where the attacker is already authenticated.

**Fix:** Track cursor count per connection-id and enforce a per-connection cap (e.g., 500 cursors per connection).

### I4 — `$regex` residual ReDoS risk despite pattern-length cap

**File:** `src/secantus/query.py:649`

A 1000-char pattern length cap (`_MAX_REGEX_PATTERN_LEN`) blocks the largest class of ReDoS patterns but does **not** protect against short catastrophically-backtracking patterns on long input strings. For example, `(a+)+$` (7 chars, far under cap) applied to a 30-char string like `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaab"` causes exponential backtracking that can hang the worker thread for seconds or longer.

Python's `re` module has no match timeout. The `lru_cache` caches the compiled pattern but not the match itself, so repeated lookups against long strings still incur match-time cost each time.

**Fix options (in order of preference):**  
1. Use the `regex` PyPI package (drop-in `re` replacement with `timeout=` parameter).  
2. Pre-screen strings for catastrophic-backtracking potential (complex heuristic).  
3. Document the known limitation in the threat model section of `CLAUDE.md`.

  contents: write
  pull-requests: write

`id-token: write` enables OIDC token minting for the workflow. **Fix:** Remove `id-token: write` from `security-review.yml`.
