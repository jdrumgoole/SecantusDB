## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Uncapped Cartesian-product probe expansion in `scan_index_for_id_keys` —
  ordinary-privilege remote OOM/hang via an array-equality `find` against a
  compound index** (high/high, overall high, confidence high; **issue
  #2954**). `scan_index_for_id_keys` (`crates/secantus-storage/src/lib.rs:23924-23974`,
  entirely new in this diff window) builds a full Cartesian product of probe
  key combinations whenever a filter value is `Bson::Array`: for `k`
  array-valued fields it materializes `2^k` `Vec<Bson>` combinations in
  memory **before any WiredTiger cursor opens**, with no size cap and no
  fallback. Its caller `try_compound_eq_id_keys` (`lib.rs:24488-24542`) and
  `route_index_id_keys` (`lib.rs:23486-23492`) admit `Bson::Array` filter
  values into this path with no type restriction. The **only** gate in the
  whole chain is `crates/secantus-commands/src/admin.rs:3646`'s 32-field
  compound-index cap (mirroring mongod's own limit) — nothing bounds how many
  of those 32 fields may later carry array values in a query. An ordinary
  client with normal `createIndex` + `find` privileges — no administrator
  role — can create such an index and issue one `find` with array-equality
  on, say, 25-32 fields (an entirely ordinary query shape, e.g. multi-tag
  search) to force on the order of 33 million to 4.3 billion eager
  allocations in the request-handling thread, exhausting memory or hanging
  the single shared `secantusd-mdb` process for every connected client. Real
  `mongod` bounds the equivalent explosion via `internalQueryMaxScansToExplode`
  (default 200), falling back to a collection scan past that cap; this
  codebase has no equivalent throttle on this path (confirmed by a
  crate-wide grep — the only matching string, `maxScansToExplodeReached` in
  explain output, is a hardcoded `false` that gates nothing).
  **Independently confirmed three separate times** — the original hunter, a
  post-wave coverage critic, and a fully independent verifier with no access
  to either prior agent's reasoning — all reached the identical trace and
  severity by reading the current source directly, and the critic/verifier
  additionally confirmed this is genuinely new (the pre-diff version of this
  function had no array handling at all) and distinct from the closest
  existing tracked issue, #2763 (a different function, `db_check.rs::doc_keys()`,
  gated behind a separate `dbCheck` administrator privilege). This project
  already has a working fix pattern for exactly this bug class:
  `MAX_COMPOUND_KEYS = 10_000` (`lib.rs:1854`), reused by two *other*
  functions (`index_key_variants()` at `lib.rs:4459-4530`, `reference_keys()`
  at `lib.rs:18390`) but not by this one. **Fix:** reuse `MAX_COMPOUND_KEYS`
  inside `scan_index_for_id_keys`'s probe-building loop
  (`lib.rs:23939-23958`), breaking out once the running combination count
  would exceed the cap and falling back to a filter/collection scan for the
  remainder, mirroring `index_key_variants()`'s existing pattern exactly.
  **Filed as new issue #2954.**

## 🟡 INFO (Best-practice recommendations)

### New this cycle

- **`row_key` hashes a clustered collection's client-controlled `_id` bytes
  with a fixed (non-randomized) `DefaultHasher`, making its lock-bucket key
  predictable** (medium/low, overall informational, confidence high; not
  filed as a dedicated issue per this review's CRITICAL/WARNING-only filing
  rule). `row_key` (`crates/secantus-storage/src/lib.rs:705-715`, new in this
  diff's clustered-collection work) hashes `RecordId::Bytes` via
  `std::collections::hash_map::DefaultHasher::new()`, which — unlike
  `HashMap`'s `RandomState` — uses a fixed, non-randomized SipHash key, so a
  client that controls a clustered collection's `_id` bytes could in
  principle precompute colliding values. **Scored informational, not
  low/medium**, because two independent traces of the full locking path
  (`note_row` → `share_locks::write_blocked`, `relock_row`, `lock_matching`)
  found every use is a non-blocking, fail-fast check (`Err(WriteConflict)`
  returned immediately, no `Condvar`/park/wait primitive reachable from this
  code) and the actual row read/write always keys by the full `RecordId`,
  never by this hash — so a deliberately engineered collision can only cause
  spurious write-conflict aborts (forced retries) between unrelated rows,
  never a deadlock and never data mixing, exactly as the code's own comment
  states. **Fix (optional hardening, not required for correctness):** use a
  keyed/randomized hasher (e.g. seed a per-process `RandomState`-style key at
  startup) if bucketed lock contention from a maliciously-colliding `_id` set
  is judged worth closing; low priority given the bounded, self-correcting
  impact.
