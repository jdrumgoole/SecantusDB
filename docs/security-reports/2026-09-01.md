## 🔴 CRITICAL (Immediate action required)

Nine carried forward from 2026-08-31, re-confirmed present and unfixed, plus
**three new**:

- **#1037** — `src/secantus/query.py:874-928` (`_resolve_bitmask`): the
  `$bitsAllSet`/`$bitsAnySet`/`$bitsAllClear`/`$bitsAnyClear` array-argument
  branch still has no upper bound on the bit-position integer (`mask |= 1 <<
  bit`), forcing CPython to allocate and touch gigabytes of real memory from
  an attacker-chosen multi-billion `bit` in an ordinary filter. `query.py`
  did not change this window. Not fixed.
- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`):
  a `message_length = -1` wire frame still sign-extends to `usize::MAX` under
  the lower-bound check and still compares as negative under the upper-bound
  check (`MAX_MESSAGE_SIZE: i32 = 48_000_000` at line 57, a signed
  comparison), so both guards pass and `crates/secantus-server/src/lib.rs:
  553-562`'s `vec![0u8; body_len]` aborts the whole Rust server from one
  unauthenticated 16-byte frame. Re-confirmed this window that the preceding
  `alloc_budget.acquire(body_len)` (line 561) does **not** block a lone
  oversized request — its loop condition (`while *used != 0 && *used + n >
  self.cap`) is false when `used == 0`, by design, so a single malicious
  frame sails through the budget check too. File unchanged this window. Not
  fixed.
- **#996** — `src/secantus/sql/authz.py:42-63` (`_command_privilege`): no
  `"CREATE_PROCEDURE"`/`"DROP_PROCEDURE"`/`"CALL"` branch, while `planner.py`

  4000) and `engine.py` dispatches all three (lines 6279/6282/6285) with no
  authorization gate. Both files unchanged this window. Not fixed.
- **#909** — `src/secantus/sql/plpgsql.py`: `_open_cursor` (line 696 →
  `_engine.materialize_cursor(...)` at 711), `_run_into` (line 771 →

  `_engine._run_statement(...)` at 789) all still call their engine entry
  points directly, bypassing `_dispatch`/`authz.authorize`. File unchanged

  due to intervening — unrelated — edits, re-located and confirmed). Not
  fixed.
- **#947** — `src/secantus/sql/planner.py:12265` still builds
  `exp.Command(this="MULTIDROP_TABLE", expression=exp.Literal.string(sql))`
  for `DROP TABLE a, b, c` with no matching `_command_privilege` branch →
  unauthorized multi-table drop. Site unchanged this window. Not fixed.
- **#948** — `src/secantus/sql/engine.py:2849-2870` (`_execute_statement`)

- **#1117 / #1161 (C7/C9)** — Unbounded recursion in four Rust
  error-message renderers, all re-confirmed still present, still with no
  depth guard: `crates/secantus-commands/src/argtypes.rs:750`
  (`render_stage_value`), `crates/secantus-core/src/update.rs:1142`
  (`render_value`), `crates/secantus-core/src/aggregate.rs:264`
  (`redact_list`) and `:286` (`render_value_compact`), plus
  `crates/secantus-commands/src/bulkwrite.rs:67,121` (both calling
  `render_stage_value`). A repo-wide grep for `max_depth`/`MAX_DEPTH`/
  `recursion_limit`/`nesting` across `crates/` again found nothing but
  `$graphLookup`'s unrelated `maxDepth` *option*. The systemic fix
  recommended as the #1 priority in both prior reports (a BSON

  error message.

- **C10 (new)** — **The new Rust PostgreSQL server
  (`crates/secantus-pgserver`) has no authentication and no
  authorization/privilege checking of any kind.**
  `crates/secantus-pgserver/src/lib.rs:19,163` registers
  `impl NoopStartupHandler for PgHandler` — `pgwire`'s explicit no-auth
  handler — and `Cargo.toml:20` pulls in the `pgwire` dependency with
  `default-features = false, features = ["server-api"]`, so no SCRAM/MD5
  auth module is even compiled in. `main.rs:14` hardcodes the target
  database to `"postgres"` regardless of what the client's startup packet
  requests (`PgHandler::new(storage.clone(), "postgres")`), and there is no
  equivalent anywhere in these three crates of the Python SQL engine's
  `sql/authz.py` `_command_privilege` dispatch — a repo-wide grep across
  `crates/secantus-pgserver`, `crates/secantus-pgplan`, and
  `crates/secantus-pgcatalog` for `auth`/`privilege`/`role`/`grant` returns
  only the two `NoopStartupHandler`/`StartupHandler` trait references. Every
  statement kind this window's planner supports — `CREATE TABLE`, `INSERT`,
  `SELECT`, aggregates, `UPDATE`/`DELETE`, `DROP TABLE`, transaction control
  — reaches the shared `Storage` directly from `execute()`
  (`lib.rs:259-597`) with no privilege gate anywhere in front of it. This is
  categorically worse than the five standing SQL-authz-dispatch-gap
  findings on the *Python* SQL engine (`#909`/`#947`/`#948`/`#996`/`#1118`,
  each "one statement kind slips past an otherwise-real gate") — here there
  is no gate to slip past, for any statement kind, on a server that shares
  its on-disk `Storage` with the rest of the deployment. **Mitigating
  factor, independently confirmed by direct read:** `main.rs:14` defaults
  the bind address to `127.0.0.1:25434`, loopback-only, not `0.0.0.0` — so
  this is not remotely reachable out of the box, and the module doc
  comment at `lib.rs:1-9` explicitly frames the whole crate as a
  "P1 vertical slice" with "breadth is P5's problem," suggesting auth may
  be an intentionally deferred, not overlooked, later phase. Still: as
  shipped today, any process on the same host (or across the network, the
  moment an operator points the second CLI argument at a non-loopback
  address — which `main.rs` does not validate or warn against) gets full
  CRUD + DDL over every table in the shared store with zero credentials.
  This should be tracked explicitly — e.g. a line in `tasks/backlog.md` /
  `tasks/rust-pgserver-plan.md` making the "no auth yet" posture and its
  bind-address dependency an explicit, visible gate before any future work
  makes the server easier to reach — rather than left to be inferred from
  the absence of an authz module.

- **C11 (new)** — **`crates/secantus-commands/src/argtypes.rs:989`
  (`expression_problem`), and its three helpers `problem_in_let` (1030),
  `problem_in_binding` (1046), `problem_in_reduce` (1061), recurse on
  attacker-controlled `Bson::Array`/`Bson::Document` nesting with no depth
  cap — and, unlike the #1117/#1161 renderers, this runs on the ordinary
  success path of `find`, `insert`, `update`, `delete`, `distinct`, and
  `findAndModify`, not only when constructing an error message.** Confirmed
  by direct read: `expression_problem_in_filter` (`argtypes.rs:1087`) and
  `expression_problem_in_pipeline` (`argtypes.rs:1148`) are called
  unconditionally, before any document is evaluated, from
  `crates/secantus-commands/src/find.rs:278`, `crud.rs:444` (insert),
  `crud.rs:529` (update), `crud.rs:864` (delete), `distinct.rs:33`, and
  `findandmodify.rs:52`, plus from `aggregate.rs:125` via
  `expression_problem_in_pipeline`. **Trigger:** an ordinary `find` or
  `update` whose filter contains a deeply nested `$expr` (well within the
  16 MB BSON document-size limit — nesting depth, not document size, is
  the exhaustion vector) recurses the Rust stack once per nesting level and
  aborts the whole process — taking down every other connection on the
  Rust server, not just the offending one. This function did not exist
  before this window (new file addition, `argtypes.rs` +642 lines this
  cycle) — it is a fresh instance of the #1117 root cause on a
  substantially more exposed surface than the two originally-flagged
  renderers.

- **C12 (new)** — **`crates/secantus-core/src/aggregate.rs:392`
  (`may_name_runtime_error`) and its two nested helpers,
  `has_defaultless_switch` (line 393) and `has_numeric_guard` (line 409,
  which itself calls `collect_numeric_guard` at line 606 and, via a
  separate call site, `switch_unmatched_fault`'s `walk` at line 740), all
  recurse on the client-supplied aggregation pipeline SPEC with no depth
  counter.** Confirmed by direct read: `may_name_runtime_error` is called
  unconditionally on the success path of every `aggregate` request from
  `crates/secantus-commands/src/aggregate.rs:887`, before pipeline
  execution begins — its own doc comment even notes "this walks the
  pipeline SPEC, never the documents, so it is proportional to the query
  rather than to the data," which is exactly the property that makes an
  attacker-controlled *query* shape (rather than data volume) the
  exhaustion vector. **Trigger:** `aggregate([{$project: {x: <a `$add`
  expression nested thousands of levels deep, containing anywhere a
  `$switch` with no default or a numeric-guard operator such as `$sqrt` at
  the leaf>}}])` overflows the stack while merely deciding whether the
  pipeline *might* raise a runtime error — no document needs to exist in
  the target collection. This is a second, independent fresh instance of
  the #1117 root cause this window, on the Mongo Rust server's normal
  aggregation path rather than an error-rendering path.

  **C10, C11, and C12 make this cycle's total of fresh CRITICALs three, on
  top of the two fresh instances (`render_value_compact`/`redact_list`,
  plus two new `bulkwrite.rs` call sites) already tracked under
  #1161/C9 from yesterday. The unbounded-recursion bug class is now five
  fresh call sites deep across two review cycles, on both the Mongo Rust
  server and the brand-new PG Rust server, with the systemic fix (a single
  BSON/AST nesting-depth cap enforced at decode/parse time) still not
  built anywhere.**

- **W12 (new)** — **The new PG server has no idle/read timeout and no
  connection-count cap.** `crates/secantus-pgserver/src/main.rs:26-40`: the
  accept loop spawns an unbounded `tokio::spawn` per accepted socket with
  no `Semaphore`, no max-connections limit, and no timeout wrapped around
  `pgwire::tokio::process_socket`. A client that opens a connection and
  never completes (or very slowly trickles) the startup packet occupies a
  task/socket indefinitely, with nothing bounding how many such connections
  can accumulate. Given **C10** (no auth), this is reachable by anyone who
  can reach the port — a real resource-exhaustion vector (FD/memory growth
  over time), lower severity than C10-C12 because it needs sustained
  effort rather than one crafted request.
- **W13 (new)** — **The new PG server's `SELECT`/aggregate path loads the
  entire matched result set into memory before applying `ORDER BY`/
  `OFFSET`/`LIMIT`/the extended protocol's `max_rows`.**
  `crates/secantus-pgserver/src/lib.rs:305-364` (`Statement::Select`) and
  `:428-560` (`Statement::Aggregate`) call `storage.find_matching(...)`
  first, fully decoding every matching row into a `Vec<Document>`
  (`:316-320`, `:433-437`) **before** any row-count bound is applied
  (`:322-340`). A `SELECT * FROM t` (or any query the planner can't push a
  bound into) against a large table reads and decodes the whole table into
  RAM regardless of how small a client-requested `LIMIT` is. Combined with
  **C10** (no auth) and the fact that `CREATE TABLE`/`INSERT` are equally
  unauthenticated, any anonymous connection can create such a table and
  then trigger this.
- **W14 (new)** — **Storage-layer error text, including the raw

  below) — this is an unfiltered internal-error passthrough, not a crash —
  but combined with **C10**'s lack of auth, it hands any connection
  whatever detail WiredTiger's own error strings happen to contain. Lower
  severity: information disclosure of engine internals, not credentials or
  code execution.

- **I15 (new)** — **Decimal128 arithmetic added this window bypasses
  pre-existing domain guards typed to `(int, float)` only, in
  `src/secantus/expressions.py`, producing an uncaught internal exception
  on specific inputs — safely caught by `commands.py`'s dispatch catch-all
  (~line 9828, confirmed this window handles it the same way it already
  handles `RecursionError`), so no crash/traceback-leak, just a generic
  error instead of mongod's real error code:**
  - `_epoch_millis_to_date` (line 3670, called from `$toDate`/`$convert`

    `datetime.fromtimestamp()` — `{$toDate: NumberLong("9223372036854775807")}`

    `OverflowError`. Sibling int/long conversions a few lines above already
    guard NaN/Infinity; this target didn't get the same guard.
  - `$sqrt`/`$ln`/`$log`/`$log10` (lines ~1185, ~1253, ~1287/1293/1312):
    domain guard is `isinstance(v, (int, float)) and v < 0`, so a

  gets a generic 500 instead of the right mongod error code" — the same
  "safe by construction" pattern this codebase already relies on for
  Python-side recursion (**I13**). Not filed as an issue; worth folding
  into the fidelity sweep's own backlog rather than a security tracker.
- **I16 (new)** — `src/secantus/expressions.py:3463`
  (`_parse_float_string`) lacks the digit-length cap its siblings
  (`_parse_int_string`, `_parse_decimal_string`) carry against CPython's

  under 1ms in this review — not currently exploitable, CPython's `float()`
  parser doesn't have the same quadratic-string-length pathology as
  `int()` — but worth closing for consistency with its siblings.
- **I17 (new)** — The new PG-server dependency tree
  (`crates/secantus-pgserver/Cargo.lock`, 236 packages, 75 not previously
  in the workspace) pulls in `pg_query` 6.2.0, which compiles a large
  vendored copy of PostgreSQL's own C parser (`libpg_query`) via
  `bindgen`+`cc` at build time — a meaningfully larger native/FFI surface
  added to the build pipeline, parsing untrusted SQL text through real
  PostgreSQL C parser code. No known CVE/RUSTSEC advisory found for
  `pg_query`, `pgwire` 0.31.1, or `tokio`/`mio`/`nix`/`rustix` at their
  pinned versions via WebSearch this cycle. The existing `cargo-audit.yml`
  gate does correctly cover this new lockfile (confirmed: its glob
  `crates/*/Cargo.lock` matches `crates/secantus-pgserver/Cargo.lock`), so
  this is the right ongoing control — flagging only as an architecturally
  significant new attack-surface note, not a specific vulnerability.
  Separately: `rust_decimal` (not the name-squatted `rustdecimal`) is
  confirmed the legitimate crate at its current latest release.
- **I18 (new)** — Neither `crates/secantus-pgserver` nor its Cargo.lock is
  wired into the shipped Python wheel (`CMakeLists.txt` has zero references
  to `pgserver`; only `_secantus_storage`/`_secantus_server` are built) —
  correctly a wholly separate, standalone `secantusd-pg` binary, consistent
  with CLAUDE.md's two-separate-servers model (now effectively three:
  Python Mongo, Rust Mongo, Rust Postgres, with only the first two entering
  the wheel). One minor note: `pyproject.toml`'s sdist include list ships
  the whole `crates/` tree (intentional, so the Rust storage engine is
  sdist-buildable), which means the new pgserver source plus its 2429-line
  `Cargo.lock` now rides along in the sdist even though never invoked by
  the packaging pipeline — harmless, mild sdist bloat, not a regression
  worth urgent action.
- **I19 (new)** — The new PG server does not wrap statement execution in
  `std::panic::catch_unwind` the way the existing Rust Mongo server does
  (`crates/secantus-server/src/lib.rs:853-866`, which turns a panic into a
  clean wire-level error "matching the Python server's dispatch-level
  catch-all"). No panic reachable from wire input was actually found in
  this crate this cycle (see CLEAN below), and a panic inside a
  `tokio::spawn`'d task is caught by Tokio's own task harness and only
  drops that one connection rather than the whole process — so the
  practical effect of a hypothetical future panic here is an abrupt
  connection drop with no PG `ErrorResponse`, worse UX than the Mongo
  server but not a process-wide DoS. Worth matching the existing pattern
  before this crate grows past its current P1 scope.

  What's new this cycle is a step change in surface area rather than a new

  landed this window and inherits the two dominant bug classes already
  seen on the other two servers — **no privilege/authz layer at all**
  (worse than the Python SQL engine's "gate with five known holes," since
  here there is no gate) and **unbounded recursion on client-controlled
  nesting depth** (two more fresh instances, on top of yesterday's four,
  now eight total sites across two Rust crates in two review cycles, with
  the systemic depth-cap fix recommended twice now still not built
  anywhere). The mitigating factor for the new server is that it defaults
  to loopback-only and is explicitly scoped as an early "P1 vertical
  slice" — but as shipped today it is reachable by anything on the same
  host with zero credentials, which is a materially different posture from
  every other server in this codebase.
- **Top 3 priorities for the team:**
  1. **C10 — decide and document the PG server's authentication posture
     explicitly, before it grows past its current loopback-only, single-host
     P1 scope.** Either build a real auth/privilege layer (mirroring or
     reusing the Python SQL engine's `sql/authz.py` model) before any future
     work makes the bind address easier to widen, or add an explicit,
     visible guard (a startup warning, a `tasks/rust-pgserver-plan.md` gate)
     that stops the server from binding to a non-loopback address until auth
     exists. This is now the single largest-blast-radius finding in this
     report's history — a full CRUD+DDL surface with zero credentials — even
     though today's default bind address keeps it from being remotely
     exploitable out of the box.
  2. **Build the systemic recursion-depth-cap fix once, at BSON-decode /
     AST-parse time, on both Rust servers — C11, C12, #1117, #1161 (four
     sites in the Mongo server) all share one root cause, and it is now
     also present in the brand-new PG planner's `lower_where`/`lower_negated`

     the identical unbounded-recursion *pattern* in `crates/secantus-pgplan/

     shrinking one.
