## 1. Dependency Vulnerability Check

Re-swept via WebSearch (all queries dated for the current 90-day window).

- **New this cycle — real-`mongod` CVE batch (CVE-2026-9740,
  CVE-2026-11933, CVE-2026-13077, CVE-2026-13072):** a MongoDB Server patch
  round (fixed in 7.0.39 / 8.0.28 / 8.2.12 / 8.3.7) addressing:
  - **CVE-2026-9740** — a stack overflow in mongod's BSON validator, in the
    `BSONColumn` interleaved-reference handling used by time-series bucket
    compression (subtype-7 binary `BSONColumn` format, decoded internally by
    mongod's storage layer).
  - **CVE-2026-11933** — a use-after-free in mongod's server-side
    JavaScript engine (`$where`/`$function`/`$accumulator` with `mode:
    "js"`), reachable via a crafted query and able to leak process memory or
    crash the server.
  - **CVE-2026-13077** — an out-of-bounds heap read through malformed
    `BSONColumn` data (same compressed time-series format as
    CVE-2026-9740).
  - **CVE-2026-13072** — a DoS in mongod's "compute mode" via insufficient
    BSON validation, causing memory corruption.

  **Applicability assessed, all four not applicable:**
  - `BSONColumn` (CVE-2026-9740, CVE-2026-13077) is mongod's internal
    columnar storage format for time-series buckets, implemented in
    mongod's C++ storage engine — SecantusDB has no time-series collection
    support and no `BSONColumn` decoder anywhere in `src/secantus/` or
    `crates/` (confirmed by grep: zero hits for `BSONColumn`/`bsoncolumn`
    across both trees). Documents are decoded exclusively via pymongo's
    `bson` module (`bson.decode`) on the Python side and a from-scratch
    Rust BSON reader on the Rust side — neither implements the
    `BSONColumn` subtype. Not reachable.
  - Server-side JavaScript (CVE-2026-11933) is explicitly out of scope —
    re-confirmed this cycle (§6 below) that no `eval`/`exec`/`compile`/
    `__import__` is reachable from a query or pipeline document, and
    `$where`/`$function`/`$accumulator` with `mode: "js"` are not
    implemented at all (unknown-operator/unknown-command error, not a JS
    evaluator). No JS engine exists to have a use-after-free in.
  - "Compute mode" (CVE-2026-13072) is a mongod query-execution internal
    with no analogue in SecantusDB's pure-Python/Rust operator engines.
  - Filed as new **CLEAN** entries (below), not WARNING/INFO — same
    treatment as the already-tracked MongoBleed (CVE-2025-14847) check from
    2026-08-06, which itself was re-confirmed not applicable this cycle too
    (SecantusDB still implements no wire compression:
    `grep -n "zlib|snappy|compress" src/secantus/wire.py
    src/secantus/commands.py` returns nothing).
  - Worth noting for context, not as a finding: this batch is a reminder
    that mongod's own BSON-adjacent attack surface keeps growing in areas
    (time-series compression, JS evaluation) that SecantusDB deliberately
    doesn't implement — the "surrogate, not full emulator" scoping in
    `CLAUDE.md` continues to pay off as a security property, not just a
    scope simplification.
- **`cryptography` 48.0.0` (dev-only, transitive via `trustme`):**
  re-confirmed unchanged from 2026-08-06 — `uv.lock` still pins `48.0.0`,
  one minor behind `49.0.0` (which fixes CVE-2026-69248 and
  CVE-2026-69249, both published 2026-08-03). Re-confirmed not reachable:
  `cryptography` is dev-only (absent from `pyproject.toml`'s base

  `cryptography` found this cycle beyond the two already tracked.
- **`pymongo`/`bson` 4.17.0`:** re-checked, still latest (2026-04-20

- **RUSTSEC / `pyo3` / `tokio`:** no advisory newer than the ones already

- **WiredTiger (vendored submodule, mongodb-7.0.33 pin):** no CVE search

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open — 18th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:5123` and `:5222` — re-read
both lines directly this cycle; content and line numbers unchanged
(`ctx.oplog.lock().unwrap().live_count` in the prune-sizing path and the
post-sweep count decrement).

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **eighteen** consecutive review cycles.

**Recommendation:** unchanged — convert both sites to
`ctx.oplog.lock().unwrap_or_else(|e| e.into_inner())`.

### W2 (carried forward, still open — 15th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` holds

**File:** `src/secantus/storage.py:6071` (`drop_index`) and `:6188`
(`drop_all_indexes`) — re-read both method bodies this cycle; each still
opens only `with self._lock:`, never `self._coll_lock(db, coll)`. Line
numbers unchanged from 2026-08-06 (no intervening commits).

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.

### W3 (carried forward, still open — 8th consecutive cycle) — `_emit_oplog`'s bare-autocommit path can permanently freeze the change-stream visible tail on a write error

**File:** `src/secantus/storage.py:2409` (`def _emit_oplog`) — re-read the
method this cycle; the bare-autocommit deregistration (`self.
_deregister_minted(...)` followed by the condvar notify at the end of the
method) still has no surrounding `try/finally`, unlike `_batch_transaction`
and `commit_user_transaction`'s flush paths.

Already tracked as open issue [#714](../../../../issues/714), filed
2026-07-31, unfixed across an 8th consecutive cycle.

**Recommendation:** unchanged — wrap the mint-to-deregister region of the
bare autocommit path in `try/finally`.

### W4 (carried forward, still open — 6th consecutive cycle) — Rust user-transaction async-oplog buffer (`pending_async`) has no size/count cap

**File:** `crates/secantus-storage/src/lib.rs:148`
(`UserTransactionHandle::pending_async: Vec<(OplogEntry, Option<Vec<u8>>)>`)
— re-confirmed unchanged; grep for all `pending_async` sites this cycle
shows the same six references as 2026-08-06, no new bound added.

Already tracked as open issue [#750](../../../../issues/750), filed
2026-08-02, unfixed across a 6th consecutive cycle.

**Recommendation:** unchanged — add a size/count ceiling on `pending_async`.

### W5 (carried forward, still open — 5th consecutive cycle) — `validate.yml`'s `plan` and `validate` jobs have no `permissions:` block

**File:** `.github/workflows/validate.yml` — re-confirmed by fresh grep

Already tracked as open issue [#755](../../../../issues/755), filed

**Why this still matters, calibrated to actual risk:** unchanged —
