The new SQL trigger feature (`58d53adb`) introduced a genuine **new CRITICAL
finding (C5)**: SQL statements executed from inside a plpgsql trigger body
run through the engine's execution core directly, never through the
per-statement RBAC gate — a full authorization bypass for any table a
trigger's author chooses to touch, fired by an unrelated, minimally-privileged
session's ordinary `INSERT`. This is the fifth instance of the recurring
"authorize only the primary target, not everything the statement/pipeline/
trigger actually touches" bug class this project has now produced, and the
most severe: earlier instances skipped a *secondary* check; this one skips
*all* checking for the nested statement.

## 4. Storage-engine & FFI safety (WiredTiger)

`src/secantus/storage.py` (+57/-39) — both changes strengthen, not weaken,
error handling:

- **W3 fix (`_emit_oplog`):** the mint-to-deregister region is now wrapped in
  `try/finally` (was unguarded sequential code). The `finally` block
  deregisters the minted seq range and notifies `_oplog_cv` even when the
  cursor-write loop or the opportunistic prune raises — closing a
  self-inflicted DoS where a mid-emit WT write error could permanently wedge
  `oplog_visible_tail_seq` and freeze every change stream on the server. The
  exception itself still propagates normally (not swallowed); a `try/finally`,
  not a `try/except`, so the caller still sees the failure. Deferred emits
  are correctly excluded from the `finally`'s deregister call (they resolve
  at their own transaction's commit/rollback). New concurrency test injects a
  bare-emit failure mid-flight and asserts the visible tail recovers.
- **W2 fix (`drop_index`/`drop_all_indexes`):** both now take
  `self._coll_lock(db, coll)` before the global `self._lock`, matching
  `create_index`'s existing lock order — closing a race where a concurrent
  CRUD write could land between an index-entry snapshot and its deletion, and
  introducing no lock-order inversion (same acquisition order as the existing
  `create_index` path).

Rust side (`crates/secantus-storage/src/lib.rs`, +22 lines):

- **W1 fix:** the two previously-flagged `.lock().unwrap()` sites in
  `prune_oplog_sweep` (post-fix `crates/secantus-storage/src/lib.rs:5249` and
  `:5352`) are now `.lock().unwrap_or_else(|e| e.into_inner())`. A fresh
  project-wide sweep for `.lock()/.read()/.write()` immediately followed by a
  bare `.unwrap()` found no remaining wire-reachable instance — the only 4
  remaining hits are confined to `crates/secantus-server/src/lib.rs:1296-1336`
  inside `#[cfg(test)] mod alloc_budget_tests`. A new static tripwire test
  (`tests/test_rust_lock_poison_guard.py`) now scans `secantus-storage`/
  `secantus-commands` for the bare pattern outside `#[cfg(test)]` on every
  run, since this exact pattern was reintroduced once before (per the fix
  commit's own message).
- **W4 fix — 🟠 PARTIALLY RESOLVED, kept open (see §12 / Warnings below).**
  `emit_oplog_entries` (`lib.rs:4056-4067`) now charges pre-image bytes, not
  just entry bytes, into `PENDING_DIRTY_BYTES`, closing the concrete bug the
  issue reported (a pre-image-enabled transaction's `pending_async` buffer
  could grow unbounded because the dirty-byte budget only ever saw entry
  bytes). **Verified directly against the source** that this is *not* the
  direct byte/count cap the original finding recommended: `pending_async`
  itself (`TransactionHandle.pending_async: Vec<(OplogEntry, Option<Vec<u8>>)>`,
  `lib.rs:148`) still has no field-level cap; the only enforcement is the
  pre-existing, indirect `2 * handle.dirty_bytes > self.txn_dirty_limit` check
  in `with_user_transaction` (`lib.rs:5576-5578`), now correctly fed by the
  fuller byte count. (One reviewing agent this cycle misread an unrelated,
  much-older constant — `ASYNC_OPLOG_MAX_PENDING_BYTES` at `lib.rs:2544`,
  which bounds the *background async-oplog drainer's* `Backpressure` queue,
  introduced in `b951257b` well before this window — as a new direct cap on
  `pending_async`; confirmed via `git diff 9e68dd6f..HEAD` that this constant
  and its call site are untouched this cycle and govern a different buffer
  entirely. Flagging this here so a future review doesn't repeat the
  conflation.) Functionally the growth is now bounded (both byte categories
  feed the same budget check), so the practical exposure is closed, but the
  architectural gap — no cap intrinsic to `pending_async` independent of the
  overall transaction dirty-byte budget — remains exactly as the issue
  described. **Reopened issue #750** rather than crediting it as done.

`unsafe` sweep (project-wide, not just the diff): 68 occurrences, still
confined to the same three files as the 2026-08-15 baseline

**🔴 NEW CRITICAL (C5) — SQL statements executed from inside a plpgsql
trigger body bypass RBAC entirely; a schema-DDL-only role can plant logic
that any unrelated, minimally-privileged session's ordinary `INSERT`
executes with zero authorization check.**

**Files:** `src/secantus/sql/plpgsql.py:700-706` (`_Runner._run_sql`),
`src/secantus/sql/engine.py:2003-2058` (`_run_statement`, contrasted with
`_dispatch` at `:333-384`, where `authz.authorize`/`authz.authorize_source_
reads` actually live), `src/secantus/sql/executor.py:812-855`
(`_fire_before_insert_triggers`, called from `execute_insert` at `:868`),
`src/secantus/sql/engine.py:3908-3973` (`_create_trigger`),
`src/secantus/sql/authz.py:79-81` (`required_privilege`'s `exp.Create`
branch — `CREATE TRIGGER`'s `kind` is `"TRIGGER"`, which doesn't match the
`"INDEX"` special case, so it falls through to the generic
`A_CREATE_COLLECTION` grant, same as `CREATE FUNCTION`).

Landed this cycle in `58d53adb` ("BEFORE INSERT row triggers with plpgsql
NEW records"). Traced the full call chain: `execute_insert` →
`_fire_before_insert_triggers` → `plpgsql.invoke_trigger` → the plpgsql
tree-walking interpreter's `_Runner._run_sql`, which for any embedded
INSERT/UPDATE/DELETE/WITH statement in the trigger function body calls
`_engine._run_statement(stmt, c.storage, c.db, c.catalog, c.session)`
**directly** — `_run_statement` (`engine.py:2003`) is the pure execution
core: it plans and executes the statement with no RBAC call anywhere in its
body. Authorization (`authz.authorize` at `engine.py:378`,
`authz.authorize_source_reads` at `:384`) lives exclusively in `_dispatch`,
the outer per-wire-request entry point one level above `_run_statement` —
and nothing in the trigger-firing path re-enters `_dispatch`.

Concretely: a role holding only `A_CREATE_COLLECTION` (the same generic
DDL grant `CREATE TABLE`/`CREATE INDEX` require — e.g. a `dbAdmin`-shaped
role with **no** `readWrite` on anything) can `CREATE FUNCTION`/`CREATE
TRIGGER` to plant a `BEFORE INSERT ... FOR EACH ROW` trigger on table `orders`
whose plpgsql body runs e.g. `DELETE FROM secrets` or `INSERT INTO exfil
SELECT * FROM secrets`. From then on, **any other session — including one
holding only `INSERT` privilege on `orders` and nothing else** — fires that
logic on an ordinary `INSERT INTO orders VALUES (...)`, and the embedded
`DELETE`/`SELECT` against `secrets` executes with **no privilege check
whatsoever**, not even the primary-target check that an ordinary top-level
statement would get. This is a strictly worse instance of the C1/C2/C4
pattern: those three skipped only the *secondary*-namespace check while
still gating the primary target; here **no gate runs at all** for the nested
statement, and the exploiting session need not even be the one with the
DDL grant — it just needs to perform an everyday write the trigger's author
chose to intercept. Reachable under the same threat model as C1-C4
(`--auth` + per-user/table-scoped roles), and — like those — not reachable at
all when `--auth` is off (the default).

**Fix direction:** route `plpgsql._Runner._run_sql` (and any other embedded-
SQL execution path inside plpgsql, e.g. a function invoked directly via
`SELECT fn()`) through `_dispatch` — or at minimum call `authz.authorize`/
`authz.authorize_source_reads` before `_run_statement` — using the firing
session's actual privileges, matching how a top-level statement is checked.
A separate design question worth raising to the team: should a
security-definer-style trigger even inherit the *firing* session's
privileges, or should trigger/function execution privilege be modeled
explicitly (closer to real Postgres's `SECURITY DEFINER`/`INVOKER`)? Either
answer requires *some* check to run, which today is entirely absent.
**A new tracking issue has been filed for this (see below).**

`--auth` gating (general): unchanged, no other regression found.

## 6. Command dispatch & operator-engine safety

No `eval`/`exec`/`compile`/`__import__` reachable from a query/pipeline/SQL
statement in the new diffs. plpgsql execution (`58d53adb`) runs through a
hand-rolled tokenizer/parser (`plpgsql._Parser`) and a tree-walking
interpreter (`plpgsql._Runner`); expression evaluation delegates to the
existing, already-audited `scalar.evaluate` engine — no Python `eval`
anywhere in the new interpreter.

**🟡 NEW INFO (I49)** — no recursion-depth guard for a self-referencing
`BEFORE INSERT` trigger (a trigger function that itself inserts into its own
table). Relies on Python's default recursion limit plus `pgserver.py`'s
generic `except Exception` handlers to bound the blast radius to one failed
request rather than a process crash. By contrast, the FK-cascade path a few
hundred lines away in `executor.py:2516` has an explicit `_depth > 20` guard
for the analogous unbounded-recursion risk; triggers have no equivalent.
Low severity (bounded by the interpreter recursion limit, not unbounded
memory growth), but worth a follow-up cap for symmetry with the FK-cascade
guard.

`166e67f5`'s recorded-SRF expansion (`_pg_expandarray`) runs the inner query
through the normal, already-authorized `_run_select`, then expands rows in
pure Python bounded by the actual returned array length — no new unbounded
path. `search_path`-aware `pg_table_is_visible` only affects unqualified-name
*visibility* for catalog introspection; this codebase's RBAC is database-
scoped, not schema-scoped, so it can't grant access to data a session's
db-level role didn't already permit.

`$regex` DoS guard (1000-char cap, `query.py:1034-1049`) unchanged; no diff
touched it this cycle.
