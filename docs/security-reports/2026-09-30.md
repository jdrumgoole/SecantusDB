**Awaitable-`hello` actually waits, and `helloOk` is echoed**
(`src/secantus/server.py`, `crates/secantus-server/src/lib.rs`) — two
driver-compatibility fixes, read in full on both servers. Previously an
awaitable `hello` (`topologyVersion` + `maxAwaitTimeMS`) answered immediately
instead of holding the reply, which made a driver polling this way spin; now
the wait is honoured, clamped to 60s server-side
(`server.py:545`/`crates/secantus-server/src/lib.rs`'s `await_hello_reply`,
both hold the connection thread for at most the clamped budget and remain
interruptible by the shutdown event — no unbounded hold). `helloOk` is now
echoed back only when the client sent it, matching a measured mongod 8.2.11
behaviour. Neither changes an authorization or parsing-bounds property; both
are read/handshake-path only. Clean.

**PL/pgSQL interpreter, triggers, DO blocks**
(`crates/secantus-pgserver/src/{plpgsql_fn,triggers,do_block}.rs`, `Cargo.toml`)
— a genuinely new execution engine: `CREATE FUNCTION ... LANGUAGE plpgsql`
bodies (parsed by `pg_query::parse_plpgsql`) are walked by a hand-written
`stmt()`/`stmts()` interpreter (`plpgsql_fn.rs:788`/`:805`) that mutually
recurses on nested control structures (`IF`/`LOOP`/`BEGIN...END`/`CASE`), and
`call_user_function` re-enters this interpreter once per PL/pgSQL call level.
This is exactly the shape of the "unbounded Rust recursion" class this project
already tracks at 19+ open issues — and this time the fix landed **in the same
commit that introduced the recursion**, not after: `with_call_depth`
(`crates/secantus-pgserver/src/lib.rs:4218`) caps call-level recursion at 200
(`54001 stack depth limit exceeded`, PostgreSQL's own code) and wraps every
level in `stacker::maybe_grow(1 MiB red zone, 16 MiB segment, ...)`
(`:4243`) so a level that needs more stack gets a fresh segment instead of
overflowing the worker thread — the dependency was added for exactly this
reason (`Cargo.toml`'s comment: "a recursive function (`fact(n-1)`) overflowed
a worker thread's fixed stack within a few levels -- aborting the whole
server -- long before the 54001 depth guard could answer", i.e. this was
caught and fixed pre-merge, not left for this review to find). **Read but not
independently reproduced:** the depth counter only increments at the
`call_user_function` boundary, not at every `stmt()`/`stmts()` recursion step,
so a *single* function body with extremely deep control-flow nesting (no
recursive calls at all) is bounded only by the 16 MiB `stacker` segment, not
by the 200-level counter. Not filed — no crash was reproduced, the primary
attack shape (recursive PL/pgSQL calls, the one the dependency comment
describes) is now guarded, and speculating a second, narrower gap without a
reproduction contradicts this project's own "reproduce before working it"
rule. Recorded here as an INFO item for whoever next touches this file to
check with a corpus of deeply-nested-but-non-recursive control flow.

**Hand-rolled XML parser** (`crates/secantus-pgplan/src/xml.rs`, new, 1112
lines) — `xml()`/`xmlparse()`/`xmlserialize()` etc. for the SQL/XML surface,
including `<!DOCTYPE ... [<!ENTITY e "x">]>` internal-subset parsing. This is
the classic XXE shape (external entities, billion-laughs) so it got a close
read of every entity-related path: `doctype()` (`:415`) and
`internal_subset()` (`:443`) record only entity **names**
(`self.entities.push(name)`, `:464`) from `<!ENTITY name "...">`
declarations; an entity **reference** in document content
(`entity_ref`, `:360`) is checked only for **well-formedness** — does the name
exist in the declared set, or is it one of the five predefined
(`amp`/`lt`/`gt`/`quot`/`apos`) — and is never substituted with a value, let
alone fetched. `grep`ped the whole crate for any file/network path
(`std::fs`, `reqwest`, `TcpStream`, `File::open`) reachable from this
module: none. No entity expansion happens at all, so neither XXE (no
`SYSTEM`/`PUBLIC` external ID is ever dereferenced — the external ID is
consumed as an opaque quoted string in `doctype()`, never opened) nor
entity-expansion billion-laughs (no substitution, so no exponential blow-up)
is reachable. Clean — and worth stating explicitly given how often this
exact parser shape is the vulnerability in other codebases.

**Rust MongoDB server: index/mongod-fidelity batch**
(`crates/secantus-storage/src/lib.rs`, +447/-*, the commit titled "index
data-loss fixes and a mongod-fidelity sweep") — read the whole diff. Entirely
correctness fixes (sparse/partial index edge cases, hint resolution on a
missing collection) matching the same class of bug the Python storage layer
already had fixed and documented in `CLAUDE.md`; no new `unsafe`, no
path/URI construction from query input, no swallowed error on a write path.
Data-loss bugs are a correctness concern this project treats as seriously as
a security one (`CLAUDE.md` "Never ignore an error"), but none of the fixed
shapes were attacker-triggerable beyond what a legitimate query already
reaches — no new finding.

**SCRAM-SHA-1 + legacy MD5 prepass added to the Rust `secantus-auth` crate**
(`crates/secantus-auth/src/lib.rs`, +206/-12) — mongod 8.2 still creates both
SCRAM-SHA-1 and SCRAM-SHA-256 credentials for every user and accepts either;
this was previously unimplemented (SHA-256 only) and is now measured fidelity.
Read the whole diff: the user-enumeration protection (fabricate same-shape
fake credentials before failing the proof step, `begin()` at
`crates/secantus-auth/src/lib.rs:315`) is preserved for the SHA-1 path
exactly as it existed for SHA-256, and the wrong-password comparison still
goes through `constant_time_eq`. Adding a client-selectable weaker mechanism
alongside a stronger one is, in the abstract, a downgrade-attack surface — but
this mirrors mongod's *own* default (both mechanisms are created and offered
by a real 8.2 server), so an implementation that offered only SHA-256 would
itself be a fidelity gap, and a client that only speaks SCRAM-SHA-1 already
has no other option in this codebase's threat model (a developer's own test
suite talking to a local test server, not an adversarial network). Not filed.

**PostgreSQL wire SCRAM password verification lands**
(`crates/secantus-pgserver/src/lib.rs`, the `StartupHandler`/
`continue_password_login` block, ~`:9660`-`:9857` in the diff) — this is new
*within this window* (the previous cycle's report, dated 2026-09-29 but cut at
`8b179541`, predates it). Read the whole exchange: a role with a
`SCRAM-SHA-256$<iter>:<salt>$<stored>:<server>` verifier now must complete a
real SASL exchange (`secantus_auth::begin_scram_pg`/`continue_scram`, the
same constant-time-compare code path the Mongo-wire server uses) before
`finish_startup` is reached; a role with an `md5`-form verifier is refused
outright (this server speaks only SCRAM); a role with **no** password, or a
name this server has never heard of, is still trusted with no exchange at all
— which is a deliberate, documented tradeoff (`CLAUDE.md`: "a role with a
password must pass SCRAM-SHA-256; a role with none, and an unknown user, are
still trusted (test fixtures rely on that)"), not an oversight: it narrows the
standing #1191 ("no authentication at all") for the subset of roles an
operator explicitly assigns a password to, while leaving the default
(password-less fixture roles) exactly as open as before. Re-confirmed #1191
itself is still open below.

## The new finding this cycle

**New WARNING — `replSetStepDown` bypasses RBAC entirely on both servers; an
authenticated zero-privilege connection can force a write outage of an
attacker-chosen, effectively unbounded duration.**
`src/secantus/commands.py:8991` (`_HANDLERS["replSetStepDown"]`), the
`_COMMAND_ACTIONS` dict (`:9082`-`:9166`, re-read in full) has **no**
`"replSetStepDown"` entry; `crates/secantus-commands/src/lib.rs:537`
(handler registration) / `:1924`-`:1974` (`command_action`, re-read in full)
likewise has no `"replSetStepDown" =>` arm before its `_ => return None`
fallback at `:1974`. Both dispatchers' own documented policy is that a
missing entry means **no privilege required**
(`commands.py:9077`-`9081`: "missing entries default to 'no privilege
required' so a user with even minimal roles can still invoke them... be
deliberate") — this is the same class already tracked at #1226
(`killSessions` family), #996, #948, #947, #909, #1118, just a new command
falling into it.

Traced the mechanism end to end in `src/secantus/stepdown.py` (new this
cycle, 135 lines, read in full): `step_down()` (`:103`) takes
`doc.get("replSetStepDown")` as the step-down period with **no upper bound**
— `period = raw if isinstance(raw, (int, float)) and not isinstance(raw,
bool) else None`, only a *negative* value is refused (`:115`); `force: true`
skips the catch-up-period check entirely and goes straight to
`state.step_down_for(seconds)` (`:133`-`:134`). `StepDownState.step_down_for`
(`:78`) just sets `self._until = self._clock() + seconds` with no cap. So
`{replSetStepDown: 999999999, force: true}` is accepted and the node reports
`isWritablePrimary: false` / refuses every write with `10107 NotPrimary`
(`commands.py:10279`-`10287`, the write-command gate added this cycle) for
~31 years, from one request, with no privilege beyond a bare authenticated
connection under `--auth`. The Rust server's `crates/secantus-commands/src/
stepdown.rs` mirrors the same contract (not independently re-derived here,
but the missing RBAC entry alone is sufficient to reach the same outcome via
the same mechanism `crates/secantus-server/src/lib.rs`'s write-gate wires up).

This is graded WARNING rather than CRITICAL to match this project's own
precedent for the class: like `killSessions`/`killAllSessions` (#1226), it
needs *some* valid credential (however unprivileged) under `--auth`, and its
blast radius is availability (writes refused) rather than the read/write
data-access widening that earns #1160 (`bulkWrite`) its CRITICAL rating. It
is filed as a **new** issue rather than folded into #1226 because it is a
distinct command with its own reachable outcome (a persistent topology-wide
write outage, not a session kill), consistent with how #996/#948/#947/#909
were each filed separately from #1226 despite sharing the same root defect
class. **Filed as a new GitHub issue this cycle.**
