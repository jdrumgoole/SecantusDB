### The Ops Board (new this cycle) — reviewed in full

`secantus-opsboard` is a local, loopback-bound FastAPI app (ships behind a
new opt-in `opsboard` extra, correctly excluded from the base `pip install
secantus` — confirmed via `uv.lock`/`pyproject.toml` diff) that lets a
developer start/cancel/tail build, test, and release jobs, watch recent
GitHub Actions runs, and dispatch new ones, all from a browser window. This
is exactly the kind of new attack surface the review checklist calls out
(§10), so it got a full read of every router, the middleware, the job
runner, and the GitHub CLI wrapper:

- **Auth:** `TokenAuthMiddleware` (`middleware.py`) gates every route except
  `/healthz` and `/static/*` behind a per-launch, `secrets.token_urlsafe(32)`
  token (constant-time `hmac.compare_digest` check), accepted via query
  param / header / cookie. The bypass-prefix check reads `request.scope["path"]`
  rather than the Host-header-derived `request.url.path` — the same
  CVE-2026-48710 (Starlette `BadHost`) hardening the admin app already
  applies. The token file (`~/.secantus/opsboard-token`) is written
  `chmod 0600`. Default bind is `127.0.0.1` (`launcher.py`), matching the
  network-exposure default this checklist requires; `--host` is an explicit
  opt-in.
- **CSRF:** the auth cookie is `httponly`, `samesite="strict"` — a
  cross-site form POST from an attacker's page won't carry it, so the
  job-start / cancel / dispatch endpoints aren't reachable via a
  drive-by CSRF even though they're simple unauthenticated-looking HTML
  forms under the hood.
- **Command construction:** every subprocess call in the new module
  (`github.py`'s `gh` wrapper, `discovery.py`'s `ps` scan, `readiness.py` /
  `versions.py`'s `git` calls, `runner.py`'s job spawn) passes a list argv to
  `subprocess.run`/`Popen` — **no `shell=True` anywhere**, so there is no
  shell-injection vector even though several of these take form-submitted
  strings (workflow `ref`, task `extra` args). `runner.py`'s `JobRunner.start`
  spawns `[python, -m, secantus.jobkit, *argv]` directly (`start_new_session=True`,
  stdin/stdout/stderr closed), so a crafted `extra` field can only append
  extra argv elements to an already-allowlisted task, not break out of the
  argv array.
- **Task allowlisting:** `/jobs/start` resolves `task_key` through
  `registry.resolve_task`, a fixed, hardcoded catalog (`registry.py`) — a
  client cannot name an arbitrary command, only one of the ~35 declared
  `Task` entries plus a bounded `--jobs N` (capped at 16) and free-text
  `extra` args appended to that task's own fixed argv. `/ci/dispatch`
  similarly only accepts a `workflow` name that round-trips through `gh
  workflow list`'s own output (`known.get(workflow)` lookup), so it cannot
  dispatch a workflow that doesn't already exist in the repo.
- **XSS:** `Jinja2Templates` default-autoescapes; grepped every template
  under `src/secantus/opsboard/templates/` for `| safe` / `{% autoescape
  false %}` — **zero matches**. Job logs (arbitrary subprocess output,
  effectively attacker-adjacent if a test prints something HTML-shaped) are
  rendered through the default-escaped `{{ log_text }}`.
- **SQL:** the job journal (`jobkit/_core.py`, sqlite-backed) uses
  parameterized `?` placeholders throughout; the one f-string-built clause
  (`WHERE status != '{RUNNING}'`) interpolates a module constant, never
  request input. Pagination is enforced (`limit` clamped to 500) — matches
  the "no unbounded materialisation" requirement.

Two gaps found, written up below as **W2** (WARNING) and an INFO item.

### Rust storage — RecordId re-keying + index-DDL locking fix

- **`b90b5490`** re-keys the doc-table from `id_key` (`SSu`) to a monotonic
  `RecordId` (`SSq`), dropping the forward natural-order table
  (4→3 write-amplification). Reviewed the FFI delta
  (`crates/secantus-wt/src/lib.rs`, +9 lines): one new `get_value_s` cursor
  accessor, following the exact same checked-return-code /
  `owned(*const c_char)` pattern as every existing `get_value_*` method — no
  new `unsafe` invariant introduced. A store written before this change (doc
  shards keyed `SSu`) is **refused at open** (`reject_pre_recordid_doc_format`,
  a fatal `StorageError::Internal`) rather than silently misread — sound,
  and not attacker-reachable (fires once at process start, before any
  connection is accepted). Grepped the full diff for new `unsafe` /
  `.unwrap()` / `.expect()` / `panic!` outside test code
  (`git diff 55944381..HEAD -- crates/secantus-storage/src/lib.rs | grep
  -nE '^\+.*(unsafe|\.unwrap\(\)|\.expect\(|panic!)'`) — every hit is inside
  the new `open_rejects_pre_recordid_doc_shard` unit test (tempfile /
  `Storage::open` setup), none in the request path.
- **`7a9e230c`** fixes a real data-integrity bug: `create_index` took only
  the global `_lock`, not the per-collection `_coll_lock` that its own
  docstring already promised DDL would hold — a concurrent insert landing
  between the index build's doc-table scan and its catalog-row write was
  invisible to both halves, silently producing an index that under-reports
  matching docs. Auditing the fix surfaced (and closed) a real AB-BA
  deadlock hazard in `_collection_uuid`'s mint path. New regression test
  (`test_ddl_and_crud_never_deadlock_and_index_stays_complete`) runs
  concurrent writers against an index build and asserts both no deadlock and
  full index coverage. Reviewed and sound — but see **W2**: the sibling
  `drop_index` / `drop_all_indexes` paths were deliberately left unfixed by
  the same commit (self-documented: "same one-line pattern, left out to
  keep a locking change narrow") and are a live, currently-untracked
  instance of the identical race class.
- **`79421bcd`**/**`da8da7ab`** (prealloc / close-checkpoint) were already
  reviewed in the 2026-07-23 report; unchanged this cycle.

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open — 4th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**Files:** `crates/secantus-storage/src/lib.rs:3038` and `:3117`, inside
`prune_oplog_inner` (line numbers shifted again — this cycle's `b90b5490`
inserted ~370 lines earlier in the same file; same two call sites,
re-verified present by direct grep of every `self.oplog.lock()` call site in
the current file: 11 total, 9 using the poison-tolerant
`unwrap_or_else(|e| e.into_inner())` pattern, and the two holdouts at 3038
and 3117 still using bare `.lock().unwrap()`).

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, still open, now unfixed across four consecutive review cycles
(07-21, 07-22, 07-23, 07-24) — including three cycles (07-22, 07-23, and
today) that each landed substantial edits to this exact file
(`crates/secantus-storage/src/lib.rs`) without touching these two lines. No
new issue filed for it today; it stays tracked under #593.

**Recommendation:** unchanged — convert both sites to
`self.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The grep-based CI
gate recommended in the last three reports
(`! grep -rn '\.lock()\.unwrap()' crates/secantus-storage crates/
secantus-commands` outside `#[cfg(test)]`) remains the highest-leverage fix
here — a two-line manual patch has now survived four nightly re-discoveries
that a one-time CI check would have made unnecessary.

### W2 (new) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` just gained, leaving the identical race class open

**File:** `src/secantus/storage.py:5254` (`drop_index`) and `:5371`
(`drop_all_indexes`).

Today's `7a9e230c` gave `create_index` the per-collection `_coll_lock` it
was missing, closing a race where a concurrent insert landing mid-build was
invisible to both the index scan and the write path, silently producing an
index that under-reports matching documents. The commit message explicitly
flags that it left `drop_index` and `drop_all_indexes` on the old, narrower
`with self._lock:` — confirmed by direct read of both methods: neither
acquires `self._coll_lock(db, coll)`, only the global `self._lock`.

This is the same class of hazard, the opposite direction: `drop_index`
snapshots the collection's index-entries table
(`self._collect_prefix(_IDX_ENTRIES_TABLE, (db, coll, name))`) and deletes
what it read, all while `_coll_lock` — the lock CRUD writers coordinate
against — is not held. A concurrent `insert`/`update`/`delete` on the same
collection, which *does* take `_coll_lock` first, is not excluded by
`drop_index`'s `_lock`-only critical section, so a write's index-entry
mutation and a drop's index-entries scan-then-delete can interleave in ways
the just-fixed `create_index` bug is a direct precedent for (entries left
behind referencing a since-removed index catalog row, or a write's new
entry silently dropped by the delete sweep depending on interleaving). No
existing test exercises this — a grep of `tests/test_storage.py` for a
`drop_index` concurrency/race test found none, versus the new
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` covering exactly
this hazard for `create_index`.

Calibrated to this project's own standard (`CLAUDE.md`: "an error is a
correctness and durability signal, never noise to step over" — and the
sibling bug was judged worth a same-day fix): this is a real, currently
exploitable-by-ordinary-concurrent-use data-integrity gap, reachable by any
wire client issuing normal `dropIndex`/`insert` traffic concurrently — no
`--auth` bypass or malformed input required.

**Recommendation:** the fix is the one-line pattern already applied to
`create_index` — change `with self._lock:` to `with self._coll_lock(db,
coll), self._lock:` in both `drop_index` and `drop_all_indexes`, following
the same "acquire `_coll_lock` before `_lock`" canonical order the
7a9e230c docstring now documents. A regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` (concurrent
writers + a `dropIndex` on the same collection, asserting no deadlock and no
orphaned/lost entries) would close this the same way. Filing as a tracked
issue below.

## 🟡 INFO (Best-practice recommendations)

### New this cycle

- **I31 — the Ops Board's generic `/jobs/start` endpoint can resolve
  confirm-gated release-class tasks with a weaker gate than the dedicated
  `/release/start` endpoint, and currently is safe only by accident, not by
  design.** `routers/release.py`'s own docstring states it "deliberately does
  NOT reuse the generic `/jobs/start` path" specifically because release
  tasks need an exact-match typed confirmation *and* a passing readiness
  check (clean tree, right branch, in sync with origin, changelog fragment
  present). But `routers/jobs.py:start_job` resolves the *same* task keys
  (`registry.resolve_task` is not scoped to non-release tasks) and only
  requires `confirm.strip().lower() in ("yes", "y")` — no readiness check at
  all. Today this is inert: `py-release-prepare`/`py-release-finalize`
  require a `version` positional argument that `/jobs/start` never supplies
  (the underlying `invoke release-prepare` task errors out immediately for a
  missing required arg), and `rs-bump`'s registered argv (`["rust-bump"]`)
  doesn't correspond to any task currently defined in `tasks.py` (grepped
  `tasks.py` for `rust-bump`/`rust_bump` — no matches), so it would also fail
  fast. But neither protection is intentional — a future change that gives
  `release-prepare` a default version, or that wires up a real `rust-bump`
  invoke task (both plausible follow-ups per `tasks/opsboard-plan.md`), would
  silently reopen a path to start an irreversible, outward-facing release
  action by typing "yes" with none of `/release/start`'s readiness gates.
  Low severity given the token-gate + CSRF-safe cookie already bound this to
  the same trusted local operator who could just run `invoke
  release-prepare X.Y.Z` directly — but worth closing by having `/jobs/start`
  reject `task.confirm` tasks outright (`use /release/start`, which
  `/release/start` already does for the inverse case) rather than relying on
  argv-shape happenstance.
- **I32 — the opsboard auth token is accepted via a `?t=` query parameter**
  (`middleware.py` `QUERY_NAME = "t"`), same pattern as the existing admin
  app. A token that reaches a URL bar or a redirect chain can land in shell
  history, browser history, or (if ever proxied) upstream access logs. This
  mirrors an already-accepted design tradeoff in the admin app (loopback
  tool, ease-of-use for pasting a link) — noted here only because it's a
  second, independent instance of the same pattern; not a new risk class.
- **I33 — RUSTSEC-2026-0176, pywebview, and `setproctitle` re-checked this
  cycle for the new `opsboard` extra: no advisories found.** WebSearch this
  cycle for `pywebview CVE`, `setproctitle CVE`, and `Swatinem/rust-cache CVE`
  (the new cache action) turned up nothing. `pywebview`/`setproctitle`/
  `fastapi`/`uvicorn`/`starlette`/`jinja2`/`python-multipart`/`httpx` in the
  new `opsboard` extra are the exact same pinned versions already reviewed
  for the `admin` extra in prior cycles (`fastapi` 0.136.1, `uvicorn` 0.46.0,
  `starlette` 1.3.1, `jinja2` 3.1.6, `python-multipart` 0.0.32, `httpx`
  0.28.1) — no new version, no new advisory surface.
