## 🔴 CRITICAL (Immediate action required)

All three unchanged, re-confirmed by direct read against current HEAD:

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  Re-read in full this cycle, byte-identical to the prior cycle's citation:
  `if (self.message_length as usize) < HEADER_SIZE` casts the signed `i32` to
  `usize` first — `message_length = -1` sign-extends to `usize::MAX` on
  64-bit, which is not `< HEADER_SIZE (16)`, so this guard passes. The second
  guard, `self.message_length > MAX_MESSAGE_SIZE`, is a signed `i32`
  comparison (`MAX_MESSAGE_SIZE: i32 = 48_000_000`), so a negative value also
  passes it. The function returns `self.message_length as usize - HEADER_SIZE`
  = `usize::MAX - 16`. Traced the one caller this cycle
  (`crates/secantus-server/src/lib.rs:553-562`): `body_len()`'s result feeds
  `shared.alloc_budget.acquire(body_len)` before `vec![0u8; body_len]`. That
  budget (`AllocBudget`, `crates/secantus-server/src/lib.rs:70-95`) exists to
  cap *concurrent* allocation, not a single oversized one — its own comment
  says so ("unless nothing is outstanding, so a lone oversized request
  proceeds rather than deadlock"), so a single connection sending this
  16-byte frame passes the budget check immediately (`used == 0`) and reaches
  `vec![0u8; usize::MAX - 16]` uncapped. Rust's global allocator has no
  in-process way to catch an allocation failure of that size — it calls
  `std::alloc::handle_alloc_error`, which **aborts the whole process**, not
  just the offending connection's thread. One unauthenticated 16-byte frame
  on the accept path is a full-server abort. **Not fixed.**

- **#1160** — `src/secantus/commands.py` (RBAC) and
  `crates/secantus-commands/src/lib.rs` (RBAC), both servers. Re-read this
  cycle: `"bulkWrite": _bulk_write` / `"bulkWrite" => bulkwrite::bulk_write`
  are both still registered in dispatch. Grepped `_COMMAND_ACTIONS`

  reply shape — read the full diff of both `commands.py`'s `_bulk_write` and

- **#977** — `src/secantus/query.py:1407-1471` (`_MAX_REGEX_PATTERN_LEN =

- **`AllocBudget` (`crates/secantus-server/src/lib.rs:57-109`), read in full
  while tracing #995's caller.** This is a genuine, already-shipped mitigation
  against *concurrent* large-message memory exhaustion (a `Mutex`+`Condvar`
  byte budget, `MAX_INFLIGHT_BYTES = 512 MiB`, acquired before the body
  buffer is allocated) — not new this cycle (`crates/secantus-server/src/
  lib.rs` has no diff since `9ef270c0`), but it does not mitigate #995: its
  own comment documents the "unless nothing is outstanding" escape hatch that
  lets a single oversized request through by design, which is exactly the
  path #995's cast bug reaches. No finding beyond #995 itself, but worth
  recording so a future cycle doesn't mistake the budget's existence for a
  fix.
- **`create_unique_indexes` (`crates/secantus-pgserver/src/lib.rs`, new this
  cycle) builds a storage `key_spec` `Document` from user-declared SQL column
  names via `.insert(f.clone(), 1)` with no dot-escaping.** This is the same
  *shape* as the "user-supplied path used as a dict key" bug class
  `CLAUDE.md` calls out (a PostgreSQL quoted identifier can contain a literal
  `.`, e.g. `CREATE TABLE t ("a.b" text UNIQUE)`). Checked whether this is a
  *new* instance: it is not — `Column::field()` /
  `secantus_pgcatalog::field_for` (unchanged this cycle) already maps every
  column name straight through with no dot-escaping for the *base* column
  storage field, so a dotted-identifier column already has this property for
  ordinary `INSERT`/`SELECT`, independent of `UNIQUE`. The new
  `create_unique_indexes` code inherits an existing general property of the
  SQL-to-Mongo column mapping rather than introducing a new one. Not filed —
  recorded here in case a future session narrows the general SQL
  dotted-identifier gap and wants the concrete `UNIQUE`-constraint angle
  without re-deriving it.
