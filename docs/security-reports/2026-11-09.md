## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **A single `explain` command with a long dotted field path aborts the
  entire `secantusd-rs` process — reachable with no authentication on the
  default configuration** (high/high/high). Two new functions in the SBE
  explain plan builders, `crates/secantus-commands/src/explain/sbe/group.rs`
  (`fn traverse`, line 583) and `crates/secantus-commands/src/explain/sbe/
  filter.rs` (`fn traverse`, line 130), are directly self-recursive with one
  native stack frame per dotted-path component taken verbatim from the
  client's `$group`/`$match` field path. The component vectors come from an
  unbounded `path.split('.')` with no count cap anywhere on the call chain
  (`sbe_front` -> `group_compatible` -> `group::build` -> `traverse`).
  Connection-handling threads use a bare `thread::spawn` with Rust's 2 MiB
  default stack (`crates/secantus-server/src/lib.rs:608`) — a `grep` across
  `crates/` for `stack_size` finds hits only in the PostgreSQL server's
  crates, never the MongoDB server's. A Rust stack overflow is a guard-page
  SIGSEGV that aborts the process rather than unwinding, so the
  `catch_unwind` wrapping command dispatch cannot intercept it: one
  connection's request kills every other connection and leaves WiredTiger
  without a clean checkpoint. A ~100 KB field name (well under the 16 MiB
  BSON document limit) is enough, on an `explain` of an `aggregate` whose
  one `$group` stage satisfies the SBE pushdown gate, against any existing
  collection. A fresh verifier independently re-read both `traverse`
  functions, re-confirmed every link in the chain (the unbounded split, the
  absent depth parameter, the default-stack `thread::spawn`, and that no
  signal handler/`sigaltstack`/allocator trick in this codebase changes
  whether the SIGSEGV is catchable), and specifically searched for — and did
  not find — any raw field-name length cap distinct from BSON nesting depth
  that might have rejected the payload earlier.
  **Fix:** cap dotted-path component count in `explain/sbe/filter.rs#leaf`
  and `explain/sbe/group.rs#arg_of` (returning `None` so the pipeline falls
  back to classic explain, as the module already does for every other
  unsupported shape), mirroring mongod's own ~200-component field-path
  limit. Rewrite both `traverse` functions as iterative folds to remove the
  stack dependence entirely. Separately, set an explicit `stack_size` on
  MongoDB connection threads, as the PostgreSQL server already does.
  **Filed as a new issue** (duplicate search for "SBE", "dotted", "stack
  overflow" found #2132, a different mechanism — `sbe.rs`'s *compatibility
  checker* recursing on nested `$and`/`$or`/`$nor`, confirmed by reading its
  body — and ~25 other unrelated unbounded-recursion issues; none covers the
  new `explain/sbe/{filter,group}.rs::traverse` functions).

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **A transactional `bulkWrite` runs an uncapped O(n²) namespace
  de-duplication before the command's own 100,000-op batch limit is checked**
  (medium/medium/medium). `crates/secantus-commands/src/session.rs`'s new
  `txn_write_targets` (called at line 896, before `run_handler` at line 917)
  walks a client `bulkWrite`'s `ops` array and, for each op, scans the whole
  accumulated namespace list (`out.iter().any(...)`, line 1018) before
  pushing — O(n²) for n distinct namespaces. The handler's own
  `ops.len() > MAX_OPS` (100,000) rejection lives inside `bulk_write`
  (`bulkwrite.rs:611`), reached only *after* this loop returns, and the loop
  contains no `deadline::check()` or kill poll, while the transaction's
  Global IX/Database IX locks and its own mutex are held throughout. A
  verifier independently confirmed the full chain and the reaper's/
  `killSessions`'s inability to interrupt it, but corrected the hunter's
  proposed "high" severity down to "medium": impact is availability-only
  with sub-total blast radius (other databases' connections are unaffected),
  on a server normally bound to `127.0.0.1`.
  **Fix:** replace the linear-scan dedup with a `HashSet<(String, String)>`;
  validate `bulkWrite`'s batch size before the transaction path reaches
  `txn_write_targets`; add a `deadline::check()`/kill poll inside the loop.
  **Filed as a new issue** (duplicate search for "bulkWrite", "txn_write_targets"
  found #1160/#1746/#1226/#1661/#1723/#1678 — all unrelated RBAC-bypass or
  batch-size-fidelity issues on different code paths — no existing coverage
  of this quadratic).

- **Quadratic linear scans in the new SBE `$group` builder let one `explain`
  command pin a CPU core on the client's accumulator/key count** (medium/
  medium/medium). `crates/secantus-commands/src/explain/sbe/group.rs::build`
  has four `Vec::contains`/`Vec::iter().find()` scan sites (lines 186, 223,
  229, 354) inside loops sized by the client's `$group` document, with no
  cardinality cap anywhere (`group_compatible` checks operator names only).
  One site (line 186) runs its full quadratic cost *before* the
  `paths.len() > 1` refusal two lines later, so even refused input pays for
  it. A verifier independently confirmed all four sites and the complete
  absence of a count cap on the call chain, while narrowing the hunter's
  "no cancel::check in the whole explain/ subtree" claim: `explain/plan.rs`
  does poll the deadline, just downstream of this builder.
  **Fix:** replace the `Vec` scans with `HashMap`/`HashSet` lookups; hoist
  the cheap `paths.len() > 1` refusal ahead of the dedup loop; add a deadline
  poll inside the per-accumulator loop.
  **Filed as a new issue** (duplicate search found only the unrelated #2132
  compatibility-checker recursion; no existing coverage of `group.rs::build`'s
  quadratic scans).

- **`hoist_matches`'s pre-existing quadratic prefix rescan is widened this
  window and gains a new call site on the plain `aggregate` path** (medium/
  medium/medium). `crates/secantus-commands/src/explain/hoist.rs::
  hoist_matches` re-evaluates `out[..at].iter().all(leading)` at every pipeline
  position (O(n²) per pass) inside an outer loop that restarts the whole scan
  after every rewrite. This structural defect predates this review window
  (confirmed present at the diff base commit, `7cf9c05e`); this window widens
  `leading` from four predicates to six (two of them newly allocating), adds
  one new mutation branch, and adds a call site in `agg_stream.rs`.
  `hoist_matches` already runs on the server's primary `aggregate` command
  path (`aggregate.rs:712`, `agg_executor.rs:164`), not only `explain`, and
  no `internalPipelineLengthLimit` is enforced anywhere in `crates/` despite
  being advertised in `getParameter`'s help text. A verifier corrected two of
  the hunter's quantitative claims after diffing against the base revision
  (predicate count 4→6, not 2→6; one new restart branch, not two) and
  explicitly framed this as a pre-existing-and-worsened gap rather than a
  defect introduced this cycle.
  **Fix:** enforce mongod's `internalPipelineLengthLimit` (1000) at pipeline
  parse time; make the prefix check incremental instead of rescanning; resume
  from the mutation point instead of restarting the whole pass; add a
  cancellation poll.
  **Filed as a new issue** (duplicate search found #1994, a different
  mechanism in the same file — unguarded *recursion depth* in
  `clause_paths`/`filter_paths`/`expr_paths` — confirmed by reading its body;
  does not cover `hoist_matches`'s iterative complexity).

- **O(N²) uninterruptible CTE-scope cloning in the new `domain_scope`
  planner module** (medium/medium/medium). `crates/secantus-pgplan/src/
  domain_scope.rs` (new, 760 lines) resolves domain-typed columns by
  hand-rolled recursion with no cancellation point of any kind. For a WITH
  of N sibling CTEs, `with_clause_ctes` re-clones the growing CTE-scope
  vector once per CTE (line 217, via `output_columns`'s unconditional
  re-clone at line 275), giving O(N²) clones; the walk runs unconditionally
  before the `has_domains()` short-circuit, so the cost is paid even against
  a domain-free catalog. A WITH nested inside a FROM subquery is not stripped
  by the top-level CTE-inliner (which only fires on the statement's own
  outer `with_clause`), so it survives intact to this walk. A verifier
  independently re-derived the O(N²) shape, confirmed the complete absence
  of any `cancel::check`/`walk_point` in the module by grep, and confirmed
  the FROM-subquery-nested-WITH reachability claim by reading the inliner's
  actual gating condition.
  **Fix:** stop re-cloning the scope vector per sibling (borrow/extend in
  place); add a cancellation point to the recursion.
  **Filed as a new issue** (duplicate search for "domain_scope" found no
  match).

- **New process-global catalog-change tracker never reclaims a namespace
  entry; `drop` of a non-existent collection leaks the name with no length
  bound** (medium/medium/medium). `crates/secantus-storage/src/
  catalog_changes.rs` (new, 199 lines) keeps a process-global
  `MARKS: HashMap` keyed by client-supplied database/collection names,
  inserted by `CatalogChange::begin` before a DDL runs; its `Drop` impl
  mutates an in-flight counter and watermark but never removes the entry —
  the only removal anywhere in the file is `forget_store`, called solely at
  `Storage` teardown. `StorageAdapter::drop_collection` (and five sibling
  DDL methods) create the mark *before* checking whether the target exists,
  and `drop` of a non-existent collection answers `{ok: 1.0}` (idempotent
  success), so a client can repeat `{drop: "<fresh name>"}` indefinitely with
  no privilege beyond ordinary drop rights. No length cap applies on this
  path (`namespace_too_long`'s only call site is `create`). A verifier
  independently re-read the full 199-line file confirming no sweep/cap/LRU
  exists, confirmed the create-before-check ordering repeats at five more
  adapter call sites, and confirmed the idempotent-success `drop` handler
  and `namespace_too_long`'s single call site by grep.
  **Fix:** remove an uncommitted mark on `Drop`; add amortised pruning of
  committed marks once no live transaction's snapshot can be older than
  their watermark (mirroring this same crate's `coll_lock` registry, fixed
  for RM-194 against the identical unbounded-per-namespace-map pattern);
  wire `namespace_too_long` into `drop`/`dropIndexes`/`collMod`.
  **Filed as a new issue** (duplicate search for "catalog_changes", "MARKS"
  found no match).
