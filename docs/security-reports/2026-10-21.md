# Security Review — 2026-10-21

Diff-driven review against the 24 commits that landed since the last report
(`b0fd7df3`, the 2026-10-20 report's own merge commit → `f9511ad3`, HEAD,
confirmed unchanged on `origin/main` throughout this review via
`git rev-parse HEAD` == `git rev-parse origin/main`). This is an unusually
large window — **554 files, +40,041/-15,240 lines** — dominated by two
things: the planned "fully deprecate the Python servers" cut (deleting
`publish.yml`/`wheels.yml`/`rust-wheels.yml`/`crash-repro.yml`/
`record-durations.yml`, cutting ~1,283 lines from `test.yml`, trimming
`pyproject.toml`/`uv.lock`), and a very large batch of new Rust
MongoDB-server feature work (eleven batches, `secantus-commands` alone
touched 44 files: `local.oplog.rs` in mongod's shape, retryable-write
session tracking, `applyOps`, seven new admin commands, chunked index
builds, hybrid-search stages, a connection rate limiter, mongod's planner
text) plus continued Rust PostgreSQL join-order work
(`crates/secantus-pg/src/join_order.rs`).

Four foreground sub-agents reviewed the diff in parallel along the same
"one server, one concern" lines the last several reports have used: (1)
CI workflows / dependencies / secrets / the PyPI-deprecation cut, (2) the
Rust MongoDB server's command layer (`secantus-commands`, itself split
into four further foreground sub-reviews given its size: `applyOps` +
sessions, admin-command auth gating, locking/rate-limiter/panic-handler,
and a grep sweep of the remaining files), (3) the Rust core engines and
storage/FFI layer, (4) the Rust PostgreSQL server plus a status check on
every carried-forward finding from the 2026-10-20 report. Every candidate
finding below was traced to a concrete call chain and the relevant
function read in full (not inferred from a diff hunk) — several were
additionally spot-verified directly in this top-level review by reading
the cited lines myself before writing them up.

**Net result: 5 new CRITICAL findings and 7 new WARNING findings — the
first cycle since 2026-10-17 to find new instances of the project's
open "unguarded recursion on client-controlled input" class, and the
first to find a new instance of a related-but-distinct shape (unbounded
heap allocation driven by a single client field, no recursion involved).**
This tracks the size of the window: five separate new/changed tree-walking
or arithmetic functions were added across three crates (two in
`secantus-commands`, one in `secantus-core`, one in `secantus-pg`, one more
an allocation bug in `secantus-commands`) in a single 24-commit batch, and
one of them is a **regression** — it replaces a function the 2026-10-20
report specifically read and certified CLEAN for being a flat iterative
loop with no recursion, with a genuinely recursive tree walk that has no
depth guard ahead of the recursion.

## 🔴 CRITICAL (Immediate action required)

### New this cycle

1. **Stack-overflow DoS via nested `$jsonSchema`/`$and`/`$or` in an
   ordinary `find`, `update`, `delete`, `distinct`, or `explain` —
   `crates/secantus-commands/src/explain/json_schema.rs` and
   `crates/secantus-commands/src/explain/parsed.rs` (both new/changed this
   window).** `json_schema.rs`'s `object_clauses` (:127) ↔
   `object_keyword`/`property_clauses` (:151, :183, :364) recurse through
   nested `properties`/`dependencies`/`not`/`allOf`/`anyOf` with no depth
   limit, driven entirely by a client-supplied `$jsonSchema` document.
   `parsed.rs`'s new `optimize()` (:218, verified directly — recurses over
   `$and`/`$or` children with no depth parameter) and `with_schemas_parsed()`
   (:255, recurses over `$and`/`$or`/`$nor` and calls into
   `json_schema::translate`) wrap the pre-existing `tidy`/`operator` mutual
   recursion with no guard either. Traced call path, confirmed: `parsed_query()`
   (`parsed.rs:179`) is invoked from every `explain` reply's `parsedQuery`
   field (`explain/mod.rs:285,1035`) **and** from `explain/order.rs:499,824,1017`
   inside `ordered_rows` — which `CLAUDE.md` documents as driving document
   *order* for ordinary `find`/`update`/`delete` since 2026-10-13 (not just
   `explain` itself) — plus `distinct.rs:40` and `summary.rs:94`. A deeply
   nested filter needs no special privilege or admin setting; it reaches a
   process-wide stack overflow (an abort, not a catchable panic — the
   per-request `catch_unwind` in `crates/secantus-server/src/lib.rs:1112`
   does not protect against stack exhaustion) via commands every ordinary
   client sends.

2. **Stack-overflow DoS via a `$score`/`$rankFusion`/`$scoreFusion`
   aggregation stage — `crates/secantus-core/src/hybrid.rs:47`
   (`render`/`expression_text`), new file this window.** `render()` recurses
   over nested `Bson::Document`/`Bson::Array` values with no depth cap
   (verified directly: `d.iter().map(|(k, v)| format!("{k}: {}", render(v)))`
   has no depth parameter at all). `expression_text()` wraps it and is
   called **unconditionally** while desugaring the `$score` stage
   (`crates/secantus-commands/src/hybrid.rs:176`, verified directly — the
   call is not gated behind the `scoreDetails: true` option, so it runs for
   every `$score` pipeline regardless), so a single aggregate pipeline with
   a deeply nested `score` expression crashes the whole server before the
   pipeline even executes.

3. **Stack-overflow DoS via `$addFields`/`$project`/`$set` —
   `crates/secantus-core/src/expressions.rs:436` (`object_literal_keys_parse`,
   new this window).** Reached from the pre-existing `validate_expression_args`,
   so it is reachable from any pipeline/update stage that validates an
   object-literal expression. Same shape as findings 1–2: a recursive
   tree-walk over client-supplied document structure with no depth cap, a
   second, independent crash site alongside the already-open `#1780`
   (unbounded BSON-decode recursion in the Rust `bson` crate itself).

4. **Stack-overflow DoS via a long or bushy `JOIN` list on the Rust
   PostgreSQL server — `crates/secantus-pg/src/join_order.rs::walk_tree`
   (:156) and `::reduce` (~:394), new this window (`cc287d01`, `eefc8ed2`,
   "RP-028 part") — a REGRESSION against code the 2026-10-20 report
   specifically verified CLEAN for not being recursive.** The prior
   version of this function (`git show b0fd7df3:crates/secantus-pg/src/join_order.rs`,
   lines 262–268) found the join count with a flat iterative
   `while let JoinNode::Join { left, .. } = cur { ...; cur = left; }` loop —
   O(N), zero recursion — and the 2026-10-20 report cited exactly this as
   the reason `four_table_chain` was safe against a large join count. This
   window's diff replaces it with `walk_tree()`, a genuine pre-order
   recursive descent (`walk_tree(left, ...)` then `walk_tree(right, ...)`)
   added to support bushy/`RIGHT JOIN` trees. Verified directly: the only
   depth guard (`if leaves.len() >= 8 { return None; }`, :163) sits inside
   the `Leaf` match arm, i.e. it only fires *after* the recursion has
   already walked all the way down to a leaf — for a left-deep chain
   (`FROM t1 JOIN t2 ON true JOIN t3 ON true ... JOIN tN ON true`, which is
   exactly how `pg_query`'s grammar associates a flat `JOIN` list), the
   walk must recurse to depth **N** before the cap can ever be checked. The
   size check at the call site (`:322`) also runs only after `walk_tree`
   returns. Confirmed no upstream gate: `four_table_join`/
   `four_table_plan_applies` (:814, :826) are called directly on the full
   parsed join tree from `crates/secantus-pg/src/lib.rs:7710` (`join_rows`,
   the general join path) and `crates/secantus-pg/src/stream_join.rs:780`,
   with no join-count bound applied before the walk. The fix pattern
   already exists in this codebase and simply wasn't reused here:
   `crates/secantus-pgplan/src/lib.rs:3754-3769`'s `MAX_EXPR_DEPTH`/
   `nesting_bound()` is an *iterative* pre-scan, with the comment
   "Scanning is iterative, so this is safe on any input," that raises
   PostgreSQL's real `stack depth limit exceeded` (53200-class) error
   before any recursive planning starts. A single authenticated SQL client
   issuing a query with a long `JOIN` list (well within ordinary message-
   size limits — no huge document, no special privilege) crashes
   `secantusd-pg` for every connected session. Note: `build_join`/`build`
   in `crates/secantus-pgplan/src/joins.rs` (:549, :1022) already recurse
   over the same join tree with no depth guard and are *pre-existing*, not
   new this window — so some exposure to this exact shape may already have
   existed via that path before this cycle; what is newly introduced and
   attributable to this diff is the second, independent recursive pass in
   `join_order.rs` that the prior audit specifically relied on being safe.

5. **Unbounded heap allocation (OOM abort) via a single `applyOps`
   array-diff entry — `crates/secantus-commands/src/apply_ops.rs::apply_subdiff`
   (~:850-885), new this window.** Verified directly by reading the
   function: when an array sub-diff entry has no `"l"` (resize) key, the
   bound check at :875 (`resized.is_some_and(|len| idx >= len)`)
   short-circuits to `false` because `resized` is `None` — it is simply
   skipped — so `while items.len() <= idx { items.push(Bson::Null); }`
   (:883-885) runs with `idx` parsed straight from an attacker-chosen key
   suffix (e.g. `{"u9999999999": 1}` → `idx = 9999999999`) with **no upper
   bound of any kind**. A ~30-byte `applyOps` entry (one `op:"u"`, `$v:2`
   diff, one array sub-diff with one such key) forces an attempt to
   allocate billions of `Bson` elements before any `MAX_BSON_OBJECT_SIZE`
   check ever runs (that check only applies later, inside
   `storage.insert`/`update_matching`). Rust's default behaviour on
   allocation failure is `abort()`, not an unwind — so this is **not**
   caught by the per-request `catch_unwind` at
   `crates/secantus-server/src/lib.rs:1112` the way an ordinary panic would
   be. Call path, confirmed: `pymongo` → `applyOps` command →
   `apply_ops::apply_ops` (:121) → `apply_entry` `"u"` branch (:424) with
   `$v:2` → `apply_diff` (:765) → `apply_subdiff` (:830). `applyOps`
   requires the `applyOps` cluster privilege only when `--auth` is enabled
   (matching mongod's own model); with `--auth` off — the default — any
   connected client can trigger this.

## 🟠 WARNING (Address within 1 week)

### New this cycle

1. **Panic on a non-char-boundary split — `crates/secantus-commands/src/apply_ops.rs::apply_subdiff`
   (:858-864).** The guard `k.chars().count() < 2` (:858) counts Unicode
   *characters*, but `k.split_at(1)` (:864) splits at *byte* offset 1. A
   diff-array key whose first character is multi-byte UTF-8 (e.g. `"é0"`,
   2 chars / 3 bytes) passes the length check and then panics ("byte index
   1 is not a char boundary") inside `apply_subdiff` — one level up from
   CRITICAL finding 5, same call path. Unlike finding 5 this *is* a
   recoverable panic, caught by the per-request `catch_unwind`, so it drops
   one request rather than the whole process — WARNING, not CRITICAL.
2. **Unconfirmed panic path — `crates/secantus-commands/src/session.rs:868`,
   `.expect("handle created above")`** inside the transaction-statement
   path (`statement`/`run_checked`). Relies on an invariant that
   `t.handle` was populated earlier in the same transaction's lifecycle;
   not every code path that could reach this with `handle == None` under
   adversarial `txnNumber`/`autocommit` sequencing was traced to exhaustion
   in this review. PLAUSIBLE, not CONFIRMED — flagging for a dedicated
   follow-up probe. Caught by `catch_unwind` either way (per-request, not
   process-wide).
3. **Integer over/underflow in time-series bucket-bound arithmetic —
   `crates/secantus-commands/src/timeseries.rs:702`,
   `let (at_low, at_high) = (at - self.span_ms, at + self.span_ms);`.**
   `at` comes directly from a client filter's BSON date value on a
   time-series collection's time field, unconstrained by pymongo's own
   `datetime` range on the wire; an extreme value near `i64::MIN`/`MAX`
   plus an *unrecognized* `hint` (`timeseries::check_hint` only
   short-circuits for a *known* index) reaches `bucket_filter` →
   `time_bounds`. No release profile in the repo sets
   `overflow-checks = true`, so a release build silently wraps (affecting
   only the refusal-message text, not actual query execution, per the
   reviewing agent's read of `bucket_filter`'s caller), while a debug/test
   build panics with "attempt to add with overflow" — a per-connection DoS,
   caught by `catch_unwind`.
4. **Permanent cross-connection deadlock via two opposite-direction
   `renameCollection` calls — `crates/secantus-commands/src/lock_manager.rs`
   (:336, :619-623) and the non-transactional `statement_chain` path
   (`lib.rs:2004`).** Plain (non-transactional) CRUD/DDL statements have no
   built-in per-request lock-wait timeout — the wait is bounded only by
   `secantus_core::deadline::expired()`, itself armed only from a
   client-supplied `maxTimeMS` (`lib.rs:1984-1988`); the module's own doc
   comment (`lock_manager.rs:23-26`) states this is deliberate, matching
   mongod. Two concurrent, non-transactional `renameCollection` calls in
   opposite directions (connection A: rename X→Y, connection B: rename
   Y→X) each lock their *source* collection before their *target*
   (:517-525) — a fixed order per call that differs across the two calls —
   a textbook AB/BA deadlock across two connections. Neither client-side
   `maxTimeMS` is required by the command, so without one supplied, both
   renaming threads (and any later request needing a lock on either
   collection) hang **forever**, with no server-side timeout or deadlock
   detector on this path. Thread-per-connection means this is a
   per-connection-pair resource leak rather than a literal whole-server
   hang, but it is attacker-triggerable and repeatable (two stuck threads
   per pair, every time) with no safety net.
5. **Rate limiter fails open on mutex poisoning —
   `crates/secantus-commands/src/params.rs:290-293`,
   `let Ok(mut bucket) = self.ingress.lock() else { return true; };`.** On
   `Mutex` poisoning, `admit_connection()` returns `true`, silently
   admitting every subsequent connection and permanently disabling the
   limiter for the rest of the process's life. Inconsistent with this same
   file's own convention elsewhere (`.unwrap_or_else(|e| e.into_inner())`,
   used throughout `params.rs` and most of `secantus-commands`) and with
   the project's own "never silently let an error through" principle
   (`CLAUDE.md`, "Never ignore or discount an error"). Currently
   low-likelihood (the locked section is pure arithmetic with no obvious
   panic path today) but a latent trap for any future change inside that
   lock scope.
6. **Connection rate limiter does not prevent the resource it is named
   for — `crates/secantus-server/src/lib.rs:486-502`.** The admission
   check (`conn_shared.server_params.admit_connection()`) runs *inside* a
   thread that `thread::spawn` already created for every accepted TCP
   connection, before the check runs. A raw connection flood still forces
   one OS thread spawned per `connect()` regardless of what the limiter
   decides — it throttles reply issuance, not thread/stack creation, which
   is exactly the resource the limiter's name implies it bounds. (The
   limiter is off by default, matching mongod's own default-disabled
   posture for `ingressConnectionEstablishmentRateLimiterEnabled`, and is
   a single global, unkeyed token bucket — also matching mongod — so
   neither of those is itself a finding.)
7. **Swallowed thread-join failure on the storage close path —
   `crates/secantus-storage/src/lib.rs:6254` and `:6262`,
   `let _ = h.join();`** for both the checkpoint-join and the new
   journal-join handles. A panicked journal-flusher or checkpoint thread's
   result is silently discarded at close time, while the adjacent new
   async-oplog-drainer code added in the same window was hardened to
   report exactly this failure class via the new fallible `Storage::close()`.
   Per `CLAUDE.md`'s "Never ignore or discount an error... this is a
   database" rule, a close-path error (here, evidence that a background
   writer thread panicked) should surface, not vanish — this is the one
   place in an otherwise carefully fallible-close-reworked file that still
   discards it.

- **Top 3 priorities for the team:**
  1. **Give the unguarded-recursion class a structural fix, not another
     one-off patch.** Four independent new instances landed in a single
     batch of feature work (findings 1–4), on top of the ~27 already
     tracked from 2026-08–2026-10-17 and the still-open `#1780` (`bson`
     decoder). The project already has the right pattern in its own

     `crates/secantus-pgplan/src/lib.rs:3754-3769`'s `MAX_EXPR_DEPTH` +

     default posture.
  3. **Bump the `pymongo` floor to `>=4.18.2`** (`#1742`) — unchanged for
     a sixth cycle, still the cheapest fix in the whole open tracker,
     against a CVSS-8.4 heap-out-of-bounds-write CVE.
