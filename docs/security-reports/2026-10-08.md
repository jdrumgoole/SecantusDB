## 🟠 WARNING (Address within 1 week)

### 1. The new WiredTiger dsync group-commit patch applies one of its optimizations to *every* sync method, not just the one its own docstring says it's scoped to — and the affected path (`method=fsync`, used by both MongoDB servers and the non-macOS PostgreSQL server) is explicitly untested

`cmake/patch_wt_dsync_group.py` (new in `dae59af5`, "perf(pgserver): group
commit for method=dsync in the vendored WiredTiger") patches WiredTiger's
`src/log/log.c` / `src/log/log_slot.c` to let concurrent `WT_LOG_DSYNC`
commits share one log-slot write instead of each forcing its own — a real,
measured perf win (30.9k → 37.3k commits/s at 8 clients on macOS,
`secantusd-pg`), and the commit message documents genuine fault-injection
validation (a kill-test harness passing 10/10 for the correct build and
failing 3/3 for a deliberately-broken one).

The module docstring states up front: *"What the patch changes, for a
`WT_LOG_DSYNC` commit only"* — and four of its five edits are in fact gated
by a `grouped` boolean that is `false` unless `LF_ISSET(WT_LOG_DSYNC)` holds.
**The fifth edit is not.** It patches `__wt_log_release`'s directory-sync
wait loop (a different function from the one `grouped` is scoped to) to skip
taking `log_sync_lock` when `log->sync_dir_lsn.l.file >=
slot->slot_end_lsn.l.file` already holds — with no conditional on sync
method at all:

```c
while (F_ISSET_ATOMIC_16(slot, WT_SLOT_SYNC | WT_SLOT_SYNC_DIR)) {
    /* secantus-patch: dsync group commit */
    if (!F_ISSET_ATOMIC_16(slot, WT_SLOT_SYNC) &&
      log->sync_dir_lsn.l.file >= slot->slot_end_lsn.l.file) {
        F_CLR_ATOMIC_16(slot, WT_SLOT_SYNC_DIR);
        break;
    }
    ...
```

This runs for **every** commit on **every** WiredTiger-backed server in this
project — both MongoDB servers (`method=fsync` always) and the PostgreSQL
server off macOS (`method=fsync`) — not only the intended
`secantusd-pg`-on-macOS `method=dsync` path. It reads `log->sync_dir_lsn`
without the lock that the surrounding stock code otherwise takes for exactly
this check, as a lock-free fast-path short-circuit.

Two reviewers independently read this and neither could rule out a problem
by static inspection alone (no `vendor/wiredtiger` checkout in this
sandbox to compare against stock behavior, and no ability to build/run a
fault-injection test here): the concern is whether this unlocked read of
`sync_dir_lsn` can observe a value that lets a waiter exit the loop and
report "directory synced" before the directory entry is actually durable,
on a code path that was never exercised by this change's own kill-tests
(which only drove the macOS `dsync` path). This project's own task notes
(`tasks/backlog.md`) say exactly that: the `fsync` path this edit also
touches is **"NOT measured: Linux."** Given this project's standing rule
that a storage-durability defect is never noise ("Never ignore an error —
this is a database"), an optimization that silently widened its own
documented scope to cover the one path it didn't fault-test deserves a
dedicated review and a kill-test run under `method=fsync` on Linux before
being trusted at the same level as the `dsync` path its own validation
covered.

**New finding — filed.**
