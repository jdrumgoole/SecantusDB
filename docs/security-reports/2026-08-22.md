### #995 (carried forward, still open, re-confirmed)

`crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`) — re-read in
full this cycle, byte-for-byte unchanged (last touched by commit `d91fb72d`,
well before this window):

```rust
pub fn body_len(&self) -> Result<usize, WireError> {
    if (self.message_length as usize) < HEADER_SIZE {   // message_length: i32
        return Err(...);                                 // sign-extends to
    }                                                     // usize::MAX for a
    if self.message_length > MAX_MESSAGE_SIZE {           // negative value,
        return Err(...);                                 // defeating this
    }                                                     // check
    Ok(self.message_length as usize - HEADER_SIZE)         // still-signed i32
}                                                           // compare, also
                                                             // defeated
```

Independently traced the full path this cycle: a wire frame with
`message_length = -1` (bytes `FF FF FF FF`) casts to `usize::MAX` under the
first check (not `< 16`), and the second check still compares the signed
`i32` (`-1 > 48_000_000` is false), so both guards pass and `body_len()`
returns `usize::MAX - 16`. The caller
(`crates/secantus-server/src/lib.rs:558`) then calls
`shared.alloc_budget.acquire(body_len)` — read `AllocBudget::acquire` in
full this cycle (`lib.rs:87-94`): `while *used != 0 && *used + n > self.cap`
only blocks when another allocation is *already* outstanding, precisely to
let one legitimately large (≤48MB) request through without deadlocking; a
lone connection with `used == 0` sails through regardless of `n`'s size.
Immediately after, `let mut body = vec![0u8; body_len];` attempts a
~`usize::MAX`-byte allocation, which aborts the process via
`handle_alloc_error` — a single unauthenticated 16-byte frame kills the
whole Rust server. Not fixed. Tracked as **#995**.
