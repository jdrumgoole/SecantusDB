## 🟠 WARNING (Address within 1 week)

### New this cycle

- **DROP DATABASE's busy-check is blind to a connection that is mid-login to
  the target database, letting an attacker-paced client evade it and keep
  using a database after it is dropped.** RP-344's `refuse_busy_database`
  (`crates/secantus-pg/src/database_ddl.rs:82`, used by `DROP DATABASE`,
  `CREATE DATABASE ... TEMPLATE` at line 296, and `ALTER DATABASE ... RENAME`
  at line 410) decides whether the operation may proceed purely by scanning
  `backend_registry()`. A connection joins that registry only in
  `post_startup` (`crates/secantus-pg/src/lib.rs:26548`), reached only after
  its SCRAM/password proof succeeds. But `select_database`
  (`lib.rs:26479-26516`, called from `on_startup` at line 25761) binds the
  target database name to the connection *before* the password check, during
  a SCRAM round trip the client fully paces — no `authentication_timeout` is
  enforced anywhere in the crate (it exists only as an inert
  `pg_settings`-compatibility row, `pg15_settings.tsv:9`). A concurrent
  `DROP DATABASE` therefore sees zero other sessions throughout its
  5-second retry budget and succeeds while a connection is actively mid-connect
  to that exact database, directly contradicting the handler's own invariant
  comment (`lib.rs:38671-38672`). Independently confirmed by a fresh verifier
  re-reading every cited line from scratch, including the two additional call
  sites a coverage-critic found share the same gap. **Fix:** enforce the
  already-declared `authentication_timeout` so the pre-auth window has a
  bound; if pending (pre-auth) connections are also made visible to the
  busy-check, that visibility needs its own enforced timeout too, or a flood
  of never-authenticating connections becomes a new way to block legitimate
  DDL. Bounded to this single local dev/test server (CLAUDE.md's threat
  model) — no cross-host or privilege-escalation effect, and the racing
  session must still eventually hold valid credentials.
- **EXPLAIN's new RP-320/RP-321 cost-estimation blocks do uncapped O(n²)
  target-list de-duplication, which `statement_timeout`/`CancelRequest`
  cannot interrupt.** `crates/secantus-pg/src/lib.rs:40794-40795` (RP-320,
  reached for `SELECT DISTINCT ... ORDER BY ...` over an unindexed table via
  a `Unique → Sort → Seq Scan` plan shape) and `lib.rs:40894-40899` (RP-321,
  a plain `Aggregate` of `count(...)` targets) each dedup a
  client-controlled-length column list with a `Vec::contains`-in-a-loop
  scan — O(n²) when the n columns are pairwise distinct. No code bounds `n`:
  `plan_create` (CREATE TABLE, `crates/secantus-pgplan/src/lib.rs:10571-11154`)
  has no column-count cap, and the one size guard, `MAX_TEXT_BYTES`
  (`lib.rs:4308`), only disables plan-memoization caching past 2 MiB rather
  than rejecting the statement. Both loops run synchronously in a non-`async`
  function with no cancellation checkpoint, so neither `statement_timeout`
  nor `CancelRequest` can stop one mid-flight. Independently confirmed and
  re-scoped by a fresh verifier: `secantus-pg` runs one dedicated OS thread
  per connection (`crates/secantus-pg/src/server.rs:762-808`), so the stall is
  confined mainly to the attacking connection's own thread/CPU core — the
  realistic effect on other sessions is CPU-contention-driven slowdown
  proportional to the host's spare cores, not a hard whole-process freeze (a
  correction to the hunter's initial, stronger framing). **Fix:** replace
  both `Vec::contains` scans with a `HashSet`-based O(n) dedup.
