## 1. The headline finding: unpatched ICU 57.1, vendored directly (not as a
   submodule), reachable via an unbounded client-supplied locale string

This review's single most serious finding does not come from this project's
own code so much as from what it now links: `crates/secantus-icu` (new this
window) vendors real ICU 57.1 — released in **2016** — directly into the
repository as 818 plain files under `vendor/icu4c-57.1`, *not* as a `git
submodule` the way every other vendored dependency (WiredTiger, every
driver) is. A public CVE, **CVE-2016-7415**, documents a stack-based buffer
overflow in exactly the ICU routine (`Locale` construction) and exactly the
trigger shape ("a long locale string") that a client's `$collation.locale`
field reaches with zero length validation anywhere in SecantusDB's own Rust
code. See the CRITICAL section below for the full trace; see Section 3 for
the advisory research.

## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Unbounded, unauthenticated client-supplied `$collation.locale` string
  reaches `icu::Locale::createFromName` in unpatched, directly-vendored ICU
  57.1 — the exact library, routine, and trigger shape a public CVE
  documents** (high/high/high). `crates/secantus-core/src/collation.rs`
  reads a client command's `collation.locale` BSON field (`f.locale`, lines
  105/161/251) with no maximum-length check anywhere in the file — only a
  null-byte rejection (line 534) and an empty-string rejection (line
  573-578), both applied only after the ICU call. The unbounded string
  (`crates/secantus-core/src/collation.rs:533`) is handed to
  `Collator::open(&locale)` (line 562), which in
  `crates/secantus-icu/src/lib.rs:147-179` does `CString::new(locale)` with
  no length cap and passes the raw pointer into the `extern "C"` call
  `secantus_icu_open`; the 160-byte `name`/`valid` buffers in that function
  are *output*-only (confirmed via `shim.cpp`'s `strncpy` usage) and never
  truncate the input. `crates/secantus-icu/shim/shim.cpp:32` calls
  `icu::Locale::createFromName(locale)` directly on the full, unbounded
  pointer. **CVE-2016-7415** ("Stack-based buffer overflow in the Locale
  class in common/locid.cpp in International Components for Unicode (ICU)
  through 57.1 for C/C++ … via a long locale string") describes exactly this
  function and exactly this trigger shape; `vendor/icu4c-57.1` (added
  verbatim from mongod r8.2.11's own ICU build, commit `109f5401`, this
  window) carries no patch file or changelog evidence of a backport for this
  2016 advisory. The only size ceiling anywhere above this path is the
  generic 16 MiB BSON document limit — a locale string of a few hundred
  bytes is sufficient and is accepted at every layer above ICU.
  `require_auth` defaults to `false` (`crates/secantus-server/src/args.rs:583`),
  so an ordinary, unauthenticated `find`/`aggregate`/`createIndexes` command
  on any collection reaches this path with no credential of any kind. An
  independent verifier re-read every cited line, re-confirmed the CVE's
  identity, affected-version range and trigger shape against multiple public
  sources, and confirmed no patch/backport evidence exists anywhere in the
  vendored tree.
  **Fix:** add an explicit maximum-length check on `locale` (a real ICU
  locale ID is never more than a few dozen bytes) before any FFI call into
  ICU, in `crates/secantus-core/src/collation.rs` and/or defensively in
  `crates/secantus-icu/src/lib.rs::Collator::open`; separately, track and
  apply the upstream fix for CVE-2016-7415 (and CVE-2016-6293, same affected
  range) in the `vendor/icu4c-57.1` build, consistent with this project's
  existing pattern of patching vendored C/C++ dependencies via dedicated
  patchers rather than hand-editing the vendored tree.
  **Filed as a new issue** (duplicate search for "icu", "locale collation"
  found no existing coverage).

- **Slow-query log embeds the full, untruncated client command into a
  process-wide shared ring buffer with no per-entry byte bound** (medium/
  high/high). `crates/secantus-commands/src/slowop.rs::command_shown()`
  (lines 544-552) strips only an `insert`'s `documents` array; everything
  else in a client's request — filters, update/replacement documents,
  pipeline stages, large literal values — is cloned verbatim and inserted
  into a `Slow query` log line's `attr.command`
  (`slowop.rs::attributes()`, line 587), which `crates/secantus-server/src/lib.rs:1326`
  appends to `Shared.logs`, a single `Arc<LogBuffer>` created once at server
  start and shared by every connection the process serves. The sibling
  control added in this same window for `system.profile`,
  `profiler/record.rs::abbreviated()` (`MAX_COMMAND_BYTES = 50 * 1024`), is
  never applied to this path. `LogBuffer` (`crates/secantus-commands/src/logbuf.rs`)
  evicts strictly by entry COUNT (`DEFAULT_CAPACITY = 5000`, line 18) with
  no byte-size accounting anywhere in the file. The decision to log is
  purely time-based (default `slowms=100ms`, `sample_rate=1.0`, both active
  out of the box) with no privilege/role gate, so any client with ordinary
  read/write privilege on one collection it may query can trigger it. A
  single command document is bounded only by the ~48 MB wire message cap,
  not the 16 MB `MAX_BSON_OBJECT_SIZE` (the latter is enforced on stored
  documents, not on the wire-layer parse of a command document itself). A
  verifier independently confirmed the full chain, the complete absence of
  any byte-size accounting in `logbuf.rs`, and the asymmetry against the
  sibling profiler control, and corrected the realistic worst-case growth
  estimate to "tens of GB under sustained abuse" rather than the
  theoretical maximum.
  **Fix:** apply `profiler::record::abbreviated()`'s truncation (or an
  equivalent) to the command field `slowop.rs::attributes()` inserts before
  it reaches `LogEntry`/`shared.logs.log()`; add a byte-level backstop to
  `LogBuffer` itself as defense in depth.
  **Filed as a new issue** (duplicate search for "slowop", "logbuf", "slow
  query" found no existing coverage).
