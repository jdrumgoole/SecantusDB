through today's `HEAD` (`3e52e1d7`) — the busiest window in several cycles.
Highlights: a new server-wide SQL advisory-lock feature (`AdvisoryLockHub`,

new `TransactionTooLargeForCache` rejection path, #787/#789/#791/#792/#793/

(#799/#802/#804), and one SQL numeric-scale feature (#803).

This cycle's method: rather than only re-confirming the standing findings
from 2026-08-09 (C1, C2, W1–W5), a full line-by-line review of every commit
in the window was run against the same "does authorization/DoS/panic-safety
hold" lens applied to prior cycles. That surfaced one genuine **new
WARNING**, filed below as **W6**: `configureFailPoint` — present on both
servers, wired into every `SecantusDBServer`/Rust server instance
unconditionally (not test-gated) — is absent from both servers' RBAC action
tables (`_COMMAND_ACTIONS` / `command_action()`), so it silently takes the
"no privilege required" fallback path. With `--auth` off (the default), any
unauthenticated wire client can arm a server-wide `failCommand` failpoint
(e.g. `closeConnection: true, mode: alwaysOn` against `find`) and DoS every
connected client, not just its own. With `--auth` on, an authenticated
principal holding zero role grants can do the same.

The 2026-08-08/09 cycles' successful "does this bug's *shape* recur
elsewhere" method was reapplied specifically to the new `#801` advisory-lock
feature (the most novel security-relevant surface introduced this cycle) —
that turned up clean: session-scoped acquire/release matches PostgreSQL's
actual advisory-lock semantics, release-on-disconnect is guaranteed via a
`finally` block, and the blocking wait doesn't hold the storage-wide lock.
No cross-session unlock path exists. See §5 for the full trace.

All other standing findings (C1, C2, W1–W5, all INFO items) were
independently re-confirmed against the live tree this cycle; two had their
cited line numbers shift due to unrelated upstream churn (W1, W2 — noted
below), and one (**W4**) appears to have been fixed as a side effect of the

**New this cycle — W6 (WARNING): `configureFailPoint` has no RBAC action
mapping on either server — an unprivileged or unauthenticated client can
arm a server-wide DoS failpoint.**

Both servers wire a single, per-server-instance `FailPointRegistry`
unconditionally, in production code, not gated behind a test-only flag:

- Python: `src/secantus/server.py:201` `self.failpoints =
  FailPointRegistry()`, passed into every `CommandContext` (`:711`, `:801`).
- Rust: `crates/secantus-server/src/lib.rs:379`
  `Arc::new(secantus_commands::failpoints::FailPointRegistry::new())`,
  attached via `.with_failpoints(...)` at `:870`.

`configureFailPoint` is dispatched at `commands.py:5812` /
`crates/secantus-commands/src/lib.rs:451`, and is **not** listed in
`_NO_PRIVILEGE_COMMANDS` (`commands.py:5952-5975`) — so it isn't explicitly
exempted the way `getMore`/`ping`/`hello` are — but it is **also absent
from `_COMMAND_ACTIONS`** (`commands.py:5866`, and the Rust mirror
`command_action()` at `crates/secantus-commands/src/lib.rs:1330`, whose own
doc comment spells out the fallback: *"`None` for 'no privilege required'
(a permissive default — an authenticated user with any role can invoke
it)"*). The RBAC gate at `commands.py:6668-6694` only runs a check when
`_COMMAND_ACTIONS.get(name)` returns something; for `configureFailPoint` it
returns `None`, so the `if info is not None:` guard is false and the
command reaches its handler with **zero** privilege check. Rust's
`command_action(name)` match arms (`lib.rs:1332` onward) likewise have no
`"configureFailPoint"` arm.

**Concrete failure scenario:**
- **`--auth` off (the default):** any TCP client that can reach the
  listener — no credentials at all — sends
  `{configureFailPoint: "find", mode: "alwaysOn", data: {closeConnection: true}}`.
  Every subsequent `find` on *any* connection (not just the attacker's) has
  its socket abruptly closed by the server (`commands.py:6705-6710`'s
  documented `close_connection` behavior). This is a cross-tenant,
  wire-reachable DoS with no privilege required, reachable the moment the
  port is open.
- **`--auth` on:** a principal that authenticated successfully but was
  granted **zero** roles (e.g. `createUser` with an empty `roles: []`, a
  state every other command correctly rejects at
  `commands.py:6686-6694`'s `Unauthorized` path) can still call
  `configureFailPoint` freely, because the check never runs for this
  command name.

Real `mongod` ships the equivalent `configureFailPoint` command too, but
gates it behind the `enableTestCommands=1` startup parameter — off by
default in any real deployment, and additionally requires a privileged
role even when enabled. SecantusDB has no equivalent opt-in gate at all;
the feature is always live.

**Severity rationale:** filed as WARNING rather than CRITICAL — this is a
DoS, not a data-exposure/RCE primitive, SecantusDB's default bind is
loopback-only per §8 (so exploitation needs some form of local/network
reachability, same calibration CLAUDE.md applies to the admin UI's
loopback-only CSRF gap), and the feature exists specifically to let driver
conformance-test suites simulate `mongod` failures — this is a genuine gap
in how that feature is gated, not a data-integrity or authentication
bypass. It is filed as a WARNING rather than INFO because it *is*
wire-reachable with **zero** authentication in the default (`--auth` off)
configuration and its blast radius is every connected client, not just the
caller's own session — a materially different risk than a
defense-in-depth-only gap.

**Recommendation:** add `"configureFailPoint": (A_SERVER_ADMIN or
equivalent, SCOPE_CLUSTER)` to both `_COMMAND_ACTIONS` and Rust's
`command_action()` so `--auth` deployments require an explicit admin-level
grant; separately, consider mirroring mongod's `enableTestCommands`
opt-in gate (default off) so the command surface doesn't exist at all
unless a test harness explicitly asks for it, closing the `--auth`-off
gap too. Add a regression test: an authenticated zero-role principal
attempting `configureFailPoint` should get `Unauthorized` (13), and (if
the opt-in gate is added) an unauthenticated client without
`enableTestCommands` should get `CommandNotFound` (59).

**New this cycle — #801 `AdvisoryLockHub` traced end-to-end, found sound.**
`pg_advisory_lock`/`pg_try_advisory_lock`/`pg_advisory_unlock` and friends
route through a server-wide `AdvisoryLockHub` shared across all SQL
sessions. Verified: lock keys are the same `(classid, objid)` / single
64-bit-int pairing Postgres uses (not attacker-arbitrary beyond the normal
SQL argument space); a session can only release a lock it itself holds —
no cross-session unlock code path exists anywhere in the hub; release on
both graceful disconnect and abnormal connection teardown is guaranteed via
a `finally` block in `pgserver.py`'s connection-handling loop (so a client
that drops mid-hold cannot leak the lock forever); the blocking
`pg_advisory_lock` wait does not hold the storage-wide `RLock`, so it can't
stall unrelated Mongo-wire or other SQL-session storage operations while
parked. This matches real Postgres's actual advisory-lock semantics
(session-scoped, not row/table-scoped) rather than inventing a new gap.
Only a soft note, filed as INFO not a standing finding: there is no cap on
the number of distinct lock keys a single session can hold — same trust
tier as being able to run arbitrary SQL against the connected database, so
not independently exploitable, but worth a bound if the SQL server is ever
exposed to less-trusted callers than it is today.

`--auth` gating (Mongo-wire, general): re-confirmed unchanged —
`_NO_PRIVILEGE_COMMANDS` allowlist minimal (aside from the new W6 gap),
`getMore` cursor ownership check present (I18, unchanged).
