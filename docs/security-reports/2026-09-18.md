## 🔴 CRITICAL (Immediate action required)

All three unchanged, re-confirmed by direct read against current HEAD:

- **#995** — `crates/secantus-wire/src/lib.rs:137-150` (`Header::body_len`).
  Re-read in full this cycle: `if (self.message_length as usize) < HEADER_SIZE`
  casts the signed `i32` to `usize` first — `message_length = -1`
  sign-extends to `usize::MAX` on 64-bit, which is not `< HEADER_SIZE (16)`,

  against `MAX_MESSAGE_SIZE`, so a negative value also passes it. The

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **NEW — reachable panic in the new PostGIS WKT parser, `crates/secantus-
  pgplan/src/geometry.rs`.** The `Wkt` struct (added this cycle by
  `2cc51808`, part of the hstore/PostGIS/roles feature) walks a `&str` with a
  byte offset `self.pos` and, on several syntax-error paths, advances that
  offset by a raw `self.pos += 1` before calling `fail()`, which slices
  `&self.s[..self.pos]` (`geometry.rs:442-445`). The advance-by-one is safe
  only when the byte at `pos` is single-byte ASCII; every one of these error
  paths runs precisely when the parser has just found something OTHER than
  the ASCII token it expected, which includes a multi-byte UTF-8 character
  sitting at that offset. When it is, `self.pos += 1` lands mid-character and
  the subsequent `&self.s[..self.pos]` slice panics with "byte index N is not
  a char boundary" — an unhandled `panic!` unwinding the connection's request
  thread. Seven call sites carry the same pattern: `geometry.rs:506, 512,
  521, 533, 552, 684, 696` (the safe, ASCII-only-stepping uses inside `ws()`
  / `word()` / `number()` at lines 450/468/479 are not affected, since those
  loops only ever consume a byte they already confirmed is single-byte
  ASCII).

  **Confirmed by direct reproduction, not just code reading.** A temporary
  `#[test]` was added to `geometry.rs` calling
  `from_text("POINT(1 \u{1F600})")` (a WKT point whose second ordinate is
  replaced by an emoji) and run via `cargo test -p secantus-pgplan
  secreview_repro_nonascii_panic -- --nocapture`:

  ```
  thread 'geometry::tests::secreview_repro_nonascii_panic' (16651) panicked at secantus-pgplan/src/geometry.rs:443:20:
  end byte index 9 is not a char boundary; it is inside '😀' (bytes 8..12 of string)
  ```

  The test file was reverted immediately after (`git checkout --
  crates/secantus-pgplan/src/geometry.rs`; `git status --short` confirmed a
  clean tree before continuing the review) — no fix was attempted, per this
  run's scope.

  **Reachability:** `geometry::from_text` is called directly from
  `crates/secantus-pgplan/src/scalar.rs:227` (`st_srid(text)`) and `:232`
  (`st_astext`/`st_asewkt`), i.e. straight from a client-supplied SQL string
  argument such as `SELECT st_srid('POINT(1 😀)')` — no cast machinery, no
  authentication (the PG server has none at all, #1191), one query. This is
  the same bug *class* already tracked at WARNING tier for the sibling
  `expressions::parse_date_text` boundary panic (**#1455**) and the broader
  Rust unbounded-recursion/panic family (14 tracked instances) — a single
  crafted request panics the handling thread, not the whole process (no
  `panic = "abort"` in any workspace `Cargo.toml`, no `catch_unwind` found in
  `secantus-pgserver`), which is why this is WARNING and not CRITICAL, same
  as #1454/#1455's classification. **Filed as a new issue this cycle** (see
  "Actionable findings" below) since it is a distinct file/function from
  every one of the 46 already-open security issues.

- **Examined but NOT filed separately — two new PG-server capability
  surfaces that inherit, rather than extend, the already-tracked #1191 gap.**
  Both are genuinely new code this cycle and both were checked for their own
  distinct authorization defect (not just "no auth at all"), and in both
  cases the defect found is exactly the blanket gap #1191 already covers, so
  filing them separately would fragment one root cause into duplicate
  tickets:
  - **Prepared-transaction hijack.** `COMMIT PREPARED '<gid>'` /
    `ROLLBACK PREPARED '<gid>'` (`crates/secantus-pgserver/src/lib.rs:6903-
    6935`, `finish_prepared`) resolve `gid` via `Storage::commit_prepared` /
    `rollback_prepared` with **no comparison against the `owner` field**
    recorded at `PREPARE TRANSACTION` time (`crates/secantus-storage/src/
    lib.rs`'s `PreparedXact.owner`, threaded through but never read back on
    finish). In real PostgreSQL, `COMMIT PREPARED`/`ROLLBACK PREPARED` is
    restricted to the preparing role or a superuser; here any connection can
    resolve any other connection's parked transaction. A resource cap does
    exist (`MAX_PREPARED_TRANSACTIONS = 100`, a `199`-byte gid cap matching
    PostgreSQL's `GIDSIZE`) — the gap is authorization, not exhaustion, and
    is the same "every connection is trusted" gap #1191 already tracks.
  - **`pg_authid.rolpassword` disclosure.** `crates/secantus-pgserver/src/
    lib.rs:3344-3375` renders `pg_authid` (unlike the `pg_roles` view, which
    masks every password as `********`) with the raw stored SCRAM-SHA-256
    verifier string. Faithful to PostgreSQL's on-disk format (a verifier,
    never a plaintext password — `RoleInfo`'s doc comment is explicit about
    this), but real PostgreSQL additionally restricts `pg_authid` row
    visibility to the owning role or a superuser via a built-in row-security
    policy; here, with no authentication, any client can `SELECT rolpassword
    FROM pg_authid` and read every role's verifier for offline dictionary
    attack. Same root cause as #1191.

  Both are noted here for the record and to save the next cycle from
  re-deriving them, but are treated as within #1191's existing scope rather
  than filed as new tickets, consistent with how this report's CRITICAL/
  WARNING-filing rule treats "new manifestation of an already-tracked root
  cause."

- Verified CLEAN in the same new code: `hstore.rs`'s binary (`from_binary`)
  and text (`parse`) decoders operate on `&[u8]` throughout (never `&str`
  slicing), use `.get()`-checked bounds on every read, and `syntax_near`'s
  error-position renderer explicitly walks decreasing UTF-8 prefix lengths
  to avoid exactly the boundary panic found in `geometry.rs` — this file does
  not share the defect. `geometry.rs`'s EWKB binary reader (`Reader::u8`/
  `u32`/`f64`/`coords`) is also `&[u8]`-based with `.get()`-checked slicing
  and a pre-allocation size guard (`coords()`'s `saturating_mul` check against
  remaining buffer length) — binary-input paths are sound; only the WKT
  *text* parser has the boundary bug. `CreateRole`/`AlterRole`/`DropRole` set
  and store attributes (`superuser`, `createrole`, `createdb`, ...) that are
  never read back for any authorization decision anywhere in
  `secantus-pgserver` (grepped for `createdb`/`superuser`/`createrole`
  followed by any check — none found) — this is consistent with, not an
  addition to, the "every connection is trusted" model, so it is cosmetic
  rather than a false sense of security (no `GRANT`/`REVOKE` statement exists
  to imply otherwise).
