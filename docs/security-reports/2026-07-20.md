See W1 below.

## 🟠 WARNING (Address within 1 week)

### W1 — Rust storage engine: non-poison-tolerant `.lock().unwrap()` on wire-reachable mutexes, with an escalated blast radius versus the previously-tracked instances

**Files:** `crates/secantus-storage/src/lib.rs:1673-1678` (`coll_lock`) and ~20 call sites including `insert_one` (`:2708`), `insert` (`:2783`), update/delete paths (`:2964`, `:3040`, `:3092`, `:3264`, `:3311`), and the raw-BSON `update_matching`/`delete_matching` paths added by `df66c3f1` (`:5577`, `:5780`); `crates/secantus-commands/src/lib.rs:1030,1041` (per-statement transaction lock); `crates/secantus-commands/src/cursors.rs:191,227,258,284,326,373,394,410,418,429` (cursor registry, find/getMore/killCursors path).

The 2026-07-04 report's I14 tracked five `.lock().expect("...poisoned")` sites (auth/roles) and rated them INFO because their blast radius was one connection and no reachable panic-while-holding-lock path existed. This cycle's `b5a8de59` ("Rust server: per-collection write locks, statement transactions, write-conflict retry") introduced a much larger, structurally different instance of the same anti-pattern: `coll_lock()` mints one `Arc<Mutex<()>>` per `(db, coll)` pair and every CRUD write (`insert_one`, `insert`, update, delete — roughly 20 call sites) takes it via plain `.lock().unwrap()`, not the poison-tolerant `unwrap_or_else(|e| e.into_inner())` pattern used by `failpoints.rs`/`logbuf.rs`/`transactions.rs` and the `conn_auth`/`effective_roles` locks in the same crate.

**Failure scenario:** if any code executing while a collection's write lock is held ever panics (today's audit did not find a concrete trigger — `decode_doc`/`id_key` inside `insert_one`'s critical section are `Result`-propagated, not panic-capable, on the paths checked), the standard library poisons that `Mutex` permanently. Every subsequent write to that specific collection then also panics on `.lock().unwrap()`. The panic itself is caught by the `catch_unwind` boundary in `secantus-server`'s `run_dispatch` (confirmed intact, `crates/secantus-server/src/lib.rs:816-829`), so the process does not crash — but the collection becomes durably unwritable until the server restarts, which is a worse and more persistent outcome than the previously-tracked per-connection blast radius. The cursor-registry (`cursors.rs`) and per-statement-transaction (`lib.rs:1030,1041`) instances are the same pattern with a per-cursor / per-transaction blast radius respectively, both directly reachable from ordinary find/getMore/killCursors and transactional-write wire traffic.

No currently-reachable panic trigger inside any of these critical sections was found in this review pass — this is a defense-in-depth / robustness gap, not a demonstrated live exploit, which is why it's WARNING rather than CRITICAL. It is a genuine regression in blast-radius discipline relative to the pattern the same commit era established elsewhere in the crate, on a code path (every write) with much higher exposure than the previously-tracked auth-mutex instances.

**Recommendation:** convert `coll_lock`'s ~20 call sites, `secantus-commands/src/lib.rs:1030,1041`, and `cursors.rs`'s 10 sites to the same `unwrap_or_else(|e| e.into_inner())` pattern already standard elsewhere in the codebase, so a stray panic degrades gracefully (the operation that triggered it fails, subsequent operations on that collection/cursor/transaction are unaffected) instead of durably wedging a collection, a cursor, or a transaction.

- **I20 — Rust `coll_locks` map is never pruned.** `crates/secantus-storage/src/lib.rs:1268,1673-1678` — the `(db, coll) → Arc<Mutex<()>>` registry grows for the life of the `Storage` instance and is never cleared on `drop`/`dropDatabase`. A client that writes to a very large number of distinct collection names causes unbounded, permanent memory growth. Symmetric with the pre-existing Python-side per-collection bookkeeping; requires sustained, high-cardinality collection creation to matter in practice (not a single-request amplification vector). Worth a `tasks/backlog.md` line; not urgent.
- **I21 (folded from a re-check of `$jsonSchema`, commit `22c27306`) — unbounded schema-nesting recursion.** `src/secantus/query.py:176-320`'s `_check_json_schema_keywords`/`_validate_json_schema` recurse into `properties`/`patternProperties`/`items`/`allOf`/`anyOf`/`oneOf`/`dependencies`/`additionalProperties`/`not` with no explicit depth cap. A pathologically deep schema can raise `RecursionError`, but this shares the exact bounded-impact profile already tracked as the baseline's I1 (`RecursionError` caught by `commands.py`'s blanket `except Exception` at dispatch, one generic internal-error reply, connection survives, no traceback leak). No such secret exists in the codebase today; residual/defense-in-depth risk only.
- **I24 — admin UI routers don't use a centralized Pydantic validation layer.** No `pydantic.BaseModel` found under `src/secantus/admin/routers/`; inputs go through `Form(...)`/path-param type annotations plus manual per-handler checks. Recommend a follow-up sweep of the routers not spot-checked this cycle (`query.py`, `connections.py`).

### Top 3 priorities

1. **Convert the Rust storage engine's `coll_lock` call sites, the per-statement-transaction lock, and the cursor-registry locks to the poison-tolerant `unwrap_or_else(|e| e.into_inner())` pattern** (W1, new) — closes the escalated-blast-radius gap in one pass across ~32 call sites in three files; no live exploit found, but the impact analysis (a durably-wedged collection versus a single dropped connection) makes this worth doing proactively rather than waiting for a triggering panic to be found the hard way.
2. **Add a `cargo audit`/`cargo deny` CI gate** (I22, new) — the Rust dependency sweep in this and the prior report has been manual; a standing gate would catch a newly-disclosed RUSTSEC advisory between review cycles without relying on the nightly review to happen to search for it.
3. **Sweep the remaining Python-side robustness INFOs in one pass** (I1/I21's `RecursionError` handling in `wire.py` and `query.py`'s `$jsonSchema`, I16/I17's PG-server error-surfacing gaps) — none of these are urgent individually (all are bounded-blast-radius, already-caught-by-an-outer-handler cases), but they've now been carried across three consecutive review cycles and share a common fix shape (catch `RecursionError` explicitly, return a typed error instead of a raw string) that would close several items at once.
