## 1. Dependency Vulnerability Check

Re-swept via WebSearch (all queries dated for the current 90-day window).

- **`cryptography` 48.0.0` (dev-only, transitive via `trustme`; see I42
  below for the "why is it even in the lock file" trace):** two new
  advisories published 2026-08-03, **after** the 2026-08-05 report's sweep
  window closed:
  - **CVE-2026-69248** — a name-constrained intermediate CA's
    `permittedSubtrees` check can be bypassed by a wildcard SAN on the leaf
    (`*.example.com` escapes a `foo.example.com` constraint). Fixed in
    49.0.0.
  - **CVE-2026-69249** — duplicate self-signed intermediates in an invalid
    chain trigger exponential path-building recursion (resource-exhaustion
    DoS during verification). Fixed in 49.0.0.
  - Both require **path validation of an attacker-supplied certificate
    chain** to be reachable. `cryptography` reaches this repo only via
    `trustme` (`pyproject.toml` `dev` group, `trustme>=1.2`), and
    `trustme`'s only use in this codebase (`tests/test_tls.py`) is
    **generating** ephemeral self-signed test certs, not **validating**
    attacker-controlled chains — confirmed by grep: zero direct
    `cryptography`/`x509` imports anywhere under `src/secantus/` (the mTLS
    peer-cert path in `auth.py` uses the stdlib `ssl` module's already-
    verified `getpeercert()` output, not `cryptography`'s own path
    builder). And `cryptography` is dev-only — not a runtime dependency of
    the shipped `secantus`/`SecantusDB` wheel (re-confirmed: absent from
    `pyproject.toml`'s base `dependencies` and from the `admin` extra).
    **Not applicable to the shipped product or to any attacker-reachable
    path in this codebase.** Filed as INFO (dependency-freshness), not
    WARNING, on that basis — see I42.
  - The two advisories already tracked as not-applicable in every prior
    report (CVE-2026-39892, buffer overflow, fixed ≤46.0.7; CVE-2026-26007,
    ECC subgroup key recovery, CVSS 8.2) remain not-applicable — pinned
    48.0.0 is past both fix floors. Re-confirmed against `uv.lock`
    (unchanged this cycle: `cryptography==48.0.0`).
- **`pymongo`/`bson` 4.17.0`:** re-checked, still latest (released
  2026-04-20 per the driver's own changelog/releases page); no advisory in
  the 2026-08 window. The historical bson out-of-bounds-read advisory
  (GHSA-cr6f-gf5w-vhrc, fixed 4.6.3) remains long-superseded.
- **MongoDB server-side CVE-2025-14847 ("MongoBleed")** — an unauthenticated
  heap-memory-leak vulnerability in real `mongod`'s zlib-compressed
  `OP_MSG` handling, actively exploited in the wild per multiple vendor
  writeups. Checked for applicability: SecantusDB implements **no wire
  compression at all** — `grep -n "zlib|snappy|compress" src/secantus/wire.py
  src/secantus/commands.py` returns nothing. A client that negotiates
  `compression` in `hello` gets no compressed frames back because the
  server never advertises or accepts one. **Not applicable** — new CLEAN
  item, not previously recorded in any prior report (the advisory itself
  predates this report's cadence but hadn't been explicitly checked
  against SecantusDB's wire layer before).
- **RUSTSEC / `pyo3` / `tokio`:** no advisory newer than the ones already
  tracked under open issue #584 (RUSTSEC-2025-0020, RUSTSEC-2026-0177,
  RUSTSEC-2026-0176, all requiring pyo3 ≥0.29 — this repo remains pinned to
  `"0.22"` in all three PyO3 binding crates, re-confirmed by direct grep
  this cycle). No new tokio advisory affecting the pinned version found.
- **WiredTiger (vendored submodule, mongodb-7.0.33 pin):** no CVE search
  hit specific to the WT storage engine itself in the 2026 window; the only
  MongoDB-branded 2026-relevant CVE found (MongoBleed, above) is in
  mongod's network layer, not WT, and is separately confirmed not
  applicable.

### W1 (carried forward, still open — 17th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:5123` and `:5222` — re-read
both lines directly this cycle; content and line numbers unchanged
(`ctx.oplog.lock().unwrap().live_count` in the prune-sizing path and the
post-sweep count decrement).

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **seventeen** consecutive review cycles.

**Recommendation:** unchanged — convert both sites to
`ctx.oplog.lock().unwrap_or_else(|e| e.into_inner())`.

### W2 (carried forward, still open — 14th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` holds

**File:** `src/secantus/storage.py:6071` (`drop_index`) and `:6188`
(`drop_all_indexes`) — re-read both method bodies this cycle; each still
opens only `with self._lock:`, never `self._coll_lock(db, coll)`. Line
numbers unchanged from 2026-08-05 (no intervening commits).

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.
