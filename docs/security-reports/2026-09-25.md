## 🔴 CRITICAL (Immediate action required)

All three re-confirmed by fresh direct reads against current HEAD:

- **#995** — `crates/secantus-wire/src/lib.rs:100-151` (`Header::body_len`).
  File re-read in full this cycle (zero diff since last report, confirmed by
  `git diff --stat 697778ba..1b935c1e -- crates/secantus-wire`).
  `message_length` is `pub message_length: i32` and `body_len()` still does
  `if (self.message_length as usize) < HEADER_SIZE { ... }` first — for a
  negative `message_length` (e.g. `-1`) this sign-extends to
  `usize::MAX - n`, which is `>= HEADER_SIZE`, so the floor guard does not
  fire; `if self.message_length > MAX_MESSAGE_SIZE` next compares the
  still-negative signed `i32` against a positive bound, which is never true,
  so the ceiling guard does not fire either. The final line
  `Ok(self.message_length as usize - HEADER_SIZE)` returns the same huge
  value minus 16, which the caller feeds to `vec![0u8; body_len]` after an
  `AllocBudget::acquire` that (per the 2026-09-24 re-read, itself zero-diff)
  skips its own wait whenever `*used == 0`. Rust's default allocator aborts
  the process on an allocation failure at this size — one unauthenticated
  16-byte frame takes the whole server down. **Not fixed.**
- **#1160** — `src/secantus/commands.py:8749` (handler table),
  `:8924` (`_NO_PRIVILEGE_COMMANDS`), `:9747-9760` (the RBAC gate). Re-read
  the gate this cycle: `info = _COMMAND_ACTIONS.get(name); if info is not
  None: ...` — skip-on-unknown rather than deny-on-unknown, and a fresh
  grep for `bulkWrite` inside `_COMMAND_ACTIONS`'s literal body (between its
  opening brace and the closing one before `_NO_PRIVILEGE_COMMANDS`) still
  returns nothing. `commands.py` has zero diff this cycle
  (`git diff --stat 697778ba..1b935c1e -- src/secantus/commands.py`). An
  authenticated connection with zero role grants under `--auth` can still
  call `bulkWrite`. **Not fixed.**
- **#977** — `src/secantus/query.py:1407-1471`. Re-read `_compile_regex`:
  the only gate is `len(pattern) > _MAX_REGEX_PATTERN_LEN` (1000 chars)
  ahead of an unbounded `re.compile(pattern, flags)` — no backtracking-depth
  limit, no compile/match timeout — and the `TypeError`-recovery fallback at
  the bottom of `_op_regex` still does a second, uncapped
  `re.compile(regex_pattern, flags)` that bypasses even the length check.
  `query.py` has zero diff this cycle. A short pathological pattern (e.g.
  `(a+)+b`) against an adversarial non-matching string pins a worker
  thread's CPU indefinitely via an unauthenticated `find`. **Not fixed.**

## 🟡 INFO (Best-practice recommendations)

Dependency/CVE sweep this cycle (all manifests zero-diff — confirmed by
targeted `git diff --stat` against `pyproject.toml`, `uv.lock`, and every
`Cargo.toml`/`Cargo.lock` — so any movement here is purely a newly-published
advisory against an unchanged pin):

- **NEW — pymongo CVE-2026-96748** (CVSS 6.5, connection-string host-list
  injection). PyMongo decodes percent-encoded characters in the host portion
  of a `mongodb://` URI *before* splitting the host list on its delimiters,
  so an unauthenticated party who supplies a **hostname fragment** that an
  application later splices into a connection string it builds can smuggle
  in extra hosts of their choosing. Fixed in pymongo 4.18.2; this repo's pin
  is `4.17.0` (`uv.lock`), so the pin is technically behind. **Classified
  INFO, not reachable**: grepped every `MongoClient(` construction in
  `src/secantus/` and found exactly one, `src/secantus/admin/client.py:171`
  (`MongoFacade._get_client`). That call takes `self._uri` verbatim from
  `MongoFacade.__init__`'s `mongo_uri` argument — traced through
  `src/secantus/admin/routers/server.py` and `admin/history.py`, this is the
  **admin dashboard operator's own complete, self-typed URI** (a loopback
  FastAPI app the operator runs locally and drives through its own web form
  — see §10/CLAUDE.md's calibration that this is a trusted local surface,
  not a remote multi-tenant one). The CVE's exploit shape requires an
  application to take a **partial value** (just a hostname) from an
  untrusted third party and interpolate it into a URI *the app itself
  constructs*; nowhere in this codebase is a URI assembled from an
  externally-supplied fragment — the one call site takes the whole string as
  the operator's own input, so there is no boundary for a smuggled host to
  cross that the operator didn't already control. Recommend bumping the
  `pymongo>=4.6` floor to `>=4.18.2` as ordinary dependency hygiene (two
  outstanding CVEs now sit behind this pin, alongside the already-tracked
  GridFS one below) — not urgent enough to file as WARNING given the
  unreachability finding, consistent with this project's existing
  calibration for the `anyio`/`cryptography` INFO entries below.
- `pymongo` CVE-2026-88029 (GridFS NoSQL injection, previously tracked at
  INFO: dependency used only for its bundled `bson` codec, never as a GridFS
  client over attacker input; pin `4.17.0` unchanged, fixed at 4.18.1) —
  re-confirmed still open, still unreachable, still INFO.
- `anyio` CVE-2026-63349, CVE-2026-64847, and `cryptography` CVE-2026-69247
  (all previously classified INFO: unreachable — no `anyio.to_process`/
  `run_process`/`open_process`/process-pool usage and no `pkcs7_*` decrypt
  call anywhere in `src/secantus/`, re-confirmed by fresh grep this cycle)
  — re-confirmed still open, still unreachable, still INFO. No advisory
