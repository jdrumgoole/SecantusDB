rises to a new WARNING:

- **`$currentOp`'s new `appName`/`clientMetadata` fields (#815, both
  servers) were traced for a cross-connection information leak** — real
  `mongod` gates `$currentOp` behind the `inprog` privilege because it can
  reveal *other* sessions' in-flight commands. SecantusDB's `$currentOp` is
  a stub that returns exactly one synthetic row describing the calling
  aggregate request's own handshake metadata (`aggregate.py:2313-2362`
  `_stage_current_op`; `crates/secantus-commands/src/aggregate.rs:305-363`
  `apply_source_stage`) — there is no per-op registry to leak another
  connection's data from, so the fidelity fix (added so the connecting
  driver sees its own `appName` reflected back, per the mongocxx
  client-metadata-handshake test) doesn't create a disclosure surface. This
  reconfirms C1's framing is still accurate: `$currentOp`/`$listSessions`
  read no cross-namespace data today, they're synthetic single-row stubs.
- **The `pgjdbc-report` job added to `validate.yml` (#817) also lacks a
  `permissions:` block**, widening the pre-existing W5 gap from two jobs
  (`plan`, `validate`) to three. Its actions are all SHA-pinned (matching
  this repo's discipline elsewhere in the file), so this doesn't introduce
  a distinct new finding — folded into W5's re-confirmation below with the
  updated count.

All eight standing findings (C1, C2, W1–W6) were independently re-confirmed

## 4. Storage-engine & FFI safety (WiredTiger)

`src/secantus/storage.py` and `crates/secantus-storage/src/lib.rs` both had
targeted changes this cycle, reviewed in full:

- **`release_thread_snapshot()`** (`storage.py:3478-3507`, called from
  `server.py:635` and `sql/pgserver.py:536`): releases a thread's WT read
  snapshot + cursor positions before the connection thread blocks on the
  next socket read. Fixes a real availability bug (an idle connection
  pinning WT's oldest-transaction horizon degraded every other
  connection's write cost until page reads stalled — the pgjdbc gauge's
  `CopyLargeFileTest` wedge), not a new attack surface: it's a no-op inside
  an open user transaction (`if getattr(self._tls, "user_txn", None) is
  not None: return`) so it can't silently drop transaction semantics, and
  the `s.reset()` call itself is wrapped in `contextlib.suppress(Exception)`
  — the fourth such suppression site in this file (see **I41**, updated
  count below), consistent with the existing pattern for this class of
  best-effort cleanup, not a new swallowed-error-on-a-write-path concern
  (it runs on the read/idle path, not a commit path).
- **New `_UNIQ_TABLE` (`table:secantus_unique_keys`, Python) / `UNIQ_TABLE`
  (Rust, same table name)**: both servers now claim each unique-index key
  in a dedicated WT table with `overwrite=false` (Python:
  `storage.py:6674 _claim_unique_key` region; Rust:
  `crates/secantus-storage/src/lib.rs:8043-8081`) so WiredTiger itself
  rejects a duplicate, including one an open transaction holds
  uncommitted — closing a real cross-transaction TOCTOU race the old
  snapshot-read probe couldn't see (two concurrent writers could each
  insert the same "unique" value and both commit). Verified the claims
  table is purged everywhere the owning index/collection/db can disappear:
  `drop_index` (`storage.py:6717-6720`), `drop_all_indexes`
  (`storage.py:6828-6829`), `drop_collection`, `dropDatabase`, and
  `renameCollection` (all four call sites confirmed to include `_UNIQ_TABLE`
  in their per-table purge loops) on the Python side; the Rust
  `drop_index` path purges via `purge_unique_claims` at
  `crates/secantus-storage/src/lib.rs:7528-7529`. This was a genuine
  correctness/data-integrity gap being closed, not one being introduced —
  filed as a **CLEAN** item below, not a finding.
- **WT submodule gitlink** re-confirmed unchanged (`eaa187c8`,
  mongodb-7.0.33). Zero new `unsafe` blocks introduced anywhere in
  `crates/` by this window's commits (confirmed by diff-scoped grep across
  `crates/secantus-storage/src/lib.rs`, `crates/secantus-commands/src/
  aggregate.rs`, `crates/secantus-commands/src/cursors.rs` — the only three
  Rust files touched this window).
- **`_SEQ_ALLOC_CACHE`** (`src/secantus/sql/catalog.py:33-40`, new
  server-wide `WeakKeyDictionary[storage, {(db,name): [pending,
  last_handed]}]` backing batched `nextval()` allocation, #816): every
  mutator (`_sequence_nextval_locked`, `_invalidate_sequence_cache`, and
  their callers `create_sequence`/`drop_sequence`/`setval`/
  `alter_sequence`) is reachable only through paths already serialized by
  the SQL executor's per-storage `_write_lock` (`sql/executor.py:34-48`,
  an `RLock` — `sequence_nextval` takes it explicitly at
  `catalog.py:727`, and `create_sequence`/`drop_sequence`/`alter_sequence`
  are invoked from `_serialized_write`-wrapped executor paths at
  `executor.py:232`/`:257`), so the batch-allocation cache introduces no
  new race despite living outside the storage layer proper. Cache key is
  scoped `(db, name)`, so no cross-database value leakage. Not
  independently exploitable — filed as CLEAN, not a finding.

## 7. Resource exhaustion / DoS

**`release_thread_snapshot()` (#812) and the SQL idle-in-txn timeout
(#810), reviewed together as a matched pair this cycle:** both close the
same underlying resource-exhaustion class — a connection thread going idle
(between requests, or mid-abandoned-transaction) while still pinning WT's
oldest-transaction horizon, which degrades every other connection's write
cost until the server stalls. `release_thread_snapshot()` covers the
inter-request idle window on both wire servers (Mongo: `server.py:635`;
SQL: `pgserver.py:536`, called right before the blocking `read_message`/
`pgwire.read_message`); the idle-in-txn timeout covers the
abandoned-open-transaction window specifically. Between them the two gaps
that produced the pgjdbc gauge's 2-hour lane wedge are now closed by
default. Rust-side: `docs`-only commit `c1e0da29` records that the Rust
server was audited and found immune to the same idle-session snapshot-pin
class (no equivalent fix needed there) — spot-checked this cycle by
confirming the Rust server's session/statement lifecycle doesn't cache a
positioned WT cursor across an idle wait the way the Python
`threading.local()`-cached session did; found consistent with the
docs-recorded conclusion.
