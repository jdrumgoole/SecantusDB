## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **`$group`'s new memory budget (RM-211) does not account for `$firstN`/
  `$lastN`/`$minN`/`$maxN`/`$top`/`$bottom`/`$topN`/`$bottomN`/`$stdDevPop`/
  `$stdDevSamp`/`$avg`/`$sum`/`$count`/`$percentile` accumulator state, so an
  ordinary, single aggregation query with one of these accumulators grows
  memory without bound and never spills or refuses — the exact failure mode
  the new feature exists to prevent.**
  `crates/secantus-core/src/group.rs:2150-2162` (`acc_memory`): the match
  only returns real, growing payload size for `Acc::Push`/`AddToSet`/
  `ConcatArrays`/`SetUnion` (`.mem`), `Acc::Min`/`Max` (`engine_size`), and
  (SBE-only) `First`/`Last`/`MergeObjects`. Every other variant — `Sum`,
  `Count`, `Avg`, `StdDev`, `Percentile`, `NElem` (the four `*N` accumulators
  that take an explicit `n`), and `TopN` (`$top`/`$bottom`/`$topN`/
  `$bottomN`) — falls through to `_ => 0`, so `acc_memory` reports only the
  fixed `classic_base()` overhead (176–640 bytes, `group.rs:2171-2192`)
  regardless of how much data the accumulator is actually holding. But
  `apply_acc` (`group.rs:959-1014`) unconditionally grows real backing
  storage per input document for exactly these variants — confirmed by
  direct read: `Acc::NElem { n, vals, .. } => { ...; vals.push(eval(...)?); }`
  (`group.rs:959-969`) pushes one evaluated value per document with **no
  cap related to `n`**; truncation to the requested `n` happens only at
  `finalize` (`nelem_result`, `group.rs:1548`). `run_group`'s spill/refuse
  check (`mem > limit`, around `group.rs:2225-2290`) reads `acc_memory`'s
  fixed-overhead number, which never rises with the data, so it never trips.
  **Concrete trigger, ordinary `pymongo`, no privilege needed:**
  ```js
  db.coll.aggregate([
    {$group: {_id: "$lowCardinalityField",
              f: {$firstN: {n: 1, input: "$bigBlobField"}}}}
  ])
  ```
  over a collection where one group key covers many large documents: `vals`
  grows by one `bigBlobField` copy per document in that group, forever,
  while `acc_memory` reports a constant 200 bytes for the whole vector. The
  same gap is reachable through `$setWindowFields`'s `Growing` function path
  (`windowfields.rs`'s `FunctionMemory::Growing` calls
  `group::acc_memory_classic`, which shares the same match). This is not a
  sustained-interaction or multi-session resource-growth gap like the
  2026-10-26 SSI WARNING (#2182) — it is unbounded growth from a **single**
  ordinary query, which this project's threat model treats as the more
  serious case.
  **Fix direction:** extend `acc_memory` to add the real backing-storage
  size for `NElem.vals`, `TopN.items`, and the `Sum`/`Count`/`Avg`/`StdDev`/
  `Percentile` running-state structures, the same way `Push`/`AddToSet`
  already do via `.mem`.

- **`secantus-pgplan`'s new join-filter classifier recurses into every arm
  of a client-supplied `WHERE ... OR ...` tree with no depth bound — an
  ordinary, authenticated SQL query with a deeply nested `OR` over a two-
  (or more-) table join overflows the stack and crashes the connection
  thread (or the process, depending on platform stack-overflow handling),
  the same bug class as the ~20 already-open "unbounded recursion" findings,
  just a brand-new instance this window.**
  `crates/secantus-pgplan/src/joins.rs:1560-1604` (`filter_kind`, new this
  window, part of RP-028's join-filter-selectivity work): the `OrExpr` arm
  (`joins.rs:1570-1577`) is `let arms: Vec<FilterKind> =
  b.args.iter().map(filter_kind).collect();` — direct, unguarded recursion
  on every operand of every nested `OR`. Confirmed reachable: its only
  caller, `joins.rs:523` (`let kind = filter_kind(c);`), runs on every
  top-level conjunct of **any** query's `WHERE` clause that references
  columns from two or more joined table aliases (`key_aliases(c).len() >=
  2`, `joins.rs:519-521`) — i.e. any ordinary join query, not a privileged
  or unusual one. **Concrete trigger:**
  ```sql
  SELECT * FROM a JOIN b ON a.k = b.k
  WHERE a.k = b.k OR (a.k = b.k OR (a.k = b.k OR (... nested ~50,000 deep ...)));
  ```
  No cap exists anywhere on the call path between the raw `pg_query`-parsed
  AST and this function (unlike the depth guard this project uses
  elsewhere, per already-filed issue #1783 about call sites that bypass
  it). This is the same stack-overflow-DoS shape as #2070's `walk_tree`
  (independently reconfirmed unchanged this window — see Carried, below) —
  it just lives in a different, brand-new function this window's diff
  introduced, in the join-cost/selectivity path rather than the join-order
  search.
  **Fix direction:** route `filter_kind` through this project's existing
  recursion-depth guard before it is called on client-supplied `WHERE`
  nodes, the same remediation already planned for the rest of this bug
  class.

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **Aggregation spill files (new `$group`/blocking-sort/`$setWindowFields`
  spilling, RM-211/RM-315) always land in the shared OS temp directory with
  default file permissions, not the dbpath-scoped private directory the
  code's own comment says mongod uses — a confidentiality gap on a
  multi-user host.** `crates/secantus-core/src/memlimit.rs:377-387`:
  `spill_dir()`'s doc comment reads "Where spill files go (mongod:
  `<dbpath>/_tmp`). Unset: the system's temporary directory," and
  `set_spill_dir()` (the function meant to set it to the dbpath-scoped
  value) exists but — confirmed via `grep -rn "set_spill_dir"
  crates/secantus-core crates/secantus-commands crates/secantusdb
  crates/secantus-server` — has **zero production call sites**, only its
  own definition; so every real deployment falls through to
  `std::env::temp_dir()`. The three spill-file creation sites
  (`group_spill.rs:111`, `sorter.rs:266`, `windowfields.rs:656`) all use
  plain `File::create(&path)` with no explicit mode, so files are created
  under the process's default umask (typically world-readable on Linux).
  Any other local user on the host can read in-flight aggregation document
  contents for the duration of a spilling query — a real document-content
  leak, though it requires another local user on the same machine (this
  project's test-tool threat model treats that as WARNING, not CRITICAL:
  cleanup is otherwise solid — `Drop` on the spill types removes files on
  error/panic/normal unwind, so this is exposure-in-place, not an unbounded
  leak). **Fix direction:** wire `set_spill_dir` to the server's own
  dbpath at startup, matching the comment's stated intent, and create spill
  files with `0600` explicitly rather than relying on umask.

- **A non-UTF-8-string escape ambiguity lets `$setField`'s NUL-byte guard be
  bypassed via `{$literal: "...\0..."}`, silently writing a different,
  shorter field name than the one requested — the same class of silent
  corruption RM-222's own commit message says it was fixing.**
  `crates/secantus-core/src/expressions.rs`: the parse-time guard added this
  window, `set_field_name_parse` (3996-4013), rejects an embedded NUL only
  when `field` is a **bare** string literal (`matches!(field, Bson::String(s)
  if s.contains('\0'))`, line 4007). When `field` is instead
  `{$literal: "a\0ff"}`, that check is skipped (the value is a `Document`,
  not a `String`) and the subsequent match (4014-4046) only validates that
  the *folded* constant is of type `String` (4047-4057) — it never re-checks
  for an embedded NUL on the unwrapped `$literal` value. At runtime,
  `op_set_field` (4092-4130) evaluates `field` via `eval(fe, ctx)?` and, for
  the resulting `Bson::String(field) => field` arm (4101-4102), passes it
  straight to `doc.insert(field, value)` with no NUL check at all.
  **Concrete trigger:**
  ```js
  db.coll.aggregate([{$project: {x: {$setField: {
      field: {$literal: "a\u0000ff"}, input: "$$ROOT", value: 1
  }}}}])
  ```
  The resulting document key `"a\u0000ff"` (4 characters) is a literal NUL
  followed by the ASCII bytes "ff" — which is bit-for-bit the same string
  `bsondoc::escape_key`/`key_bytes` (the new RM-222 machinery, `bsondoc.rs:
  203-235`) uses to mean "the single byte `0xff`, not valid UTF-8." When
  this result is re-encoded for the wire (or written via a following
  `$merge`/`$out`), the encoder's `key_bytes` round-trip check reinterprets
  the 4-character key as the escape, and the client's requested field name
  is silently replaced with a 2-byte field named `a\xff` — different data
  than what `$setField` was asked to write, persisted if the pipeline
  writes out. **Fix direction:** have `set_field_name_parse` check for an
  embedded NUL on the *folded* constant (after unwrapping `$literal`), not
  just on a bare string literal, and have `op_set_field`'s runtime path
  apply the same NUL check mongod does on the type-checked value before
  `doc.insert`.

## 🟡 INFO (Best-practice recommendations)

- **Point-in-time snapshot reads' `atClusterTime` wait has no server-side
  cap independent of `maxTimeMS`.** `crates/secantus-commands/src/
  snapshot.rs:76-88`: a client that requests a future-but-not-yet-committed
  `atClusterTime` and omits `maxTimeMS` blocks the connection thread until
  real commit progress catches up, `killOp` fires, or the (optional)
  `maxTimeMS` expires. `check_at` (`snapshot.rs:189`) already rejects any
  `atClusterTime` beyond the server's own current committed cluster time,
  so the wait is bounded by genuine in-flight commit progress rather than an
  arbitrary attacker-chosen value — the same characteristic real mongod has.
  Worth a note if a connection-thread pool is ever bounded, but not a new
  vulnerability.
- Both `snapshot::read_point` and `check_at` silently treat a non-`Timestamp`
  `atClusterTime` as absent rather than raising mongod's `TypeMismatch` —
  a fidelity gap, not a security issue (falls back to "read latest
  committed," never to stale or freed history).
- The carried-forward INFO notes from prior cycles (the `BinDataOrder`
  thread-local, the synchronous index-rebuild-at-open startup latency, stale
  comments referencing deleted workflows, the unbounded `planCacheSetFilter`

## 🟢 CLEAN (Passed review)

- **`killOp`/interrupt authorization** (`interrupt.rs`, new, 336 lines):
  `kill_op` (`serverinfo.rs:417`) has no self/other distinction internally,
  but the pre-existing, unmodified `authz.rs:381` (`"killOp" => c.cluster
  ("killop")`) requires the `killop` cluster privilege unconditionally for
  every caller regardless of whose operation is named — strictly stronger
  than mongod's own gate. The op-id namespace is global and sequential
  (enumerable), but reaching it at all already requires privilege. The new
  `kill_sessions` wiring (`ops.rs:178-188`, called from `lib.rs:1797,1963`)
  reuses the pre-existing `authz.rs:161-182` own-session-unless-
  `killAnySession` restriction, correctly unmodified.
- **Point-in-time snapshot reads' scoping and resource hold** (`snapshot.rs`,
  new, 240 lines): `read_point`/`run` only ever operate on the already-
  authorized command's own db/collection; the WT transaction each snapshot
  read opens is scoped to one command's execution and rolled back
  immediately after (`secantus-storage/src/lib.rs:7535-7561`), including on
  each `getMore` of a snapshot-backed cursor — unlike a long-running
  transaction, it does **not** pin WiredTiger history across calls. This is
  a materially different (and safer) shape than the PG SSI gap (#2182).
  Cursor `read_at` lookup reuses the already-known, already-filed
  "ownership is namespace-only" limitation rather than introducing a new
  one.
- **Privilege-table diff around the new features** (`auth.rs`, `authz.rs`,
  `handshake.rs`, `roles.rs`, `umc.rs`, `cluster_admin.rs`,
  `cluster_params.rs`, `params.rs`): changes are incidental — a `bson::
  to_vec`/`to_writer` → `bsondoc::write` encoder swap (part of the unrelated
  RM-222 work), one new, additive `autoCompact => c.cluster("compact")`
  gate, and new `setParameter` type/range bounds for the aggregation budget
  constants. No privilege removed, no command moved into
  `_NO_PRIVILEGE_COMMANDS`.
- **`secantus-wt`'s new FFI surface** (`Connection::set_timestamp`/
  `query_timestamp`, `Session::compact`/`salvage`/`verify`): every string
  input crosses the FFI boundary via `CString::new(..).map_err(nul_err)`,
  never raw pointer arithmetic on wire-derived data; the one fixed-size
  buffer (`query_timestamp`'s `[0; 64]`) is sized for WiredTiger's own
  hex-timestamp output, not attacker data.
- **Storage compact/repair/sizes/index-build error-handling discipline**
  (five new files, ~3,450 lines combined): zero `unwrap()`/`expect()`/
  `let _ =` outside `#[cfg(test)]`; every WT call on a write/commit/
  checkpoint/compact/verify/salvage path is matched and propagated or
  explicitly logged, satisfying this project's "never ignore an error"
  standard.
- **Path/name handling in the new storage surface**: `compact.rs`'s table
  URIs are built only from the pre-existing fixed/enumerated table set
  (`doc_table_for` hashes into one of 16 fixed shard names; never
  interpolates a raw collection name into a URI); `index_build.rs`'s sorter
  filenames use a server-generated UUID, never wire-supplied text.
- **Hybrid (online) index builds**: batched/chunked scan, load, drain, and
  purge (`SCAN_BATCH`, `INDEX_BUILD_CHUNK_MAX_ENTRIES`, `DRAIN_BATCH`,
  `PURGE_CHUNK_MAX_ROWS`), with an `ExtSorter` that spills once a
  per-build memory budget is exceeded rather than growing RAM unbounded —
  this one, unlike the `$group` budget above, was traced end to end and
  does enforce its stated limit. A crash mid-build is handled by
  `restart_index_builds()` discarding orphaned side rows and rerunning from
  scratch at open, matching mongod's own restart-from-start semantics.
  `createIndexes`'s pre-existing authz gate is untouched.
- **`--repair` CLI flag**: parsed only from process argv
  (`secantus-server/src/args.rs`), consulted only in `secantusdb/src/
  main.rs::main()` before the wire server starts listening — no command
  dispatch path reaches it, and it doesn't shell out.
- **The non-UTF-8 byte-string decoder itself** (`bsondoc.rs`'s hand-rolled
  `read_doc`/`read_value`/`key_bytes`): every length/offset is read through
  bounds-checked `.get(..)`, never raw indexing past a derived bound; no
  panic found on a truncated/malformed buffer, and no unbounded allocation
  (every size is checked against the real remaining buffer, itself capped
  by the wire layer's 16 MiB BSON limit, before any allocation). The
  pre-existing lack of a recursion-depth cap on nested documents/arrays in
  this decoder is **not a regression** — it is identical to the bson
  crate's own prior recursive decoder, and `MAX_NESTING_DEPTH` is enforced
  after full decode either way, for both the old and new code paths.
  `$arrayToObject`'s own NUL-in-key check (unlike `$setField`'s, above)
  correctly covers both its object and array-pair forms.
- **The new PostgreSQL lock-wait-wakeup mechanism (RP-270/271)**: no
  deadlock-detection cadence was weakened (`table_locks::acquire` and
  `row_waits`' loop still poll `deadlocked()` on the same 1s/20-poll
  cadence as before, and the plain-DFS cycle detector (`lock_manager::
  deadlocked`) is lock-ownership-agnostic, so it still fires on any cycle
  including ones the new "autocommit statements hold table locks" change
  makes newly possible); every new mutex-poisoning path recovers via
  `unwrap_or_else(|e| e.into_inner())` rather than panicking; waiter
  cleanup on disconnect is unconditional (`WaitGuard::drop`, unchanged);
  lock ordering between the resource mutex and the wait-graph mutex is
  one-directional in all three new call sites, so no new deadlock between
  them was introduced. The same commit window incidentally removes a
  pre-existing panic risk in `join_order.rs` (`chain.ons[i]` →
  `.get(i).copied().flatten()`).
- **Full-diff secrets scan, dependency check, workflow review, build-output
  check**: all clean, detailed above.
