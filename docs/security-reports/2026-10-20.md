# Security Review — 2026-10-20

Diff-driven review against the 14 commits that landed since the last report
(`46ad0de0`, the 2026-10-17 report's own merge commit → `6d8a6bba`, HEAD,
confirmed unchanged on `origin/main` throughout this review via
`git rev-parse HEAD` == `git rev-parse origin/main`). All 14 are real
code/test changes, overwhelmingly the Rust PostgreSQL server (new 4–8 table
join-order search and cost estimation, a consolidated lock wait-for graph,
transaction-state consolidation, full ICU collation coverage), plus two
small Rust MongoDB-server commits (`$merge` write rounds, real locks on
index builds / `$out` / `dbStats`) and one skills-doc-only commit
(`6d100d0c`). No file under `src/secantus/**` (the deprecated Python
servers) was touched.

Four foreground sub-agents reviewed the diff in parallel, split along the
same "one server, one concern" lines this project already uses for
development: (1) the new join planner/cost code, (2) lock managers and
transaction state on both servers, (3) privileges/catalog/collation code,
(4) GitHub Actions workflow diff, secrets scan, and dependency review. Every
candidate finding was traced to a call chain and read in full (not inferred
from a diff hunk), per this project's own "reproduce before reporting"
standard, and the two highest-value carried-forward questions — "did
`4bda60b6` actually fix the `RP-048` WARNING from the 2026-10-17 report?"
and "does this cycle's `privileges.rs` touch the open `#1973` GRANT/REVOKE
gap?" — were asked explicitly and answered with file:line evidence rather
than taken on the commit message's word.

**Net result: zero new CRITICAL or WARNING findings. One WARNING from the
previous cycle is resolved and its tracking issue closed.** This is the
first cycle in the four most recent to find no fresh instance of the
unguarded-recursion-on-client-input class — the new join-order search,
hash-join batching, and ICU collation code all either cap recursion depth by
a fixed small constant (≤8 tables) regardless of query text, or use
`Option`-returning combinators with no panic path, which is a meaningfully
different shape from the uncapped tree-walkers found in each of the three
preceding cycles.

## 🟠 WARNING (Address within 1 week)

None new this cycle.

### Resolved this cycle

- **`RP-048`/`RP-047` cross-lock-kind deadlock gap — FIXED, issue closed.**
  The 2026-10-17 report filed a WARNING (tracked as GitHub issue `#2021`)
  that the Rust PostgreSQL server's new advisory-lock wait-for-graph detector
  (`crates/secantus-pg/src/lock_manager.rs`) didn't see edges held by the
  pre-existing, separately-bookkept `row_waits.rs` / `table_locks.rs`
  detectors, so a session holding an advisory lock while waiting on a row
  (or vice versa) could complete a real deadlock cycle no single detector
  could see, hanging two sessions forever instead of one being aborted with
  `40P01`/`55P03`. Commit `4bda60b6` ("one wait-for graph for every lock
  kind + lock-wait observability (RP-047, RP-048)", merged as #2024,
  2026-10-18) fixes this directly: `lock_manager.rs:22-44` adds a `WaitKind`
  enum (`Relation`/`TransactionId`/`Advisory`); `row_waits.rs:150-174` and
  `table_locks.rs:163-192` were rewritten to wrap `lock_manager::WaitGuard`
  instead of keeping their own `registry()`/`waiting` state (the old
  separate bookkeeping in both files is deleted, confirmed by `git diff`);
  `advisory.rs:117` was updated to pass `WaitKind::Advisory` into the same
  structure. All three lock kinds now register edges into one graph
  (`lock_manager.rs:58-63`), and the single iterative-DFS `deadlocked()`
  (`:124-127`, no stack-overflow risk of its own — not recursive) walks all
  of them. No new, ungoverned fourth lock kind was introduced alongside this
  fix. Verified directly in this review by reading the current code (not
  the commit message alone); `RP-047`/`RP-048` are gone from
  `tasks/backlog-rust-postgres.md`, consistent with closure. Issue `#2021`
  closed with this evidence during this review.

## 🟡 INFO (Best-practice recommendations)

- **The shipped Rust MongoDB server (`secantusd-rs`) still depends on
  `rustls-pemfile`, an unmaintained crate (`RUSTSEC-2025-0134`), even though
  this cycle cleaned the same dependency out of an unrelated dev-only
  surface.** Commit `de939ca9` removed `[dev-dependencies.rustls-pemfile]`
  from `crates/secantus-pgwire/Cargo.toml` and its example binaries
  (`client.rs`, `keycloak_oauth.rs`, `oauth.rs`, `scram.rs`,
  `secure_server.rs` — a vendored fork of the upstream `pgwire` crate, used
  only so `secantus-pg` can build from crates.io; the examples aren't part
  of the shipped server). But `crates/secantus-server/Cargo.toml:31` — the
  crate that backs the actually-shipped `secantusd-rs` binary and the
  embedded-handle TLS/mTLS PEM loader, per its own comment at lines 27–31 —
  still pins `rustls-pemfile = "2"`, resolving to `2.2.0` in
  `crates/secantusdb/Cargo.lock`, `crates/secantus-server-py/Cargo.lock`, and
  `crates/secantus-storage-adapter/Cargo.lock` (all zero-diff this window).
  WebSearch confirms `2.2.0` is still the latest published version — the
  upstream repository was archived 2025-08-19 with no newer release to bump
  to; RustSec's own advisory, issued 2025-12-05, calls this an unmaintained-
  dependency notice rather than a disclosed vulnerability, and recommends
  migrating directly onto `rustls-pki-types::PemObject`, which
  `secantus-pgwire`'s dev examples now do and `secantus-server`'s production
  TLS loader does not. Severity stays INFO (no CVE, no newer version
  exists, same calibration this project has applied to other unmaintained-
  but-not-vulnerable advisories) — but flagging it now, with the inconsistency
  freshly visible in one diff, is cheaper than re-discovering it later. No
  GitHub issue filed for an INFO-level finding, per this project's severity
  gate (CRITICAL/WARNING get issues; INFO does not).
- **The new 4–8 table join-order search (`RP-028`, commit `de939ca9`) is
  hard-capped, not combinatorially explosive — a structural CLEAN, not
  merely untested.** `crates/secantus-pg/src/join_order.rs::four_table_chain`
  (`:267`) rejects any chain outside `(3..=7).contains(&joins.len())` (i.e.
  4–8 base tables, matching PostgreSQL's own `join_collapse_limit` default,
  named in the module's own doc comment), and `search_four`'s DP (`:581`)
  runs only over that same fixed, small bound regardless of the query's
  text — a client cannot grow the search space by writing a larger query;
  it simply falls through to the pre-existing, unaccelerated join path once
  past 8 tables. This is the same "hard-capped" shape the 2026-10-17 report
  found CLEAN for the narrower 3/4-table case, now confirmed to extend
  unchanged through 8.
- **The new hash-join batching arithmetic (`RP-014`/`RP-028`, `joincost.rs`)
  cannot underflow or panic on a hostile column-width estimate.** Traced
  `hash_table_size`/`hash_batch`/`page_size`/`maxalign`/`prev_power_of_two`:
  `nbuckets`/`bucket_bytes` are bounded against a fixed `HASH_MEM_BYTES`
  constant (8 MiB) rather than anything a client's row/column counts can
  inflate past a capped branch (`sbuckets = 1` fires once `bucket_size ≥
  hash_table_bytes`, which bounds the one subtraction that could otherwise
  underflow). The one place a client-influenced width could balloon
  (`char(n)`'s uncapped declared-max width) is itself bounded by
  PostgreSQL's own typmod ceiling, not raw client bytes. A pessimistic
  float→u64 cast on an inflated row estimate saturates under Rust's defined
  `as` semantics rather than panicking or wrapping into a tiny value — a
  bogus-but-memory-safe plan choice at worst, correctly INFO rather than a
  crash-class finding.
- **No new panic (`unwrap()`/`expect()`/`panic!()`/raw indexing) reachable
  from client SQL or MongoDB wire input anywhere in this cycle's diff.**
  Checked across all reviewed files (`join_order.rs`/`join_search.rs`/
  `joincost.rs`/`joins.rs` in both `secantus-pg` and `secantus-pgplan`,
  `lock_manager.rs`/`row_waits.rs`/`table_locks.rs`/`txn_state.rs`/
  `advisory.rs`/`xids.rs`/`triggers.rs`/`plan_cache.rs`, `privileges.rs`/
  `schemas.rs`/`snapshots.rs`/`collation.rs`/`lib.rs` in `secantus-pgplan`,
  the 852-line `secantus-pg/src/lib.rs` diff, and `secantus-commands/src/
  {lock_manager,aggregate,lib}.rs` on the MongoDB side). The few `.expect()`/
  `panic!` calls found anywhere in the diff are confined to `#[cfg(test)]`
  modules. The one previously-flagged unverified cross-function invariant
  (`lib.rs:8745`'s `narrow_with_implied(...).expect("narrow_join_method
  checked it")`, noted as INFO on 2026-10-17) has zero diff this window —
  unchanged, not re-escalated.
- **The previously-flagged swallowed-`Result` pattern is fixed, not merely
  relocated.** Commit `a78a4422` changed `crates/secantus-pg/src/lib.rs`'s
  implicit-rollback-on-failed-batch path from `let _ =
  self.rollback_implicit();` to `if let Err(re) = self.rollback_implicit()
  { eprintln!("secantusd-pg: rolling back a failed batch: {re}"); }` — the
