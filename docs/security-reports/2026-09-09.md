## 🔴 CRITICAL (Immediate action required)

All three unchanged from 2026-09-08 — re-verified by reading current source.
All are reachable from an ordinary (unauthenticated, for the first two) wire
client:

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`).
  `self.message_length as usize` (line 138) casts the `i32` directly, so
  `message_length = -1` sign-extends to `usize::MAX` on 64-bit *before*
  either bound check runs; the `MAX_MESSAGE_SIZE` check (line 144) still
  compares the raw signed `i32`, so `-1 > 48_000_000` is also false. Both
  guards let a negative length through and the function returns
  `Ok(usize::MAX - 16)`. Feeds straight into an oversized allocation on the
  accept path, aborting the process from one unauthenticated 16-byte frame.
  Line numbers unchanged since last cycle. **Not fixed.**

- **#1160** — `src/secantus/commands.py`. `"bulkWrite": _bulk_write` is
  registered in `_HANDLERS` (line 8646) but `_COMMAND_ACTIONS`
  (8731-8814) and `_NO_PRIVILEGE_COMMANDS` (8821-8844) both have zero
  `"bulkWrite"` entries. Dispatch logic (9651-9652): `info =
  _COMMAND_ACTIONS.get(name)`; `if info is not None:` guards the entire RBAC
  block with no `else` branch — when `info is None` the check is silently
  skipped. `bulkWrite` still bypasses authorization entirely under `--auth`.
  This cycle's 24-line `commands.py` diff is an unrelated
  `AmbiguousSortPathError` catch clause. **Not fixed.**

- **#977** — `src/secantus/query.py:1407` (`_MAX_REGEX_PATTERN_LEN = 1000`,
  line moved from 1364 due to unrelated diff above it). `_compile_regex`
  (1411-1416) still only checks pattern *length*, then calls `re.compile`
  unguarded; a second bare `re.compile` call (now line 1467, was 1424) is
  equally unguarded. No backtracking-depth or match-time budget — the cap
  doesn't help against a pathological `(a+)+$`-shaped pattern, 6 characters,
  far under the 1000-char ceiling. CPython's `_sre` engine never releases
  the GIL mid-match, so this remains a whole-server CPU-pinning DoS from one
  unauthenticated `find`. This cycle's 67-line `query.py` diff is an
  unrelated numeric-path-vs-array-index correctness fix and never touches
  `_compile_regex`. **Not fixed.**

**Four new findings this cycle — all extend the same standing "no BSON/
array/type nesting-depth cap on the Rust decode/validate/render path"
recursion class, each independently re-derived from source (function body
read, recursive call confirmed, no `MAX_DEPTH`/`recursion_limit` guard
anywhere in the relevant crate):**

- **NEW — `crates/secantus-core/src/order.rs:157-164` (`is_comparable`),
  reachable from any `find`/`aggregate` using `$expr` with a comparison
  operator.** New function this cycle, replacing the old `is_sortable` gate:
  `Bson::Document(d) => d.values().all(is_comparable)` /
  `Bson::Array(a) => a.iter().all(is_comparable)`, no depth counter. Called
  from `expressions.rs`'s `ord_op` (backs `$gt`/`$gte`/`$lt`/`$lte`/`$eq`/
  `$ne` inside `$expr`) and `op_cmp` (backs `$cmp`). **Trigger:** an ordinary
  `find`/`aggregate` with `{$expr: {$gt: [<literal nested tens of thousands
  of levels deep>, 1]}}` — no stored data or auth required.
- **NEW — `crates/secantus-core/src/paths.rs:136-160` (`ambiguity_walk`,
  called via `ambiguous_sort_path` at line 128), reachable from any `find`
  with a `sort` on a dotted path, or the `$sort` aggregation stage.** New
  this cycle. Recurses through `Bson::Document`/`Bson::Array` with no depth
  cap, tracking both the dotted-path length in the sort spec and the
  matching document's nesting depth. Wired into `crates/secantus-
  storage/src/lib.rs:2531` (`sort_key`), called from `find`'s sort path and
  the `$sort` stage (`storage/lib.rs:5166`, `:10113`, `aggregate.rs:885`).
  **Trigger:** insert a document nested N levels deep, then `find` with
  `sort` on a dotted path of matching length — two ordinary, unprivileged
  commands.
- **NEW — `crates/secantus-storage/src/lib.rs:12916` (`collect_upsert_seed`),
  reachable from any `update`/`findAndModify` with `upsert: true`.** New
  this cycle (upsert-seed-from-query feature). Recurses into `$and`/`$or`
  filter branches with no depth cap. **Trigger:** `update({$and: [{$and:
  [...tens of thousands of levels...]}]}, {$set: {x: 1}}, {upsert: true})`
  — no auth, no prior state.
- **NEW — `crates/secantus-pgplan/src/lib.rs:6798` (`ArrayParser::
  parse_braced`, called from `parse_array` at line 6677), reachable from any
  text→array cast or bound array parameter on the (unauthenticated) PG
  server.** New this cycle (multidimensional-array literal support).
  Recurses on itself for every nested `{`, no depth limit. **Trigger:** any
  client sends `SELECT '{{{{...tens of thousands of levels...}}}}'::int4[]`
  (or the binary-parameter equivalent) — more practically exploitable than
  the type-name-based `#1356` since a few KB of `{` characters alone give
  thousands of stack frames in one round trip, and per standing issue
  **#1191** the PG-wire path has **no authentication at all**.

  All four: single unauthenticated request (Mongo-wire `$expr`/`sort`/
  upsert paths require no special privilege beyond an open connection; the
  PG-wire path has no auth whatsoever per #1191), no precondition beyond an
  existing collection or none at all. Rated WARNING, matching this repo's
  established tier for the rest of the recursion-DoS class: exploitation
  requires constructing a several-KB-to-MB request to reach practical stack
  limits, and the failure mode is a single connection thread's process-wide
  abort (not memory disclosure or RCE) — the same calibration used for
  `#1355`/`#1356`/`#1357` and the three filed last cycle.

  1. **Fix the two whole-server-DoS-from-one-request bugs** — `#995`'s Rust
     `body_len` cast-before-check (reorder: validate the sign/lower-bound on
     the raw `i32` before casting to `usize`) and `#977`'s regex
     GIL-starvation (add a backtracking-safe engine or a match-time budget
     for `$regex`). Both remain a single crafted request away from taking
     the entire server offline for every client, unauthenticated in the
     first case. Neither has moved in at least eight review cycles.
  2. **Give the Rust decode/validate/render/parse path one shared
     nesting-depth cap.** This is now the sixth cycle in a row to find *new*
     instances of the identical root cause — fifteen tracked instances
     across nine issues (`#1117`/`#1161`/`#1192`/`#1193`/`#1355`/`#1356`/

     comparison operators, sort-path resolution, upsert-seed filters, and
     SQL array literals — i.e. essentially every place a `Bson`/AST value
     gets walked. A single recursion-depth guard at each language boundary,
     or a shared "walk this value, bail out past depth N" helper that every
     new recursive function is required to route through, would close the
     whole class at once instead of continuing to surface one call site per
     feature PR. Given how consistently new instances keep appearing with
     every feature batch, this is now costing more reviewer time than a
     systemic fix would.
  3. **Close the recurring "command/statement missing from the
     privilege table silently skips RBAC" bug class systemically** — six
     confirmed live instances now across both engines
     (`bulkWrite`/`#1160`, `killSessions` family/`#1226`,

     `DROP TABLE`/`#947`, plpgsql triggers/`#909`, plus the related
     `ROLLBACK TO SAVEPOINT` index-DDL gap/`#1118`). Invert both dispatch
     points (`commands.py:9651` and `sql/engine.py`'s `_dispatch`) to
     fail-closed: unknown command/statement + auth on + not explicitly
     no-privilege → deny. This pattern has now reproduced independently in
     three different subsystems (Mongo commands, SQL statements, plpgsql),
     which is a strong signal the fix belongs in the dispatch primitive, not
     per call site.

standing Rust unbounded-recursion class:

- **Unbounded recursion in `order::is_comparable`** — stack-overflow DoS via
  any `find`/`aggregate` using `$expr` with a deeply nested comparison
  operand
- **Unbounded recursion in `paths::ambiguity_walk`** — stack-overflow DoS
  via `find`/`$sort` on a dotted sort path against a deeply nested stored
  document
- **Unbounded recursion in `storage::collect_upsert_seed`** — stack-overflow
  DoS via `update`/`findAndModify` with `upsert: true` and a deeply nested
  `$and`/`$or` filter
- **Unbounded recursion in `pgplan::ArrayParser::parse_braced`** —
  stack-overflow DoS via any deeply nested SQL array literal or binary array
  parameter on the (unauthenticated) PG server; more easily triggered than
  the existing tracked instances

No CRITICAL issues filed this cycle (all three CRITICAL findings are
carried-forward, already tracked). The two new INFO findings (unused-but-
