## 4. Storage-engine & FFI safety (WiredTiger)

`src/secantus/storage.py` — zero commits. `crates/secantus-storage/src/lib.rs`
changed substantially (+285/-79) but entirely for the chunked
`renameCollection` rewrite (see below); no new `unsafe` block, and the WT
cursor calls follow the same error-propagation (`?`) discipline as the
existing chunked-drop-purge code it's modeled on. WT submodule gitlink
unchanged (mongodb-7.0.33).

**Chunked `renameCollection` reviewed in full** (`Storage::rename_collection`,
`crates/secantus-storage/src/lib.rs`): replaces the old single-transaction
row-for-row move (unbounded dirty content on a large collection — the same
WT-livelock class the chunked drop-purge fixed for `dropCollection`) with a
four-phase tombstone-and-batch-copy sequence (`PURGE_CHUNK_MAX_ROWS`-sized
batches, resumable by source RecordId). All four crash windows funnel
through the existing `recover_pending_drops` open-time recovery path, and
the namespace locks (`self.locks()`) are held for the whole operation so no
concurrent reader/writer observes an intermediate state. A failed copy batch
purges the partial destination before surfacing the error rather than
leaving orphaned rows behind an unregistered name. This is a resource-
exhaustion *fix*, not a new finding — noted here because it's the largest
code change in the window and touches the storage engine's crash-recovery
contract.

**New this cycle — I43 (INFO, not independently exploitable):** SecantusDB's
session registry (`src/secantus/sessions.py: SessionRegistry`) does not bind
an `lsid` to the authenticated principal that created it — matching mongod's
actual model less closely than assumed (mongod's logical session cache
stores a `uid` alongside each session and rejects cross-user reuse). Under
`--auth`, a second authenticated connection that guesses another session's
`lsid` + `txnNumber` could interfere with that session (abort a transaction,
or — new this cycle — trigger a retryable-write cache replay). Investigated
as a possible new WARNING; downgraded to INFO because every path gated by
RBAC re-checks the *acting* connection's privileges before touching
`ctx.transactions`, so the blast radius is "annoy/observe your own
transaction state," not "read or write data you're not authorized for."
Worth a follow-up design note if session-scoped RBAC (per-session role
narrowing) is ever added, since that would change the trust boundary this
gap currently sits inside.

`--auth` gating (general): unchanged — `_NO_PRIVILEGE_COMMANDS` allowlist
minimal (aside from W6), `getMore` cursor ownership check present.
