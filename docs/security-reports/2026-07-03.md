## 🟠 WARNING (Address within 1 week)

### W1 — PG/SQL server has no authorization (RBAC) layer at all; an authenticated (or, by default, unauthenticated) SQL client gets unrestricted read/write on any database name it supplies

**Files:** `src/secantus/sql/pgserver.py`, `src/secantus/sql/pgauth.py`, `src/secantus/sql/engine.py`

`src/secantus/sql/` has zero references to `check_privilege`/RBAC. `SecantusPGServer` defaults to `require_auth=False` (`pgserver.py:58`, matching the documented dev-tool posture and mirroring the Mongo server's own opt-in `--auth`), and even *with* SCRAM auth turned on, a successfully-authenticated client is handed unrestricted access to whatever database name it supplies at connect time (`pgserver.py:210`) — there is no per-database or per-role gate analogous to the Mongo server's `_NO_PRIVILEGE_COMMANDS` allowlist + `check_privilege` pass (`commands.py:6500-6526`). Credential storage is also entirely separate from Mongo's: `UserStore.from_passwords()` (`pgauth.py:34-44`) is a constructor-supplied in-memory dict with no persistence and no `createUser`/`dropUser`/`system.users` parity with the Mongo side.

**Failure scenario:** when a `SecantusPGServer` shares the *same* `Storage` instance as a `SecantusDBServer` (the documented "both protocols, one dataset" pattern, `docs/sql.md`), a SQL client that authenticates as any one PG user — or connects at all, under the documented default trust mode — has broader effective access than an equivalently-authenticated Mongo client on the same data, because there is no RBAC layer to narrow it. This is exactly the kind of two-front-end security-property divergence CLAUDE.md's parity discipline calls out for the Rust/Python engine pair, just not yet applied across the Mongo/PG server pair.

**Fix:** either scope this explicitly as a documented limitation of the SQL interface (if RBAC parity is out of scope by design), or add a minimal per-connection/per-database authorization check before executing any statement, mirroring the Mongo server's privilege table.

### W2 — PG/SQL server has no cap on concurrent connections, no cap or TTL on server-side cursors, and no statement-length/parser-recursion guard before handing text to `sqlglot.parse` — three independent, unauthenticated-by-default resource-exhaustion vectors

**Files:** `src/secantus/sql/pgserver.py:149-158`, `src/secantus/sql/session.py:91`, `src/secantus/sql/engine.py:256-278`, `src/secantus/sql/planner.py:3572-3588`

Three related gaps, none present in the Mongo server's equivalent surfaces:

1. **No connection cap.** `SecantusPGServer._serve_forever` accepts and spawns a thread for every incoming connection unconditionally — no equivalent of `server.py`'s `DEFAULT_MAX_CONNECTIONS = 1000` check. A client can open unbounded TCP connections, each pinning a daemon thread.
2. **No server-side cursor cap or TTL.** `session.cursors` (`session.py:91`) is an uncapped per-connection `dict`; `_declare_cursor` (`engine.py:256-278`) materializes the *entire* query result into memory at `DECLARE CURSOR` time with no row-count limit, and a connection can `DECLARE` arbitrarily many named cursors, including `WITH HOLD` cursors that survive `COMMIT` (`engine.py:399-400`) and are never TTL-pruned — unlike `CursorRegistry`'s `DEFAULT_MAX_CURSORS` cap and opportunistic idle-TTL pruning on the Mongo side.
3. **No parser-recursion guard.** `sqlglot.parse()` is called with no query-length cap and no recursion-depth guard (`planner.py:3572-3588`, `engine.py`). Reproduced directly: `sqlglot.parse('SELECT ' + '('*300 + '1' + ')'*300, read='postgres')` raises a Python `RecursionError` inside the parser from a single ~600-byte message. This does **not** crash the process — it's caught by the same broad `except Exception` that converts any uncaught exception into a wire-level `ErrorResponse` (`pgserver.py:300-302`, `pgextended.py:236-239`), the same bounded-impact shape as the pre-existing INFO-grade I1 (a deeply-nested BSON document raising `RecursionError` inside `bson.decode`, uncaught by `wire.py`'s except tuple) — but here it is trivially repeatable pre-authentication (default `require_auth=False`) with no length/depth cap at all, unlike the Mongo side's 16MB/48MB size ceilings which at least bound the *cost* of triggering it.

Combined, the three gaps compound: an unauthenticated (by default) client can open unbounded connections, each declaring unbounded in-memory cursors and/or sending cheap-to-craft, CPU-costly parse requests, with no eviction and no rate limit anywhere in the path.

**Fix:** add a connection cap mirroring `DEFAULT_MAX_CONNECTIONS`; cap and idle-TTL server-side cursors per session (mirroring `CursorRegistry`); cap statement length before `sqlglot.parse` and/or wrap the call to catch `RecursionError` explicitly rather than relying on the generic exception handler.

### W3 — `pgauth.py`'s SCRAM client-key verification is not constant-time, unlike the Mongo server's equivalent check

**Files:** `src/secantus/sql/pgauth.py:116`, `src/secantus/auth.py:413`

The Mongo-side SCRAM implementation uses `hmac.compare_digest(expected_stored, state.creds.stored_key)` (`auth.py:413`) for the stored-key comparison — constant-time, correct. The PostgreSQL-side implementation performs the analogous check with a plain value comparison:

```python
if hashlib.sha256(client_key).digest() != self._creds.stored_key:
```

(`pgauth.py:116`) — an ordinary `!=` byte comparison, not guaranteed constant-time in CPython. `pgauth.py` otherwise correctly shares `secantus.auth`'s `derive_credentials`/`StoredCredentials` and mirrors the no-user-enumeration `mock_credentials()` pattern, so this is a narrow, single-line divergence rather than a systemic weakness — but it's exactly the class of two-front-end auth-property drift the project's own parity discipline (CLAUDE.md, "the two [engines] must not diverge on a security property") is meant to catch, just not yet extended to the Mongo/PG auth pair. Practical exploitability is low: SCRAM proof timing attacks over a real network are hard, and this is a local dev tool — hence WARNING rather than CRITICAL.

**Fix:** replace the `!=` comparison at `pgauth.py:116` with `hmac.compare_digest(...)`, matching `auth.py:413`.

Both of the prior report's actionable findings are confirmed **fixed**, reverified against live code:

This pass surfaced **3 new WARNINGs and 5 new INFO items**, all but one concentrated in the newly-landed PostgreSQL/SQL server (`src/secantus/sql/**`), which had no prior security review:

- **W2** — no connection cap, no server-side-cursor cap/TTL, and no parser-recursion guard on the PG server — three independent resource-exhaustion vectors, one reproduced directly (a 300-deep-paren `SELECT` triggers a Python `RecursionError` inside `sqlglot.parse`, pre-authentication).
- **W3** — `pgauth.py`'s SCRAM proof comparison uses `!=` instead of `hmac.compare_digest`, unlike the Mongo server's equivalent check.
- **I16–I19, I21** — smaller PG-server wire-framing, error-message, and workflow-input-hygiene gaps; see above.

### Top 3 priorities

1. **Decide and implement (or explicitly document as out of scope) an authorization model for the PG/SQL server** (W1) — today, reaching the server at all (its documented default is trust-mode) grants full read/write to any database name supplied, with no per-role gating, which is a meaningful step down from the Mongo server's RBAC even when both are pointed at the same underlying `Storage`.
2. **Add connection/cursor/parser-recursion guards to the PG server** (W2) — none of the three resource-exhaustion backstops the Mongo server already has (connection cap, cursor cap+TTL, size ceiling ahead of expensive parsing) exist yet on the SQL side, and the parser-recursion gap is trivially reproducible pre-auth.
3. **Fix the `pgauth.py` non-constant-time comparison** (W3) — a one-line change (`!=` → `hmac.compare_digest`) to match the Mongo server's existing correct pattern; low practical risk today but exactly the kind of two-front-end drift worth closing before it compounds.
