## 🔴 CRITICAL (Immediate action required)

### NEW — `$bitsAllSet`/`$bitsAnySet`/`$bitsAllClear`/`$bitsAnyClear` bit-position argument is unbounded in the Python query engine → wire-reachable memory-exhaustion DoS

`src/secantus/query.py:855-908` (`_resolve_bitmask`), the array-argument
branch:

```python
if isinstance(arg, list):
    mask = 0
    for i, bit in enumerate(arg):
        ...
        if bit < 0:
            raise QueryError(...)   # lower bound enforced
        mask |= 1 << bit            # NO upper bound — bit is an attacker int
    return mask
```

`bit` comes straight from a query filter's `$bits*` argument array — 8 bytes
on the wire for an `Int64` — and the only validation is "not bool, not
fractional, not negative." There is no upper bound. Python integers are
arbitrary-precision, and `1 << bit` requires the interpreter to allocate and
zero-fill a result object of `O(bit)` bits: choosing `bit ≈ 3.4×10¹⁰` (an
ordinary in-range `Int64`, nowhere near the max) makes CPython allocate and
physically touch **~4 GB of real memory** computing a single left-shift,
holding the GIL for the whole computation — which blocks every other
connection on the process, not just the caller's. A handful of concurrent
connections each picking a multi-GB `bit` value exhausts the host's RAM in
seconds; picking a `bit` near `Int64::MAX` (`9223372036854775807`) instead
asks for an ~1-exabyte allocation, which fails fast with `MemoryError` (caught
by `dispatch`'s blanket `except Exception`, so that particular shape degrades
gracefully) — but the attacker controls the dial between "graceful failure"
and "several GB of real RSS growth per request," and nothing stops them
picking the damaging middle ground. This is reachable through any ordinary
`find` / `count` / `aggregate $match` / `update` / `delete` filter — no
elevated privilege beyond whatever read/write access the connection already
has, and with `--auth` off (the shipped default) no authentication at all.
`_op_bitwise` (`query.py:912-919`) is the only caller, invoked from
`_op_matches`, which every filter-evaluation path in `query.py` and
`storage.py`'s COLLSCAN fallback routes through.

This is precisely the failure mode section 6 of the review checklist names
explicitly ("huge `$in` arrays... confirm it can't be triggered to exhaust
memory from a single small request") and section 7 names again ("resource
exhaustion / DoS"). Unlike the regex operator (`#977`, WARNING — at least
bounded by a 1000-character pattern cap), this operator has **no cap of any
kind** on the value that drives its cost.

**The Rust engine does not have this bug** — `crates/secantus-core/src/query.rs:1795-1820`
(`resolve_bitmask`) explicitly bounds every bit position to `(0..64)` and
returns `Fallback` (defers to the Python oracle only for *test-parity*
purposes, not reachable from the standalone Rust server's own wire path)
otherwise, keeping the mask a fixed-width `u64`. Confirmed by direct read: the
`Bson::Array` arm rejects any position outside `0..64` before the `mask |= 1
<< p` line ever executes with an out-of-range `p`. This is a Python-server-
only bug — the two engines diverge on a security property, which `CLAUDE.md`
calls out as something that must not happen.

**Recommended fix shape** (not applied this run per this run's
review-only scope): cap `bit` the same way the Rust side does — reject (or
saturate the mask to 0/all-clear, matching mongod's own real behaviour, worth
confirming against a live `mongod`) any bit position ≥ some small bound (64
is the natural choice, matching int64's own width, since no stored integer
value can have a set bit beyond position 63 anyway). Filing an issue below.
