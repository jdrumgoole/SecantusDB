## What's new since the last review

Only **2 commits** landed since 2026-08-02's `7324b001` cutoff
(`git log 7324b001..HEAD`) — a quiet cycle. Both are SQL/Postgres-wire
front-end changes, reviewed in full:

- **`c483c464` — `_pg_expandarray` and composite field access in the select
  list (#751).** Adds recognition for `information_schema._pg_expandarray(arr)`
  (a per-element `(x, n)` record expander used by pgjdbc's
  `DatabaseMetaData`) and `(schema.srf(...)).field` composite-field access in
  `src/secantus/sql/planner.py` (`_srf_of`, `_RECORD_SRF_KINDS`) and
  `src/secantus/sql/executor.py` (`_expandarray_cell`). Reviewed for
  `eval`/injection hazards (none — pure AST pattern-matching on already-parsed
  `sqlglot` nodes and dict construction), unbounded recursion (`_srf_of`
  recurses one level into a `Paren`, bounded by call-site shape, not user
  input depth), and array-index safety (`_expandarray_cell` bounds-checks `k
  >= len(arr)` before indexing). No security-relevant change.
- **`d1fcb64e` — fold unquoted identifiers to lower case, as Postgres does
  (#753).** Adds `planner._fold_unquoted_identifiers`, which walks every
  `exp.Identifier` node in an already-parsed statement (`stmt.find_all`,
  bounded by the pre-existing statement-length cap applied before parsing —
  unchanged) and lower-cases the unquoted ones in place; a companion 3-line
  fix in `src/secantus/sql/engine.py`'s `_grant_principals` restores `PUBLIC`
  to upper case (Postgres treats it as a keyword, not a foldable identifier).
  Pure string transform on parser-internal AST nodes, no `eval`/injection
  surface, no new I/O. No security-relevant change.
- Untouched this cycle (re-confirmed clean by direct check): `wire.py`,
  `server.py`, `auth.py`, `commands.py`, `cursors.py`, `changestreams.py`,

## 🟠 WARNING (Address within 1 week)

### W1 (carried forward, still open — 14th consecutive cycle) — Two non-poison-tolerant `.lock().unwrap()` sites remain on the Rust oplog mutex

**File:** `crates/secantus-storage/src/lib.rs:4897` and `:4989` — unchanged
this cycle (`storage.py`/`lib.rs` line numbers re-confirmed by direct grep;
the file was not touched by either of this cycle's 2 commits). Still exactly
2 bare `.lock().unwrap()` sites, both the same `prune_oplog`-adjacent
accessors reading/decrementing `live_count`.

Already tracked as open issue [#593](../../../../issues/593), filed
2026-07-21, unfixed across **fourteen** consecutive review cycles.

**Recommendation:** unchanged — convert both sites to
`ctx.oplog.lock().unwrap_or_else(|e| e.into_inner())`. The recommended
grep-based CI gate (`! grep -rn '\.lock()\.unwrap()' crates/secantus-storage
crates/secantus-commands` outside `#[cfg(test)]`) remains unimplemented after
fourteen nightly re-discoveries.

### W2 (carried forward, still open — 11th consecutive cycle) — `drop_index` / `drop_all_indexes` still lack the collection lock that `create_index` gained on 2026-07-24

**File:** `src/secantus/storage.py:6004` (`drop_index`) and `:6121`
(`drop_all_indexes`) — re-confirmed present by direct read this cycle: both
still open only `with self._lock:`, never `self._coll_lock(db, coll)`, unlike
`create_index` (`:5768`, `with self._coll_lock(db, coll), self._lock:`).

Already tracked as open issue [#635](../../../../issues/635), filed
2026-07-24. The hazard is unchanged: a concurrent `insert`/`update`/`delete`
(which takes `_coll_lock` first) is not excluded by `drop_index`'s
`_lock`-only critical section.

**Recommendation:** unchanged — `with self._coll_lock(db, coll),
self._lock:` in both methods, plus a regression test mirroring
`test_ddl_and_crud_never_deadlock_and_index_stays_complete` for the drop
path.

### W3 (carried forward, still open — 4th consecutive cycle) — `_emit_oplog`'s bare-autocommit path can permanently freeze the change-stream visible tail on a write error

**File:** `src/secantus/storage.py:2382-2484` (`_emit_oplog`) — untouched
this cycle; the bare-autocommit deregistration at `:2481`
(`self._deregister_minted([(start_seq, start_seq + n)])`) still has no
surrounding `try/finally`, unlike `_batch_transaction` and
`commit_user_transaction`'s flush, which both deregister inside a `finally`.

Already tracked as open issue [#714](../../../../issues/714), filed
2026-07-31, unfixed across a 4th consecutive cycle.

**Recommendation:** unchanged — wrap the mint-to-deregister region of the
bare autocommit path in `try/finally`.

### W4 (carried forward, still open — 2nd consecutive cycle) — Rust user-transaction async-oplog buffer (`pending_async`) has no size/count cap

**File:** `crates/secantus-storage/src/lib.rs:137`
(`UserTransactionHandle::pending_async: Vec<(OplogEntry, Option<Vec<u8>>)>`)
— re-confirmed present and unchanged this cycle (`grep -n pending_async` still
returns the same 6 sites as last cycle; `crates/secantus-storage/src/lib.rs`
was not touched by either of this cycle's 2 commits).

Already tracked as open issue [#750](../../../../issues/750), filed
2026-08-02, unfixed across a 2nd consecutive cycle.

**Recommendation:** unchanged — add a size/count ceiling on `pending_async`
and reject or flush early once exceeded, rather than growing unbounded for
the life of an open transaction (bounded to the 60s
`transactionLifetimeLimitSeconds`-equivalent reap, not truly unbounded, but
still uncapped within that window).

### W5 (new this cycle) — `validate.yml`'s `validate` job has no `permissions:` block; only its downstream `aggregate` job scopes one down

**File:** `.github/workflows/validate.yml` — the `validate` job (`:25-356`,
the 13-entry driver-conformance matrix) declares no `permissions:` block, and
the workflow itself has no top-level `permissions:` for it to inherit from
(only the `aggregate` job at `:357` explicitly scopes `contents: write` /
`pull-requests: write`). Concretely: the job that checks out this repo and
then builds/runs third-party driver toolchains — Go modules, npm packages,
Maven/Gradle dependencies, Ruby gems, Cargo crates, PHP extensions (built
from source per `test-libmongoc`/`mongocxx`), and the .NET SDK's own
dependency resolution — runs with whatever the repository's *default*
`GITHUB_TOKEN` permission is, rather than an explicit least-privilege grant.
None of those third-party toolchains' own transitive dependencies carry this
repo's SHA-pinning discipline (that discipline is applied to this repo's own
`uses:` lines, not to `go.sum`/`package-lock.json`/`Gemfile.lock`/etc. inside
the vendored driver-test submodules `validate.yml` builds).

This repo's own admin API token lacks the scope to read the org/repo default
workflow-permission setting (`gh api repos/.../actions/permissions/workflow`
→ `403 Resource not accessible by integration`), so whether the *current*
default happens to be read-only or read-write could not be confirmed from
this vantage — which is itself the point: an explicit `permissions:` block
makes the job's privilege independent of a setting this review can't see and
an admin could change at any time.

**Why this matters, calibrated to this repo's actual risk (per the threat
model in `scripts/security-review-prompt.md`):** `validate.yml` only runs on
a weekly `schedule` or manual `workflow_dispatch` — it is not attacker-
triggerable via a PR, so this is a defence-in-depth gap, not a directly
exploitable one. But it is exactly the kind of gap the "explicit `permissions:`
everywhere" convention (already applied to every *other* job in this repo's
13 workflow files) exists to close: if any one of the 13 driver toolchains
this job builds from source pulled a compromised transitive dependency during
a scheduled run, the blast radius of that compromise is bounded only by
whatever ambient token scope the job happens to have — which should be
`contents: read` and nothing else, matching what the job actually needs
(checkout + artifact upload, both read-safe).

**Recommendation:** add
```yaml
  validate:
    permissions:
      contents: read
```
to the `validate` job (artifact upload does not require write access to
`contents`). This also fixes the count so `I6`'s "every workflow declares a
permissions block" claim becomes true again rather than merely repeated.
