## 🟠 WARNING (Address within 1 week)

### W1 — `admin.system.users` is readable via ordinary `find`/`count`/`aggregate`/`explain`, leaking SCRAM credential material to any `read`-privileged connection

**Files:** `src/secantus/storage.py:1442-1472` (`_find_system_users`), `src/secantus/commands.py:5700-5707` (privilege table)

`Storage._find_system_users` — the read path used whenever a query targets `admin.system.users` via `find`/`count`/`aggregate`/`explain`/`distinct`/`mapReduce` — returns each user document "unchanged": `_id`, `user`, `db`, **`credentials`** (the full SCRAM `storedKey`/`serverKey`/`salt`/iteration-count blob), and `roles`/`mechanisms`, with no stripping and no elevated-privilege gate:

```python
def _find_system_users(...) -> list[dict[str, Any]]:
    """Read path for ``admin.system.users``. The user records
    themselves already carry the mongod-shaped fields (``_id`` =
    ``<db>.<user>``, ``user``, ``db``, ``credentials``, ``roles``,
    ``mechanisms``), so the view is the row set unchanged plus the
    usual filter / sort / skip / limit / projection pipeline."""
    ...
    rows = self._scan_user_records()
    ...
    return rows
```

This is inconsistent with the codebase's own `usersInfo` command, which explicitly strips `credentials` unless the caller both passes `showCredentials: true` **and** holds the `A_VIEW_USER` privilege (`commands.py:4968-4972`, gated by `commands.py:5740`). But the *generic* CRUD privilege table requires only the ordinary collection-read action for `admin.system.users`:

```python
"find": (A_FIND, SCOPE_COLLECTION),
"count": (A_FIND, SCOPE_COLLECTION),
"distinct": (A_FIND, SCOPE_COLLECTION),
"aggregate": (A_FIND, SCOPE_COLLECTION),
"mapReduce": (A_FIND, SCOPE_COLLECTION),
"explain": (A_FIND, SCOPE_COLLECTION),
```

**Failure scenario:** a principal granted only the built-in `read`/`readAnyDatabase` role on `admin` (a routine monitoring/backup-tool grant, far short of full admin) runs `db.getSiblingDB("admin").system.users.find()` and receives every user's raw SCRAM `storedKey`/`serverKey`/salt/iterations. That data isn't the plaintext password, but it is exactly the artifact real MongoDB (and every SCRAM-based system) treats as sensitive: it lets an attacker run offline dictionary/brute-force cracking against the password using the disclosed salt+iteration count (the same risk class as a leaked `/etc/shadow`-style hash file), and knowledge of `serverKey` lets an attacker stand up a rogue server that completes the SASL server side and impersonates SecantusDB to a legitimate client. This is a straightforward privilege-model gap — `find`-class access should not implicitly grant what `usersInfo` intentionally gates behind `A_VIEW_USER` + `showCredentials`.

**Fix:** route `admin.system.users` reads through `find`/`count`/`aggregate`/`explain` the same way `usersInfo` does — either require `A_VIEW_USER` for any query touching that namespace, or unconditionally strip `credentials` from the generic CRUD read path and only surface it via the already-gated `usersInfo` command.

### W2 — Rust `cstr()` panics on an embedded NUL byte in wire-supplied db/coll/index names, dropping the connection with no wire-level error reply

**Files:** `crates/secantus-wt/src/lib.rs:489-491`, `crates/secantus-commands/src/lib.rs:421-427`

**Unchanged since 2026-07-01 (W2 in that report) — still open, still tracked as [GitHub issue #139](../../../../issues/139), not re-filed here.**

```rust
fn cstr(s: &str) -> CString {
    CString::new(s).expect("string has interior NUL")
}
```

Verified live against current `HEAD`: `cstr()` is unchanged, `secantus-commands`'s namespace validation still only rejects components over 63 bytes with no NUL-byte check, and `grep -rn catch_unwind crates/` still returns nothing — there is still no panic-isolation boundary anywhere in the Rust dispatch path. A well-formed BSON command with a db/coll/index name containing an embedded NUL byte still panics the per-connection thread and drops the socket with no `{ok:0, errmsg, code, codeName}` reply, unlike the Python server's equivalent path.

**Fix:** (unchanged) Make `cstr()` return `Result<CString, _>` (or reject embedded-NUL names during BSON command validation before they reach `secantus-wt`), and add a `catch_unwind` boundary around per-connection dispatch as defense-in-depth. Tracked in issue #139 — no code change made in this review pass per the review-only mandate.

### I1 — Deeply-nested BSON filter/document can raise an uncaught `RecursionError` inside `bson.decode`, which `wire.py`'s parse-error handling doesn't catch (bounded to a single dropped connection)

**File:** `src/secantus/wire.py:127-144`

`read_message`'s parse-error handling only catches `(bson.InvalidBSON, _BodyBoundsError, struct.error)`:

```python
try:
    if header.op_code == OP_MSG:
        return Message(header=header, op=_parse_op_msg(body))
    ...
except (bson.InvalidBSON, _BodyBoundsError, struct.error) as exc:
    raise MalformedBodyError(header, f"invalid BSON in body: {exc}") from exc
```

Neither `bson.decode` nor SecantusDB impose an explicit document-nesting-depth limit; Python's own call-stack recursion (default limit 1000) is the only backstop. A sufficiently deeply nested document (e.g. `{"$and":[{"$and":[...]}]}` several hundred levels deep, well within the 16MB document / 48MB message size ceilings) raises `RecursionError` during `bson.decode` itself — a case this except tuple doesn't cover, contradicting the wire layer's own documented intent ("real mongod replies with `BadValue` ... never drops the socket on a malformed frame").

In practice the exception still doesn't crash the process or leak a traceback to the client: `RecursionError` is a `RuntimeError`/`Exception` subclass, so it's caught one layer up by `server.py`'s per-connection `except Exception` (`server.py:795`), which logs it and tears down just that connection. Net effect is a single dropped connection with no `BadValue` reply — a self-contained, low-severity gap against the wire layer's stated contract rather than a process-wide DoS. Query-side recursion (`query.py`'s `_match_clause`, `expressions.py`'s `_eval`) has the identical characteristic and the identical (safe) outer backstop.

**Fix:** add `RecursionError` to `read_message`'s except tuple (translating it to the same `MalformedBodyError`/`BadValue` reply as the other parse-error cases), or impose an explicit nesting-depth cap in the BSON decode path / query-document walk.

3. **Add `RecursionError` to `wire.py`'s parse-error except tuple** (this report's I1) — low severity (bounded to a single dropped connection today) but a real gap against the wire layer's own documented "never drop the socket on a malformed frame" contract; a one-line fix now avoids it becoming a recurring finding.
