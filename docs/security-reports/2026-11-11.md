## 🔴 CRITICAL (Immediate action required)

### New this cycle

- **Unauthenticated `explain` of a collection-less `$documents`/`$match`
  aggregate causes unbounded recursion (stack-overflow DoS) in the new
  `$replaceRoot` push-down walker** (high/high/high).
  `crates/secantus-commands/src/explain/hoist.rs`'s `renameable()`/`clause()`
  (lines 135-160) and `under_root()` (lines 163-182) walk a client-supplied
  `$match` filter's `$and`/`$or`/`$nor` tree recursively, one Rust stack
  frame per nesting level, with **no depth counter anywhere in the function,
  the file, or any caller**. Reachable with zero credentials
  (`require_auth` defaults `false`) via `explain` of an `aggregate` whose
  first stage is `$documents` (`shape::own_source()`, needing no real
  collection) followed by a deeply `$and`-nested `$match`; the call chain is
  `explain::mod::explain` -> `aggregate` -> `own_source_reply` (which
  prepends a synthetic `$replaceRoot`) -> `hoist::hoist_after_source` (the
  **sole call site**, confirmed by grep) -> `hoist()`'s main loop ->
  `through_replace_root` -> `renameable`/`under_root`. No generic
  BSON-decode-time nesting-depth guard exists anywhere above this code: the
  wire layer's `validate_bson` (`crates/secantus-wire/src/lib.rs:736`) only
  checks declared-length-vs-slice-length, and `secantus_core::bsondoc::
  from_bytes` (called by `merge_op_msg_body` on every incoming command
  document) has no depth check either. The project's only document-nesting
  guard, `MAX_NESTING_DEPTH=180` in `crud.rs`, is scoped to insert/update
  document bodies only, never to query/match filters. The per-connection
  thread has no `stack_size` override, so it runs on the small default OS
  thread stack; a Rust stack overflow aborts the **whole process**, not
  just the one connection (`catch_unwind` around `dispatch()` cannot
  intercept a non-unwinding stack overflow). An independent verifier
  re-read every cited line, confirmed the call chain and the absence of any
  depth guard at every layer, and confirmed the lack of a `stack_size`
  override.
  **Fix:** add one generic nesting-depth guard (mirroring mongod's
  `BSONDepth::kDefaultMaxAllowableDepth`, 200) to every incoming command
  document at decode time in `secantus_core::bsondoc::from_bytes`, not just
  to insert/update bodies in `crud.rs` — this single choke point protects
  `hoist.rs`'s walkers and any other recursive walker uniformly.
  **Filed as a new issue** (duplicate search for "hoist replaceRoot" found
  no existing coverage).

- **Unbounded, uncancellable recursion in jsonb subscript assignment
  (`set_path`) can crash a `secantusd-pg` connection worker thread**
  (medium/high/high). The new `jsonb_subs.rs` (`crates/secantus-pgplan/src/`,
  implementing PostgreSQL's jsonb subscripting assignment, `UPDATE t SET
  j['a']['b']...['z'] = v`) recurses in `set_path`/`set_path_object`/
  `set_path_array` (lines 189-267) once per subscript in the assignment's
  indirection chain whenever that step already matches an existing nesting
  level, with **no depth cap and no `crate::cancel::check()`/`walk_point()`
  call anywhere in the file**. The chain length is an ordinary,
  client-controlled SQL construct represented as a *flat* `indirection`
  list — it is **not** bounded by the planner's existing `MAX_EXPR_DEPTH=
  2500` guard, which only walks AST parent-child nesting. The sibling
  `array_assign.rs` caps its own analogous write path at `MAXDIM=6`, and
  this file's own `fetch()` function (the read-path counterpart) already
  demonstrates the iterative alternative over the identical `path` shape —
  `set_path` alone breaks that pattern. Reachable by any authenticated
  client with ordinary `UPDATE` privilege on a table with a jsonb column;
  the attacker builds an N-deep target document cheaply (O(N) client-side
  work via repeated shallow `UPDATE`s, each individually well under the
  AST-depth guard), then sends one `UPDATE` with an N-long subscript chain
  to drive the same N-deep, uncapped Rust recursion on the 256 MiB
  (`WORKER_STACK_BYTES`) connection-worker stack. An independent verifier
  re-confirmed the recursion mechanism, the absence of any cap/cancellation
  point, and the contrast with both sibling files, while flagging as
  genuinely unmeasured (no execution available) the exact N needed to
  exhaust the stack and whether PostgreSQL's own grammar really flattens
  the subscript chain rather than nesting it in the AST — kept `confirmed`
  at `medium` confidence rather than `needs_validation`, since the missing
  bound itself is fully established by source alone regardless of the
  exact crash threshold.
  **Fix:** rewrite `set_path`/`set_path_object`/`set_path_array` to walk
  iteratively (as the file's own `fetch()` already demonstrates), or add an
  explicit depth cap plus a `cancel::check()`/`walk_point()` call per level.
  **Filed as a new issue** (duplicate search for "jsonb_subs" found no
  existing coverage).

## 🟠 WARNING (Address within 1 week)

### New this cycle

- **`$queryStats` store (RM-215) has no size cap or eviction: unauthenticated
  clients can grow unbounded, permanent server memory** (medium/medium/
  medium). The new query-stats store (`crates/secantus-commands/src/
  query_stats.rs`, 1043 new lines) records one permanent `Entry` per
  distinct dedup-key hash for every successful `find`/`aggregate`/`count`/
  `distinct`, once `internalQueryStatsRateLimit` is non-zero (default `0`,
  off). Unlike mongod 8.2.11, which bounds the store by
  `internalQueryStatsCacheSize` and LRU-evicts past it, this implementation
  has **no cap and no eviction anywhere in the 1043-line file** — confirmed
  by reading it end to end. Several fields feeding the dedup hash are
  copied verbatim rather than shapified: the connection's raw handshake
  client metadata (`client()`), the literal `hint` document/string
  (`hint()`), and `readConcern`'s `afterClusterTime`/`atClusterTime` kept
  "as it was given" even in the representative key — so varying any one of
  them per request manufactures a new permanent entry. Because
  `require_auth` defaults `false` and `authorize()` is an unconditional
  no-op whenever it is off (applied to every command including
  `setParameter`), both enabling the collector and flooding it with
  distinct-keyed reads need zero credentials under the server's default
  configuration. Independently and explicitly corroborated by this
  project's own open backlog item **RM-532** (filed 2026-11-10, same
  window), which states the identical gap in mongod-comparison language and
  already has a verify test. A verifier re-confirmed every cited line and
  the require_auth/authorize() interaction, and kept the hunter's proposed
  medium/medium/medium severity (growth is linear in attacker request
  volume, a materially different class from a single bounded input with
  superlinear effect, per this project's own resource-exhaustion
  calibration).
  **Fix:** track `internalQueryStatsCacheSize` (already reported as a
  parameter per RM-532 but not enforced) and evict least-recently-used
  entries once total size would exceed it, using the existing `order:
  Vec<String>` as an LRU list; this closes RM-532 and the unbounded-growth
  path together.
  **Filed as a new issue** (duplicate search for "queryStats" found no
  existing coverage).

- **The plain `dataSize` command on `local.oplog.rs` forces up to three full
  decode+re-encode passes over the entire oplog per request, with no
  caching** (medium/medium/medium). RM-419's fix for `local.oplog.rs`'s
  `dataSize`/`collStats` previously reading `0` replaces the lookup with
  `oplog_rs_sizes` (`crates/secantus-storage/src/lib.rs:14902`), which
  decodes every oplog entry and re-encodes it just to sum byte lengths, with
  no running counter the way `self.sizes` already keeps for every ordinary
  collection. `stats_admin.rs`'s `data_size` handler calls `collection_sizes`,
  `collection_data_size`, and the pre-existing `count_matching` back to back
  for the same namespace; each independently triggers a full oplog scan for
  `local.oplog.rs`, so one plain `dataSize` request now costs **three** full
  passes (up from two before this window's fix, not zero to three — the fix
  made a previously-cheap-but-wrong `collection_data_size` answer also do a
  full pass). A verifier independently confirmed the triple-invocation and
  the complete absence of caching, but materially corrected the hunter's
  framing: `collStats`/`$collStats` cost only one full pass (unchanged by
  this diff) and `dbStats` is unaffected entirely (since `local.oplog.rs`
  has no catalog entry `list_collections` returns) — only the plain
  `dataSize` form hits all three. The verifier also established that
  `local`-database access (needed for this path under `--auth`) is
  restricted to backup/clusterManager/clusterAdmin-equivalent roles, mirroring
  mongod's own restriction — under the server's default `require_auth=false`
  configuration, though, no privilege at all is required.
  **Fix:** maintain the oplog's record count and summed byte size
  incrementally (as `self.sizes` already does for ordinary collections)
  rather than recomputing it by decoding every entry on every
  `collection_sizes`/`collection_data_size`/`count_matching` call.
  **Filed as a new issue** (duplicate search for "oplog.rs dataSize" found
  no existing coverage).
