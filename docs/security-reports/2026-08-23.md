### #995 (carried forward, still open, re-confirmed)

`crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`) — re-read in
full this cycle, byte-for-byte unchanged (the crate's only change this
window is its `Cargo.toml` version bump to `0.5.3-beta.161`, confirmed by
`git diff acd7d523..HEAD -- crates/secantus-wire/src`, which is empty):

```rust
pub fn body_len(&self) -> Result<usize, WireError> {
    if (self.message_length as usize) < HEADER_SIZE {   // message_length: i32
        return Err(...);                                 // sign-extends to
    }                                                     // usize::MAX for a
    if self.message_length > MAX_MESSAGE_SIZE {           // negative value,
        return Err(...);                                 // defeating this
    }                                                     // check
    Ok(self.message_length as usize - HEADER_SIZE)         // still-signed i32
}                                                           // compare, also
                                                             // defeated
```

A wire frame with `message_length = -1` (bytes `FF FF FF FF`) casts to
`usize::MAX` under the first check (not `< 16`), and the second check still
compares the signed `i32` (`-1 > 48_000_000` is false), so both guards pass
and `body_len()` returns `usize::MAX - 16`. The caller
(`crates/secantus-server/src/lib.rs:558`, also unchanged this window) then
calls `shared.alloc_budget.acquire(body_len)`, which only blocks when
another allocation is already outstanding, so a lone connection sails
through regardless of `n`'s size; the subsequent
`vec![0u8; body_len]` aborts the process via `handle_alloc_error` — a single
unauthenticated 16-byte frame kills the whole Rust server. Not fixed.
Tracked as **#995**.

### W1 (new) — `cryptography` 48.0.0 pin is behind two named, fixed CVEs

`uv.lock:525-536` pins `cryptography==48.0.0`, pulled in transitively by
`trustme>=1.2` (`pyproject.toml:46`) under the `dev` extra only — re-verified
this cycle: `grep -rn "^import cryptography\|^from cryptography" src/`
returns nothing, so the package is never imported by shipped code, only by
the dev-extra `trustme` (ephemeral CA generation for `tests/test_tls.py`).
Two CVEs against `pyca/cryptography`, both published **2026-08-03** (before
yesterday's 2026-08-22 review, which searched for and reported none — this
is a sweep miss, not a new disclosure), both fixed only in **49.0.0**:

- **CVE-2026-69248** — the X.509 path-verifier's wildcard-DNS-name matcher
  lets a leaf certificate's `*.example.com` SAN escape a `permittedSubtrees`
  name constraint that only permits the more specific `foo.example.com`.
- **CVE-2026-69249** — resolving a certificate chain containing duplicate
  self-signed intermediates triggers exponential path-building; bounded by a
  max-depth cap so it terminates, but an attacker-controlled chain can push
  verification past 5 seconds, a DoS on whatever calls the verifier.

Both require *verifying an attacker-supplied certificate chain* to trigger.
`trustme` only ever generates and signs its own trusted certs for local test
fixtures — it does not exercise the verifier against externally-supplied
chains — so the realistic exposure through this codebase's actual usage is
low. That said: this is a dependency pin sitting on a named, fixed CVE with
no countervailing reason not to bump (dev-only, no API break expected across
a patch-level cryptography bump in this range). Recommend bumping past
49.0.0. Not tracked by an open issue before this cycle — filing one below.

### W2 (new) — macOS wheel build downloads lz4 source with no integrity check

`tools/build_lz4_macos.sh` is new this window (part of the lz4
block-compressor switch) and runs as the macOS wheel's `cibuildwheel`
`before-build` step (`pyproject.toml:323`,
`before-build = "... bash tools/build_lz4_macos.sh"`) — i.e. it is in the
build path for the actual macOS wheels `publish.yml` ships to PyPI, not just
a dev convenience script. It does:

```bash
curl -fsSL "https://github.com/lz4/lz4/archive/refs/tags/v${LZ4_VERSION}.tar.gz" \
    -o "$work/lz4.tar.gz"
...
tar xzf "$work/lz4.tar.gz" -C "$work/src" --strip-components=1
make -C "$work/src/lib" liblz4.a ...
```

with **no checksum or signature verification** of the downloaded tarball —
unlike this project's other native-code supply-chain path, the vendored
WiredTiger submodule, which is pinned by git commit SHA
(`eaa187c86147b561c940e9b0e5e628f5e86d075d`) and therefore content-addressed.
A GitHub release tag is technically mutable (a repo maintainer, or anyone who
compromises the `lz4/lz4` GitHub account or GitHub's CDN, can force-push a
tag), so `v1.10.0.tar.gz`'s bytes are not pinned the way the submodule's are.
The build output is a **static** `liblz4.a` linked into the shipped binary,
so a compromised tarball would mean malicious code compiled directly into
every macOS wheel on PyPI. Section 13b of the checklist asks explicitly
"confirm the build doesn't download arbitrary remote code at build time
beyond the pinned submodule + the patch scripts" — this is exactly that
gap, newly opened by this window's changes. Recommend pinning a SHA256
checksum of the `v1.10.0` tarball in the script and verifying it before
`tar xzf`. (Linux/Windows wheels are unaffected — they link the
distro-provided `liblz4-dev` package via the normal package manager's own
integrity chain, not a bespoke curl-and-build step.) Filing an issue below.
