## 🔴 CRITICAL (Immediate action required)

All three unchanged, re-confirmed by direct read against current HEAD:

- **#995** — `crates/secantus-wire/src/lib.rs:137-145` (`Header::body_len`).
  Re-read in full: `if (self.message_length as usize) < HEADER_SIZE` casts
  the signed `i32` to `usize` first — `message_length = -1` sign-extends to
  `usize::MAX` on 64-bit, which is not `< HEADER_SIZE (16)`, so this guard
  passes. The second guard compares the raw signed `i32` against
  `MAX_MESSAGE_SIZE`, so a negative value also passes it. The function
  returns `self.message_length as usize - HEADER_SIZE` = `usize::MAX - 16`,
  feeding an oversized allocation from one unauthenticated 16-byte frame on
  the accept path. **Not fixed.**

- **#1160** — `src/secantus/commands.py`. `"bulkWrite": _bulk_write` is
  registered in the dispatch table (line 8646). Grepped `_COMMAND_ACTIONS`
  (line 8731) and `_NO_PRIVILEGE_COMMANDS` (line 8821) directly this cycle —
  `bulkWrite` appears in neither table (the two `bulkWrite` hits at lines
  9194/9295 are the unrelated `_API_V1_COMMANDS` and `_TXN_ALLOWED_COMMANDS`
  sets, confirmed by reading their surrounding context). `_authorize_command`
  falls through to `default_db, False` for any name missing from
  `_COMMAND_ACTIONS` rather than denying it, so `bulkWrite` still runs with no
  RBAC check under `--auth`. **Not fixed.**

- **#977** — `src/secantus/query.py:1407-1416` (`_MAX_REGEX_PATTERN_LEN =
  1000`, `_compile_regex`). Still only a length guard before an unguarded
  `re.compile`; a second bare `re.compile` call at line 1467 has no cap at
  all. No backtracking-depth or match-time budget. A short pathological
  pattern (`(a+)+$`-shaped) is far under the 1000-char ceiling and still pins
  a CPU core via CPython's `_sre`, which never releases the GIL mid-match.
  **Not fixed.**
