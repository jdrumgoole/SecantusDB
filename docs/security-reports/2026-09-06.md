## 🔴 CRITICAL (Immediate action required)

All three unchanged from 2026-09-05 — re-verified by reading current source,
not carried on trust. All are reachable from an ordinary (unauthenticated, for
the first two) wire client:

- **#995** — `crates/secantus-wire/src/lib.rs:136-150` (`Header::body_len`).
  Re-read this cycle, byte-identical to the last four cycles:
  ```rust
  pub fn body_len(&self) -> Result<usize, WireError> {
      if (self.message_length as usize) < HEADER_SIZE { ... }
      if self.message_length > MAX_MESSAGE_SIZE { ... }
      Ok(self.message_length as usize - HEADER_SIZE)
  }
  ```
  `message_length` is `i32`. A header with `message_length = -1` sign-extends
  under `as usize` to `usize::MAX` in the first check (comparison becomes
  `usize::MAX < 16` → false, guard doesn't fire), and the second check
  compares the still-signed `i32` (`-1 > MAX_MESSAGE_SIZE` → false) — both
  guards let a negative length through, and the function returns
  `Ok(usize::MAX - 16)`. This feeds straight into an oversized allocation on
  the accept path (`crates/secantus-server/src/lib.rs`, unchanged this
  cycle), aborting the process from one unauthenticated 16-byte frame.
  **Not fixed.**

- **#1160** — `src/secantus/commands.py`. Re-confirmed this cycle:
  `"bulkWrite": _bulk_write` is registered in the dispatch table (line 8608,
  unmoved) but has no entry in `_COMMAND_ACTIONS`, confirmed by grepping the
  full `_COMMAND_ACTIONS` mapping body for `bulkWrite`/`killSessions` (zero
  hits both). The privilege gate is still fail-*open*: a command absent from
  the table is silently exempted from RBAC rather than denied. `bulkWrite`
  still bypasses authorization entirely under `--auth`. **Not fixed.**

- **#977** — `src/secantus/query.py:1275` (`_MAX_REGEX_PATTERN_LEN = 1000`),
  re-read this cycle at the same line. Still a length cap only, no
  backtracking-depth or match-time budget — and the cap doesn't help against a
  pathological `(a+)+$`-shaped pattern, which is 6 characters, far under the
  1000-char ceiling. CPython's `_sre` engine never releases the GIL mid-match
  (live-verified in an earlier cycle to hang an unrelated second connection's
  `ping`, not just the attacking connection), so this remains a whole-server
  CPU-pinning DoS from one unauthenticated `find`. **Not fixed.**
