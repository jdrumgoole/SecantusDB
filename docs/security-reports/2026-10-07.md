# Security Review — 2026-10-07

Full-breadth review across all 13 sections of `scripts/security-review-prompt.md`
(dependencies, secrets, wire-protocol parsing, storage/FFI, auth, command
dispatch, resource exhaustion, network defaults, the Rust server, the admin
UI, git history, GitHub Actions, and PyPI wheel integrity), run by seven
parallel review agents each owning a disjoint slice of the spec, then
synthesized and independently spot-verified in the main session (CVE-pin
re-checks, sdist-exclude re-reads, `bson`-crate version/depth-guard confirmation).

This cycle deliberately weighted attention toward **code that changed since the
last report** (2026-10-06, commit `b968addb`): 22 commits landed in the
intervening day, heavily concentrated in the Rust PostgreSQL server (READ
COMMITTED read-overlay machinery, joins over LATERAL/subquery/function sides,
`GROUPING()`, grouping-set streaming, a removed "read-path concurrency
ceiling") and the Rust MongoDB server (a hand-ported `timelib` date scanner
replacing the old recursive one, embedded TTL/heartbeat sweeper threads,
validator/write-concern parsing). Each reviewer was hand-briefed with the
specific diffs and asked to form an independent judgment, not inherit one.

Findings were cross-checked against the 78 already-open `security`-labelled
issues so this report doesn't re-file known items — where a finding matches
tracked work, it's marked **(status check, not re-filed)**. Two results of
particular note this cycle: a tracked panic class (**#1454/#1455**) was
independently confirmed **fixed** by the timelib rewrite, and a tracked panic
class (**#1227**) was found **escalated** — the vulnerable pattern it names now
also runs, unsupervised and on by default, inside the embedded server bundled
in the wheel, not only the standalone daemon behind opt-in flags.

## 🔴 CRITICAL (Immediate action required)

### 1. The Rust server's BSON decoder has no nesting-depth limit — a single unauthenticated frame causes a whole-process stack-overflow abort

`crates/Cargo.lock`, `crates/secantusdb/Cargo.lock`, and
`crates/secantus-pgserver/Cargo.lock` all pin `bson = 2.15.0` (confirmed
directly: `grep -A2 'name = "bson"' crates/Cargo.lock` → `version = "2.15.0"`).
That crate's `Document::from_reader` recurses once per nested
document/array level with **no depth cap** — confirmed by grep across
`crates/secantus-wire/src` and `crates/secantus-server/src` for any
`stack_size`/`RecursionError`/`max*depth`/`nesting` guard: none exists on
either the Python-equivalent concept or a Rust substitute. The upstream fix
(`mongodb/bson-rust` PR #694, "add a max nesting limit to decoding", bounding
depth to 200 — mongod's own `BSONDepth::kDefaultMaxAllowableDepth`) merged to
`main` on 2026-09-18 but **ships only in v3.1.0, which is not yet released as
of today** — two major versions past the vendored 2.15.0.

This decode runs on **every** inbound document, reached from two call sites
that are both pre-dispatch and pre-auth:

- `crates/secantus-server/src/lib.rs:872-891` (`merge_op_msg_body`) — every
  `OP_MSG` body and every kind-1 document-sequence entry.
- `crates/secantus-server/src/lib.rs:697-714` — the legacy `OP_QUERY`
  handshake path pymongo uses for its initial `isMaster`/`hello` probe.

Connection-handler threads use the Rust default stack (`thread::spawn` with no
`Builder::stack_size` override — confirmed: no `stack_size` call anywhere in
`crates/secantus-server/src/lib.rs`). A Rust stack overflow is not a
catchable `panic!`: it trips the runtime's guard-page handler, which prints
"thread '...' has overflowed its stack" and calls `abort()`, terminating **the
entire process** — every connection, not just the attacker's. The existing
`catch_unwind` around `dispatch` (`lib.rs:909-925`, added specifically for
ordinary handler panics) cannot help here because unwinding never starts.

**Exploit:** an attacker with a bare TCP connection — no credentials, no prior
commands, nothing but the socket — sends one `OP_MSG` (or the legacy
`OP_QUERY` handshake) carrying a document nested roughly 200,000+ levels deep.
Each nesting level costs ~9 bytes, so the whole payload is well under 2 MB —
inside both the 16 MB single-document limit and the 48 MB message cap this
project itself advertises and enforces at the framing layer (the upstream
bug report that drove the depth-limit fix reproduced with a ~3.9 MB, 483,000-level
document). The server process aborts; every other connected client is
dropped.

This is the same severity class as the already-fixed/tracked **#995**
(`body_len()` sign-extension abort) — "unauthenticated, single-frame, remote
process-crash DoS" — not the lower-severity "standing unbounded-recursion"
class (#1117/#1161/#1192/.../#1456, consistently WARNING in this tracker),
because those require an authenticated-or-not session to first reach specific
command/query logic *after* successful dispatch; this one fires during
deserialization, before dispatch exists at all, on the very first frame.

**Fix:** don't wait on `bson` 3.1.0. Add a cheap pre-decode bounds check in
`secantus-wire` (or immediately before each `Document::from_reader` call) that
walks the raw bytes counting nested embedded-document/array type markers
(`0x03`/`0x04`) and rejects anything past ~200 levels, mirroring mongod's own
limit — this is a self-contained fix independent of the upstream crate
release.

**New finding — not a duplicate of any tracked issue.**

## 🟠 WARNING (Address within 1 week)

### 2. The legacy `OP_QUERY` handshake dispatch path has no panic boundary, unlike the `OP_MSG` path

`crates/secantus-server/src/lib.rs:712-714` calls `dispatch(&request, &mut ctx)`
directly with no `catch_unwind`, while the `OP_MSG` path's `run_dispatch`
(`lib.rs:916-925`) wraps the identical call specifically so a handler panic
degrades to `{ok:0, code:1 InternalError}` instead of dropping the socket.
Since this path serves `isMaster`/`hello` — attacker-reachable pre-auth — any
panic in that handler silently kills the connection with no reply, violating
this project's own "a parse error ... keeps the connection alive" contract.
Lower severity than Finding 1 (drops one connection, doesn't abort the
process).

**New finding.**

### 3. Unbounded recursion in `order::cmp` (Rust sort/comparison engine) — stack-overflow DoS via any sort, `$min`/`$max`, or comparison over a deeply nested document

`crates/secantus-core/src/order.rs`: `cmp`/`doc_cmp`/`array_cmp` recurse once
per BSON nesting level with no depth counter, and the Rust MongoDB server has
no insert-time cap on document nesting depth (grepped `crud.rs` and the rest
of `secantus-commands`/`secantus-core` for a `BSONDepth`-style check — none
exists). **Empirically confirmed**: a temporary test comparing two clones of a
200,000-level-deep document via `order::cmp` under `cargo test` (debug
profile, default stack) reliably aborted with `has overflowed its stack` /
`fatal runtime error: stack overflow` (test added, run, and reverted — working
tree confirmed clean afterward). Concrete input: `db.c.insertOne({a: <200,000
levels deep>})` then `db.c.find().sort({a:1})` (or `$min`/`$max` in `$group`).
Same root cause and same severity class as the already-tracked **#1456**
(`group::gkey`) — this is a sibling call site through the identical missing
guard, not a duplicate of that specific function.

**New finding — extends the standing unbounded-recursion class (#1117 family).**

### 4. Several Rust PostgreSQL-planner call sites parse raw client SQL text directly, bypassing the project's own depth guard — stack-overflow DoS confirmed via `ON CONFLICT ... WHERE`

The project already built a defense for exactly this bug class:
`secantus_pgplan::parse_tree` (`lib.rs:3573`) routes through `parse_guarded`
(a token-based `nesting_bound` pre-check plus a post-parse `check_depth`,
refusing past `MAX_EXPR_DEPTH = 2500` with a clean `54001`). But several
functions call `pg_query::parse(...)` **directly** on attacker-controlled SQL
fragments, skipping both checks:

- `crates/secantus-pgplan/src/lib.rs:1055-1057` (`predicate_implied`), called
  from `crates/secantus-pgserver/src/lib.rs:16032`/`16099` with the literal
  `WHERE` text of an `INSERT ... ON CONFLICT (...) WHERE <text> DO ...`
  arbiter clause. **Empirically confirmed**: a temporary test feeding
  `predicate_implied` a ~500,000-term flat operator chain (`1+1+1+...`, ≈1 MB)
  reliably aborted with a stack overflow (test added, run, reverted; tree
  confirmed clean). A matching *parenthesis*-nesting payload of the same
  depth did **not** reproduce it — PostgreSQL's grammar collapses redundant
  parens without adding an AST node — the reproducer needed a flat operator
  chain, one AST level per term.
- `crates/secantus-pgserver/src/lib.rs:1086-1089` (`transaction_statement_tag`)
  and `:977-980` (`non_volatile_refusal`) — same direct-`parse` pattern, over
  `LANGUAGE sql` function-body statement text; `transaction_statement_tag`
  runs on every statement of every SQL function body on every call.

Concrete wire-reachable input, from an ordinary authenticated session with no
special privilege: `CREATE TABLE t (id int); CREATE UNIQUE INDEX t_idx ON t
(id) WHERE true; INSERT INTO t (id) VALUES (1) ON CONFLICT (id) WHERE
1+1+1+...+1 /* ~500,000 terms */ DO NOTHING;` — aborts the whole shared
single-node server.

A further ~9 other direct `pg_query::parse(...)` call sites were identified
but not individually reproduced (`domains.rs`, `enum_order.rs`, `errpos.rs`,
`filter_sublink.rs`, `rule_rewrite.rs`, `ruleutils.rs`, `schemas.rs`,
`semijoin_hash.rs`, `view_deps.rs`, `pg_expandarray.rs`, `prune_outputs.rs`,
`plan_cache.rs::eligible_sql`, `plpgsql_fn.rs`) — worth a dedicated pass since
several reformat a fragment of user SQL into a fresh string and re-parse it
raw, the same shape as the confirmed bug.

**New finding — extends the standing unbounded-recursion class, but notably
bypasses an existing, purpose-built defense rather than simply lacking one.**

### 5. Unchecked integer overflow in the newly-ported `timelib` date scanner — reachable panic (debug) / silent wrong date (release) via `$dateFromString`/`$toDate`

`crates/secantus-core/src/timelib/scan.rs:481`, inside the
`Rule::Timestamp | Rule::TimestampMs` action: `self.time.relative.s += i;` is
a raw, unchecked add. Every other field-merge in `set_relative()` nearby uses
`checked_add` and reports `ERR_NUMBER_OUT_OF_RANGE` on overflow
(`scan.rs:978-984`) — this one line doesn't. If `relative.s` already holds a
value from an earlier "N sec" token and a later `@<digits>` timestamp token
(the `@-?[0-9]+` regex has no digit cap beyond `get_signed_nr`'s internal
24-char limit, which still permits full `i64`-range values) supplies an `i`
close enough to `i64::MAX`, the sum overflows. **Empirically confirmed** with
input `"9999999999999 sec @9223372036854775806"` fed through `mongo_parse()`:
reliably panicked with `attempt to add with overflow` at `scan.rs:481`.

This panic *is* caught by `secantus-server`'s per-request `catch_unwind`
(degrading to a generic `InternalError` reply) in a debug build, so in CI/dev
it's "only" a wire-fidelity bug. The **shipped release build has no
`overflow-checks` override** in any `[profile.release]` found in the
workspace, so the identical input silently **wraps** instead of panicking and
returns a wrong date with no error — a silent-data-corruption shape this
project's own standing rules treat as a serious correctness bug in its own
right, independent of the DoS angle.

**New finding.**

### 6. SQL `regexp_*`/`~`/`SIMILAR TO` on the Python PostgreSQL server has no ReDoS guard at all — worse than the two related, already-tracked paths

`src/secantus/sql/scalar.py:1621-1635` (`_re_compile`) has no pattern-length
cap and no complexity check, unlike the Mongo-side `query.py:_compile_regex`
(1000-char cap, itself only a partial mitigation and already tracked as
#1744/#977) and unlike the Rust PostgreSQL server's regex functions (compiled
via the linear-time Rust `regex` crate, not vulnerable to catastrophic
backtracking by construction — the existing #1707 formally covers that path
but doesn't reproduce the same way). Called from `~`/`~*` (`_eval_regexp`),
`regexp_replace`, `regexp_count`, `regexp_match`, `regexp_split_to_array`,
pattern-anchored `substring()`, and `SIMILAR TO`. The Python PG server has no
authentication by default (`src/secantus/sql/pgserver.py:189`,
`require_auth: bool = False`), so `SELECT
'aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!' ~ '^(a+)+\$'` (or the
`regexp_replace`/`SIMILAR TO` equivalent) hangs the handling thread in
classic catastrophic backtracking with zero preconditions — and since
CPython's `re` engine doesn't release the GIL mid-match, this stalls the
entire process, not just one connection.

**New finding — distinct from #1744/#977 (Mongo, has a partial cap) and
#1707 (Rust PG, uses a backtracking-free engine); this is the one SQL regex
surface with zero mitigation of any kind.**

### 7. Embedded Rust MongoDB server now runs unsupervised TTL/heartbeat sweeper threads by default — widens the reach of tracked #1227

Commit `2f897bea` (#1772, landed 2026-10-06) adds `spawn_sweeper`
(`crates/secantusdb/src/lib.rs:405-420`) to `secantus_mdb::Server`, copying
the standalone daemon's pattern, and wires it in **on by default**
(`Default for Builder` sets `ttl_sweep: Some(DEFAULT_TTL_SWEEP)`). Before this
commit, the *embedded* server (the PyO3 extension bundled in the wheel —
what `_secantus_server` and every pymongo-against-Rust-server test actually
runs) spawned no sweeper at all; only the standalone `secantusd-rs` daemon
could reach this code, and only behind explicit `--ttl-sweep-seconds` /
`--noop-heartbeat-seconds` CLI flags. Now every embedded server instance
reaches it automatically, with no opt-in.

Neither `spawn_sweeper` nor the daemon's original `spawn_interval` wraps its
task closure in `catch_unwind` — unlike the per-request dispatch path, which
explicitly is panic-isolated (`crates/secantus-server/src/lib.rs:917`). The
sweep calls `storage.prune_ttl_all_collections(now)`, which contains an
unchecked `i64` subtraction (`crates/secantus-storage/src/lib.rs:8933`:
`(when_ms - v.timestamp_millis()) as f64 / 1000.0`) over a client-controlled
TTL-indexed `DateTime` value — exactly the defect #1227 already names. A
panic there (debug builds panic on overflow) permanently kills that one
sweeper thread with no restart and no log: `Server::stop()` discards the join
result outright (`crates/secantusdb/src/lib.rs:162`: `let _ =
sweeper.join();`), a direct instance of the "never ignore an error" pattern
this project explicitly treats as a defect in its own right. Net effect: TTL
expiry (and oplog-heartbeat pruning, if enabled) can go silently and
permanently dead for the remaining life of any embedded server process.

**New finding — escalates #1227 to a new, default-on surface (the embedded
server shipped to every consumer), not a re-confirmation of the original
daemon-only text.**

wheel most users actually install.

**New finding.**

### 9. `cryptography` 48.0.0 is now behind a third, more recent CVE than the two tracked in #1023 — the correct remediation target has moved from 49.0.0 to 50.0.0

`uv.lock` pins `cryptography==48.0.0`, reached only via the dev-only

leave the server exposed to this one.

**New finding — updates #1023's remediation target, not a duplicate; low
practical exploitability since the pin is dev-only.**

## 🟡 INFO (Best-practice recommendations)

- **Release-mode silent `i64` wraparound, not just a debug-mode panic, in the
  same TTL-prune arithmetic as Finding 7.** `crates/secantus-storage/src/lib.rs:8923,8931-8936`'s
  `when_ms - v.timestamp_millis()` is unchecked in every build profile; no
  workspace `Cargo.toml` sets `[profile.release] overflow-checks = true`.
  Depending on the exact out-of-range value, a release build doesn't panic —
  it silently wraps and can reach a wrong expiry verdict, up to and including
  unsupervised deletion of a document that wasn't actually expired. Fix
  alongside Finding 7 with `checked_sub`/`saturating_sub`, failing safe
  ("not expired") on overflow.
- **The "Protect release tags" ruleset doesn't cover the third tag
  namespace.** `gh api repos/:owner/:repo/rulesets/18530430` covers
  `refs/tags/v*` and `refs/tags/secantusdb-v*` (deletion + non-fast-forward
  protection) but not `refs/tags/secantusd-pg-v*`, which
  `release-pg-binaries.yml` also triggers on. Base repo permissions (push
  access required to create any tag) still gate tag creation either way —
  this is a ruleset-scope inconsistency, not an access-control gap.
- Carried from 2026-10-06 and still accurate: the Python server has no
  cross-connection allocation budget for in-flight message bodies (Rust has
  an explicit 512 MB `AllocBudget`); `killAllSessionsByPattern` is an
  unlisted third sibling of tracked #1226; `replSetGetStatus` and the three
  search-index commands remain outside the RBAC action table at low
  practical impact (read-only / stub-routed respectively).

  crates `0.5.3-beta.171`; Rust PostgreSQL-server crates `0.1.0-beta.2`
  (commit `46fae9567f13656bf784b0f4b1455535a7fdc9bc`).
- **This cycle's new findings:** 1 CRITICAL, 8 WARNING, 2 INFO.
- **Status-confirmed from prior cycles (not re-filed):** 25 issues spot-
  re-verified with fresh evidence — 23 confirmed still present/open, 1
  (**#1454/#1455**, counted together) confirmed **fixed**, 1 (**#1227**)
  confirmed **escalated** in scope.
- **Comparison with previous report (2026-10-06):** that cycle's single new
  CRITICAL was a dependency/supply-chain finding (the `pymongo` CVE, still
  open today — see priorities below); today's new CRITICAL is a different
  shape entirely — a vendored Rust crate's own missing recursion guard,
  reachable pre-auth on the very first frame, found by treating the Rust
  wire layer's BSON *content* decode (as opposed to its already-audited
  framing logic) as a first-class part of §3 rather than assuming it inherits
  the framing layer's soundness. Both the prior and current CRITICALs share
  the same root lesson this project's `CLAUDE.md` already states for storage
  bugs: a dependency can be the vulnerable component, not just first-party
  code. This cycle also produced the review's first confirmed **fix** of a
  previously-tracked finding (#1454/#1455, superseded by a full rewrite) and
  its first confirmed **escalation** of one (#1227, now reachable by default
  in the embedded server), both surfaced only by diffing this cycle's commits
  against the standing tracker rather than re-running a generic sweep.
- **Top 3 priorities for the team:**
  1. **Add a pre-decode BSON nesting-depth guard to the Rust wire layer**
     (Finding 1). This is the one CRITICAL: an unauthenticated, single-frame,
     whole-process-crash DoS, and — unlike #995, its closest precedent — it
     cannot be fixed by a one-line arithmetic correction; it needs a small
     new depth-counting pass ahead of every `Document::from_reader` call,
     since the fix shipped upstream (`bson` 3.1.0) isn't released yet.
  2. **Bump the `pymongo` floor to `>=4.18.2` and re-lock** (tracked #1742,
     still open 24+ hours after being flagged as yesterday's sole CRITICAL).
     This remains the cheapest fix in the whole report — a one-line
     dependency change — against a CVSS-8.4 memory-corruption bug in the
     exact BSON encoder every document write path on the Python server uses.
  3. **Route the Rust PostgreSQL planner's direct `pg_query::parse(...)` call
     sites through the existing `parse_guarded`/`nesting_bound` depth check**
     (Finding 4). Unlike most of the ~30 other tracked unbounded-recursion
     instances, this one isn't a *missing* defense — it's an *existing,
     purpose-built* defense (`parse_tree`/`parse_guarded`) that a handful of
     call sites simply don't use. Wiring those ~4 confirmed-plus-reproduced
     sites (and auditing the ~9 unreviewed ones with the same shape) through
     the mechanism that already exists is a narrow, well-understood fix with
     an unusually high confidence-to-effort ratio for this bug class.

If any of the above is superseded by a fix landed after this report was
written, the next review cycle is expected to catch it via re-execution
against the oracle — per this project's own standing rule, not by re-reading
this document's claims.
