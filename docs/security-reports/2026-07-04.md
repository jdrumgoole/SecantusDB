## 🟠 WARNING (Address within 1 week)

### W1 — PG/SQL server still has no authorization (RBAC) enforcement; `GRANT`/`REVOKE`/`CREATE ROLE` now parse and succeed as pure no-ops, which risks looking like real RBAC

**Tracking:** GitHub issue [#193](../../../../issues/193) (open, filed 2026-07-03).
**Files:** `src/secantus/sql/engine.py:978-988`, `:1268-1299`, `src/secantus/sql/virtual.py:775`, `src/secantus/sql/pgserver.py:212`

This is the same gap as the 2026-07-03 report: a connected SQL client gets
unrestricted read/write on whatever database name it supplies
(`pgserver.py:212` takes the `database` startup param verbatim, with no
check against the authenticated user's roles), and `require_auth=False` is
still the default.

**What changed this cycle:** PR #200 landed `CREATE ROLE` / `CREATE USER` /
`ALTER ROLE` / `DROP ROLE` and `GRANT`/`REVOKE` *syntax*. Both `GRANT`/
`REVOKE` code paths are explicit no-ops:

```python
# engine.py:978-980
if verb in ("GRANT", "REVOKE"):
    # Role-membership / privilege grants aren't enforced — accept no-op.
    return SQLResult(command_tag=verb)
```

```python
# engine.py:983-988 (exp.Grant / exp.Revoke AST-node branch)
# Privileges aren't enforced (single-node dev surface) — accept as a no-op.
```

`CREATE ROLE`/`GRANT` write role attributes into `catalog.put_role(...)`
purely for `pg_roles`/`\du` reflection (`virtual.py:775`); nothing reads
those records back to gate a query. A grep across `src/secantus/sql/*.py`
for `has_privilege`/`check_grant`/`authorize`/`permission`/`privilege`/
`insufficient_privilege` finds zero enforcement call sites.

**Failure scenario:** a test or migration script runs `REVOKE ALL ON foo
FROM bar;` and observes it succeed, and `pg_roles`/`\du` will show a
plausible-looking role catalog — but `bar` retains full read/write on
`foo` (and every other database reachable via the connection's
client-supplied `database` param) regardless. Before this feature landed,
the absence of RBAC was an honest gap; now the surface *looks* like RBAC
exists, which is a worse trap for anyone who assumes Postgres-standard
grant semantics apply. Actual exploitability stays low for the reasons the
original report gave (ephemeral, single-tenant, in-process dev/test
surrogate, not a multi-tenant production database) — kept at WARNING, not
escalated to CRITICAL.

**Recommendation:** record this framing explicitly in `tasks/backlog.md`
(no existing entry covers it) so `GRANT`/`REVOKE` isn't mistaken for real
enforcement, and keep issue #193 open until an actual privilege-check call
site exists gating query execution.

### W2 — PG/SQL server still has no connection cap, no server-side-cursor cap/TTL, and no parser-recursion guard (three independent resource-exhaustion vectors)

**Tracking:** GitHub issue [#194](../../../../issues/194) (open, filed 2026-07-03).
**Files:** `src/secantus/sql/pgserver.py:154-160`, `src/secantus/sql/session.py:61-89`, `src/secantus/sql/planner.py:295,3945`

Re-verified live against current code; all three gaps are unchanged:

1. **No connection cap** — `pgserver.py:154-160` (`_serve_forever`) accepts
   and spawns a thread per connection unconditionally; grep confirms zero
   hits for `max_connections`/`MAX_CONNECTIONS` anywhere in `pgserver.py`,
   unlike `server.py`'s `DEFAULT_MAX_CONNECTIONS = 1000`.
2. **No server-side-cursor cap/TTL** — `Session.cursors` (`session.py:89`)
   is a plain unbounded `dict`, no TTL, no max-count check anywhere in
   `pgserver.py`/`pgextended.py`/`session.py`.
3. **No parser-recursion guard** — reproduced directly again this cycle:
   `sqlglot.parse("SELECT " + "("*300 + "1" + ")"*300 + ";", read="postgres")`
   raises an uncaught `RecursionError` against the installed
   `sqlglot==30.12.0`. `planner.parse()` has no length/depth precheck and
   no `except RecursionError`.

**Correction to the previous report's severity framing:** tracing the call
path this cycle shows `planner.parse(sql)` is invoked from
`_handle_query` (`pgserver.py:295`), *outside* that function's own
`try/except` (which starts at line 299) — so the `RecursionError` isn't
caught there, but it *is* caught one level up by `_handle_client`'s
blanket `except Exception:` (`pgserver.py:177`, since `RecursionError` is
a `RuntimeError` is an `Exception`). Net effect: the malicious query drops
only the one offending connection (logged server-side via
`logger.exception`, but with **no PG `ErrorResponse` sent to the client**
— the socket just closes) rather than crashing the whole server or
affecting other sessions. This also happens strictly *after* the startup
handshake completes, not literally pre-authentication as previously
worded — though since `require_auth=False` is the documented default, "no
auth required" and "post-handshake" collapse to the same practical
exposure. The underlying gaps (no cap, no guard, no eviction) are still
completely unpatched, so the WARNING stands; only the crash-blast-radius
description is corrected (single dropped connection with a silent
client-side hang, not a server-wide DoS).

**Recommendation:** unchanged from the prior report — add a connection cap
mirroring `DEFAULT_MAX_CONNECTIONS`; cap and idle-TTL server-side cursors
per session; cap statement length before `sqlglot.parse` and/or wrap the
call to catch `RecursionError` explicitly and return a proper
`ErrorResponse` instead of silently dropping the connection.
