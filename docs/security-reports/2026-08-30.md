## 🔴 CRITICAL (Immediate action required)

Six carried forward from 2026-08-29, re-confirmed present and unfixed, plus
**one new**:

- **#1037** — `src/secantus/query.py:874-928` (`_resolve_bitmask`): the
  `$bitsAllSet`/`$bitsAnySet`/`$bitsAllClear`/`$bitsAnyClear` array-argument
  branch still has no upper bound on the bit-position integer
  (`mask |= 1 << bit` at line 926), so an attacker-chosen multi-billion `bit`
  forces CPython to allocate and physically touch gigabytes of real memory
  while holding the GIL — wire-reachable via any `find`/`count`/
  `aggregate $match`/`update`/`delete` filter, no auth required with
  `--auth` off (the shipped default). `query.py` did not change this window.
  The Rust engine already bounds this to `0..64` and does not have the bug
  (re-confirmed this window: the new `argtypes.rs` argument-validation sweep
  does not touch bitmask logic at all — grepped for `<<`/`shift`/
  `resolve_bitmask` across the full Rust diff, zero hits). Not fixed. Issue
  **#1037** open.
- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`): a
  `message_length = -1` wire frame sign-extends to `usize::MAX` under the
  lower-bound check and still compares as a negative `i32` under the
  upper-bound check, so both guards pass; the caller's `vec![0u8; body_len]`
  aborts the whole Rust server via `handle_alloc_error` from one
  unauthenticated 16-byte frame. File unchanged this window. Not fixed.
- **#996** — `src/secantus/sql/authz.py:42-63` (`_command_privilege`): no
  `"CREATE_PROCEDURE"`/`"DROP_PROCEDURE"`/`"CALL"` branch, all three fall
  through to `return None` (no-op authorization); `plpgsql.py:789`
  (`_run_sql`) also bypasses `_dispatch`/`authz.authorize` directly for a
  procedure body. Both files unchanged this window. Not fixed.
- **#909** — `src/secantus/sql/plpgsql.py`: `_open_cursor` (line 711),
  `_run_into` (line 777), `_run_sql` (line 789, shared with #996) all call
  their engine entry points directly, none route through
  `_dispatch`/`authz.authorize`. File unchanged this window. Not fixed.
- **#947** — `src/secantus/sql/planner.py:12187` (shifted from 12149 by this
  window's `search_path`-qualification additions earlier in the file — the
  line was re-found by grep, not assumed) builds `exp.Command(this=
  "MULTIDROP_TABLE", ...)` for `DROP TABLE a, b, c`; `_command_privilege` has
  no matching branch → unauthorized multi-table drop. `planner.py` changed
  this window, but not at or near this site (confirmed by direct read); the
  construction site and `_command_privilege` itself both directly re-read and
  confirmed untouched. Not fixed.
- **#948** — `src/secantus/sql/engine.py:2849` (`_execute_statement`, shifted
  from line 2778 by this window's `search_path` additions) binds and runs a
  prepared statement directly via `_run_statement` at line 2869, bypassing
  `_dispatch` (the only call site of `authz.authorize`, confirmed by grep —
  `authz\.` appears exactly twice in the whole file, both inside `_dispatch`
  at lines 406/412); no `"EXECUTE"` branch in `_command_privilege` either
  (confirmed by direct read of `authz.py`), so `EXECUTE name` runs the bound
  statement's actual `INSERT`/`UPDATE`/`DELETE`/... unauthorized regardless of
  the underlying statement's own privilege requirement. `engine.py` changed
  this window (147 lines, all in `search_path` name-qualification and the new
  savepoint-index-restore machinery — see **W8**), but the `EXECUTE`
  dispatch chain (verb-routing at line 2647-2648, `_execute_statement` itself)
  is untouched by that diff, confirmed by direct read. Not fixed.
- **C7 (new)** — Unbounded recursion in two Rust error-message renderers,
  each newly added or newly wired to attacker/data-controlled BSON this
  window, with no depth guard anywhere in the Rust wire/BSON-decode path
  (grepped the full `crates/` tree for `max_depth`/`MAX_DEPTH`/
  `recursion_limit`/`nesting`: the only hits are `$graphLookup`'s *unrelated*
  `maxDepth` pipeline option and unrelated SQL-parser depth counters — there
  is no BSON nesting-depth cap anywhere on the Rust server):
  - `crates/secantus-commands/src/argtypes.rs:360` (`render_stage_value`)
    recurses into every nested `Bson::Array`/`Bson::Document` with no depth
    cap, and is called directly on a wire-supplied, not-yet-validated
    aggregation-stage argument from `stage_spec_error` (lines 412, 464, 482,
    496) the moment a `$limit`/`$skip`/`$count` stage's value fails its type
    check. **Trigger, no auth required, no prior state needed:** a single
    `aggregate` command with `pipeline: [{$skip: <a BSON array nested tens of
    thousands of levels deep>}]` — one 16 MB BSON document can encode far more
    array nesting than a thread stack can sustain, and the type-check that
    would reject `$skip`'s argument runs `render_stage_value` on the
    rejected value *to build the error message*, so the crash happens on the
    error path of an intentionally-malformed request.
  - `crates/secantus-core/src/update.rs:1142` (`render_value`), used by the
    new `path_not_viable_error` (line 1112), recurses the same way over a
    document read back from storage. **Trigger:** insert a document with a
    deeply nested array field (subject only to whatever the BSON decoder
    itself tolerates — no depth cap was found anywhere in the decode path
    either), then run an update whose dotted path walks into that array
    where mongod would refuse to create a field (e.g. `$set: {"a.0.x": 1}`
    where the element at `a.0` is itself a deeply nested array) — `paths::
    path_block` hands the whole nested container to `render_value` while
    building the `PathNotViable` error message.

  A Rust stack overflow aborts the whole process (`SIGSEGV`/`SIGABRT`) rather
  than unwinding through the existing `catch_unwind` wrapper in
  `secantus-server`, so both are **full, unauthenticated, single-request
  denial-of-service** on the Rust server — the same severity class as the
  already-tracked #995, and a new instance of it, not a duplicate (different
  root cause: unbounded recursion in error rendering vs. an integer
  sign-extension bug in header validation). Both call sites are new/newly
  reachable this window (`argtypes.rs` is a brand-new file; `update.rs`'s
  `path_not_viable_error` is new this window per the commit history). Not
  filed until this report lands (see "Land the report" below — a matching
  issue will be opened as part of this cycle).

  data privilege, per `authz.py`'s own docstring — `_dispatch` returns for it
  at line 387-388, *before* the `authz.authorize` call at line 406). This

  `_restore_savepoint_indexes` (line 737) calls `storage.drop_index`/
  `storage.create_index` directly, with no authorization check anywhere in
  the call chain — the same structural shape as the four standing SQL-authz
  CRITICALs above (a storage mutation reachable without going through
  `_dispatch`'s single authz gate). It does not escalate privilege the way
  those four do — reaching this path at all requires the session to already
  hold whatever DB-wide `A_CREATE_INDEX`/`A_DROP_INDEX` grant let it create

  savepoint_indexes`, line 804, only runs when the session's own,
  already-authorized index DDL triggers `_is_index_ddl`) — so this is filed
  as WARNING, not CRITICAL. What it does introduce is a **cross-session
  integrity/availability hazard**: `_capture_savepoint_indexes` snapshots
  **every table in the database**, not just the DDL statement's target
  (`catalog.list_tables(db)` at line 813 — the code comment explains this is
  because `DROP INDEX name` doesn't name its table, so per-table attribution
  isn't possible from the AST alone), so a session with index-DDL privilege
  that opens a savepoint, does one `CREATE INDEX`/`DROP INDEX` anywhere, and
  later runs `ROLLBACK TO SAVEPOINT` will silently revert *any other
  session's* concurrent, independently-authorized index DDL on tables it has
  no relationship to — entirely outside the authz path and with no audit
  trail, since the restore's own errors are swallowed (`contextlib.
  suppress(Exception)` at lines 752 and 763). A GitHub issue will be filed
  for this alongside **C7**.
