## 🟡 INFO (Best-practice recommendations)

- **The per-thread `BinDataOrder` global is a new piece of shared mutable
  state to keep straight, though not a vulnerability as implemented.**
  `crates/secantus-core/src/order.rs`'s `BINDATA_ORDER` thread-local is set
  on every thread either Rust server runs query/compare/index code on
  (`secantus-pg/src/server.rs`'s `on_thread_start` hooks on both the
  connection-acceptor and per-connection single-worker runtimes, plus
  `mark_bytea_order()` called directly before each is built;
  `portal_stream.rs`'s detached reader thread inherits its spawning
  connection's order explicitly) and restored via a `Drop` guard
  (`with_bindata_order`) everywhere it's scoped rather than set
  permanently — reviewed every call site
  (`grep -rn 'set_thread_bindata_order\|with_bindata_order'`) and found no
  thread that runs comparison/index code without it set to the right value
  for the server owning that thread, and no `Mutex`/global (it's `Cell`,
  thread-local, so no poisoning or cross-thread race is possible by
  construction). Worth flagging only because it is exactly the shape of
  thing ("which thread am I on, and did someone remember to set the flag on
  it") that regresses silently if a future PG-server thread pool is added
  without the same `on_thread_start` treatment — a code comment at the
  `BINDATA_ORDER` declaration pointing at this review would help the next
  person extending the thread model notice the invariant.
- **`index_entries_outdated`'s format-4→5 rebuild runs synchronously at
  store open**, scanning every document in every affected collection to
  re-key it (`Storage::open` → `rebuild_outdated_indexes`, confirmed by
  reading `index_entries_outdated`'s new `entryFormat` check and the
  `open_rebuilds_an_entry_format_4_index` test added this window). This is
  not attacker-reachable (open happens once, at server startup, never from a
  wire request), so it is not a DoS finding — noted only because a future
  entry-format bump that reuses this mechanism on a very large store is a
  startup-latency concern for whoever ships it, not a security one.
- The remaining carried-forward INFO notes from 2026-10-21 (stale comments
  referencing deleted workflows in `test.yml`/`publish-crates.yml`; the
  starlette CVE already clear of the pinned `1.3.1`; the unbounded
  `planCacheSetFilter` filter table; `applyOps`-of-`applyOps` recursion not
  yet independently probed; `killOp`'s lack of self-vs-other distinction
  matching mongod's own model; `validateDBMetadata`'s ignored options; the
  `rustls-pemfile` RUSTSEC-2025-0134 unmaintained-dependency pin) were
  re-checked this cycle and are unchanged — none of the referenced files or
  lines appear in this window's diff.

## 🟢 CLEAN (Passed review)

- **The `BinDataOrder` fix is a correctness change with no security
  regression.** Traced the full call chain: `secantus-core/src/order.rs`'s
  new `bindata_cmp`/`BinDataOrder`/thread-local plumbing,
  `secantus-core/src/sortkey.rs`'s entry-format-5 key encoding (with
  entry-format-4 compatibility preserved for `_id` keys via
  `BinDataOrder::Format4`, so existing stores and the deprecated Python
  servers' `_id`-key bytes are unaffected), `secantus-core/src/expressions.rs`'s
  `py_eq`/`py_order` fixes for `MinKey`/`MaxKey` equality and
  field-order-sensitive document equality, and
