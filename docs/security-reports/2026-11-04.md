## 🟠 WARNING (Address within 1 week)

### New this cycle

- **EXPLAIN's new `reduce_const_classes` (RP-350) does an uncapped O(n²)
  `Vec::contains` scan over a client-supplied flat AND chain, uninterruptible
  by `statement_timeout`.** `crates/secantus-pgplan/src/lib.rs:43830` defines
  `reduce_const_classes`, reached from `plan_explain` (`lib.rs:10047-10048`,
  gated by `!options.analyze`) for any plain `EXPLAIN` — not `EXPLAIN
  ANALYZE` — over a single-relation `SELECT`. Its `flatten()` helper
  (`lib.rs:43843-43852`) flattens the WHERE's top-level `AND` conjuncts into
  an unbounded `Vec<PNode>`, and for each of the N conjuncts the function
  tests membership in a per-column accumulator with `members.contains(&value)`
  (`lib.rs:43936`, inside the loop starting at `lib.rs:43894`) — an O(N)
  linear scan against a `Vec<Value>` that grows by one per distinct constant,
  giving O(N²) total work for a query like `EXPLAIN SELECT * FROM t WHERE
  a=1 AND a=2 AND ... AND a=N`. This is not bounded by the crate's existing
  `MAX_EXPR_DEPTH=2500`/`check_depth` nesting guard: `nesting_bound` resets
  its depth-run counter at `AND`/`OR` tokens (`lib.rs:4390`), so a *flat*
  conjunct chain never increases nesting depth regardless of its width — the
  only applicable limit is `parse_tree`'s `MAX_TEXT_BYTES = 2 MiB` statement
  cap (`lib.rs:4340`), which comfortably admits on the order of 150,000+ short
  `AND a=NNNNN` conjuncts, deep enough into the quadratic regime (~10¹⁰
  comparisons) to peg a CPU core for seconds to tens of seconds, with no
  `cancel::check()` call anywhere in the function body. Independently
  confirmed by a fresh verifier re-reading every cited line from scratch,
  including confirming reachability is in fact *narrower* than a join
  (`reduce_const_classes` itself requires a single-relation `FROM`, so a join
  never reaches this code at all). Bounded to this single local dev/test
  server (CLAUDE.md's threat model) and to the attacking connection's own
  OS thread (the server is one thread per connection), so the realistic
  effect on other sessions is CPU-contention-driven slowdown rather than a
  whole-process freeze or any data/privilege compromise — the same
  proportionate read this report's lineage gave the analogous RP-320/RP-321
  dedup finding (#2289) last cycle. **Fix:** replace the `Vec<Value>`
  membership check with a `HashSet<Value>` (O(1) lookup), and/or cap
  `parts.len()` before entering the reduction loop, falling back to treating
  the clause as ordinary/unreduced past the cap — mirroring the project's own
  `MAX_EXPR_DEPTH`-style guard pattern.
