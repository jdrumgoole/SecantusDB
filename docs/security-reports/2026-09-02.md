## 🔴 CRITICAL (Immediate action required)

Three findings, all reachable from an ordinary wire client, all already
tracked by an **open** issue from a prior cycle — re-confirmed present at
HEAD, not fixed:

- **#995** — `crates/secantus-wire/src/lib.rs:137-151` (`Header::body_len`):
  a `message_length = -1` header sign-extends to `usize::MAX` under the
  lower-bound check (cast happens *before* the sign check) and the
  upper-bound check (`message_length > MAX_MESSAGE_SIZE`, a signed `i32`
  compare) also lets a negative value through. Both guards pass, `body_len`
  returns `Ok(~1.8×10^19)`, and `crates/secantus-server/src/lib.rs:562`'s
  `vec![0u8; body_len]` triggers Rust's OOM abort — not catchable, not a
  panic, kills the whole process from one unauthenticated 16-byte frame.
  Re-verified this cycle by tracing the cast/compare order directly; file
  unchanged since the last report. **Not fixed.**

- **#1160** — `src/secantus/commands.py` (`bulkWrite` handler, registered at
  line 8580 area, no entry in `_COMMAND_ACTIONS`, dict at lines 8693-8776):
  `bulkWrite` calls `_insert`/`_update`/`_delete` directly rather than going
  through the RBAC-checked dispatch path, and has no `_COMMAND_ACTIONS`
  entry of its own — the check at `commands.py:9613-9614` (`info =
  _COMMAND_ACTIONS.get(name); if info is not None: ...`) silently *skips*
  the privilege check for any command missing from the table. A previously
  reported live exploit (user with `roles: []` under `require_auth=True`)
  confirmed the identical write succeeds via `bulkWrite` when the same op
  via `insert_one` is correctly rejected. **Not fixed.**

- **#977 (severity note — see below)** — `src/secantus/query.py:1082-1089`
  (`_MAX_REGEX_PATTERN_LEN`): `$regex` still only caps pattern *length*
  (1000 chars), with no backtracking-depth/timeout guard. This cycle's
  Python sub-review went further than the existing issue and **live-tested**
  a classic short catastrophic-backtracking pattern (`(a+)+$`) against a
  non-matching string: because CPython's `_sre` engine never releases the
  GIL mid-match, the pathological match starves **every thread in the
  process**, confirmed by showing an independent second thread — and a
  second, unrelated `pymongo` client's `ping` — both hang indefinitely while
  one connection evaluates the match. The existing issue's title
  ("CPU-pinning DoS") describes a single connection's cost; the actual
  blast radius is **the entire server**, indistinguishable in effect from
  the wire-level process-abort above. Escalated to CRITICAL here on that
  basis. **Not fixed.** A clarifying comment with the live-verified
  whole-process evidence was added to #977 rather than opening a duplicate
  issue (see "Actionable findings" below).

## 🟠 WARNING (Address within 1 week)

**New this cycle:**

- **`killSessions`/`killAllSessions`/`killAllSessionsByPattern` bypass RBAC
  entirely** — `src/secantus/commands.py:8580-8582` register the three
  handlers; none of the three names appear in `_COMMAND_ACTIONS` (lines
  8693-8776) or in `_NO_PRIVILEGE_COMMANDS` (lines 8783-8806). Because the
  privilege check at `commands.py:9613-9614` is `info =
  _COMMAND_ACTIONS.get(name); if info is not None: ...`, a command absent
  from the table is **silently exempted** rather than denied — the same bug
  shape already tracked for `bulkWrite` (#1160), `getParameter` (fixed, see
  the comment at line 8757), and lowercase `dbstats` (fixed, line 8726-8729).
  Confirmed directly by reading both tables. Effect: any authenticated user,
  regardless of role, can call `killSessions`/`killAllSessions` and abort
  arbitrary other principals' sessions and in-flight transactions —
  disruption/DoS against other tenants of the same server, not a data
  breach or privilege escalation into write access. **New issue filed.**

- **Rust `secantusd-rs` background maintenance threads have no panic
  isolation, and one already-latent bug can trigger it** —
  `crates/secantusdb/src/main.rs:197-224`'s `spawn_interval` closures (noop
  heartbeat + oplog prune; TTL sweep) are plain `thread::spawn` with no
  `catch_unwind` — the only two `catch_unwind` sites in the whole Rust
  codebase are `secantus-server/src/lib.rs:858` (per-request dispatch) and
  a test helper in `admission.rs:210`. No `panic = "abort"` profile is set
  anywhere (`grep -rn "^panic" crates/*/Cargo.toml Cargo.toml` — zero
  hits), so the default `panic = "unwind"` means a panic here does **not**
  crash the process — it silently kills that one maintenance thread with no
  log line (the `if let Err(e) = ...` arm only handles a returned `Result`,
  never a panic) while the server keeps serving client connections
  normally. TTL expiry, oplog retention, and change-stream heartbeat
  liveness stop forever, invisibly. The concrete trigger path exists today
  but is currently masked: `crates/secantus-storage/src/lib.rs:6692`
  (`Storage::prune_ttl`) does `(when_ms - v.timestamp_millis()) as f64 /
  1000.0 > *secs` on a client-supplied `DateTime` (e.g. `DateTime(i64::MIN)`
  on a TTL-indexed field is legal BSON) with unchecked `i64` subtraction —
  silently wraps under the shipped release profile (no `overflow-checks =
  true` anywhere in the workspace) rather than panicking today, but would
  become exactly this silent-forever-outage the moment any build enables
  overflow checks (debug builds, or a future profile change). Recommend (a)
  wrapping the maintenance closures in `catch_unwind` with a logged restart,
  matching the per-request dispatch pattern, and (b) `checked_sub`/
  `saturating_sub` in `prune_ttl` regardless of current profile safety.
  **New issue filed.**

- **The `#139` namespace-NUL guard doesn't cover secondary namespace
  fields** — the generic guard at `crates/secantus-commands/src/lib.rs:
  728-740` only checks `ctx.db_name` and the command's own *primary*
  first-value string; index names are separately guarded in the index
  handlers (`admin.rs:1120,1229`). It is not applied to namespace strings
  read deeper in a request body: `renameCollection`'s `to` field
  (`admin.rs:1307-1327` → `Storage::rename_collection` →
  `secantus-storage/src/lib.rs:7199`/`12498-12500`'s `set_key_ss`), `$out`'s
  target, `$merge`'s `into`, `$lookup`'s `from`, `$graphLookup`'s `from`,
  and `$unionWith`'s collection argument (all in
  `crates/secantus-commands/src/aggregate.rs`). A BSON string may legally
  contain an embedded NUL; `crates/secantus-wt/src/lib.rs:535-537`'s
  `cstr()` (`CString::new(s).expect(...)`) panics on one. Severity is
  WARNING not CRITICAL because the per-request `catch_unwind`
  (`secantus-server/src/lib.rs:858`) turns the panic into a clean `{ok:0}`
  reply and every lock in the codebase uses the poison-tolerant
  `.lock().unwrap_or_else(|e| e.into_inner())` pattern (confirmed zero bare
  `.lock().unwrap()` sites via grep) — so the connection and the process
  both survive, and no other request is affected. Net effect: six specific
  request shapes always fail with a generic error instead of mongod's
  `InvalidNamespace` (73) — a real, narrow input-validation gap and an
  inconsistent application of the existing (closed) `#139` fix. **New issue
  filed** (a fresh issue, since `#139` is closed and scoped to the sites it
  originally fixed).

- **`.github/workflows/publish.yml`'s pre-publish jobs have no `permissions:`
  block** — `verify_tag` (line 17), `build_wheels` (line 43), and
  `build_sdist` (line 149) declare no job-level `permissions:`, and the
  workflow has no top-level default either; only the final `publish` job
  (line 177) scopes `id-token: write`. These jobs run third-party build
  tooling (`cibuildwheel`, arbitrary C/Rust compilation) on a tag push, so
  they fall back to whatever the repo/org default `GITHUB_TOKEN` grant is —
  inconsistent with this repo's own stated convention, which `wheels.yml`
  and `test.yml` both comment as deliberately scoped down. Structurally the
  same gap already tracked for `rust-wheels.yml` (**#978**, open) and
  `validate.yml`'s `pgjdbc-report` job (**#910**, open) — those two are
  cited, not re-filed; `publish.yml` itself was not previously flagged.
  **New issue filed.**

- **PyPI sdist packaging gaps** — two related but distinct config issues in
  `pyproject.toml`'s `[tool.scikit-build] sdist.exclude`:
  (a) every other vendored driver-conformance gauge has a matching
  `vendor/mongo-<lang>-driver/**` + `<lang>_validation/**` exclude pair, but
  **`vendor/mongo-rust-driver/**` and `rust_validation/**` have none**
  (`grep -n "mongo-rust-driver\|rust_validation" pyproject.toml` → zero
  matches) — `publish.yml`'s `build_sdist` job checks out submodules
  recursively (line 155), so the published sdist likely bundles the full
  vendored Rust driver source plus the dev-only gauge harness, contradicting
  both `CLAUDE.md`'s "all gauge dirs are dev-only, excluded from sdist/
  wheel" and the "we don't redistribute" rationale used for every other
  driver; (b) the exclude entries for `vendor/wiredtiger/{test,bench,
  examples}/**` are dead config — scikit-build-core's `match_path()` checks
  `include_spec` before `exclude_spec`, so the broader `sdist.include =
  ["vendor/wiredtiger/**"]` always wins, and an empirical sdist build in
  this session confirmed 1352 extra files under those three directories
  ship anyway (WT's own perf scripts, `.ipynb` notebooks). Neither is
  independently exploitable, but (a) is a real redistribution-policy
  violation and (b) is misleading dead config masking the sdist's actual,
  larger size. **New issue filed** (combined — both are the same
  `sdist.exclude` block).

- **`secantus-core` PyPI dependency-confusion exposure** —
  `pyproject.toml`'s `rust` extra pins `"secantus-core==0.5.2b15"` as a
  plain PyPI dependency (line 138), but `https://pypi.org/pypi/secantus-core
  /json` returns **404** — the name is not registered on PyPI under any
  spelling checked (`secantus-core`, `secantuscore`, `secantus_core`).
  `[tool.uv.sources]` overrides this locally for `uv`-based installs, but a
  plain `pip install "SecantusDB[rust]"` would either fail resolution or —
  worse, if anyone ever registers that name on PyPI first — silently
  install an attacker-controlled package satisfying the pin. Blast radius
  is limited (the shipping base wheel never pulls the `rust` extra, per
  `CLAUDE.md`), but the exposure is real, current, and unmitigated by any
  placeholder registration. **New issue filed.**
